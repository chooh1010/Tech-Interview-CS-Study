**내 답변**

``` 
알고리즘을 평가할떄 사용하는 지표로 시간 복잡도와 공간복잡도를 판단하는데 
그 중 시간 복잡도는 알고리즘의 수행시간을 평가하는 지표이고
공간복잡도는 알고리즘을 수행하기 위한 메모리의 크기(양)을 평가하는 지표입니다. 
```

**꼬리 질문 답변**

- Big-O, Big-Theta, Big-Omega 에 대해 설명해 주세요.
```
세 표기법 모두 함수의 점근적(asymptotic) 증가율을 표현하며, 차이는 "어떤 경계를 보장하느냐"이다.

- Big-O (O) — 상한(upper bound). 아무리 나빠도 이 정도 이상 걸리지 않는다는 보장. 보통 최악의 경우(worst case)를 나타낼 때 사용.
  예: 삽입 정렬은 O(n²) → 아무리 나빠도 n²을 넘지 않음.
- Big-Omega (Ω) — 하한(lower bound). 아무리 좋아도 최소 이 정도는 걸린다는 보장. 보통 최선의 경우(best case)를 나타낼 때 사용.
  예: 삽입 정렬은 이미 정렬된 배열이면 Ω(n).
- Big-Theta (Θ) — 상한과 하한이 같을 때(tight bound). O와 Ω가 동일한 함수로 수렴하는 경우, 정확히 이 정도 걸린다고 말할 수 있음.
  예: 병합 정렬은 최선/평균/최악 모두 n log n이므로 Θ(n log n).
```

- 다른 것을 사용하지 않고, Big-O를 사용하는 이유가 있을까요?
```
엔지니어링 관점에서는 "최악의 경우"가 가장 중요하기 때문이다. 시스템을 설계할 때는 평균적으로 얼마나 빠른지보다,
가장 나쁜 입력이 들어왔을 때도 시스템이 버틸 수 있는지가 더 중요하다 (SLA, 응답시간 보장 등).

Big-O는 안전한 상한을 제시하므로 성능을 보수적으로 예측하고 대비할 수 있다. Ω(최선의 경우)만 보고 설계하면
실제 최악의 상황에서 문제가 생길 수 있다.

또한 Θ는 항상 구할 수 있는 게 아니다. 최선과 최악의 경우가 다른 알고리즘(퀵 정렬 등)에서는 정확한 Θ를 정의하기
어려운 경우가 많아, 실용적으로 상한선인 O만 명시하는 경우가 많다.
```

- O(1)은 O(N^2) 보다 무조건적으로 빠른가요?
```
아니다. Big-O는 점근적(asymptotic) 개념으로, 입력 크기 n이 충분히 커질 때의 증가 추세를 나타내는 것이지
특정 입력값 하나에서의 절대적인 속도 비교가 아니다.

또한 Big-O 표기법은 상수 계수를 생략한다. 예를 들어 O(1)이 실제로는 1,000,000번의 연산이 걸리고,
O(n²)이 0.001 * n²번의 연산이 걸린다면, n이 작을 때는 O(n²) 쪽이 더 빠를 수 있다.

실제로 퀵 정렬(O(n log n))이 이론적으로 삽입 정렬(O(n²))보다 낫지만, n이 작을 때(보통 10~20 이하)는
삽입 정렬이 실제로 더 빠르다. 그래서 Timsort, IntroSort 같은 하이브리드 정렬은 작은 구간에서 삽입 정렬로 전환한다.

결론적으로 Big-O는 "n이 무한히 커질 때 누가 더 느리게 증가하는가"를 보장하는 것이지, "이 순간 이 입력에서
누가 더 빠른가"를 보장하지 않는다.
```

**핵심 키워드** → 
시간복잡도 / 공간복잡도 — 알고리즘의 수행시간·메모리 사용량을 평가하는 지표
점근적 표기법(Asymptotic Notation) — 입력 크기 n이 커질 때의 증가 추세를 나타냄
Big-O (상한) / Big-Ω (하한) / Big-Θ (상한=하한, tight bound)
최악의 경우(worst case) 기준 — 엔지니어링에서 Big-O를 주로 쓰는 이유
상수 계수 생략(constant factor) — Big-O는 계수를 무시하므로 절대적 속도 비교가 아님


**막힌 부분 / 다시 볼 것** → 점근적 표기법에 대한 설명, Big-theta의 정의(평소에는 쓰이지 않는 개념이라 생소)

#### 2. 링크드 리스트에 대해 설명해 주세요.

`★☆☆` · `필수` · 원본 [자료구조·알고리즘 #2](../01-DATA_STRUCTURE_ALGORITHM.md)

<details>
<summary><b>꼬리 질문 5개 (펼치기)</b></summary>

- 일반 배열과, 링크드 리스트를 비교해 주세요.
- 동적 배열(ex. Java의 ArrayList)은 일반 배열, 링크드 리스트와 각각 어떤 차이를 갖나요?
- 리스트에서 인덱스가 아닌 "값"으로 데이터를 찾는다면, 시간복잡도는 어떻게 되나요?
- 그 리스트가 정렬되어 있다는 조건이 붙는다면, 시간복잡도는 어떻게 달라질까요? 링크드 리스트여도 마찬가지일까요?
- 링크드 리스트를 사용해서 구현할 수 있는 다른 자료구조에 대해 설명해 주세요.

</details>

**내 답변**

```
링크드 리스트는 데이터를 노드(Node) 단위로 저장하고, 각 노드가 다음(또는 이전) 노드를 가리키는 포인터를 가지는
선형 자료구조입니다. 배열과 달리 메모리 상에 연속적으로 저장되지 않고, 노드들이 포인터로 흩어져 연결되어 있습니다.

포인터 방향에 따라 단일 연결 리스트(Singly), 이중 연결 리스트(Doubly), 원형 연결 리스트(Circular)로 나뉩니다.

가장 큰 특징은, 삽입/삭제 시 해당 위치의 포인터만 바꾸면 되기 때문에(위치를 이미 알고 있다면) O(1)에 가능하다는
점입니다. 대신 특정 위치에 접근(인덱스 접근)하려면 head부터 순차적으로 따라가야 하므로 O(n)이 걸리고,
Random Access가 불가능합니다.
```

**꼬리 질문 답변**

- 일반 배열과, 링크드 리스트를 비교해 주세요.
```
- 메모리 구조: 배열은 연속된 메모리 공간을 사용하고, 링크드 리스트는 노드들이 메모리 여기저기 흩어져 포인터로 연결됨
- 접근(access): 배열은 인덱스로 O(1) 접근 가능. 링크드 리스트는 순차 접근만 가능해 O(n)
- 삽입/삭제: 배열은 중간에 삽입/삭제 시 뒤 요소들을 이동해야 해서 O(n). 링크드 리스트는 위치(노드)를 이미 알고
  있다면 포인터만 변경하면 되므로 O(1)
- 크기: 정적 배열은 크기가 고정, 링크드 리스트는 필요할 때마다 노드를 동적으로 할당해 유연함
- 캐시 지역성(cache locality): 배열은 연속 메모리라 캐시 히트율이 높아 실제 성능이 좋은 경우가 많고,
  링크드 리스트는 메모리가 분산돼 있어 캐시 미스가 잦아 이론적 복잡도보다 실제 성능이 떨어질 수 있음
```

- 동적 배열(ex. Java의 ArrayList)은 일반 배열, 링크드 리스트와 각각 어떤 차이를 갖나요?
```
- 배열과의 차이: 일반(정적) 배열은 크기가 고정이지만, 동적 배열은 크기가 가변적입니다. 인덱스 접근은 둘 다 O(1).
- 링크드 리스트와의 차이: 동적 배열은 여전히 연속 메모리를 사용하므로 캐시 지역성이 좋고 포인터 오버헤드가 없지만,
  중간 삽입/삭제는 뒤 요소를 이동해야 해서 O(n)입니다. 링크드 리스트는 포인터 오버헤드와 캐시 미스가 있지만
  위치를 알고 있는 삽입/삭제는 O(1)입니다.
```

- 리스트에서 인덱스가 아닌 "값"으로 데이터를 찾는다면, 시간복잡도는 어떻게 되나요?
```
정렬되어 있지 않다면 배열이든 링크드 리스트든 처음부터 끝까지 순회하며 값을 비교해야 하므로 둘 다 O(n)입니다.
배열이 인덱스 접근은 O(1)이지만, "값 찾기"는 인덱스를 모르는 상태에서 순회가 필요하므로 이 경우엔 이점이 없습니다.
```

- 그 리스트가 정렬되어 있다는 조건이 붙는다면, 시간복잡도는 어떻게 달라질까요? 링크드 리스트여도 마찬가지일까요?
```
배열이 정렬되어 있다면 이진 탐색(Binary Search)을 사용할 수 있어 O(log n)으로 줄어듭니다. 이진 탐색이
가능한 이유는 배열이 Random Access(임의의 인덱스에 O(1) 접근)를 지원하기 때문입니다.

링크드 리스트는 정렬되어 있어도 중간 노드에 바로 접근할 방법이 없기 때문에(Random Access 불가) 이진 탐색을
쓸 수 없고, 여전히 순차 탐색 O(n)에 머무릅니다. 다만 "찾는 값이 없다"는 조기 종료는 정렬 덕분에 평균적으로
더 빨리 판단할 수 있습니다. (참고로 Skip List처럼 링크드 리스트에 여러 층의 포인터를 추가하면 O(log n)에
근접한 탐색이 가능한 변형 구조도 있습니다.)
```

- 링크드 리스트를 사용해서 구현할 수 있는 다른 자료구조에 대해 설명해 주세요.
```
- 스택 / 큐 / 덱(Deque): head(또는 head, tail 둘 다)에서 삽입·삭제만 하면 되므로 O(1) push/pop 구현 가능
- 해시 테이블의 체이닝(Separate Chaining): 같은 버킷에 충돌한 값들을 링크드 리스트로 연결해 저장
- 그래프의 인접 리스트(Adjacency List): 각 정점마다 연결된 정점들을 링크드 리스트로 관리
- LRU 캐시: 이중 연결 리스트(사용 순서 유지) + 해시맵(O(1) 접근)을 결합해서 구현
```

**핵심 키워드** → 노드(Node)·포인터, 단일/이중/원형 연결 리스트, Random Access 불가(순차 접근만 가능), 삽입·삭제 O(1) vs 인덱스 접근 O(n), 캐시 지역성(Cache Locality)·캐시 미스, 동적 배열(ArrayList)의 상각(amortized) O(1), 정렬돼도 이진 탐색 불가, 활용 사례(체이닝·인접 리스트·LRU 캐시)

**막힌 부분 / 다시 볼 것** → 활용 사례부분 복습(해시 테이블 체이닝, 인접 리스트, LRU캐쉬 등)

**내 답변**

```
스택(Stack)은 마지막에 들어간 데이터가 가장 먼저 나오는 LIFO(Last In First Out) 구조입니다. 한쪽 끝(top)에서만
삽입(push)·삭제(pop)가 일어나며, 배열이나 링크드 리스트 어느 쪽으로 구현해도 push/pop/peek 모두 O(1)입니다.

큐(Queue)는 먼저 들어간 데이터가 먼저 나오는 FIFO(First In First Out) 구조입니다. 삽입은 뒤(rear)에서,
삭제는 앞(front)에서 일어나며, 이 역시 O(1)에 처리할 수 있습니다.

두 구조 모두 임의의 위치에 접근하는 것이 아니라 정해진 한쪽(또는 양쪽) 끝에서만 데이터를 다루기 때문에,
"삽입 순서"와 "처리 순서"의 관계를 표현하는 데 특화된 자료구조입니다. 스택은 재귀 호출 스택, 실행 취소(Undo),
괄호 짝 검사 등에, 큐는 작업 대기열, BFS 탐색, 프린터 스풀 등에 사용됩니다.
```

**꼬리 질문 답변**

- 스택 2개로 큐를, 큐 2개로 스택을 만드는 방법과, 그 시간복잡도에 대해 설명해 주세요.
```
[스택 2개로 큐 구현]
inStack(입력용), outStack(출력용) 두 개를 둡니다.
- enqueue(x): 항상 inStack에 push → O(1)
- dequeue(): outStack이 비어있으면, inStack의 모든 원소를 pop해서 outStack에 push(순서가 뒤집혀
  가장 먼저 들어온 게 outStack의 top으로 옴). 그 다음 outStack에서 pop → 그 회차만 O(n),
  outStack에 값이 남아있는 동안의 dequeue는 O(1)
- 원소 하나는 평생 최대 두 번(in→out) 이동하므로, 상각 분석(amortized) 기준으로는 dequeue도 O(1)

[큐 2개로 스택 구현]
q1, q2 두 개를 두고, 매번 새로 들어오는 값을 기준으로 순서를 뒤집는 방식입니다.
- push(x): q2에 x를 넣고, 그 다음 q1에 있던 기존 원소들을 순서대로 꺼내 q2 뒤에 붙임 → q1, q2 이름을 스왑
  (결과적으로 방금 넣은 x가 항상 큐의 맨 앞에 위치) → O(n)
- pop(): q1의 front를 그대로 꺼내면 됨 → O(1)
(반대로 push를 O(1)로 하고 pop을 O(n)으로 설계할 수도 있습니다. 어느 한쪽은 반드시 O(n)이 필요합니다.)
```

- 시간복잡도를 유지하면서, 배열로 스택과 큐를 구현할 수 있을까요?
```
스택은 배열 + top 인덱스만으로 자연스럽게 O(1) push/pop이 됩니다(맨 뒤에서만 다루므로).

큐는 배열의 앞(front)에서 원소를 빼는 방식으로 단순 구현하면, 남은 원소를 앞으로 한 칸씩 당겨야 해서
dequeue가 O(n)이 됩니다. 이를 피하려면 원형 버퍼(Circular Array/Circular Buffer)를 사용합니다.
front, rear 두 인덱스를 두고 배열 끝에 도달하면 (index + 1) % capacity 로 다시 처음으로 되돌아가게
만들면, 요소 이동 없이 enqueue/dequeue 모두 O(1)을 유지할 수 있습니다. (용량이 가득 찼을 때만 더 큰
배열로 재할당하면 되고, 이 비용은 상각 분석상 O(1)입니다.)
```

- Prefix, Infix, Postfix 에 대해 설명하고, 이를 스택을 활용해서 계산/하는 방법에 대해 설명해 주세요.
```
- Infix(중위): 연산자가 피연산자 사이에 위치 (a + b). 사람이 읽기 편하지만, 계산 순서를 정하려면
  연산자 우선순위와 괄호가 필요합니다.
- Prefix(전위): 연산자가 피연산자 앞에 위치 (+ a b). 괄호 없이도 계산 순서가 모호하지 않습니다.
- Postfix(후위): 연산자가 피연산자 뒤에 위치 (a b +). 역시 괄호가 필요 없고, 스택만으로 바로 계산할
  수 있어 컴퓨터(계산기, 컴파일러)가 다루기 편합니다.

[스택을 이용한 Postfix 계산]
왼쪽부터 토큰을 하나씩 읽으면서
1) 피연산자(숫자)면 스택에 push
2) 연산자를 만나면 스택에서 두 번 pop(먼저 나온 게 오른쪽 피연산자)해서 연산을 수행하고, 그 결과를 다시 push
모든 토큰을 다 읽고 나면 스택에 결과값 하나만 남습니다.

[Infix → Postfix 변환]
Shunting-yard 알고리즘처럼, 연산자용 스택을 따로 두고 우선순위를 비교하며 스택에 쌓인 연산자를
언제 출력(pop)할지 결정해 Postfix 순서로 재배열합니다.
```

- Deque는 어떻게 구현할 수 있을까요?
```
- 배열 기반: 원형 버퍼(circular buffer)를 사용하되, front와 rear 양쪽 모두에서 삽입/삭제가 가능하도록
  두 인덱스를 앞뒤로 모두 이동시킬 수 있게 구현. capacity가 부족하면 재할당.
- 링크드 리스트 기반: 이중 연결 리스트(Doubly Linked List)를 사용해 head, tail 양쪽에 포인터를 두면
  양쪽 끝 삽입/삭제 모두 포인터 갱신만으로 O(1)에 처리 가능.
```

- (C++ 한정) Deque의 Random Access 시간복잡도는 O(1) 입니다. 이게 어떻게 가능한걸까요?
```
C++의 std::deque는 하나의 연속된 배열이 아니라, 고정 크기의 청크(chunk/block) 여러 개를 가리키는
포인터 배열(map)로 구성됩니다. 각 청크는 정해진 개수의 원소를 담는 작은 배열입니다.

임의의 인덱스 i에 접근할 때는 (몫, 나머지) = (i / 청크크기, i % 청크크기) 연산으로 "몇 번째 청크의
몇 번째 원소인지"를 바로 계산할 수 있기 때문에 O(1)입니다.

이 구조 덕분에 양쪽 끝에 새로운 청크를 추가하는 방식으로 확장할 수 있어, 앞/뒤 삽입도 기존 원소를
이동시키지 않고 O(1)(상각 기준)에 처리할 수 있습니다. 대신 중간 삽입/삭제는 여전히 O(n)이고, 배열처럼
완전히 연속된 메모리가 아니라서 순수 배열보다는 캐시 지역성이 약간 떨어집니다.
```

**내 답변**

```
해시 테이블은 키(key)를 해시 함수에 넣어 나온 값을 배열의 인덱스로 사용해서 데이터를 저장하는 자료구조입니다.
평균적으로 삽입·탐색·삭제 모두 O(1)에 처리할 수 있다는 게 가장 큰 특징입니다(순차 탐색이 필요 없기 때문).

구성 요소는 크게 세 가지입니다.
1) 내부에 값을 담는 배열(버킷 배열)
2) 키를 배열 인덱스로 변환하는 해시 함수
3) 서로 다른 키가 같은 인덱스로 매핑됐을 때(충돌) 이를 처리하는 정책

평균 O(1)이라는 성능은 해시 함수가 값을 얼마나 고르게 분산시키는지, 그리고 충돌을 얼마나 잘 처리하는지에
크게 의존합니다. 최악의 경우(모든 키가 한 버킷에 몰리는 경우)엔 O(n)까지 저하될 수 있습니다.
```

**꼬리 질문 답변**

- 값이 주어졌을 때, 어떻게 하면 충돌이 최대한 적은 해시 함수를 설계할 수 있을까요?
```
좋은 해시 함수가 갖춰야 할 조건은 다음과 같습니다.
- 결정성(Deterministic): 같은 입력에는 항상 같은 해시값을 반환해야 함
- 균등 분포(Uniform Distribution): 가능한 모든 버킷에 값이 고르게 퍼지도록 해서 특정 버킷에 몰리지 않게 함
- 눈사태 효과(Avalanche Effect): 입력값이 아주 조금만 바뀌어도 출력 해시값은 크게 달라져야 함 (비슷한 키가
  비슷한 해시값을 가지면 특정 구간에 몰릴 위험이 커짐)
- 빠른 계산: 해시 함수 자체가 O(1)에 가깝게 가벼워야 전체 성능 이점이 사라지지 않음

실무적으로는 테이블 크기를 소수(prime number)로 두고 나머지 연산을 하거나, MurmurHash·FNV 같이 검증된
비암호화 해시 함수를 사용해 충돌 확률을 낮춥니다. 보안이 중요한 경우(해시 플러딩 공격 방지)에는 매번
랜덤한 시드(salt)를 섞어 공격자가 해시 충돌을 의도적으로 유발하지 못하게 합니다.
```

- 해시값이 충돌했을 때, 어떤 방식으로 처리할 수 있을까요?
```
크게 두 갈래로 나뉩니다.

1) Separate Chaining (분리 연결법)
   같은 버킷에 충돌한 값들을 링크드 리스트(또는 트리)로 연결해서 저장. 구현이 단순하고 Load Factor가
   1을 넘어도 동작하지만, 체인이 길어지면 탐색 성능이 저하됨(최악 O(n)).

2) Open Addressing (개방 주소법)
   충돌이 나면 정해진 규칙에 따라 배열 내 다른 빈 슬롯을 찾아 저장.
   - Linear Probing: 충돌 시 다음 칸(index+1)을 순서대로 확인. 구현은 간단하지만 클러스터링(값이
     한 구간에 뭉치는 현상)이 발생하기 쉬움
   - Quadratic Probing: 충돌 시 index + 1², index + 2² ... 식으로 제곱수만큼 건너뛰며 확인.
     클러스터링을 완화하지만 여전히 특정 패턴에 몰릴 수 있음
   - Double Hashing: 두 번째 해시 함수로 건너뛸 간격(step)을 계산. 클러스터링을 가장 잘 완화함
   Open Addressing은 삭제 시 슬롯을 그냥 비우면 탐색 체인이 끊기므로, "삭제됨" 표시(tombstone)를
   남기는 방식으로 처리해야 함
```

- 본인이 사용하는 언어에서는, 어떤 방식으로 해시 충돌을 처리하나요?
```
(사용 언어에 맞게 채워 넣기)
예) Java의 HashMap: 기본적으로 Separate Chaining(링크드 리스트) 방식을 사용하고, 하나의 버킷에 몰린
    노드 수가 임계치(TREEIFY_THRESHOLD = 8)를 넘고 테이블 전체 크기도 충분히 크면(64 이상), 그 버킷의
    링크드 리스트를 레드-블랙 트리로 변환해 최악의 경우도 O(log n)까지 개선합니다.
예) Python의 dict: Open Addressing 방식(의사 난수 기반 probing)을 사용합니다.
예) C++의 std::unordered_map: 반복자/참조 안정성을 보장해야 하는 표준 요구사항 때문에 대부분 구현체가
    Separate Chaining 방식을 사용합니다.
```

- Double Hashing 의 장점과 단점에 대해서 설명하고, 단점을 어떻게 해결할 수 있을지 설명해 주세요.
```
[장점]
두 번째 해시 함수로 충돌 시 건너뛸 간격(step)을 계산하기 때문에, Linear/Quadratic Probing보다
클러스터링이 훨씬 적고 값이 테이블 전체에 고르게 분산됩니다.

[단점]
- 해시 함수를 두 번 계산해야 하므로 연산 비용이 더 큼
- 두 번째 해시 함수가 0을 반환하면 같은 자리만 계속 확인하게 되어 무한루프(제자리 반복)에 빠질 위험
- 두 번째 해시 함수의 결과와 테이블 크기의 최대공약수(gcd)가 1이 아니면, 전체 슬롯을 다 순회하지 못하고
  일부 슬롯만 맴도는 문제가 생김 (예: step=2, 테이블크기=10이면 짝수 인덱스만 방문)

[해결 방법]
- 두 번째 해시 함수가 절대 0을 반환하지 않도록 설계 (예: step = 1 + (key % (m-1)))
- 테이블 크기(m)를 소수(prime number)로 잡으면, step 값이 무엇이든 gcd(step, m) = 1이 보장되어
  probing 순서가 테이블 전체 슬롯을 빠짐없이 순회할 수 있음
```

- Load Factor에 대해 설명해 주세요. 본인이 사용하는 언어에서의 해시 자료구조는 Load Factor에 관련한 정책이 어떻게 구성되어 있나요?
```
Load Factor(적재율) = 저장된 원소 개수(n) / 버킷(테이블) 크기(m)

Load Factor가 높아질수록 충돌 확률이 커지고, Separate Chaining의 체인이 길어지거나 Open Addressing에서
빈 슬롯을 찾기까지 더 많이 탐색해야 해서 성능이 O(1)에서 점점 O(n)에 가까워집니다.

그래서 대부분의 해시 자료구조는 Load Factor가 특정 임계값을 넘으면 테이블 크기를 늘리고(보통 2배),
기존 원소들을 새 테이블에 다시 배치하는 리사이징(rehashing)을 수행합니다. 이 재해싱 비용(O(n))은
자주 발생하지 않으므로 삽입 연산은 상각 분석 기준 O(1)을 유지합니다.

예) Java HashMap: 기본 Load Factor는 0.75. 원소 수가 (테이블 크기 × 0.75)를 넘으면 테이블 크기를
    2배로 늘리고 재해싱합니다. (생성자에서 초기 용량·load factor를 직접 지정할 수도 있음)
```

- 다른 자료구조와 비교하여, 해시 테이블은 멀티스레드 환경에서 심각한 수준의 Race Condition 문제에 빠질 위험이 있습니다. 성능 감소를 최소화 한 채로 해당 문제를 해결할 수 있는 방법을 설계해 보세요.
```
[왜 위험한가]
여러 스레드가 동시에 같은 버킷에 삽입하거나, 리사이징(rehashing) 도중 다른 스레드가 테이블을 읽고
쓰면 링크드 리스트 구조가 깨지거나 데이터가 유실될 수 있습니다. (실제로 Java 7의 HashMap은 멀티스레드
환경에서 resize 중 링크드 리스트가 순환 구조가 되어 무한루프에 빠지는 유명한 버그가 있었습니다.)

가장 단순한 해결책은 테이블 전체에 하나의 락(lock)을 거는 것이지만, 이러면 모든 스레드가 순차적으로만
접근 가능해져 사실상 멀티스레드의 이점이 사라집니다.

[성능 감소를 최소화하는 설계]
1) Lock Striping(락 분할): 테이블 전체가 아니라, 버킷을 여러 구간(세그먼트)으로 나누고 구간별로
   별도의 락을 둡니다. 서로 다른 구간에 접근하는 스레드끼리는 동시에 진행할 수 있어 경합이 줄어듭니다.
   (Java 7의 ConcurrentHashMap이 Segment 단위 락으로 이 방식을 사용)
2) 버킷(Bin) 단위의 세밀한 락: 세그먼트보다 더 잘게, 각 버킷(연결 리스트의 head)마다 락을 겁니다.
   같은 버킷이 아니면 락 경합이 거의 없습니다.
3) CAS(Compare-And-Swap) 기반 무잠금(lock-free) 삽입: 빈 버킷에 처음 삽입할 때는 락 없이
   CAS 연산으로 원자적으로 삽입을 시도하고, 실패(이미 다른 값이 들어감)했을 때만 락을 겁니다.
   (Java 8 ConcurrentHashMap이 이 방식: 버킷이 비어있으면 CAS, 충돌 시에만 해당 버킷을 synchronized)
4) 읽기 연산은 락 없이(lock-free) volatile 읽기로 처리: 쓰기 스레드와 읽기 스레드가 겹쳐도
   읽기는 항상 락을 타지 않게 해서 읽기가 많은 워크로드에서 성능을 크게 개선

결론적으로 "테이블 전체에 하나의 락" 대신 "락의 범위를 최대한 잘게 쪼개고, 가능한 경우는 락 없이
원자적 연산(CAS)으로 처리"하는 것이 성능 저하를 최소화하는 핵심 전략입니다.
```

**핵심 키워드** → 해시 함수(결정성·균등분포·눈사태효과), 충돌 처리: Separate Chaining vs Open Addressing(Linear/Quadratic/Double Hashing), Load Factor·리사이징(rehashing)과 상각 O(1), 언어별 구현(Java HashMap 체이닝+트리화, Python dict open addressing, C++ unordered_map 체이닝), 동시성 문제와 해결(Lock Striping, CAS 기반 lock-free, Java 8 ConcurrentHashMap)

#### 5. 트리와 이진트리, 이진탐색트리에 대해 설명해 주세요.

`★★☆` · `필수` · 원본 [자료구조·알고리즘 #5](../01-DATA_STRUCTURE_ALGORITHM.md)

<details>
<summary><b>꼬리 질문 6개 (펼치기)</b></summary>

- 그래프와 트리의 차이가 무엇인가요?
- 이진탐색트리에서 중위 탐색을 하게 되면, 그 결과는 어떤 의미를 가지나요?
- 이진탐색트리의 주요 연산에 대한 시간복잡도를 설명하고, 왜 그런 시간복잡도가 도출되는지 설명해 주세요.
- 이진탐색트리의 한계점에 대해 설명해주세요.
- 이진탐색트리의 값 삽입, 삭제 방법에 대해 설명하고, 어떤식으로 값을 삽입하면 편향이 발생할까요?
- 이진탐색트리와 동일한 로직을 사용하면, 삼진탐색트리도 정의할 수 있을까요? 안 된다면, 그 이유에 대해 설명해 주세요.

</details>

**내 답변**

```
트리(Tree)는 노드와 간선으로 구성된 계층적 비선형 자료구조입니다. 하나의 루트에서 시작해 부모-자식 관계로
뻗어나가며, 사이클이 없다는 특징이 있습니다.

이진트리(Binary Tree)는 각 노드가 최대 2개의 자식(왼쪽/오른쪽)만 가질 수 있는 트리입니다.

이진탐색트리(BST)는 이진트리에 "정렬 속성"을 추가한 구조입니다. 모든 노드에 대해 왼쪽 서브트리의 값은
모두 그 노드보다 작고, 오른쪽 서브트리의 값은 모두 그 노드보다 크다는 규칙을 만족합니다. 이 속성 덕분에
탐색할 때마다 후보군을 절반씩 줄여나갈 수 있어, 트리가 균형 잡혀 있다면 탐색·삽입·삭제가 평균 O(log n)에
가능합니다.
```

**꼬리 질문 답변**

- 그래프와 트리의 차이가 무엇인가요?
```
트리는 그래프의 특수한 형태입니다. 트리가 만족해야 하는 조건은:
- 사이클이 없다(Acyclic)
- 모든 노드가 연결되어 있다(Connected)
- 노드가 N개면 간선은 정확히 N-1개다
- 루트가 있고, 부모-자식이라는 계층 구조가 명확하다

그래프는 이런 제약이 없습니다. 사이클이 있을 수 있고, 방향/무방향 둘 다 가능하며, 전체가 연결되어
있지 않아도 되고(여러 컴포넌트로 나뉠 수 있음), 루트라는 개념 자체가 없습니다.
```

- 이진탐색트리에서 중위 탐색을 하게 되면, 그 결과는 어떤 의미를 가지나요?
```
중위 순회(In-order Traversal, 왼쪽 → 루트 → 오른쪽 순서로 방문)를 하면, 오름차순으로 정렬된 값의
목록이 그대로 나옵니다. BST의 "왼쪽 < 루트 < 오른쪽" 속성이 모든 노드에서 재귀적으로 성립하기 때문에,
왼쪽 서브트리를 먼저 다 방문하고 루트, 그다음 오른쪽 서브트리를 방문하면 자연스럽게 정렬된 순서가 됩니다.
```

- 이진탐색트리의 주요 연산에 대한 시간복잡도를 설명하고, 왜 그런 시간복잡도가 도출되는지 설명해 주세요.
```
탐색·삽입·삭제 모두 평균적으로 O(log n)입니다(트리가 균형 잡혀 있다는 전제 하에).

이유: 매 단계마다 찾는 값과 현재 노드를 비교해서 왼쪽 또는 오른쪽, 둘 중 한쪽 서브트리로만 이동하면
됩니다. 즉 한 번 비교할 때마다 탐색해야 할 후보 노드 수가 절반으로 줄어듭니다. n개의 노드를 절반씩
줄여나가는 횟수는 log₂n번이므로, 트리의 높이(h)만큼만 내려가면 되고 균형 트리에서 h = O(log n)입니다.

다만 이는 트리가 균형 잡혀 있을 때의 이야기이고, 편향된 트리에서는 높이가 O(n)까지 늘어나
최악의 경우 O(n)이 됩니다.
```

- 이진탐색트리의 한계점에 대해 설명해주세요.
```
가장 큰 한계는 "균형을 보장하지 않는다"는 점입니다. 데이터가 삽입되는 순서에 따라 트리가 한쪽으로
치우칠 수 있고, 극단적인 경우(예: 정렬된 순서로 계속 삽입) 트리가 사실상 링크드 리스트 형태가 되어
모든 연산이 O(n)까지 저하됩니다. 이 한계를 해결하기 위해 삽입/삭제 후 스스로 균형을 재조정하는
BBST(AVL Tree, Red-Black Tree 등)가 등장했습니다.
```

- 이진탐색트리의 값 삽입, 삭제 방법에 대해 설명하고, 어떤식으로 값을 삽입하면 편향이 발생할까요?
```
[삽입]
루트부터 시작해서 삽입할 값과 현재 노드를 비교하며 왼쪽/오른쪽으로 내려가다가, 자식이 없는 위치(리프
자리)에 도달하면 그 자리에 새 노드를 연결합니다.

[삭제] 세 가지 경우로 나뉩니다.
1) 삭제할 노드가 리프(자식 없음): 그냥 부모와의 연결을 끊고 제거
2) 자식이 1개: 삭제할 노드의 자리에 그 자식을 그대로 끌어올림
3) 자식이 2개: 오른쪽 서브트리에서 가장 작은 값(또는 왼쪽 서브트리에서 가장 큰 값)을 찾아 그 값으로
   현재 노드를 대체한 뒤, 원래 그 값을 가지고 있던 노드(자식이 최대 1개인 상태)를 삭제

[편향이 발생하는 경우]
값을 이미 정렬된 순서(오름차순 또는 내림차순)로 계속 삽입하면, 매번 한쪽 방향(예: 오른쪽)으로만
자식이 붙게 되어 트리가 한쪽으로 완전히 치우친 링크드 리스트 형태가 됩니다.
```

- 이진탐색트리와 동일한 로직을 사용하면, 삼진탐색트리도 정의할 수 있을까요? 안 된다면, 그 이유에 대해 설명해 주세요.
```
개념적으로는 정의할 수 있습니다. 각 노드가 최대 3개의 자식을 갖고, 이를 구분하려면 노드마다 2개의
기준값(key1, key2)을 두어 "key1보다 작음 / key1과 key2 사이 / key2보다 큼" 3구간으로 나누면 됩니다.

다만 실용성이 떨어집니다. 노드마다 저장해야 하는 키가 2개로 늘어나 구현이 복잡해지고, 비교 연산
기반 탐색에서는 "한 번 비교(2지 분기)"가 정보 이론적으로 가장 효율적인 단위입니다(한 번의 비교로
얻을 수 있는 정보량이 이진 분기에 최적화되어 있음). 그래서 일반적인 삼진탐색트리는 잘 쓰이지 않습니다.

참고로 이름이 비슷한 Ternary Search Tree(TST)라는 자료구조가 실제로 존재하는데, 이는 값 전체를
비교하는 구조가 아니라 문자열의 문자 하나하나를 노드로 두고 (작음/같음/큼) 3방향으로 분기하는,
문자열 검색에 특화된 전혀 다른 자료구조입니다.
```

**핵심 키워드** → 트리 vs 그래프(사이클 없음·N-1개 간선), 이진트리 vs 이진탐색트리(왼쪽<루트<오른쪽), 중위 순회(In-order)로 정렬된 결과 획득, 탐색·삽입·삭제 평균 O(log n)/최악 O(n)(편향 시), 삭제 3가지 경우(리프·자식1개·자식2개), 정렬된 순서 삽입 시 편향(링크드 리스트화), 삼진탐색트리의 비실용성 vs Ternary Search Tree(TST, 문자열 특화 별개 구조)

#### 6. 힙에 대해 설명해 주세요.

`★★☆` · `필수` · 원본 [자료구조·알고리즘 #6](../01-DATA_STRUCTURE_ALGORITHM.md)

<details>
<summary><b>꼬리 질문 3개 (펼치기)</b></summary>

- 힙을 배열로 구현한다고 가정하면, 어떻게 값을 저장할 수 있을까요?
- 힙의 삽입, 삭제 방식에 대해 설명하고, 왜 이진탐색트리와 달리 편향이 발생하지 않는지 설명해 주세요.
- 힙 정렬의 시간복잡도는 어떻게 되나요? Stable 한가요?

</details>

**내 답변**

```
힙(Heap)은 완전이진트리(Complete Binary Tree)를 기반으로 하며, 부모-자식 간에 특정 순서 속성(힙 속성)을
만족하는 자료구조입니다.

- 최대 힙(Max Heap): 부모 값 ≥ 자식 값 → 루트에 항상 최댓값
- 최소 힙(Min Heap): 부모 값 ≤ 자식 값 → 루트에 항상 최솟값

이 속성 덕분에 최댓값(또는 최솟값)을 O(1)에 바로 조회할 수 있고, 삽입·삭제(루트 추출)는 O(log n)에
처리할 수 있습니다. 주로 우선순위 큐(Priority Queue)를 구현하는 데 사용됩니다.
```

**꼬리 질문 답변**

- 힙을 배열로 구현한다고 가정하면, 어떻게 값을 저장할 수 있을까요?
```
힙은 항상 완전이진트리 형태를 유지하기 때문에(마지막 레벨만 왼쪽부터 채워짐), 포인터 없이 배열의
인덱스 관계만으로 트리 구조를 표현할 수 있습니다.

0-indexed 배열 기준:
- 인덱스 i 노드의 왼쪽 자식: 2i + 1
- 인덱스 i 노드의 오른쪽 자식: 2i + 2
- 인덱스 i 노드의 부모: (i - 1) / 2 (정수 나눗셈)

빈 칸 없이 위에서 아래, 왼쪽에서 오른쪽 순서로 배열이 채워지기 때문에 메모리 낭비 없이 효율적으로
저장할 수 있습니다.
```

- 힙의 삽입, 삭제 방식에 대해 설명하고, 왜 이진탐색트리와 달리 편향이 발생하지 않는지 설명해 주세요.
```
[삽입]
배열의 맨 끝(트리의 마지막 빈자리)에 새 값을 추가한 뒤, 부모 노드와 비교하면서 힙 속성이 깨지면
교환(swap)하는 것을 반복합니다 (Up-heapify / Sift-up). 루트에 도달하거나 더 이상 속성이 깨지지
않을 때 멈추므로, 트리 높이만큼인 O(log n)이 걸립니다.

[삭제] (보통 루트 제거를 의미)
루트를 배열의 마지막 값으로 교체하고 마지막 칸을 제거한 뒤, 새로운 루트를 자식들과 비교하며
힙 속성이 깨지면 더 우선순위가 높은 자식과 교환하는 것을 반복합니다 (Down-heapify / Sift-down).
역시 O(log n)입니다.

[왜 편향이 발생하지 않는가]
BST는 값의 크기에 따라 삽입 위치가 결정되기 때문에, 입력 순서에 따라 한쪽으로 계속 자식이 붙는
편향이 생길 수 있습니다. 반면 힙은 삽입 위치가 값의 크기와 무관하게 항상 "배열의 다음 빈자리
(=완전이진트리의 다음 위치)"로 고정되어 있고, 값의 크기 비교는 오직 부모-자식 간 교환(swap) 여부를
정하는 데만 사용됩니다. 즉 트리의 "형태(shape)"는 완전이진트리 규칙에 의해 항상 강제로 유지되고,
값 비교는 그 형태 안에서 위치를 재배열하는 데만 관여하기 때문에 구조적으로 균형이 깨지지 않습니다.
```

- 힙 정렬의 시간복잡도는 어떻게 되나요? Stable 한가요?
```
힙 정렬(Heap Sort)의 시간복잡도는 O(n log n)입니다. (배열 전체로 힙을 만드는 Build-Heap 과정이
O(n), 이후 루트를 하나씩 꺼내며 재정렬하는 과정이 n번 × O(log n) = O(n log n))

Stable 하지 않습니다. 루트와 마지막 원소를 교환한 뒤 Sift-down 하는 과정에서, 값이 같은 원소들끼리도
위치가 멀리 떨어진 상태로 교환이 일어날 수 있어 원래의 상대적 순서가 보장되지 않습니다.
```

**핵심 키워드** → 완전이진트리(Complete Binary Tree)와 힙 속성(최대힙/최소힙), 배열 기반 구현(2i+1·2i+2·(i-1)/2), Sift-up(삽입)/Sift-down(삭제) O(log n), 삽입 위치가 값 크기와 무관 → 형태(shape) 고정으로 편향 없음(BST와 대비), 힙 정렬 O(n log n)·Unstable, 우선순위 큐(Priority Queue) 구현체

#### 7. BBST (Balanced Binary Search Tree) 와, 그 종류에 대해 설명해 주세요.

`★★★` · `심화` · 원본 [자료구조·알고리즘 #7](../01-DATA_STRUCTURE_ALGORITHM.md)

<details>
<summary><b>꼬리 질문 3개 (펼치기)</b></summary>

- Red Black Tree는 어떻게 균형을 유지할 수 있을까요?
- Red Black Tree의 주요 성질 4가지에 대해 설명해 주세요.
- 2-3-4 Tree, AVL Tree 등의 다른 BBST 가 있음에도, 왜 Red Black Tree가 많이 사용될까요?

</details>

**내 답변**

```
여기부분은 모르는 부분....
BBST(Balanced Binary Search Tree)는 일반 BST의 "편향 문제"를 해결하기 위해, 삽입·삭제가 일어날 때마다
스스로 구조를 재조정해서 트리의 높이를 항상 O(log n)으로 유지하는 이진탐색트리입니다.

재조정은 보통 회전(Rotation) 연산(Left Rotation / Right Rotation)을 통해 이루어지며, 이 덕분에
어떤 순서로 데이터가 삽입되더라도 탐색·삽입·삭제 연산이 항상 O(log n)임을 보장할 수 있습니다.

대표적인 종류로 AVL Tree, Red-Black Tree, 2-3-4 Tree(및 그 일반화인 B-Tree) 등이 있습니다.
```

**꼬리 질문 답변**

- Red Black Tree는 어떻게 균형을 유지할 수 있을까요?
```
삽입이나 삭제로 인해 색상 규칙(아래 4가지 성질)이 깨지면, 회전(Rotation)과 재색칠(Recoloring)을
조합해서 규칙을 다시 만족시키도록 트리를 재조정합니다.

- 삽입 시: 새 노드는 항상 빨간색으로 넣습니다. 부모도 빨간색이라 "빨간 노드의 자식은 검정"이라는
  규칙이 깨지면, 삼촌(부모의 형제) 노드의 색에 따라 재색칠만으로 해결하거나, 회전 + 재색칠로 해결합니다.
- 삭제 시: 검정 노드가 제거되면 Black Height(검정 노드 개수) 균형이 깨질 수 있어, 형제 노드의 상태에
  따라 회전과 재색칠을 반복하며 균형을 복구합니다.

회전 자체는 O(1) 연산이고, 삽입·삭제 후 재조정 과정 전체는 트리 높이에 비례해 O(log n)입니다.
```

- Red Black Tree의 주요 성질 4가지에 대해 설명해 주세요.
```
1. 모든 노드는 빨강(Red) 또는 검정(Black) 색을 가진다.
2. 루트(Root) 노드는 항상 검정이다.
3. 빨간 노드의 자식은 항상 검정이다 (즉, 빨간 노드가 연속으로 나올 수 없다 = No Red-Red Violation).
4. 임의의 노드에서 그 노드의 자손인 리프(NIL)까지 내려가는 모든 경로에는 항상 같은 개수의 검정
   노드가 있다 (Black Height가 모든 경로에서 동일).

이 성질들 덕분에 "가장 긴 경로가 가장 짧은 경로보다 2배 이상 길어질 수 없다"는 것이 보장되어,
트리 높이가 항상 O(log n)으로 유지됩니다.
```

- 2-3-4 Tree, AVL Tree 등의 다른 BBST 가 있음에도, 왜 Red Black Tree가 많이 사용될까요?
```
- AVL Tree와 비교: AVL Tree는 모든 노드에서 왼쪽·오른쪽 서브트리의 높이 차이가 최대 1이 되도록 매우
  엄격하게 균형을 유지합니다. 그래서 트리가 더 낮고 탐색(조회)은 Red-Black Tree보다 살짝 빠를 수
  있지만, 그만큼 삽입·삭제할 때마다 균형을 맞추기 위한 회전이 더 자주, 더 많이 일어나 삽입·삭제
  비용이 더 큽니다. Red-Black Tree는 균형 조건이 상대적으로 느슨해서(최악의 높이가 이론상
  2*log₂(n+1) 정도까지 허용) 삽입·삭제 시 재조정 비용이 더 적습니다. 조회와 삽입·삭제가 골고루
  섞여 발생하는 범용적인 상황에서는 Red-Black Tree가 전체적으로 더 유리한 경우가 많습니다.

- 2-3-4 Tree와 비교: 2-3-4 Tree는 한 노드가 여러 개의 키(최대 3개)와 자식(최대 4개)을 가질 수 있는
  구조라 개념적으로 균형이 잘 잡히지만, 노드 하나의 크기가 가변적이라 구현이 복잡하고 메모리 오버헤드가
  큽니다. Red-Black Tree는 2-3-4 Tree와 구조적으로 동형(isomorphic)이면서도, 각 노드가 자식을
  최대 2개만 갖는 순수한 이진트리 형태로 구현할 수 있어 기존 BST 코드/인터페이스를 그대로 재사용하기
  쉽습니다.

그래서 삽입·삭제·탐색이 고르게 일어나는 범용 자료구조(Java TreeMap/TreeSet, C++ std::map/std::set,
Linux 커널의 프로세스 스케줄러 등)에서 Red-Black Tree가 널리 채택되었습니다.
```

**핵심 키워드** → BBST는 회전(Rotation)으로 높이 O(log n) 유지, AVL Tree(엄격한 균형·조회 우세) vs Red-Black Tree(느슨한 균형·삽입삭제 우세), RBT 4가지 성질(빨강/검정, 루트는 검정, No Red-Red, 모든 경로 Black Height 동일), 2-3-4 Tree와 RBT의 동형(isomorphic) 관계, 삽입 시 재색칠·삭제 시 회전+재색칠 O(log n)

**막힌 부분 / 다시 볼 것** →

#### 8. 정렬 알고리즘에 대해 설명해 주세요.

`★★☆` · `필수` · 원본 [자료구조·알고리즘 #8](../01-DATA_STRUCTURE_ALGORITHM.md)

<details>
<summary><b>꼬리 질문 9개 (펼치기)</b></summary>

- Quick Sort와 Merge Sort를 비교해 주세요.
- Quick Sort에서 O(N^2)이 걸리는 예시를 들고, 이를 개선할 수 있는 방법에 대해 설명해 주세요.
- Stable Sort가 무엇이고, 어떤 정렬 알고리즘이 Stable 한지 설명해 주세요.
- Merge Sort를 재귀를 사용하지 않고 구현할 수 있을까요?
- Radix Sort에 대해 설명해 주세요.
- Bubble, Selection, Insertion Sort의 속도를 비교해 주세요.
- 값이 **거의** 정렬되어 있거나, 아예 정렬되어 있다면, 위 세 알고리즘의 성능 비교 결과는 달라질까요?
- 본인이 사용하고 있는 언어에선, 어떤 정렬 알고리즘을 사용하여 정렬 함수를 제공하고 있을까요?
- 정렬해야 하는 데이터는 50G 인데, 메모리가 4G라면, 어떤 방식으로 정렬을 진행할 수 있을까요?

</details>

**내 답변**

```
정렬 알고리즘은 데이터를 특정 순서(오름차순/내림차순)로 재배열하는 알고리즘입니다. 크게 두 갈래로
나눌 수 있습니다.

- 비교 기반 정렬: 원소끼리 크기를 비교해서 순서를 정하는 방식. 이론적으로 O(n log n)이 하한입니다
  (n개를 정렬하는 모든 경우의 수 n!을 구분하려면 최소 log₂(n!) ≈ n log n 번의 비교가 필요하다는
  정보 이론적 근거). 대표적으로 O(n²) 계열(Bubble, Selection, Insertion)과 O(n log n) 계열
  (Quick, Merge, Heap Sort)이 있습니다.
- 비교 없이 정렬하는 방식: 값의 특성(자릿수, 범위 등)을 이용해 O(n) 근처의 성능을 내는 Counting Sort,
  Radix Sort, Bucket Sort 등이 있습니다. 비교 기반이 아니므로 O(n log n) 하한의 제약을 받지 않습니다.
```

**꼬리 질문 답변**

- Quick Sort와 Merge Sort를 비교해 주세요.
```
- Quick Sort: pivot을 하나 정해서 pivot보다 작은 값/큰 값으로 배열을 분할(partition)한 뒤, 각
  부분을 재귀적으로 정렬합니다. 평균 O(n log n), 최악(분할이 계속 한쪽으로 치우칠 때) O(n²)입니다.
  추가 배열 없이 in-place로 구현 가능(재귀 호출 스택만 O(log n)). Unstable.
- Merge Sort: 배열을 절반으로 계속 나눈 뒤, 각각 정렬된 두 부분을 병합(merge)하며 합칩니다. 분할이
  항상 균등해서 최선/평균/최악 모두 O(n log n)이 보장됩니다. 병합 과정에서 원본 크기만큼의 추가
  메모리(O(n))가 필요합니다. Stable.

실무에서는 배열 정렬처럼 캐시 지역성이 중요하고 메모리를 아껴야 할 때는 Quick Sort(또는 그 개선형인
Introsort)를, 안정 정렬이 필요하거나 외부 정렬(디스크 기반) 상황에서는 Merge Sort를 선호합니다.
```

- Quick Sort에서 O(N^2)이 걸리는 예시를 들고, 이를 개선할 수 있는 방법에 대해 설명해 주세요.
```
[O(N²) 예시]
항상 배열의 첫 번째(또는 마지막) 원소를 pivot으로 고르는 구현에서, 이미 정렬되어 있거나 역순으로
정렬된 배열이 입력으로 들어오면, 매번 분할이 "1개 : 나머지(n-1)개"로 극단적으로 치우칩니다. 이 경우
재귀 깊이가 n이 되고, 각 단계에서 O(n)만큼 비교하므로 전체 O(n²)이 됩니다.

[개선 방법]
- Pivot을 무작위로 선택(Randomized Quick Sort): 특정 입력 패턴에 성능이 좌우되지 않게 함
- Median-of-three: 배열의 처음·중간·끝 값 중 중간값을 pivot으로 선택해 극단적인 분할 확률을 낮춤
- Introsort: 재귀 깊이가 일정 임계값(보통 2*log n)을 넘으면 Quick Sort를 포기하고 Heap Sort로
  전환해서, 최악의 경우에도 O(n log n)을 보장하도록 만듦 (C++ std::sort가 이 방식 사용)
```

- Stable Sort가 무엇이고, 어떤 정렬 알고리즘이 Stable 한지 설명해 주세요.
```
Stable Sort는 정렬 기준이 되는 값이 같은 원소들끼리는, 정렬 후에도 원래의 상대적 순서가 그대로
유지되는 정렬을 말합니다. (예: (이름, 나이) 쌍을 나이로 정렬할 때, 나이가 같은 사람들끼리는 정렬
전 순서 그대로 유지되어야 Stable)

- Stable: Bubble Sort, Insertion Sort, Merge Sort (Counting Sort, Radix Sort도 구현 방식에
  따라 Stable하게 만들 수 있음)
- Unstable: Quick Sort, Heap Sort, Selection Sort

여러 기준으로 순차적으로 정렬해야 할 때(예: 먼저 이름으로 정렬한 결과를 유지한 채 나이로 다시 정렬)
Stable 정렬이 필요합니다.
```

- Merge Sort를 재귀를 사용하지 않고 구현할 수 있을까요?
```
가능합니다. Bottom-up Merge Sort 방식을 사용하면 재귀 호출 없이 반복문만으로 구현할 수 있습니다.

처음에는 크기 1짜리 부분 배열들을 서로 병합해서 크기 2인 정렬된 덩어리들을 만들고, 그다음 크기 2인
덩어리끼리 병합해서 크기 4로, 그다음 8, 16... 이런 식으로 병합할 구간의 크기를 2배씩 늘려가며
전체 배열을 다 병합할 때까지 반복합니다. 재귀 대신 반복문(for/while)으로 병합 크기를 관리하는
방식이라 함수 호출 스택 오버헤드가 없습니다.
```

- Radix Sort에 대해 설명해 주세요.
```
Radix Sort(기수 정렬)는 값끼리 직접 비교하지 않고, 자릿수(digit) 단위로 나누어 정렬하는 알고리즘입니다.

가장 낮은 자릿수(1의 자리)부터 시작해서, 각 자릿수를 기준으로 Counting Sort 같은 안정적인 정렬을
반복 적용합니다(LSD 방식). 안정 정렬을 자릿수 단위로 계속 적용하기 때문에, 이전 자릿수에서 정해진
상대적 순서가 다음 자릿수 정렬에서도 유지되어 최종적으로 전체가 정렬됩니다.

시간복잡도는 O(d × (n + k))입니다. (d = 최대 자릿수, n = 데이터 개수, k = 각 자릿수가 가질 수 있는
값의 범위, 예: 10진수면 k=10). d와 k가 n에 비해 작다면 사실상 O(n)에 가까운 성능을 냅니다. 정수나
고정 길이 문자열처럼 자릿수가 명확하게 정의되는 데이터에 적합합니다.
```

- Bubble, Selection, Insertion Sort의 속도를 비교해 주세요.
```
세 알고리즘 모두 평균/최악 시간복잡도는 O(n²)로 동일하지만, 실제 동작 방식이 달라 체감 성능은 다릅니다.

- Selection Sort: 매번 남은 범위에서 최솟값을 찾아 맨 앞과 교환. 비교 횟수는 입력 상태와 무관하게
  항상 n²/2번으로 고정되지만, 교환(swap) 횟수는 최대 n-1번으로 셋 중 가장 적습니다. 쓰기(교환) 비용이
  큰 환경(예: 메모리 쓰기가 비싼 경우)에서 유리합니다.
- Bubble Sort: 인접한 두 원소를 계속 비교하며 교환. 비교할 때마다 교환이 자주 일어나(값이 한 칸씩만
  이동) 실제로는 세 알고리즘 중 가장 느린 경우가 많습니다.
- Insertion Sort: 이미 정렬된 부분에 새 원소를 적절한 위치에 삽입. 평균적으로 세 알고리즘 중 실용적인
  성능이 가장 좋은 편이며(적은 이동, 좋은 캐시 지역성), 특히 데이터가 이미 어느 정도 정렬되어 있을
  때 매우 빠릅니다.
```

- 값이 **거의** 정렬되어 있거나, 아예 정렬되어 있다면, 위 세 알고리즘의 성능 비교 결과는 달라질까요?
```
네, 크게 달라집니다.

- Insertion Sort: 적응형(Adaptive) 정렬입니다. 거의 정렬된 배열에서는 각 원소를 삽입할 때 비교·이동
  횟수가 거의 없어 O(n)에 가깝게 빨라집니다. 완전히 정렬된 배열이면 정확히 O(n)입니다.
- Bubble Sort: 한 번의 패스에서 교환이 전혀 일어나지 않으면 조기 종료하는 최적화를 추가하면, 이미
  정렬된 배열에서는 O(n)까지 개선될 수 있습니다(적응형으로 만들 수 있음).
- Selection Sort: 입력 상태와 무관하게 항상 정확히 n²/2번 비교를 수행하기 때문에, 거의 정렬되어
  있든 완전히 무작위든 성능이 전혀 달라지지 않습니다(비적응형, Non-adaptive).

결론적으로 "거의 정렬된 데이터"에는 Insertion Sort가 가장 유리합니다.
```

- 본인이 사용하고 있는 언어에선, 어떤 정렬 알고리즘을 사용하여 정렬 함수를 제공하고 있을까요?
```
(사용 언어에 맞게 채워 넣기)
예) Java: Arrays.sort()는 원시 타입(int[] 등)에6는 Dual-Pivot Quicksort를 사용합니다(Stable 여부가
    중요하지 않고 성능이 우선이라 Unstable해도 무방). 반면 객체 배열(Object[])이나 Collections.sort()는
    Stable 정렬이 보장되어야 하므로 TimSort(Merge Sort와 Insertion Sort를 결합한 하이브리드 알고리즘,
    이미 정렬된 구간을 찾아 활용)를 사용합니다.
예) Python: 리스트의 sort()/sorted()는 TimSort를 사용합니다.
예) C++: std::sort는 보통 Introsort(Quick Sort + Heap Sort + 작은 구간은 Insertion Sort로 전환하는
    하이브리드, Unstable)를 사용하고, 안정 정렬이 필요하면 std::stable_sort(Merge Sort 기반)를 씁니다.
```

- 정렬해야 하는 데이터는 50G 인데, 메모리가 4G라면, 어떤 방식으로 정렬을 진행할 수 있을까요?
```
데이터 전체를 메모리에 올릴 수 없으므로, 외부 정렬(External Sort)을 사용합니다. Merge Sort의
"분할 후 병합" 아이디어를 디스크 I/O 환경으로 확장한 방식입니다.

1) 분할 및 부분 정렬 (Sort Phase)
   메모리에 들어갈 수 있는 크기(예: 3G 정도)만큼씩 데이터를 순서대로 읽어 들여, 메모리 내에서
   정렬한 뒤 그 결과를 디스크에 임시 파일(정렬된 run)로 저장합니다. 이 과정을 데이터를 전부 읽을
   때까지 반복해서, 여러 개의 정렬된 run 파일을 만듭니다. (50G / 3G ≈ 17개 정도의 run)

2) 병합 (Merge Phase)
   여러 개의 정렬된 run 파일을 K-way Merge로 합칩니다. 각 run 파일에서 맨 앞의 값들만 조금씩
   메모리로 읽어와 최소 힙(min-heap)에 넣고, 힙에서 가장 작은 값을 하나씩 꺼내 결과 파일에 쓰면서,
   그 값이 있던 run에서 다음 값을 다시 힙에 채워 넣는 방식을 반복합니다. 이렇게 하면 각 시점에
   메모리에는 run 개수만큼의 값(아주 적은 양)만 있으면 되므로, 4G 메모리로도 충분히 처리할 수 있습니다.

이 방식은 실제 대용량 데이터베이스의 정렬 연산이나 분산 처리 시스템(Hadoop MapReduce의 shuffle 단계 등)
에서 사용되는 방식과 동일한 원리입니다.
```

**핵심 키워드** → 비교 기반 정렬 하한 O(n log n) vs 비교 없는 정렬(Counting/Radix/Bucket Sort), Quick Sort(평균 O(n log n)·최악 O(n²)·Unstable) vs Merge Sort(항상 O(n log n)·Stable), Pivot 개선(랜덤·median-of-three)과 Introsort, Stable Sort 개념과 Stable/Unstable 알고리즘 분류, Adaptive(Insertion·Bubble) vs Non-adaptive(Selection), Bottom-up Merge Sort(반복문 기반), Radix Sort O(d×(n+k)), 언어별 정렬(TimSort, Introsort), 외부 정렬(External Sort)과 K-way Merge

**내 답변**

```
객체지향 프로그래밍(OOP)은 데이터(속성)와 그 데이터를 다루는 동작(메서드)을 "객체(Object)"라는 하나의

보통 네 가지 특성으로 설명합니다.
- 캡슐화(Encapsulation): 데이터와 메서드를 하나로 묶고, 내부 구현을 외부로부터 감춤
- 상속(Inheritance): 기존 클래스의 속성/동작을 물려받아 재사용·확장
- 다형성(Polymorphism): 같은 인터페이스로 서로 다른 동작을 하게 함
- 추상화(Abstraction): 불필요한 세부사항을 감추고 필요한 부분만 노출

목표는 코드의 재사용성, 유지보수성, 확장성을 높여서 복잡한 시스템을 더 관리하기 쉬운 단위로
나누어 설계하는 것입니다.
```

**꼬리 질문 답변**

- SOLID 원칙에 대해 설명해 주세요.
```
- SRP (단일 책임 원칙, Single Responsibility Principle): 클래스는 단 하나의 책임(변경되어야 할
  이유)만 가져야 한다.
- OCP (개방-폐쇄 원칙, Open-Closed Principle): 확장에는 열려 있고, 수정에는 닫혀 있어야 한다.
  기존 코드를 고치지 않고도 새로운 기능을 추가할 수 있게 설계해야 한다.
- LSP (리스코프 치환 원칙, Liskov Substitution Principle): 자식 클래스는 부모 클래스를 대체해서
  사용해도 프로그램의 동작이 깨지지 않아야 한다.
- ISP (인터페이스 분리 원칙, Interface Segregation Principle): 클라이언트가 사용하지 않는 메서드에
  의존하지 않도록, 하나의 거대한 인터페이스보다 여러 개의 작은 인터페이스로 분리해야 한다.
- DIP (의존관계 역전 원칙, Dependency Inversion Principle): 구체적인 구현 클래스가 아니라
  추상화(인터페이스)에 의존해야 한다. 상위 모듈과 하위 모듈 모두 추상화에 의존해야 한다.
```

- 다형성이 무엇인지 설명하고, 동적 다형성과 정적 다형성이 무엇인지 설명해 주세요.
```
다형성(Polymorphism)은 같은 이름의 메서드(또는 같은 인터페이스)를 호출해도, 실제로 어떤 객체인지에
따라 서로 다른 동작을 하게 만드는 성질입니다.

- 정적 다형성(컴파일타임 다형성): 오버로딩(Overloading)처럼, 컴파일 시점에 매개변수의 타입·개수를
  보고 어떤 메서드를 호출할지 결정됩니다.
- 동적 다형성(런타임 다형성): 오버라이딩(Overriding)처럼, 부모 타입 참조 변수가 실제로 가리키는
  객체의 타입에 따라 어떤 메서드가 실행될지 런타임에 결정됩니다.
```

- 오버로딩과 오버라이딩의 차이에 대해 설명해 주세요.
```
- 오버로딩(Overloading): 같은 이름의 메서드를 매개변수의 타입/개수/순서를 다르게 해서 한 클래스
  안에 여러 개 정의하는 것. 어떤 메서드가 호출될지는 컴파일 시점에 매개변수를 보고 결정됩니다
  (정적 바인딩).
- 오버라이딩(Overriding): 부모 클래스에 정의된 메서드를, 자식 클래스가 동일한 시그니처(이름,
  매개변수)로 재정의하는 것. 어떤 메서드가 실행될지는 런타임에 실제 객체의 타입을 보고 결정됩니다
  (동적 바인딩).
```

- 상속이 무엇인지 설명하고, 상속을 사용했을 때 얻는 것과 잃는 것을 설명해 주세요.
```
상속(Inheritance)은 부모(상위) 클래스가 가진 속성과 메서드를 자식(하위) 클래스가 물려받아 재사용하는
것입니다. "is-a" 관계를 표현합니다.

[얻는 것]
- 코드 재사용: 공통 로직을 부모 클래스에 두고 자식들이 재사용
- 계층적 분류를 통한 다형성 활용: 부모 타입으로 여러 자식 객체를 일관되게 다룰 수 있음

[잃는 것]
- 강한 결합(Tight Coupling): 부모 클래스를 수정하면 자식 클래스들도 영향을 받는 "취약한 기반 클래스
  문제(Fragile Base Class Problem)"가 생길 수 있음
- 캡슐화 약화: 자식 클래스가 부모의 내부 구현에 암묵적으로 의존하기 쉬움
- 유연성 저하: 상속 관계는 보통 컴파일 타임에 고정되어, 런타임에 동작 방식을 바꾸기 어려움
```

- "상속보다 합성(Composition)을 사용하라"는 말이 있습니다. 왜 그럴까요?
```
상속은 부모 클래스의 구현 세부사항까지 자식 클래스에 그대로 노출되고 강하게 결합되는 반면, 합성은
다른 객체를 필드로 "가지고 있다가"(has-a 관계) 그 객체의 기능을 위임(delegate)해서 사용하는
방식입니다.

합성을 쓰면:
- 결합도가 낮아짐: 내부적으로 어떤 구현체를 쓰는지 인터페이스만 맞으면 자유롭게 교체 가능
- 런타임 유연성: 생성자나 setter로 구현체를 주입받아 실행 중에도 동작을 바꿀 수 있음
- 불필요한 상속 계층 오염 방지: 부모의 모든 메서드를 강제로 물려받지 않고, 필요한 기능만 선택적으로
  가져다 쓸 수 있음

그래서 "재사용"이 목적이라면 상속보다 합성으로 필요한 기능만 조합하는 편이 변경에 더 유연하고
결합도가 낮은 설계가 됩니다.
```

- 캡슐화와 정보은닉은 어떤 차이가 있나요? 접근제어자만 붙이면 캡슐화가 되는 걸까요?
```
캡슐화(Encapsulation)는 "데이터와 그 데이터를 다루는 메서드를 하나의 단위(클래스)로 묶는 것" 자체를
의미합니다. 정보은닉(Information Hiding)은 그 중에서도 "내부 구현 세부사항을 외부에서 직접 접근하지
못하도록 감추는 것"을 의미하며, 캡슐화가 추구하는 목적/결과 중 하나입니다.

접근제어자(private 등)만 붙인다고 완전한 캡슐화가 되는 것은 아닙니다. 예를 들어 필드를 private으로
감췄더라도, getter가 내부의 mutable한 객체(예: List) 참조를 그대로 반환해버리면 외부에서 그 참조를
통해 내부 상태를 마음대로 바꿀 수 있어 사실상 정보은닉이 깨진 것입니다. 진짜 캡슐화는 "무엇을 할 수
있는지(행위, 퍼블릭 인터페이스)"만 노출하고 "어떻게 하는지(내부 구현)"는 철저히 숨기는 것을 의미합니다.
```

- 다형성이 실제 코드에서 어떻게 쓰이는지, 본인의 언어를 기준으로 예시를 들어 설명해 주세요.
```
(사용 언어에 맞게 채워 넣기)
예) Java: List<T> 인터페이스를 사용할 때, 실제 구현체로 ArrayList나 LinkedList 중 무엇을 쓰든
    호출하는 코드(add, get, remove 등)는 동일합니다. List<String> list = new ArrayList<>() 로
    선언해두면, 나중에 new LinkedList<>()로 구현체만 바꿔도 List 타입을 사용하는 코드는 전혀
    수정할 필요가 없습니다. 이것이 인터페이스 기반의 다형성입니다.
예) 부모 클래스 Animal에 makeSound() 메서드가 있고, Dog·Cat이 각각 오버라이딩해서 다른 소리를
    낸다면, Animal a = new Dog(); a.makeSound(); 처럼 부모 타입 변수로 다뤄도 실제로는 Dog의
    makeSound()가 호출됩니다(동적 다형성).
```

- 클래스가 있는 언어는 반드시 객체지향 언어라고 할 수 있을까요? 그 반대는 성립하나요?
```
아닙니다. 클래스는 객체를 만들기 위한 "문법적 도구"일 뿐, OOP의 핵심은 캡슐화·상속·다형성·추상화
같은 설계 개념을 실제로 잘 활용하는지에 있습니다. 클래스 문법이 있는 언어(예: C++)로도 얼마든지
절차적으로(함수 위주로) 코드를 짜서 OOP의 이점을 전혀 활용하지 않을 수 있습니다.

반대도 성립하지 않습니다. 클래스라는 문법이 없는 언어도 OOP 스타일로 프로그래밍할 수 있습니다.
예를 들어 JavaScript(ES5 이전)는 클래스 없이 프로토타입 기반 상속으로 객체지향을 구현했고, Go는
클래스 대신 구조체(struct)와 인터페이스의 구조적 타이핑(structural typing)으로 캡슐화·다형성을
구현합니다.

즉 "클래스가 있다"와 "객체지향적으로 설계했다"는 서로 다른 축의 이야기이며, 어느 한쪽이 다른 쪽을
자동으로 보장하지 않습니다.
```

**핵심 키워드** → 캡슐화·상속·다형성·추상화(OOP 4대 특성), SOLID 원칙(SRP·OCP·LSP·ISP·DIP), 정적 다형성(오버로딩·컴파일타임) vs 동적 다형성(오버라이딩·런타임), 상속(is-a)의 이점과 단점(Fragile Base Class), 합성(Composition, has-a)이 상속보다 유연한 이유, 캡슐화 vs 정보은닉의 차이, 클래스 유무와 OOP는 별개 개념(프로토타입 기반·구조적 타이핑)

#### [자료구조 1/6] LinkedList

**구현 범위** — 단일 연결 리스트의 `add(index, e)` · `remove(index)` · `get(index)`. 이중 연결 리스트로 확장하면 무엇이 달라지는지도 함께 정리

```java
class Node<T> {
    T data;
    Node<T> next;
    Node(T data) { this.data = data; }
}

class SinglyLinkedList<T> {
    private Node<T> head;
    private int size;

    // index 위치에 e를 삽입 (0 <= index <= size)
    void add(int index, T e) {
        Node<T> newNode = new Node<>(e);
        if (index == 0) {
            newNode.next = head;
            head = newNode;
        } else {
            Node<T> prev = head;
            for (int i = 0; i < index - 1; i++) {
                prev = prev.next;
            }
            newNode.next = prev.next;
            prev.next = newNode;
        }
        size++;
    }

    // index 위치의 노드를 제거
    void remove(int index) {
        if (index == 0) {
            head = head.next;
        } else {
            Node<T> prev = head;
            for (int i = 0; i < index - 1; i++) {
                prev = prev.next;
            }
            prev.next = prev.next.next;
        }
        size--;
    }

    // index 위치의 값을 반환
    T get(int index) {
        Node<T> cur = head;
        for (int i = 0; i < index; i++) {
            cur = cur.next;
        }
        return cur.data;
    }
}
```

**이중 연결 리스트로 확장하면 달라지는 점**
- 각 노드에 `prev` 포인터가 추가되고, 보통 `tail` 포인터도 함께 유지
- 삭제 시 "이전 노드"를 찾기 위해 head부터 순회할 필요 없이 `node.prev`로 바로 접근 가능해 삭제 로직이 단순해짐
- `tail`을 유지하면 리스트 뒤쪽(끝 근처) 삽입/삭제는 뒤에서부터 순회할 수 있어 유리
- 대신 노드마다 포인터가 하나 더 필요해 메모리 사용량이 늘어남(상수 배 증가), 삽입/삭제 시 갱신해야 할 포인터 수도 늘어남

**시간복잡도** → `add`/`remove`: index==0이면 O(1), 그 외에는 해당 위치까지 순회해야 하므로 O(n). `get`: O(n)
**공간복잡도** → 리스트 전체 O(n) (노드마다 데이터+포인터), 연산 자체에 필요한 추가 공간은 O(1)

#### 15. 스택 두개로 큐를, 큐 두개로 스택을 구현하는 코드를 작성해 보세요.

```java
// 스택 2개로 큐 구현
class MyQueue<T> {
    private Deque<T> inStack = new ArrayDeque<>();
    private Deque<T> outStack = new ArrayDeque<>();

    void enqueue(T x) {
        inStack.push(x);
    }

    T dequeue() {
        if (outStack.isEmpty()) {
            while (!inStack.isEmpty()) {
                outStack.push(inStack.pop());
            }
        }
        return outStack.pop();
    }
}

// 큐 2개로 스택 구현
class MyStack<T> {
    private Queue<T> q1 = new LinkedList<>();
    private Queue<T> q2 = new LinkedList<>();

    void push(T x) {
        q2.offer(x);
        while (!q1.isEmpty()) {
            q2.offer(q1.poll());
        }
        Queue<T> temp = q1;
        q1 = q2;
        q2 = temp;
    }

    T pop() {
        return q1.poll();
    }
}
```

**시간복잡도** → 스택 2개로 큐: `enqueue` O(1), `dequeue`는 상각(amortized) O(1) (원소마다 in→out 이동이 최대 1회). 큐 2개로 스택: `push` O(n), `pop` O(1)
**공간복잡도** → 둘 다 O(n) (원소 n개를 담기 위한 보조 자료구조 1개씩 추가 사용)
