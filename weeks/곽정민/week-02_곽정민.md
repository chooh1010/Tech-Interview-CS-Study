<details>
<summary><b>꼬리 질문 3개 (펼치기)</b></summary>

- 각 방법에 대해, "두 정점이 연결되었는지" 확인하는 시간복잡도와 "한 정점에 연결된 모든 정점을 찾는" 시간복잡도, 그리고 공간복잡도를 비교해 주세요.
- 정점의 개수가 N개, 간선의 개수가 N^3 개라면, 어떤 방식으로 구현하는 것이 효율적일까요?
- 사이클이 없는 그래프는 모두 트리인가요? 그렇지 않다면, 예시를 들어주세요.

</details>

**내 답변**

```
그래프는 정점(Vertex)과, 정점들을 잇는 간선(Edge)으로 구성된 비선형 자료구조입니다. 트리와 달리
사이클이 있을 수 있고, 루트 개념이 없으며, 전체가 하나로 연결되어 있지 않아도 됩니다. 간선에 방향이
있는지에 따라 방향 그래프·무방향 그래프로, 간선에 비용이 있는지에 따라 가중치 그래프·비가중치
그래프로 나눌 수 있습니다.

구현 방법은 크게 두 가지입니다. 인접 행렬(Adjacency Matrix)은 N×N 크기의 2차원 배열을 두고
matrix[i][j]에 i와 j 사이 간선의 유무(또는 가중치)를 저장하는 방식입니다. 인접 리스트(Adjacency
List)는 각 정점마다 자신과 연결된 정점들의 리스트를 따로 관리하는 방식으로, 보통 배열이나 해시맵에
링크드 리스트(또는 동적 배열)를 매달아 구현합니다.
```

**꼬리 질문 답변**

- 각 방법에 대해, "두 정점이 연결되었는지" 확인하는 시간복잡도와 "한 정점에 연결된 모든 정점을 찾는" 시간복잡도, 그리고 공간복잡도를 비교해 주세요.
```
인접 행렬은 matrix[i][j]를 바로 인덱싱해서 확인하면 되므로 두 정점의 연결 여부 확인이 O(1)입니다.
반면 한 정점에 연결된 모든 정점을 찾으려면 그 정점에 해당하는 행(또는 열) 전체를 순회해야 하므로
O(N)이 걸립니다. 공간복잡도는 정점 개수만큼의 정사각 배열을 항상 확보해야 하므로 간선 수와 무관하게
O(N²)입니다.

인접 리스트는 정반대의 트레이드오프를 갖습니다. 두 정점의 연결 여부를 확인하려면 한 정점의 리스트를
처음부터 끝까지 순회해야 하므로, 그 정점의 차수(degree)를 d라 할 때 O(d)가 걸리고 최악의 경우
O(N)입니다. 반면 한 정점에 연결된 모든 정점을 찾는 건 그 정점의 리스트를 그대로 순회하면 되므로
O(d), 즉 나온 만큼만 순회하면 되어 인접 행렬보다 유리합니다. 공간복잡도는 존재하는 간선의 개수만큼만
저장하면 되므로 O(V + E)입니다.

그래서 간선이 정점 수 제곱에 가까울 만큼 촘촘한 밀집 그래프(dense graph)라면 인접 행렬이, 간선이
정점 수에 비례하는 정도로 성긴 희소 그래프(sparse graph)라면 인접 리스트가 공간·시간 면에서 유리한
경우가 많습니다.
```

- 정점의 개수가 N개, 간선의 개수가 N^3 개라면, 어떤 방식으로 구현하는 것이 효율적일까요?
```
사실 이 조건 자체가 모순에 가깝습니다. 단순 그래프에서 정점이 N개면 가능한 간선의 최대 개수는
N(N-1)/2, 즉 O(N²)이기 때문에 간선이 N³개가 될 수는 없습니다(다중 간선이나 멀티그래프를 허용하는
특수한 경우가 아니라면요). 아마 "간선이 N²에 가까운 정도로 매우 촘촘한 밀집 그래프"라는 취지의
질문으로 이해하고 답하겠습니다.

이 경우엔 인접 행렬이 더 효율적입니다. 인접 리스트를 쓰면 공간복잡도가 어차피 O(V+E) ≈ O(N²)로
인접 행렬과 같아지는데, 인접 리스트 특유의 포인터·노드 오버헤드까지 추가로 붙어서 실제 메모리 사용량은
오히려 더 큽니다. 게다가 간선이 이렇게 촘촘하면 대부분의 알고리즘에서 결국 모든 정점 쌍을 확인해야
하는 경우가 많아서(예: 플로이드-워셜), 인접 행렬의 O(1) 연결 확인과 캐시 지역성 좋은 2차원 배열
순회가 인접 리스트의 포인터 추적보다 유리합니다.
```

- 사이클이 없는 그래프는 모두 트리인가요? 그렇지 않다면, 예시를 들어주세요.
```
아니요, 모두 트리는 아닙니다. 트리이려면 사이클이 없다는 조건에 더해 "모든 정점이 하나로 연결되어
있어야" 합니다. 사이클이 없지만 여러 개의 연결 컴포넌트로 나뉘어 있는 그래프는 트리가 아니라
포레스트(Forest, 트리들의 집합)라고 부릅니다.

예를 들어 정점이 {A, B, C, D} 이렇게 4개 있고 간선이 A-B 하나뿐이라면, 사이클은 전혀 없지만
{A, B}와 {C}, {D}가 서로 연결되어 있지 않은 별개의 컴포넌트라서 트리 하나가 아니라 3개의 트리로
이루어진 포레스트입니다. 정리하면 "트리 = 사이클이 없고 + 연결되어 있음"이고, 사이클만 없는 경우는
"포레스트 ⊇ 트리"라는 상위 개념이 됩니다.
```

**핵심 키워드** → 정점(Vertex)·간선(Edge), 방향/무방향·가중치/비가중치 그래프, 인접 행렬(O(1) 연결확인·O(N²) 공간) vs 인접 리스트(O(d) 연결확인·O(V+E) 공간), 밀집 그래프(dense) → 인접 행렬 유리 / 희소 그래프(sparse) → 인접 리스트 유리, 트리 = 사이클 없음 + 연결됨, 포레스트(Forest, 트리들의 집합)

#### 2. 그래프에서, 최단거리를 구하는 방법에 대해 설명해 주세요.

`★★★` · `심화` · 원본 [자료구조·알고리즘 #10](../01-DATA_STRUCTURE_ALGORITHM.md)

<details>
<summary><b>꼬리 질문 5개 (펼치기)</b></summary>

- 트리에서는 어떤 방식으로 최단거리를 구할 수 있을까요? (위 방법을 사용하지 않고)
- 다익스트라 알고리즘에서, 힙을 사용하지 않고 구현한다면 시간복잡도가 어떻게 변화할까요?
- 정점의 개수가 N개, 간선의 개수가 N^3 개라면, 어떤 알고리즘이 효율적일까요?
- A* 알고리즘에 대해 설명해 주세요. 이 알고리즘은 다익스트라와 비교해서 어떤 성능을 낼까요?
- 음수 간선이 있을 때와, 음수 사이클이 있을 때 각각 어떤 최단거리 알고리즘을 사용해야 하는지 설명해 주세요.

</details>

**내 답변**

```
상황에 따라 크게 세 가지 알고리즘을 씁니다.

모든 간선의 가중치가 동일하다면(또는 비가중치 그래프라면) BFS만으로 O(V+E)에 최단거리를 구할 수
있습니다. 레벨 단위로 퍼져나가는 BFS의 특성상 처음 방문하는 순간이 곧 최단거리이기 때문입니다.

가중치가 있고 모두 양수라면 다익스트라(Dijkstra) 알고리즘을 씁니다. 시작 정점에서 거리가 가장
가까운 정점부터 확정해 나가면서, 그 정점을 거쳐 갈 수 있는 다른 정점들의 거리를 갱신(relax)하는
그리디 방식입니다. 우선순위 큐(힙)를 쓰면 O((V+E) log V)에 처리할 수 있습니다.

음수 가중치 간선이 있다면 벨만-포드(Bellman-Ford) 알고리즘을 씁니다. 모든 간선에 대해 완화 연산을
정점 수-1번 반복하는 방식으로 O(VE)가 걸리지만, 다익스트라와 달리 음수 간선에서도 정확한 답을
보장하고, 음수 사이클의 존재 여부까지 탐지할 수 있습니다.

모든 정점 쌍 사이의 최단거리가 필요하다면 플로이드-워셜(Floyd-Warshall)을 씁니다. 각 정점을
경유지로 하나씩 고려해가며 모든 쌍의 거리를 갱신하는 DP 방식으로 O(V³)이 걸립니다.
```

**꼬리 질문 답변**

- 트리에서는 어떤 방식으로 최단거리를 구할 수 있을까요? (위 방법을 사용하지 않고)
```
트리는 임의의 두 정점 사이에 경로가 정확히 하나뿐이라는 특성이 있기 때문에, 그래프 최단경로
알고리즘 없이도 훨씬 단순하게 구할 수 있습니다.

가장 기본적인 방법은 한 정점에서 DFS나 BFS로 한 번만 순회하면서 시작점부터 각 정점까지의 거리를
누적해서 기록하는 것입니다. 경로가 유일하므로 이 거리가 곧 최단거리입니다.

임의의 두 정점 u, v 사이의 거리를 자주 질의해야 하는 상황이라면 LCA(최소 공통 조상)를 활용합니다.
루트에서부터 각 정점까지의 깊이(depth)를 미리 전처리해두면, u와 v 사이의 거리는
depth[u] + depth[v] - 2 × depth[LCA(u, v)]로 구할 수 있습니다. LCA를 오일러 투어 + 스파스
테이블이나 이진 리프팅으로 전처리해두면 각 질의를 O(log N)에 답할 수 있어서, 질의가 많은 경우
매번 BFS/DFS를 도는 것보다 훨씬 효율적입니다.
```

- 다익스트라 알고리즘에서, 힙을 사용하지 않고 구현한다면 시간복잡도가 어떻게 변화할까요?
```
힙 없이 구현하면, 매 단계마다 아직 확정되지 않은 정점들 중 거리가 가장 짧은 정점을 배열을 순회하며
찾아야 합니다. 이 탐색이 O(V)이고, 이걸 모든 정점에 대해 반복하므로 O(V²)이 되고, 여기에 각 정점의
간선을 순회하며 완화하는 비용 O(E)를 더하면 전체 시간복잡도는 O(V² + E), 즉 보통 O(V²)로
표현합니다.

힙을 쓰면 최솟값 추출이 O(log V)로 줄어드는 대신 간선 완화마다 힙에 값을 넣는 비용이 붙어서
O((V+E) log V)가 됩니다. 그래서 간선이 촘촘한 밀집 그래프(E ≈ V²)에서는 오히려 힙 없는 O(V²)
구현이 O(V² log V)보다 더 빠르고, 간선이 성긴 희소 그래프에서는 힙 기반 구현이 유리합니다.
```

- 정점의 개수가 N개, 간선의 개수가 N^3 개라면, 어떤 알고리즘이 효율적일까요?
```
위 그래프 질문과 마찬가지로 단순 그래프에서 간선은 최대 O(N²)이므로, 여기서는 "간선이 O(N²)에
가까운 매우 밀집된 그래프"라는 의미로 이해하고 답하겠습니다.

이런 밀집 그래프에서 모든 정점 쌍의 최단거리가 필요하다면 플로이드-워셜이 유리합니다. 플로이드-워셜은
어차피 O(V³)이 걸리는데, 밀집 그래프에서는 E가 이미 V²에 가까우므로 힙 기반 다익스트라를 모든
정점에서 반복하는 O(V·(V+E)logV) ≈ O(V³ log V)보다 로그 인자가 없는 플로이드-워셜이 더 빠릅니다.
만약 단일 출발점의 최단거리만 필요하다면, 앞서 설명한 대로 힙 없는 O(V²) 다익스트라가 힙 기반보다
유리합니다.
```

- A* 알고리즘에 대해 설명해 주세요. 이 알고리즘은 다익스트라와 비교해서 어떤 성능을 낼까요?
```
A*는 다익스트라에 "목적지까지 남은 거리를 추정하는 휴리스틱 함수"를 결합한 최단경로 알고리즘입니다.
다익스트라가 시작점부터의 실제 거리 g(n)만 기준으로 다음에 방문할 정점을 고르는 반면, A*는
f(n) = g(n) + h(n), 즉 지금까지 온 거리(g)에 목적지까지 남았다고 추정되는 거리(h)를 더한 값을
기준으로 우선순위를 정합니다. h가 목적지 방향을 가리켜주기 때문에, 다익스트라처럼 사방으로 균일하게
퍼져나가지 않고 목적지 쪽으로 탐색을 집중시킬 수 있습니다.

성능 면에서는, 휴리스틱 h(n)이 실제 남은 거리를 절대 과대평가하지 않는 admissible한 함수라면 A*도
다익스트라처럼 최단경로를 보장하면서, 탐색해야 하는 정점 수는 훨씬 줄어들어 실제로는 더 빠르게
동작하는 경우가 많습니다. 극단적으로 h(n)을 항상 0으로 두면 A*는 다익스트라와 완전히 동일하게
동작합니다. 즉 A*는 다익스트라의 일반화된 상위 개념이라고 볼 수 있고, 좋은 휴리스틱(예: 격자 맵에서의
유클리드/맨해튼 거리)이 있는 문제에서 다익스트라보다 실질적인 탐색 범위를 크게 줄여줍니다.
```

- 음수 간선이 있을 때와, 음수 사이클이 있을 때 각각 어떤 최단거리 알고리즘을 사용해야 하는지 설명해 주세요.
```
음수 "간선"만 있고 음수 "사이클"은 없는 경우엔 벨만-포드를 씁니다. 다익스트라는 한 번 확정한
정점의 거리를 다시 갱신하지 않는 그리디 알고리즘이라, 나중에 음수 간선을 통해 더 짧은 경로가
발견되어도 이미 확정된 값을 되돌리지 못해 잘못된 결과를 낼 수 있습니다. 벨만-포드는 모든 간선을
정점 수-1번 반복해서 완화하기 때문에 음수 간선이 있어도 정확한 최단거리를 보장합니다.

음수 "사이클"이 있는 경우엔 애초에 "최단거리"라는 개념 자체가 정의되지 않습니다. 사이클을 돌 때마다
총 비용이 계속 줄어들기 때문에, 그 사이클에 도달할 수 있는 정점이라면 이론상 무한히 도는 것으로
비용을 -∞까지 줄일 수 있기 때문입니다. 이럴 때 벨만-포드는 정점 수-1번의 완화가 끝난 뒤에 한 번 더
완화를 시도해서, 그래도 값이 더 줄어드는 간선이 있으면 그 간선이 음수 사이클에 포함되어 있다고
판단해 "음수 사이클 존재"를 탐지하는 용도로 사용합니다.
```

**핵심 키워드** → BFS(비가중치, O(V+E)) / 다익스트라(양수 가중치, 그리디, 힙 기반 O((V+E)logV)) / 벨만-포드(음수 간선 허용, O(VE), 음수 사이클 탐지) / 플로이드-워셜(모든 쌍, O(V³)), 트리 최단거리(단일 경로 유일 → DFS/BFS 1회 또는 LCA로 O(log N) 질의), 힙 없는 다익스트라 O(V²) vs 힙 기반(밀집 그래프에서 전자가 유리), A* = 다익스트라 + 휴리스틱 h(n)(admissible이면 최단경로 보장, 탐색 범위 축소), 음수 간선→벨만포드 / 음수 사이클→최단거리 정의 불가(벨만포드로 탐지만 가능)

- 언어의 스펙에 따라, 재귀함수의 최적화를 진행해주는 경우가 있습니다. 어떤 경우에 재귀함수의 최적화가 가능하며, 이를 어떻게 최적화 할 수 있을지 설명해 주세요.

```
재귀함수는 함수가 자기 자신을 직접 또는 간접적으로 호출하는 함수입니다. 어떤 문제를 더 작은 크기의
동일한 문제로 쪼갤 수 있을 때 유용하고, 크게 두 부분으로 구성됩니다. 더 이상 쪼개지지 않고 바로 답을
낼 수 있는 기저 조건(Base Case)과, 문제를 더 작게 만들어 자기 자신을 다시 호출하는 재귀 조건
(Recursive Case)입니다. 기저 조건이 없거나 매 호출마다 문제 크기가 실제로 줄어들지 않으면 무한
재귀에 빠지게 됩니다.
```

**꼬리 질문 답변**

- 재귀 함수의 동작 과정을 Call Stack을 활용해서 설명해 주세요.
```
재귀 호출이 일어날 때마다 각 호출은 자신만의 지역 변수, 매개변수, 그리고 복귀할 주소를 담은 스택
프레임(stack frame)을 만들어 Call Stack에 쌓습니다.

함수가 자기 자신을 호출하면 새 스택 프레임이 스택 맨 위에 push되고, 그 호출이 기저 조건에 도달해
값을 반환하면 해당 프레임이 pop되면서 실행 흐름이 자신을 호출했던 이전 프레임으로 돌아가고, 그
지점부터 나머지 코드가 이어서 실행됩니다. 즉 호출이 계속될수록 스택이 위로 쌓이다가(down 방향),
기저 조건에 도달하는 순간부터 거꾸로 pop되며 결과를 조립해 돌아오는(up 방향) LIFO 구조로 동작하는
것입니다.

이 스택 프레임 하나하나가 메모리를 차지하기 때문에, 재귀 깊이가 너무 깊어지면 스택에 할당된 메모리
한계를 넘어서는 StackOverflowError가 발생할 수 있습니다.
```

- 언어의 스펙에 따라, 재귀함수의 최적화를 진행해주는 경우가 있습니다. 어떤 경우에 재귀함수의 최적화가 가능하며, 이를 어떻게 최적화 할 수 있을지 설명해 주세요.
```
꼬리 호출 최적화(Tail Call Optimization, TCO)를 말씀드릴 수 있습니다. 재귀 호출이 함수의 가장
마지막 동작이고, 그 호출의 반환값을 가지고 추가로 뭔가를 더 계산하지 않는 형태를 꼬리 호출(Tail
Call)이라고 합니다.

이 경우가 최적화 가능한 이유는, 현재 스택 프레임이 재귀 호출 이후에 더 이상 할 일이 없다는 게
보장되기 때문입니다. 그래서 컴파일러나 인터프리터는 새 스택 프레임을 추가로 쌓는 대신, 현재 프레임을
재사용해서 마치 반복문(loop)처럼 변환할 수 있습니다. 이렇게 하면 재귀를 아무리 깊게 호출해도 스택
깊이가 늘어나지 않아 StackOverflow 걱정 없이 O(1) 공간으로 동작합니다.

다만 이 최적화가 되려면 재귀 형태를 꼬리 재귀로 바꿔야 하는 경우가 많습니다. 예를 들어
`return n * fact(n-1)` 처럼 곱셈이 재귀 호출 뒤에 남아 있으면 꼬리 호출이 아니고, 누적값을 별도
매개변수로 넘겨 `return fact(n-1, acc * n)` 형태로 바꿔야 컴파일러가 최적화할 수 있습니다.

다만 언어별 지원 여부가 다르다는 점도 함께 말씀드립니다. Scala, Kotlin(tailrec 키워드), 그리고
스킴(Scheme) 같은 함수형 언어 계열은 TCO를 명시적으로 지원하지만, Java와 Python은 디버깅 스택
트레이스가 불명확해지는 문제 등을 이유로 언어/런타임 차원에서 TCO를 보장하지 않습니다. 그런
언어에서는 재귀 깊이가 클 것으로 예상되면 반복문으로 직접 바꾸거나 명시적인 스택 자료구조를 사용해서
재귀를 흉내 내는 방식으로 최적화해야 합니다.
```

**핵심 키워드** → 기저 조건(Base Case)·재귀 조건(Recursive Case), Call Stack과 스택 프레임(down: 호출 누적 / up: 반환값 조립), StackOverflowError, 꼬리 호출(Tail Call)과 TCO(꼬리 재귀를 반복문으로 변환, O(1) 공간), 꼬리 재귀로의 변환(누적값을 매개변수로 전달), 언어별 TCO 지원 여부(Scala/Kotlin O, Java/Python X)

#### 4. MST가 무엇이고, 어떻게 구할 수 있을지 설명해 주세요.

`★★★` · `심화` · 원본 [자료구조·알고리즘 #12](../01-DATA_STRUCTURE_ALGORITHM.md)

<details>
<summary><b>꼬리 질문 3개 (펼치기)</b></summary>

- Kruskal 알고리즘에서 사용하는 Union-Find 자료구조에 대해 설명해 주세요.
- Kruskal 과 Prim 중, 어떤 것이 더 빠를까요?
- Kruskal 과 Prim 알고리즘을 통해 얻어진 결과물은 무조건 트리인가요? 만약 그렇다면 증명해 주세요. 그렇지 않다면, 반례를 설명해 주세요.

</details>

**내 답변**

```
MST(Minimum Spanning Tree, 최소 신장 트리)는 가중치가 있는 연결 무방향 그래프에서, 모든 정점을
포함하면서 사이클 없이 연결하는 부분 그래프(신장 트리) 중에서 간선 가중치의 합이 가장 작은 트리를
말합니다. 정점이 N개라면 반드시 N-1개의 간선으로 구성됩니다.

대표적으로 두 가지 그리디 알고리즘으로 구할 수 있습니다. Kruskal 알고리즘은 모든 간선을 가중치
오름차순으로 정렬한 뒤, 작은 것부터 순서대로 확인하면서 사이클을 만들지 않는 간선만 선택해 나갑니다.
사이클 생성 여부는 보통 Union-Find 자료구조로 판별합니다. Prim 알고리즘은 임의의 한 정점에서
시작해서, 현재까지 만든 트리와 연결된 간선 중 가중치가 가장 작은 간선을 하나씩 선택해 트리를
확장해 나가는 방식입니다. 둘 다 "매 순간 가장 저렴한 선택을 한다"는 그리디 전략을 쓰지만, 최종적으로
항상 최적해(MST)를 보장한다는 점(Cut Property, Cycle Property로 증명됨)이 특징입니다.
```

**꼬리 질문 답변**

- Kruskal 알고리즘에서 사용하는 Union-Find 자료구조에 대해 설명해 주세요.
```
Union-Find(또는 Disjoint Set)는 서로 겹치지 않는 여러 집합을 관리하면서, "두 원소가 같은 집합에
속하는지" 판별하는 자료구조입니다. 이름 그대로 두 가지 핵심 연산을 제공합니다. Find(x)는 x가 속한
집합의 대표(루트) 원소를 찾는 연산이고, Union(x, y)은 x가 속한 집합과 y가 속한 집합을 하나로
합치는 연산입니다.

Kruskal에서는 이걸 사이클 판별에 씁니다. 정렬된 간선을 순서대로 보면서 간선의 양 끝 정점 u, v에
대해 Find(u)와 Find(v)가 같으면 이미 같은 집합, 즉 같은 트리에 속해 있다는 뜻이라 이 간선을 추가하면
사이클이 생기므로 버립니다. 다르면 사이클 걱정 없이 간선을 선택하고 Union(u, v)로 두 집합을
합칩니다.

기본 구현은 각 원소가 부모를 가리키는 트리 형태의 배열로, 최적화 없이는 Find가 최악 O(N)까지 걸릴
수 있습니다. 그래서 두 가지 최적화를 함께 씁니다. 경로 압축(Path Compression)은 Find를 하면서
거쳐간 노드들이 전부 루트를 직접 가리키도록 갱신해서 다음 Find를 빠르게 만들고, Union by
Rank/Size는 항상 크기(또는 높이)가 작은 트리를 큰 트리 밑에 붙여서 트리가 한쪽으로 길어지는 것을
막습니다. 두 최적화를 함께 쓰면 연산당 시간복잡도가 사실상 상수에 가까운 O(α(N))(α는 애커만
함수의 역함수)까지 떨어집니다.
```

- Kruskal 과 Prim 중, 어떤 것이 더 빠를까요?
```
그래프의 밀집도에 따라 다릅니다.

Kruskal은 전체 간선을 정렬하는 데 O(E log E)가 걸리고, 이후 Union-Find 연산은 간선 수만큼
O(E α(N))으로 거의 무시할 수 있는 수준이라 전체적으로 O(E log E)입니다. 정렬 비용이 지배적이기
때문에 간선 수가 적은 희소 그래프(E가 V에 가까운 경우)에서 상대적으로 유리합니다.

Prim은 우선순위 큐(힙)로 구현하면 O(E log V)입니다. 정점 수 V에 대한 로그이기 때문에, 간선이
정점 수 제곱에 가까운 밀집 그래프(E가 V²에 가까운 경우)에서는 Kruskal의 O(E log E) ≈
O(V² log V²)보다 Prim의 O(E log V) ≈ O(V² log V)가 로그의 밑이 되는 값이 작아 상대적으로 유리한
경우가 많습니다. 참고로 Prim을 배열 기반(힙 없이) O(V²)로 구현하면, 아주 밀집된 그래프에서는
이 방식이 오히려 가장 빠를 수도 있습니다.

정리하면, 희소 그래프에서는 Kruskal, 밀집 그래프에서는 Prim(또는 힙 없는 O(V²) Prim)이 이론적으로
더 유리한 경향이 있습니다.
```

- Kruskal 과 Prim 알고리즘을 통해 얻어진 결과물은 무조건 트리인가요? 만약 그렇다면 증명해 주세요. 그렇지 않다면, 반례를 설명해 주세요.
```
네, 원본 그래프가 연결 그래프라는 전제 하에 두 알고리즘의 결과물은 항상 트리입니다.

Kruskal은 알고리즘 자체가 "사이클을 만들지 않는 간선만" 고르도록 설계되어 있기 때문에, 결과물에는
사이클이 생길 수 없습니다. 또한 그래프가 연결되어 있다면 Kruskal은 결국 모든 정점을 하나로 묶을
때까지 간선을 계속 추가하므로 최종적으로 모든 정점이 연결됩니다. 사이클이 없으면서 모든 정점이
연결되어 있다는 것이 곧 트리의 정의이므로, 결과는 트리입니다. 간선 개수 관점에서 봐도, 연결
컴포넌트가 하나로 합쳐질 때까지 Union이 정확히 V-1번 성공하므로 선택된 간선도 정확히 V-1개가
되고, 이는 정점이 V개인 트리의 필요충분조건과 일치합니다.

Prim도 마찬가지입니다. 매번 "현재 트리에 아직 포함되지 않은 정점"으로 연결되는 간선만 선택하도록
설계되어 있기 때문에, 이미 트리 안에 있는 두 정점을 잇는 간선은 애초에 후보에서 배제됩니다. 그래서
사이클이 생기지 않고, 시작 정점에서부터 한 정점씩 계속 트리에 편입시키므로 그래프가 연결되어 있다면
결국 모든 정점을 포함하게 됩니다.

다만 전제 조건인 "원본 그래프가 연결 그래프"가 깨지면 결과가 트리가 아닐 수 있습니다. 그래프가 여러
컴포넌트로 나뉘어 있다면 Kruskal은 각 컴포넌트 내부에서만 트리를 만들어 전체적으로는 트리들의
집합(Minimum Spanning Forest)이 되고, Prim은 애초에 시작 정점이 속한 컴포넌트 하나만 처리하고
다른 컴포넌트의 정점들은 아예 방문하지 못합니다.
```

**핵심 키워드** → MST = 사이클 없이 모든 정점 연결(N-1개 간선) + 가중치 합 최소, Kruskal(간선 정렬 + Union-Find로 사이클 판별, O(E log E)) vs Prim(정점에서 확장, 힙 기반 O(E log V)), Union-Find(경로 압축·Union by Rank로 O(α(N))), 희소 그래프→Kruskal 유리 / 밀집 그래프→Prim 유리, 두 알고리즘 모두 연결 그래프 전제 시 결과는 항상 트리(전제 깨지면 MSF)

**막힌 부분 / 다시 볼 것** →

#### 5. Thread Safe 한 자료구조가 있을까요? 없다면, 어떻게 Thread Safe 하게 구성할 수 있을까요?

`★★★` · `심화` · 원본 [자료구조·알고리즘 #13](../01-DATA_STRUCTURE_ALGORITHM.md)

<details>
<summary><b>꼬리 질문 2개 (펼치기)</b></summary>

- 배열의 길이를 알고 있다면, 조금 더 빠른 Thread Safe 한 연산을 만들 순 없을까요?
- 사용하고 있는 언어의 자료구조는 Thread Safe 한가요? 그렇지 않다면, Thread Safe 한 Wrapped Data Structure 를 제공하고 있나요?

</details>

**내 답변**

```
기본 제공되는 대부분의 자료구조(ArrayList, HashMap 등)는 성능을 위해 기본적으로 Thread Safe하지
않습니다. 여러 스레드가 동시에 값을 추가·삭제하면 내부 상태가 깨지거나, Java 7 HashMap의 resize
버그처럼 무한 루프에 빠지거나, 데이터가 유실될 수 있습니다.

그래서 언어들은 보통 Thread Safe한 버전을 별도로 제공합니다. 이를 구현하는 방법은 크게 두 가지로
나뉩니다. 하나는 자료구조의 모든 메서드에 락(주로 synchronized 같은 상호 배제 락)을 걸어서, 한
시점에 하나의 스레드만 접근할 수 있게 강제하는 방식입니다. 구현이 단순하지만 락을 얻기 위해 대기하는
스레드가 많아지면 성능이 크게 떨어집니다. 다른 하나는 CAS(Compare-And-Swap) 같은 하드웨어
수준의 원자적 연산을 사용해서 락 없이(lock-free) 동시성을 제어하는 방식입니다. 락을 아예 걸지
않거나 아주 좁은 범위에만 걸기 때문에 성능이 더 좋지만, 구현이 훨씬 복잡합니다.
```

**꼬리 질문 답변**

- 배열의 길이를 알고 있다면, 조금 더 빠른 Thread Safe 한 연산을 만들 순 없을까요?
```
네, 가능합니다. 길이가 고정되어 있고 리사이징이 없다는 전제라면, 배열 전체에 하나의 큰 락을 거는
대신 인덱스 단위로 락의 범위를 잘게 쪼갤 수 있습니다.

가장 단순한 방법은 인덱스마다 별도의 락(또는 락 배열을 정해진 개수만큼 두고 index % lockCount로
매핑하는 Lock Striping)을 두는 것입니다. 이러면 서로 다른 인덱스에 접근하는 스레드들은 서로
기다릴 필요 없이 동시에 진행할 수 있어서, 배열 전체를 잠그는 것보다 훨씬 병렬성이 높아집니다.

더 나아가서, 배열의 각 원소가 int나 참조값처럼 원자적으로 읽고 쓸 수 있는 타입이라면 락 자체가
필요 없을 수도 있습니다. Java의 AtomicIntegerArray나 AtomicReferenceArray처럼, 각 인덱스의
값을 CAS 연산으로 직접 갱신하면 락 없이도 Thread Safe한 단일 원소 갱신을 O(1)에 처리할 수
있습니다. 다만 이건 원소 하나에 대한 단일 연산에 한정되고, 여러 인덱스를 함께 원자적으로 바꿔야 하는
연산에는 여전히 별도의 동기화가 필요합니다.
```

- 사용하고 있는 언어의 자료구조는 Thread Safe 한가요? 그렇지 않다면, Thread Safe 한 Wrapped Data Structure 를 제공하고 있나요?
```
(사용 언어에 맞게 채워 넣기)
예) Java: ArrayList, HashMap, LinkedList 등 기본 컬렉션은 Thread Safe하지 않습니다. 대신 여러
    대안을 제공합니다. Collections.synchronizedList(list)처럼 기존 컬렉션을 감싸서 모든 메서드에
    synchronized를 붙이는 래퍼가 있고, java.util.concurrent 패키지에는 ConcurrentHashMap(버킷
    단위 락 + CAS), CopyOnWriteArrayList(쓰기 시 배열 전체를 복사해서 읽기는 락 없이 빠른, 읽기가
    압도적으로 많은 상황에 적합), ConcurrentLinkedQueue(CAS 기반 lock-free 큐) 같은 정교하게
    설계된 동시성 자료구조들이 있습니다.
예) Python: GIL(Global Interpreter Lock) 덕분에 바이트코드 한 개 단위의 연산(예: list.append)은
    사실상 원자적으로 보이는 경우가 많지만, "값 확인 후 갱신"처럼 여러 연산이 묶인 로직은 여전히
    Race Condition에서 자유롭지 않습니다. queue.Queue처럼 명시적으로 Thread Safe하게 설계된
    자료구조도 별도로 제공됩니다.
```

**핵심 키워드** → 기본 컬렉션은 대부분 Thread Safe 하지 않음(성능 우선), 락 기반(synchronized 래퍼, 단순하지만 경합 시 성능 저하) vs Lock-free(CAS 기반, 복잡하지만 고성능), Lock Striping(인덱스 단위로 락 세분화), Atomic 클래스(AtomicIntegerArray 등, 원소 단위 CAS로 락 없는 갱신), 언어별 제공(Java ConcurrentHashMap·CopyOnWriteArrayList, Python GIL과 queue.Queue)

**막힌 부분 / 다시 볼 것** →

#### 6. 문자열을 저장하고, 처리하는 주요 자료구조 및 알고리즘 (Trie, KMP, Rabin Karp 등) 에 대해 설명해 주세요.

`★★★` · `심화` · 원본 [자료구조·알고리즘 #14](../01-DATA_STRUCTURE_ALGORITHM.md)

> 지정된 꼬리 질문이 없습니다. 답변자가 스스로 심화 주제를 하나 정해 덧붙이세요.

**내 답변**

```
문자열 처리에서 자주 등장하는 자료구조·알고리즘을 목적별로 정리하면 다음과 같습니다.

Trie(트라이)는 문자열들을 문자 단위로 트리 형태로 저장하는 자료구조입니다. 루트에서부터 한 글자씩
간선을 따라 내려가고, 공통 접두사(prefix)를 가진 문자열들은 경로를 공유합니다. 문자열 하나를
삽입·탐색하는 데 걸리는 시간은 문자열 길이 L에 대해 O(L)로, 저장된 문자열 개수와 무관합니다. 그래서
자동완성, 사전 검색처럼 "특정 접두사로 시작하는 단어들"을 빠르게 찾아야 하는 상황에 적합합니다.
단점은 각 노드가 알파벳 크기만큼의 자식 포인터(또는 맵)를 가져야 해서 메모리 사용량이 클 수 있다는
점입니다.

KMP(Knuth-Morris-Pratt)는 텍스트 안에서 패턴 문자열을 찾는 문자열 매칭 알고리즘입니다. 단순
매칭은 불일치가 날 때마다 패턴을 한 칸씩만 옮겨 다시 처음부터 비교해서 O(NM)이 걸리는데, KMP는
패턴 자신의 접두사·접미사가 겹치는 정보를 미리 계산한 실패 함수(failure function, 부분 일치
테이블)를 이용해서 불일치가 나도 이미 비교했던 부분을 다시 비교하지 않고 패턴을 필요한 만큼만
건너뛸 수 있습니다. 전처리 O(M), 매칭 O(N)으로 전체 O(N+M)에 처리합니다.

Rabin-Karp는 패턴과 텍스트의 부분 문자열을 직접 비교하는 대신, 각각을 해시값으로 바꿔서 해시값이
같을 때만 실제 문자열을 비교하는 방식입니다. 텍스트를 한 칸씩 미끄러뜨릴 때마다 해시를 처음부터
다시 계산하지 않고, 롤링 해시(Rolling Hash)로 앞의 문자 하나를 빼고 뒤의 문자 하나를 더하는 식으로
O(1)에 갱신합니다. 평균적으로 O(N+M)이지만, 해시 충돌이 잦으면(모든 부분 문자열의 해시가 같은
경우 등) 매번 실제 비교까지 해야 해서 최악 O(NM)이 될 수 있습니다. 대신 여러 패턴을 동시에
찾아야 하는 경우로 확장하기 쉽다는 장점이 있습니다.
```

**스스로 정한 심화 주제 — Z 알고리즘과 접미사 배열(Suffix Array)**
```
KMP·Rabin-Karp가 "패턴 하나를 텍스트에서 찾는" 문제에 최적화되어 있다면, 더 일반적인 문자열
문제(부분 문자열 관련 질의가 여러 번 반복되는 경우)에서는 접미사 배열(Suffix Array)이 자주 쓰입니다.

접미사 배열은 문자열의 모든 접미사(suffix)를 사전순으로 정렬한 뒤, 그 시작 인덱스들을 배열로
저장한 구조입니다. 이 배열과, 인접한 접미사끼리 공통으로 겹치는 접두사 길이를 담은 LCP(Longest
Common Prefix) 배열을 함께 구성해두면, 두 부분 문자열이 얼마나 겹치는지, 특정 부분 문자열이 몇 번
등장하는지 같은 질의를 이진 탐색이나 슬라이딩 윈도우로 O(log N)~O(N) 수준에 답할 수 있습니다.
접미사 배열 자체는 접미사 자동자(Suffix Automaton)나 접미사 트리(Suffix Tree)로 대체할 수도
있는데, 접미사 트리가 이론적으로 더 강력하지만(선형 시간 구축) 구현이 매우 까다로워서 실무·대회
모두에서 접미사 배열 + LCP 조합이 훨씬 널리 쓰입니다.

Z 알고리즘은 KMP와 비슷한 목적(패턴 매칭)으로도 쓰이지만 조금 다른 관점으로 접근합니다. 문자열
S에 대해 Z[i]를 "S와 S를 i번째 위치부터 시작하는 부분 문자열이 공통으로 갖는 접두사의 길이"로
정의하는 Z-배열을 O(N)에 구축합니다. 패턴 매칭을 하려면 `패턴 + 구분자 + 텍스트` 형태로 문자열을
이어붙인 뒤 Z-배열을 구해서, 패턴 길이만큼 Z값이 나오는 위치를 찾으면 그게 곧 매칭된 위치입니다.
KMP의 실패 함수보다 정의가 더 직관적이라는 평이 있어서, 실패 함수 자체를 헷갈려 하는 경우 Z
알고리즘으로 문자열 매칭 문제에 접근하는 것도 좋은 대안이 됩니다.
```

**핵심 키워드** → Trie(접두사 공유, 삽입·탐색 O(L)), KMP(실패 함수/부분일치테이블로 불필요한 재비교 제거, O(N+M)), Rabin-Karp(롤링 해시로 O(1) 해시 갱신, 평균 O(N+M)·최악 O(NM)), 접미사 배열(Suffix Array) + LCP 배열(반복 질의에 강함), Z 알고리즘(Z-배열, O(N), KMP의 대안), 접미사 트리/자동자(이론적으로 강력하나 구현 난이도 높음)

**막힌 부분 / 다시 볼 것** →

#### 7. 이진탐색이 무엇인지 설명하고, 시간복잡도를 증명해 보세요.

`★★☆` · `필수` · 원본 [자료구조·알고리즘 #15](../01-DATA_STRUCTURE_ALGORITHM.md)

<details>
<summary><b>꼬리 질문 3개 (펼치기)</b></summary>

- Lower Bound, Upper Bound 는 무엇이고, 이를 어떻게 구현할 수 있을까요?
- 이진탐색의 논리를 적용하여 삼진탐색을 작성한다고 가정한다면, 시간복잡도는 어떻게 변화할까요? (실제 존재하는 삼진탐색 알고리즘은 무시하세요!)
- 기존 이진탐색 로직에서 부등호의 범위가 바뀐다면, (ex. <= 라면 <로, <이라면 <= 로) 결과가 달라질까요?

**내 답변**

```
이진탐색은 정렬된 배열에서 찾고자 하는 값을 탐색 범위를 절반씩 줄여가며 찾는 알고리즘입니다. 배열의
중간 인덱스 값을 목표값과 비교해서, 목표값이 더 크면 오른쪽 절반, 더 작으면 왼쪽 절반만 다시
탐색하는 과정을 값을 찾거나 탐색 범위가 없어질 때까지 반복합니다.

시간복잡도를 증명하면, 매 비교마다 탐색 범위(원소 개수)가 정확히 절반으로 줄어듭니다. 초기 범위가
n일 때, k번 비교한 뒤 남은 범위는 n / 2^k입니다. 이 값이 1 이하가 되는(즉 더 이상 나눌 수 없는)
시점까지 반복하므로 n / 2^k ≤ 1, 즉 2^k ≥ n, 양변에 로그를 취하면 k ≥ log₂n이 됩니다. 따라서
필요한 비교 횟수는 최대 ⌈log₂n⌉ + 1번 정도이고, 이는 곧 시간복잡도가 O(log n)임을 의미합니다.
```

**꼬리 질문 답변**

- Lower Bound, Upper Bound 는 무엇이고, 이를 어떻게 구현할 수 있을까요?
```
Lower Bound는 정렬된 배열에서 "목표값 이상인 값이 처음 등장하는 위치"를 찾는 것이고, Upper Bound는
"목표값을 초과하는 값이 처음 등장하는 위치"를 찾는 것입니다. 즉 [lower_bound, upper_bound) 구간이
바로 배열에서 목표값과 정확히 같은 원소들이 모여 있는 구간이 되고, 그 차이(upper - lower)가 곧
목표값의 개수입니다.

구현은 일반 이진탐색과 비슷하지만, 값을 찾자마자 반환하지 않고 조건을 만족하는 가장 왼쪽(또는 가장
오른쪽) 경계를 계속 좁혀나가는 방식으로 짭니다. 예를 들어 Lower Bound는 mid 값이 목표값 이상이면
그 위치가 정답 후보이므로 결과를 기록해두고 오른쪽 경계를 mid로 좁히고, mid 값이 목표값보다 작으면
왼쪽 경계를 mid+1로 옮기는 식으로, `array[mid] >= target`을 기준으로 계속 범위를 좁혀서 최종적으로
두 경계가 만나는 지점을 반환합니다. Upper Bound는 비교 조건만 `array[mid] > target`으로 바꾸면
됩니다.
```

- 이진탐색의 논리를 적용하여 삼진탐색을 작성한다고 가정한다면, 시간복잡도는 어떻게 변화할까요? (실제 존재하는 삼진탐색 알고리즘은 무시하세요!)
```
결론적으로 점근적 시간복잡도의 차수(order)는 여전히 O(log n)으로 동일하지만, 로그의 밑이 바뀌고
비교 횟수 자체는 오히려 늘어나서 상수 인자 면에서는 이진탐색보다 불리해집니다.

범위를 세 구간으로 나누려면 두 개의 기준점이 필요하므로, 한 번의 "단계"마다 2번의 비교를 하고
범위는 1/3로 줄어듭니다. 범위가 1이 될 때까지 필요한 단계 수는 log₃n이고, 여기에 단계당 비교
2번을 곱하면 총 비교 횟수는 약 2 log₃n = 2 log n / log 3 ≈ 1.26 log₂n입니다. 반면 이진탐색은
단계당 비교 1번, 필요한 단계는 log₂n이므로 총 비교 횟수는 log₂n입니다.

즉 삼진탐색은 이진탐색보다 약 26% 더 많은 비교를 수행하게 되어, 둘 다 O(log n)이라는 같은
점근적 등급에 속하지만 실제 비교 횟수(상수 인자)는 이진탐색이 더 적어 실용적으로 더 유리합니다.
```

- 기존 이진탐색 로직에서 부등호의 범위가 바뀐다면, (ex. <= 라면 <로, <이라면 <= 로) 결과가 달라질까요?
```
네, 결과가 크게 달라질 수 있습니다. 부등호를 어떻게 쓰느냐가 반복문의 종료 조건, 그리고 left/right를
갱신할 때 mid를 포함할지 말지를 결정하기 때문에, 짝을 맞추지 않고 하나만 바꾸면 무한루프에 빠지거나
경계값을 놓치는 버그로 이어집니다.

예를 들어 반복문 조건을 `while (left <= right)`로 쓰는 표준적인 구현에서는, 값을 못 찾았을 때
`right = mid - 1`, `left = mid + 1`처럼 mid를 탐색 범위에서 확실히 제외해야 합니다. 만약 조건을
`while (left < right)`로 바꾸면서 갱신 로직은 그대로 두면(`right = mid`처럼 mid를 포함한 채로
좁히면), 어떤 경우엔 left와 right가 영원히 좁혀지지 않아 무한루프에 빠질 수 있습니다.

그래서 부등호를 바꾸려면 "이 범위가 닫힌 구간인지 반열린 구간인지"부터 다시 정의하고, 그에 맞춰
초기 range·종료 조건·mid 갱신 로직을 전부 일관되게 맞춰야 합니다. 특히 Lower/Upper Bound처럼
"경계"를 찾는 이진탐색은 `<`와 `<=`를 어디에 쓰느냐에 따라 lower bound가 되기도, upper bound가
되기도 하므로 더욱 조심해서 다뤄야 하는 부분입니다.
```

**핵심 키워드** → 매 비교마다 탐색 범위 1/2로 감소 → O(log n) 증명(n/2^k ≤ 1), Lower Bound(값 이상 첫 위치)/Upper Bound(값 초과 첫 위치)와 [lower, upper) 구간 = 개수, 삼진탐색은 여전히 O(log n)이지만 비교 횟수는 이진탐색보다 많음(2log₃n ≈ 1.26 log₂n), 부등호(<, <=)는 구간이 닫힌 구간/반열린 구간인지와 함께 일관되게 맞춰야 함(안 그러면 무한루프·경계 누락)

**막힌 부분 / 다시 볼 것** →

#### 8. 그리디 알고리즘과 동적 계획법을 비교해 주세요.

`★★☆` · `필수` · 원본 [자료구조·알고리즘 #16](../01-DATA_STRUCTURE_ALGORITHM.md)

<details>
<summary><b>꼬리 질문 2개 (펼치기)</b></summary>

- 그렇다면, 어떤 경우에 각각의 기법을 사용할 수 있을까요?
- 그렇다면, 동적 계획법으로 풀 수 있는 모든 문제는 재귀로 변환하여 풀 수 있나요?

</details>

**내 답변**

```
둘 다 큰 문제를 작은 부분 문제로 나눠서 푼다는 공통점이 있지만, "부분 문제의 해를 어떻게 결정하고
조합하느냐"에서 결정적인 차이가 납니다.

그리디(Greedy) 알고리즘은 매 단계에서 지금 이 순간 가장 좋아 보이는 선택을 하고, 그 선택을 절대
번복하지 않습니다. 각 단계의 부분 최적해를 그대로 쌓아 올려서 전체 최적해가 되기를 "기대"하는
방식입니다. 구현이 단순하고 빠르지만(대체로 O(n log n) 이하), 문제가 그리디 선택 속성(Greedy
Choice Property)과 최적 부분 구조(Optimal Substructure)를 만족한다는 게 증명된 경우에만 최적해를
보장합니다.

동적 계획법(DP)은 부분 문제들이 서로 겹칠 수 있다는 전제 하에, 각 부분 문제의 해를 한 번 계산하면
저장해뒀다가(메모이제이션/테이블화) 재사용하면서, 가능한 선택지들을 모두 고려해 그중 최적인 것을
고릅니다. 그리디처럼 당장의 최선만 선택하는 게 아니라 여러 경우의 수를 비교하기 때문에, 그리디로는
최적해를 보장할 수 없는 문제에서도 정확한 최적해를 구할 수 있는 대신, 일반적으로 그리디보다 시간·공간
비용이 더 큽니다.
```

**꼬리 질문 답변**

- 그렇다면, 어떤 경우에 각각의 기법을 사용할 수 있을까요?
```
문제가 그리디 선택 속성과 최적 부분 구조를 둘 다 만족한다는 게 증명되면 그리디를 씁니다. 그리디
선택 속성이란 "각 단계에서 지역적으로 최적인 선택을 하면, 그 선택이 전체 최적해의 일부가 됨이
보장된다"는 성질이고, 최적 부분 구조란 "전체 문제의 최적해가 부분 문제의 최적해들로 구성될 수 있다"는
성질입니다. 예를 들어 활동 선택 문제(회의실 배정)는 "종료 시간이 가장 빠른 회의를 먼저 고르는" 그리디
선택이 항상 최적해로 이어진다는 게 증명되어 있어서 그리디로 풀 수 있습니다.

반대로 이런 증명이 없거나, 당장의 최선이 전체 최적을 보장하지 못하는 문제(예: 0/1 배낭 문제 — 그리디로
가치/무게 비율이 높은 것부터 담으면 부분 최적에 빠질 수 있음)에는 DP를 씁니다. DP는 그리디와 달리
"이 선택을 하면 vs 안 하면"처럼 여러 선택지를 모두 시도해보고 그중 최선을 고르기 때문에, 반례가
존재해 그리디가 틀리는 문제에서도 정확한 답을 보장합니다. 실무적으로는 먼저 그리디로 반례를
찾아보려고 시도하고, 반례가 발견되거나 최적성을 증명하기 어렵다면 DP로 접근 전략을 바꾸는 흐름이
일반적입니다.
```

- 그렇다면, 동적 계획법으로 풀 수 있는 모든 문제는 재귀로 변환하여 풀 수 있나요?
```
네, 가능합니다. DP가 성립하기 위한 전제 조건 자체가 "최적 부분 구조"와 "부분 문제의 중복"인데, 이
두 조건은 본질적으로 재귀적 정의와 맞닿아 있습니다. 큰 문제의 해를 더 작은 크기의 동일한 문제들의
해로 표현할 수 있다는 것 자체가 재귀 점화식(recurrence relation)으로 표현 가능하다는 뜻이기
때문입니다.

실제로 DP는 보통 두 가지 방식으로 구현되는데, 하나가 바로 재귀 기반입니다. 하향식(Top-down)
방식은 재귀 호출로 문제를 자연스럽게 부분 문제로 쪼개면서, 이미 계산한 부분 문제의 결과를
메모이제이션(캐시)에 저장해두고 다시 필요할 때 재귀 호출 없이 바로 꺼내 쓰는 방식입니다. 반대로
상향식(Bottom-up) 방식은 가장 작은 부분 문제부터 반복문으로 순서대로 테이블을 채워나가서, 재귀
호출과 그로 인한 함수 호출 오버헤드·스택 오버플로우 위험 없이 같은 결과를 얻습니다.

따라서 모든 DP 문제는 하향식 재귀(+메모이제이션)로 풀 수 있고, 반대로 모든 재귀 기반 DP는 상향식
반복문으로도 변환할 수 있습니다. 다만 실무에서는 재귀 깊이가 매우 깊어질 수 있는 문제(스택 오버플로우
위험)나 반복적인 함수 호출 오버헤드를 피하고 싶을 때, 재귀로 먼저 로직을 설계한 뒤 반복문 기반의
상향식으로 변환해서 최종 구현하는 경우가 많습니다.
```

**핵심 키워드** → 그리디(매 단계 지역 최적, 번복 없음, 그리디 선택 속성+최적 부분 구조 증명 필요) vs DP(모든 선택지 비교, 부분 문제 중복 활용, 메모이제이션/테이블화), 0/1 배낭 문제(그리디 실패 사례) vs 회의실 배정(그리디 성공 사례), DP의 두 구현 방식(Top-down 재귀+메모이제이션 / Bottom-up 반복문 테이블), 모든 DP는 재귀 점화식으로 표현 가능 → 재귀 변환 가능(실무에선 스택 오버플로우·호출 오버헤드 피하려 Bottom-up 선호)

**막힌 부분 / 다시 볼 것** →

#### 9. Call By Value와 Call By Reference의 차이를 본인의 언어를 기반으로 설명해 주세요.

`★★☆` · `필수` · 원본 [개발상식·기타 #7](../05-ETC.md)

<details>
<summary><b>꼬리 질문 1개 (펼치기)</b></summary>

- 사실 이 질문에는 약간의 낚시가 있습니다. 과연 모든 언어에 저 개념이 존재할까요?

</details>

**내 답변**

```
Call by Value(값에 의한 호출)는 함수를 호출할 때 인자의 "값을 복사"해서 넘기는 방식입니다. 함수
내부에서 매개변수를 변경해도, 그건 복사본을 바꾸는 것일 뿐 호출자가 가지고 있던 원본 변수에는 아무
영향이 없습니다.

Call by Reference(참조에 의한 호출)는 인자의 "메모리 주소(참조) 자체"를 넘기는 방식입니다. 함수와
호출자가 같은 메모리 공간을 가리키고 있기 때문에, 함수 내부에서 매개변수가 가리키는 값을 바꾸면
호출자의 원본 변수도 함께 바뀝니다.

(사용 언어에 맞게 채워 넣기)
예) Java는 원시 타입(int, double 등)이든 객체 타입이든 항상 Call by Value입니다. 다만 객체를
    넘길 때는 "객체에 대한 참조값 자체"를 복사해서 넘기기 때문에, 복사된 참조가 원본과 같은 객체를
    가리키고 있어 그 객체의 필드를 바꾸면 호출자 쪽에서도 변경이 보입니다. 하지만 함수 내부에서
    매개변수(참조 변수) 자체를 다른 객체로 재할당해도 호출자의 원본 참조는 바뀌지 않습니다. 이런
    특성 때문에 흔히 "Call by Reference처럼 보이지만 사실은 참조값을 값으로 복사하는 Call by
    Value"라고 설명합니다.
```

**꼬리 질문 답변**

- 사실 이 질문에는 약간의 낚시가 있습니다. 과연 모든 언어에 저 개념이 존재할까요?
```
아니요, 정확히는 이 두 용어를 있는 그대로 적용할 수 없는 언어들이 많습니다.

먼저 Java나 Python처럼 참조 타입/객체 타입을 다루는 대부분의 현대 언어는 엄밀히 말하면 순수한 Call
by Reference를 지원하지 않습니다. 이런 언어들은 "객체에 대한 참조(주소)"라는 값 자체를 복사해서
넘기는 것이라, 더 정확한 용어로는 Call by Object Reference 또는 Call by Sharing이라고 부릅니다.
이게 왜 Call by Reference와 다르냐면, 진짜 Call by Reference라면 함수 안에서 매개변수 자체를
다른 객체로 재할당했을 때 호출자의 원본 변수도 그 새 객체를 가리키도록 바뀌어야 하는데, Java나
Python에서는 그런 재할당이 호출자에게 전혀 영향을 주지 않기 때문입니다. 즉 "객체 내부 값 수정은
보이지만, 참조 자체의 재할당은 안 보인다"는 점에서 진짜 Call by Reference와 구분됩니다.

반면 C++의 참조 매개변수(`int& x`)나 C#의 `ref`/`out` 키워드는 명시적으로 진짜 Call by
Reference를 지원해서, 함수 안에서 매개변수를 재할당하면 호출자의 원본 변수도 실제로 바뀝니다.

그래서 이 질문의 낚시 포인트는, "당신이 쓰는 언어가 Call by Value와 Call by Reference 둘 중
하나로 완전히 설명되는 게 맞는지", 그리고 흔히 오해하는 것처럼 "Java의 객체 매개변수 전달을 Call
by Reference라고 부르는 게 정확한 표현인지"를 되짚어보게 만드는 데 있다고 생각합니다. 정확히
말하면 Java는 순수하게 Call by Value만 존재하는 언어이고, Call by Reference라는 개념 자체가
아예 없습니다.
```

**핵심 키워드** → Call by Value(값 복사, 원본 영향 없음) vs Call by Reference(주소 자체 전달, 매개변수 재할당도 원본에 반영), Java/Python은 "참조값을 값으로 복사"(Call by Object Reference/Call by Sharing) — 필드 변경은 보이지만 재할당은 원본에 반영 안 됨, C++ 참조(`&`)·C# ref/out은 진짜 Call by Reference, Java에는 Call by Reference 개념 자체가 존재하지 않음(흔한 오해)

#### [정렬 1/6] 버블 · 선택 · 삽입 정렬

**구현 범위** — 세 정렬을 각각 구현하고, 최선/평균/최악 케이스와 안정성(stable) 여부를 비교

```java
class SortWarmup {

    // 버블 정렬 — 인접한 두 원소를 비교하며 교환, 조기 종료 최적화 포함
    static void bubbleSort(int[] arr) {
        int n = arr.length;
        for (int i = 0; i < n - 1; i++) {
            boolean swapped = false;
            for (int j = 0; j < n - 1 - i; j++) {
                if (arr[j] > arr[j + 1]) {
                    int tmp = arr[j];
                    arr[j] = arr[j + 1];
                    arr[j + 1] = tmp;
                    swapped = true;
                }
            }
            if (!swapped) break; // 이미 정렬됐으면 조기 종료
        }
    }

    // 선택 정렬 — 남은 범위에서 최솟값을 찾아 맨 앞과 교환
    static void selectionSort(int[] arr) {
        int n = arr.length;
        for (int i = 0; i < n - 1; i++) {
            int minIdx = i;
            for (int j = i + 1; j < n; j++) {
                if (arr[j] < arr[minIdx]) {
                    minIdx = j;
                }
            }
            int tmp = arr[i];
            arr[i] = arr[minIdx];
            arr[minIdx] = tmp;
        }
    }

    // 삽입 정렬 — 이미 정렬된 앞부분에 새 원소를 알맞은 위치로 밀어 넣음
    static void insertionSort(int[] arr) {
        int n = arr.length;
        for (int i = 1; i < n; i++) {
            int key = arr[i];
            int j = i - 1;
            while (j >= 0 && arr[j] > key) {
                arr[j + 1] = arr[j];
                j--;
            }
            arr[j + 1] = key;
        }
    }
}
```

**세 정렬 비교**

| 알고리즘 | 최선 | 평균 | 최악 | Stable | 비고 |
|---|:--:|:--:|:--:|:--:|---|
| 버블 정렬 | O(n) (조기 종료 시) | O(n²) | O(n²) | ✅ | 교환이 잦아 실제로 셋 중 가장 느린 경우가 많음 |
| 선택 정렬 | O(n²) | O(n²) | O(n²) | ❌ | 입력 상태와 무관하게 항상 n²/2 비교(비적응형), 교환 횟수는 최대 n-1로 가장 적음 |
| 삽입 정렬 | O(n) (거의 정렬된 경우) | O(n²) | O(n²) | ✅ | 적응형(adaptive) — 거의 정렬된 데이터에 특히 강함 |

**시간복잡도** → 셋 다 평균/최악 O(n²), 버블·삽입은 최선 O(n) (적응형)
**공간복잡도** → 셋 다 in-place 정렬이라 O(1) (입력 배열 외 추가 공간 거의 없음)

### 응용 문항

> 원본: [손코딩 연습 문항](../06-ALGORITHM.md) · IDE 없이 손으로 먼저 써본 뒤, 스터디에서 서로 비교합니다.

#### 9. 길이가 N인 배열이 있을 때, 이 배열에서 K 번째로 큰 수를 추출하는 프로그램을 작성해 보세요. (단, 시간복잡도는 O(NlogN) 보다 작아야 합니다.)

```java
import java.util.Random;

class KthLargest {

    // Quickselect — 퀵 정렬의 분할(partition) 아이디어를 재사용, 한쪽만 재귀적으로 탐색
    static int findKthLargest(int[] arr, int k) {
        // K번째로 "큰" 수 = 오름차순 정렬했을 때 뒤에서 K번째
        // = 0-indexed 기준으로 정렬 후 인덱스 (n - k)에 해당하는 값
        return quickSelect(arr, 0, arr.length - 1, arr.length - k);
    }

    private static int quickSelect(int[] arr, int left, int right, int targetIdx) {
        if (left == right) return arr[left];

        Random rand = new Random();
        int pivotIdx = left + rand.nextInt(right - left + 1); // 랜덤 pivot으로 최악 케이스 방지
        pivotIdx = partition(arr, left, right, pivotIdx);

        if (pivotIdx == targetIdx) {
            return arr[pivotIdx];
        } else if (targetIdx < pivotIdx) {
            return quickSelect(arr, left, pivotIdx - 1, targetIdx); // 왼쪽만 재귀
        } else {
            return quickSelect(arr, pivotIdx + 1, right, targetIdx); // 오른쪽만 재귀
        }
    }

    private static int partition(int[] arr, int left, int right, int pivotIdx) {
        int pivotValue = arr[pivotIdx];
        swap(arr, pivotIdx, right); // pivot을 맨 끝으로 이동
        int storeIdx = left;
        for (int i = left; i < right; i++) {
            if (arr[i] < pivotValue) {
                swap(arr, storeIdx, i);
                storeIdx++;
            }
        }
        swap(arr, storeIdx, right); // pivot을 제자리로 복귀
        return storeIdx;
    }

    private static void swap(int[] arr, int i, int j) {
        int tmp = arr[i];
        arr[i] = arr[j];
        arr[j] = tmp;
    }
}
```

**풀이 설명**

퀵 정렬처럼 pivot으로 배열을 분할하되, 정렬처럼 양쪽을 모두 재귀 호출하지 않고 **찾는 인덱스가 속한
한쪽만** 재귀적으로 파고드는 Quickselect 방식을 사용했습니다. pivot을 기준으로 분할한 뒤 pivot이
놓인 위치가 목표 인덱스와 정확히 같으면 바로 답이고, 목표가 왼쪽에 있으면 왼쪽만, 오른쪽에 있으면
오른쪽만 다시 partition 합니다. 이렇게 한쪽을 완전히 버리기 때문에 매번 절반씩 문제 크기가 줄어들어
평균적으로 전체를 정렬하는 것보다 훨씬 빠릅니다. pivot을 매번 무작위로 골라서, 이미 정렬된 배열
같은 입력에서 특정 위치를 고정으로 고르는 구현이 겪는 최악의 경우(O(n²))를 확률적으로 회피합니다.

크기 K인 최소 힙을 유지하며 배열을 한 번 순회하는 방법(힙 크기를 K로 고정하고, 새 값이 힙의 최솟값보다
크면 교체)으로도 O(N log K)에 풀 수 있어, K가 N에 비해 아주 작을 때는 이 방식이 더 유리합니다.

**시간복잡도** → 평균 O(N) (매 단계 범위가 절반씩 줄어드는 등비수열 합), 최악 O(N²) (pivot이 계속 한쪽으로 치우치는 경우, 랜덤 pivot으로 확률 최소화)
**공간복잡도** → O(1) 추가 공간 (in-place partition), 재귀 호출 스택은 평균 O(log N)
