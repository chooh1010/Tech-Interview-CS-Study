#### 1. 시스템 콜이 무엇인지 설명해 주세요.

`★★☆` · `필수` · 원본 [운영체제 #1](../02-OPERATING_SYSTEM.md)

<details>
<summary><b>꼬리 질문 6개 (펼치기)</b></summary>

- 우리가 사용하는 시스템 콜의 예시를 들어주세요.
- 시스템 콜이, 운영체제에서 어떤 과정으로 실행되는지 설명해 주세요.
- 시스템 콜의 유형에 대해 설명해 주세요.
- 운영체제의 Dual Mode 에 대해 설명해 주세요.
- 왜 유저모드와 커널모드를 구분해야 하나요?
- 서로 다른 시스템 콜을 어떻게 구분할 수 있을까요?

</details>

**내 답변**

```
시스템 콜은 사용자 프로그램(유저 모드)이 운영체제 커널이 관리하는 자원과 기능(파일 입출력, 프로세스
생성, 메모리 할당, 네트워크 통신 등)을 이용하기 위해 커널에게 요청을 보내는 인터페이스입니다.

파일을 열거나 새 프로세스를 만드는 것처럼 하드웨어에 직접 접근하거나 시스템 전역에 영향을 주는 작업은
유저 프로그램이 마음대로 수행하게 두면 안전성과 보안이 깨지기 때문에, 이런 특권 작업은 오직 커널만
수행할 수 있게 제한되어 있습니다. 유저 프로그램은 이런 기능이 필요할 때 시스템 콜이라는 정해진
관문을 통해서만 커널에게 "대신 실행해 달라"고 요청할 수 있습니다.
```

**꼬리 질문 답변**

- 우리가 사용하는 시스템 콜의 예시를 들어주세요.
```
크게 카테고리별로 예를 들 수 있습니다. 프로세스 제어에는 fork(), exec(), exit(), wait()가 있고,
파일 관리에는 open(), read(), write(), close()가 있습니다. 메모리 관리에는 mmap(), brk()가,
장치 관리에는 ioctl()이, 프로세스 간 통신에는 pipe(), shmget()가 있습니다.

평소에 직접 쓰는 printf(), malloc() 같은 표준 라이브러리 함수들도 내부적으로는 결국 write(),
mmap()/brk() 같은 시스템 콜을 감싸고 있는 래퍼(wrapper)인 경우가 많아서, 우리가 의식하지 못한
채로도 시스템 콜을 매우 자주 사용하고 있습니다.
```

- 시스템 콜이, 운영체제에서 어떤 과정으로 실행되는지 설명해 주세요.
```
전체 흐름은 유저 모드에서 커널 모드로 전환됐다가, 요청을 처리하고 다시 유저 모드로 복귀하는
과정입니다.

먼저 유저 프로그램이 시스템 콜을 호출하면, 어떤 시스템 콜인지 식별하는 고유 번호를 정해진 레지스터에
넣고 트랩(trap, 소프트웨어 인터럽트)을 발생시킵니다. 이 트랩 명령이 실행되면 CPU는 모드 비트를
커널 모드로 전환하고, 제어를 커널의 트랩 핸들러로 넘깁니다. 커널은 레지스터에 저장된 시스템 콜
번호를 이용해 시스템 콜 테이블(함수 포인터 배열)에서 해당하는 커널 함수를 찾아 실행합니다. 요청된
작업이 끝나면 결과값을 레지스터에 담고, 다시 유저 모드로 전환하면서 트랩을 호출했던 다음 명령어로
제어를 돌려줍니다.
```

- 시스템 콜의 유형에 대해 설명해 주세요.
```
보통 다섯 가지 정도로 분류합니다. 프로세스 제어(Process Control)는 fork, exec, exit, wait처럼
프로세스를 생성·종료·대기시키는 작업이고, 파일 관리(File Management)는 open, read, write,
close처럼 파일을 다루는 작업입니다. 장치 관리(Device Management)는 ioctl처럼 디바이스에 요청을
보내는 작업이고, 정보 유지(Information Maintenance)는 getpid, alarm처럼 시스템 정보를 얻거나
설정하는 작업입니다. 마지막으로 통신(Communication)은 pipe, shmget, mmap처럼 프로세스 간 데이터를
주고받는 작업이고, 보호(Protection)는 chmod, chown처럼 접근 권한을 다루는 작업입니다.
```

- 운영체제의 Dual Mode 에 대해 설명해 주세요.
```
Dual Mode는 CPU가 유저 모드(User Mode)와 커널 모드(Kernel Mode) 두 가지 실행 모드를 구분해서
운영되는 방식입니다. CPU에는 현재 어느 모드인지를 나타내는 모드 비트(mode bit)가 있고, 하드웨어
차원에서 이를 검사합니다.

유저 모드에서는 메모리 접근 범위나 특권 명령어(I/O 명령, 인터럽트 비활성화, 메모리 관리 레지스터
조작 등) 사용이 제한됩니다. 커널 모드에서는 이런 제약 없이 하드웨어 전체와 모든 메모리에 접근할 수
있습니다. 유저 프로그램이 특권 명령을 시도하면 하드웨어가 이를 감지해 트랩을 발생시켜 커널에게
제어권을 넘기고, 커널이 대신 안전하게 처리하거나 잘못된 접근이면 프로세스를 종료시킵니다.
```

- 왜 유저모드와 커널모드를 구분해야 하나요?
```
보호(Protection)와 안정성 때문입니다. 만약 모든 프로그램이 하드웨어와 메모리에 제약 없이 접근할 수
있다면, 버그가 있거나 악의적인 프로그램 하나가 다른 프로세스의 메모리를 마음대로 읽고 쓰거나,
디스크를 직접 조작해 시스템 전체를 망가뜨릴 수 있습니다.

모드를 구분하면 커널이 자원에 대한 유일한 관문 역할을 하게 되어, 모든 특권 작업이 커널의 검증과
스케줄링을 거치도록 강제할 수 있습니다. 그래서 한 프로세스에서 문제가 생기더라도 커널이 이를 격리해서
다른 프로세스나 시스템 전체로 영향이 번지는 것을 막을 수 있고, 자원에 대한 접근을 중앙에서 일관되게
관리(스케줄링, 권한 검사)할 수 있습니다.
```

- 서로 다른 시스템 콜을 어떻게 구분할 수 있을까요?
```
각 시스템 콜에는 고유한 번호(system call number)가 부여되어 있습니다. 유저 프로그램이 시스템
콜을 호출하기 직전에, 이 번호를 정해진 레지스터(x86에서는 관례적으로 eax/rax)에 저장하고 트랩을
발생시킵니다.

커널은 트랩을 받으면 이 레지스터 값을 읽어서, 시스템 콜 번호를 인덱스로 하는 시스템 콜 테이블(함수
포인터 배열)을 조회해 그에 해당하는 커널 함수로 점프합니다. 즉 번호 하나하나가 테이블의 인덱스와
1:1로 매핑되어 있어서, 이 번호만으로 어떤 시스템 콜이 요청됐는지 명확하게 구분할 수 있습니다.
```

**핵심 키워드** → 시스템 콜(유저 모드가 커널 기능을 요청하는 인터페이스), 트랩(Trap, 소프트웨어 인터럽트)으로 커널 진입, 시스템 콜 번호 + 시스템 콜 테이블(함수 포인터 배열), 시스템 콜 유형(프로세스 제어·파일 관리·장치 관리·정보 유지·통신·보호), Dual Mode(유저 모드/커널 모드, 모드 비트, 특권 명령어), 모드 구분 이유(보호·안정성·자원 중앙 관리)

#### 2. 인터럽트가 무엇인지 설명해 주세요.

`★★☆` · `필수` · 원본 [운영체제 #2](../02-OPERATING_SYSTEM.md)

<details>
<summary><b>꼬리 질문 4개 (펼치기)</b></summary>

- 인터럽트는 어떻게 처리하나요?
- Polling 방식에 대해 설명해 주세요.
- HW / SW 인터럽트에 대해 설명해 주세요.
- 동시에 두 개 이상의 인터럽트가 발생하면, 어떻게 처리해야 하나요?

</details>

**내 답변**

```
인터럽트는 CPU가 현재 실행 중인 작업을 즉시 처리해야 하는 이벤트가 발생했을 때, CPU에게 이를 알려서
현재 작업을 잠시 멈추고 그 이벤트를 먼저 처리하도록 만드는 신호입니다.

키보드 입력, 타이머 만료, 디스크 I/O 완료 같은 외부 장치의 이벤트(하드웨어 인터럽트)나, 시스템 콜·
예외 상황(SW 인터럽트) 등 다양한 원인으로 발생합니다. 인터럽트가 발생하면 CPU는 실행 중이던 명령의
문맥(레지스터, PC)을 저장하고, 인터럽트 벡터 테이블을 통해 해당 인터럽트를 처리하는 인터럽트
서비스 루틴(ISR)으로 점프해서 처리한 뒤, 저장해둔 문맥을 복원하고 원래 실행하던 지점으로 돌아갑니다.
```

**꼬리 질문 답변**

- 인터럽트는 어떻게 처리하나요?
```
CPU는 매 명령어 사이클이 끝날 때마다 인터럽트가 발생했는지를 확인합니다. 인터럽트가 감지되면, 현재
실행 중이던 명령의 문맥(Program Counter, 레지스터 상태, 플래그 등)을 스택에 저장합니다.

그다음 발생한 인터럽트의 종류를 나타내는 번호를 이용해 인터럽트 벡터 테이블(Interrupt Vector
Table, IVT)을 조회해서 해당하는 인터럽트 서비스 루틴(ISR)의 주소를 찾고, 그 주소로 점프해서 ISR을
실행합니다. ISR 처리 도중에는 보통 같은(또는 낮은 우선순위) 인터럽트가 중첩되지 않도록 인터럽트를
비활성화하거나 마스킹합니다. ISR 실행이 끝나면 저장해뒀던 문맥을 복원하고, iret 같은 명령으로
인터럽트가 발생했던 원래 지점으로 복귀해서 실행을 이어갑니다.
```

- Polling 방식에 대해 설명해 주세요.
```
Polling은 CPU가 인터럽트처럼 장치가 먼저 신호를 보낼 때까지 기다리는 게 아니라, CPU가 능동적으로
반복문을 돌면서 장치의 상태 레지스터를 주기적으로 확인해서 이벤트 발생 여부를 스스로 체크하는
방식입니다.

구현이 단순하고 인터럽트 처리에 필요한 문맥 저장·복원 오버헤드가 없다는 장점이 있지만, 이벤트가
실제로 거의 발생하지 않는 상황에서도 CPU가 계속 확인 루프를 도느라 자원을 낭비하게 됩니다. 그래서
일반적인 상황에서는 CPU를 다른 작업에 쓸 수 있는 인터럽트 방식이 더 효율적이고, Polling은 이벤트
발생 빈도가 매우 높아서 인터럽트 처리 오버헤드가 오히려 더 크거나, 아주 낮은 지연시간이 중요한
특수한 저수준 상황(예: 초고속 네트워크 카드)에서 제한적으로 사용됩니다.
```

- HW / SW 인터럽트에 대해 설명해 주세요.
```
HW(하드웨어) 인터럽트는 CPU 외부의 장치가 인터럽트 컨트롤러의 IRQ 라인을 통해 발생시키는
인터럽트입니다. 키보드 입력, 타이머 만료, 디스크 I/O 완료, 네트워크 패킷 도착 등이 예시이고, CPU의
현재 실행 흐름과 비동기적으로(예측 불가능한 시점에) 발생합니다.

SW(소프트웨어) 인터럽트는 실행 중인 프로그램 자체가 명령어를 통해 의도적으로 발생시키는 인터럽트로,
대표적으로 시스템 콜을 호출할 때 쓰는 트랩(trap)이 있습니다. 또한 0으로 나누기, 잘못된 메모리
접근(page fault)처럼 프로그램 실행 중 예상치 못한 오류로 CPU가 자동으로 발생시키는 예외
(Exception)도 넓은 의미에서 SW 인터럽트로 분류하기도 합니다. HW 인터럽트와 달리 현재 실행 흐름과
동기적으로(정해진 명령어 실행 시점에) 발생한다는 차이가 있습니다.
```

- 동시에 두 개 이상의 인터럽트가 발생하면, 어떻게 처리해야 하나요?
```
인터럽트마다 우선순위(priority)를 부여해서, 인터럽트 컨트롤러(PIC나 APIC 같은 하드웨어)가
동시에 들어온 여러 인터럽트 중 가장 우선순위가 높은 것부터 CPU에 전달하도록 중재합니다.

높은 우선순위 인터럽트를 처리하는 도중에 더 높은 우선순위의 인터럽트가 새로 발생하면, 현재 처리
중인 ISR을 잠시 중단하고 문맥을 다시 저장한 뒤 새 인터럽트를 먼저 처리하는 중첩(nested) 인터럽트
처리가 일어날 수 있습니다. 반대로 낮거나 같은 우선순위의 인터럽트는 현재 ISR이 끝날 때까지 마스킹
(대기)되었다가, 처리 가능한 시점이 되면 순서대로(또는 다시 우선순위에 따라) 처리됩니다. 이런 방식
덕분에 타이머나 하드웨어 오류처럼 시급한 인터럽트가 덜 중요한 인터럽트에 밀려 지연되는 것을 막을 수
있습니다.
```

**핵심 키워드** → 인터럽트 = CPU 실행 흐름을 강제로 전환시키는 이벤트 신호, 문맥 저장 → IVT(인터럽트 벡터 테이블) 조회 → ISR 실행 → 문맥 복원, Polling(능동적 상태 확인, 단순하지만 CPU 낭비) vs 인터럽트(이벤트 기반, 효율적), HW 인터럽트(외부 장치, 비동기) vs SW 인터럽트(트랩·예외, 동기), 인터럽트 우선순위와 중첩(nested) 처리, PIC/APIC를 통한 다중 인터럽트 중재

**내 답변**

```
프로세스는 디스크에 정적으로 저장된 프로그램이 메모리에 적재되어 실제로 실행되고 있는 상태를
말합니다. 단순히 코드가 실행되는 것뿐 아니라, 그 실행을 위해 운영체제로부터 독립적으로 할당받은
자원(주소 공간, 파일 디스크립터, 레지스터 상태 등)을 함께 갖고 있는 하나의 단위입니다.

운영체제는 각 프로세스의 상태를 PCB(Process Control Block)라는 커널 자료구조로 관리하며, 이를
기반으로 여러 프로세스를 번갈아 실행시키는 스케줄링, 프로세스 간 격리와 보호를 수행합니다.
```

**꼬리 질문 답변**

- 프로그램과 프로세스, 스레드의 차이에 대해 설명해 주세요.
```
프로그램은 디스크에 저장된, 실행되지 않은 정적인 코드 파일 자체입니다. 그 자체로는 아무 자원도
점유하지 않고 그냥 명령어들의 모음일 뿐입니다.

프로세스는 그 프로그램이 메모리에 적재되어 실행 중인 상태로, 독립된 주소 공간과 자원(메모리, 열린
파일, 레지스터 값 등)을 갖습니다. 같은 프로그램이라도 여러 번 실행하면 서로 다른, 독립된 프로세스가
여러 개 생깁니다.

스레드는 프로세스 내부에서 실제로 실행되는 흐름의 단위입니다. 하나의 프로세스는 하나 이상의 스레드를
가질 수 있고, 같은 프로세스에 속한 스레드들은 그 프로세스의 코드·데이터·힙 영역은 공유하지만, 각자
독립된 스택과 레지스터 값(PC 포함)을 가져서 서로 다른 실행 흐름을 유지합니다.
```

- PCB가 무엇인가요?
```
PCB(Process Control Block)는 커널이 각 프로세스를 관리하기 위해 유지하는 자료구조로, 그 프로세스에
대한 모든 정보를 담고 있습니다.

대표적으로 프로세스 식별자(PID), 프로세스 상태(ready/running/waiting 등), 프로그램 카운터와
레지스터 값(문맥 정보), CPU 스케줄링 정보(우선순위 등), 메모리 관리 정보(페이지 테이블 주소 등),
열려 있는 파일 목록, 부모/자식 프로세스 정보 등을 포함합니다. 프로세스가 생성될 때 함께 만들어지고,
컨텍스트 스위칭이 일어날 때 이 PCB에 현재 실행 상태를 저장하고, 다시 실행될 때 PCB로부터 상태를
복원합니다.
```

- 그렇다면, 스레드는 PCB를 갖고 있을까요?
```
전통적인 의미의 PCB, 즉 별도의 주소 공간·파일 목록까지 포함한 완전한 PCB는 갖고 있지 않습니다.
대신 스레드는 보통 TCB(Thread Control Block)라는 더 가벼운 구조체를 가지며, 여기에는 스레드
고유의 정보(스레드 ID, 프로그램 카운터, 레지스터 값, 스택 포인터, 스케줄링 정보)만 담깁니다. 주소
공간, 열린 파일, 힙 등 프로세스 단위의 자원은 자신이 속한 프로세스의 PCB를 그대로 공유해서 참조합니다.

다만 리눅스는 이 구분을 더 단순화해서, 프로세스든 스레드든 모두 task_struct라는 동일한 자료구조로
표현합니다. 스레드를 생성할 때는 clone() 시스템 콜에 CLONE_VM 같은 플래그를 줘서 주소 공간 등
일부 자원을 부모와 공유하는 task_struct를 만드는 식으로, 프로세스와 스레드를 "공유하는 자원의
범위가 다른 task"로 통합해서 다룹니다.
```

- 리눅스에서, 프로세스와 스레드는 각각 어떻게 생성될까요?
```
프로세스는 fork() 시스템 콜로 생성합니다. fork()는 호출한 프로세스(부모)의 거의 모든 상태를
복제한 자식 프로세스를 만드는데, 실제 메모리를 그 자리에서 통째로 복사하지는 않고 Copy-On-Write
방식으로 페이지 테이블만 공유하다가, 부모나 자식 중 한쪽이 실제로 쓰기를 시도하는 순간에만 해당
페이지를 복사합니다. 이후 새로운 프로그램을 실행하려면 exec() 계열 시스템 콜로 현재 프로세스의
주소 공간을 완전히 새 프로그램의 이미지로 덮어씁니다. 그래서 새 프로세스를 실행할 때는 보통
fork() + exec() 조합을 사용합니다.

스레드는 보통 pthread_create() 같은 라이브러리 함수로 생성하는데, 이는 내부적으로 리눅스의
clone() 시스템 콜을 호출합니다. clone()은 fork()와 비슷하지만 CLONE_VM(주소 공간 공유),
CLONE_FS(파일시스템 정보 공유), CLONE_FILES(파일 디스크립터 테이블 공유) 같은 플래그를 세밀하게
조정할 수 있어서, 이 플래그들을 켜면 부모와 자원을 공유하는 "가벼운 프로세스", 즉 스레드가
생성됩니다.
```

- 자식 프로세스가 상태를 알리지 않고 죽거나, 부모 프로세스가 먼저 죽게 되면 어떻게 처리하나요?
```
두 상황 모두 별도의 이름과 처리 방식이 있습니다.

자식 프로세스가 종료됐는데 부모가 아직 wait()를 호출해서 종료 상태를 회수(reap)하지 않은 경우,
그 자식은 좀비(Zombie) 프로세스가 됩니다. 프로세스 자체의 실행은 끝났지만, 종료 코드 등 최소한의
정보를 담은 PCB 항목만 프로세스 테이블에 남아 있는 상태입니다. 부모가 wait()를 호출하면 그제서야
커널이 이 정보를 완전히 정리하고 항목을 제거합니다. 부모가 계속 wait()를 하지 않으면 좀비 프로세스가
누적되어 프로세스 테이블 자원을 낭비할 수 있습니다.

반대로 부모 프로세스가 자식보다 먼저 종료돼버리면, 그 자식은 고아(Orphan) 프로세스가 됩니다.
리눅스에서는 이런 고아 프로세스를 init(PID 1) 프로세스, 혹은 프로세스가 별도로 지정한 subreaper
프로세스가 새로운 부모로 입양(reparent)해서, 자식이 종료될 때 이를 대신 wait()로 회수해줍니다.
그래서 부모가 먼저 죽어도 자식이 좀비인 채로 영원히 남지 않도록 보장합니다.
```

- 리눅스에서, 데몬프로세스에 대해 설명해 주세요.
```
데몬(Daemon) 프로세스는 사용자와 직접 상호작용하는 제어 터미널 없이, 백그라운드에서 계속 실행되며
특정 서비스를 제공하는 프로세스입니다. sshd(SSH 서버), cron(예약 작업 실행기), systemd 같은
프로세스들이 대표적인 예입니다.

일반적으로 데몬을 만드는 절차는, fork()로 자식 프로세스를 만든 뒤 부모는 종료시켜서 자식이 고아가
되어 init에게 입양되게 만들고, setsid()를 호출해 새로운 세션의 세션 리더가 되면서 기존 제어
터미널과의 연결을 끊습니다. 이후 표준 입출력을 /dev/null로 리다이렉트하고 작업 디렉터리를
루트(/)로 옮기는 등 터미널이 닫히거나 사용자가 로그아웃해도 영향을 받지 않도록 독립시켜서 계속
백그라운드에서 실행되도록 만듭니다.
```

- 리눅스는 프로세스가 일종의 트리를 형성하고 있습니다. 이 트리의 루트 노드에 위치하는 프로세스에 대해 설명해 주세요.
```
그 루트 노드는 PID 1번을 가진 init 프로세스입니다. (현대 대부분의 배포판에서는 systemd가 이
역할을 담당합니다.)

부팅 과정에서 커널이 가장 먼저 시작시키는 유저 공간 프로세스로, 이후 생성되는 모든 프로세스는
직접 또는 간접적으로 fork()를 거쳐 이 init 프로세스의 자손이 됩니다. init은 시스템 서비스들을
초기화하고 실행하는 역할을 할 뿐 아니라, 앞서 설명한 것처럼 고아 프로세스를 입양해서 대신 회수해주는
역할도 담당합니다. 만약 init 프로세스 자체가 죽으면 커널이 시스템 전체를 패닉 상태로 처리할 만큼,
전체 프로세스 트리를 지탱하는 근간이 되는 프로세스입니다.
```

**핵심 키워드** → 프로그램(정적 코드) vs 프로세스(실행 중 + 독립 자원) vs 스레드(프로세스 내 실행 흐름 단위, 자원 공유), PCB(프로세스 상태·문맥 정보를 담는 커널 자료구조) vs TCB(스레드용 경량 구조체), 리눅스 task_struct(프로세스·스레드 통합 표현), fork()+exec()로 프로세스 생성 / clone()으로 스레드 생성(CLONE_VM 등), Copy-On-Write, 좀비 프로세스(부모의 wait() 미호출) vs 고아 프로세스(init/subreaper가 입양), 데몬 프로세스(setsid로 세션 분리), init(PID 1) = 프로세스 트리의 루트

#### 4. 프로세스 주소공간에 대해 설명해 주세요.

`★★☆` · `필수` · 원본 [운영체제 #4](../02-OPERATING_SYSTEM.md)

- 일반적인 주소공간 그림처럼, Stack과 Heap의 크기는 매우 크다고 할 수 있을까요? 그렇지 않다면, 그 크기는 언제 결정될까요?

**내 답변**

```
프로세스가 실행될 때 운영체제는 각 프로세스에게 독립된 가상 주소 공간을 할당하고, 이 공간은 용도에
따라 몇 개의 영역(세그먼트)으로 나뉩니다.

낮은 주소부터 순서대로, Text(Code) 영역은 실행할 기계어 명령어를 저장하고 보통 읽기 전용입니다.
Data 영역은 초기화된 전역/정적 변수를 저장하고, BSS 영역은 초기화되지 않은 전역/정적 변수를
저장합니다. 그 위로 Heap 영역이 있어서 malloc/new 같은 동적 할당에 쓰이며 주소가 증가하는
방향으로 확장되고, 가장 높은 주소 쪽에는 Stack 영역이 있어서 함수 호출 시의 지역 변수·매개변수·
복귀 주소를 저장하며 주소가 감소하는 방향으로 확장됩니다. Heap과 Stack이 서로 마주 보고 자라나는
구조라, 두 영역 사이의 남은 공간을 최대한 유연하게 나눠 쓸 수 있습니다.
```

**꼬리 질문 답변**

- 초기화 하지 않은 변수들은 어디에 저장될까요?
```
초기화하지 않은 전역 변수나 static 변수는 BSS(Block Started by Symbol) 영역에 저장됩니다. BSS는
Data 영역과 달리 실제 초기값을 실행 파일 안에 저장해두지 않고, 그냥 "이만큼의 크기가 필요하다"는
정보만 갖고 있다가 프로세스가 로드될 때 그 크기만큼 0으로 채워진 메모리를 확보합니다. 그래서
실행 파일의 용량을 아낄 수 있다는 장점이 있습니다. (참고로 함수 내부의 초기화되지 않은 지역 변수는
전역/정적 변수와 달리 Stack에 저장되며, 값이 0으로 자동 초기화되지 않고 이전에 그 스택 위치에
남아있던 쓰레기 값을 갖습니다.)
```

- 일반적인 주소공간 그림처럼, Stack과 Heap의 크기는 매우 크다고 할 수 있을까요? 그렇지 않다면, 그 크기는 언제 결정될까요?
```
그림에서는 넓은 공간을 차지하는 것처럼 그려지지만, 실제로는 무한하지 않고 명확한 한계가 있습니다.

Stack은 보통 운영체제나 스레드 생성 옵션에서 정한 고정 한계(리눅스 기본값은 흔히 8MB 정도, ulimit
-s로 확인·조정 가능)를 넘어서면 스택 오버플로우가 발생합니다. 실제 물리 메모리는 스택을 사용하는
만큼(페이지 폴트가 발생할 때마다) 점진적으로 할당되지만, 그 상한선은 이미 정해져 있습니다.

Heap은 프로그램 실행 중 malloc 등을 통해 brk()나 mmap() 시스템 콜로 동적으로 확장할 수 있어서
Stack보다는 유연하지만, 결국 시스템의 가용 가상 메모리와 물리 메모리(또는 스왑) 한계, 그리고
설정된 리소스 제한(ulimit -v 등)을 넘어설 수는 없습니다. 즉 두 영역 모두 "무한히 크다"기보다는
필요한 만큼 늘어나되, 정해진 한계 안에서만 늘어날 수 있는 구조입니다.
```

- Stack과 Heap 공간에 대해, 접근 속도가 더 빠른 공간은 어디일까요?
```
일반적으로 Stack이 더 빠릅니다.

Stack은 push/pop처럼 스택 포인터를 단순히 증가·감소시키는 것만으로 할당·해제가 끝나서 O(1)이고,
별도의 메모리 관리 오버헤드가 없습니다. 또한 함수 호출이 이어질 때 스택의 상단부를 반복해서 쓰기
때문에 캐시 지역성(cache locality)이 매우 좋아 실제 접근 속도도 빠릅니다.

Heap은 할당할 때마다 메모리 할당자(allocator)가 적당한 크기의 빈 블록을 찾는 탐색·관리 작업
(free list 탐색, 단편화 처리 등)이 필요해서 상대적으로 오버헤드가 크고, 할당된 블록들이 메모리
여기저기 흩어져 있어서 포인터를 따라가며 접근할 때 캐시 미스가 잦아질 수 있습니다.
```

- 다음과 같이 공간을 분할하는 이유가 있을까요?
```
크게 세 가지 이유가 있다고 생각합니다.

첫째, 각 영역의 용도와 생명주기가 다릅니다. 코드는 실행 중 바뀌지 않고, 전역 변수는 프로그램 전체
생명주기 동안 유지되고, 지역 변수는 함수 호출·반환에 맞춰 짧게 살고 죽고, 동적 할당 데이터는
개발자가 명시적으로 관리해야 합니다. 이렇게 접근·해제 패턴이 다른 데이터를 한 곳에 뒤섞으면 관리가
매우 복잡해집니다.

둘째, 메모리 보호(protection)를 세그먼트 단위로 다르게 적용할 수 있습니다. 예를 들어 Text
영역은 읽기·실행 전용으로 설정해서 실행 중인 코드가 실수로(혹은 공격에 의해) 변조되는 것을 막을 수
있습니다.

셋째, Heap과 Stack을 서로 반대 방향에서 자라나게 배치하면, 둘 사이의 여유 공간을 미리 나눠두지
않고도 유동적으로 나눠 쓸 수 있어서 공간 활용이 효율적입니다.
```

- 스레드의 주소공간은 어떻게 구성되어 있을까요?
```
같은 프로세스에 속한 스레드들은 그 프로세스의 Text, Data, BSS, Heap 영역을 전부 공유합니다. 즉
전역 변수나 동적 할당된 객체는 모든 스레드가 함께 접근할 수 있습니다.

다만 각 스레드는 자신만의 독립된 Stack을 별도로 할당받습니다. 이는 각 스레드가 서로 다른 함수
호출 흐름과 지역 변수를 독립적으로 가져야 하기 때문입니다. 이 스레드별 Stack들은 보통 프로세스의
전체 가상 주소 공간 안에서(주로 Heap과 시스템 영역 사이 등) 별도로 매핑되어, 다른 스레드의 스택과
겹치지 않도록 배치됩니다.
```

- "스택"영역과 "힙"영역은 정말 자료구조의 스택/힙과 연관이 있는 걸까요? 만약 그렇다면, 각 주소공간의 동작과정과 연계해서 설명해 주세요.
```
Stack 영역은 자료구조 스택과 실제로 밀접하게 연관되어 있습니다. 함수를 호출할 때마다 그 함수의
지역 변수·매개변수·복귀 주소를 담은 스택 프레임이 스택의 맨 위에 push되고, 함수가 반환되면 그
프레임이 pop되어 사라집니다. 가장 최근에 호출된 함수가 가장 먼저 반환되는 LIFO 순서가 자료구조
스택의 동작과 정확히 일치하기 때문에, 이름 자체가 그 동작 방식에서 그대로 유래했습니다.

반면 Heap 영역의 이름은 자료구조 힙(이진 힙, 완전이진트리 기반의 우선순위 자료구조)과는 직접적인
연관이 없습니다. "쌓아놓은 더미"라는 일반적인 영어 단어 heap의 의미에서 따온 이름으로, 크기가
다양한 메모리 블록들이 자유롭게 할당·해제되며 뒤섞여 쌓여있는 영역이라는 뜻에 가깝습니다. 실제
Heap 메모리 할당자는 보통 free list(가용 블록 연결 리스트)나 이진 탐색 트리 기반 구조로 구현되지,
이진 힙 자료구조 자체로 동작하지 않습니다. 즉 "스택"은 동작 방식과 이름이 정확히 일치하는 경우이고,
"힙"은 이름만 같을 뿐 자료구조 힙과는 직접적인 관계가 없는 경우입니다.
```

- IPC의 Shared Memory 기법은 프로세스 주소공간의 어디에 들어가나요? 그런 이유가 있을까요?
```
보통 Heap과 Stack 사이의 별도 매핑 영역(mmap 영역)에 위치합니다. 리눅스에서는 shmget()이나
mmap()으로 공유 메모리를 요청하면, 커널이 그 프로세스의 가상 주소 공간 안에 새로운 매핑 영역을
하나 추가로 만들어줍니다.

Heap이나 Stack의 일부로 넣지 않는 이유는, 공유 메모리는 여러 프로세스가 동일한 물리 메모리 영역을
가리켜야 하는 특수한 목적을 가진 매핑이기 때문입니다. Heap은 각 프로세스가 자신만 사용하는 사적인
동적 할당 공간이고 sbrk/brk로 연속적으로 확장되는 구조라 중간에 다른 목적의 매핑을 끼워 넣기
어렵고, Stack도 마찬가지로 각 스레드·프로세스 전용 공간입니다. 그래서 커널은 이런 공유 매핑을
별도의 독립된 가상 주소 영역으로 관리해서, 다른 프로세스의 동일한 매핑과 페이지 테이블 상에서 같은
물리 프레임을 가리키도록 연결합니다.
```

- 스택과 힙영역의 크기는 언제 결정되나요? 프로그램 개발자가 아닌, 사용자가 이 공간의 크기를 수정할 수 있나요?
```
Stack 크기는 보통 프로세스(또는 스레드) 생성 시점에 결정됩니다. 메인 스레드의 스택 크기는 OS가
정한 기본 한계(리눅스는 보통 ulimit -s 값, 기본 8MB)를 따르고, 이후 생성되는 스레드는
pthread_attr_setstacksize() 같은 API로 개별적으로 지정할 수 있습니다. Heap은 고정 크기가
미리 정해지는 게 아니라, 프로그램 실행 중 malloc 등을 호출할 때마다 필요한 만큼 brk()나 mmap()으로
동적으로 늘어나는 방식입니다.

사용자도 이 크기를 수정할 수 있습니다. 셸에서 ulimit -s 8192 처럼 명령을 실행하면 그 셸에서
시작되는 프로세스들의 스택 크기 소프트 리밋을 조정할 수 있고, 프로그램 코드 안에서도 setrlimit()
시스템 콜로 RLIMIT_STACK, RLIMIT_AS(전체 주소 공간 한계, Heap 성장에 영향) 같은 값을 직접
조정할 수 있습니다. 다만 시스템 관리자가 설정한 하드 리밋(hard limit)을 넘어서는 값으로는 일반
사용자가 조정할 수 없습니다.
```

**핵심 키워드** → 주소공간 레이아웃(낮은 주소→높은 주소: Text·Data·BSS·Heap↑·…·Stack↓), BSS(초기화 안 된 전역/정적 변수, 실행 파일에 값 저장 안 함), Stack/Heap 모두 상한선 존재(ulimit, brk/mmap으로 점진적 확장), Stack이 Heap보다 빠름(포인터 이동 O(1) + 캐시 지역성), 세그먼트 분할 이유(생명주기 차이·세그먼트별 보호 설정·유동적 공간 활용), 스레드는 Text/Data/BSS/Heap 공유 + Stack만 개별, Stack=자료구조 스택과 동작 일치(LIFO 스택 프레임) / Heap=이름만 유사(free list 등으로 구현), Shared Memory는 별도 mmap 매핑 영역에 위치, 크기 조정(ulimit, setrlimit, pthread_attr_setstacksize)

#### 5. 단기, 중기, 장기 스케쥴러에 대해 설명해 주세요.

`★★☆` · `필수` · 원본 [운영체제 #5](../02-OPERATING_SYSTEM.md)

<details>
<summary><b>꼬리 질문 4개 (펼치기)</b></summary>

- 현대 OS에는 단기, 중기, 장기 스케쥴러를 모두 사용하고 있나요?
- 프로세스의 스케쥴링 상태에 대해 설명해 주세요.
- preemptive/non-preemptive 에서 존재할 수 없는 상태가 있을까요?
- Memory가 부족할 경우, Process는 어떠한 상태로 변화할까요?

</details>

**내 답변**

```
세 스케줄러는 프로세스의 생명주기 중 서로 다른 단계에서, 서로 다른 빈도로 개입합니다.

장기 스케줄러(Long-term Scheduler, Job Scheduler)는 디스크의 작업 풀(job pool)에 있는 프로그램
중 어떤 것을 메모리로 적재해서 프로세스로 만들지, 즉 시스템의 다중 프로그래밍 정도(degree of
multiprogramming)를 조절합니다. 상대적으로 아주 드물게(초 단위 이상) 개입합니다.

단기 스케줄러(Short-term Scheduler, CPU Scheduler)는 이미 메모리에 있는 준비(ready) 상태
프로세스들 중 다음에 CPU를 할당받을 프로세스를 고릅니다. 매우 빈번하게(밀리초 단위) 실행되어야
하므로 실행 속도가 빨라야 합니다.

중기 스케줄러(Medium-term Scheduler)는 메모리에 있는 프로세스 일부를 디스크로 스왑아웃했다가
필요할 때 다시 스왑인하는 방식으로 메모리에 올라와 있는 프로세스 수를 조절해서, 다중 프로그래밍
정도를 완화하거나 메모리 압박을 해소합니다.
```

**꼬리 질문 답변**

- 현대 OS에는 단기, 중기, 장기 스케쥴러를 모두 사용하고 있나요?
```
단기 스케줄러는 CPU를 나눠 쓰는 모든 현대 OS에 필수적으로 존재합니다.

중기 스케줄러도 스왑(swap) 메커니즘이라는 형태로 대부분의 현대 범용 OS(리눅스, 윈도우 등)에
남아있습니다. 메모리가 부족해지면 당장 쓰이지 않는 프로세스를 스왑 영역으로 내보내는 방식입니다.

반면 장기 스케줄러는 초기 배치(batch) 시스템에서처럼 명확한 형태로 존재하는 경우는 드뭅니다.
현대의 시분할(time-sharing) 범용 OS는 새 프로세스를 만들면 곧바로 메모리에 적재하는 것이 보통이라,
"메모리에 올릴지 말지 별도로 심사하는" 명시적인 장기 스케줄러 단계가 뚜렷하게 드러나지 않습니다.
다만 개념적으로는 가상 메모리(당장 전부 물리 메모리에 있을 필요가 없음)와 시스템 부하 제한 정책들이
장기 스케줄러의 역할 일부를 대신하고 있고, 배치 처리 위주의 서버 스케줄링 시스템(작업 큐 관리자
등)에서는 여전히 명시적인 장기 스케줄러 개념이 쓰입니다.
```

- 프로세스의 스케쥴링 상태에 대해 설명해 주세요.
```
기본적으로 다섯 가지 상태가 있습니다. New는 프로세스가 막 생성되어 아직 시스템에 완전히 등록되지
않은 상태이고, Ready는 CPU만 할당받으면 바로 실행 가능한, 실행 준비를 마치고 대기 중인 상태입니다.
Running은 실제로 CPU를 할당받아 명령어를 실행 중인 상태이고, Waiting(Blocked)은 I/O 완료나
이벤트 발생 등 어떤 조건을 기다리느라 CPU를 줘도 당장 실행할 수 없는 상태입니다. Terminated는
실행이 끝나 자원 회수를 기다리는 상태입니다.

여기에 중기 스케줄러가 개입하는 시스템에서는 Ready-Suspended, Waiting-Suspended처럼 메모리에서
스왑아웃되어 디스크에 내려가 있는 확장된 상태들이 추가되기도 합니다.
```

- preemptive/non-preemptive 에서 존재할 수 없는 상태가 있을까요?
```
상태 자체(New/Ready/Running/Waiting/Terminated)는 두 방식 모두에서 동일하게 존재하지만,
"Running에서 Ready로" 향하는 상태 전이(transition)는 non-preemptive 방식에서는 발생하지
않습니다.

Non-preemptive(비선점형) 스케줄링에서는 한 번 CPU를 할당받은 프로세스는 스스로 종료하거나
I/O 등을 기다리며 자발적으로 CPU를 반납(Running → Waiting 또는 Running → Terminated)할 때까지
절대 강제로 CPU를 빼앗기지 않습니다. 반면 Preemptive(선점형) 스케줄링에서는 타이머 인터럽트로
시간 할당량이 끝나거나 더 우선순위가 높은 프로세스가 준비 상태가 되면, 실행 중이던 프로세스를
강제로 중단시켜 Ready 상태로 되돌릴 수 있습니다(Running → Ready). 그래서 "Running → Ready"
전이는 선점형 스케줄링에만 존재하는 전이입니다.
```

- Memory가 부족할 경우, Process는 어떠한 상태로 변화할까요?
```
중기 스케줄러가 개입해서 해당 프로세스를 메모리에서 디스크(스왑 영역)로 내보내는 스왑아웃을
수행하고, 이 프로세스는 Suspended(중단) 상태로 전환됩니다.

구체적으로는, 원래 Ready 상태였던 프로세스가 스왑아웃되면 Ready-Suspended 상태로, I/O를
기다리며 Waiting 상태였던 프로세스가 스왑아웃되면 Waiting(Blocked)-Suspended 상태로
바뀝니다. 이 상태의 프로세스는 메모리에 올라와 있지 않으므로 단기 스케줄러의 선택 대상에서 제외되고,
이후 메모리 여유가 생기면 중기 스케줄러가 다시 스왑인해서 원래의 Ready 또는 Waiting 상태로
복귀시킵니다.
```

**핵심 키워드** → 장기 스케줄러(Job Scheduler, 다중 프로그래밍 정도 조절, 드문 빈도), 단기 스케줄러(CPU Scheduler, Ready 중 다음 실행 프로세스 선택, 매우 빈번), 중기 스케줄러(스왑아웃/스왑인으로 메모리 부담 조절), 현대 OS는 장기 스케줄러 역할이 약해지고 중기(스왑)만 뚜렷, 5가지 기본 상태(New·Ready·Running·Waiting·Terminated) + Suspended 확장 상태, Running→Ready 전이는 Preemptive 전용, 메모리 부족 시 Ready/Waiting-Suspended로 전환

#### 6. 컨텍스트 스위칭 시에는 어떤 일들이 일어나나요?

`★★☆` · `필수` · 원본 [운영체제 #6](../02-OPERATING_SYSTEM.md)

<details>
<summary><b>꼬리 질문 3개 (펼치기)</b></summary>

- 프로세스와 스레드는 컨텍스트 스위칭이 발생했을 때 어떤 차이가 있을까요?
- 컨텍스트 스위칭이 발생할 때, 기존의 프로세스 정보는 커널스택에 어떠한 형식으로 저장되나요?
- 컨텍스트 스위칭은 언제 일어날까요?

</details>

**내 답변**

```
컨텍스트 스위칭은 CPU가 실행하던 프로세스(또는 스레드)를 다른 프로세스로 교체할 때, 현재 실행
문맥(context)을 저장하고 다음에 실행할 프로세스의 문맥을 복원하는 과정입니다.

구체적으로는, 커널이 현재 실행 중이던 프로세스의 프로그램 카운터·레지스터 값·스택 포인터 같은
CPU 상태를 그 프로세스의 PCB에 저장합니다. 그다음 스케줄러가 다음에 실행할 프로세스를 선택하고,
그 프로세스의 PCB에 저장돼 있던 문맥을 CPU 레지스터로 복원합니다. 만약 프로세스 단위 전환이라면
메모리 주소 공간을 가리키는 페이지 테이블(예: x86의 CR3 레지스터)도 함께 교체하고, 이 과정에서
보통 TLB 플러시가 함께 일어납니다. 이 모든 과정은 그 자체로는 유용한 계산을 전혀 수행하지 않는
순수한 오버헤드이기 때문에, 너무 자주 발생하면 시스템 전체 처리량이 떨어집니다.
```

**꼬리 질문 답변**

- 프로세스와 스레드는 컨텍스트 스위칭이 발생했을 때 어떤 차이가 있을까요?
```
가장 큰 차이는 주소 공간(메모리 매핑) 전환 여부입니다.

프로세스 간 컨텍스트 스위칭은 서로 다른 독립된 가상 주소 공간을 사용하므로, 레지스터와 스택 포인터
교체뿐 아니라 페이지 테이블 베이스 레지스터(CR3 등)까지 새 프로세스의 것으로 바꿔야 합니다. 이
과정에서 이전 프로세스의 가상 주소에 대한 캐시였던 TLB(Translation Lookaside Buffer) 엔트리들이
더 이상 유효하지 않게 되어 플러시(또는 무효화)되고, 이후 한동안 TLB 미스가 늘어나 성능이 저하되는
비용이 추가로 발생합니다.

반면 같은 프로세스에 속한 스레드 간 전환은 주소 공간을 그대로 공유하므로 페이지 테이블 교체나
TLB 플러시가 필요 없고, 레지스터 값과 스택 포인터, 프로그램 카운터만 바꾸면 됩니다. 그래서 스레드
간 컨텍스트 스위칭이 프로세스 간 전환보다 훨씬 가볍고 빠릅니다.
```

- 컨텍스트 스위칭이 발생할 때, 기존의 프로세스 정보는 커널스택에 어떠한 형식으로 저장되나요?
```
일반적으로 함수 호출 시 쌓이는 스택 프레임과 비슷한 형식으로, 그 시점의 CPU 레지스터 값들을 담은
구조체(예: 리눅스의 경우 struct pt_regs, 아키텍처별 레지스터 세트를 반영)가 해당 프로세스(또는
스레드)의 커널 스택에 push되는 형태로 저장됩니다.

여기에는 범용 레지스터 값들, 프로그램 카운터(PC), 스택 포인터(SP), 상태 플래그 레지스터 등이
포함됩니다. 리눅스에서는 switch_to()라는 아키텍처별 저수준 루틴이 이 저장·복원을 수행하는데,
현재 실행 흐름의 레지스터 상태를 이전 태스크의 스택(정확히는 태스크 구조체에 연결된 커널 스택
영역)에 기록하고, 다음 태스크의 저장된 값들을 CPU 레지스터로 로드한 뒤 그 태스크의 커널 스택
포인터로 스택 자체를 전환하는 방식으로 동작합니다. 이렇게 각 태스크가 자신만의 커널 스택을 갖고
있기 때문에, 다음에 그 태스크가 다시 스케줄링될 때 저장해뒀던 지점부터 정확히 이어서 실행을 재개할
수 있습니다.
```

- 컨텍스트 스위칭은 언제 일어날까요?
```
크게 네 가지 상황에서 발생합니다.

첫째, 타이머 인터럽트로 현재 프로세스에게 할당된 시간 할당량(time quantum)이 만료됐을 때(선점형
스케줄링). 둘째, 실행 중인 프로세스가 I/O 요청 등으로 자발적으로 블로킹(Waiting 상태로 전환)될
때. 셋째, 더 높은 우선순위의 프로세스가 인터럽트 처리 등으로 인해 갑자기 Ready 상태가 되어 현재
실행 중인 프로세스를 선점할 때. 넷째, 시스템 콜 처리 등으로 커널 모드에 진입했다가, 처리 결과
다른 프로세스로 전환해야 한다고 스케줄러가 판단할 때입니다.

공통적으로는 항상 인터럽트(타이머, I/O 완료, 시스템 콜 트랩 등)를 계기로 커널이 개입해서 스케줄링
결정을 내린 뒤에 컨텍스트 스위칭이 이루어진다는 흐름을 갖습니다.
```

**핵심 키워드** → 컨텍스트 스위칭 = 현재 문맥을 PCB에 저장 + 다음 프로세스 문맥을 복원(순수 오버헤드, 유용한 연산 없음), 프로세스 전환은 페이지 테이블(CR3) 교체 + TLB 플러시 필요(스레드 전환은 불필요, 더 가벼움), 커널 스택에 레지스터 세트(pt_regs 등)를 스택 프레임 형태로 저장(리눅스 switch_to()), 발생 시점(타임 퀀텀 만료·자발적 블로킹·선점·시스템 콜 이후 스케줄링 판단)

#### 7. 프로세스 스케줄링 알고리즘에는 어떤 것들이 있나요?

`★★☆` · `필수` · 원본 [운영체제 #7](../02-OPERATING_SYSTEM.md)

<details>
<summary><b>꼬리 질문 7개 (펼치기)</b></summary>

- RR을 사용할 때, Time Slice에 따른 trade-off를 설명해 주세요.
- 싱글 스레드 CPU 에서 상시로 돌아가야 하는 프로세스가 있다면, 어떤 스케쥴링 알고리즘을 사용하는 것이 좋을까요? 또 왜 그럴까요?

- 타 스케쥴러와 비교하여, Multi-level Feedback Queue는 어떤 문제점들을 해결한다고 볼 수 있을까요?
- FIFO 스케쥴러는 정말 쓸모가 없는 친구일까요? 어떤 시나리오에 사용하면 좋을까요?
- 우리는 스케줄링 알고리즘을 "프로세스" 스케줄링 알고리즘이라고 부릅니다. 스레드는 다른 방식으로 스케줄링을 하나요?

**내 답변**

```
대표적인 CPU 스케줄링 알고리즘은 다음과 같습니다.

FCFS(First-Come First-Served)는 준비 큐에 도착한 순서대로 처리하는 가장 단순한 비선점형
알고리즘입니다. SJF(Shortest Job First)는 다음 CPU 버스트 시간이 가장 짧은 프로세스를 먼저
실행해서 평균 대기시간을 최소화하지만, 정확한 미래 실행 시간을 미리 알기 어렵다는 한계가 있고,
선점형 버전은 SRTF(Shortest Remaining Time First)라고 부릅니다. 우선순위 스케줄링(Priority
Scheduling)은 프로세스마다 부여된 우선순위가 높은 것부터 실행하며, 선점형·비선점형 모두 가능하지만
낮은 우선순위 프로세스가 영원히 실행 못하는 기아(starvation) 문제가 생길 수 있어 보통 Aging
기법으로 보완합니다. RR(Round Robin)은 정해진 시간 할당량(time quantum)만큼씩 돌아가며 CPU를
할당하는 선점형 방식으로 응답 시간이 중요한 시분할 시스템에 적합합니다. 마지막으로 Multilevel
Queue와 Multilevel Feedback Queue는 프로세스를 여러 큐로 나눠 큐마다 다른 정책을 적용하고,
Feedback 방식은 프로세스가 실제로 보이는 행동에 따라 큐 사이를 이동시켜 더 유연하게 대응합니다.
```

**꼬리 질문 답변**

- RR을 사용할 때, Time Slice에 따른 trade-off를 설명해 주세요.
```
Time Slice(할당 시간)의 크기는 응답성과 처리량(오버헤드) 사이의 트레이드오프를 만듭니다.

Time Slice가 너무 크면, 극단적으로는 무한대에 가까워질수록 RR이 사실상 FCFS와 동일하게 동작하게
되어, 뒤에 대기하는 프로세스들의 응답 시간이 길어지고 시분할 시스템 특유의 체감 반응성이 나빠집니다.

반대로 Time Slice가 너무 작으면, 프로세스 하나가 실제로 유의미한 작업을 하기도 전에 컨텍스트
스위칭이 계속 발생해서, 컨텍스트 스위칭 자체의 오버헤드(레지스터 저장/복원, 캐시·TLB 갱신 비용)가
전체 시간에서 차지하는 비중이 커져 시스템 처리량(throughput)이 크게 떨어집니다.

그래서 보통 Time Slice는 대부분의 CPU 버스트가 한 번의 할당 시간 안에 끝날 수 있을 만큼 충분히
크면서도, 응답 시간을 인간이 체감하기 어려울 만큼 짧게 유지할 수 있는 값(보통 10~100ms 수준)으로
경험적으로 조정합니다.
```

- 싱글 스레드 CPU 에서 상시로 돌아가야 하는 프로세스가 있다면, 어떤 스케쥴링 알고리즘을 사용하는 것이 좋을까요? 또 왜 그럴까요?
```
선점형(preemptive) 우선순위 스케줄링을 사용해서, 그 프로세스에게 시스템에서 가장 높은 고정
우선순위를 부여하는 것이 적합하다고 생각합니다.

이유는, RR처럼 모든 프로세스를 동등하게 순환시키는 방식은 "상시로 계속 실행돼야 하는" 요구를
보장해줄 수 없고, 다른 프로세스들과 공평하게 시간을 나눠 갖게 되어 지연이 생길 수 있기 때문입니다.
반면 선점형 우선순위 스케줄링에서 그 프로세스를 최고 우선순위로 두면, 그 프로세스가 Ready
상태가 될 때마다(예: I/O를 마치고 복귀할 때마다) 다른 낮은 우선순위 프로세스가 실행 중이더라도
즉시 선점해서 CPU를 넘겨받을 수 있습니다. 즉 "상시성"을 보장하려면 그 프로세스가 준비되는 즉시
반드시 CPU를 차지할 수 있어야 하고, 이는 고정 최고 우선순위 + 선점형 조합으로만 확실하게 보장할
수 있습니다. (실시간 운영체제라면 이런 목적을 위한 실시간 스케줄링 정책(SCHED_FIFO 등)을 별도로
제공하기도 합니다.)
```

- 동시성과 병렬성의 차이에 대해 설명해 주세요.
```
동시성(Concurrency)은 여러 작업이 겹치는 시간대 안에서 "진행"되는 것을 말합니다. 싱글 코어
CPU 하나만 있어도, 매우 짧은 시간 단위로 여러 프로세스를 빠르게 번갈아 실행(컨텍스트 스위칭)하면
사용자 입장에서는 여러 작업이 동시에 진행되는 것처럼 보입니다. 즉 실제로 동시에 실행되는 게 아니라
"동시에 진행되는 것처럼 다루는" 논리적인 개념입니다.

병렬성(Parallelism)은 여러 작업이 물리적으로 정확히 같은 순간에 실제로 함께 실행되는 것을
말합니다. 이는 코어(또는 CPU)가 여러 개 있어야만 가능하고, 각 코어가 서로 다른 작업을 동시에
처리합니다.

정리하면 동시성은 "여러 작업을 다루는 방식(구조)"에 대한 개념이고, 병렬성은 "실제로 동시에 실행되는
하드웨어적 사실"에 대한 개념입니다. 병렬성이 있으면 동시성도 자연히 있지만, 동시성이 있다고 해서
반드시 병렬성이 있는 것은 아닙니다(싱글 코어에서의 멀티태스킹이 그 예시).
```

- 타 스케쥴러와 비교하여, Multi-level Feedback Queue는 어떤 문제점들을 해결한다고 볼 수 있을까요?
```
가장 핵심적으로 해결하는 문제는, SJF/SRTF처럼 이론적으로 우수한 알고리즘들이 요구하는 "다음 CPU
버스트 시간을 미리 정확히 알아야 한다"는 비현실적인 전제입니다. MLFQ는 이런 사전 정보 없이, 각
프로세스가 실제로 실행되는 동안 보여주는 행동(CPU를 얼마나 오래 쓰는지)을 관찰해서 동적으로
적응합니다.

구체적으로는 여러 단계의 큐를 두고, 새 프로세스는 가장 높은 우선순위 큐에서 짧은 Time Slice로
시작합니다. 만약 그 시간 안에 작업을 끝내지 못하고 CPU를 계속 쓰려고 하면(CPU-bound라고 판단),
한 단계 낮은 우선순위 큐로 강등시켜서 더 긴 Time Slice를 줍니다. 이런 방식으로 I/O를 자주
요청하는 대화형(interactive) 프로세스는 짧은 CPU 버스트만 쓰고 금방 큐를 벗어나 계속 높은
우선순위를 유지해 응답성이 좋아지고, CPU를 오래 쓰는 배치성 작업은 점점 낮은 우선순위로 밀려나
백그라운드에서 처리됩니다.

또한 낮은 큐에 있는 프로세스가 영원히 실행되지 못하는 기아(starvation) 문제를 막기 위해, 일정
시간 이상 대기한 프로세스를 주기적으로 높은 큐로 다시 승격시키는 Aging도 함께 적용해서, 우선순위
기반 스케줄링의 공평성 문제까지 함께 완화합니다.
```

- FIFO 스케쥴러는 정말 쓸모가 없는 친구일까요? 어떤 시나리오에 사용하면 좋을까요?
```
쓸모가 없다고 할 수는 없습니다. 오히려 단순함 자체가 강점이 되는 상황들이 있습니다.

FCFS는 구현이 매우 단순하고, 스케줄링 결정 자체에 별도의 계산 비용이 거의 들지 않아 오버헤드가
작습니다. 또한 도착한 순서를 그대로 지킨다는 점에서 직관적인 공정성을 제공하고, 아사(starvation)
현상 자체가 구조적으로 발생하지 않습니다(먼저 온 순서대로 반드시 처리되므로).

그래서 응답 시간이나 실행 시간 편차보다 처리 순서의 공정성이 중요한 일괄 처리(batch) 시스템,
프로세스들의 실행 시간이 대체로 비슷해 Convoy Effect(짧은 작업이 긴 작업 뒤에 걸려 오래 기다리는
현상)의 악영향이 크지 않은 경우, 혹은 프린터 작업 큐나 순서가 중요한 로그 처리 큐처럼 "먼저 요청한
것을 먼저 처리하는 것" 자체가 요구사항인 시나리오에 적합합니다.
```

- 우리는 스케줄링 알고리즘을 "프로세스" 스케줄링 알고리즘이라고 부릅니다. 스레드는 다른 방식으로 스케줄링을 하나요?
```
어떤 스레드 모델을 쓰느냐에 따라 다릅니다.

커널 스레드(1:1 모델, 리눅스가 대표적)에서는 스레드도 커널이 관리하는 스케줄링 단위(리눅스에서는
프로세스와 동일하게 task_struct)로 취급되어, 프로세스와 완전히 동일한 스케줄링 알고리즘(리눅스의
CFS 등)을 그대로 적용받습니다. 이 경우 "프로세스 스케줄링 알고리즘"이라는 이름이 스레드에도
사실상 그대로 적용되는 셈입니다.

반면 유저 레벨 스레드(N:1 모델)에서는 커널은 이 스레드들의 존재 자체를 모르고, 하나의 프로세스
단위로만 스케줄링합니다. 그 프로세스 내부에서 여러 스레드를 어떻게 번갈아 실행할지는 유저 공간의
스레드 라이브러리(런타임)가 자체적인 스케줄러로 결정하며, 이 스케줄링 정책은 커널의 것과 다를 수
있습니다(예: 협력형/cooperative 스케줄링).
```

- 유저 스레드와 커널 스레드의 스케쥴링 알고리즘은 똑같을까요?
```
반드시 같지는 않습니다.

커널 스레드는 운영체제의 전역 스케줄러(예: 리눅스의 CFS)에 의해 스케줄링되며, 이 스케줄러는 여러
CPU 코어에 걸쳐 선점형으로 동작하고 시스템 전체의 자원 배분을 함께 고려합니다.

유저 스레드는 커널의 개입 없이 유저 공간의 스레드 라이브러리가 자체적으로 구현한 스케줄러를
따릅니다. 이 스케줄러는 커널 스케줄러보다 훨씬 가볍게 구현되는 경우가 많고, 문맥 전환 비용도
시스템 콜 없이 유저 공간 안에서 처리되어 훨씬 저렴하지만, 반대로 커널이 이 스레드들의 존재를 모르기
때문에 한 유저 스레드가 블로킹되면(예: 블로킹 I/O 호출) 커널 입장에서는 프로세스 전체가 멈춘 것으로
보여 같은 프로세스의 다른 유저 스레드들도 함께 멈춰버리는 한계가 있습니다. 또한 멀티코어를 스레드
단위로 실질적으로 병렬 활용하지 못하는 경우도 많습니다. 그래서 두 계층의 스케줄링은 알고리즘도,
동작 방식도, 가시성(커널이 알고 있는지)도 서로 다르다고 볼 수 있습니다.
```

**핵심 키워드** → FCFS(단순, Convoy Effect), SJF/SRTF(최단 버스트 우선, 미래 예측 필요), 우선순위 스케줄링(기아 문제 → Aging으로 보완), RR(Time Slice 크기의 응답성 vs 처리량 트레이드오프), MLFQ(사전 정보 없이 행동 관찰로 적응, Aging으로 기아 방지), 고정 최고 우선순위 + 선점형 → 상시 실행 프로세스 보장, 동시성(논리적, 겹치는 시간대에 진행) vs 병렬성(물리적, 실제 동시 실행), 커널 스레드(1:1, 커널 스케줄러 그대로 적용) vs 유저 스레드(N:1, 유저 라이브러리 자체 스케줄러, 블로킹 시 전체 정지 위험)

```
전처리(Preprocessing) 단계에서는 매크로 치환, #include 같은 지시문을 처리해서 순수한 소스

파일(.o)로 바꿉니다. 링킹(Linking) 단계에서는 링커가 여러 오브젝트 파일과 필요한 라이브러리를
하나로 묶고, 서로 참조하는 심볼(함수·전역 변수 주소 등)을 연결해서 실행 가능한 파일을 만듭니다.

이후 사용자가 프로그램을 실행하면, 운영체제의 로더(Loader)가 이 실행 파일을 읽어 메모리에 적재하고
새로운 프로세스의 주소 공간을 구성한 뒤, 프로그램의 시작 지점(entry point)으로 제어를 넘기면서
비로소 CPU가 실제로 명령어를 실행하기 시작합니다.
```

**꼬리 질문 답변**

- 링커와, 로더의 차이에 대해 설명해 주세요.
```
링커(Linker)는 컴파일 타임(정확히는 빌드 타임) 도구로, 여러 개의 오브젝트 파일과 라이브러리를
하나로 결합해서 실행 파일을 만드는 역할을 합니다. 서로 다른 파일에서 정의되고 사용되는 함수·전역
변수 같은 심볼들의 주소를 확정해서 연결(symbol resolution & relocation)하는 것이 핵심 작업이고,
이 결과물은 디스크에 저장되는 정적인 실행 파일입니다.

로더(Loader)는 런타임(프로그램 실행 시점)에 동작하는 운영체제의 구성 요소로, 디스크에 있는 실행
파일을 읽어서 실제 메모리에 적재하고 프로세스의 주소 공간(Text, Data, Heap, Stack 등)을 구성하는
역할을 합니다. 동적 링킹을 사용하는 프로그램이라면, 로더가 필요한 공유 라이브러리(.so, .dll)를
찾아 메모리에 매핑하고 그 시점에 남은 심볼 주소를 마저 연결하는 것도 로더(또는 동적 링커)의 역할입니다.

정리하면 링커는 "빌드 시점에 여러 코드 조각을 하나로 묶는" 역할이고, 로더는 "실행 시점에 그 결과물을
실제로 메모리에 올려 살아있는 프로세스로 만드는" 역할이라는 시점의 차이가 있습니다.
```

- 컴파일 언어와 인터프리터 언어의 차이에 대해 설명해 주세요.
```
컴파일 언어는 실행 전에 소스 코드 전체를 컴파일러가 한 번에 대상 플랫폼의 기계어(또는 중간 코드)로
미리 번역해두는 언어입니다(C, C++, Go 등). 실행 시점에는 이미 만들어진 기계어를 CPU가 바로
실행하므로 실행 속도가 빠르지만, 플랫폼(CPU 아키텍처·OS)마다 별도로 컴파일해야 하고 배포 전에
빌드 과정이 필요합니다.

인터프리터 언어는 소스 코드(또는 그것을 변환한 중간 표현)를 실행 시점에 한 줄씩, 혹은 한
명령어씩 읽어가며 즉석에서 해석하고 실행하는 언어입니다(전통적인 Python, Ruby 등). 별도의 빌드
과정 없이 바로 실행할 수 있어 이식성이 좋고 개발 편의성이 높지만, 매번 해석하는 오버헤드 때문에
일반적으로 순수 컴파일 언어보다 실행 속도가 느립니다.

다만 실제로는 이 둘의 경계가 뚜렷하지 않은 경우도 많습니다. Java는 컴파일해서 바이트코드를 만들지만
그 바이트코드는 JVM이 인터프리터 방식(+JIT)으로 실행하고, Python도 내부적으로는 소스를 바이트코드로
컴파일한 뒤 그 바이트코드를 인터프리터가 실행하는 하이브리드 구조를 갖고 있습니다.
```

- JIT에 대해 설명해 주세요.
```
JIT(Just-In-Time Compilation)는 인터프리터 방식의 이식성과 컴파일 방식의 실행 속도를 절충한
하이브리드 실행 전략입니다.

기본적으로는 바이트코드를 인터프리터로 한 줄씩 실행하다가, 실행 중에 특정 코드 경로(함수, 루프
등)가 반복적으로 자주 실행되는 것을 런타임이 감지하면("hot" 코드), 그 부분만 그 시점의 실제 CPU
아키텍처에 맞는 네이티브 기계어로 즉석에서 컴파일해서 캐시해두고, 이후에는 인터프리팅 없이 이
네이티브 코드를 바로 실행합니다.

이렇게 하면 프로그램 배포 시에는 여전히 플랫폼 독립적인 바이트코드 형태를 유지해 이식성을 지키면서,
실제로 반복 실행되어 성능이 중요한 부분은 네이티브 코드 수준의 속도를 얻을 수 있습니다. 대표적으로
JVM의 HotSpot, JavaScript 엔진인 V8, .NET의 CLR이 JIT를 사용합니다.
```

- 본인이 사용하는 언어는, 어떤식으로 컴파일 및 실행되는지 설명해 주세요.
```
(사용 언어에 맞게 채워 넣기)
예) Java: 개발자가 작성한 .java 소스 코드를 javac 컴파일러가 플랫폼 독립적인 바이트코드(.class
    파일)로 컴파일합니다. 이 바이트코드는 실제 기계어가 아니라 JVM(Java Virtual Machine)이라는
    가상 머신이 이해하는 중간 표현입니다. 프로그램을 실행하면 JVM의 클래스 로더가 이 바이트코드를
    메모리에 적재하고, 처음에는 인터프리터가 한 줄씩 해석·실행하다가, 자주 실행되는 hot 코드는
    JIT 컴파일러(HotSpot)가 네이티브 기계어로 변환해서 이후 실행 속도를 높입니다. 이런 구조
    덕분에 "한 번 작성하면 어디서든 실행된다(Write Once, Run Anywhere)"는 이식성과 준수한 실행
    성능을 함께 얻을 수 있습니다.
```

- Python 같은 언어는 CPython, Jython, PyPy등의 다양한 구현체가 있습니다. 각각은 어떤 차이가 있을까요? 또한, 실행되는 과정 또한 다를까요?
```
셋 다 "Python 언어"라는 같은 문법·의미 규칙을 따르지만, 그 문법을 실제로 어떻게 실행하는지(실행
엔진)가 완전히 다릅니다.

CPython은 Python의 기준(reference) 구현체로, C 언어로 작성된 인터프리터입니다. Python 소스를
자체 바이트코드로 컴파일한 뒤, C로 작성된 가상 머신이 이 바이트코드를 순수하게 인터프리팅 방식으로
실행합니다. 가장 널리 쓰이지만 JIT가 없어 실행 속도 면에서는 상대적으로 느린 편입니다.

Jython은 Python 코드를 JVM의 바이트코드로 컴파일해서 JVM 위에서 실행하는 구현체입니다. 그래서
Java 클래스 라이브러리와 자유롭게 상호운용할 수 있고, JVM의 JIT 컴파일 이점도 누릴 수 있지만, C로
작성된 CPython 확장 모듈(C 확장)과는 호환되지 않는다는 제약이 있습니다.

PyPy는 Python으로 Python 인터프리터를 구현한 뒤, 자체적으로 JIT 컴파일 기능을 갖춘 구현체입니다.
반복 실행되는 코드를 네이티브 코드로 변환해서 CPython보다 훨씬(경우에 따라 수 배~수십 배) 빠른
실행 속도를 낼 수 있지만, 마찬가지로 일부 C 확장과의 호환성 문제나 시작 시간(warm-up) 오버헤드가
있을 수 있습니다.
```

- 우리는 흔히 fork(), exec() 시스템 콜을 사용하여 프로세스를 적재할 수 있다고 배웠습니다. 로더의 역할은 이 시스템 콜과 상관있는 걸까요? 아니면 다른 방식으로 프로세스를 적재할 수 있는 건가요?
```
네, 직접적으로 연관이 있습니다. 로더의 역할은 exec() 계열 시스템 콜(execve 등)이 커널 내부에서
호출될 때 수행되는 작업 그 자체라고 볼 수 있습니다.

exec()가 호출되면 커널은 지정된 실행 파일을 열어서 ELF 같은 실행 파일 형식의 헤더를 해석하고,
그 안에 정의된 각 세그먼트(Text, Data 등)를 현재 프로세스의 주소 공간에 매핑하고, BSS 영역을
0으로 초기화하고, 필요하다면 동적 링커(ld.so 같은)를 함께 매핑해서 공유 라이브러리 연결을 준비시킨
뒤, 최종적으로 프로그램의 시작 지점(entry point)으로 실행 흐름을 넘깁니다. 이 전체 과정이 바로
"로더가 하는 일"이며, 리눅스에서는 이 로직이 커널 내부(exec 관련 코드 경로)에 구현되어 있어서
exec() 시스템 콜을 호출하는 것 자체가 곧 로더를 실행시키는 것과 같습니다.

fork()는 이와 달리 이미 존재하는 프로세스를 복제만 할 뿐 새로운 프로그램을 적재하지 않으므로,
로더가 개입하지 않습니다. 그래서 보통 "새 프로그램을 실행한다"는 목적을 이루려면 fork()로 새
프로세스(자식)를 만든 뒤 그 자식이 exec()를 호출해서 비로소 로더가 새 프로그램을 적재하는,
fork() + exec() 조합을 사용합니다.
```

**핵심 키워드** → 전처리 → 컴파일(소스→어셈블리) → 어셈블(어셈블리→오브젝트 파일) → 링킹(심볼 해석·연결, 실행 파일 생성) → 로딩(메모리 적재·주소 공간 구성) → 실행, 링커(빌드 타임, 여러 오브젝트 결합) vs 로더(런타임, 메모리 적재+동적 링킹), 컴파일 언어(사전 번역, 빠름) vs 인터프리터 언어(즉석 해석, 이식성), JIT(인터프리팅 + hot code만 네이티브 컴파일), CPython(C 인터프리터, 기준 구현) vs Jython(JVM 바이트코드) vs PyPy(자체 JIT), 로더 역할 = exec() 계열 시스템 콜(execve)의 커널 내부 동작, fork()+exec() 조합으로 새 프로그램 실행

#### 9. 32비트와 64비트의 차이는 무엇인가요?

`★★☆` · `심화` · 원본 [개발상식·기타 #12](../05-ETC.md)

<details>

- 32비트에서 가용한 메모리의 크기는 최대 4GB라고 하는데, 왜 그런걸까요?

</details>

**내 답변**

```
32비트, 64비트는 CPU가 한 번에 처리하는 데이터(레지스터)의 단위 크기, 그리고 메모리 주소를
표현하는 데 사용하는 비트 수를 의미합니다.

32비트 시스템은 레지스터와 메모리 주소 버스가 32비트 폭을 가져서, 한 번의 연산으로 다룰 수 있는
데이터 크기가 32비트(4바이트)이고, 표현 가능한 메모리 주소의 개수도 2^32개, 즉 이론상 최대 4GB의
메모리 공간까지만 주소를 매길 수 있습니다.

64비트 시스템은 이 폭이 64비트로 늘어나서, 한 번에 더 큰 수를 직접 연산할 수 있어 특정 연산(큰
정수 계산 등)에서 유리하고, 이론상 2^64개의 주소를 표현할 수 있어 훨씬 넓은 메모리 공간(현실적인
구현체는 보통 48비트 정도만 실제로 사용하지만, 그래도 32비트와는 비교할 수 없이 큼)을 활용할 수
있습니다. 또한 64비트 CPU는 대체로 레지스터 개수도 더 많이 제공하는 경우가 많아, 함수 호출 시
인자를 레지스터로 더 많이 전달할 수 있는 등 전반적인 성능 이점도 있습니다.
```

**꼬리 질문 답변**

- 32비트에서 가용한 메모리의 크기는 최대 4GB라고 하는데, 왜 그런걸까요?
```
메모리의 각 바이트에는 고유한 주소가 부여되는데, 32비트 시스템에서는 이 주소를 32비트 폭의
포인터(레지스터)로 표현합니다. 32비트로 표현할 수 있는 서로 다른 값의 개수는 2^32개이므로,
정확히 2^32 = 4,294,967,296개의 서로 다른 주소를 나타낼 수 있습니다.

메모리의 최소 주소 단위는 보통 1바이트이므로, 표현 가능한 주소 개수인 2^32개가 곧 접근 가능한
최대 바이트 수, 즉 4GB(2^32 바이트)가 됩니다. 이는 실제로 설치된 물리 메모리(RAM) 용량과는
무관하게, 순전히 주소를 표현하는 비트 수라는 구조적인 한계에서 나오는 상한선입니다. 그래서 32비트
시스템에서는 아무리 물리 메모리를 더 많이 장착해도(일부 PAE 같은 확장 기법을 쓰지 않는 이상) CPU가
가리킬 수 있는 주소 공간 자체가 4GB를 넘어설 수 없습니다.
```

**핵심 키워드** → 32/64비트 = 레지스터·주소 버스의 폭(한 번에 처리하는 데이터 크기), 표현 가능 주소 개수 = 2^(비트 수), 32비트 → 2^32 = 4GB 한계, 64비트 → 이론상 2^64(실제 구현은 보통 48비트 사용), 물리 메모리 용량과 무관한 구조적 상한선(주소 지정 가능 범위), 64비트의 추가 이점(레지스터 개수 증가 등)

#### [자료구조 2/6] Stack

**구현 범위** — 배열 기반 Stack(`push`/`pop`/`peek` + 동적 확장)과 연결 리스트 기반 Stack. 두 방식의 트레이드오프 정리

```java
// 배열 기반 Stack — 동적 확장 지원
class ArrayStack<T> {
    private Object[] arr;
    private int size;

    ArrayStack() {
        arr = new Object[10];
        size = 0;
    }

    void push(T x) {
        if (size == arr.length) {
            resize(arr.length * 2); // 꽉 차면 2배로 확장 (상각 O(1))
        }
        arr[size++] = x;
    }

    @SuppressWarnings("unchecked")
    T pop() {
        if (size == 0) throw new RuntimeException("Stack is empty");
        T value = (T) arr[size - 1];
        arr[--size] = null; // 메모리 누수 방지를 위해 참조 해제
        return value;
    }

    @SuppressWarnings("unchecked")
    T peek() {
        if (size == 0) throw new RuntimeException("Stack is empty");
        return (T) arr[size - 1];
    }

    private void resize(int newCapacity) {
        Object[] newArr = new Object[newCapacity];
        System.arraycopy(arr, 0, newArr, 0, size);
        arr = newArr;
    }

    boolean isEmpty() {
        return size == 0;
    }
}

// 연결 리스트 기반 Stack
class LinkedStack<T> {
    private static class Node<T> {
        T data;
        Node<T> next;
        Node(T data, Node<T> next) {
            this.data = data;
            this.next = next;
        }
    }

    private Node<T> top;
    private int size;

    void push(T x) {
        top = new Node<>(x, top); // 항상 head 자리에 새 노드를 연결 — O(1)
        size++;
    }

    T pop() {
        if (top == null) throw new RuntimeException("Stack is empty");
        T value = top.data;
        top = top.next;
        size--;
        return value;
    }

    T peek() {
        if (top == null) throw new RuntimeException("Stack is empty");
        return top.data;
    }

    boolean isEmpty() {
        return top == null;
    }
}
```

**두 방식의 트레이드오프**
- **배열 기반**: 연속된 메모리를 사용해 캐시 지역성이 좋고, 요소당 추가 포인터 오버헤드가 없어 메모리 효율이 좋음. 다만 용량이 꽉 찼을 때 더 큰 배열로 재할당·복사해야 하는 리사이징 비용이 발생(상각 O(1)이지만 그 순간은 O(n))
- **연결 리스트 기반**: push/pop이 항상 정확히 O(1)로 일정하고(리사이징 없음), 필요한 만큼만 노드를 할당해 최대 크기를 미리 알 필요가 없음. 다만 노드마다 포인터 저장 공간이 추가로 필요하고, 메모리가 흩어져 있어 캐시 미스가 잦을 수 있음
- 최대 크기를 예측하기 어렵고 삽입/삭제가 매우 빈번하다면 연결 리스트 기반이, 크기가 어느 정도 예측 가능하고 캐시 성능이 중요하다면 배열 기반(동적 배열)이 유리한 경우가 많음

**시간복잡도** → `push`/`pop`/`peek` 모두 두 방식 공통으로 O(1) (배열은 리사이징 시에만 상각 기준 O(1))
**공간복잡도** → 둘 다 O(n) (배열 기반은 리사이징 여유분만큼 추가 공간을 가질 수 있음, 연결 리스트는 노드당 포인터 오버헤드)

### 응용 문항

> 원본: [손코딩 연습 문항](../06-ALGORITHM.md) · IDE 없이 손으로 먼저 써본 뒤, 스터디에서 서로 비교합니다.

#### 3. 배열에 1,000,000 개의 수가 있다고 가정할 때, 여기에서 원하는 수가 몇 번째 인덱스에 위치해 있는지 확인하는 프로그램을 작성해 보세요. (단, 원하는 수가 하나가 아닐 수 있습니다.)

```java
import java.util.ArrayList;
import java.util.List;

class FindAllIndices {

    // 배열이 정렬되어 있지 않다는 전제 — 전체를 한 번 순회하며 일치하는 인덱스를 모두 수집
    static List<Integer> findIndices(int[] arr, int target) {
        List<Integer> result = new ArrayList<>();
        for (int i = 0; i < arr.length; i++) {
            if (arr[i] == target) {
                result.add(i);
            }
        }
        return result;
    }

    // (배열이 정렬되어 있다는 조건이 추가된다면) Lower/Upper Bound 이진 탐색으로 더 빠르게 구할 수 있음
    static List<Integer> findIndicesSorted(int[] arr, int target) {
        int lower = lowerBound(arr, target);
        int upper = upperBound(arr, target);

        List<Integer> result = new ArrayList<>();
        for (int i = lower; i < upper; i++) {
            result.add(i);
        }
        return result;
    }

    // target 이상인 값이 처음 등장하는 인덱스
    private static int lowerBound(int[] arr, int target) {
        int left = 0, right = arr.length;
        while (left < right) {
            int mid = left + (right - left) / 2;
            if (arr[mid] < target) left = mid + 1;
            else right = mid;
        }
        return left;
    }

    // target을 초과하는 값이 처음 등장하는 인덱스
    private static int upperBound(int[] arr, int target) {
        int left = 0, right = arr.length;
        while (left < right) {
            int mid = left + (right - left) / 2;
            if (arr[mid] <= target) left = mid + 1;
            else right = mid;
        }
        return left;
    }
}
```

**풀이 설명**

문제에 정렬 여부가 명시되어 있지 않으므로, 기본적으로는 배열 전체를 한 번 순회하며 값이 일치하는
모든 인덱스를 리스트에 모으는 선형 탐색으로 풀었습니다. 값이 여러 번 등장할 수 있다는 조건 때문에
값을 찾자마자 종료할 수 없고, 100만 개 전체를 반드시 한 번은 훑어야 하므로 O(N)이 최선입니다.

만약 배열이 미리 정렬되어 있다는 조건이 추가된다면, 목표값과 정확히 일치하는 구간이 배열 안에서
항상 연속된 하나의 구간을 이룬다는 성질을 이용해 훨씬 빠르게 풀 수 있습니다. Lower Bound(목표값
이상이 처음 나오는 위치)와 Upper Bound(목표값을 초과하는 값이 처음 나오는 위치)를 각각 이진
탐색으로 구하면, 그 사이 [lower, upper) 구간이 바로 목표값과 일치하는 모든 인덱스의 범위가
됩니다. 이 경우 구간을 찾는 데는 O(log N)이 걸리고, 이후 그 구간의 인덱스들을 리스트로 만드는 데는
등장 개수(K)만큼인 O(K)가 추가로 필요해서 전체 O(log N + K)에 처리할 수 있습니다.

**시간복잡도** → 미정렬: O(N) (전체 순회 필수) · 정렬됨: O(log N + K) (K = 목표값 등장 횟수, 이진 탐색으로 구간을 찾은 뒤 결과를 담는 비용)
**공간복잡도** → O(K) (결과를 담는 리스트, K = 목표값이 등장하는 횟수)
