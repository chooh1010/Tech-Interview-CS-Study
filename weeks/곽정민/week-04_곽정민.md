#### 1. 뮤텍스와 세마포어의 차이점은 무엇인가요?

`★★☆` · `필수` · 원본 [운영체제 #8](../02-OPERATING_SYSTEM.md)

<details>
<summary><b>꼬리 질문 3개 (펼치기)</b></summary>

- 이진 세마포어와 뮤텍스의 차이에 대해 설명해 주세요.
- Lock을 얻기 위해 대기하는 프로세스들은 Spin Lock 기법을 사용할 수 있습니다. 이 방법의 장단점은 무엇인가요? 단점을 해결할 방법은 없을까요?
- 뮤텍스와 세마포어 모두 커널이 관리하기 때문에, Lock을 얻고 방출하는 과정에서 시스템 콜을 호출해야 합니다. 이 방법의 장단점이 있을까요? 단점을 해결할 수 있는 방법은 없을까요?

</details>

**내 답변**

```
뮤텍스는 하나의 공유 자원에 대해 한 번에 한 스레드만 접근하도록 하는 잠금 장치로, 반드시 잠근 스레드 자신이 해제해야 하는 소유권 개념을 가집니다. 세마포어는 정수 카운터를 이용해 동시에 접근
가능한 자원의 개수를 관리하는 방식으로, 소유권이 없어서 잠근 스레드가 아니어도 값을 올려줄 수 있습니다. 그래서 뮤텍스는 상호배제 전용이고, 세마포어는 여러 개의 자원을 관리하거나 스레드 간
실행 순서를 맞추는 동기화 용도로도 쓸 수 있다는 차이가 있습니다.
```

**꼬리 질문 답변**

- 이진 세마포어와 뮤텍스의 차이에 대해 설명해 주세요.
```
이진 세마포어는 값이 0과 1만 가진다는 점에서 뮤텍스와 겉보기엔 비슷하지만, 소유권 개념이 없다는
근본적인 차이가 있습니다. 뮤텍스는 잠근 스레드만 해제할 수 있지만, 이진 세마포어는 다른 스레드가
signal을 줄 수 있어서 상호배제뿐 아니라 스레드 간 신호(순서 동기화) 용도로도 쓸 수 있습니다.
```

- Lock을 얻기 위해 대기하는 프로세스들은 Spin Lock 기법을 사용할 수 있습니다. 이 방법의 장단점은 무엇인가요? 단점을 해결할 방법은 없을까요?
```
Spin Lock은 락을 못 얻으면 잠들지 않고 반복문을 돌며 계속 확인하는 방식이라, 컨텍스트 스위칭
오버헤드가 없어서 임계 구역이 매우 짧을 때는 빠릅니다. 하지만 대기 시간이 길어지면 그동안 CPU를
계속 낭비하게 되는 단점이 있습니다. 이를 보완하기 위해 일정 시간 스핀하다가 안 되면 잠드는
하이브리드 락(adaptive lock)을 사용하기도 합니다.
```

- 뮤텍스와 세마포어 모두 커널이 관리하기 때문에, Lock을 얻고 방출하는 과정에서 시스템 콜을 호출해야 합니다. 이 방법의 장단점이 있을까요? 단점을 해결할 수 있는 방법은 없을까요?
```
락을 얻고 반납하는 과정에서 매번 커널로 전환하는 시스템 콜을 쓰면, 유저-커널 모드 전환
오버헤드가 경쟁이 없는 상황에서도 항상 발생한다는 단점이 있습니다. 이를 해결하기 위해 리눅스의
futex처럼, 경쟁이 없을 때는 유저 공간에서 원자적 명령어만으로 처리하고, 실제로 경합이 발생했을
때만 시스템 콜로 커널에 개입을 요청하는 방식을 씁니다.
```

**핵심 키워드** → 뮤텍스(이진 락, 소유권 O, 상호배제 전용) vs 세마포어(정수 카운터, 소유권 X, 다중 자원 관리·순서 동기화 가능), Spin Lock(컨텍스트 스위칭 없음 vs CPU 낭비, adaptive lock으로 보완), futex(무경쟁 시 유저 공간에서 처리, 경합 시에만 시스템 콜)

#### 2. Deadlock 에 대해 설명해 주세요.

`★★☆` · `필수` · 원본 [운영체제 #9](../02-OPERATING_SYSTEM.md)

<details>
<summary><b>꼬리 질문 5개 (펼치기)</b></summary>

- Deadlock 이 동작하기 위한 4가지 조건에 대해 설명해 주세요.
- 그렇다면 3가지만 충족하면 왜 Deadlock 이 발생하지 않을까요?
- 어떤 방식으로 예방할 수 있을까요?
- 왜 현대 OS는 Deadlock을 처리하지 않을까요?
- Wait Free와 Lock Free를 비교해 주세요.

</details>

**내 답변**

```
데드락은 둘 이상의 프로세스가 서로가 가진 자원을 기다리며 무한정 대기하는 상태를 말합니다.
상호 배제, 점유 대기, 비선점, 원형 대기라는 네 가지 조건이 동시에 성립할 때 발생하고, 이 중
하나라도 깨뜨리면 예방할 수 있습니다. 예를 들어 모든 자원에 고유한 순서를 매겨서 항상 그 순서
대로만 자원을 요청하게 하면, 서로 물고 물리는 원형 대기 자체가 만들어질 수 없어서 데드락을
방지할 수 있습니다.
```

**꼬리 질문 답변**

- Deadlock 이 동작하기 위한 4가지 조건에 대해 설명해 주세요.
```
상호 배제는 자원을 한 번에 한 프로세스만 쓸 수 있다는 조건이고, 점유 대기는 자원을 가진 채로
다른 자원을 기다린다는 조건입니다. 비선점은 다른 프로세스가 가진 자원을 강제로 뺏을 수 없다는
조건이고, 원형 대기는 프로세스들이 서로 물고 물리는 순환 형태로 자원을 기다린다는 조건입니다.
이 네 가지가 동시에 성립해야 데드락이 발생합니다.
```

- 그렇다면 3가지만 충족하면 왜 Deadlock 이 발생하지 않을까요?
```
네 조건은 모두 동시에 성립해야만 순환 대기 구조가 만들어지기 때문에, 하나라도 빠지면 그 순환
고리 자체가 끊어집니다. 예를 들어 비선점 조건이 없다면, 누군가 자원을 기다리다가 그냥 상대방
자원을 강제로 뺏어올 수 있으므로 무한 대기가 성립하지 않습니다.
```

- 어떤 방식으로 예방할 수 있을까요?
```
네 조건 중 하나를 구조적으로 없애는 방식으로 예방합니다. 가장 실용적인 방법은 원형 대기를 막는
것으로, 모든 자원에 고유한 순서를 매겨서 프로세스가 항상 그 순서대로만 자원을 요청하게 하면
순환 고리 자체가 생길 수 없습니다.
```

- 왜 현대 OS는 Deadlock을 처리하지 않을까요?
```
데드락을 정확히 탐지하고 회복하려면 자원 할당 그래프를 계속 추적하고 검사해야 하는데, 이
오버헤드가 실제로 데드락이 발생하는 빈도에 비해 너무 큽니다. 그래서 대부분의 범용 OS는 데드락을
사전에 막거나 감시하기보다는, 실제로 발생하면 사용자가 프로세스를 강제 종료하는 식으로 사후에
대응하는 타조 알고리즘(Ostrich Algorithm) 방식을 택합니다.
```

- Wait Free와 Lock Free를 비교해 주세요.
```
Lock Free는 락을 아예 쓰지 않고 CAS 같은 원자적 명령어로 동기화하지만, 여러 스레드 중 최소한
하나는 항상 진행할 수 있다는 것만 보장할 뿐, 특정 스레드가 계속 재시도만 하다가 기아 상태에
빠질 가능성은 남아있습니다. Wait Free는 여기서 더 나아가 모든 스레드가 유한한 단계 안에 반드시
진행을 보장하는, 더 강한 조건입니다.
```

**핵심 키워드** → 데드락 = 자원을 서로 기다리며 무한 대기, 4가지 조건(상호 배제·점유 대기·비선점·원형 대기) 동시 성립 시 발생, 조건 하나만 깨도 예방 가능(자원 순서 부여로 원형 대기 차단), 현대 OS는 타조 알고리즘(탐지·회복 오버헤드가 커서 사후 대응), Lock Free(최소 하나는 진행 보장, 기아 가능) vs Wait Free(모든 스레드 유한 단계 내 진행 보장)

**막힌 부분 / 다시 볼 것** →

#### 3. IPC가 무엇이고, 어떤 종류가 있는지 설명해 주세요.

`★★☆` · `심화` · 원본 [운영체제 #11](../02-OPERATING_SYSTEM.md)

<details>
<summary><b>꼬리 질문 2개 (펼치기)</b></summary>

- Shared Memory가 무엇이며, 사용할 때 유의해야 할 점에 대해 설명해 주세요.
- 메시지 큐는 단방향이라고 할 수 있나요?

</details>

**내 답변**

```
IPC는 서로 독립된 주소 공간을 가진 프로세스들이 직접 메모리를 공유할 수 없기 때문에, 데이터를
주고받기 위해 사용하는 프로세스 간 통신 방법입니다. 대표적으로 파이프, 메시지 큐, 공유 메모리,
소켓, 시그널 등이 있습니다. 공유 메모리는 커널 개입 없이 같은 메모리 영역을 직접 공유해서 가장
빠르지만 동기화를 직접 처리해야 하고, 파이프나 메시지 큐는 커널을 거쳐 데이터를 복사하므로
상대적으로 느리지만 안전합니다.
```

**꼬리 질문 답변**

- Shared Memory가 무엇이며, 사용할 때 유의해야 할 점에 대해 설명해 주세요.
```
공유 메모리는 여러 프로세스가 동일한 물리 메모리 영역을 각자의 가상 주소 공간에 매핑해서,
커널 개입 없이 직접 데이터를 주고받는 IPC 방식입니다. 가장 빠르다는 장점이 있지만, 커널이
접근 순서를 대신 관리해주지 않기 때문에 여러 프로세스가 동시에 읽고 쓰면 경쟁 상태가 생길 수
있어 세마포어 같은 별도의 동기화 수단을 직접 챙겨야 합니다.
```

- 메시지 큐는 단방향이라고 할 수 있나요?
```
구현에 따라 다릅니다. 전통적인 System V 메시지 큐는 하나의 큐를 여러 프로세스가 공유하며
메시지 타입으로 구분해 읽기 때문에 양방향으로도 쓸 수 있지만, 보통 실무에서는 요청용과 응답용
큐를 각각 따로 두어 사실상 단방향 큐 두 개로 양방향 통신을 구현하는 경우가 많습니다.
```

**핵심 키워드** → IPC = 독립된 주소 공간 때문에 필요한 프로세스 간 통신, 종류(파이프·메시지 큐·공유 메모리·소켓·시그널), 공유 메모리(커널 미개입, 빠름, 직접 동기화 필요) vs 파이프·메시지 큐(커널 경유, 느리지만 안전), 메시지 큐는 구현상 양방향 가능하나 보통 단방향 큐 2개로 구성

#### 4. Thread Safe 하다는 것은 어떤 의미인가요?

`★★☆` · `필수` · 원본 [운영체제 #12](../02-OPERATING_SYSTEM.md)

<details>
<summary><b>꼬리 질문 4개 (펼치기)</b></summary>

- Thread Safe 를 보장하기 위해 어떤 방법을 사용할 수 있나요?
- Peterson's Algorithm 이 무엇이며, 한계점에 대해 설명해 주세요.
- Race Condition 이 무엇인가요?
- Thread Safe를 구현하기 위해 반드시 락을 사용해야 할까요? 그렇지 않다면, 어떤 다른 방법이 있을까요?

</details>

**내 답변**

```
스레드 세이프하다는 건 여러 스레드가 동시에 어떤 코드나 자원에 접근해도 항상 올바른 결과를
보장한다는 뜻입니다. 여러 스레드가 순서를 예측할 수 없이 끼어들며 공유 자원을 동시에 읽고 쓸 때
발생하는 경쟁 상태(Race Condition)가 이 안전성을 깨는 주된 원인입니다. 그래서 락이나 세마포어로
임계 구역을 보호하거나, 아예 상태를 공유하지 않는 불변 객체·스레드 로컬 변수를 사용하는 방식으로
스레드 안전성을 보장할 수 있습니다.
```

**꼬리 질문 답변**

- Thread Safe 를 보장하기 위해 어떤 방법을 사용할 수 있나요?
```
가장 기본적인 방법은 락이나 세마포어로 임계 구역을 감싸서 한 번에 하나의 스레드만 접근하게
만드는 것입니다. 그 외에도 CAS 같은 원자적 연산을 활용한 락프리 자료구조를 쓰거나, 애초에
스레드끼리 상태를 공유하지 않도록 불변 객체나 스레드 로컬 변수로 설계하는 방법이 있습니다.
```

- Peterson's Algorithm 이 무엇이며, 한계점에 대해 설명해 주세요.
```
Peterson's Algorithm은 두 프로세스가 flag와 turn이라는 두 개의 공유 변수만으로 락 없이
상호배제를 구현하는 소프트웨어적 알고리즘입니다. 다만 두 프로세스에서만 정확히 동작하도록
설계되어 있어 세 개 이상으로 일반화하기 어렵고, 최신 CPU의 명령어 재정렬(out-of-order
execution) 환경에서는 메모리 배리어 없이는 정확성이 깨질 수 있다는 한계가 있습니다.
```

- Race Condition 이 무엇인가요?
```
경쟁 상태는 둘 이상의 스레드가 공유 자원에 동시에 접근하고, 그중 적어도 하나가 쓰기 작업을 할
때, 실행 순서(타이밍)에 따라 결과가 달라지는 상황을 말합니다. 예를 들어 두 스레드가 동시에
카운터를 증가시키면, 읽고-더하고-쓰는 과정이 끼어들면서 증가 횟수보다 실제 값이 덜 늘어날 수
있습니다.
```

- Thread Safe를 구현하기 위해 반드시 락을 사용해야 할까요? 그렇지 않다면, 어떤 다른 방법이 있을까요?
```
반드시 락이 필요한 건 아닙니다. CAS 기반의 락프리 자료구조를 쓰면 락 없이도 원자성을 보장할
수 있고, 더 근본적으로는 스레드끼리 아예 가변 상태를 공유하지 않도록 설계하면(불변 객체,
스레드 로컬 변수, 메시지 전달 방식) 동기화 자체가 필요 없어집니다.
```

**핵심 키워드** → Thread Safe = 동시 접근에도 항상 올바른 결과 보장, 경쟁 상태(Race Condition)가 원인, 보장 방법(락/세마포어로 임계구역 보호, 불변 객체·스레드 로컬로 공유 자체를 회피), Peterson's Algorithm(2개 프로세스 전용 소프트웨어 상호배제, out-of-order 환경에서 한계), CAS 기반 락프리도 대안

**막힌 부분 / 다시 볼 것** →

#### 5. Thread Pool, Monitor, Fork-Join에 대해 설명해 주세요.

`★★★` · `심화` · 원본 [운영체제 #13](../02-OPERATING_SYSTEM.md)

<details>
<summary><b>꼬리 질문 2개 (펼치기)</b></summary>

- Thread Pool을 사용한다고 가정하면, 어떤 기준으로 스레드의 수를 결정할 것인가요?
- 어떤 데이터를 정렬 하려고 합니다. 어떤 방식의 전략을 사용하는 것이 가장 안전하면서도 좋은 성능을 낼 수 있을까요?

</details>

**내 답변**

```
스레드 풀은 스레드를 미리 여러 개 생성해두고 작업이 들어올 때마다 재사용하는 방식으로, 매번
스레드를 새로 만들고 없애는 오버헤드를 줄여줍니다. 모니터는 상호배제(락)와 조건변수를 하나로
묶어서 언어나 런타임 차원에서 동기화를 더 쉽고 안전하게 쓸 수 있게 해주는 고수준 동기화 도구입니다.
Fork-Join은 큰 작업을 작은 단위로 재귀적으로 쪼갠 뒤(fork) 각 조각을 병렬로 처리하고, 그 결과를
다시 합치는(join) 분할 정복 기반의 병렬 처리 모델입니다.
```

**꼬리 질문 답변**

- Thread Pool을 사용한다고 가정하면, 어떤 기준으로 스레드의 수를 결정할 것인가요?
```
작업의 성격에 따라 다릅니다. CPU 위주의 연산이 많다면 코어 개수만큼(또는 코어 수+1 정도)으로
맞춰야 컨텍스트 스위칭 낭비 없이 효율적이고, I/O 대기가 많은 작업이라면 대기하는 동안 다른
스레드가 CPU를 쓸 수 있도록 코어 개수보다 훨씬 많은 스레드를 두는 것이 유리합니다.
```

- 어떤 데이터를 정렬 하려고 합니다. 어떤 방식의 전략을 사용하는 것이 가장 안전하면서도 좋은 성능을 낼 수 있을까요?
```
데이터 규모가 크고 병렬 처리가 가능한 정렬이라면, 배열을 절반씩 나눠 각 부분을 별도 스레드
(또는 Fork-Join)로 병렬 정렬한 뒤 병합하는 병렬 병합 정렬이 안전하면서도 좋은 성능을 냅니다.
각 스레드가 서로 겹치지 않는 독립된 구간만 다루기 때문에 별도의 락 없이도 안전하게 동시성을
활용할 수 있습니다.
```

**핵심 키워드** → Thread Pool(스레드 재사용, 생성·소멸 오버헤드 감소), Monitor(락+조건변수를 묶은 고수준 동기화 도구), Fork-Join(분할 정복 기반 병렬 처리, fork로 쪼개고 join으로 합침), 스레드 수 기준(CPU-bound는 코어 수, I/O-bound는 코어 수보다 많게), 병렬 병합 정렬(독립 구간 분할로 락 없이 안전)

#### 6. 동기화를 구현하기 위한 하드웨어적인 해결 방법에 대해 설명해 주세요.

`★★★` · `심화` · 원본 [운영체제 #20](../02-OPERATING_SYSTEM.md)

<details>
<summary><b>꼬리 질문 2개 (펼치기)</b></summary>

- volatile 키워드는 어떤 의미가 있나요?
- 싱글코어가 아니라 멀티코어라면, 어떻게 동기화가 이뤄질까요?

</details>

**내 답변**

```
소프트웨어만으로 동기화를 구현하면 명령어 사이에 인터럽트가 끼어들어 원자성이 깨질 수 있기
때문에, CPU가 제공하는 원자적 명령어를 활용합니다. 대표적으로 Test-and-Set이나 Compare-and-
Swap 같은 명령어는 값을 읽고 비교하고 쓰는 과정을 하드웨어 차원에서 하나의 명령으로 묶어서,
중간에 다른 스레드나 인터럽트가 절대 끼어들 수 없도록 보장합니다. 이런 원자적 명령어를 기반으로
스핀락 같은 동기화 기법을 소프트웨어 계층에서 구현할 수 있습니다.
```

**꼬리 질문 답변**

- volatile 키워드는 어떤 의미가 있나요?
```
volatile은 컴파일러와 CPU에게 이 변수는 다른 스레드나 하드웨어에 의해 예상치 못하게 바뀔 수
있으니, 레지스터나 캐시에 값을 캐싱하지 말고 매번 실제 메모리에서 읽고 쓰라고 알려주는
키워드입니다. 다만 읽기-수정-쓰기 같은 복합 연산까지 원자적으로 만들어주지는 않기 때문에,
상호배제 자체를 보장하는 용도로는 부족하고 가시성(visibility) 문제만 해결해줍니다.
```

- 싱글코어가 아니라 멀티코어라면, 어떻게 동기화가 이뤄질까요?
```
멀티코어에서는 Test-and-Set이나 Compare-and-Swap 같은 원자적 명령어가 CPU 간 공유되는 캐시
일관성 프로토콜(cache coherence protocol)과 함께 동작해서, 한 코어가 해당 메모리 위치에
접근하는 동안 다른 코어의 접근을 하드웨어 차원에서 잠가(버스 락 또는 캐시 라인 락) 원자성을
보장합니다.
```

**핵심 키워드** → 소프트웨어 동기화의 한계(명령어 사이 인터럽트로 원자성 붕괴), 하드웨어 원자적 명령어(Test-and-Set, Compare-and-Swap)로 read-compare-write를 한 명령으로 묶음, 이를 기반으로 스핀락 등 구현, volatile(가시성만 보장, 원자성은 아님), 멀티코어는 캐시 일관성 프로토콜+원자적 명령어로 동기화

**막힌 부분 / 다시 볼 것** →

#### 7. 동기와 비동기, 블로킹과 논블로킹의 차이에 대해 설명해 주세요.

`★★★` · `필수` · 원본 [운영체제 #23](../02-OPERATING_SYSTEM.md)

<details>
<summary><b>꼬리 질문 3개 (펼치기)</b></summary>

- 그렇다면, 동기이면서 논블로킹이고, 비동기이면서 블로킹인 경우는 의미가 있다고 할 수 있나요?
- I/O 멀티플렉싱에 대해 설명해 주세요.
- 논블로킹 I/O를 수행한다고 하면, 그 결과를 어떻게 수신할 수 있나요?

</details>

**내 답변**

```
블로킹과 논블로킹은 함수를 호출했을 때 제어권을 바로 돌려받는지에 대한 차이입니다. 블로킹은
작업이 끝날 때까지 호출한 쪽이 멈춰서 기다리고, 논블로킹은 결과와 상관없이 즉시 제어권을 돌려받아
다른 일을 할 수 있습니다. 동기와 비동기는 작업 완료를 누가 확인하는지의 차이로, 동기는 호출한
쪽이 직접 결과를 확인하고, 비동기는 작업이 끝나면 콜백이나 이벤트로 통보받습니다. 즉 블로킹/
논블로킹은 제어권 반환 시점, 동기/비동기는 결과를 받는 방식에 대한 서로 다른 축의 개념입니다.
```

**꼬리 질문 답변**

- 그렇다면, 동기이면서 논블로킹이고, 비동기이면서 블로킹인 경우는 의미가 있다고 할 수 있나요?
```
네, 둘 다 실제로 의미가 있습니다. 동기+논블로킹은 호출 즉시 제어권은 돌아오지만 결과가
준비됐는지는 호출자가 직접 반복적으로 확인(폴링)해야 하는 경우이고, 비동기+블로킹은 흔치는
않지만 작업을 비동기로 요청해두고 여러 작업의 완료를 한 번에 기다리는 select/epoll 같은 대기
방식에서 나타날 수 있습니다.
```

- I/O 멀티플렉싱에 대해 설명해 주세요.
```
I/O 멀티플렉싱은 하나의 스레드가 여러 개의 I/O 디스크립터(소켓 등)를 동시에 감시하다가, 그중
준비가 된 것이 생기면 그것만 골라서 처리하는 방식입니다. select, poll, epoll 같은 시스템 콜이
대표적이고, 스레드 하나로 수많은 연결을 효율적으로 처리할 수 있어 고성능 서버에서 많이 씁니다.
```

- 논블로킹 I/O를 수행한다고 하면, 그 결과를 어떻게 수신할 수 있나요?
```
크게 두 가지 방식이 있습니다. 콜백 함수를 등록해뒀다가 작업이 끝나면 그 콜백이 호출되는 방식,
또는 Future·Promise 객체를 즉시 반환받고 나중에 그 객체를 통해 결과를 조회하거나 완료를
기다리는(await) 방식입니다.
```

**핵심 키워드** → 블로킹/논블로킹 = 호출 즉시 제어권을 돌려받는지(호출 방식 축), 동기/비동기 = 결과 완료를 누가 확인하는지(결과 수신 방식 축), 두 개념은 서로 독립된 축이라 4가지 조합 모두 성립 가능, I/O 멀티플렉싱(select/poll/epoll로 여러 디스크립터 동시 감시), 논블로킹 결과 수신(콜백 또는 Future/Promise)

**막힌 부분 / 다시 볼 것** →

#### 8. 가상화가 무엇이고, 이것이 가상머신과 어떠한 차이가 있는지 설명해 주세요.

`★★☆` · `필수` · 원본 [개발상식·기타 #1](../05-ETC.md)

<details>
<summary><b>꼬리 질문 3개 (펼치기)</b></summary>

- 그렇다면 Docker는 둘 중 어디에 속하나요? 왜 사람들이 Docker를 많이 채택할까요?
- 하나의 Host OS에서 돌아간다면 충분히 한 컨테이너가 다른 컨테이너에 간섭할 수 있는 위험이 있지 않을까요? 이를 어떻게 방어할 수 있을까요?
- Docker 위에 Docker를 올릴 순 없을까요?

</details>

**내 답변**

```
가상화는 물리적인 하드웨어 자원을 논리적으로 추상화해서, 실제와 다르게 여러 개로 나누거나 다른
형태로 보이도록 만드는 기술 전반을 말합니다. 가상머신은 이 가상화 기술 중 하나로, 하이퍼바이저
위에 게스트 OS 커널까지 통째로 에뮬레이션해서 하나의 독립된 컴퓨터처럼 동작시키는 방식입니다.
즉 가상화가 더 큰 상위 개념이고, 가상머신은 그걸 구현하는 대표적인 방식 중 하나이며, 컨테이너도
가상화의 한 형태지만 OS 커널은 호스트와 공유한다는 점에서 가상머신과 다릅니다.
```

**꼬리 질문 답변**

- 그렇다면 Docker는 둘 중 어디에 속하나요? 왜 사람들이 Docker를 많이 채택할까요?
```
Docker는 컨테이너 가상화에 속합니다. 게스트 OS 없이 호스트 커널을 그대로 공유하면서 프로세스만
격리하기 때문에, 커널을 통째로 부팅하는 가상머신보다 훨씬 가볍고 시작 속도도 빠릅니다. 게다가
이미지 하나로 어디서든 동일한 실행 환경을 보장할 수 있어서 개발-배포 환경 불일치 문제를 줄여준다는
점 때문에 널리 채택됩니다.
```

- 하나의 Host OS에서 돌아간다면 충분히 한 컨테이너가 다른 컨테이너에 간섭할 수 있는 위험이 있지 않을까요? 이를 어떻게 방어할 수 있을까요?
```
네, 같은 커널을 공유하는 구조라 가상머신보다는 격리 수준이 약한 것이 사실입니다. 이를 방어하기
위해 리눅스는 네임스페이스(프로세스·네트워크·파일시스템 등을 컨테이너별로 독립된 것처럼 보이게
분리)와 cgroups(자원 사용량 제한)를 함께 사용하고, 추가로 seccomp나 AppArmor 같은 보안
프로파일로 컨테이너가 쓸 수 있는 시스템 콜 자체를 제한합니다.
```

- Docker 위에 Docker를 올릴 순 없을까요?
```
가능합니다. Docker-in-Docker(DinD)라는 방식으로 컨테이너 안에 별도의 Docker 데몬을 띄워서
실행할 수 있고, 더 가벼운 대안으로는 호스트의 Docker 소켓을 컨테이너에 마운트해서 내부에서
호스트의 Docker를 그대로 제어하는 방식(Docker socket mounting)도 CI 파이프라인 등에서 자주
씁니다.
```

**핵심 키워드** → 가상화(하드웨어 자원의 논리적 추상화, 상위 개념) vs 가상머신(하이퍼바이저+게스트 OS 커널까지 통째로 에뮬레이션), 컨테이너는 커널을 호스트와 공유하는 가벼운 가상화 방식, Docker=컨테이너 가상화(빠른 시작·환경 일관성), 격리는 네임스페이스+cgroups+seccomp/AppArmor, DinD 또는 Docker socket mounting으로 Docker-in-Docker 가능

**막힌 부분 / 다시 볼 것** →

#### 9. CI/CD 를 사용해 본 경험이 있나요? 있다면 간단하게 설명해 주세요.

`★★☆` · `필수` · 원본 [개발상식·기타 #2](../05-ETC.md)

<details>
<summary><b>꼬리 질문 7개 (펼치기)</b></summary>

- 소스코드를 작성하고 나서, 실제 사용자에게 배포되기까지의 과정을 순서대로 설명해 주세요.
- 빌드와 배포는 어떻게 다른가요?
- CI와 CD는 각각 무엇을 자동화하는 것인가요? CD의 Delivery와 Deployment는 어떤 차이가 있나요?

- 빌드 결과물을 이미지로 만들어 배포하는 방식은, 서버에서 직접 빌드하는 방식과 비교해 어떤 장점이 있을까요?

</details>

**내 답변**

```
CI는 개발자들이 작성한 코드를 자주 통합하면서 빌드와 테스트를 자동으로 돌려 문제를 빠르게
발견하는 것이고, CD는 그렇게 검증된 결과물을 운영 환경까지 자동으로 배포하는 것을 말합니다.

(사용 경험에 맞게 채워 넣기)
예) GitHub Actions를 사용해본 경험이 있습니다. PR이 올라오면 자동으로 빌드와 테스트를 실행해서
    통과해야만 머지할 수 있게 했고, main 브랜치에 머지되면 Docker 이미지를 빌드해서 서버에
    배포하는 파이프라인을 구성해봤습니다.
```

**꼬리 질문 답변**

- 소스코드를 작성하고 나서, 실제 사용자에게 배포되기까지의 과정을 순서대로 설명해 주세요.
```
개발자가 코드를 작성해서 커밋·푸시하면, CI 파이프라인이 트리거되어 자동으로 빌드하고 테스트를
실행합니다. 통과하면 배포 가능한 산출물(이미지 등)을 만들어 저장소에 등록하고, CD 파이프라인이
이를 스테이징이나 운영 서버에 자동(또는 승인 후) 배포해서 최종적으로 사용자가 새 버전을 쓸 수
있게 됩니다.
```

- 빌드와 배포는 어떻게 다른가요?
```
빌드는 소스 코드를 컴파일하고 테스트해서 실행 가능한 산출물(바이너리, 이미지 등)을 만드는
과정이고, 배포는 그 산출물을 실제 서버 환경에 옮겨서 사용자가 쓸 수 있도록 실행시키는 과정입니다.
빌드가 끝난다고 곧바로 사용자에게 반영되는 게 아니라, 배포라는 별도의 단계를 거쳐야 합니다.
```

- CI와 CD는 각각 무엇을 자동화하는 것인가요? CD의 Delivery와 Deployment는 어떤 차이가 있나요?
```
CI는 코드 통합·빌드·테스트를 자동화해서 통합 시점의 문제를 빠르게 발견하는 것이고, CD는 그
이후 배포 과정을 자동화하는 것입니다. Delivery는 배포 가능한 상태까지만 자동으로 준비해두고
실제 운영 반영은 사람이 승인해서 진행하는 것이고, Deployment는 그 반영까지도 완전히 자동으로
이뤄지는 것이라는 차이가 있습니다.
```

- 파이프라인의 어느 단계에 테스트를 넣는 것이 좋을까요? 그 이유는 무엇인가요?
```
보통 빌드 직후, 배포 가능한 산출물로 만들기 전 단계에 단위 테스트와 통합 테스트를 넣습니다.
문제를 최대한 일찍 발견할수록 고치는 비용이 적기 때문에, 무거운 테스트는 뒤로 미루더라도
빠르게 도는 단위 테스트만큼은 파이프라인 초반에 실행해서 실패 시 이후 단계로 넘어가지 않도록
막는 것이 좋습니다.
```

- 무중단 배포는 어떻게 구현할 수 있을까요? (Rolling, Blue-Green, Canary)
```
Rolling 배포는 기존 인스턴스를 순차적으로 하나씩 새 버전으로 교체하는 방식이고, Blue-Green은
동일한 환경 두 벌을 두고 트래픽을 한 번에 새 환경으로 전환하는 방식입니다. Canary는 새 버전을
일부 트래픽에만 먼저 노출해서 문제가 없는지 확인한 뒤 점진적으로 비중을 늘려가는 방식으로, 셋
다 이전 버전에서 새 버전으로 무중단 전환하는 게 목표입니다.
```

- 배포한 버전에 장애가 발생했을 때, 롤백은 어떤 방식으로 준비해 둘 수 있을까요?
```
이전 버전의 이미지나 아티팩트를 항상 별도로 보관해두고, 배포 시스템에서 손쉽게 이전 버전을
다시 배포할 수 있도록 태그나 버전 번호로 관리합니다. Blue-Green 방식이라면 트래픽을 이전
환경으로 다시 돌리기만 하면 되므로 롤백이 특히 빠르고 안전합니다.
```

- 빌드 결과물을 이미지로 만들어 배포하는 방식은, 서버에서 직접 빌드하는 방식과 비교해 어떤 장점이 있을까요?
```
이미지로 빌드해서 배포하면, 빌드 시점에 필요한 라이브러리와 런타임 환경이 이미지 안에 모두
고정되기 때문에 서버마다 환경이 달라서 생기는 문제("내 컴퓨터에서는 됐는데" 상황)를 막을 수
있습니다. 반면 서버에서 직접 빌드하면 그 서버의 환경 설정에 실행이 좌우되고, 빌드 과정에서
운영 서버의 자원을 추가로 소모하게 된다는 단점이 있습니다.
```

**핵심 키워드** → CI(빌드·테스트 자동화, 문제 조기 발견) vs CD(검증된 결과물을 운영 환경까지 자동 배포), 대표 도구(GitHub Actions 등), Docker 이미지 빌드 후 배포하는 파이프라인 예시, 빌드(산출물 생성) vs 배포(서버에 반영), Delivery(승인 후 반영) vs Deployment(완전 자동 반영), 테스트는 빌드 직후 초반 배치, 무중단 배포(Rolling·Blue-Green·Canary), 롤백(이전 아티팩트 보관+버전 관리), 이미지 배포는 환경 일관성 보장·서버 자원 절약
