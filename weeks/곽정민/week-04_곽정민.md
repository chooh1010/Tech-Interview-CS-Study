#### 1. 뮤텍스와 세마포어의 차이점은 무엇인가요?

`★★☆` · `필수` · 원본 [운영체제 #8](../02-OPERATING_SYSTEM.md)

<details>
<summary><b>꼬리 질문 3개 (펼치기)</b></summary>

- 이진 세마포어와 뮤텍스의 차이에 대해 설명해 주세요.
- Lock을 얻기 위해 대기하는 프로세스들은 Spin Lock 기법을 사용할 수 있습니다. 이 방법의 장단점은 무엇인가요? 단점을 해결할 방법은 없을까요?
- 뮤텍스와 세마포어 모두 커널이 관리하기 때문에, Lock을 얻고 방출하는 과정에서 시스템 콜을 호출해야 합니다. 이 방법의 장단점이 있을까요? 단점을 해결할 수 있는 방법은 없을까요?

</details>

**내 답변**

```
가장 큰 차이는 "동시에 몇 개까지 허용하느냐"와 "소유권이 있느냐"입니다. 뮤텍스는 오직 하나의
스레드만 임계 구역에 들어갈 수 있는 상호 배제 전용 락이고, 잠근 스레드만 풀 수 있는 소유권
개념이 있습니다. 세마포어는 정수 카운터로 동시 접근 가능한 자원 개수를 관리해서 여러 스레드의
접근을 허용할 수 있고, 소유권 없이 다른 스레드가 값을 올려줄 수도 있습니다. 그래서 단일 자원
보호에는 뮤텍스를, 제한된 개수의 자원 풀 관리에는 세마포어를 사용합니다.
```

**꼬리 질문 답변**

- 이진 세마포어와 뮤텍스의 차이에 대해 설명해 주세요.
```
값이 0과 1만 갖는다는 점에서 비슷해 보이지만, 소유권 개념 유무가 핵심 차이입니다. 뮤텍스는 잠근
스레드만 해제할 수 있어 데드락 원인 추적이 쉬운 반면, 이진 세마포어는 다른 스레드가 signal을
호출해도 되기 때문에 락보다는 스레드 간 신호 전달(이벤트 알림) 용도로 더 자주 쓰입니다.
```

- Lock을 얻기 위해 대기하는 프로세스들은 Spin Lock 기법을 사용할 수 있습니다. 이 방법의 장단점은 무엇인가요? 단점을 해결할 방법은 없을까요?
```
Spin Lock은 컨텍스트 스위칭 없이 계속 락을 확인(busy-wait)하기 때문에, 락 보유 시간이 아주
짧을 때는 스위칭 오버헤드를 피해 오히려 빠릅니다. 단점은 대기 시간이 길어지면 CPU를 낭비하고,
싱글 코어에서는 락을 쥔 스레드의 실행 기회까지 뺏을 수 있다는 것입니다. 이를 보완하기 위해 짧게
스핀하다가 실패하면 스레드를 재우는 Adaptive Lock을 사용합니다.
```

- 뮤텍스와 세마포어 모두 커널이 관리하기 때문에, Lock을 얻고 방출하는 과정에서 시스템 콜을 호출해야 합니다. 이 방법의 장단점이 있을까요? 단점을 해결할 수 있는 방법은 없을까요?
```
커널이 관리하면 프로세스 간에도 동작하고, 대기 중인 스레드를 스케줄러가 재워둘 수 있다는 장점이
있습니다. 다만 락을 얻고 놓을 때마다 시스템 콜과 모드 전환 비용이 든다는 단점이 있습니다. 이를
줄이기 위해 경합이 없을 때는 유저 공간에서 CAS만으로 처리하고, 실제 경합이 발생했을 때만 커널에
진입하는 Futex 같은 하이브리드 방식을 사용합니다.
```

**핵심 키워드** → 뮤텍스(상호 배제, 1개, 소유권 O) vs 세마포어(카운팅, N개, 소유권 X), 이진 세마포어(소유권 없음, 신호 전달용), Spin Lock(busy-wait, 짧은 락에 유리, CPU 낭비 위험) → Adaptive Lock, 커널 관리 락의 시스템 콜 비용 → Futex(유저 공간 CAS + 경합 시에만 커널 진입)

**막힌 부분 / 다시 볼 것** →

#### 2. Deadlock 에 대해 설명해 주세요.

`★★☆` · `필수` · 원본 [운영체제 #9](../02-OPERATING_SYSTEM.md)

<details>
<summary><b>꼬리 질문 5개 (펼치기)</b></summary>

- Deadlock 이 동작하기 위한 4가지 조건에 대해 설명해 주세요.
- 그렇다면 3가지만 충족하면 왜 Deadlock 이 발생하지 않을까요?
- 어떤 방식으로 예방할 수 있을까요?
- 왜 현대 OS는 Deadlock을 처리하지 않을까요?
- Wait Free와 Lock Free를 비교해 주세요.

</details>

**내 답변**

```
데드락은 두 개 이상의 프로세스(또는 스레드)가 서로 상대방이 점유한 자원을 기다리며 무한정
대기하는 상태를 말합니다. 상호 배제, 점유 대기, 비선점, 순환 대기라는 네 가지 조건이 동시에
성립할 때 발생하고, 이 중 하나라도 구조적으로 깨뜨리면 예방할 수 있습니다.
```

**꼬리 질문 답변**

- Deadlock 이 동작하기 위한 4가지 조건에 대해 설명해 주세요.
```
상호 배제는 자원을 한 번에 하나의 프로세스만 쓸 수 있다는 조건, 점유 대기는 자원을 쥔 채로 다른
자원을 기다린다는 조건, 비선점은 자원을 강제로 뺏을 수 없다는 조건, 순환 대기는 프로세스들이
원형으로 서로의 자원을 기다린다는 조건입니다. 이 네 가지가 동시에 성립해야 데드락이 발생합니다.
```

- 그렇다면 3가지만 충족하면 왜 Deadlock 이 발생하지 않을까요?
```
넷 중 하나라도 빠지면 대기의 순환 고리를 끊을 여지가 생기기 때문입니다. 예를 들어 비선점 조건이
없다면 자원을 강제로 빼앗아 다른 프로세스에게 줄 수 있어서, 애초에 순환 대기 자체가 성립할 수
없습니다.
```

- 어떤 방식으로 예방할 수 있을까요?
```
네 조건 중 하나를 구조적으로 깨뜨리는 방식을 씁니다. 대표적으로 모든 자원에 고정된 순서를 매겨
항상 그 순서대로만 요청하게 하면 순환 대기가 원천적으로 불가능해지고, 필요한 자원을 처음에 한
번에 모두 요청하게 하면 점유 대기 조건을 없앨 수 있습니다.
```

- 왜 현대 OS는 Deadlock을 처리하지 않을까요?
```
예방이나 회피는 자원 요청 패턴을 사전에 다 알아야 해서 비용이 크고 시스템 활용도를 떨어뜨리기
때문입니다. 실제 발생 빈도가 낮은 편이라, 대부분의 범용 OS는 이를 감수하고 문제가 생기면 재부팅이나
프로세스 강제 종료로 대응하는 타조 알고리즘(Ostrich Algorithm) 전략을 택합니다.
```

- Wait Free와 Lock Free를 비교해 주세요.
```
둘 다 락 없이 동시성을 처리하지만 보장 수준이 다릅니다. Lock-Free는 시스템 전체적으로 어떤
스레드는 반드시 진행된다는 것만 보장하고, Wait-Free는 한 걸음 더 나아가 모든 개별 스레드가 유한한
단계 안에 반드시 진행됨을 보장합니다. 그만큼 Wait-Free 구현이 훨씬 까다롭습니다.
```

**핵심 키워드** → 데드락 4조건(상호 배제·점유 대기·비선점·순환 대기, 넷 다 성립해야 발생), 예방 = 조건 하나를 구조적으로 제거(자원 순서화 → 순환 대기 제거, 일괄 요청 → 점유 대기 제거), 현대 OS는 타조 알고리즘(예방/회피 비용 > 발생 빈도), Lock-Free(전체 중 하나는 진행 보장) vs Wait-Free(모든 스레드 유한 단계 내 진행 보장)

#### 3. IPC가 무엇이고, 어떤 종류가 있는지 설명해 주세요.

`★★☆` · `심화` · 원본 [운영체제 #11](../02-OPERATING_SYSTEM.md)

<details>
<summary><b>꼬리 질문 2개 (펼치기)</b></summary>

- Shared Memory가 무엇이며, 사용할 때 유의해야 할 점에 대해 설명해 주세요.
- 메시지 큐는 단방향이라고 할 수 있나요?

</details>

**내 답변**

```
IPC(Inter-Process Communication)는 서로 다른 프로세스가 데이터를 주고받거나 동작을 동기화하기
위한 방법입니다. 크게 메모리를 공유하는 방식과 커널을 거쳐 메시지를 주고받는 방식으로 나뉘고,
대표적으로 Shared Memory, Pipe, Message Queue, Socket, Signal이 있습니다.
```

**꼬리 질문 답변**

- Shared Memory가 무엇이며, 사용할 때 유의해야 할 점에 대해 설명해 주세요.
```
Shared Memory는 여러 프로세스가 동일한 물리 메모리 영역을 각자의 주소 공간에 매핑해서 직접
데이터를 주고받는 방식으로, 커널을 거치지 않아 IPC 중 가장 빠릅니다. 다만 동시 접근에 대한
동기화를 운영체제가 대신해주지 않기 때문에, 세마포어 같은 별도의 동기화 기법을 직접 구현해야
경쟁 상태를 막을 수 있습니다.
```

- 메시지 큐는 단방향이라고 할 수 있나요?
```
단방향이라고 단정할 수는 없습니다. 메시지마다 타입을 지정할 수 있어서 하나의 큐 안에서도 타입을
구분해 양방향처럼 쓸 수 있고, 필요하면 요청용과 응답용 큐를 따로 두어 완전한 양방향 통신을
구성할 수도 있습니다.
```

**핵심 키워드** → IPC = 프로세스 간 통신·동기화 수단, 메모리 공유(Shared Memory) vs 커널 경유 메시지 전달(Pipe·Message Queue·Socket·Signal), Shared Memory(가장 빠름, 동기화는 직접 구현 필요), 메시지 큐는 타입 구분/큐 분리로 양방향 구성 가능

**막힌 부분 / 다시 볼 것** →

#### 4. Thread Safe 하다는 것은 어떤 의미인가요?

`★★☆` · `필수` · 원본 [운영체제 #12](../02-OPERATING_SYSTEM.md)

<details>
<summary><b>꼬리 질문 4개 (펼치기)</b></summary>

- Thread Safe 를 보장하기 위해 어떤 방법을 사용할 수 있나요?
- Peterson's Algorithm 이 무엇이며, 한계점에 대해 설명해 주세요.
- Race Condition 이 무엇인가요?
- Thread Safe를 구현하기 위해 반드시 락을 사용해야 할까요? 그렇지 않다면, 어떤 다른 방법이 있을까요?

</details>

**내 답변**

```
Thread Safe하다는 것은 여러 스레드가 동시에 같은 코드나 데이터에 접근해도 항상 올바른 결과를
보장한다는 의미입니다. 공유 자원에 대한 접근을 락이나 원자적 연산으로 보호해서, 실행 순서에
따라 결과가 달라지는 경쟁 상태(Race Condition)가 발생하지 않도록 만든 상태를 말합니다.
```

**꼬리 질문 답변**

- Thread Safe 를 보장하기 위해 어떤 방법을 사용할 수 있나요?
```
크게 세 가지로 접근합니다. 락으로 임계 구역에 한 번에 하나의 스레드만 들어가게 하거나, CAS 같은
원자적 연산으로 락 없이 안전하게 값을 갱신하거나, 아예 공유 상태를 없애고 각 스레드가 독립된
데이터만 다루도록 불변 객체나 Thread-Local로 설계하는 방법입니다.
```

- Peterson's Algorithm 이 무엇이며, 한계점에 대해 설명해 주세요.
```
Peterson's Algorithm은 두 프로세스가 flag 배열과 turn 변수만으로, 하드웨어 지원 없이
소프트웨어만으로 상호 배제를 구현하는 알고리즘입니다. 다만 두 프로세스 사이에서만 동작하고,
현대 CPU의 명령어 재정렬 때문에 메모리 배리어 없이는 실제로 올바르게 동작한다는 보장이 없다는
한계가 있습니다.
```

- Race Condition 이 무엇인가요?
```
Race Condition은 두 개 이상의 스레드가 공유 자원에 동시에 접근할 때, 실행 순서(타이밍)에 따라
결과가 달라지는 상태를 말합니다. 예를 들어 두 스레드가 동시에 카운터를 증가시키면, 읽고-더하고-
쓰는 세 연산이 겹쳐서 값이 유실될 수 있습니다.
```

- Thread Safe를 구현하기 위해 반드시 락을 사용해야 할까요? 그렇지 않다면, 어떤 다른 방법이 있을까요?
```
반드시 필요하지는 않습니다. CAS 기반의 락-프리 자료구조를 쓰거나, 애초에 상태를 공유하지 않도록
불변 객체나 스레드마다 독립된 데이터(Thread-Local Storage)를 사용하는 방법으로도 락 없이
Thread Safe를 달성할 수 있습니다.
```

**핵심 키워드** → Thread Safe = 동시 접근에도 항상 올바른 결과 보장, Race Condition(타이밍에 따라 결과 달라짐), 보장 방법(락 / CAS 원자적 연산 / 불변 객체·Thread-Local로 공유 상태 제거), Peterson's Algorithm(2프로세스 한정, 명령어 재정렬로 현대 CPU에서 보장 안 됨)

**막힌 부분 / 다시 볼 것** →

#### 5. Thread Pool, Monitor, Fork-Join에 대해 설명해 주세요.

`★★★` · `심화` · 원본 [운영체제 #13](../02-OPERATING_SYSTEM.md)

<details>
<summary><b>꼬리 질문 2개 (펼치기)</b></summary>

- Thread Pool을 사용한다고 가정하면, 어떤 기준으로 스레드의 수를 결정할 것인가요?
- 어떤 데이터를 정렬 하려고 합니다. 어떤 방식의 전략을 사용하는 것이 가장 안전하면서도 좋은 성능을 낼 수 있을까요?

</details>

**내 답변**

```
세 가지 모두 동시성을 더 안전하고 효율적으로 다루기 위한 상위 수준의 도구입니다. Thread Pool은
스레드를 미리 만들어두고 재사용해서 생성·소멸 비용을 줄이는 기법이고, Monitor는 락과 조건 변수를
캡슐화해 동기화 로직을 안전하게 감싸는 고수준 동기화 도구이며, Fork-Join은 작업을 재귀적으로
쪼갠 뒤 병렬로 처리하고 결과를 합치는 병렬 처리 모델입니다.
```

**꼬리 질문 답변**

- Thread Pool을 사용한다고 가정하면, 어떤 기준으로 스레드의 수를 결정할 것인가요?
```
작업의 성격에 따라 다르게 잡습니다. CPU 바운드 작업이라면 코어 수만큼(또는 코어 수+1)으로 맞춰
불필요한 컨텍스트 스위칭을 줄이고, I/O 바운드 작업이라면 대기 시간이 많으므로 코어 수보다 훨씬
많은 스레드를 두어 대기 중에도 다른 작업이 CPU를 쓸 수 있게 합니다.
```

- 어떤 데이터를 정렬 하려고 합니다. 어떤 방식의 전략을 사용하는 것이 가장 안전하면서도 좋은 성능을 낼 수 있을까요?
```
데이터 크기가 특정 임계값 이상일 때만 Fork-Join으로 배열을 재귀적으로 나눠 각 부분을 병렬로
정렬하고, 임계값 이하로 작아지면 순차 정렬로 전환한 뒤 병합하는 전략이 안전하면서도 효율적입니다.
병렬 처리 오버헤드가 작은 크기의 데이터에서는 오히려 손해이기 때문입니다.
```

**핵심 키워드** → Thread Pool(스레드 재사용, 생성·소멸 비용 절감), Monitor(락+조건 변수 캡슐화, 고수준 동기화), Fork-Join(재귀 분할+병렬 처리+병합), 스레드 수 결정(CPU 바운드→코어 수, I/O 바운드→코어 수보다 많이), 병렬 정렬 전략(임계값 이상은 Fork-Join, 이하는 순차 정렬로 전환)

#### 6. 동기화를 구현하기 위한 하드웨어적인 해결 방법에 대해 설명해 주세요.

`★★★` · `심화` · 원본 [운영체제 #20](../02-OPERATING_SYSTEM.md)

<details>
<summary><b>꼬리 질문 2개 (펼치기)</b></summary>

- volatile 키워드는 어떤 의미가 있나요?
- 싱글코어가 아니라 멀티코어라면, 어떻게 동기화가 이뤄질까요?

</details>

**내 답변**

```
대표적으로 Test-and-Set, Compare-and-Swap 같은 원자적 명령어를 CPU가 직접 제공해서
동기화를 구현합니다. 이 명령어들은 "값을 읽고 비교하고 바꾸는" 과정을 하드웨어가 하나의 쪼갤 수
없는 연산으로 처리해주기 때문에, 소프트웨어만으로는 막을 수 없는 중간 끼어들기를 원천 차단할 수
있습니다.
```

**꼬리 질문 답변**

- volatile 키워드는 어떤 의미가 있나요?
```
volatile은 컴파일러나 CPU가 그 변수에 대한 접근을 캐시나 레지스터에 최적화해 재정렬하지 못하게
하고, 항상 메인 메모리에서 읽고 쓰도록 강제하는 키워드입니다. 다만 가시성만 보장할 뿐 읽고-바꾸고-
쓰는 복합 연산의 원자성은 보장하지 않아서, 단독으로는 Thread Safe를 완전히 보장하지 못합니다.
```

- 싱글코어가 아니라 멀티코어라면, 어떻게 동기화가 이뤄질까요?
```
멀티코어에서는 각 코어가 자체 캐시를 갖기 때문에, CAS 같은 원자적 명령어가 캐시 일관성 프로토콜
(MESI 등)과 함께 동작해서 다른 코어의 캐시에 있는 값까지 무효화·동기화시킵니다. 그래서 한 코어가
값을 바꾸면 다른 코어도 그 변경을 즉시 인지하도록 하드웨어가 보장해줍니다.
```

**핵심 키워드** → 원자적 명령어(Test-and-Set, Compare-and-Swap)로 읽기-비교-변경을 한 번에 처리, volatile(가시성 보장, 원자성은 보장 안 함), 멀티코어는 캐시 일관성 프로토콜(MESI)과 결합해 원자적 명령어 보장

#### 7. 동기와 비동기, 블로킹과 논블로킹의 차이에 대해 설명해 주세요.

`★★★` · `필수` · 원본 [운영체제 #23](../02-OPERATING_SYSTEM.md)

<details>
<summary><b>꼬리 질문 3개 (펼치기)</b></summary>

- 그렇다면, 동기이면서 논블로킹이고, 비동기이면서 블로킹인 경우는 의미가 있다고 할 수 있나요?
- I/O 멀티플렉싱에 대해 설명해 주세요.
- 논블로킹 I/O를 수행한다고 하면, 그 결과를 어떻게 수신할 수 있나요?

</details>

**내 답변**

```
이 둘은 서로 다른 축의 개념입니다. 블로킹/논블로킹은 "호출한 함수가 결과를 받을 때까지 제어권을
계속 붙잡고 있는가"의 문제이고, 동기/비동기는 "작업 완료 여부를 호출자가 직접 확인하는가, 아니면
통보를 받는가"의 문제입니다. 서로 독립된 축이라 이 둘을 조합하면 네 가지 경우가 모두 나올 수
있습니다.
```

**꼬리 질문 답변**

- 그렇다면, 동기이면서 논블로킹이고, 비동기이면서 블로킹인 경우는 의미가 있다고 할 수 있나요?
```
둘 다 실제로 의미가 있는 조합입니다. 동기+논블로킹은 호출 즉시 제어권은 돌아오지만, 결과가
준비됐는지는 호출자가 직접 반복해서 확인(polling)해야 하는 방식이고, 비동기+블로킹은 콜백은
등록해두었지만 다른 이유로 호출자가 잠시 대기하게 되는, 드물지만 실제로 존재하는 조합입니다.
```

- I/O 멀티플렉싱에 대해 설명해 주세요.
```
I/O 멀티플렉싱은 하나의 스레드가 select, poll, epoll 같은 시스템 콜로 여러 개의 파일
디스크립터를 동시에 감시하다가, 그중 준비된 것이 생기면 그것만 처리하는 방식입니다. 소켓 수만큼
스레드를 늘리지 않고도 다수의 연결을 효율적으로 처리할 수 있어 대규모 동시 접속 서버에서 널리
쓰입니다.
```

- 논블로킹 I/O를 수행한다고 하면, 그 결과를 어떻게 수신할 수 있나요?
```
주로 세 가지 방식이 있습니다. 콜백 함수를 등록해서 완료 시 호출받거나, Future/Promise 객체를
반환받아 나중에 결과를 조회하거나, epoll 같은 이벤트 루프에 등록해두고 준비 완료 이벤트가 오면
그때 직접 읽어오는 방식입니다.
```

**핵심 키워드** → 블로킹/논블로킹 = 제어권 반환 시점, 동기/비동기 = 완료 통보 방식(호출자 확인 vs 통보받음), 서로 다른 축이라 4가지 조합 모두 존재, I/O 멀티플렉싱(select/poll/epoll, 스레드 하나로 다중 연결 감시), 논블로킹 결과 수신(콜백 / Future·Promise / 이벤트 루프)

**막힌 부분 / 다시 볼 것** →

#### 8. 가상화가 무엇이고, 이것이 가상머신과 어떠한 차이가 있는지 설명해 주세요.

`★★☆` · `필수` · 원본 [개발상식·기타 #1](../05-ETC.md)

<details>
<summary><b>꼬리 질문 3개 (펼치기)</b></summary>

- 그렇다면 Docker는 둘 중 어디에 속하나요? 왜 사람들이 Docker를 많이 채택할까요?
- 하나의 Host OS에서 돌아간다면 충분히 한 컨테이너가 다른 컨테이너에 간섭할 수 있는 위험이 있지 않을까요? 이를 어떻게 방어할 수 있을까요?
- Docker 위에 Docker를 올릴 순 없을까요?

</details>

**내 답변**

```
가상화는 물리적인 자원(CPU, 메모리, 디스크 등)을 논리적으로 추상화해서 여러 개의 독립된
환경처럼 나눠 쓰는 기술 전체를 가리키는 큰 개념입니다. 가상머신은 그 가상화를 하이퍼바이저가
하드웨어 수준까지 완전히 에뮬레이션해서, 각자 별도의 커널을 갖는 형태로 구현한 하나의 결과물입니다.
즉 가상머신은 가상화라는 개념의 여러 구현 방식 중 하나입니다.
```

**꼬리 질문 답변**

- 그렇다면 Docker는 둘 중 어디에 속하나요? 왜 사람들이 Docker를 많이 채택할까요?
```
Docker는 컨테이너 방식의 가상화에 속합니다. 하드웨어를 통째로 에뮬레이션하지 않고 호스트 OS의
커널을 그대로 공유하면서 프로세스 수준에서 격리하기 때문에, 가상머신보다 훨씬 가볍고 시작 속도가
빠릅니다. 배포 환경을 코드로 일관되게 재현하면서도 자원 오버헤드가 적다는 점 때문에 많이
채택됩니다.
```

- 하나의 Host OS에서 돌아간다면 충분히 한 컨테이너가 다른 컨테이너에 간섭할 수 있는 위험이 있지 않을까요? 이를 어떻게 방어할 수 있을까요?
```
같은 커널을 공유하기 때문에 격리 수준이 가상머신보다 약한 것은 맞습니다. 이를 방어하기 위해
리눅스 커널의 namespace로 프로세스·네트워크·파일시스템 시야를 컨테이너별로 분리하고, cgroups로
CPU·메모리 사용량에 한도를 걸어 한 컨테이너가 자원을 독점하지 못하도록 제한합니다.
```

- Docker 위에 Docker를 올릴 순 없을까요?
```
가능합니다. Docker-in-Docker(DinD)라는 이름으로, 컨테이너 내부에 별도의 Docker 데몬을 새로
띄워 중첩 실행할 수 있습니다. 다만 권한·격리 측면에서 복잡성이 커지기 때문에, 보통은 호스트의
Docker 소켓을 컨테이너에 마운트해서 공유하는 방식을 더 많이 사용합니다.
```

**핵심 키워드** → 가상화(자원의 논리적 추상화, 상위 개념) vs 가상머신(하이퍼바이저가 하드웨어까지 에뮬레이션, 구현 방식 중 하나), Docker = 컨테이너 가상화(커널 공유, 가볍고 빠름), 격리 방어(namespace로 시야 분리, cgroups로 자원 한도), Docker-in-Docker vs 소켓 마운트 방식

`★★☆` · `필수` · 원본 [개발상식·기타 #2](../05-ETC.md)

- 소스코드를 작성하고 나서, 실제 사용자에게 배포되기까지의 과정을 순서대로 설명해 주세요.
```
코드 작성 → 커밋/푸시 → 자동 빌드 → 테스트 → 아티팩트(이미지) 생성 → 스테이징 배포 → 검증 →
프로덕션 배포 순서로 진행됩니다. CI가 앞부분(빌드·테스트·이미지화)을, CD가 그 이후 배포 단계를
자동화합니다.
```

- 빌드와 배포는 어떻게 다른가요?
```
빌드는 소스 코드를 실행 가능한 형태(바이너리, 이미지 등)로 변환하는 과정이고, 배포는 그 결과물을
실제 서버 환경에 올려 사용자가 쓸 수 있게 만드는 과정입니다. 빌드가 배포의 전제 조건입니다.
```

- CI와 CD는 각각 무엇을 자동화하는 것인가요? CD의 Delivery와 Deployment는 어떤 차이가 있나요?
```
CI(지속적 통합)는 코드 변경마다 빌드와 테스트를 자동 실행해서 통합 문제를 빨리 발견하는 것을
자동화하고, CD는 그 이후 배포 과정을 자동화합니다. Continuous Delivery는 언제든 배포 가능한
상태까지만 자동으로 준비해두고 실제 배포는 수동 승인을 거치는 반면, Continuous Deployment는
승인 없이 프로덕션까지 완전 자동으로 배포합니다.
```

- 파이프라인의 어느 단계에 테스트를 넣는 것이 좋을까요? 그 이유는 무엇인가요?
```
빌드 직후, 배포 이전 단계에 넣는 것이 좋습니다. 문제를 최대한 빨리 발견해야(shift-left) 수정
비용이 적고, 잘못된 코드가 실제 배포 단계까지 흘러가는 것을 막을 수 있기 때문입니다.
```

- 무중단 배포는 어떻게 구현할 수 있을까요? (Rolling, Blue-Green, Canary)
```
Rolling은 여러 서버 인스턴스를 순차적으로 하나씩 교체해서 항상 일부는 서비스 중인 상태를
유지합니다. Blue-Green은 기존(Blue)과 동일한 새 환경(Green)을 통째로 띄운 뒤 트래픽을 한 번에
전환해서 즉시 롤백이 가능합니다. Canary는 새 버전에 트래픽 일부만 먼저 흘려보내 문제가 없는지
검증한 뒤 점진적으로 확대합니다.
```

- 배포한 버전에 장애가 발생했을 때, 롤백은 어떤 방식으로 준비해 둘 수 있을까요?
```
이전 버전의 이미지나 아티팩트를 항상 레지스트리에 버전 태그로 보관해두고, 배포 자동화 도구에서
한 번의 명령으로 직전 버전을 다시 배포할 수 있도록 구성해둡니다. Blue-Green이라면 트래픽을
이전 환경으로 즉시 되돌리기만 하면 되므로 롤백이 가장 빠릅니다.
```

- 빌드 결과물을 이미지로 만들어 배포하는 방식은, 서버에서 직접 빌드하는 방식과 비교해 어떤 장점이 있을까요?
```
이미지로 배포하면 빌드 환경과 실행 환경이 완전히 동일하게 고정되어 환경 차이로 인한 문제가
사라지고, 서버에서 매번 의존성을 설치하고 빌드할 필요가 없어 배포 속도도 훨씬 빠르고 일관적입니다.
```

**핵심 키워드** → CI(빌드·테스트 자동화, 통합 문제 조기 발견) vs CD(배포 자동화, Delivery=수동 승인 vs Deployment=완전 자동), 테스트는 빌드 직후·배포 이전(shift-left), 무중단 배포(Rolling·Blue-Green·Canary), 롤백(이전 이미지 태그 보관 + 즉시 전환), 이미지 기반 배포(환경 일관성 + 빌드 시간 단축)

#### [정렬 2/6] 병합 정렬

**구현 범위** — 재귀 분할 + `merge` 병합. 임시 배열을 매번 할당하지 않는 방법과, 병합 정렬이 안정 정렬인 이유

```java
class MergeSort {

    // 재귀 호출마다 배열을 새로 할당하지 않도록, 전체 크기의 임시 배열을 한 번만 만들어 재사용
    static void sort(int[] arr) {
        int[] temp = new int[arr.length];
        mergeSort(arr, temp, 0, arr.length - 1);
    }

    private static void mergeSort(int[] arr, int[] temp, int left, int right) {
        if (left >= right) return; // base case: 원소가 1개 이하면 이미 정렬된 상태

        int mid = left + (right - left) / 2;
        mergeSort(arr, temp, left, mid);
        mergeSort(arr, temp, mid + 1, right);
        merge(arr, temp, left, mid, right);
    }

    private static void merge(int[] arr, int[] temp, int left, int mid, int right) {
        int i = left, j = mid + 1, k = left;

        // 두 정렬된 구간을 앞에서부터 비교하며 temp에 순서대로 채움
        while (i <= mid && j <= right) {
            // 같을 때 왼쪽(i) 원소를 먼저 넣는 것이 안정 정렬을 만드는 핵심
            if (arr[i] <= arr[j]) {
                temp[k++] = arr[i++];
            } else {
                temp[k++] = arr[j++];
            }
        }
        while (i <= mid) temp[k++] = arr[i++];
        while (j <= right) temp[k++] = arr[j++];

        // 병합 결과를 원본 배열의 해당 구간에 다시 복사
        for (int x = left; x <= right; x++) {
            arr[x] = temp[x];
        }
    }
}
```

**임시 배열을 매번 할당하지 않는 방법** — `merge`를 호출할 때마다 `new int[]`로 구간 크기만큼 배열을 새로 만들면 재귀 호출 횟수만큼(O(n log n)번) 할당이 일어나 GC 부담이 커집니다. 위 구현처럼 최상위에서 전체 크기의 `temp` 배열을 딱 한 번만 만들어 모든 재귀 호출이 이를 공유해서 쓰면, 할당 횟수를 O(1)로 줄일 수 있습니다.

**병합 정렬이 안정 정렬인 이유** — `merge` 단계에서 두 값이 같을 때(`arr[i] <= arr[j]`) 항상 왼쪽 구간의 원소를 먼저 temp에 넣도록 비교 조건을 `<=`로 두었기 때문입니다. 왼쪽 구간은 원본 배열에서 항상 더 앞쪽에 있던 원소들이므로, 같은 값끼리는 원래 순서가 그대로 유지되어 안정성이 보장됩니다.

**시간복잡도** → O(n log n) (분할 log n단계 × 각 단계 병합 O(n))
**공간복잡도** → O(n) (재사용하는 임시 배열 1개, 재귀 호출 스택은 O(log n))

#### 12. 정렬된 두 LinkedList를 합쳐 하나의 정렬된 LinkedList로 만드는 코드를 작성해 보세요.

```java
class ListNode {
    int val;
    ListNode next;
    ListNode(int val) { this.val = val; }
}

class MergeTwoLists {

    static ListNode merge(ListNode l1, ListNode l2) {
        // dummy(더미) head를 두면 "첫 노드가 어느 쪽에서 올지" 분기 처리를 하지 않아도 됨
        ListNode dummy = new ListNode(0);
        ListNode tail = dummy;

        while (l1 != null && l2 != null) {
            if (l1.val <= l2.val) {
                tail.next = l1;
                l1 = l1.next;
            } else {
                tail.next = l2;
                l2 = l2.next;
            }
            tail = tail.next;
        }

        // 둘 중 하나가 먼저 끝나면, 남은 쪽은 이미 정렬되어 있으므로 그대로 이어붙이면 됨
        tail.next = (l1 != null) ? l1 : l2;

        return dummy.next;
    }
}
```

**풀이 설명**

두 리스트가 이미 각각 정렬되어 있다는 점을 이용해서, 새 노드를 만들지 않고 기존 노드의 포인터만
재배치하는 방식으로 풀었습니다. 두 리스트의 head를 각각 가리키는 포인터를 두고, 두 값을 비교해서
더 작은 쪽 노드를 결과 리스트의 꼬리에 이어 붙이고 그 리스트의 포인터만 한 칸 전진시키는 과정을
한쪽이 끝날 때까지 반복합니다. 분기 처리를 단순화하기 위해 실제 데이터를 담지 않는 dummy 노드를
head로 미리 만들어두고, 마지막에 `dummy.next`를 반환하는 방식을 사용했습니다. 두 리스트 중 하나가
먼저 소진되면, 남은 리스트는 이미 정렬되어 있으므로 나머지를 통째로 이어 붙이기만 하면 됩니다.

**시간복잡도** → O(N + M) (N, M은 각 리스트의 길이, 모든 노드를 정확히 한 번씩만 방문)
**공간복잡도** → O(1) (새 노드를 생성하지 않고 기존 노드의 포인터만 재사용, dummy 노드 1개만 추가)
