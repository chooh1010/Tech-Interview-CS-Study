#### 1. 캐시 메모리 및 메모리 계층성에 대해 설명해 주세요.

`★★☆` · `필수` · 원본 [운영체제 #14](../02-OPERATING_SYSTEM.md)

<details>
<summary><b>꼬리 질문 8개 (펼치기)</b></summary>

- 캐시 메모리는 어디에 위치해 있나요?
- L1, L2 캐시에 대해 설명해 주세요.
- 캐시에 올라오는 데이터는 어떻게 관리되나요?
- 캐시간의 동기화는 어떻게 이루어지나요?
- 캐시 메모리의 Mapping 방식에 대해 설명해 주세요.
- 캐시의 지역성에 대해 설명해 주세요.
- 캐시의 지역성을 기반으로, 이차원 배열을 가로/세로로 탐색했을 때의 성능 차이에 대해 설명해 주세요.
- 캐시의 공간 지역성은 어떻게 구현될 수 있을까요? (힌트: 캐시는 어떤 단위로 저장되고 관리될까요?)

</details>

**내 답변**

```
메모리 계층성(Memory Hierarchy)은 레지스터 → 캐시(L1/L2/L3) → 주기억장치(RAM) → 보조기억장치
(SSD/HDD) 순으로, 위로 갈수록 빠르지만 비싸고 용량이 작으며, 아래로 갈수록 느리지만 저렴하고
용량이 큰 계층 구조입니다.

캐시 메모리는 CPU와 RAM 사이의 속도 차이를 완화하기 위해 그 중간에 두는 작고 빠른 저장 장치입니다.
프로그램이 최근에 접근한 데이터나 그 주변 데이터를 다시 쓸 가능성이 높다는 지역성(Locality)
원리를 이용해서, 자주 쓰는 데이터를 캐시에 올려두면 매번 느린 RAM까지 가지 않고도 평균 접근
속도를 크게 끌어올릴 수 있습니다.
```

**꼬리 질문 답변**

- 캐시 메모리는 어디에 위치해 있나요?
```
CPU 레지스터와 주기억장치(RAM) 사이에 위치합니다. L1·L2는 보통 CPU 코어 내부(또는 코어와 매우
가까운 위치)에 코어마다 개별적으로 있고, L3는 여러 코어가 공유하는 형태로 CPU 칩 안에 위치하는
것이 일반적입니다.
```

- L1, L2 캐시에 대해 설명해 주세요.
```
L1 캐시는 코어에 가장 가깝고 가장 빠르지만 용량이 가장 작은 캐시로, 보통 명령어용(I-Cache)과
데이터용(D-Cache)으로 나뉘어 있습니다. L2 캐시는 L1보다 용량은 크지만 속도는 조금 느리고, 코어마다
개별로 두거나 두 코어가 함께 공유하는 식으로 구성됩니다. 그 아래 L3는 보통 모든 코어가 함께
공유하는, L1·L2보다 더 크고 느린 마지막 단계의 캐시입니다.
```

- 캐시에 올라오는 데이터는 어떻게 관리되나요?
```
캐시는 데이터를 캐시 라인(Cache Line)이라는 고정 크기 블록 단위로 저장하고, 각 라인마다 그
데이터가 실제 메모리의 어느 주소에서 왔는지를 나타내는 태그(tag)와, 유효한 데이터인지를 나타내는
valid 비트, 쓰기 작업이 있었는지를 나타내는 dirty 비트를 함께 관리합니다. 캐시가 가득 차서 새
데이터를 들여와야 할 때는 LRU 같은 교체 정책으로 기존 라인 중 하나를 내쫓고, 쓰기 작업은 즉시
메모리에 반영하는 Write-Through 또는 일단 캐시에만 반영하고 나중에 한꺼번에 내려보내는
Write-Back 방식으로 처리합니다.
```

- 캐시간의 동기화는 어떻게 이루어지나요?
```
멀티코어 환경에서는 각 코어가 자신만의 캐시를 갖고 있어서, 같은 메모리 주소의 값이 여러 캐시에
서로 다르게 존재할 수 있습니다. 이를 막기 위해 MESI(Modified-Exclusive-Shared-Invalid) 같은
캐시 일관성 프로토콜을 사용해서, 한 코어가 값을 수정하면 다른 코어가 들고 있는 같은 주소의 캐시
라인을 무효화(Invalidate)하거나 갱신해서, 모든 코어가 항상 일관된 값을 보게 만듭니다.
```

- 캐시 메모리의 Mapping 방식에 대해 설명해 주세요.
```
메모리 블록을 캐시의 어느 위치에 저장할지 정하는 방식으로 크게 세 가지가 있습니다. Direct
Mapped는 각 메모리 블록이 캐시의 정확히 하나의 위치에만 매핑되는 방식으로 구현이 단순하지만
충돌(같은 위치를 두고 다투는 상황)이 잦습니다. Fully Associative는 어떤 블록이든 캐시의 어느
위치에나 저장될 수 있어 충돌이 거의 없지만, 저장된 위치를 찾기 위해 모든 라인을 비교해야 해서
하드웨어 비용이 큽니다. Set Associative는 두 방식을 절충해서, 캐시를 여러 세트로 나누고 각 블록은
정해진 하나의 세트 안에서는 여러 위치 중 어디에나 저장될 수 있게 합니다. 실제로는 이 절충안이
가장 널리 쓰입니다.
```

- 캐시의 지역성에 대해 설명해 주세요.
```
지역성은 프로그램이 메모리를 접근하는 패턴에 일정한 규칙성이 있다는 경험적 원리로, 시간적
지역성(Temporal Locality)과 공간적 지역성(Spatial Locality)으로 나뉩니다. 시간적 지역성은
최근에 접근한 데이터가 가까운 미래에 다시 접근될 가능성이 높다는 것이고, 공간적 지역성은 어떤
주소에 접근하면 그 주변 주소도 곧 접근될 가능성이 높다는 것입니다. 캐시는 이 두 지역성을 전제로
동작하기 때문에, 실제 프로그램들이 이 패턴을 따를 때 캐시 적중률이 높아집니다.
```

- 캐시의 지역성을 기반으로, 이차원 배열을 가로/세로로 탐색했을 때의 성능 차이에 대해 설명해 주세요.
```
대부분의 언어는 2차원 배열을 행 우선(Row-major)으로, 즉 메모리상에 한 행의 원소들이 연속되게
저장합니다. 그래서 행 방향(가로)으로 순차 접근하면, 한 번 캐시 라인을 불러올 때 이후에 접근할
원소들이 이미 같은 라인에 함께 들어와 있어서 공간 지역성을 그대로 활용할 수 있어 캐시 적중률이
높습니다.

반면 열 방향(세로)으로 접근하면, 한 번 접근할 때마다 다음 원소가 메모리상 멀리 떨어진 다른 행에
있어서 매번 새로운 캐시 라인을 불러와야 할 가능성이 높습니다. 그래서 같은 연산량이라도 세로
탐색이 가로 탐색보다 캐시 미스가 훨씬 잦아 실제 실행 속도가 눈에 띄게 느려질 수 있습니다.
```

- 캐시의 공간 지역성은 어떻게 구현될 수 있을까요? (힌트: 캐시는 어떤 단위로 저장되고 관리될까요?)
```
캐시가 데이터를 1바이트씩 개별로 저장하는 게 아니라, 캐시 라인(보통 64바이트 등 고정 크기 블록)
단위로 한 번에 가져오기 때문입니다. 특정 주소에 접근해서 캐시 미스가 나면, 그 주소 하나만
가져오는 게 아니라 그 주소를 포함한 블록 전체를 한 번에 메모리에서 읽어 캐시에 올립니다. 그래서
방금 접근한 주소 바로 옆에 있는 데이터는 이미 캐시에 함께 올라와 있게 되고, 곧이어 그 주변
데이터에 접근하면 추가로 메모리에 가지 않고도 캐시에서 바로 찾을 수 있습니다. 이 "블록 단위로
가져온다"는 설계 자체가 공간 지역성을 하드웨어적으로 구현하는 방법입니다.
```

**핵심 키워드** → 메모리 계층(레지스터>캐시>RAM>보조기억장치, 속도↕비용·용량), 캐시 위치(L1/L2 코어별, L3 공유), 캐시 라인(tag·valid·dirty 비트, Write-Through/Write-Back), MESI(캐시 일관성 프로토콜), Mapping 방식(Direct Mapped·Fully Associative·Set Associative), 지역성(시간적·공간적), 2차원 배열 행 우선 저장 → 가로 탐색이 캐시 친화적, 공간 지역성 구현 = 캐시 라인 단위 블록 전송

#### 2. 메모리의 연속할당 방식 세 가지를 설명해주세요. (first-fit, best-fit, worst-fit)

`★☆☆` · `심화` · 원본 [운영체제 #15](../02-OPERATING_SYSTEM.md)

<details>
<summary><b>꼬리 질문 2개 (펼치기)</b></summary>

- worst-fit 은 언제 사용할 수 있을까요?
- 성능이 가장 좋은 알고리즘은 무엇일까요?

</details>

**내 답변**

```
세 방식 모두 메모리에 비어있는 여러 개의 구멍(hole) 중 어디에 새 프로세스를 할당할지를 정하는
전략입니다.

First-fit은 처음부터 순서대로 훑다가 요청한 크기보다 큰 구멍을 처음 발견하는 즉시 그 자리에
할당하는 방식으로, 탐색이 빨리 끝날 수 있습니다. Best-fit은 모든 구멍을 다 확인해서 요청 크기에
가장 가깝게 맞는(낭비가 가장 적은) 구멍을 골라 할당하는 방식으로, 공간 낭비는 적지만 전체를
탐색해야 해서 느리고 매우 작은 쪼가리(fragment)를 많이 남깁니다. Worst-fit은 반대로 가장 큰
구멍을 골라 할당하는 방식으로, 남는 공간을 최대한 크게 남겨서 이후에도 쓸모 있게 하려는 의도지만
결국 큰 구멍들을 빠르게 소진시킨다는 단점이 있습니다.
```

**꼬리 질문 답변**

- worst-fit 은 언제 사용할 수 있을까요?
```
작게 쪼개진, 재사용하기 어려운 아주 작은 단편(fragment)이 남는 것을 피하고 싶을 때 쓸 수
있습니다. 가장 큰 구멍에서 떼어 쓰면 남는 공간도 어느 정도 크기를 유지해서 당장은 다른 요청에도
쓸모 있는 크기로 남길 수 있기 때문입니다. 다만 이런 장점이 실제로는 오래가지 못해서, 실무에서는
잘 채택되지 않는 전략입니다.
```

- 성능이 가장 좋은 알고리즘은 무엇일까요?
```
정답이 하나로 정해져 있지는 않지만, 실무·시뮬레이션 상으로는 First-fit이 가장 균형 잡힌
선택으로 꼽히는 경우가 많습니다. Best-fit은 공간 낭비를 줄이는 데는 이론적으로 유리하지만 매번
전체를 탐색해야 해서 속도가 느리고, 아주 작은 쓸모없는 단편을 오히려 더 많이 만드는 경향이
있습니다. Worst-fit은 대체로 가장 성능이 나쁜 것으로 알려져 있습니다. 그래서 탐색 속도와 단편화
정도를 종합하면 First-fit이 가장 실용적인 선택으로 평가받는 경우가 많습니다.
```

**핵심 키워드** → First-fit(처음 맞는 곳, 빠른 탐색) vs Best-fit(가장 딱 맞는 곳, 느리지만 낭비 적음 → 작은 단편 多) vs Worst-fit(가장 큰 곳, 큰 구멍 빨리 소진), worst-fit은 작은 단편 방지 목적이나 실무에서 잘 안 쓰임, 종합적으로는 First-fit이 실용적

**막힌 부분 / 다시 볼 것** →

#### 3. Thrashing 이란 무엇인가요?

`★★☆` · `필수` · 원본 [운영체제 #16](../02-OPERATING_SYSTEM.md)

<details>
<summary><b>꼬리 질문 1개 (펼치기)</b></summary>

- Thrashing 발생 시, 어떻게 완화할 수 있을까요?

</details>

**내 답변**

```
Thrashing은 프로세스에게 할당된 프레임 수가 그 프로세스가 당장 필요로 하는 작업 집합(working
set)보다 부족해서, 페이지 폴트가 끊임없이 발생하고 CPU가 실제 연산보다 페이지를 디스크에서
읽고 쓰는 데에 대부분의 시간을 쓰는 현상입니다. 다중 프로그래밍 정도를 과도하게 높여서 전체
프로세스가 요구하는 메모리가 실제 물리 메모리를 넘어설 때 주로 발생하고, CPU 이용률이 오히려
급격히 떨어지는 역설적인 결과로 나타납니다.
```

**꼬리 질문 답변**

- Thrashing 발생 시, 어떻게 완화할 수 있을까요?
```
핵심은 다중 프로그래밍 정도를 낮춰서 각 프로세스가 필요한 만큼의 프레임을 확보하게 해주는
것입니다. 중기 스케줄러가 일부 프로세스를 스왑아웃시켜 메모리에 올라온 프로세스 수를 줄이거나,
Working Set Model을 적용해서 각 프로세스가 최근에 실제로 사용한 페이지 집합만큼의 프레임을
보장해주는 방법을 씁니다. 또한 Page-Fault Frequency(PFF) 알고리즘처럼 프로세스의 페이지 폴트
발생률을 모니터링해서, 폴트율이 너무 높으면 프레임을 더 할당하고 너무 낮으면 다른 프로세스에게
나눠주는 방식으로 동적으로 조정할 수도 있습니다.
```

**핵심 키워드** → Thrashing = 프레임 부족으로 페이지 폴트가 끊이지 않아 CPU 이용률이 급락하는 현상, 원인 = 과도한 다중 프로그래밍 정도, 완화(다중 프로그래밍 정도 낮추기, Working Set Model, Page-Fault Frequency로 동적 프레임 조정)

#### 4. 가상 메모리란 무엇인가요?

`★★☆` · `필수` · 원본 [운영체제 #17](../02-OPERATING_SYSTEM.md)

<details>
<summary><b>꼬리 질문 5개 (펼치기)</b></summary>

- 가상 메모리가 가능한 이유가 무엇일까요?
- Page Fault가 발생했을 때, 어떻게 처리하는지 설명해 주세요.
- 페이지 크기에 대한 Trade-Off를 설명해 주세요.
- 페이지 크기가 커지면, 페이지 폴트가 더 많이 발생한다고 할 수 있나요?
- 세그멘테이션 방식을 사용하고 있다면, 가상 메모리를 사용할 수 없을까요?

</details>

**내 답변**

```
가상 메모리는 각 프로세스에게 실제 물리 메모리 크기와 무관하게, 자신만의 거대하고 연속된 독립된
주소 공간을 쓰는 것처럼 보이게 해주는 추상화 기법입니다. 실제로는 그 주소 공간의 일부만 물리
메모리에 적재되어 있고 나머지는 디스크에 있다가 필요할 때 적재(Demand Paging)되며, 페이지
테이블을 통해 가상 주소를 물리 주소로 변환합니다. 이 덕분에 물리 메모리보다 큰 프로그램도 실행할
수 있고, 프로세스 간 메모리 공간이 완전히 분리되어 보호와 격리도 함께 얻을 수 있습니다.
```

**꼬리 질문 답변**

- 가상 메모리가 가능한 이유가 무엇일까요?
```
프로그램이 실행되는 동안 실제로 한 시점에 참조하는 메모리는 전체 주소 공간의 일부분에 집중되어
있다는 지역성(Locality of Reference) 덕분입니다. 그래서 전체 프로그램을 한꺼번에 메모리에 올릴
필요 없이, 당장 필요한 일부 페이지만 올려두고 나머지는 디스크에 남겨둬도 대부분의 실행 흐름에
문제가 없습니다. 이 가정이 성립하기 때문에 실제 물리 메모리보다 훨씬 큰 가상 주소 공간을 다룰 수
있는 것입니다.
```

- Page Fault가 발생했을 때, 어떻게 처리하는지 설명해 주세요.
```
먼저 하드웨어(MMU)가 페이지 테이블에서 해당 가상 주소의 valid 비트가 꺼져 있는 것을 감지하면
트랩을 발생시켜 커널에게 제어를 넘깁니다. 커널은 이 주소가 실제로 유효한 접근인지 확인하고(잘못된
접근이면 프로세스를 종료), 유효하다면 빈 프레임을 찾습니다. 빈 프레임이 없으면 교체 알고리즘으로
기존 페이지 하나를 디스크로 내보낸(필요하면 dirty 페이지는 먼저 디스크에 씀) 뒤, 요청된 페이지를
디스크에서 그 프레임으로 읽어 들입니다. 마지막으로 페이지 테이블을 갱신해 그 가상 페이지가 이
프레임에 있다고 표시하고, 폴트가 발생했던 명령어부터 다시 실행합니다.
```

- 페이지 크기에 대한 Trade-Off를 설명해 주세요.
```
페이지 크기를 크게 하면, 같은 주소 공간을 나타내는 데 필요한 페이지 수가 줄어서 페이지 테이블
크기가 작아지고 TLB도 더 넓은 주소 범위를 커버할 수 있어 TLB 미스가 줄어듭니다. 다만 프로세스가
실제로 쓰는 양보다 더 큰 단위로 메모리를 할당받게 되어 내부 단편화가 커지고, 한 번의 페이지 폴트마다
디스크에서 읽어와야 하는 양도 늘어나 I/O 비용이 커집니다.

페이지 크기를 작게 하면 내부 단편화는 줄지만, 같은 공간을 표현하는 데 필요한 페이지 수와 페이지
테이블 엔트리 수가 늘어나 테이블 관리 오버헤드와 TLB 미스 가능성이 커집니다. 그래서 두 요소
사이에서 적절한 크기(보통 4KB 전후, 필요에 따라 Huge Page 같은 더 큰 크기도 병행)를 선택하는
트레이드오프가 존재합니다.
```

- 페이지 크기가 커지면, 페이지 폴트가 더 많이 발생한다고 할 수 있나요?
```
일반적으로는 오히려 반대로, 페이지 폴트 발생 횟수가 줄어드는 경향이 있습니다. 페이지가 커지면
한 번의 폴트로 더 많은 양의 데이터를 한꺼번에 가져오기 때문에, 지역성이 있는 접근 패턴에서는
주변 데이터까지 이미 적재되어 있어 추가 폴트가 덜 발생합니다.

다만 공짜는 아닙니다. 폴트 한 번에 가져오는 데이터 양이 늘어난 만큼 디스크 I/O 시간이 길어지고,
실제로 쓰이지 않는 데이터까지 함께 적재되는 내부 단편화·낭비가 커집니다. 그래서 "폴트 횟수"는
줄어드는 경향이 있지만, "폴트 한 번의 비용"은 커진다고 정리할 수 있습니다.
```

- 세그멘테이션 방식을 사용하고 있다면, 가상 메모리를 사용할 수 없을까요?
```
사용할 수 있습니다. 세그멘테이션 자체도 각 세그먼트를 필요할 때만 메모리에 올리는 방식으로
가상 메모리를 구현할 수 있고, 더 나아가 세그멘테이션과 페이징을 결합한 세그먼트별 페이징
(Paged Segmentation) 방식도 가능합니다. 이 경우 주소 공간을 논리적인 세그먼트로 먼저 나누고,
각 세그먼트 내부를 다시 고정 크기 페이지로 나눠서, 세그멘테이션의 논리적 보호·공유 장점과
페이징의 외부 단편화 해소 장점을 함께 가져가려 한 것입니다. 실제로 초기 x86 아키텍처가 이런
방식을 채택했던 적이 있습니다.
```

**핵심 키워드** → 가상 메모리 = 프로세스별 독립된 큰 주소 공간 추상화(Demand Paging), 가능한 이유 = 지역성(Locality of Reference), Page Fault 처리(트랩 → 유효성 확인 → 빈 프레임 확보/교체 → 디스크에서 적재 → 페이지 테이블 갱신 → 재실행), 페이지 크기 트레이드오프(큰 페이지: 테이블·TLB 미스 ↓ but 내부 단편화·I/O 비용 ↑), 큰 페이지는 폴트 "횟수"는 줄고 폴트 "비용"은 커짐, 세그먼트별 페이징(Paged Segmentation)으로 세그멘테이션+가상 메모리 결합 가능

**막힌 부분 / 다시 볼 것** →

#### 5. 세그멘테이션과 페이징의 차이점은 무엇인가요?

`★★☆` · `필수` · 원본 [운영체제 #18](../02-OPERATING_SYSTEM.md)

<details>
<summary><b>꼬리 질문 7개 (펼치기)</b></summary>

- 페이지와 프레임의 차이에 대해 설명해 주세요.
- 내부 단편화와, 외부 단편화에 대해 설명해 주세요.
- 페이지에서 실제 주소를 어떻게 가져올 수 있는지 설명해 주세요.
- 어떤 주소공간이 있을 때, 이 공간이 수정 가능한지 확인할 수 있는 방법이 있나요?
- 32비트에서, 페이지의 크기가 1kb 이라면 페이지 테이블의 최대 크기는 몇 개일까요?
- 32비트 운영체제는 램을 최대 4G 까지 사용할 수 있습니다. 이 이유를 페이징과 연관 지어서 설명해 주세요.
- C/C++ 개발을 하게 되면 Segmentation Fault 라는 에러를 접할 수 있을텐데, 이 에러는 세그멘테이션/페이징과 어떤 관계가 있을까요?

</details>

**내 답변**

```
가장 큰 차이는 "나누는 단위를 프로그램의 논리적 구조에 맞출 것인가, 고정된 크기로 기계적으로
나눌 것인가"입니다. 세그멘테이션은 코드, 데이터, 스택처럼 프로그램이 실제로 쓰는 논리적 단위
(세그먼트)대로 가변 크기로 주소 공간을 나눠서, 사람이 이해하는 구조와 자연스럽게 맞고 세그먼트
단위의 보호·공유가 쉽습니다. 다만 세그먼트 크기가 제각각이라 메모리에 쓸 수 없는 작은 구멍들이
생기는 외부 단편화가 발생합니다.

페이징은 논리적 구조와 무관하게 고정된 크기로 주소 공간을 나눠서, 외부 단편화 문제를 완전히
없앨 수 있습니다. 다만 프로세스가 쓰는 양이 페이지 크기에 딱 맞지 않으면 마지막 페이지의 남는
공간이 낭비되는 내부 단편화가 생기고, 논리적 구조와 메모리 단위가 일치하지 않아 세그멘테이션만큼
직관적인 보호 단위를 제공하기는 어렵습니다.
```

**꼬리 질문 답변**

- 페이지와 프레임의 차이에 대해 설명해 주세요.
```
페이지(Page)는 프로세스의 가상(논리) 주소 공간을 나누는 고정 크기 단위이고, 프레임(Frame)은
물리 메모리(RAM)를 나누는 같은 크기의 단위입니다. 페이지는 "어디에 담길 내용"의 단위이고
프레임은 "실제로 담기는 그릇"의 단위라고 볼 수 있고, 페이지 테이블이 어떤 페이지가 어떤 프레임에
적재되어 있는지를 매핑해줍니다.
```

- 내부 단편화와, 외부 단편화에 대해 설명해 주세요.
```
내부 단편화(Internal Fragmentation)는 할당해준 공간이 실제로 필요한 양보다 커서, 그 할당된
블록 내부에 쓰이지 않고 낭비되는 공간이 생기는 것입니다. 페이징에서 마지막 페이지가 꽉 채워지지
않는 경우가 대표적입니다.

외부 단편화(External Fragmentation)는 전체적으로는 충분한 빈 공간이 있지만, 그 공간이 여러
개의 작은 조각으로 흩어져 있어서 하나의 연속된 큰 요청을 만족시킬 수 없는 상태를 말합니다.
세그멘테이션이나 연속 할당 방식에서 할당·해제가 반복되며 생기는 대표적인 문제입니다.
```

- 페이지에서 실제 주소를 어떻게 가져올 수 있는지 설명해 주세요.
```
가상 주소를 페이지 번호(Page Number)와 페이지 내 오프셋(Offset)으로 나눕니다. 페이지 번호는
페이지 테이블의 인덱스로 사용되어 그에 해당하는 프레임 번호(Frame Number)를 찾아내고, 오프셋은
그 프레임 안에서 몇 번째 바이트인지를 그대로 나타냅니다. 최종 물리 주소는 이 프레임 번호와
오프셋을 이어 붙여서 계산합니다(물리 주소 = 프레임 번호 × 페이지 크기 + 오프셋).
```

- 어떤 주소공간이 있을 때, 이 공간이 수정 가능한지 확인할 수 있는 방법이 있나요?
```
페이지 테이블 엔트리(PTE)에는 주소 변환 정보 외에도 보호 비트(읽기/쓰기/실행 권한)와 유효(valid)
비트가 함께 저장되어 있습니다. 이 엔트리의 쓰기 권한 비트를 확인하면 그 페이지가 쓰기 가능한지
알 수 있고, 만약 쓰기 금지로 설정된 페이지(예: 코드 영역)에 쓰기를 시도하면 MMU가 이를 감지해
보호 오류(폴트)를 발생시켜 커널에게 알립니다.
```

- 32비트에서, 페이지의 크기가 1kb 이라면 페이지 테이블의 최대 크기는 몇 개일까요?
```
32비트 주소 공간의 전체 크기는 2^32바이트이고, 페이지 크기가 1KB(2^10바이트)이므로, 전체 주소
공간을 커버하려면 2^32 / 2^10 = 2^22, 즉 4,194,304개의 페이지 테이블 엔트리가 필요합니다.
```

- 32비트 운영체제는 램을 최대 4G 까지 사용할 수 있습니다. 이 이유를 페이징과 연관 지어서 설명해 주세요.
```
페이징을 쓰더라도 가상 주소 자체를 표현하는 레지스터와 포인터의 폭이 32비트라는 사실은 변하지
않습니다. 32비트로 표현 가능한 주소의 개수는 2^32개뿐이라서, 각 프로세스가 가리킬 수 있는 가상
주소 공간의 한계가 이미 4GB로 정해져 있습니다. 페이징은 이 가상 주소 공간을 물리 프레임에 유연하게
매핑해줄 뿐이지, 주소를 표현하는 비트 수 자체의 한계를 늘려주지는 않기 때문에, 결국 프로세스가
다룰 수 있는 주소 공간은 32비트 한계인 4GB를 넘어설 수 없습니다.
```

- C/C++ 개발을 하게 되면 Segmentation Fault 라는 에러를 접할 수 있을텐데, 이 에러는 세그멘테이션/페이징과 어떤 관계가 있을까요?
```
이름은 과거 세그멘테이션 기반 보호 시스템에서 유래했지만, 현대의 페이징 기반 시스템에서도 이
이름이 그대로 쓰이고 있습니다. 실제 동작은 페이징 수준에서 이루어집니다. 프로그램이 유효하지
않은 가상 주소(매핑되지 않은 페이지, 혹은 읽기/쓰기 권한이 없는 페이지)에 접근하면, MMU가 페이지
테이블을 확인하다가 valid 비트가 꺼져 있거나 보호 비트에 위반되는 것을 감지해 폴트를 일으킵니다.
이 폴트가 정상적인 Demand Paging용 폴트가 아니라 "원천적으로 잘못된 접근"이라고 커널이 판단하면,
프로세스에게 SIGSEGV 시그널을 보내 강제 종료시키는데, 이것이 바로 Segmentation Fault입니다. 즉
이름은 세그멘테이션에서 왔지만, 실제 감지 메커니즘은 페이지 단위의 보호 검사입니다.
```

**핵심 키워드** → 세그멘테이션(논리적·가변 크기, 외부 단편화) vs 페이징(고정 크기, 내부 단편화), 페이지(가상 주소 단위) vs 프레임(물리 주소 단위), 가상 주소 = 페이지 번호+오프셋 → 페이지 테이블로 프레임 번호 조회, PTE의 보호 비트(읽기/쓰기/실행, valid), 32비트 2^32/2^10=2^22 페이지 테이블 엔트리, 4GB 한계는 포인터 비트 폭 자체의 한계(페이징과 무관), Segmentation Fault = 이름은 세그멘테이션 유래, 실제는 페이지 단위 보호 검사 위반 → SIGSEGV

#### 6. TLB는 무엇인가요?

`★★☆` · `심화` · 원본 [운영체제 #19](../02-OPERATING_SYSTEM.md)

<details>
<summary><b>꼬리 질문 5개 (펼치기)</b></summary>

- TLB를 쓰면 왜 빨라지나요?
- MMU가 무엇인가요?
- TLB와 MMU는 어디에 위치해 있나요?
- 코어가 여러개라면, TLB는 어떻게 동기화 할 수 있을까요?
- TLB 관점에서, Context Switching 발생 시 어떤 변화가 발생하는지 설명해 주세요.

</details>

**내 답변**

```
TLB(Translation Lookaside Buffer)는 최근에 사용한 가상 주소 → 물리 주소(페이지 → 프레임)
변환 결과를 캐싱해두는 작고 빠른 전용 캐시입니다. 페이지 테이블은 보통 메모리(RAM)에 있어서
매번 조회하려면 추가 메모리 접근이 필요한데, TLB에 변환 결과가 캐싱되어 있으면 이 메모리 접근
없이 즉시 물리 주소를 얻을 수 있어 주소 변환 속도를 크게 높여줍니다.
```

**꼬리 질문 답변**

- TLB를 쓰면 왜 빨라지나요?
```
페이지 테이블은 메모리에 있고, 특히 멀티레벨 페이지 테이블 구조에서는 하나의 주소를 변환하는 데
여러 번의 메모리 접근이 필요할 수 있습니다. TLB에 해당 변환 결과가 캐싱되어 있다면(TLB Hit),
이 여러 번의 메모리 접근 없이 거의 한 번의 조회(캐시 접근과 비슷한 속도)만으로 물리 주소를 바로
얻을 수 있기 때문에 빨라집니다. TLB Miss가 나야만 실제 페이지 테이블을 메모리에서 조회하는
무거운 작업을 하게 됩니다.
```

- MMU가 무엇인가요?
```
MMU(Memory Management Unit)는 CPU가 메모리에 접근할 때마다 가상 주소를 물리 주소로 변환하고,
그 접근이 권한에 맞는지 검사하는 하드웨어 장치입니다. TLB를 먼저 확인해서 캐싱된 변환이 있으면
바로 쓰고, 없으면 페이지 테이블을 직접 조회(Page Table Walk)해서 변환을 수행하며, 유효하지 않은
접근이면 CPU에 트랩(페이지 폴트)을 발생시켜 커널에게 처리를 넘깁니다.
```

- TLB와 MMU는 어디에 위치해 있나요?
```
둘 다 CPU 칩 내부에 위치합니다. MMU는 CPU 코어의 메모리 접근 파이프라인에 포함되어 있고, TLB는
그 MMU 안(또는 바로 옆)에 있는 작은 전용 캐시로, L1 캐시에 접근하기 전 단계에서 주소 변환을
수행하도록 위치해 있습니다.
```

- 코어가 여러개라면, TLB는 어떻게 동기화 할 수 있을까요?
```
각 코어는 보통 자신만의 TLB를 독립적으로 갖고 있습니다. 그런데 한 코어에서 페이지 테이블 엔트리를
변경(예: 페이지 매핑 해제, 권한 변경)하면, 다른 코어의 TLB에는 여전히 오래된 변환 정보가 남아있을
수 있습니다. 이를 해결하기 위해 TLB Shootdown이라는 기법을 사용하는데, 변경을 수행한 코어가
다른 모든 코어에게 인터럽트를 보내서 해당 TLB 엔트리를 무효화하도록 강제합니다.
```

- TLB 관점에서, Context Switching 발생 시 어떤 변화가 발생하는지 설명해 주세요.
```
TLB에 캐싱된 변환은 특정 프로세스의 주소 공간을 기준으로 만들어진 것이기 때문에, 다른 프로세스로
컨텍스트 스위칭이 일어나면 기존 TLB 엔트리가 더 이상 유효하지 않습니다. 가장 단순한 방식은
컨텍스트 스위칭마다 TLB를 완전히 비우는(flush) 것이지만, 이렇게 하면 전환 직후 TLB Miss가
잦아져 성능이 떨어집니다. 그래서 많은 현대 CPU는 각 TLB 엔트리에 ASID(Address Space
Identifier) 같은 프로세스 식별 태그를 함께 저장해서, 전체를 비우지 않고도 "이 엔트리는 어느
프로세스의 것인지"를 구분해 다른 프로세스로 전환해도 기존 엔트리를 무효화하지 않고 유지할 수
있게 최적화합니다.
```

**핵심 키워드** → TLB = 가상→물리 주소 변환 결과를 캐싱하는 전용 캐시, TLB Hit는 메모리 접근 없이 즉시 변환(페이지 테이블 직접 조회보다 빠름), MMU(주소 변환+권한 검사 수행하는 하드웨어, TLB 먼저 확인 후 Page Table Walk), TLB/MMU는 CPU 칩 내부(L1 캐시 이전 단계), 멀티코어에서 TLB Shootdown(인터럽트로 다른 코어 TLB 무효화), Context Switching 시 TLB flush 또는 ASID 태깅으로 선택적 무효화

**막힌 부분 / 다시 볼 것** →

#### 7. 페이지 교체 알고리즘에 대해 설명해 주세요.

`★★☆` · `필수` · 원본 [운영체제 #21](../02-OPERATING_SYSTEM.md)

<details>
<summary><b>꼬리 질문 3개 (펼치기)</b></summary>

- LRU 알고리즘은 어떤 특성을 이용한 알고리즘이라고 할 수 있을까요?
- LRU 알고리즘을 구현한다면, 어떻게 구현할 수 있을까요?
- LRU 알고리즘의 단점을 설명해 주세요. 이를 해결할 수 있는 대안에 대해서도 설명해 주세요.

</details>

**내 답변**

```
페이지 교체 알고리즘은 빈 프레임이 없을 때, 새 페이지를 적재하기 위해 기존에 적재된 페이지 중
어떤 것을 내쫓을지 정하는 정책입니다. FIFO는 가장 먼저 들어온 페이지를 내쫓고, Optimal(이론상
최적)은 앞으로 가장 오랫동안 쓰이지 않을 페이지를 내쫓아 폴트를 최소화하지만 미래를 알아야 해서
실제로는 구현할 수 없는 이상적인 기준입니다. LRU는 가장 오랫동안 사용되지 않은 페이지를 내쫓아
Optimal을 실용적으로 근사하고, Clock(Second-Chance) 알고리즘은 참조 비트를 이용해 LRU를
적은 오버헤드로 근사합니다.
```

**꼬리 질문 답변**

- LRU 알고리즘은 어떤 특성을 이용한 알고리즘이라고 할 수 있을까요?
```
시간적 지역성(Temporal Locality), 즉 "최근에 사용된 데이터는 가까운 미래에도 다시 사용될
가능성이 높다"는 특성을 이용합니다. 이 가정을 거꾸로 적용해서, 가장 오랫동안 쓰이지 않은
페이지는 앞으로도 당분간 쓰이지 않을 것이라고 보고 교체 대상으로 선택합니다. 미래를 직접 알 수
없는 대신, 과거의 사용 패턴을 미래 예측의 대리 지표로 쓰는 셈입니다.
```

- LRU 알고리즘을 구현한다면, 어떻게 구현할 수 있을까요?
```
이중 연결 리스트와 해시맵을 함께 사용하는 구조가 일반적입니다. 해시맵은 페이지 번호 → 리스트
노드를 빠르게 찾기 위한 용도이고, 이중 연결 리스트는 사용 순서를 유지하는 용도입니다. 어떤
페이지에 접근할 때마다 해당 노드를 리스트의 맨 앞(가장 최근 사용)으로 옮기고, 교체가 필요할 때는
리스트의 맨 뒤(가장 오래 전에 사용) 노드를 제거합니다. 이렇게 하면 접근·삽입·삭제 모두 O(1)에
처리할 수 있습니다.
```

- LRU 알고리즘의 단점을 설명해 주세요. 이를 해결할 수 있는 대안에 대해서도 설명해 주세요.
```
가장 큰 단점은 정확한 LRU를 구현하려면 모든 접근마다 "사용 순서"를 갱신해야 해서 오버헤드가
크고, 이를 하드웨어로 완벽히 지원하는 비용도 만만치 않다는 것입니다. 그래서 실제로는 완벽한
LRU 대신 근사치를 많이 씁니다.

대표적인 대안이 Clock(Second-Chance) 알고리즘입니다. 각 페이지에 참조 비트(reference bit)
하나만 두고, 페이지가 접근될 때마다 하드웨어가 이 비트를 1로 세팅합니다. 교체가 필요할 때는
시계처럼 순환하며 페이지들을 확인하다가, 참조 비트가 0인 페이지를 만나면 그걸 교체하고, 1인
페이지는 비트를 0으로 내린 뒤(한 번 더 기회를 주고) 다음으로 넘어갑니다. 정확한 사용 순서까지는
추적하지 못하지만 훨씬 적은 오버헤드로 LRU와 비슷한 효과를 냅니다. 더 나아가 최근 접근 빈도까지
함께 고려하는 LFU나, 최근성과 빈도를 모두 적응적으로 조합하는 ARC(Adaptive Replacement
Cache) 같은 알고리즘도 대안으로 쓰입니다.
```

**핵심 키워드** → FIFO·Optimal(이론상 최적, 구현 불가능)·LRU·Clock(Second-Chance), LRU는 시간적 지역성을 과거로 미래를 근사, 구현(이중 연결 리스트+해시맵, 접근 시 맨 앞 이동, 교체 시 맨 뒤 제거, O(1)), LRU 단점(모든 접근마다 순서 갱신 오버헤드) → Clock 알고리즘(참조 비트로 근사) / LFU·ARC(빈도까지 고려)

#### 8. File Descriptor와, File System에 에 대해 설명해 주세요.

`★★☆` · `심화` · 원본 [운영체제 #22](../02-OPERATING_SYSTEM.md)

<details>
<summary><b>꼬리 질문 2개 (펼치기)</b></summary>

- I-Node가 무엇인가요?
- 프로그래밍 언어 상에서 제공하는 파일 관련 함수 (Python - open(), Java - BufferedReader/Writer 등)은, 파일을 어떤 방식으로 읽어들이나요?

</details>

**내 답변**

```
File Descriptor는 프로세스가 열어놓은 파일(또는 소켓, 파이프 등)을 가리키기 위해 커널이 부여하는
작은 정수 번호입니다. 프로세스마다 커널이 관리하는 열린 파일 테이블의 인덱스 역할을 하고,
read/write 같은 시스템 콜을 호출할 때 이 번호로 대상을 지정합니다.

File System은 디스크 같은 저장 장치에 데이터를 파일과 디렉터리 단위로 어떻게 조직하고, 이름
붙이고, 저장하고, 찾아낼지를 정의하는 운영체제의 체계입니다. 디렉터리 구조, 파일의 메타데이터
관리, 실제 데이터 블록을 어디에 둘지 관리하는 공간 할당까지를 포함합니다.
```

**꼬리 질문 답변**

- I-Node가 무엇인가요?
```
I-Node는 파일 하나하나에 대한 메타데이터(소유자, 권한, 크기, 생성/수정 시각, 그리고 실제 데이터가
저장된 디스크 블록들의 위치 포인터)를 담고 있는 자료구조입니다. 파일 이름은 이 I-Node를 직접
담고 있지 않고, 디렉터리 안에 "파일 이름 → I-Node 번호" 매핑만 저장되어 있습니다. 그래서 같은
파일을 여러 이름(하드 링크)으로 가리키는 것이 가능하고, 파일의 실제 식별자는 이름이 아니라
I-Node라고 볼 수 있습니다.
```

- 프로그래밍 언어 상에서 제공하는 파일 관련 함수 (Python - open(), Java - BufferedReader/Writer 등)은, 파일을 어떤 방식으로 읽어들이나요?
```
이런 함수들은 내부적으로 OS의 저수준 read()/write() 시스템 콜을 감싸면서, 그 위에 유저 공간
버퍼링을 추가로 얹은 형태입니다. 매번 한 바이트, 한 줄씩 읽을 때마다 시스템 콜을 호출하면
모드 전환 비용이 누적되어 비효율적이기 때문에, 한 번에 디스크에서 비교적 큰 덩어리(버퍼)를 읽어
메모리에 올려두고, 이후 애플리케이션이 요청하는 작은 단위의 읽기는 이미 올라와 있는 버퍼에서
바로 꺼내주다가, 버퍼가 다 소진되면 그때 또 한 번 시스템 콜로 다음 덩어리를 채워 넣는 방식으로
동작합니다. 쓰기도 마찬가지로 버퍼에 모아뒀다가 일정 양이 차거나 flush가 호출될 때 한 번에
시스템 콜로 내보냅니다.
```

**핵심 키워드** → File Descriptor(프로세스별 열린 파일 테이블의 정수 인덱스), File System(디렉터리 구조+메타데이터 관리+공간 할당 체계), I-Node(파일 메타데이터+데이터 블록 포인터, 파일명은 I-Node 번호에 대한 매핑일 뿐 → 하드 링크 가능), 언어 레벨 파일 함수는 read/write 시스템 콜을 유저 공간 버퍼링으로 감싸서 시스템 콜 횟수를 줄임

#### 9. GC에 대해 설명해 주세요.

`★★☆` · `필수` · 원본 [개발상식·기타 #11](../05-ETC.md)

- GC는 어떤 영역에 있는 데이터를 관리하나요?

**내 답변**

```
GC(Garbage Collection)는 프로그램이 더 이상 참조하지 않는, 즉 어디서도 접근할 수 없게 된 힙
메모리를 런타임이 자동으로 탐지해서 회수해주는 메모리 관리 기법입니다. 개발자가 직접 free()나
delete를 호출하지 않아도 되게 해줘서, 메모리 누수나 이미 해제된 메모리를 다시 참조하는 버그
같은 수동 메모리 관리의 위험을 크게 줄여줍니다.
```

**꼬리 질문 답변**

- 본인이 사용하는 언어에서는 GC를 어떻게 구현했나요?
```
(사용 언어에 맞게 채워 넣기)
예) Java: 객체를 생성된 시기에 따라 Young/Old 영역으로 나누는 세대별(Generational) GC를
    기본으로 합니다. 대부분의 객체는 금방 참조가 끊기므로 Young 영역에서 Mark-Sweep 방식으로
    빠르게 처리하고(Minor GC), 여러 번의 Minor GC를 거쳐도 살아남은 객체만 Old 영역으로 옮겨서
    상대적으로 드물게 Major/Full GC를 수행합니다. G1GC 같은 최신 수집기는 힙을 여러 작은
    영역(Region)으로 나누고 Stop-the-world 시간을 줄이는 데 중점을 둡니다.
```

- GC의 장단점에 대해 설명해 주세요.
```
장점은 개발자가 메모리 해제 시점을 직접 신경 쓰지 않아도 되어, 메모리 누수나 댕글링 포인터 같은
수동 관리 실수를 원천적으로 줄여주고 개발 생산성을 높인다는 것입니다.

단점은 GC가 동작하는 시점과 소요 시간을 개발자가 세밀하게 제어하기 어렵다는 것입니다. 특히
Stop-the-world 방식의 GC는 수집 도중 애플리케이션 실행을 잠시 완전히 멈추기 때문에, 지연 시간에
민감한 시스템에서는 예측하기 어려운 응답 지연으로 이어질 수 있습니다. 또한 참조 그래프를
추적·관리하는 데 그 자체로 CPU와 메모리 오버헤드가 추가로 든다는 점도 있습니다.
```

- GC는 어떤 영역에 있는 데이터를 관리하나요?
```
주로 힙(Heap) 영역에서 동적으로 할당된 객체들을 관리합니다. 스택에 있는 지역 변수는 함수가
반환될 때 자동으로 해제되므로 GC가 관여할 필요가 없고, 전역/정적 영역(Data/BSS)도 프로그램
생명주기 동안 고정되어 있어 GC의 대상이 아닙니다.
```

- Reference Counting 방식에 대해 설명하고, 이 알고리즘에서 발생할 수 있는 순환 참조 및 Retain Cycle에 대해 설명해 주세요.
```
Reference Counting은 각 객체마다 "지금 몇 개의 참조가 나를 가리키고 있는지"를 카운터로 관리하는
방식입니다. 새로운 참조가 생기면 카운터를 올리고, 참조가 끊기면 카운터를 내리다가 카운터가
0이 되는 순간 그 즉시 메모리를 해제합니다. Mark-Sweep처럼 전체를 훑는 수집 과정 없이 즉각적으로
회수된다는 장점이 있습니다.

다만 두 객체가 서로를 참조하는 순환 참조(Circular Reference)가 생기면 문제가 됩니다. 두 객체
A, B가 서로를 가리키고 있으면, 외부에서는 이 둘에 더 이상 아무도 접근할 수 없는 상태가 되어도
A는 B의 참조를 갖고 B는 A의 참조를 갖고 있어서 둘의 카운터가 절대 0이 되지 않습니다. 그 결과
이 객체들은 영원히 회수되지 않는 메모리 누수(Swift의 ARC에서는 이를 Retain Cycle이라고
부릅니다)가 발생합니다. 이를 해결하기 위해 참조를 "강한 참조(Strong)"와 "약한 참조(Weak)"로
구분해서, 순환을 만들 수 있는 한쪽을 weak 참조로 바꿔 카운트에 반영되지 않게 하거나(Swift의
weak/unowned), Python처럼 별도의 세대별 순환 참조 탐지기를 보조적으로 함께 돌려 순환된
객체 그룹을 찾아내 강제로 회수하는 방식을 씁니다.
```

**핵심 키워드** → GC = 도달 불가능한 힙 메모리 자동 회수, Java 세대별 GC(Young/Old, Minor/Major GC, G1GC의 Region), 장점(수동 관리 실수 방지) vs 단점(Stop-the-world 지연, 추적 오버헤드), 관리 대상 = 힙(스택·전역 영역은 GC 대상 아님), Reference Counting(카운터 0이 되면 즉시 회수) → 순환 참조/Retain Cycle(상호 참조로 카운트가 0이 안 됨) → Weak Reference 또는 보조 순환 탐지기로 해결

#### [자료구조 3/6] 이진 탐색 트리 (BST)

**구현 범위** — `insert` / `search` / `delete`(자식 0개·1개·2개 케이스) + 중위 순회. 편향 트리가 되면 왜 O(N)이 되는지

```java
class BSTNode {
    int key;
    BSTNode left, right;
    BSTNode(int key) { this.key = key; }
}

class BST {
    private BSTNode root;

    void insert(int key) {
        root = insert(root, key);
    }

    private BSTNode insert(BSTNode node, int key) {
        if (node == null) return new BSTNode(key); // 빈 자리를 찾으면 새 노드 생성
        if (key < node.key) node.left = insert(node.left, key);
        else if (key > node.key) node.right = insert(node.right, key);
        return node; // key == node.key면 중복, 그대로 반환(무시)
    }

    boolean search(int key) {
        BSTNode cur = root;
        while (cur != null) {
            if (key == cur.key) return true;
            cur = (key < cur.key) ? cur.left : cur.right;
        }
        return false;
    }

    void delete(int key) {
        root = delete(root, key);
    }

    private BSTNode delete(BSTNode node, int key) {
        if (node == null) return null;

        if (key < node.key) {
            node.left = delete(node.left, key);
        } else if (key > node.key) {
            node.right = delete(node.right, key);
        } else {
            // 삭제할 노드를 찾은 경우 — 자식 개수에 따라 3가지로 분기
            if (node.left == null && node.right == null) {
                return null; // 자식 0개: 그냥 제거
            } else if (node.left == null) {
                return node.right; // 자식 1개(오른쪽만): 자식을 그 자리로 끌어올림
            } else if (node.right == null) {
                return node.left; // 자식 1개(왼쪽만): 자식을 그 자리로 끌어올림
            } else {
                // 자식 2개: 오른쪽 서브트리의 최솟값으로 현재 노드를 대체한 뒤,
                // 그 최솟값 노드를 오른쪽 서브트리에서 삭제
                BSTNode successor = findMin(node.right);
                node.key = successor.key;
                node.right = delete(node.right, successor.key);
            }
        }
        return node;
    }

    private BSTNode findMin(BSTNode node) {
        while (node.left != null) node = node.left;
        return node;
    }

    // 중위 순회 — 왼쪽, 루트, 오른쪽 순서로 방문하면 오름차순으로 나옴
    void inorder(BSTNode node, List<Integer> result) {
        if (node == null) return;
        inorder(node.left, result);
        result.add(node.key);
        inorder(node.right, result);
    }
}
```

**편향 트리가 되면 왜 O(N)이 되는지** — BST의 탐색·삽입·삭제가 O(log N)인 이유는 매 비교마다 후보군이 절반씩 줄어드는 트리의 높이(log N)만큼만 내려가면 되기 때문입니다. 하지만 값을 이미 정렬된 순서로 계속 삽입하면 매번 한쪽 자식에만 노드가 붙어서, 트리의 높이가 노드 수만큼(N) 그대로 늘어난 사실상의 연결 리스트 형태가 됩니다. 이 경우 루트에서부터 한 칸씩 전부 내려가야 하므로 모든 연산이 O(N)으로 저하됩니다. (이 문제를 막기 위해 AVL Tree, Red-Black Tree 같은 BBST가 등장했습니다.)

**시간복잡도** → 균형 트리 기준 `insert`/`search`/`delete` 모두 O(log N), 편향 시 O(N) · `inorder` O(N)
**공간복잡도** → 트리 전체 O(N), 재귀 호출 스택은 균형 시 O(log N)·편향 시 O(N)

> 원본: [손코딩 연습 문항](../06-ALGORITHM.md) · IDE 없이 손으로 먼저 써본 뒤, 스터디에서 서로 비교합니다.

#### 11. 2,000,000 자리의 숫자 여러개가 있고, 이 숫자들을 모두 더해야 한다고 합니다. 어떻게 코드를 작성하면 좋을까요? (Python을 사용하고 있다고 해도, 다른 언어의 long long 범위까지만 사용할 수 있다고 가정합시다.)

```java
class BigNumberAddition {

    // 두 개의 큰 수(문자열)를 더해 문자열로 반환 — 초등학교 때 배운 자리별 덧셈을 그대로 구현
    static String addTwo(String a, String b) {
        StringBuilder result = new StringBuilder();
        int i = a.length() - 1, j = b.length() - 1;
        int carry = 0;

        // 두 수 모두 끝(1의 자리)부터 거슬러 올라가며 한 자리씩 더함
        while (i >= 0 || j >= 0 || carry > 0) {
            int digitA = (i >= 0) ? a.charAt(i--) - '0' : 0;
            int digitB = (j >= 0) ? b.charAt(j--) - '0' : 0;
            int sum = digitA + digitB + carry;
            result.append(sum % 10);
            carry = sum / 10; // 10 이상이면 다음 자리로 올림(carry)
        }

        return result.reverse().toString(); // 뒤에서부터 채웠으므로 마지막에 뒤집기
    }

    // 숫자가 몇 개든, 누적합을 유지하며 하나씩 순서대로 더해나감
    static String addAll(String[] numbers) {
        String sum = "0";
        for (String num : numbers) {
            sum = addTwo(sum, num);
        }
        return sum;
    }
}
```

**풀이 설명**

숫자가 2,000,000자리면 long이나 BigInteger 라이브러리에 기대지 않고, 자릿수를 그대로 문자열(또는
문자 배열)로 다루면서 초등학교 때 하던 "자리별로 더하고 올림수를 넘기는" 세로 덧셈을 그대로
구현하면 됩니다. 각 숫자를 끝자리(1의 자리)부터 거슬러 올라가며 같은 자리끼리 더하고, 합이
10을 넘으면 다음 자리에 올림수(carry)를 넘겨줍니다. 한 자리 계산은 항상 0~9 범위의 작은
정수 연산이라 long long 같은 고정 크기 정수형 범위를 절대 벗어나지 않습니다.

숫자가 여러 개 있는 경우에는, 이 두 수 덧셈 함수를 재사용해서 누적합(sum)을 하나 두고 숫자들을
순서대로 하나씩 더해나가면 됩니다. 숫자 K개, 각 숫자의 최대 자릿수가 N이라면, 매 덧셈이 그
시점의 누적합 길이(최대 N에 가까움)에 비례하므로 전체 비용은 숫자 개수와 자릿수에 선형으로
비례합니다.

**시간복잡도** → O(K × N) (K = 숫자 개수, N = 숫자당 최대 자릿수, 매 덧셈이 O(N)이고 이를 K-1번 반복)
**공간복잡도** → O(N) (결과 문자열 하나의 길이만큼, 입력 자체를 제외하면 추가 공간은 결과값 크기에 비례)
