#### 1. 쿠키와 세션의 차이에 대해 설명해 주세요.

`★☆☆` · `필수` · 원본 [네트워크 #1](../03-NETWORK.md)

<details>
<summary><b>꼬리 질문 4개 (펼치기)</b></summary>

- 세션 방식의 로그인 과정에 대해 설명해 주세요.
- HTTP의 특성인 Stateless에 대해 설명해 주세요.
- Stateless의 의미를 살펴보면, 세션은 적절하지 않은 인증 방법 아닌가요?
- 규모가 커져 서버가 여러 개가 된다면, 세션을 어떻게 관리할 수 있을까요?

</details>

**내 답변**

```
가장 큰 차이는 "상태가 어디에 저장되는가"입니다. 쿠키는 서버가 클라이언트(브라우저)에게 내려준
작은 데이터를 클라이언트 쪽에 저장해두고, 이후 같은 도메인으로 요청을 보낼 때마다 자동으로
함께 실어 보내는 방식입니다. 세션은 실제 상태 데이터는 서버에 저장하고, 클라이언트는 그 상태를
가리키는 식별자(세션 ID)만 들고 있습니다. 보통 이 세션 ID 자체는 쿠키에 담아 전달하기 때문에,
세션은 쿠키라는 전달 수단 위에서 동작하는 상위 개념이라고 볼 수 있습니다.
```

**꼬리 질문 답변**

- 세션 방식의 로그인 과정에 대해 설명해 주세요.
```
클라이언트가 아이디·비밀번호를 서버로 전송하면, 서버는 이를 검증한 뒤 로그인에 성공한 사용자를
위한 세션 객체를 서버 메모리(또는 별도 저장소)에 생성하고 고유한 세션 ID를 발급합니다. 서버는
응답의 Set-Cookie 헤더에 이 세션 ID를 담아 클라이언트에게 내려주고, 브라우저는 이를 쿠키로
저장합니다. 이후 클라이언트의 모든 요청에는 이 쿠키가 자동으로 함께 전송되므로, 서버는 매번
아이디·비밀번호를 다시 검증하는 대신 세션 ID로 서버에 저장된 세션을 조회해서 로그인 상태를
유지합니다.
```

- HTTP의 특성인 Stateless에 대해 설명해 주세요.
```
Stateless는 서버가 이전 요청에 대한 정보를 전혀 기억하지 않고, 매 요청을 완전히 독립적으로
처리한다는 특성입니다. 그래서 하나의 요청을 처리하는 데 필요한 모든 정보는 그 요청 자체에 담겨
있어야 하고, 서버는 "이 클라이언트가 방금 전에 무엇을 했는지"를 별도로 기억하지 않습니다.
```

- Stateless의 의미를 살펴보면, 세션은 적절하지 않은 인증 방법 아닌가요?
```
프로토콜 자체의 Stateless한 성격과, 애플리케이션이 상태를 다루는 방식은 서로 다른 층위의
이야기라고 생각합니다. HTTP 프로토콜 자체는 여전히 Stateless합니다. 즉 서버가 커넥션 차원에서
클라이언트를 자동으로 기억해주는 것은 전혀 없습니다. 세션은 이 Stateless한 프로토콜 위에, 매
요청마다 클라이언트가 세션 ID라는 "필요한 정보"를 직접 실어 보내게 함으로써 애플리케이션 계층에서
상태를 흉내 내는 방식입니다. 그래서 Stateless를 위반하는 게 아니라, Stateless한 전송 방식을
그대로 유지하면서 그 위에 상태 관리 계층을 얹은 것이라고 볼 수 있습니다.
```

- 규모가 커져 서버가 여러 개가 된다면, 세션을 어떻게 관리할 수 있을까요?
```
대표적으로 세 가지 방법이 있습니다. Sticky Session은 로드 밸런서가 같은 클라이언트의 요청을
항상 같은 서버로 보내도록 라우팅해서, 그 서버의 로컬 메모리에 있는 세션을 그대로 쓰는 방식입니다.
구현이 간단하지만 특정 서버에 부하가 몰릴 수 있고 그 서버가 죽으면 세션이 날아갑니다. Session
Replication은 모든 서버가 세션 데이터를 서로 복제해서 어느 서버로 가도 동일한 세션을 볼 수
있게 하지만, 서버 수가 늘수록 복제 비용이 커집니다. 가장 널리 쓰이는 방법은 세션 저장소를
Redis 같은 외부의 중앙 집중형 저장소로 분리하는 것으로, 어떤 서버가 요청을 받아도 그 저장소에서
세션을 조회할 수 있어 서버를 자유롭게 확장(scale-out)할 수 있습니다.
```

**핵심 키워드** → 쿠키(클라이언트 저장) vs 세션(서버 저장 + 쿠키로 세션 ID만 전달), 세션 로그인(Set-Cookie로 세션 ID 발급 → 이후 요청마다 자동 전송), Stateless(서버가 이전 요청을 기억하지 않음, 프로토콜 레벨), 세션은 Stateless 위반이 아니라 애플리케이션 레벨에서 상태를 흉내내는 것, 다중 서버 세션 관리(Sticky Session·Session Replication·중앙 저장소(Redis)로 분리)

#### 2. HTTP 응답코드에 대해 설명해 주세요.

`★☆☆` · `필수` · 원본 [네트워크 #2](../03-NETWORK.md)

<details>
<summary><b>꼬리 질문 3개 (펼치기)</b></summary>

- 401 (Unauthorized) 와 403 (Forbidden)은 의미적으로 어떤 차이가 있나요?
- 200 (ok) 와 201 (created) 의 차이에 대해 설명해 주세요.
- 필요하다면 저희가 직접 응답코드를 정의해서 사용할 수 있을까요? 예를 들어 285번 처럼요.

</details>

**내 답변**

```
HTTP 응답코드는 첫 번째 숫자를 기준으로 다섯 가지 범주로 나뉩니다. 1xx는 요청을 받아 처리
중이라는 정보성 응답, 2xx는 요청이 성공적으로 처리됐다는 응답, 3xx는 리소스의 위치가 바뀌었거나
추가 작업이 필요하다는 리다이렉션, 4xx는 클라이언트 쪽의 잘못(잘못된 요청, 인증·권한 문제 등),
5xx는 서버 쪽의 잘못(서버 내부 오류 등)을 의미합니다.
```

**꼬리 질문 답변**

- 401 (Unauthorized) 와 403 (Forbidden)은 의미적으로 어떤 차이가 있나요?
```
401은 "당신이 누군지 증명되지 않았다"는 의미로, 인증(authentication) 자체가 안 됐거나 실패한
경우입니다. 로그인하지 않았거나 토큰이 없거나 만료된 경우가 해당하고, 보통 다시 인증을 시도하라는
의미를 담습니다. 403은 "당신이 누군지는 알지만, 그 권한으로는 이 자원에 접근할 수 없다"는
의미로, 인증은 이미 됐지만 권한(authorization)이 부족한 경우입니다. 즉 401은 신원 확인의
문제, 403은 그 신원으로도 허용되지 않는 접근 제어의 문제라는 차이가 있습니다.
```

- 200 (ok) 와 201 (created) 의 차이에 대해 설명해 주세요.
```
200은 요청이 성공적으로 처리됐다는 일반적인 성공 응답으로, GET이나 PUT처럼 다양한 요청에
포괄적으로 쓰입니다. 201은 그 요청의 결과로 새로운 리소스가 실제로 생성됐다는 더 구체적인
성공 응답으로, 주로 POST(또는 리소스를 새로 만드는 PUT) 이후에 사용하고, 보통 새로 생성된
리소스의 위치를 가리키는 Location 헤더를 함께 내려줍니다.
```

- 필요하다면 저희가 직접 응답코드를 정의해서 사용할 수 있을까요? 예를 들어 285번 처럼요.
```
기술적으로는 숫자 자체를 임의로 보내는 것이 불가능하지는 않지만, 권장되지 않습니다. HTTP
응답코드는 표준(RFC)으로 의미가 정의되어 있고, 브라우저·프록시·캐시 서버·클라이언트 라이브러리
같은 중간 구성 요소들은 이 표준 코드(혹은 최소한 코드의 첫 자리, 즉 클래스)를 보고 공통적인
동작을 수행합니다. 등록되지 않은 임의의 코드를 보내면, 그 코드를 모르는 중간 시스템이 예상과
다르게 동작하거나 단순히 그 코드가 속한 클래스(예: 2xx면 성공)로만 취급해버릴 수 있습니다. 그래서
실무에서는 표준 코드를 그대로 쓰고, 애플리케이션 고유의 세부 정보는 응답 본문(body)이나 커스텀
헤더에 별도의 애플리케이션 전용 에러 코드로 담아 전달하는 방식을 더 많이 씁니다.
```

**핵심 키워드** → 응답코드 5개 범주(1xx 정보·2xx 성공·3xx 리다이렉션·4xx 클라이언트 오류·5xx 서버 오류), 401(인증 실패, 신원 미확인) vs 403(인증 됐지만 권한 없음), 200(일반 성공) vs 201(리소스 생성 성공, Location 헤더), 비표준 커스텀 코드는 비권장(중간 시스템 호환성) → 본문/커스텀 헤더로 애플리케이션 에러 전달

#### 3. HTTP Method 에 대해 설명해 주세요.

`★☆☆` · `필수` · 원본 [네트워크 #3](../03-NETWORK.md)

<details>
<summary><b>꼬리 질문 4개 (펼치기)</b></summary>

- HTTP Method의 멱등성에 대해 설명해 주세요.
- GET과 POST의 차이는 무엇인가요?
- POST와 PUT, PATCH의 차이는 무엇인가요?
- HTTP 1.1 이후로, GET에도 Body에 데이터를 실을 수 있게 되었습니다. 그럼에도 불구하고 왜 아직도 이런 방식을 지양하는 것일까요?

</details>

**내 답변**

```
HTTP Method는 클라이언트가 서버의 리소스에 대해 어떤 동작을 수행하려는지를 나타내는 요청의
종류입니다. 대표적으로 조회에 쓰는 GET, 생성에 쓰는 POST, 전체 교체에 쓰는 PUT, 부분 수정에
쓰는 PATCH, 삭제에 쓰는 DELETE가 있고, 각 메서드는 안전성(Safe, 서버 상태를 변경하지 않는지)과
멱등성(Idempotent, 여러 번 반복해도 결과가 같은지) 같은 특성으로 구분할 수 있습니다.
```

**꼬리 질문 답변**

- HTTP Method의 멱등성에 대해 설명해 주세요.
```
멱등성은 같은 요청을 한 번 보내든 여러 번 반복해서 보내든, 서버의 최종 상태가 항상 동일하게
유지된다는 성질입니다. GET은 조회만 하므로 당연히 멱등하고, PUT은 리소스를 특정 값으로 통째로
덮어쓰는 것이라 몇 번을 호출해도 결과가 같아서 멱등합니다. DELETE도 몇 번을 호출하든 그 리소스가
삭제되어 있는 최종 상태는 동일하므로 멱등하다고 봅니다. 반면 POST는 호출할 때마다 새로운 리소스를
생성하는 경우가 많아서, 같은 요청을 여러 번 보내면 그만큼 리소스가 여러 개 만들어질 수 있어
멱등하지 않습니다.
```

- GET과 POST의 차이는 무엇인가요?
```
GET은 리소스를 조회하기 위한 메서드로, 전달할 데이터를 URL의 쿼리 스트링에 실어 보내고,
캐싱이 가능하며, 멱등하고, 브라우저 히스토리에 남습니다. 다만 URL 길이에 실질적인 제한이
있습니다. POST는 리소스를 생성하거나 서버에 어떤 처리를 요청하기 위한 메서드로, 데이터를 요청
본문(body)에 담아 보내서 URL 길이 제한 없이 더 크고 복잡한 데이터를 전달할 수 있고, 일반적으로
캐싱되지 않으며, 앞서 설명한 것처럼 멱등하지 않습니다.
```

- POST와 PUT, PATCH의 차이는 무엇인가요?
```
POST는 새로운 리소스를 생성(또는 특정 처리를 수행)하는 데 쓰이고, 요청할 때마다 새로운
리소스가 만들어질 수 있어 멱등하지 않습니다. PUT은 특정 URI의 리소스 전체를 요청 본문의 내용으로
완전히 교체(덮어쓰기)하는 데 쓰이고, 같은 요청을 반복해도 최종 상태가 같아서 멱등합니다. PATCH는
리소스 전체가 아니라 지정한 일부 필드만 부분적으로 수정하는 데 쓰입니다. PATCH는 구현 방식에
따라 멱등할 수도, 아닐 수도 있습니다(예: "값을 5로 설정"은 멱등하지만 "값을 1 증가시켜라"는
멱등하지 않습니다).
```

- HTTP 1.1 이후로, GET에도 Body에 데이터를 실을 수 있게 되었습니다. 그럼에도 불구하고 왜 아직도 이런 방식을 지양하는 것일까요?
```
스펙상 명시적으로 금지하지는 않지만, 실제 생태계 전반이 "GET은 본문이 없다"는 전제로 구축되어
있기 때문입니다. 많은 캐시 서버·프록시·로드 밸런서·라이브러리들이 GET 요청의 본문을 무시하거나
제대로 전달하지 않을 수 있습니다. 또한 캐싱 시스템은 보통 URL을 기준으로 캐시 키를 결정하는데,
본문에 담긴 데이터는 이 캐시 키에 반영되지 않아서 서로 다른 본문으로 보낸 GET 요청이 같은
캐시된 응답을 돌려받는 등 예상과 다른 동작으로 이어질 수 있습니다. 그래서 호환성과 캐싱의
일관성을 지키기 위해, 실무에서는 여전히 데이터를 쿼리 스트링에 싣거나, 본문이 꼭 필요하다면
POST를 쓰는 것을 권장합니다.
```

**핵심 키워드** → HTTP Method(GET·POST·PUT·PATCH·DELETE), 안전성(Safe) vs 멱등성(Idempotent, 반복 호출해도 최종 상태 동일), GET·PUT·DELETE는 멱등 / POST는 비멱등 / PATCH는 구현에 따라 다름, GET=쿼리스트링·캐시 가능 vs POST=본문·캐시 안 됨, GET에 Body 지양 이유(캐시 키가 URL 기준이라 본문이 캐싱에 반영 안 됨, 중간 인프라 호환성 문제)

#### 4. HTTP에 대해 설명해 주세요.

`★★☆` · `필수` · 원본 [네트워크 #4](../03-NETWORK.md)

<details>
<summary><b>꼬리 질문 3개 (펼치기)</b></summary>

- 공개키와 대칭키에 대해 설명해 주세요.
- 왜 HTTPS Handshake 과정에서는 인증서를 사용하는 것 일까요?
- SSL과 TLS의 차이는 무엇인가요?

</details>

**내 답변**

```
HTTP(HyperText Transfer Protocol)는 클라이언트와 서버가 리소스(HTML, JSON, 이미지 등)를
요청-응답 형태로 주고받기 위한 애플리케이션 계층 프로토콜입니다. TCP(또는 HTTP/3에서는
QUIC/UDP) 위에서 동작하고, Stateless한 특성을 가지며, 메서드·URI·헤더·본문으로 구성된 요청을
보내면 상태 코드·헤더·본문으로 구성된 응답을 받습니다. HTTPS는 이 HTTP 통신을 TLS로 암호화해서
기밀성과 무결성, 그리고 서버 신원 인증까지 함께 제공하는 보안이 강화된 버전입니다.
```

**꼬리 질문 답변**

- 공개키와 대칭키에 대해 설명해 주세요.
```
대칭키(Symmetric Key) 방식은 암호화와 복호화에 동일한 하나의 키를 사용합니다. 연산이 빠르지만,
그 키를 통신 상대에게 안전하게 전달하는 방법이 문제가 됩니다(키 자체가 중간에 탈취되면 전체
통신이 뚫립니다).

공개키(비대칭키, Asymmetric Key) 방식은 공개키와 개인키라는 한 쌍의 키를 사용하는데, 공개키로
암호화한 데이터는 그 쌍을 이루는 개인키로만 복호화할 수 있습니다. 공개키는 누구에게나 공개해도
안전하기 때문에 키 분배 문제를 해결할 수 있지만, 연산이 대칭키보다 훨씬 무겁습니다. 그래서
TLS는 두 방식을 함께 씁니다. 처음에 공개키 방식으로 안전하게 대칭키(세션 키)를 교환하고,
이후 실제 데이터 통신은 가벼운 대칭키 방식으로 처리합니다.
```

- 왜 HTTPS Handshake 과정에서는 인증서를 사용하는 것 일까요?
```
공개키를 주고받는 것만으로는 "그 공개키가 실제로 내가 접속하려는 서버의 것"이라는 사실까지는
보장할 수 없기 때문입니다. 중간에 공격자가 자신의 공개키를 진짜 서버의 공개키인 것처럼 바꿔치기
해서 통신을 가로채는 중간자 공격(MITM)이 가능합니다.

인증서는 신뢰할 수 있는 제3의 기관(CA, Certificate Authority)이 "이 공개키는 실제로 이
도메인의 것이다"라는 사실을 서명해서 보증해주는 문서입니다. 브라우저는 미리 신뢰하는 CA 목록을
갖고 있어서, 서버가 제시한 인증서가 그 CA의 서명으로 유효하게 검증되는지 확인함으로써, 지금
받은 공개키가 정말 그 서버의 것이 맞다는 것을 신뢰할 수 있게 됩니다.
```

- SSL과 TLS의 차이는 무엇인가요?
```
SSL(Secure Sockets Layer)은 더 오래된 프로토콜로, SSL 2.0·3.0 모두 심각한 취약점이 발견되어
현재는 사용이 금지되어 있습니다. TLS(Transport Layer Security)는 SSL의 뒤를 이은 후속
프로토콜로, TLS 1.0부터 현재의 TLS 1.3까지 발전하며 더 안전한 암호화 스위트와 더 빠른 핸드셰이크
과정을 제공합니다. 다만 관용적으로 지금도 "SSL 인증서", "HTTPS는 SSL을 쓴다"처럼 SSL이라는
이름이 널리 쓰이지만, 실제로 현재 웹에서 동작하고 있는 것은 거의 전부 TLS입니다.
```

**핵심 키워드** → HTTP = 요청-응답 기반 애플리케이션 계층 프로토콜(Stateless, TCP 위에서 동작), HTTPS = HTTP + TLS(기밀성·무결성·인증), 대칭키(빠름, 키 분배 문제) vs 공개키(키 분배 해결, 느림) → TLS는 공개키로 대칭키 교환 후 대칭키로 통신, 인증서(CA가 공개키-신원 바인딩을 서명으로 보증, MITM 방지), SSL(구버전, 취약점으로 폐기) → TLS(현재 표준, TLS 1.3)

**막힌 부분 / 다시 볼 것** →

#### 5. 웹소켓과 소켓 통신의 차이에 대해 설명해 주세요.

`★★☆` · `심화` · 원본 [네트워크 #5](../03-NETWORK.md)

<details>
<summary><b>꼬리 질문 3개 (펼치기)</b></summary>

- 소켓과 포트의 차이가 무엇인가요?
- 여러 소켓이 있다고 할 때, 그 소켓의 포트 번호는 모두 다른가요?
- 사용자의 요청이 무수히 많아지면, 소켓도 무수히 생성되나요?

</details>

**내 답변**

```
소켓(Socket)은 운영체제가 제공하는 네트워크 통신의 기본 추상화로, TCP나 UDP를 직접 다루며
전송 계층 수준에서 저수준으로 통신합니다. 데이터의 형식이나 의미는 애플리케이션이 알아서 정해야
합니다.

웹소켓(WebSocket)은 이 TCP 위에 구축된 애플리케이션 계층 프로토콜로, 처음에는 HTTP 요청으로
핸드셰이크(Upgrade 헤더 사용)를 시작해서 일반 웹 인프라(80/443 포트, 프록시·방화벽)를 그대로
통과한 뒤, 연결을 webSocket 프로토콜로 전환해 하나의 TCP 연결을 계속 유지하면서 클라이언트와
서버가 양방향으로 자유롭게 메시지를 주고받을 수 있게 해줍니다. 즉 소켓은 더 범용적이고 저수준인
통신 수단이고, 웹소켓은 웹 환경에서 실시간 양방향 통신을 쉽게 쓸 수 있도록 특화해서 설계된 상위
프로토콜입니다.
```

**꼬리 질문 답변**

- 소켓과 포트의 차이가 무엇인가요?
```
포트는 한 호스트 안에서 특정 프로세스(애플리케이션)를 식별하기 위한 숫자일 뿐입니다. 소켓은
그 포트를 포함해서, "어떤 프로토콜(TCP/UDP)로, 어떤 IP 주소와 포트의 상대방과" 통신하고 있는지를
나타내는 통신의 종단점(endpoint) 전체를 가리킵니다. 즉 포트는 소켓을 구성하는 요소 중 하나이고,
소켓은 그 포트를 포함한 더 큰 개념입니다.
```

- 여러 소켓이 있다고 할 때, 그 소켓의 포트 번호는 모두 다른가요?
```
반드시 그렇지는 않습니다. 서버 입장에서는 하나의 리스닝 포트(예: 80번)로 여러 클라이언트의
연결을 동시에 받아들일 수 있는데, 이때 각 연결을 구분하는 기준은 포트 번호 하나가 아니라
(출발지 IP, 출발지 포트, 목적지 IP, 목적지 포트)로 이루어진 4-튜플 전체입니다. 그래서 서버
쪽 로컬 포트는 여러 소켓에서 80번으로 동일하더라도, 각 클라이언트의 IP나 포트가 다르기 때문에
서로 다른 소켓으로 구분될 수 있습니다.
```

- 사용자의 요청이 무수히 많아지면, 소켓도 무수히 생성되나요?
```
이론적으로는 요청(연결)이 늘어날수록 소켓도 함께 늘어나지만, 운영체제가 정한 한계(파일 디스크립터
개수 제한, 사용 가능한 임시 포트 범위 등)를 넘을 수는 없습니다. 그래서 실제 서비스에서는 연결마다
전용 스레드를 쓰는 대신 epoll 같은 I/O 멀티플렉싱으로 적은 수의 스레드가 많은 소켓을 효율적으로
처리하게 하거나, 여러 서버로 부하를 분산하는 로드 밸런싱, 커넥션 풀링 같은 기법으로 자원 사용을
관리해서 요청 수가 늘어나도 시스템이 감당할 수 있게 설계합니다.
```

**핵심 키워드** → 소켓(저수준 전송 계층 통신 추상화) vs 웹소켓(HTTP 핸드셰이크로 시작해 전환되는 상위 프로토콜, 양방향 지속 연결), 포트(프로세스 식별 번호) ⊂ 소켓(4-튜플: 출발지/목적지 IP+포트로 식별), 같은 리스닝 포트라도 클라이언트별로 다른 소켓으로 구분, 소켓 자원은 OS 한계(파일 디스크립터·포트 범위) 존재 → epoll·로드밸런싱·커넥션 풀링으로 관리

**막힌 부분 / 다시 볼 것** →

#### 6. HTTP/1.1과 HTTP/2의 차이점은 무엇인가요?

`★★☆` · `필수` · 원본 [네트워크 #6](../03-NETWORK.md)

<details>
<summary><b>꼬리 질문 2개 (펼치기)</b></summary>

- HOL Blocking 에 대해 설명해 주세요.
- HTTP/3.0의 주요 특징에 대해 설명해 주세요.

</details>

**내 답변**

```
HTTP/1.1은 텍스트 기반 프로토콜로, 하나의 TCP 연결에서 기본적으로 요청을 보내고 그 응답을 받아야
다음 요청을 처리할 수 있어서, 브라우저들은 병렬성을 확보하려고 도메인당 여러 개의 TCP 연결을
동시에 여는 방식으로 대응했습니다.

HTTP/2는 메시지를 바이너리 프레임으로 다루고, 하나의 TCP 연결 위에서 여러 요청·응답을 독립된
스트림으로 동시에 주고받는 멀티플렉싱(Multiplexing)을 지원합니다. 또한 반복되는 헤더 정보를
압축하는 HPACK, 서버가 클라이언트의 요청 없이도 리소스를 먼저 보내주는 Server Push 같은 기능이
추가되어, 연결을 여러 개 열 필요 없이 적은 수의 연결로도 훨씬 효율적으로 많은 리소스를 가져올 수
있게 되었습니다.
```

**꼬리 질문 답변**

- HOL Blocking 에 대해 설명해 주세요.
```
HOL(Head-of-Line) Blocking은 줄의 맨 앞에 있는 항목이 지연되면, 그 뒤에 있는 항목들도 먼저
처리될 수 없어 전부 함께 지연되는 현상입니다.

HTTP/1.1에서는 응답이 요청을 보낸 순서대로 돌아와야 한다는 제약 때문에, 먼저 보낸 요청의 처리가
늦어지면 이미 준비된 다음 요청의 응답도 먼저 전달받지 못하고 함께 막힙니다. HTTP/2는 스트림을
독립적으로 멀티플렉싱해서 이 애플리케이션(HTTP) 계층의 HOL Blocking은 해결했지만, 그 아래의
TCP는 패킷을 보낸 순서대로 전달해야 한다는 제약이 있어서, 패킷 하나가 손실되면 그 이후의 모든
스트림 데이터가 TCP 계층에서 함께 멈춰버리는 전송 계층의 HOL Blocking은 여전히 남아 있습니다.
```

- HTTP/3.0의 주요 특징에 대해 설명해 주세요.
```
HTTP/3는 TCP 대신 UDP 기반의 QUIC이라는 새로운 전송 프로토콜 위에서 동작합니다. QUIC은
스트림마다 독립적으로 신뢰성과 순서를 관리하기 때문에, 한 스트림에서 패킷 손실이 생겨도 다른
스트림에는 영향을 주지 않아 앞서 설명한 TCP 계층의 HOL Blocking 문제를 해결합니다.

또한 QUIC은 TLS 1.3을 프로토콜 안에 기본으로 통합하고 있어서 전송 계층과 암호화 핸드셰이크를
한 번에 처리해 연결 수립 속도가 더 빠르고(처음 연결도 1-RTT, 재연결은 0-RTT도 가능), IP
주소나 네트워크가 바뀌어도(예: Wi-Fi에서 모바일 데이터로 전환) Connection ID를 기준으로 연결을
유지하는 Connection Migration 기능도 제공해 끊김 없는 연결 전환을 지원합니다.
```

**핵심 키워드** → HTTP/1.1(텍스트 기반, 연결당 순차 처리 → 다중 TCP 연결로 병렬성 확보) vs HTTP/2(바이너리 프레임, 멀티플렉싱, HPACK 헤더 압축, Server Push), HOL Blocking(앞 항목 지연이 뒤를 모두 막음), HTTP/2는 애플리케이션 레벨 HOL Blocking 해결 but TCP 레벨은 여전히 존재, HTTP/3 = QUIC(UDP 기반, 스트림별 독립 신뢰성 → TCP HOL Blocking 해소), QUIC = TLS 1.3 통합(빠른 핸드셰이크) + Connection Migration

#### 7. Stateless와 Connectionless에 대해 설명해 주세요.

`★★☆` · `필수` · 원본 [네트워크 #16](../03-NETWORK.md)

<summary><b>꼬리 질문 3개 (펼치기)</b></summary>

- 왜 HTTP는 Stateless 구조를 채택하고 있을까요?
- Connectionless의 논리대로면 성능이 되게 좋지 않을 것으로 보이는데, 해결 방법이 있을까요?
- TCP의 keep-alive와 HTTP의 keep-alive의 차이는 무엇인가요?

</details>

**내 답변**

```
Stateless는 서버가 이전 요청의 정보를 전혀 기억하지 않고, 매 요청을 독립적으로 처리한다는
HTTP의 특성입니다. Connectionless는 요청과 응답을 처리하기 위해 연결을 계속 유지하지 않고,
논리적으로는 요청마다 새로 연결하고 응답을 받으면 연결을 끝내는 것으로 취급한다는 특성으로,
초기 HTTP(1.0)는 실제로 요청마다 TCP 연결을 새로 열고 끝냈습니다.
```

**꼬리 질문 답변**

- 왜 HTTP는 Stateless 구조를 채택하고 있을까요?
```
서버 설계를 단순하고 확장하기 쉽게 만들기 위해서입니다. 서버가 클라이언트별 상태를 메모리에
기억하지 않아도 되면, 어떤 서버 인스턴스가 어떤 요청을 처리하든 결과가 같기 때문에 여러 서버로
자유롭게 부하를 분산(로드 밸런싱, 수평 확장)할 수 있습니다. 또한 특정 서버가 다운돼도 그
서버에만 있던 복잡한 클라이언트 상태를 잃어버릴 걱정이 없어서, 대규모 웹 서비스처럼 수많은
클라이언트를 동시에 상대해야 하는 환경에 훨씬 적합합니다.
```

- Connectionless의 논리대로면 성능이 되게 좋지 않을 것으로 보이는데, 해결 방법이 있을까요?
```
맞습니다. 매 요청마다 TCP 연결을 새로 맺고 끊으면 매번 3-way handshake 비용이 들어 비효율적
입니다. 이를 해결하기 위해 HTTP/1.1부터는 기본적으로 Persistent Connection(Connection:
keep-alive)을 사용해서, 하나의 TCP 연결을 여러 요청·응답에 걸쳐 재사용합니다. 그래서 실제
운영에서는 논리적으로는 Connectionless를 표방하지만, 실질적인 전송 단계에서는 연결을 유지해서
성능 문제를 완화하고 있습니다. HTTP/2의 멀티플렉싱은 이 재사용을 한 단계 더 발전시켜서, 하나의
연결 위에서 여러 요청을 동시에 주고받을 수 있게 만들었습니다.
```

- TCP의 keep-alive와 HTTP의 keep-alive의 차이는 무엇인가요?
```
목적이 다릅니다. TCP의 keep-alive는 전송 계층에서 오랫동안 아무 데이터도 오가지 않는 유휴
연결에 대해, 주기적으로 작은 프로브 패킷을 보내 상대방이 여전히 살아있는지(연결이 끊기지
않았는지)를 확인하는 용도입니다.

HTTP의 keep-alive(Persistent Connection)는 애플리케이션 계층에서, 하나의 TCP 연결을 매
요청마다 새로 맺지 않고 여러 번의 HTTP 요청·응답에 걸쳐 재사용하자는 약속입니다. 즉 TCP
keep-alive는 "연결이 살아있는지 확인"하는 것이고, HTTP keep-alive는 "연결 수립 비용을 줄이기
위해 같은 연결을 재사용"하는 것으로, 서로 다른 계층에서 서로 다른 문제를 해결하기 위한
메커니즘입니다.
```

**핵심 키워드** → Stateless(서버가 이전 요청 미기억) vs Connectionless(요청마다 연결을 새로 맺는 것으로 간주), Stateless 채택 이유(서버 단순화 + 수평 확장 용이), Connectionless 성능 문제 → HTTP/1.1의 Persistent Connection(keep-alive)로 완화, HTTP/2 멀티플렉싱으로 더 발전, TCP keep-alive(연결 생존 확인) vs HTTP keep-alive(연결 재사용으로 핸드셰이크 비용 절감) — 서로 다른 계층·목적

**내 답변**

```
문자열 인코딩은 문자(사람이 읽는 글자)와 그것을 저장·전송하기 위한 바이트 표현 사이를 변환하는
규칙입니다. ASCII는 영문·숫자·기본 기호만을 1바이트(사실상 7비트)로 표현하는 초기 표준이고,
UTF-8은 문자에 따라 1~4바이트를 가변적으로 사용하면서 ASCII와 하위 호환되어 현재 웹에서 가장
널리 쓰이는 인코딩입니다. 그 외에도 한글 전용의 EUC-KR, 고정 길이의 UTF-16 등이 있으며,

인코딩을 약속하는 것이 중요합니다.
```

**꼬리 질문 답변**

- Base64 인코딩은 일반적인 문자열 인코딩과는 달리, 사용자가 읽기 어려운 알파벳과 숫자 조합으로 변경합니다. 이를 사용하는 이유는 무엇일까요?
```
Base64는 암호화가 아니라, 임의의 바이너리 데이터를 텍스트 기반 환경에서 안전하게 전달하기 위한

텍스트, 그중에서도 일부 제어 문자나 특정 바이트 값은 깨지거나 오작동을 일으킬 수 있는 환경을
전제로 설계되어 있습니다. 이미지나 파일 같은 순수 바이너리 데이터를 그대로 이런 경로에 실어
보내면 중간에 값이 손상되거나 프로토콜이 오작동할 위험이 있습니다.

Base64는 모든 바이너리 데이터를 A-Z, a-z, 0-9, +, / (그리고 패딩용 =)로만 이루어진, 어떤
텍스트 기반 시스템에서도 안전하게 통과할 수 있는 좁은 문자 집합으로 바꿔줍니다. 그 대가로 원본
데이터보다 크기가 약 33% 커지지만, 이 변환 덕분에 바이너리 데이터도 텍스트만 다루는 기존
인프라를 그대로 통과시킬 수 있게 됩니다. 사람이 읽기 어려운 것은 목적이 아니라, "어떤 텍스트
채널에서도 깨지지 않는 안전한 형태로 바꾼다"는 목적의 부수적인 결과입니다.
```

**핵심 키워드** → 문자열 인코딩 = 문자↔바이트 변환 규칙(ASCII·UTF-8·UTF-16·EUC-KR), 같은 바이트도 인코딩에 따라 다르게 해석 → 송수신 양쪽 합의 필요, Base64 = 암호화 아님(바이너리를 텍스트 안전 문자 집합으로 변환), 목적 = 텍스트 기반 채널(이메일·URL·JSON)에서 바이너리 데이터 손상 방지, 약 33% 크기 증가 트레이드오프

```
MVC(Model-View-Controller)는 애플리케이션을 세 가지 역할로 분리하는 아키텍처 패턴입니다.
Model은 데이터와 비즈니스 로직, 상태를 담당하고, View는 그 데이터를 사용자에게 어떻게 보여줄지
```

```
대표적으로 MVP(Model-View-Presenter)와 MVVM(Model-View-ViewModel)이 있습니다.

MVP는 View와 Model 사이에 있는 Presenter가 모든 화면 로직을 담당하고, View는 Presenter가
정해준 대로 보여주기만 하는 수동적인 역할만 합니다. View와 Presenter는 보통 인터페이스로
연결되어 있어서, View를 가짜(mock)로 대체해 Presenter의 로직만 독립적으로 테스트하기 쉽다는
장점이 있습니다. MVC의 Controller는 보통 View를 어느 정도 직접 알고 조작하는 경우가 많은데,
MVP는 이 결합을 인터페이스로 한 단계 더 끊어낸 구조라고 볼 수 있습니다.

MVVM은 View와 Model 사이에 ViewModel을 두는데, View가 ViewModel의 데이터를 데이터
바인딩(Data Binding)으로 직접 구독해서, ViewModel의 값이 바뀌면 화면이 자동으로 갱신됩니다.
MVP처럼 "화면을 갱신해줘"라는 코드를 직접 호출할 필요가 없어서 View와 로직 사이의 보일러플레이트
코드가 크게 줄어듭니다. Vue, 안드로이드 Jetpack, WPF 같은 프레임워크들이 이 패턴을 채택하고
있습니다.

정리하면 MVC → MVP → MVVM으로 갈수록 View와 로직 사이의 결합이 점점 더 느슨해지고, 특히
MVVM은 데이터 바인딩이라는 선언적인 방식으로 수동적인 갱신 코드를 더 많이 자동화한다는 차이가
있습니다.
```

**핵심 키워드** → MVC(Model·View·Controller, 관심사 분리), MVP(Presenter가 화면 로직 전담, View는 인터페이스로 분리되어 테스트 용이), MVVM(ViewModel + 데이터 바인딩, View 자동 갱신으로 보일러플레이트 감소), MVC→MVP→MVVM 순으로 View-로직 결합도가 점점 느슨해짐

## Part 3. 손코딩

### 워밍업 — 자료구조 · 정렬 구현

> 원본 [손코딩 #1 (각종 정렬) · #2 (각종 자료구조)](../06-ALGORITHM.md)를 12주로 나눈 조각입니다. 매주 1개씩, **10분 안에** IDE 없이 손으로 작성합니다.

#### [정렬 3/6] 퀵 정렬

**구현 범위** — 파티션(Lomuto 또는 Hoare) + 재귀. 피벗 선택 전략과, 최악 O(N²)를 만드는 입력

```java
import java.util.Random;

class QuickSort {

    private static final Random RAND = new Random();

    static void sort(int[] arr) {
        quickSort(arr, 0, arr.length - 1);
    }

    private static void quickSort(int[] arr, int low, int high) {
        if (low >= high) return;

        int pivotIndex = partition(arr, low, high);
        quickSort(arr, low, pivotIndex - 1);
        quickSort(arr, pivotIndex + 1, high);
    }

    // Lomuto Partition — pivot을 맨 끝으로 보내고, pivot보다 작은 값들을 앞쪽에 모음
    private static int partition(int[] arr, int low, int high) {
        // 랜덤 인덱스를 pivot으로 선택해 최악의 입력(정렬된 배열 등)에서도 치우침을 방지
        int randomIndex = low + RAND.nextInt(high - low + 1);
        swap(arr, randomIndex, high);
        int pivot = arr[high];

        int storeIndex = low;
        for (int i = low; i < high; i++) {
            if (arr[i] < pivot) {
                swap(arr, storeIndex, i);
                storeIndex++;
            }
        }
        swap(arr, storeIndex, high); // pivot을 제자리로 이동
        return storeIndex;
    }

    private static void swap(int[] arr, int i, int j) {
        int tmp = arr[i];
        arr[i] = arr[j];
        arr[j] = tmp;
    }
}
```

**피벗 선택 전략** — 매번 첫 원소나 마지막 원소를 고정으로 pivot으로 쓰면, 입력이 그 패턴에 맞춰져 있을 때(예: 이미 정렬됨) 분할이 한쪽으로 완전히 치우칩니다. 이를 막기 위해 ① 매번 무작위 인덱스를 pivot으로 뽑거나(위 구현), ② 구간의 시작·중간·끝 세 값 중 중앙값을 pivot으로 쓰는 Median-of-Three 전략을 씁니다. 둘 다 특정 입력 패턴에 대해 항상 최악의 분할이 발생하는 것을 확률적/구조적으로 방지합니다.

**최악 O(N²)를 만드는 입력** — pivot을 항상 배열의 첫 원소(또는 마지막 원소)로 고정해서 구현했다면, **이미 정렬되어 있는 배열**(또는 완전히 역순으로 정렬된 배열)을 넣으면 매번 pivot이 그 구간에서 최솟값 또는 최댓값이 되어 분할이 "1개 대 나머지(n-1개)"로 극단적으로 치우칩니다. 이 경우 재귀 깊이가 N이 되고 각 단계마다 O(N)의 비교가 일어나 전체 O(N²)이 됩니다. (위 구현처럼 pivot을 무작위로 뽑으면 특정 입력에 대해 항상 최악이 되는 상황 자체를 피할 수 있습니다.)

**시간복잡도** → 평균 O(N log N), 최악 O(N²) (분할이 매번 한쪽으로 치우칠 때)
**공간복잡도** → O(1) 추가 공간(in-place partition), 재귀 호출 스택은 평균 O(log N)·최악 O(N)

#### 5. 1 ~ 999 까지의 아라비아 숫자가 주어졌을 때, 이 숫자를 로마숫자로 변환하는 프로그램을 작성해 보세요.

```java
class IntToRoman {

    // 값이 큰 것부터 순서대로 정의 — 4, 9 같은 감산 표기(IV, IX 등)까지 포함해두면 분기 없이 처리 가능
    private static final int[] VALUES = {1000, 900, 500, 400, 100, 90, 50, 40, 10, 9, 5, 4, 1};
    private static final String[] SYMBOLS = {"M", "CM", "D", "CD", "C", "XC", "L", "XL", "X", "IX", "V", "IV", "I"};

    static String convert(int num) {
        StringBuilder result = new StringBuilder();

        // 값이 큰 기호부터 차례로, 뺄 수 있는 만큼 계속 빼면서 그 기호를 이어붙임 (그리디)
        for (int i = 0; i < VALUES.length && num > 0; i++) {
            while (num >= VALUES[i]) {
                num -= VALUES[i];
                result.append(SYMBOLS[i]);
            }
        }

        return result.toString();
    }
}
```

**풀이 설명**

로마 숫자는 큰 단위의 기호(M, D, C, L, X, V, I)를 값이 큰 순서대로 그리디하게 채워나가면 만들
수 있습니다. 다만 4, 9, 40, 90, 400, 900처럼 "하나 작은 단위를 앞에 붙여 빼는" 감산 표기가
예외적으로 존재하는데, 이를 별도 분기로 처리하는 대신 `{900, "CM"}`, `{400, "CD"}`,
`{90, "XC"}`, `{40, "XL"}`, `{9, "IX"}`, `{4, "IV"}`를 기본 단위({1000, "M"} 등)와
함께 큰 값부터 정렬된 하나의 표로 미리 정의해두면, 모든 경우를 예외 처리 없이 똑같은 그리디
로직 하나로 처리할 수 있습니다. 값이 큰 항목부터 순서대로 확인하면서, 남은 숫자가 그 값 이상인
동안 계속 빼고 해당 기호를 결과에 이어붙이면 변환이 끝납니다.

**시간복잡도** → O(1) (표의 크기(13개)가 고정이고, 1~999 범위에서 반복 횟수도 최대 상수 번(자리마다 최대 3~4회)으로 제한됨)
**공간복잡도** → O(1) (고정 크기 표 외에 입력 크기에 비례하지 않는 결과 문자열만 사용, 결과 길이도 최대 15자 수준으로 상수)
