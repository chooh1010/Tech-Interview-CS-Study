#### 1. DHCP가 무엇인지 설명해 주세요.

`★★☆` · `심화` · 원본 [네트워크 #8](../03-NETWORK.md)

<details>
<summary><b>꼬리 질문 5개 (펼치기)</b></summary>

- DHCP는 몇 계층 프로토콜인가요?
- DHCP는 어떻게 동작하나요?
- DHCP에서 UDP를 사용하는 이유가 무엇인가요?
- DHCP에서, IP 주소 말고 추가로 제공해주는 정보가 있나요?
- DHCP의 유효기간은 얼마나 긴가요?

</details>

**내 답변**

```
DHCP(Dynamic Host Configuration Protocol)는 네트워크에 새로 접속한 호스트에게 IP 주소와
네트워크 설정 정보를 자동으로 할당해주는 프로토콜입니다. DHCP가 없다면 사용자가 기기마다 IP
주소, 서브넷 마스크, 게이트웨이, DNS 서버 주소를 직접 입력해야 하고, 주소가 겹치는 충돌도 직접
관리해야 합니다. DHCP 서버는 사용 가능한 IP 주소 풀(Pool)을 가지고 있다가 요청이 오면 그중
하나를 일정 기간 동안 빌려주고(임대, Lease), 기간이 끝나거나 반납되면 다시 회수해서 다른 기기에게
줍니다. 덕분에 한정된 IP 주소를 효율적으로 재사용할 수 있고, 카페나 회사처럼 기기가 수시로
들어오고 나가는 환경에서도 별도 설정 없이 바로 네트워크를 쓸 수 있습니다.
```

**꼬리 질문 답변**

- DHCP는 몇 계층 프로토콜인가요?
```
응용 계층(7계층) 프로토콜입니다. IP 주소라는 네트워크 계층의 정보를 다루긴 하지만, DHCP 메시지
자체는 UDP 위에 실려 전송되는 애플리케이션 데이터이기 때문입니다. 서버는 UDP 67번 포트, 클라이언트는
UDP 68번 포트를 사용합니다.
```

- DHCP는 어떻게 동작하나요?
```
DORA라고 부르는 4단계로 동작합니다. 첫째, Discover입니다. 아직 IP가 없는 클라이언트가 출발지
0.0.0.0, 목적지 255.255.255.255로 "DHCP 서버 있나요?"라는 메시지를 브로드캐스트합니다. 둘째,
Offer입니다. 이를 받은 DHCP 서버가 할당 가능한 IP 주소와 설정 정보를 제안합니다. 셋째,
Request입니다. 클라이언트는 받은 제안 중 하나를 골라 "이 IP를 쓰겠다"고 다시 브로드캐스트로
요청합니다. 브로드캐스트로 보내는 이유는 서버가 여러 대일 때 선택받지 못한 다른 서버들도 자신의
제안이 거절됐다는 것을 알고 주소를 회수할 수 있게 하기 위해서입니다. 넷째, Ack입니다. 선택된
서버가 최종 승인하면 클라이언트는 그 IP를 설정하고 사용합니다.

DHCP 서버가 다른 네트워크에 있다면 브로드캐스트가 라우터를 넘지 못하므로, 라우터가 DHCP
Relay Agent 역할을 해서 메시지를 서버로 유니캐스트로 전달해 줍니다.
```

- DHCP에서 UDP를 사용하는 이유가 무엇인가요?
```
가장 큰 이유는 브로드캐스트가 필요하기 때문입니다. 클라이언트는 아직 IP 주소도 없고 DHCP 서버의
주소도 모르기 때문에, 네트워크 전체에 브로드캐스트로 요청해야 합니다. TCP는 특정 상대와 1:1로
3-Way Handshake를 해서 연결을 맺어야 하므로, 상대 주소를 모르고 내 주소도 없는 상황에서는
사용할 수 없습니다. 반면 UDP는 연결 수립 없이 브로드캐스트로 바로 보낼 수 있습니다.

또한 DHCP 메시지는 작고 짧은 요청·응답으로 끝나서 TCP의 연결 관리 비용이 불필요하고, 응답이 없으면
클라이언트가 일정 시간 후 다시 요청하는 방식으로 애플리케이션 레벨에서 재전송을 처리하면 충분합니다.
```

- DHCP에서, IP 주소 말고 추가로 제공해주는 정보가 있나요?
```
네, DHCP 옵션 필드를 통해 네트워크를 쓰는 데 필요한 정보를 함께 제공합니다. 대표적으로 서브넷
마스크, 기본 게이트웨이(라우터) 주소, DNS 서버 주소, 임대 기간(Lease Time), 도메인 이름이 있고,
환경에 따라 NTP(시간) 서버 주소나, 네트워크 부팅(PXE)에 필요한 부팅 서버와 파일 정보 등도
제공할 수 있습니다. 즉 IP만 받아서는 외부와 통신할 수 없기 때문에, 통신에 필요한 설정 일체를
한 번에 받는다고 보면 됩니다.
```

- DHCP의 유효기간은 얼마나 긴가요?
```
정해진 값은 없고 DHCP 서버 관리자가 설정합니다. 윈도우 서버 기본값은 8일이고, 가정용 공유기는
보통 하루~이틀, 카페나 공항처럼 사용자가 자주 바뀌는 곳은 1~2시간처럼 짧게 설정합니다. 짧을수록
주소를 빨리 회수해 재사용할 수 있지만 갱신 트래픽이 늘어납니다.

클라이언트는 임대 기간의 50%(T1)가 지나면 원래 서버에게 유니캐스트로 갱신을 요청하고, 응답이 없으면
87.5%(T2) 시점에 아무 서버에게나 브로드캐스트로 갱신을 요청합니다. 그래도 만료되면 IP를 반납하고
처음부터 DORA 과정을 다시 진행합니다.
```

**핵심 키워드** → DHCP = IP·네트워크 설정 자동 할당, 주소 풀·임대(Lease)·회수로 IP 재사용, 응용 계층(UDP 67/68), DORA(Discover·Offer·Request·Ack, Request도 브로드캐스트하는 이유), DHCP Relay Agent, UDP 이유(IP 없음 + 서버 주소 모름 → 브로드캐스트 필요, TCP 불가), 추가 정보(서브넷 마스크·게이트웨이·DNS·임대 기간), 임대 기간(관리자 설정, T1 50% 갱신·T2 87.5% 재바인딩)

#### 2. IP 주소는 무엇이며, 어떤 기능을 하고 있나요?

`★★☆` · `필수` · 원본 [네트워크 #9](../03-NETWORK.md)

<details>
<summary><b>꼬리 질문 8개 (펼치기)</b></summary>

- IPv6는 IPv4의 주소 고갈 문제를 해결하기 위해 만들어졌지만, 아직도 수많은 기기가 IPv4를 사용하고 있습니다. 고갈 문제를 어떻게 해결할 수 있을까요?
- IPv4와 IPv6의 차이에 대해 설명해 주세요.
- 수많은 사람들이 유동 IP를 사용하고 있지만, 수많은 공유기에서는 고정 주소를 제공하는 기능이 이미 존재합니다. 어떻게 가능한 걸까요?
- IPv4를 사용하는 장비와 IPv6를 사용하는 같은 네트워크 내에서 통신이 가능한가요? 가능하다면 어떤 방법을 사용하나요?
- IP가 송신자와 수신자를 정확하게 전송되는 것을 보장해 주나요?
- IPv4에서 수행하는 Checksum과 TCP에서 수행하는 Checksum은 어떤 차이가 있나요?
- TTL(Hop Limit)이란 무엇인가요?
- IP 주소와 MAC 주소의 차이에 대해 설명해 주세요.

</details>

**내 답변**

```
IP 주소는 네트워크 계층에서 인터넷에 연결된 각 장치를 식별하기 위한 논리적인 주소입니다. 우편
주소처럼, 데이터를 보낼 때 출발지와 목적지를 나타내서 라우터들이 이 주소를 보고 패킷을 목적지까지
전달할 수 있게 합니다.

IP 주소의 기능은 크게 두 가지입니다. 첫째, 식별(Addressing)입니다. 네트워크 부분과 호스트
부분으로 나뉘어 있어서 "어느 네트워크의 어느 호스트인가"를 계층적으로 나타냅니다. 둘째,
경로 지정(Routing)입니다. 이 계층 구조 덕분에 라우터는 모든 호스트의 주소를 알 필요 없이 네트워크
부분(프리픽스)만 보고 다음 경로를 결정할 수 있어, 전 세계 규모의 네트워크에서도 효율적으로 패킷을
전달할 수 있습니다. 현재 32비트의 IPv4와 128비트의 IPv6가 함께 사용되고 있습니다.
```

**꼬리 질문 답변**

- IPv6는 IPv4의 주소 고갈 문제를 해결하기 위해 만들어졌지만, 아직도 수많은 기기가 IPv4를 사용하고 있습니다. 고갈 문제를 어떻게 해결할 수 있을까요?
```
IPv6로 완전히 전환하기 전까지는 IPv4 주소를 아껴 쓰는 기술들로 버티고 있습니다. 가장 효과가 큰
것은 NAT입니다. 내부망에서는 사설 IP를 쓰고 공유기가 하나의 공인 IP로 변환해서 내보내기 때문에,
공인 IP 하나를 수십 대의 기기가 함께 쓸 수 있습니다. 통신사 단위에서는 이를 한 번 더 적용한
CGNAT(Carrier-Grade NAT)으로 여러 가입자가 공인 IP를 공유하기도 합니다.

또한 클래스 단위로 주소를 나눠주던 방식을 CIDR로 바꿔 필요한 만큼만 할당해 낭비를 줄였고, DHCP로
주소를 필요할 때만 빌려주고 회수해서 재사용합니다. 마지막으로 IPv4와 IPv6를 동시에 지원하는
듀얼 스택이나 터널링, 변환 기술로 점진적으로 IPv6 전환을 진행하는 것이 근본적인 해결책입니다.
```

- IPv4와 IPv6의 차이에 대해 설명해 주세요.
```
가장 큰 차이는 주소 길이입니다. IPv4는 32비트로 약 43억 개, IPv6는 128비트로 약 3.4×10^38개의
주소를 표현할 수 있습니다. 표기법도 IPv4는 192.168.0.1처럼 8비트씩 10진수, IPv6는
2001:db8::1처럼 16비트씩 16진수로 쓰고 연속된 0은 ::로 생략합니다.

헤더 구조도 다릅니다. IPv6는 헤더를 40바이트 고정 길이로 단순화하고, 부가 기능은 확장 헤더로
분리했습니다. 또한 헤더 Checksum을 제거하고(상·하위 계층이 이미 검사하므로), 라우터에서의
단편화를 없애 출발지에서만 단편화하도록 해서 라우터의 처리 부담을 줄였습니다. 그 외에 주소가
충분하니 NAT 없이 모든 기기가 공인 주소를 가질 수 있고, DHCP 없이도 라우터 정보로 스스로 주소를
만드는 자동 구성(SLAAC)을 지원하며, 브로드캐스트 대신 멀티캐스트·애니캐스트를 사용하고, IPsec
지원이 기본으로 설계되었습니다.
```

- 수많은 사람들이 유동 IP를 사용하고 있지만, 수많은 공유기에서는 고정 주소를 제공하는 기능이 이미 존재합니다. 어떻게 가능한 걸까요?
```
공유기가 고정으로 주는 것은 공인 IP가 아니라 내부망의 사설 IP이기 때문입니다. 공유기는 내부망의
DHCP 서버 역할을 하는데, 사설 IP 대역(예: 192.168.0.0/24)은 공유기가 독자적으로 관리하는
주소라서 통신사와 상관없이 자유롭게 정할 수 있습니다. 그래서 특정 기기의 MAC 주소와 특정 사설 IP를
묶어두는 DHCP 예약(고정 할당) 기능으로, 그 기기가 DHCP 요청을 보낼 때마다 항상 같은 주소를 줄 수
있습니다.

반면 공유기 자신이 통신사로부터 받는 공인 IP는 여전히 유동 IP라서 바뀔 수 있습니다. 외부에서
고정된 이름으로 접속하고 싶다면, 공인 IP가 바뀔 때마다 도메인에 연결된 IP를 자동으로 갱신해주는
DDNS(Dynamic DNS)를 함께 사용합니다.
```

- IPv4를 사용하는 장비와 IPv6를 사용하는 같은 네트워크 내에서 통신이 가능한가요? 가능하다면 어떤 방법을 사용하나요?
```
두 프로토콜은 헤더 형식이 달라 서로 직접 호환되지 않지만, 전환 기술을 쓰면 통신할 수 있습니다.
첫째, 듀얼 스택(Dual Stack)입니다. 장비가 IPv4와 IPv6 주소를 모두 가지고, 상대에 맞는 프로토콜을
골라 통신합니다. 가장 일반적이고 단순한 방법입니다. 둘째, 터널링(Tunneling)입니다. IPv6 패킷을
IPv4 패킷 안에 통째로 캡슐화해서 IPv4 망을 통과시키고, 반대편에서 꺼내는 방식입니다(6to4 등).
IPv6 섬들이 IPv4 망을 사이에 두고 통신할 때 씁니다. 셋째, 변환(Translation)입니다. NAT64와
DNS64를 사용해서 중간 장비가 IPv6 헤더를 IPv4 헤더로 바꿔주기 때문에, IPv6만 쓰는 기기도
IPv4 전용 서버와 통신할 수 있습니다.
```

- IP가 송신자와 수신자를 정확하게 전송되는 것을 보장해 주나요?
```
보장하지 않습니다. IP는 최선형(Best-Effort) 서비스로, 패킷을 목적지까지 보내기 위해 최선을
다하지만 패킷이 손실되거나, 순서가 뒤바뀌거나, 중복되거나, 지연되는 것에 대해서는 아무것도 보장하지
않습니다. 라우터 큐가 가득 차면 패킷을 그냥 버리고, 각 패킷이 서로 다른 경로로 갈 수도 있습니다.
또한 IP는 출발지 주소를 검증하지도 않아서 출발지 IP를 위조하는 스푸핑도 가능합니다.

이렇게 단순하게 설계한 덕분에 네트워크 중간의 라우터는 빠르게 전달만 하면 되고, 신뢰성이 필요한
경우는 양 끝단의 TCP가 순서 번호, ACK, 재전송으로 책임지는 구조입니다(End-to-End 원칙).
```

- IPv4에서 수행하는 Checksum과 TCP에서 수행하는 Checksum은 어떤 차이가 있나요?
```
검사하는 범위와 검사하는 위치가 다릅니다. IPv4 Checksum은 IP 헤더만 검사하고 데이터(페이로드)는
검사하지 않습니다. 그리고 패킷이 거치는 모든 라우터에서 검사하며, 라우터가 TTL을 1씩 줄여 헤더가
바뀌기 때문에 홉마다 다시 계산합니다. 목적은 헤더의 목적지 주소 등이 손상되어 패킷이 엉뚱한 곳으로
가는 것을 막는 것입니다.

TCP Checksum은 TCP 헤더와 데이터 전체에, 출발지·목적지 IP 등이 담긴 가상 헤더(Pseudo Header)까지
포함해 검사합니다. 그리고 중간 라우터는 관여하지 않고 양 끝 호스트에서만 검사합니다(End-to-End).
목적은 실제 데이터가 손상 없이, 올바른 목적지에 도착했는지 확인하는 것입니다. 이처럼 계층마다
중복 검사가 있어서, IPv6는 라우터 부담을 줄이려고 IP 헤더 Checksum을 아예 없앴습니다.
```

- TTL(Hop Limit)이란 무엇인가요?
```
TTL(Time To Live)은 패킷이 네트워크에서 살아있을 수 있는 수명으로, IP 헤더의 8비트 필드입니다.
이름은 시간이지만 실제로는 거쳐갈 수 있는 라우터 수(홉 수)를 의미해서, IPv6에서는 아예 Hop
Limit이라고 이름을 바꿨습니다. 출발지가 64나 128 같은 초기값을 정해 보내면, 라우터를 하나 지날
때마다 1씩 감소하고, 0이 되면 라우터는 그 패킷을 폐기하고 출발지에 ICMP Time Exceeded 메시지를
보냅니다.

TTL이 필요한 이유는 라우팅 설정 오류로 경로가 순환(루프)하게 되면, 패킷이 영원히 네트워크를 떠돌며
대역폭을 낭비하기 때문입니다. 또한 traceroute는 이 성질을 활용해서, TTL을 1, 2, 3...으로 늘려가며
보내고 각 라우터가 돌려주는 ICMP 메시지로 목적지까지의 경로를 알아냅니다.
```

- IP 주소와 MAC 주소의 차이에 대해 설명해 주세요.
```
IP 주소는 3계층의 논리적 주소이고, MAC 주소는 2계층의 물리적 주소입니다. MAC 주소는 48비트로
제조 시 네트워크 인터페이스 카드(NIC)에 부여되어 원칙적으로 바뀌지 않고, 같은 네트워크 안에서 바로
옆의 장비(다음 홉)에게 프레임을 전달할 때 사용됩니다. IP 주소는 접속한 네트워크에 따라 할당되어
바뀔 수 있고, 최종 목적지까지 여러 네트워크를 거쳐 가는 전체 경로에서 사용됩니다.

그래서 패킷이 라우터를 지날 때마다 IP 주소(출발지와 최종 목적지)는 그대로 유지되지만, MAC 주소는
"이번 구간의 출발지와 다음 홉"으로 매번 바뀝니다. 비유하면 IP 주소는 택배의 최종 배송지 주소이고,
MAC 주소는 각 물류센터 사이를 옮기는 트럭의 다음 도착지입니다. 둘은 ARP로 연결됩니다.
```

**핵심 키워드** → IP 주소 = 3계층 논리 주소, 기능(식별 + 계층적 라우팅), 주소 고갈 대응(NAT·CGNAT·CIDR·DHCP → IPv6 전환), IPv4(32비트·10진) vs IPv6(128비트·16진·40바이트 고정 헤더·Checksum 제거·라우터 단편화 X·SLAAC·멀티캐스트), 공유기 고정 IP = 사설 IP DHCP 예약(MAC 바인딩)·공인 IP는 DDNS, 공존 기술(듀얼 스택·터널링·NAT64/DNS64), IP는 Best-Effort(신뢰성은 TCP, End-to-End), IPv4 Checksum(헤더만·홉마다) vs TCP Checksum(전체+가상 헤더·종단에서만), TTL(홉 수, 0이면 폐기 + ICMP, 루프 방지, traceroute), IP(논리·종단·유지) vs MAC(물리·홉마다 바뀜)

- DNS 쿼리를 통해 얻어진 IP는 어디를 가리키고 있나요?
```
GitHub의 웹 서버 한 대를 직접 가리키기보다는, 대부분 서비스의 진입점을 가리킵니다. 대규모
서비스는 수많은 서버를 두고 있기 때문에, DNS가 돌려주는 IP는 보통 로드밸런서나 리버스 프록시, 또는
CDN 엣지 서버의 IP입니다. 로드밸런서는 그 IP로 들어온 요청을 뒤쪽의 여러 서버 중 하나로 나눠
보내고, CDN은 사용자와 가까운 엣지 서버에서 캐시된 정적 파일을 바로 응답합니다.

또한 같은 IP를 전 세계 여러 위치에서 동시에 광고하는 애니캐스트(Anycast)를 쓰면 같은 IP라도
사용자와 가장 가까운 데이터센터로 연결되고, DNS 서버가 질의한 사용자의 위치에 따라 서로 다른 IP를
돌려주는 GeoDNS를 쓰기도 합니다. 그래서 같은 도메인이라도 사용자마다 다른 서버로 연결될 수 있습니다.
```

- Web Server와 Web Application Server의 차이에 대해 설명해 주세요.
```
Web Server는 HTML, CSS, JS, 이미지처럼 미리 만들어진 정적 콘텐츠를 HTTP 요청에 맞춰 그대로
응답하는 서버입니다. Nginx, Apache가 대표적입니다. WAS(Web Application Server)는 요청마다
DB를 조회하거나 비즈니스 로직을 실행해서 결과를 동적으로 만들어 응답하는 서버로, Tomcat, Jetty
등이 있습니다.

둘을 분리하는 이유는 역할에 맞게 부하를 나누기 위해서입니다. 정적 파일은 웹 서버가 빠르게 처리하고
동적 요청만 WAS로 넘기면, 상대적으로 무거운 WAS의 자원을 아낄 수 있습니다. 또한 웹 서버를
앞단에 두면 리버스 프록시로 WAS를 외부에 직접 노출하지 않아 보안이 좋아지고, SSL 처리, 로드밸런싱,
캐싱을 맡길 수 있으며, WAS 하나가 죽어도 다른 WAS로 요청을 넘길 수 있습니다.
```

- URL, URI, URN은 어떤 차이가 있나요?
```
URI(Uniform Resource Identifier)는 자원을 식별하는 문자열 전체를 가리키는 가장 큰 개념입니다.
그 하위에 두 가지 방식이 있습니다. URL(Locator)은 자원의 "위치"로 식별하는 방식으로,
https://github.com/user/repo처럼 프로토콜과 주소로 어디에 가서 어떻게 가져올지를 나타냅니다.
URN(Name)은 위치와 상관없이 자원의 고유한 "이름"으로 식별하는 방식으로, 책의 ISBN을 나타내는
urn:isbn:0451450523이 예입니다. 위치가 바뀌어도 이름은 그대로라는 장점이 있지만, 이름만으로
자원을 찾아가는 체계가 거의 보급되지 않아 실제로는 대부분 URL을 쓰고, 그래서 URI와 URL이 사실상
같은 의미로 쓰이는 경우가 많습니다. 즉 모든 URL은 URI이지만, 모든 URI가 URL인 것은 아닙니다.
```

**내 답변**

```
DNS(Domain Name System)는 사람이 기억하기 쉬운 도메인 이름(www.github.com)을 컴퓨터가 통신에
사용하는 IP 주소로 변환해주는 시스템입니다. 인터넷 전체의 도메인을 서버 한 대가 관리할 수는 없기
때문에, 계층적인 분산 데이터베이스 구조로 되어 있습니다. 가장 위에 루트(.) DNS 서버가 있고, 그 아래
.com, .kr 같은 TLD(Top-Level Domain) 서버, 그 아래 github.com처럼 각 도메인의 정보를 실제로
가진 권한 있는(Authoritative) DNS 서버가 있습니다. 각 서버는 자신이 모르는 하위 도메인에 대해
"누구에게 물어보라"고 알려주는 식으로 책임을 나눕니다.

사용자의 요청은 보통 통신사 등이 운영하는 로컬 DNS 서버(Recursive Resolver)가 대신 받아 이
계층을 차례로 질의하고, 결과를 TTL 동안 캐싱해서 이후 같은 질의에 빠르게 응답합니다. DNS 덕분에
서버의 IP가 바뀌어도 사용자는 같은 이름으로 접속할 수 있고, 하나의 이름에 여러 IP를 매핑해 부하를
나눌 수도 있습니다.
```

**꼬리 질문 답변**

- DNS는 몇 계층 프로토콜인가요?
```
응용 계층(7계층) 프로토콜입니다. 도메인 이름을 IP로 변환하는 일 자체는 네트워크 통신을 돕는
기능이지만, DNS 메시지는 UDP·TCP 53번 포트 위에서 주고받는 애플리케이션 데이터이기 때문입니다.
```

- UDP와 TCP 중 어떤 것을 사용하나요?
```
기본적으로 UDP 53번 포트를 사용합니다. DNS 질의와 응답은 대부분 크기가 작고 한 번 주고받으면 끝나기
때문에, 3-Way Handshake와 연결 관리 비용이 드는 TCP보다 UDP가 훨씬 빠르고, 수많은 클라이언트를
상대하는 DNS 서버의 자원 부담도 적습니다. 손실이 나면 클라이언트가 다시 보내면 됩니다.

다만 TCP도 사용합니다. 응답이 UDP로 보낼 수 있는 크기(전통적으로 512바이트, EDNS로 확장 가능)를
넘으면 서버가 응답에 잘림(TC) 플래그를 세팅하고, 클라이언트는 TCP로 다시 질의합니다. DNSSEC처럼
서명이 포함되어 응답이 커질 때가 그렇습니다. 또한 주 DNS 서버의 전체 데이터를 보조 서버로
복제하는 영역 전송(Zone Transfer)은 대용량이고 신뢰성이 중요하므로 TCP를 사용합니다. 최근에는
보안을 위해 DNS over HTTPS(DoH)나 DNS over TLS(DoT)도 쓰입니다.
```

- DNS Recursive Query, Iterative Query가 무엇인가요?
```
Recursive Query(재귀적 질의)는 질의를 받은 서버가 "최종 답"을 책임지고 찾아서 돌려주는 방식입니다.
클라이언트(내 PC)가 로컬 DNS 서버에 보내는 질의가 이 방식으로, 클라이언트는 한 번 묻고 최종 IP만
받으면 됩니다.

Iterative Query(반복적 질의)는 질의를 받은 서버가 답을 모르면 직접 찾아주지 않고 "다음에 물어볼
서버"만 알려주는 방식입니다. 로컬 DNS 서버가 루트 서버에 물으면 루트는 ".com TLD 서버에 물어봐라",
TLD 서버는 "github.com의 권한 있는 서버에 물어봐라"라고 알려주고, 로컬 DNS 서버가 이를 따라가며
반복해서 질의해 최종 답을 얻습니다. 루트나 TLD 서버가 재귀적으로 일을 대신해주면 엄청난 부하가
몰리기 때문에, 상위 서버들은 Iterative 방식으로 길만 알려주고, 실제 탐색 부담은 로컬 DNS 서버가
지는 구조입니다.
```

- DNS 쿼리 과정에서 손실이 발생한다면, 어떻게 처리하나요?
```
DNS는 UDP를 사용하므로 전송 계층에서 재전송을 해주지 않습니다. 그래서 DNS 클라이언트(리졸버)가
애플리케이션 레벨에서 직접 처리합니다. 질의를 보낸 후 정해진 시간(보통 수 초) 안에 응답이 없으면
같은 질의를 다시 보내고, 여러 번 실패하면 설정된 다른 DNS 서버(보조 DNS)로 질의합니다. 각 질의에는
16비트 ID가 있어서, 재전송으로 응답이 여러 번 와도 어느 질의에 대한 응답인지 매칭할 수 있습니다.
또한 루트·TLD 같은 상위 서버도 여러 대가 존재하고 애니캐스트로 운영되어, 일부 서버가 응답하지 않아도
다른 서버에 물을 수 있습니다.
```

- 캐싱된 DNS 쿼리가 잘못 될 수도 있습니다. 이 경우, 어떻게 에러를 보정할 수 있나요?
```
기본 장치는 TTL입니다. 모든 DNS 레코드에는 캐시 유효 시간인 TTL이 있어서, 서버의 IP가 바뀌어
캐시가 잘못된 정보를 갖고 있어도 TTL이 지나면 자동으로 버려지고 새로 조회합니다. 그래서 서버
이전을 앞두고는 미리 TTL을 짧게 줄여두어, 변경 후 잘못된 캐시가 빨리 사라지게 합니다. 급하게 바로
고쳐야 한다면 클라이언트에서 직접 캐시를 비울 수 있습니다(윈도우의 ipconfig /flushdns, 브라우저의
DNS 캐시 삭제). 공용 DNS(구글, Cloudflare)는 캐시를 지워달라고 요청하는 기능도 제공합니다.

캐시가 "잘못된" 원인이 공격자가 위조 응답을 주입하는 DNS 캐시 포이즈닝이라면, 질의 ID와 출발지
포트를 무작위화해서 위조 응답을 맞추기 어렵게 하고, 근본적으로는 DNSSEC으로 응답에 전자 서명을 붙여
위·변조 여부를 검증합니다.
```

- DNS 레코드 타입 중 A, CNAME, AAAA의 차이에 대해서 설명해주세요.
```
A 레코드는 도메인 이름을 IPv4 주소에 매핑합니다(github.com → 140.82.112.3). AAAA 레코드는
도메인을 IPv6 주소에 매핑합니다. IPv6 주소가 IPv4의 4배(128비트)라서 A를 4개 붙인 이름입니다.

CNAME(Canonical Name) 레코드는 도메인을 IP가 아닌 다른 도메인 이름에 매핑하는 별칭입니다. 예를
들어 www.example.com을 example.com의 CNAME으로 등록하면, www를 조회했을 때 example.com을
다시 조회해서 IP를 얻습니다. IP가 바뀌어도 원본 도메인의 A 레코드만 고치면 되고, AWS나 CDN처럼
IP가 자주 바뀌는 외부 서비스의 도메인을 연결할 때 유용합니다. 다만 조회가 한 번 더 일어나고,
CNAME이 있는 이름에는 다른 레코드를 함께 둘 수 없어서 example.com 같은 루트 도메인에는 쓸 수
없습니다.
```

- hosts 파일은 어떤 역할을 하나요? DNS와 비교하였을 때 어떤 것이 우선순위가 더 높나요?
```
hosts 파일은 도메인 이름과 IP 주소의 매핑을 로컬 컴퓨터에 직접 적어두는 텍스트 파일입니다(리눅스
/etc/hosts, 윈도우 C:\Windows\System32\drivers\etc\hosts). DNS가 생기기 전에는 이 파일 하나를
모두가 공유해서 이름을 변환했고, 지금은 개발 중에 특정 도메인을 로컬 서버나 테스트 서버로 연결하거나,
특정 사이트를 127.0.0.1로 연결해 차단하는 용도로 씁니다.

일반적으로 hosts 파일이 DNS보다 우선순위가 높습니다. OS는 이름을 변환할 때 hosts 파일을 먼저
확인하고, 없을 때만 DNS 서버에 질의합니다. (리눅스는 /etc/nsswitch.conf의 순서로 이를 바꿀 수
있습니다.) 이 때문에 악성코드가 hosts 파일을 변조해 은행 사이트를 피싱 서버로 연결하는 파밍
공격에 악용되기도 합니다.
```

**핵심 키워드** → DNS = 도메인 → IP 변환, 계층적 분산 DB(루트·TLD·권한 있는 DNS), 로컬 DNS(Recursive Resolver)·TTL 캐싱, 응용 계층(53번 포트), 기본 UDP(작고 빠름) + TCP(응답 크기 초과 TC 플래그·영역 전송), DoH/DoT, Recursive(클라이언트↔로컬 DNS, 최종 답) vs Iterative(로컬 DNS↔상위 서버, 다음 서버만 알려줌), 손실 처리(리졸버 타임아웃 재전송·보조 DNS·질의 ID), 잘못된 캐시(TTL 만료·이전 전 TTL 단축·flushdns, 캐시 포이즈닝 → ID/포트 랜덤화·DNSSEC), A(IPv4)·AAAA(IPv6)·CNAME(별칭, 루트 도메인 불가), hosts 파일(로컬 매핑, DNS보다 우선, 파밍)

**내 답변**

```
SOP(Same-Origin Policy, 동일 출처 정책)는 브라우저가 적용하는 보안 정책으로, 한 출처(Origin)에서
불러온 문서나 스크립트가 다른 출처의 자원에 접근하는 것을 제한합니다. 출처는 프로토콜(스킴), 호스트,
포트 세 가지로 정의되며, 셋 중 하나라도 다르면 다른 출처입니다. 예를 들어 https://a.com과
http://a.com(프로토콜), https://api.a.com(호스트), https://a.com:8080(포트)은 모두 다른
출처입니다.

이 정책이 필요한 이유는, 사용자가 악성 사이트에 접속했을 때 그 사이트의 스크립트가 사용자의 브라우저에
남아 있는 쿠키(로그인 정보)를 이용해 은행 사이트에 요청을 보내고 그 응답(계좌 정보 등)을 읽어가는
것을 막기 위해서입니다. 핵심은 다른 출처로 "요청을 보내는 것" 자체보다, 다른 출처의 "응답을 스크립트가
읽는 것"을 막는다는 점입니다. 또한 <img>, <script>, <link>로 다른 출처의 자원을 불러오는 것은
허용되며, 제한되는 대상은 주로 fetch·XMLHttpRequest 같은 스크립트 요청의 응답 읽기, 다른 출처
iframe의 DOM 접근, 쿠키·스토리지 접근입니다.
```

**꼬리 질문 답변**

- CORS 정책이 무엇인가요?
```
CORS(Cross-Origin Resource Sharing, 교차 출처 리소스 공유)는 SOP의 예외를 안전하게 허용하기 위한
메커니즘입니다. 프론트엔드(https://web.com)와 API 서버(https://api.com)를 분리하는 요즘 구조에서는
다른 출처로의 요청이 꼭 필요한데, SOP만 있으면 응답을 읽을 수 없기 때문입니다.

동작 방식은 서버가 HTTP 응답 헤더로 허용 여부를 알려주는 것입니다. 브라우저는 다른 출처로 요청할 때
Origin 헤더에 현재 출처를 담아 보내고, 서버는 응답에 Access-Control-Allow-Origin 헤더로 허용할
출처를 담아 보냅니다. 브라우저는 이 값이 현재 출처와 일치할 때만 스크립트에 응답을 넘겨주고, 아니면
CORS 에러를 냅니다. 즉 허용 여부는 서버가 결정하고 검사는 브라우저가 하기 때문에, Postman이나 서버
간 통신처럼 브라우저가 아닌 환경에서는 CORS가 적용되지 않습니다. 쿠키를 함께 보내려면
Access-Control-Allow-Credentials: true가 필요하고, 이때는 Allow-Origin에 와일드카드(*)를 쓸 수
없고 정확한 출처를 지정해야 합니다.
```

- Preflight에 대해 설명해 주세요.
```
Preflight(사전 요청)는 실제 요청을 보내기 전에, 서버가 이 교차 출처 요청을 허용하는지 미리 확인하기
위해 브라우저가 자동으로 보내는 OPTIONS 메서드 요청입니다. 요청 헤더에 Origin과 함께, 실제로 사용할
메서드(Access-Control-Request-Method)와 헤더(Access-Control-Request-Headers)를 담아 보내고,
서버가 Access-Control-Allow-Methods, Allow-Headers 등으로 허용한다고 응답하면 그때 실제 요청을
보냅니다.

Preflight가 필요한 이유는, PUT이나 DELETE처럼 서버의 데이터를 바꾸는 요청은 응답을 막더라도 요청이
서버에 도달하는 순간 이미 부작용이 일어나기 때문입니다. CORS를 모르는 오래된 서버를 보호하기 위해,
"이런 요청 보내도 되나요?"라고 먼저 묻는 것입니다. 반면 GET, HEAD, POST 메서드이면서
Content-Type이 application/x-www-form-urlencoded, multipart/form-data, text/plain 중
하나인 "단순 요청(Simple Request)"은 원래 HTML form으로도 보낼 수 있던 요청이라 Preflight 없이
바로 보냅니다. 그래서 application/json으로 POST하면 Preflight가 발생합니다. Preflight 결과는
Access-Control-Max-Age 동안 캐싱해서 매번 보내지 않도록 할 수 있습니다.
```

**핵심 키워드** → SOP = 같은 출처(프로토콜·호스트·포트)만 접근 허용, 목적(악성 스크립트가 쿠키로 요청 후 응답 읽기 방지), 요청 자체보다 응답 읽기를 막음, img·script 태그는 허용, CORS(서버가 응답 헤더로 허용·브라우저가 검사, Origin ↔ Access-Control-Allow-Origin, Credentials 시 * 불가, 브라우저 밖에선 무관), Preflight(OPTIONS 사전 요청, 부작용 있는 요청 보호, 단순 요청은 생략, JSON POST는 발생, Max-Age 캐싱)

**내 답변**

```
로드밸런서는 클라이언트의 요청을 여러 대의 서버에 적절히 분산시켜 주는 장치 또는 소프트웨어입니다.
트래픽이 늘어날 때 서버 한 대의 성능을 높이는 스케일 업에는 비용과 한계가 있기 때문에, 서버 대수를
늘리는 스케일 아웃을 하게 되는데, 이때 늘어난 서버들에게 요청을 나눠주는 역할을 로드밸런서가 합니다.

클라이언트는 로드밸런서의 주소(VIP) 하나만 알고 접속하고, 로드밸런서가 뒤쪽의 서버 중 하나를 골라
요청을 전달합니다. 이를 통해 특정 서버에 부하가 몰리는 것을 막아 성능을 높이고, 서버 중 일부가
장애가 나도 정상 서버로만 요청을 보내 서비스가 계속 유지되게 하는 고가용성을 확보할 수 있습니다.
또한 서버를 추가·제거하거나 무중단 배포를 할 때도 사용자에게 영향 없이 처리할 수 있고, SSL 종료(SSL
Termination)처럼 공통 작업을 대신 맡기도 합니다. 로드밸런서 자체가 단일 장애점이 되지 않도록 보통
이중화(Active-Standby)해서 운영합니다.
```

**꼬리 질문 답변**

- L4 로드밸런서와, L7 로드밸런서의 차이에 대해 설명해 주세요.
```
어느 계층의 정보를 보고 분산하느냐의 차이입니다. L4 로드밸런서는 전송 계층의 정보인 IP 주소와 포트
번호만 보고 요청을 분산합니다. 패킷의 내용을 열어보지 않기 때문에 빠르고 처리량이 높으며, TCP·UDP
어떤 프로토콜이든 처리할 수 있습니다. 대신 "이 요청이 어떤 URL로 가는지"는 모르기 때문에 세밀한
분산은 할 수 없습니다. AWS의 NLB가 대표적입니다.

L7 로드밸런서는 응용 계층의 정보인 HTTP URL 경로, 헤더, 쿠키 등을 보고 분산합니다. 예를 들어
/api 요청은 API 서버로, /images 요청은 이미지 서버로 보내는 경로 기반 라우팅이나, 쿠키를 보고 같은
사용자를 같은 서버로 보내는 스티키 세션, 비정상적인 요청을 걸러내는 보안 기능(WAF)이 가능합니다.
대신 TLS를 복호화하고 HTTP를 파싱해야 해서 L4보다 처리 비용이 큽니다. AWS의 ALB, Nginx가
대표적입니다.
```

- 로드밸런서 알고리즘에 대해 설명해 주세요.
```
라운드 로빈(Round Robin)은 서버들에게 순서대로 돌아가며 요청을 배분합니다. 단순하지만 서버 성능이나
요청 처리 시간이 다르면 부하가 고르지 않을 수 있습니다. 가중 라운드 로빈(Weighted Round Robin)은
서버마다 가중치를 줘서 성능이 좋은 서버에 더 많이 배분합니다.

최소 연결(Least Connection)은 현재 연결 수가 가장 적은 서버로 보냅니다. 요청 처리 시간이 들쭉날쭉하거나
연결이 오래 유지되는 경우에 적합합니다. 최소 응답 시간(Least Response Time)은 응답이 가장 빠른 서버로
보냅니다.

IP 해시(IP Hash)는 클라이언트 IP를 해시해서 서버를 정하기 때문에, 같은 클라이언트는 항상 같은 서버로
갑니다. 세션 유지에 유리하지만, 서버 수가 바뀌면 대부분의 매핑이 바뀌는 문제가 있어 일관된
해싱(Consistent Hashing)으로 보완하기도 합니다.
```

- 로드밸런싱 대상이 되는 장치중 일부 장치가 문제가 생겨 접속이 불가능하다고 가정해 봅시다. 이 경우, 로드밸런서가 해당 장비로 요청을 보내지 않도록 하려면 어떻게 해야 할까요?
```
헬스 체크(Health Check)를 사용합니다. 로드밸런서가 주기적으로 각 서버에 상태 확인 요청을 보내고,
정상 응답이 오지 않는 서버를 대상 목록에서 제외합니다. 확인 방식은 L4 수준에서 TCP 연결이 맺어지는지
보거나, L7 수준에서 /health 같은 엔드포인트에 HTTP 요청을 보내 200 OK가 오는지 확인합니다.
L7 헬스 체크는 프로세스는 살아 있지만 DB 연결이 끊긴 것처럼 애플리케이션이 실제로는 동작하지 않는
상황까지 잡아낼 수 있습니다.

일시적인 지연으로 멀쩡한 서버가 빠지는 것을 막기 위해 "연속 3번 실패하면 제외, 연속 2번 성공하면
복귀"처럼 임계값을 두고, 서버가 복구되면 자동으로 다시 목록에 포함시킵니다. 또한 서버를 제외할 때 이미
처리 중인 요청은 끝낼 수 있도록 일정 시간 기다리는 연결 드레이닝(Connection Draining)을 적용하면,
배포나 장애 시에도 진행 중이던 요청이 끊기지 않습니다.
```

- 로드밸런서 장치를 사용하지 않고, DNS를 활용해서 유사하게 로드밸런싱을 하는 방법에 대해 설명해 주세요.
```
DNS 라운드 로빈을 사용할 수 있습니다. 하나의 도메인에 여러 서버의 IP를 A 레코드로 등록해두면, DNS
서버가 질의할 때마다 IP 목록의 순서를 바꿔서 응답하고, 클라이언트는 보통 첫 번째 IP로 접속하기 때문에
요청이 여러 서버로 분산됩니다. 별도 장비 없이 간단하게 구현할 수 있다는 장점이 있습니다.

하지만 한계가 있습니다. DNS 응답은 로컬 DNS 서버와 클라이언트에 TTL 동안 캐싱되므로 실제 분산이
고르지 않고, 서버가 죽어도 DNS는 이를 모르기 때문에 장애 서버의 IP를 계속 알려줄 수 있습니다(헬스
체크 부재). 이를 보완하기 위해 AWS Route 53 같은 관리형 DNS는 헬스 체크를 해서 장애 서버의 IP를
응답에서 빼주고, 사용자 위치에 따라 가장 가까운 서버의 IP를 주는 지리 기반 라우팅(GeoDNS)이나,
가중치 기반 라우팅을 제공합니다. 실무에서는 DNS로 지역(데이터센터) 단위 분산을, 그 안에서는
로드밸런서로 서버 단위 분산을 하는 식으로 함께 씁니다.
```

**핵심 키워드** → 로드밸런서 = 여러 서버로 요청 분산, 스케일 아웃, VIP, 성능·고가용성·무중단 배포·SSL 종료, LB 이중화, L4(IP·포트, 빠름, NLB) vs L7(URL·헤더·쿠키, 경로 라우팅·스티키 세션·WAF, ALB·Nginx), 알고리즘(라운드 로빈·가중 라운드 로빈·최소 연결·최소 응답 시간·IP 해시·일관된 해싱), 헬스 체크(TCP/HTTP, 실패·복귀 임계값, 연결 드레이닝), DNS 라운드 로빈(여러 A 레코드, TTL 캐싱·헬스 체크 부재 한계 → Route 53 헬스 체크·GeoDNS·가중치)

- CSRF랑 XSS는 어떤 차이가 있나요?
- XSS는 프론트엔드에서만 막을 수 있나요?

</details>

**내 답변**

```
XSS(Cross-Site Scripting)는 공격자가 웹 페이지에 악성 스크립트를 삽입해서, 그 페이지를 방문한 다른
사용자의 브라우저에서 스크립트가 실행되도록 하는 공격입니다. 스크립트가 정상 사이트의 출처에서 실행되기
때문에 SOP를 우회해서, 사용자의 쿠키나 세션 토큰을 탈취하거나, 사용자인 척 요청을 보내거나, 페이지를
변조해 피싱 화면을 띄울 수 있습니다.

종류는 세 가지입니다. 저장형(Stored) XSS는 게시판 글이나 댓글처럼 서버 DB에 악성 스크립트가 저장되어,
그 글을 조회하는 모든 사용자에게 실행됩니다. 피해 범위가 가장 넓습니다. 반사형(Reflected) XSS는 URL
파라미터에 스크립트를 넣은 링크를 사용자가 클릭하게 하면, 서버가 그 입력을 검색 결과 등에 그대로
반사해서 응답에 포함시켜 실행되는 방식입니다. DOM 기반 XSS는 서버를 거치지 않고, 클라이언트의
자바스크립트가 URL 해시 등의 입력을 innerHTML 같은 곳에 그대로 넣으면서 실행되는 방식입니다.

방어의 핵심은 사용자 입력을 코드가 아닌 데이터로만 다루는 것입니다. 출력 시 <, >, " 같은 문자를
&lt; 같은 HTML 엔티티로 바꾸는 이스케이프 처리를 하고, HTML 입력을 허용해야 한다면 허용된 태그만
남기는 화이트리스트 기반 필터링(DOMPurify 등)을 하며, 쿠키에 HttpOnly 속성을 줘서 스크립트로
읽을 수 없게 하고, CSP(Content Security Policy) 헤더로 허가된 출처의 스크립트만 실행되게 합니다.
```

**꼬리 질문 답변**

- CSRF랑 XSS는 어떤 차이가 있나요?
```
CSRF(Cross-Site Request Forgery)는 사용자가 로그인한 상태에서 공격자가 만든 페이지에 접속하면,
그 페이지가 사용자 모르게 대상 사이트로 요청(비밀번호 변경, 송금 등)을 보내게 만드는 공격입니다.
브라우저가 요청에 대상 사이트의 쿠키를 자동으로 붙이기 때문에, 서버는 사용자의 정상 요청으로 착각합니다.

차이는 공격이 무엇을 악용하느냐입니다. XSS는 "사용자가 사이트를 신뢰하는 것"을 악용해서, 사이트
안에서 공격자의 스크립트를 실행시킵니다. 그래서 응답을 읽거나 쿠키를 탈취하는 등 할 수 있는 것이 훨씬
많습니다. CSRF는 "사이트가 사용자의 브라우저(쿠키)를 신뢰하는 것"을 악용해서, 사용자의 권한으로
요청만 위조합니다. 스크립트를 실행하지는 않으며, SOP 때문에 응답도 읽을 수 없고 상태를 바꾸는 요청을
일으키는 것이 목적입니다.

방어 방법도 다릅니다. CSRF는 요청마다 예측 불가능한 CSRF 토큰을 넣어 서버가 검증하거나, 쿠키에
SameSite 속성을 줘서 다른 사이트에서 시작된 요청에는 쿠키가 붙지 않게 하고, Referer·Origin 헤더를
검사합니다. 참고로 XSS가 뚫리면 공격자가 페이지 안에서 CSRF 토큰도 읽을 수 있어서, CSRF 방어도
무력화됩니다.
```

- XSS는 프론트엔드에서만 막을 수 있나요?
```
아니요, 오히려 프론트엔드에서만 막아서는 안 되고 서버와 함께 막아야 합니다. 프론트엔드의 입력값 검증은
사용자가 개발자 도구나 Postman으로 요청을 직접 보내면 쉽게 우회되므로 보안 수단이 될 수 없습니다.
특히 저장형·반사형 XSS는 서버가 입력을 저장하거나 응답에 포함시키면서 발생하기 때문에 서버의 책임이
큽니다.

서버 측에서는 입력값을 검증하고, 서버에서 HTML을 렌더링할 때 템플릿 엔진의 자동 이스케이프(Thymeleaf의
th:text 등)를 사용하거나 Lucy-XSS-Filter 같은 라이브러리로 필터링합니다. 또한 응답 헤더로 막는
방법도 서버의 몫입니다. 쿠키에 HttpOnly를 설정하고, CSP 헤더로 인라인 스크립트와 허가되지 않은
출처의 스크립트 실행을 막습니다.

프론트엔드에서는 innerHTML 대신 textContent를 쓰고, React처럼 기본적으로 이스케이프해주는
프레임워크를 쓰되 dangerouslySetInnerHTML 같은 우회 기능을 조심하며, DOM 기반 XSS를 막습니다.
결국 입력, 저장, 출력의 모든 단계에서 여러 겹으로 막는 심층 방어가 필요합니다.
```

**핵심 키워드** → XSS = 악성 스크립트 삽입 → 다른 사용자 브라우저에서 실행(SOP 우회, 쿠키 탈취·위장 요청·페이지 변조), 저장형·반사형·DOM 기반, 방어(출력 이스케이프·화이트리스트 필터·HttpOnly·CSP), CSRF(쿠키 자동 전송 악용, 요청만 위조·응답 못 읽음) vs XSS(스크립트 실행, 더 강력), CSRF 방어(토큰·SameSite·Origin 검사), XSS 뚫리면 CSRF 방어도 무력화, 프론트 검증은 우회 가능 → 서버(입력 검증·템플릿 자동 이스케이프·HttpOnly·CSP) + 프론트(textContent·React 이스케이프) 심층 방어

#### 8. 인증과 인가의 차이에 대해 설명해 주세요.

<details>
<summary><b>꼬리 질문 1개 (펼치기)</b></summary>

- OAuth가 무엇인지 설명하고, 이것은 인증인지 인가인지에 대해 설명해 주세요.

**내 답변**

```
인증(Authentication)은 "당신이 누구인지" 확인하는 과정이고, 인가(Authorization)는 "당신이 이것을
해도 되는지" 권한을 확인하는 과정입니다. 로그인할 때 아이디·비밀번호로 본인임을 증명하는 것이
인증이고, 로그인한 사용자가 관리자 페이지에 접근하거나 다른 사람의 글을 삭제하려 할 때 그 권한이
있는지 확인하는 것이 인가입니다.

순서상 인증이 먼저입니다. 누구인지 알아야 그 사람에게 어떤 권한이 있는지 판단할 수 있기 때문입니다.
HTTP 응답 코드도 이를 구분하는데, 인증에 실패하면 401 Unauthorized, 인증은 됐지만 권한이 없으면
403 Forbidden을 반환합니다. Spring Security에서도 인증은 AuthenticationManager가, 인가는
역할(Role)이나 권한 기반으로 AuthorizationFilter가 처리하는 식으로 단계를 분리합니다.
```

**꼬리 질문 답변**

- OAuth가 무엇인지 설명하고, 이것은 인증인지 인가인지에 대해 설명해 주세요.
```
OAuth는 사용자가 자신의 비밀번호를 제3의 서비스에 알려주지 않고도, 그 서비스가 구글이나 카카오 같은
다른 서비스에 있는 자신의 자원(프로필, 캘린더 등)에 접근할 수 있도록 권한을 위임하는 표준
프로토콜입니다. 현재는 OAuth 2.0이 주로 쓰입니다.

대표적인 Authorization Code 방식은 다음과 같습니다. 사용자가 "구글로 로그인"을 누르면 구글
인증 서버로 이동해 로그인하고, "이 서비스가 내 이메일과 프로필을 보도록 허용"하는 데 동의합니다.
그러면 구글은 서비스에게 일회용 Authorization Code를 돌려주고, 서비스의 서버는 이 코드를 자신의
Client Secret과 함께 구글에 보내 Access Token으로 교환합니다. 이후 서비스는 이 Access Token으로
허용된 범위(Scope) 안에서만 구글 API를 호출합니다.

OAuth는 본질적으로 인가(Authorization) 프로토콜입니다. Access Token은 "이 범위의 자원에 접근해도
된다"는 권한을 나타낼 뿐, 토큰을 가진 사람이 누구인지를 증명하도록 설계된 것이 아니기 때문입니다.
그런데 실제로는 "소셜 로그인"이라는 인증 용도로 많이 쓰여서 혼동되는데, 이는 Access Token으로
프로필 정보를 조회해 사용자를 식별하는 방식으로 인증을 흉내 내는 것입니다. 이 문제를 표준적으로
해결하기 위해 OAuth 2.0 위에 인증 계층을 얹은 것이 OIDC(OpenID Connect)로, 사용자 정보를 담아
서명한 ID Token(JWT)을 함께 발급해 인증을 제공합니다.
```

**핵심 키워드** → 인증(Authentication, 누구인가) vs 인가(Authorization, 권한이 있는가), 인증이 먼저, 401(인증 실패) vs 403(권한 없음), OAuth 2.0 = 비밀번호 없이 권한 위임, Authorization Code 흐름(동의 → Code → 서버가 Secret과 함께 Access Token 교환 → Scope 내 API 호출), OAuth는 인가 프로토콜, 소셜 로그인은 인증을 흉내 냄 → OIDC(ID Token)로 인증 표준화

#### 9. JWT 인증 방식이 무엇인가요?

`★★☆` · `필수` · 원본 [개발상식·기타 #14](../05-ETC.md)

<details>
<summary><b>꼬리 질문 3개 (펼치기)</b></summary>

- Signature는 어떻게 만들어지나요?
- 만약 Access Token이 탈취되면, 어떻게 대응할 수 있을까요?
- 반대로 Refresh Token이 탈취되면, 어떻게 대응해야 할까요?

</details>

**내 답변**

```
JWT(JSON Web Token)는 사용자 정보와 권한 같은 데이터(Claim)를 JSON으로 담고, 서버가 서명해서
위·변조를 검증할 수 있게 만든 토큰입니다. Header.Payload.Signature 세 부분을 각각 Base64URL로
인코딩해서 점(.)으로 이어 붙인 형태입니다. Header에는 토큰 타입과 서명 알고리즘, Payload에는
사용자 ID, 권한, 만료 시간(exp) 같은 Claim, Signature에는 앞의 두 부분이 변조되지 않았음을
증명하는 서명이 들어갑니다.

JWT 인증 방식은 사용자가 로그인하면 서버가 JWT를 발급하고, 클라이언트는 이후 요청마다 Authorization:
Bearer <토큰> 헤더에 담아 보냅니다. 서버는 서명만 검증하면 별도 저장소 조회 없이 토큰 안의 정보로
사용자를 식별할 수 있습니다. 세션 방식처럼 서버에 상태를 저장하지 않는 Stateless 방식이라, 서버를
여러 대로 늘려도 세션 공유 문제가 없고 확장에 유리합니다.

단점도 있습니다. Payload는 암호화가 아니라 인코딩일 뿐이라 누구나 디코딩해서 볼 수 있으므로 비밀번호
같은 민감 정보를 넣으면 안 되고, 세션보다 크기가 커서 매 요청 트래픽이 늘어납니다. 가장 큰 문제는
서버가 상태를 갖지 않기 때문에 한 번 발급한 토큰을 만료 전에 강제로 무효화하기 어렵다는 점입니다.
그래서 Access Token의 만료 시간을 짧게 두고, 수명이 긴 Refresh Token으로 재발급받는 구조를 함께
씁니다.
```

**꼬리 질문 답변**

- Signature는 어떻게 만들어지나요?
```
인코딩된 Header와 Payload를 점으로 이은 문자열(base64UrlEncode(header) + "." +
base64UrlEncode(payload))을, Header에 명시된 알고리즘과 서버의 키로 서명해서 만듭니다.

HS256 같은 대칭키 방식은 서버만 아는 비밀키로 HMAC-SHA256 해시를 계산합니다. 검증할 때 서버는 받은
Header와 Payload로 같은 계산을 다시 해서 Signature와 일치하는지 비교합니다. 공격자가 Payload의
권한을 admin으로 바꾸면 서명이 달라지는데, 비밀키를 모르니 올바른 서명을 다시 만들 수 없어 변조가
드러납니다. RS256 같은 비대칭키 방식은 개인키로 서명하고 공개키로 검증합니다. 발급 서버만 개인키를
갖고, 여러 서비스는 공개키만으로 검증할 수 있어서 MSA나 OIDC처럼 발급자와 검증자가 다른 환경에
적합합니다.

주의할 점은 서명은 위·변조를 막을 뿐 내용을 숨기지는 않는다는 것과, 서버가 Header의 alg 값을 그대로
믿으면 alg를 none으로 바꾸는 공격에 당할 수 있으므로 허용할 알고리즘을 서버에서 고정해야 한다는
점입니다.
```

- 만약 Access Token이 탈취되면, 어떻게 대응할 수 있을까요?
```
JWT는 Stateless라서 서버가 이미 발급한 토큰을 바로 무효화하기 어렵다는 것이 핵심 문제입니다. 그래서
사전 대비와 사후 대응으로 나눠 생각합니다.

사전 대비로 가장 중요한 것은 Access Token의 만료 시간을 15~30분 정도로 짧게 두는 것입니다. 탈취되더라도
피해가 그 시간 안으로 제한됩니다. 또한 저장 위치를 신경 써서, localStorage는 XSS로 쉽게 읽히므로
메모리에 두거나 HttpOnly·Secure 쿠키를 사용하고, HTTPS로만 전송합니다.

탈취가 확인되면, 그 토큰의 식별자(jti)를 Redis 같은 저장소의 블랙리스트에 만료 시간까지 등록하고,
요청마다 블랙리스트를 확인해서 거부합니다. 이는 Stateless의 장점을 일부 포기하는 대신 즉시 차단을
가능하게 합니다. 사용자 전체의 토큰을 무효화해야 한다면 사용자별 토큰 버전을 올리거나, 최악의 경우
서명 키를 교체해 모든 토큰을 무효화할 수 있습니다. 그리고 해당 사용자의 Refresh Token도 함께
폐기해서 공격자가 재발급받지 못하게 해야 합니다.
```

- 반대로 Refresh Token이 탈취되면, 어떻게 대응해야 할까요?
```
Refresh Token은 수명이 길고 Access Token을 계속 새로 발급받을 수 있어서 탈취 피해가 더 큽니다. 그래서
Refresh Token은 보통 Stateless로 두지 않고 서버(DB나 Redis)에 저장해 관리합니다. 서버가 저장하고
있으므로, 탈취가 의심되면 저장소에서 해당 Refresh Token을 삭제해 즉시 무효화하고, 사용자에게 다시
로그인하도록 할 수 있습니다.

탈취를 자동으로 감지하는 방법으로 Refresh Token Rotation이 있습니다. Refresh Token을 한 번 사용할
때마다 새 Refresh Token을 발급하고 이전 것은 폐기합니다. 만약 이미 사용된(폐기된) Refresh Token으로
재발급 요청이 들어오면, 공격자와 정상 사용자 중 누군가가 같은 토큰을 쓴 것이므로 탈취로 판단하고,
그 사용자와 연결된 모든 Refresh Token을 무효화해 양쪽 모두 재로그인하게 만듭니다. 그 외에 Refresh
Token을 발급할 때의 IP나 기기 정보를 함께 저장해 두고, 다른 환경에서 사용되면 차단하거나 추가 인증을
요구할 수 있으며, HttpOnly·Secure·SameSite 쿠키에 저장해 탈취 자체를 어렵게 합니다.
```

**핵심 키워드** → JWT = Header.Payload.Signature(Base64URL), Claim(sub·role·exp), Authorization: Bearer, Stateless(저장소 조회 X·확장 유리), 단점(Payload 노출·크기·강제 무효화 어려움) → 짧은 Access + 긴 Refresh, Signature(HS256 비밀키 HMAC vs RS256 개인키 서명·공개키 검증, alg none 공격 → 알고리즘 고정), Access 탈취(짧은 만료·저장 위치·HTTPS, jti 블랙리스트·토큰 버전·키 교체, Refresh도 폐기), Refresh 탈취(서버 저장 후 삭제, Rotation으로 재사용 감지 → 전체 무효화, IP·기기 바인딩, HttpOnly 쿠키)

#### 10. 암호화 알고리즘에 대해 설명해 주세요.

`★★☆` · `필수` · 원본 [개발상식·기타 #15](../05-ETC.md)

> 지정된 꼬리 질문이 없습니다. 답변자가 스스로 심화 주제를 하나 정해 덧붙이세요.

**내 답변**

```
암호화 알고리즘은 평문을 정해진 규칙과 키를 이용해 제3자가 알아볼 수 없는 암호문으로 바꾸는
알고리즘으로, 크게 양방향 암호화와 단방향 암호화(해시)로 나뉩니다.

양방향 암호화는 암호화한 것을 키로 다시 복호화할 수 있는 방식이고, 키를 쓰는 방식에 따라 두 가지로
나뉩니다. 대칭키 암호화는 암호화와 복호화에 같은 키를 씁니다. 연산이 빨라 대용량 데이터를 암호화하기에
좋지만, 상대에게 키를 안전하게 전달하기 어렵다는 키 배송 문제가 있고, N명이 서로 통신하려면 키가 많이
필요합니다. AES가 대표적이고, 과거의 DES는 키가 짧아 더 이상 쓰지 않습니다.

비대칭키(공개키) 암호화는 공개키와 개인키 한 쌍을 씁니다. 공개키로 암호화한 것은 짝이 되는 개인키로만
복호화할 수 있어서, 공개키는 누구에게나 공개해도 되므로 키 배송 문제가 해결됩니다. 반대로 개인키로
암호화(서명)한 것을 공개키로 검증하면 보낸 사람이 개인키 소유자임을 증명하는 전자 서명이 됩니다. 대신
연산이 매우 느립니다. RSA, ECC(타원 곡선)가 대표적입니다.

단방향 암호화는 해시 함수로, 원래 값으로 되돌릴 수 없고 같은 입력은 항상 같은 출력을 냅니다. 비밀번호
저장이나 데이터 무결성 검증에 쓰이며, SHA-256이 대표적이고 MD5, SHA-1은 충돌이 발견되어 쓰지
않습니다.
```

**스스로 정한 심화 주제 — HTTPS(TLS)가 대칭키와 비대칭키를 함께 쓰는 방식, 그리고 비밀번호 저장**
```
TLS는 두 방식의 장점만 골라 씁니다. 비대칭키는 키 배송 문제가 없지만 느리고, 대칭키는 빠르지만 키를
안전하게 나누기 어렵습니다. 그래서 TLS Handshake 단계에서만 비대칭키 기술을 사용해 안전하게
대칭키(세션키)를 합의하고, 실제 데이터는 그 대칭키로 빠르게 암호화합니다.

과정을 보면, 서버는 자신의 공개키가 담긴 인증서를 보내고, 클라이언트는 그 인증서가 신뢰할 수 있는
CA의 개인키로 서명되었는지 브라우저에 내장된 CA 공개키로 검증해 진짜 서버임을 확인합니다. 그 뒤 키를
교환하는데, 예전 RSA 방식은 클라이언트가 만든 비밀값을 서버의 공개키로 암호화해 보냈지만, 이 경우
나중에 서버의 개인키가 유출되면 과거에 녹화된 모든 통신이 복호화되는 문제가 있습니다. 그래서 TLS 1.3은
매 연결마다 임시 키를 만들어 양쪽이 각자 같은 세션키를 계산하는 ECDHE 방식만 허용해서, 개인키가
유출되더라도 과거 통신은 안전한 전방 비밀성(Forward Secrecy)을 보장합니다. 데이터는 AES-GCM처럼
암호화와 무결성 검증을 함께 하는 방식으로 보호합니다.

한편 비밀번호는 복호화할 필요가 없으므로 해시로 저장하는데, 단순히 SHA-256만 쓰면 위험합니다. 같은
비밀번호는 같은 해시가 나와서 미리 계산해 둔 해시 표(레인보우 테이블)로 역추적할 수 있고, SHA-256은
너무 빨라서 GPU로 초당 수십억 번 대입할 수 있기 때문입니다. 그래서 사용자마다 무작위 값인 솔트(Salt)를
섞어 같은 비밀번호도 다른 해시가 나오게 하고, 해시를 일부러 수천~수만 번 반복하는 키 스트레칭으로
계산을 느리게 만듭니다. 이를 갖춘 bcrypt, scrypt, Argon2 같은 전용 알고리즘을 사용하며, Spring
Security도 기본으로 BCryptPasswordEncoder를 제공합니다.
```

**핵심 키워드** → 양방향(복호화 가능) vs 단방향(해시), 대칭키(같은 키·빠름·키 배송 문제, AES) vs 비대칭키(공개키/개인키·키 배송 해결·전자 서명·느림, RSA·ECC), 해시(되돌릴 수 없음·무결성·비밀번호, SHA-256, MD5·SHA-1 사용 X), TLS = 비대칭키로 세션키 합의 + 대칭키로 데이터 암호화, 인증서·CA 서명 검증, RSA 키 교환 문제 → ECDHE·전방 비밀성(TLS 1.3), AES-GCM, 비밀번호 저장(레인보우 테이블·빠른 해시 위험 → 솔트·키 스트레칭, bcrypt·scrypt·Argon2)

### 워밍업 — 자료구조 · 정렬 구현

> 원본 [손코딩 #1 (각종 정렬) · #2 (각종 자료구조)](../06-ALGORITHM.md)를 12주로 나눈 조각입니다. 매주 1개씩, **10분 안에** IDE 없이 손으로 작성합니다.

#### [정렬 4/6] 힙 정렬

**구현 범위** — Week 07에서 구현한 Heap을 재사용해 제자리(in-place) 정렬. buildHeap이 O(N log N)이 아니라 O(N)인 이유

```java
class HeapSort {

    // 오름차순 정렬을 위해 최대 힙을 사용 (Week 07의 최소 힙에서 비교 방향만 반대로)
    static void sort(int[] arr) {
        int n = arr.length;

        // 1. buildHeap — 마지막 내부 노드부터 루트까지 거꾸로 siftDown
        for (int i = n / 2 - 1; i >= 0; i--) {
            siftDown(arr, i, n);
        }

        // 2. 루트(최댓값)를 배열 끝으로 보내고, 힙 크기를 1 줄인 뒤 다시 siftDown
        for (int end = n - 1; end > 0; end--) {
            swap(arr, 0, end);
            siftDown(arr, 0, end);
        }
    }

    // size까지만 힙으로 보고, index의 값을 자식들보다 크거나 같아질 때까지 아래로 내림
    private static void siftDown(int[] arr, int index, int size) {
        while (true) {
            int left = index * 2 + 1;
            int right = index * 2 + 2;
            int largest = index;

            if (left < size && arr[left] > arr[largest]) largest = left;
            if (right < size && arr[right] > arr[largest]) largest = right;
            if (largest == index) break;

            swap(arr, index, largest);
            index = largest;
        }
    }

    private static void swap(int[] arr, int i, int j) {
        int tmp = arr[i];
        arr[i] = arr[j];
        arr[j] = tmp;
    }
}
```

**제자리 정렬 방식** — Week 07처럼 별도의 힙 객체에 push/pop하면 O(N)의 추가 공간이 필요하므로, 입력 배열 자체를 힙으로 만듭니다. 오름차순이 목표라 **최대 힙**을 쓰는데, 루트(최댓값)를 배열의 맨 뒤와 바꾸면 그 자리가 정렬된 영역이 되고, 앞쪽의 남은 부분만 다시 힙으로 유지하면 되기 때문입니다. 즉 배열이 [힙 영역 | 정렬 완료 영역]으로 나뉘고, 매 단계 힙 영역이 1씩 줄어듭니다. Week 07의 siftDown에서 비교 방향(<를 >로)과, 힙의 끝을 나타내는 size를 인자로 받도록만 바꿔 재사용했습니다.

**buildHeap이 O(N)인 이유** — 원소를 하나씩 push(sift-up)하면 각각 최대 높이 log N만큼 올라가서 O(N log N)이 됩니다. 하지만 아래에서부터 siftDown하는 방식은, 각 노드가 내려갈 수 있는 거리가 **자기 아래의 높이**만큼뿐이라는 점이 다릅니다. 완전 이진 트리에서 노드의 절반(N/2개)은 리프라서 아예 내려가지 않고(n/2 - 1부터 시작하는 이유), N/4개는 최대 1칸, N/8개는 최대 2칸만 내려갑니다. 높이 log N만큼 내려가는 노드는 루트 하나뿐입니다. 전체 작업량은 Σ (N / 2^(h+1)) × h = N × Σ h / 2^(h+1)이고, 급수 Σ h / 2^h가 2로 수렴하므로 전체가 O(N)이 됩니다. 정리하면 많은 노드가 아래쪽에 몰려 있는데 아래쪽 노드일수록 할 일이 적기 때문입니다. (다만 이후 N번의 추출 단계가 각각 O(log N)이므로 정렬 전체는 여전히 O(N log N)입니다.)

**시간복잡도** → O(N log N) (buildHeap O(N) + 추출 N번 × siftDown O(log N)), 최선·평균·최악 모두 동일
**공간복잡도** → O(1) (입력 배열 안에서 제자리 정렬, siftDown도 재귀 없이 반복문), 불안정 정렬

### 응용 문항

> 원본: [손코딩 연습 문항](../06-ALGORITHM.md) · IDE 없이 손으로 먼저 써본 뒤, 스터디에서 서로 비교합니다.

#### 14. 1 부터 1,000,000 까지의 수를 이어 붙인다고 가정할 때, 이 수에서 0이 몇 번이나 등장하는지 확인하는 코드를 작성해 보세요.

```java
class CountZeros {

    // 방법 1. 모든 수를 자릿수별로 나눠보며 0을 셈 — 직관적, O(N log N)
    static long countByLoop(int n) {
        long count = 0;
        for (int i = 1; i <= n; i++) {
            int num = i;
            while (num > 0) {
                if (num % 10 == 0) count++;
                num /= 10;
            }
        }
        return count;
    }

    // 방법 2. 자릿수(1의 자리, 10의 자리, ...)마다 0이 몇 번 나오는지 수식으로 계산 — O(log N)
    static long countByDigit(int n) {
        long count = 0;
        for (long p = 10; p <= n; p *= 10) {      // 맨 앞자리는 0이 될 수 없으므로 p = 10부터
            long higher = n / p;                   // 현재 자리보다 앞부분
            long current = (n / (p / 10)) % 10;    // 현재 자리의 숫자
            long lower = n % (p / 10);             // 현재 자리보다 뒷부분

            // 앞부분이 1 ~ higher-1이면 현재 자리가 0일 때 뒷부분이 0 ~ (p/10 - 1) 모두 가능
            count += (higher - 1) * (p / 10);
            // 앞부분이 정확히 higher일 때는 현재 자리가 0인 경우만 따로 셈
            count += (current == 0) ? lower + 1 : p / 10;
        }
        return count;
    }

    public static void main(String[] args) {
        int n = 1_000_000;
        System.out.println(countByLoop(n));   // 488895
        System.out.println(countByDigit(n));  // 488895
    }
}
```

**풀이 설명**

수를 실제로 문자열로 이어 붙이면 약 590만 자의 문자열을 만들어야 하므로, 이어 붙인 결과의 0 개수는 **각 수에 들어 있는 0의 개수의 합**과 같다는 점을 이용해 문자열을 만들지 않고 셉니다.

방법 1은 1부터 N까지 각 수를 10으로 나눈 나머지를 보며 자릿수마다 0인지 확인합니다. 100만 개 × 최대 7자리라 약 700만 번의 연산으로 충분히 빠르고, 면접에서 먼저 제시하기 좋은 풀이입니다.

방법 2는 "각 자리에 0이 몇 번 나오는가"를 자리별로 계산합니다. 예를 들어 10의 자리(p = 100)를 볼 때, 수를 [앞부분 | 현재 자리 | 뒷부분]으로 나누면, 현재 자리가 0이려면 앞부분이 1 이상이어야 합니다(앞부분이 0이면 그 0은 앞에 붙는 0이라 쓰지 않음). 앞부분이 1 ~ higher-1이면 뒷부분은 아무 값이나 가능하므로 (higher - 1) × (p/10)가지이고, 앞부분이 정확히 higher일 때는 현재 자리 숫자가 0이면 뒷부분이 0 ~ lower까지만 가능하므로 lower + 1가지, 0보다 크면 뒷부분 전체 p/10가지입니다. 이를 모든 자리에 대해 더합니다. N이 아주 커져도 자릿수만큼만 반복하면 되는 장점이 있고, 두 방법의 결과가 같은지 비교해 검증할 수 있습니다.

**시간복잡도** → 방법 1: O(N log N) (N개의 수 × 자릿수 log N), 방법 2: O(log N) (자릿수만큼 반복)
**공간복잡도** → O(1) (두 방법 모두 문자열을 만들지 않고 카운터 변수만 사용)
