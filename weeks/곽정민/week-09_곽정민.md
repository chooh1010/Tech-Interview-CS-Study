`★☆☆` · `필수` · 원본 [데이터베이스 #1](../04-DATABASE.md)

<details>
<summary><b>꼬리 질문 4개 (펼치기)</b></summary>

- 기본키는 수정이 가능한가요?
- 사실 MySQL의 경우, 기본키를 설정하지 않아도 테이블이 만들어집니다. 어떻게 이게 가능한 걸까요?
- 외래키 값은 NULL이 들어올 수 있나요?
- 어떤 칼럼의 정의에 UNIQUE 키워드가 붙는다고 가정해 봅시다. 이 칼럼을 활용한 쿼리의 성능은 그렇지 않은 것과 비교해서 어떻게 다를까요?

</details>

**내 답변**

```
키는 테이블에서 튜플(행)을 유일하게 식별하거나, 테이블 간의 관계를 맺기 위해 사용하는 속성(칼럼)
또는 속성의 집합입니다. 학생(학번, 주민번호, 이름, 학과) 테이블을 예로 들면 다음과 같습니다.

슈퍼키(Super Key)는 각 튜플을 유일하게 식별할 수 있는 속성의 집합으로, 유일성만 만족하면 됩니다.
{학번}, {학번, 이름}, {주민번호, 학과}처럼 식별에 불필요한 속성이 섞여 있어도 슈퍼키입니다.

후보키(Candidate Key)는 슈퍼키 중에서 최소성까지 만족하는 키입니다. 즉 속성을 하나라도 빼면 더
이상 유일하게 식별할 수 없는 최소한의 집합으로, {학번}과 {주민번호}가 후보키입니다.

기본키(Primary Key)는 후보키 중에서 설계자가 대표로 선택한 하나의 키로, NULL을 허용하지 않고
중복될 수 없습니다(개체 무결성). 보통 값이 잘 바뀌지 않고 짧은 {학번}을 선택합니다. 대체키
(Alternate Key)는 기본키로 선택되지 못한 나머지 후보키로, 여기서는 {주민번호}입니다.

외래키(Foreign Key)는 다른 테이블의 기본키(또는 유니크 키)를 참조하는 속성으로, 두 테이블 간의
관계를 나타냅니다. 참조하는 값은 반드시 참조되는 테이블에 존재해야 합니다(참조 무결성).
```

**꼬리 질문 답변**

- 기본키는 수정이 가능한가요?
```
기술적으로는 UPDATE로 수정할 수 있지만, 가능한 수정하지 않는 것이 좋습니다. 첫째, 다른 테이블의
외래키가 그 기본키를 참조하고 있다면 참조 무결성이 깨지므로, ON UPDATE CASCADE를 설정하지 않으면
수정이 거부되고, 설정하더라도 연결된 모든 행이 함께 바뀌어 비용이 큽니다. 둘째, MySQL InnoDB는
기본키를 기준으로 데이터를 정렬해 저장하는 클러스터드 인덱스 구조라서, 기본키가 바뀌면 행의 물리적인
위치가 이동하고, 기본키 값을 포함하고 있는 모든 보조 인덱스도 갱신해야 합니다.

그래서 주민번호나 이메일처럼 의미가 있어 바뀔 수 있는 값(자연키) 대신, AUTO_INCREMENT 같은
의미 없는 일련번호(대리키, Surrogate Key)를 기본키로 쓰는 경우가 많습니다.
```

- 사실 MySQL의 경우, 기본키를 설정하지 않아도 테이블이 만들어집니다. 어떻게 이게 가능한 걸까요?
```
InnoDB는 모든 데이터를 기본키 기준의 클러스터드 인덱스(B+Tree)로 저장하기 때문에, 내부적으로는
반드시 클러스터링 기준이 필요합니다. 그래서 기본키가 없으면 다음 순서로 대신할 키를 정합니다.
첫째, NOT NULL인 UNIQUE 인덱스가 있으면 그중 첫 번째를 기본키처럼 사용합니다. 둘째, 그것도
없으면 사용자에게 보이지 않는 6바이트짜리 숨겨진 칼럼(DB_ROW_ID)을 자동으로 만들어, 행이 삽입될
때마다 증가하는 값을 넣고 이를 기준으로 클러스터드 인덱스를 만듭니다.

다만 이 숨겨진 키는 쿼리에서 사용할 수 없고, 모든 테이블이 전역 카운터를 공유해 경합이 생길 수
있으며, 복제 환경에서도 문제가 될 수 있어서 기본키는 명시적으로 지정하는 것이 좋습니다.
```

- 외래키 값은 NULL이 들어올 수 있나요?
```
네, 들어올 수 있습니다. 외래키 칼럼에 NOT NULL 제약을 따로 걸지 않았다면 NULL을 허용합니다.
NULL은 "아직 참조하는 대상이 없음"을 의미하고, 참조 무결성은 "값이 있다면 반드시 참조 테이블에
존재해야 한다"는 규칙이므로 NULL은 위반이 아닙니다. 예를 들어 사원 테이블의 부서ID 외래키에서,
아직 부서가 배정되지 않은 신입 사원은 NULL을 가질 수 있습니다. 관계가 필수라면 NOT NULL을 함께
걸어주면 됩니다. 또한 ON DELETE SET NULL 옵션을 쓰면, 참조하던 부서가 삭제될 때 외래키를 자동으로
NULL로 바꿀 수 있습니다.
```

- 어떤 칼럼의 정의에 UNIQUE 키워드가 붙는다고 가정해 봅시다. 이 칼럼을 활용한 쿼리의 성능은 그렇지 않은 것과 비교해서 어떻게 다를까요?
```
UNIQUE 제약을 걸면 중복 검사를 위해 대부분의 DBMS가 자동으로 유니크 인덱스를 생성합니다. 그래서
조회 성능은 크게 좋아집니다. 인덱스가 없다면 WHERE email = ? 같은 조건에 테이블 전체를 읽는
풀 스캔(O(N))이 필요하지만, 인덱스가 있으면 B+Tree로 O(log N)에 찾을 수 있습니다. 또한 일반
인덱스는 같은 값이 여러 개일 수 있어 첫 값을 찾은 뒤에도 다음 값을 계속 확인해야 하지만, 유니크
인덱스는 값이 하나뿐임이 보장되므로 하나를 찾는 즉시 탐색을 멈출 수 있고, 옵티마이저도 결과가 최대
한 건임을 알고 더 좋은 실행 계획을 세웁니다.

반대로 쓰기 성능은 약간 떨어집니다. INSERT나 UPDATE를 할 때마다 인덱스를 갱신하고 중복 여부를
확인해야 하기 때문입니다. 특히 InnoDB에서 일반 보조 인덱스는 변경을 모아뒀다가 나중에 반영하는
체인지 버퍼를 쓸 수 있지만, 유니크 인덱스는 중복 검사를 위해 즉시 인덱스를 읽어야 해서 이 최적화를
쓸 수 없습니다.
```

**핵심 키워드** → 슈퍼키(유일성) ⊃ 후보키(유일성 + 최소성) ⊃ 기본키(대표 선택, NOT NULL·중복 X·개체 무결성) / 대체키(나머지 후보키), 외래키(다른 테이블 PK 참조·참조 무결성), 기본키 수정(가능하지만 FK 연쇄·클러스터드 인덱스 재배치 → 대리키 권장), PK 없는 InnoDB(NOT NULL UNIQUE 사용 → 없으면 숨겨진 DB_ROW_ID), FK NULL 허용(값이 있을 때만 참조 무결성, ON DELETE SET NULL), UNIQUE(자동 유니크 인덱스 → 조회 O(log N)·한 건 찾으면 종료, 쓰기 시 중복 검사 비용·체인지 버퍼 불가)

`★★☆` · `필수` · 원본 [데이터베이스 #2](../04-DATABASE.md)

<details>
<summary><b>꼬리 질문 3개 (펼치기)</b></summary>

- NoSQL의 강점과, 약점이 무엇인가요?
- RDB의 어떠한 특징 때문에 NoSQL에 비해 부하가 많이 걸릴 "수" 있을까요? (주의: 무조건 NoSQL이 RDB 보다 빠르다라고 생각하면 큰일 납니다!)
- NoSQL을 활용한 경험이 있나요? 있다면, 왜 RDB를 선택하지 않고 해당 DB를 선택했는지 설명해 주세요.

</details>

**내 답변**

```
RDB(관계형 데이터베이스)는 데이터를 미리 정의한 스키마에 맞춰 행과 열로 이루어진 테이블에 저장하고,
테이블 간의 관계를 외래키로 표현하며, SQL로 JOIN 등을 이용해 조회합니다. 정규화로 중복을 줄이고,
트랜잭션의 ACID를 보장해서 데이터의 정합성과 일관성이 중요한 서비스(결제, 회원, 주문)에 적합합니다.
MySQL, PostgreSQL, Oracle이 대표적입니다.

NoSQL은 관계형 모델이 아닌 다양한 형태로 데이터를 저장하는 데이터베이스를 통틀어 말합니다. 키-값
(Redis), 문서(MongoDB), 컬럼 패밀리(Cassandra, HBase), 그래프(Neo4j) 같은 유형이 있습니다.
스키마가 고정되어 있지 않거나 유연해서 데이터 구조를 바꾸기 쉽고, 처음부터 여러 서버로 데이터를
나눠 저장하는 수평 확장(Scale-out)을 고려해 설계되어 대용량 데이터와 높은 트래픽을 처리하기 좋습니다.
대신 JOIN을 지원하지 않거나 제한적이어서, 함께 조회할 데이터를 한 문서에 중복해서 넣는 비정규화
방식으로 모델링하고, 많은 경우 강한 일관성 대신 최종적 일관성(Eventual Consistency)을 택합니다.

정리하면 RDB는 데이터 정합성과 복잡한 관계 조회에, NoSQL은 유연한 스키마와 수평 확장, 단순하고
대량의 읽기·쓰기에 강점이 있어 요구사항에 맞게 선택하거나 함께 사용합니다.
```

**꼬리 질문 답변**

- NoSQL의 강점과, 약점이 무엇인가요?
```
강점은 첫째, 스키마가 유연해서 요구사항이 자주 바뀌거나 데이터마다 구조가 조금씩 다른 경우에
ALTER TABLE 같은 스키마 변경 없이 바로 대응할 수 있습니다. 둘째, 샤딩과 복제를 기본으로 지원해
서버를 늘리는 것만으로 저장 용량과 처리량을 늘리기 쉽습니다. 셋째, 함께 쓰는 데이터를 한 문서나 한
키에 모아 저장하기 때문에, 정해진 패턴의 조회는 JOIN 없이 한 번에 가져와 매우 빠릅니다.

약점은 첫째, JOIN이 없거나 제한적이라 복잡한 관계 조회나 다양한 조건의 분석 쿼리가 어렵습니다.
둘째, 비정규화로 같은 데이터가 여러 곳에 중복되므로, 수정할 때 모든 복사본을 직접 갱신해야 하고
놓치면 데이터 불일치가 생깁니다. 셋째, 많은 NoSQL이 가용성과 분산을 위해 강한 일관성이나 여러
문서에 걸친 트랜잭션 지원이 약해서(최근 MongoDB는 다중 문서 트랜잭션을 지원하지만 비용이 큼),
정합성이 중요한 데이터에는 부적합합니다. 넷째, 조회 패턴을 미리 정해 모델링하기 때문에 예상하지 못한
조회 요구가 생기면 대응이 어렵습니다.
```

- RDB의 어떠한 특징 때문에 NoSQL에 비해 부하가 많이 걸릴 "수" 있을까요? (주의: 무조건 NoSQL이 RDB 보다 빠르다라고 생각하면 큰일 납니다!)
```
RDB의 장점인 정합성을 지키기 위한 장치들이 특정 상황에서 비용이 됩니다. 첫째, 정규화로 데이터가 여러
테이블에 나뉘어 있어 조회할 때 JOIN이 많아지고, 데이터가 커질수록 JOIN 비용이 커집니다. 둘째, ACID를
보장하기 위해 락, Undo·Redo 로그 기록, 제약 조건(외래키, 유니크) 검사를 수행하므로 쓰기가 몰릴 때
부담이 큽니다. 셋째, JOIN과 트랜잭션은 데이터가 한 서버에 있을 때 가장 잘 동작하기 때문에, 여러 서버로
데이터를 나누는 수평 확장이 어렵고 주로 서버 성능을 높이는 수직 확장에 의존하게 되어 한계가 있습니다.

하지만 이것은 "그런 상황에서 부하가 걸릴 수 있다"는 것이지 NoSQL이 항상 빠르다는 뜻은 아닙니다. 인덱스가
잘 설계된 RDB는 복잡한 조건의 조회에서 훨씬 효율적이고, NoSQL도 미리 설계하지 않은 패턴의 조회나
여러 문서를 함께 갱신하는 작업에서는 오히려 느리거나 애플리케이션에서 복잡하게 처리해야 합니다.
결국 성능은 데이터 모델과 접근 패턴에 달려 있습니다.
```

- NoSQL을 활용한 경험이 있나요? 있다면, 왜 RDB를 선택하지 않고 해당 DB를 선택했는지 설명해 주세요.
```
(※ 본인의 실제 경험으로 바꿔서 답변할 것 — 아래는 예시)

Redis를 로그인 세션과 인증 토큰 저장, 그리고 자주 조회되는 데이터의 캐시로 사용해 본 경험이
있습니다. 회원, 주문 같은 핵심 데이터는 정합성이 중요해서 MySQL에 저장했지만, 세션이나 Refresh
Token은 요청마다 매우 자주 조회되고, 일정 시간이 지나면 사라져야 하는 단순한 키-값 데이터였습니다.

이 데이터를 RDB에 두면 매 요청마다 디스크 기반 DB에 조회가 발생하고, 만료된 데이터를 지우는 배치
작업도 따로 만들어야 합니다. Redis는 메모리 기반이라 응답이 매우 빠르고, 키마다 TTL을 설정하면 만료
시 자동으로 삭제되기 때문에 이 용도에 잘 맞았습니다. 또한 서버를 여러 대로 늘려도 모든 서버가 같은
Redis를 바라보면 세션을 공유할 수 있었습니다. 대신 메모리에 저장되므로 유실되어도 다시 로그인하면
되는 데이터만 넣고, 영구 보존이 필요한 데이터는 RDB에 두는 식으로 역할을 나눴습니다.
```

**핵심 키워드** → RDB(고정 스키마·테이블·FK 관계·JOIN·정규화·ACID·정합성) vs NoSQL(키-값·문서·컬럼·그래프, 유연한 스키마·수평 확장·비정규화·최종적 일관성), NoSQL 강점(스키마 유연·샤딩/복제·정해진 조회 빠름) / 약점(JOIN 제한·중복 갱신 부담·트랜잭션·일관성 약함·예상 밖 조회 어려움), RDB 부하 원인(JOIN·락/로그/제약 검사·수평 확장 어려움), NoSQL이 항상 빠른 건 아님(접근 패턴에 달림), Redis 경험(세션·토큰·캐시, 메모리·TTL·서버 간 공유)

<details>

- ACID 원칙 중, Durability를 DBMS는 어떻게 보장하나요?
- 트랜잭션을 사용해 본 경험이 있나요? 어떤 경우에 사용할 수 있나요?
- 읽기에는 트랜잭션을 걸지 않아도 될까요?

</details>

**내 답변**

```
트랜잭션은 데이터베이스의 상태를 변화시키는, 더 이상 쪼갤 수 없는 하나의 논리적인 작업 단위입니다.
예를 들어 계좌 이체는 "A 계좌에서 출금"과 "B 계좌에 입금"이라는 두 개의 쿼리로 이루어지지만, 둘 중
하나만 실행되면 돈이 사라지거나 생겨나므로 반드시 하나의 단위로 묶여 모두 성공(COMMIT)하거나
모두 취소(ROLLBACK)되어야 합니다. 트랜잭션이 안전하게 수행되기 위해 지켜야 하는 성질이 ACID입니다.

Atomicity(원자성)는 트랜잭션의 작업이 모두 반영되거나, 하나도 반영되지 않아야 한다는 성질입니다
(All or Nothing). 중간에 실패하면 이미 실행된 작업도 Undo 로그를 이용해 되돌립니다.

Consistency(일관성)는 트랜잭션이 끝난 후에도 데이터베이스가 정의된 규칙(제약 조건, 무결성)을
만족하는 일관된 상태를 유지해야 한다는 성질입니다. 이체 전후 두 계좌의 잔액 합은 같아야 하고,
잔액이 음수가 되면 안 된다는 제약을 어기는 트랜잭션은 실패해야 합니다.

Isolation(격리성)은 동시에 실행되는 트랜잭션들이 서로의 중간 결과에 영향을 받지 않고, 마치 혼자
실행되는 것처럼 동작해야 한다는 성질입니다. 락이나 MVCC로 구현하며, 성능과의 트레이드오프 때문에
격리 수준을 조절할 수 있습니다.

Durability(지속성)는 커밋된 트랜잭션의 결과는 시스템 장애가 발생하더라도 영구적으로 보존되어야
한다는 성질입니다.
```

**꼬리 질문 답변**

- ACID 원칙 중, Durability를 DBMS는 어떻게 보장하나요?
```
핵심은 WAL(Write-Ahead Logging)입니다. 데이터를 변경할 때마다 디스크의 실제 데이터 파일을 바로
수정하면, 데이터 파일 여기저기에 흩어진 위치에 쓰는 랜덤 I/O가 발생해 매우 느립니다. 그래서 DBMS는
변경 내용을 먼저 메모리의 버퍼에서 처리하고, 대신 "무엇을 어떻게 바꿨는지"를 Redo 로그에 순서대로
기록합니다. 그리고 커밋 시점에는 데이터 파일이 아니라 이 Redo 로그를 디스크에 확실히 기록(fsync)한
뒤에 커밋 완료를 응답합니다. 로그는 파일 끝에 이어 쓰는 순차 I/O라 빠릅니다.

이후 메모리의 변경된 데이터 페이지는 체크포인트 시점에 모아서 디스크에 반영합니다. 만약 그 전에
서버가 죽어 메모리의 내용이 날아가더라도, 재시작할 때 디스크에 남아 있는 Redo 로그를 다시 재생(Redo)
해서 커밋된 변경을 복구하고, 커밋되지 않은 트랜잭션은 Undo 로그로 되돌립니다. MySQL에서는
innodb_flush_log_at_trx_commit 설정으로 커밋마다 디스크에 기록할지(1, 기본값이자 가장 안전) 성능을
위해 1초마다 기록할지를 정할 수 있습니다. 디스크 자체의 장애에 대비해서는 백업과 복제(Replication)를
함께 사용합니다.
```

- 트랜잭션을 사용해 본 경험이 있나요? 어떤 경우에 사용할 수 있나요?
```
여러 개의 쓰기 작업이 함께 성공하거나 함께 실패해야 하는 경우에 사용합니다. 예를 들어 주문 기능을
구현할 때, 주문 정보 저장, 상품 재고 차감, 포인트 사용 처리를 하나의 트랜잭션으로 묶었습니다. 재고
차감 후 포인트 차감에서 예외가 발생하면 주문도 재고도 모두 원래대로 되돌아가야 하기 때문입니다.

Spring에서는 서비스 메서드에 @Transactional을 붙여 사용했는데, 이 어노테이션은 프록시 기반이라 같은
클래스 안에서 내부 메서드를 호출하면 트랜잭션이 적용되지 않는다는 점, 그리고 기본적으로 Unchecked
예외(RuntimeException)에서만 롤백되고 Checked 예외는 롤백되지 않는다는 점을 주의했습니다. 또한
트랜잭션 안에서 외부 API 호출 같은 오래 걸리는 작업을 하면 DB 커넥션과 락을 오래 점유하므로,
트랜잭션 범위는 DB 작업에 필요한 만큼 최소한으로 잡는 것이 좋습니다.
```

- 읽기에는 트랜잭션을 걸지 않아도 될까요?
```
단건 조회 하나라면 큰 문제가 없지만, 여러 번 조회해서 그 결과를 함께 써야 한다면 트랜잭션을 거는 것이
좋습니다. 사실 DB에서는 트랜잭션을 명시하지 않아도 각 쿼리가 자동 커밋(auto-commit)되는 하나의
트랜잭션으로 실행됩니다. 문제는 여러 쿼리를 따로 실행하면 각 쿼리가 서로 다른 시점의 데이터를 보게
된다는 것입니다. 예를 들어 계좌 목록과 잔액 합계를 따로 조회하는 사이에 다른 트랜잭션이 이체를
커밋하면, 화면에 보이는 목록과 합계가 서로 맞지 않을 수 있습니다. 하나의 트랜잭션으로 묶으면 같은
스냅샷(일관된 읽기)을 기준으로 조회할 수 있습니다.

또한 Spring에서는 @Transactional(readOnly = true)를 쓰면 이점이 있습니다. JPA가 변경 감지를 위한
스냅샷을 만들지 않고 flush도 하지 않아 성능이 좋아지고, 실수로 데이터를 수정하는 것을 막을 수 있으며,
읽기 전용 트랜잭션을 레플리카 DB로 보내는 읽기·쓰기 분리에도 활용할 수 있습니다. 또 JPA의 지연 로딩이
트랜잭션 범위 안에서 동작하는 경우도 있습니다.
```

**핵심 키워드** → 트랜잭션 = 쪼갤 수 없는 논리적 작업 단위(COMMIT/ROLLBACK), 원자성(All or Nothing·Undo 로그), 일관성(제약·무결성 유지), 격리성(동시 트랜잭션 간섭 X·락/MVCC·격리 수준), 지속성(커밋 결과 영구 보존), Durability 보장(WAL·커밋 시 Redo 로그 fsync·순차 I/O·체크포인트·장애 후 Redo 재생/Undo, flush_log_at_trx_commit, 백업·복제), 사용 경험(주문·재고·포인트를 묶음, @Transactional 프록시 내부 호출·Checked 예외 롤백 X 주의, 범위 최소화), 읽기 트랜잭션(여러 조회의 일관된 스냅샷, readOnly = true → 변경 감지 생략·레플리카 라우팅)

#### 4. 트랜잭션 격리 레벨에 대해 설명해 주세요.

`★★★` · `필수` · 원본 [데이터베이스 #4](../04-DATABASE.md)

<details>
<summary><b>꼬리 질문 3개 (펼치기)</b></summary>

- 모든 DBMS가 4개의 레벨을 모두 구현하고 있나요? 그렇지 않다면 그 이유는 무엇일까요?
- 만약 MySQL을 사용하고 있다면, (InnoDB 기준) Undo 영역과 Redo 영역에 대해 설명해 주세요.
- 그런데, 스토리지 엔진이 정확히 무엇을 하는 건가요?

</details>

**내 답변**

```
트랜잭션 격리 레벨은 여러 트랜잭션이 동시에 실행될 때, 한 트랜잭션이 다른 트랜잭션의 변경 내용을
어디까지 볼 수 있게 할지를 정하는 기준입니다. 격리를 강하게 할수록 데이터는 정확해지지만 동시성이
떨어져 성능이 나빠지기 때문에, 허용할 이상 현상의 수준에 따라 4단계로 나눕니다.

READ UNCOMMITTED는 다른 트랜잭션이 아직 커밋하지 않은 변경까지 읽을 수 있습니다. 그래서 다른
트랜잭션이 롤백하면 존재하지 않았던 데이터를 읽은 셈이 되는 Dirty Read가 발생합니다.

READ COMMITTED는 커밋된 데이터만 읽을 수 있어 Dirty Read는 막지만, 한 트랜잭션 안에서 같은
데이터를 두 번 읽는 사이에 다른 트랜잭션이 수정 후 커밋하면 두 결과가 달라지는 Non-Repeatable
Read가 발생합니다. Oracle, PostgreSQL의 기본값입니다.

REPEATABLE READ는 트랜잭션이 시작된 시점(첫 조회 시점)의 스냅샷을 기준으로 읽어서, 같은 데이터를
여러 번 읽어도 항상 같은 결과를 보장합니다. 하지만 표준상으로는 범위 조회 시 다른 트랜잭션이 새로
INSERT한 행이 나타나는 Phantom Read가 발생할 수 있습니다. MySQL InnoDB의 기본값인데, InnoDB는
MVCC와 넥스트 키 락(갭 락) 덕분에 대부분의 Phantom Read도 막습니다.

SERIALIZABLE은 트랜잭션들을 순서대로 하나씩 실행한 것과 같은 결과를 보장하는 가장 엄격한 수준으로,
InnoDB에서는 일반 SELECT도 공유 락을 걸어 모든 이상 현상을 막지만, 동시성이 크게 떨어져 거의 쓰지
않습니다.
```

**꼬리 질문 답변**

- 모든 DBMS가 4개의 레벨을 모두 구현하고 있나요? 그렇지 않다면 그 이유는 무엇일까요?
```
아닙니다. 4단계는 ANSI SQL 표준이 "각 수준에서 최소한 어떤 이상 현상을 막아야 하는가"를 정의한
것일 뿐이고, 실제 구현 방식은 DBMS의 동시성 제어 구조에 따라 다르기 때문입니다.

예를 들어 Oracle은 READ COMMITTED와 SERIALIZABLE 두 가지만 지원합니다. Oracle은 처음부터 MVCC
(Undo 데이터로 과거 버전을 읽는 방식)로 설계되어 있어서, 커밋되지 않은 데이터를 읽는 READ
UNCOMMITTED를 일부러 구현할 이유가 없습니다. PostgreSQL은 4단계를 모두 설정할 수 있지만, READ
UNCOMMITTED를 설정해도 내부적으로 READ COMMITTED로 동작합니다. 또한 PostgreSQL의 REPEATABLE
READ는 스냅샷 격리로 구현되어 표준보다 강하게 Phantom Read까지 막습니다.

즉 표준은 "이 정도 이상은 막아라"라는 하한선이라서, 더 강하게 보장하는 것은 표준 위반이 아닙니다.
DBMS마다 자신의 구조에서 효율적으로 구현할 수 있는 수준만 제공하거나, 같은 이름이라도 실제 동작이
다를 수 있기 때문에, 사용하는 DBMS의 격리 수준 동작을 따로 확인해야 합니다.
```

- 만약 MySQL을 사용하고 있다면, (InnoDB 기준) Undo 영역과 Redo 영역에 대해 설명해 주세요.
```
Undo 로그는 데이터를 변경하기 "전"의 값을 저장하는 공간입니다. 두 가지 용도로 쓰입니다. 첫째,
트랜잭션이 롤백되면 Undo 로그의 이전 값으로 데이터를 되돌려 원자성을 보장합니다. 둘째, MVCC를
구현합니다. 한 트랜잭션이 행을 수정 중이어도, 다른 트랜잭션은 락을 기다리지 않고 Undo 로그에 남은
이전 버전을 읽습니다. REPEATABLE READ에서 트랜잭션 시작 시점의 스냅샷을 볼 수 있는 것도 Undo 로그를
따라 과거 버전을 찾아가기 때문입니다. 그래서 오래 실행되는 트랜잭션이 있으면, 그 트랜잭션이 볼 수도
있는 과거 버전들을 지울 수 없어 Undo 영역이 계속 커지는 문제가 생깁니다.

Redo 로그는 데이터를 변경한 "후"의 내용을 기록하는 공간으로, 지속성을 보장합니다. 앞에서 말한 WAL
방식대로, 커밋할 때 데이터 파일 대신 Redo 로그를 먼저 디스크에 기록하고, 장애가 나면 이 로그를 재생해서
아직 데이터 파일에 반영되지 못한 커밋된 변경을 복구합니다. Redo 로그는 고정 크기 파일을 순환하며
사용합니다.

정리하면 Undo는 "되돌리기 위한 과거 기록"으로 원자성과 MVCC를, Redo는 "다시 하기 위한 변경 기록"으로
지속성과 장애 복구를 담당합니다.
```

- 그런데, 스토리지 엔진이 정확히 무엇을 하는 건가요?
```
스토리지 엔진은 데이터를 실제로 디스크에 어떻게 저장하고, 읽고, 수정할지를 담당하는 DBMS의 하위
컴포넌트입니다. MySQL은 구조가 두 층으로 나뉘어 있습니다. 위쪽의 MySQL 엔진(서버 계층)은 클라이언트
연결, SQL 파싱, 옵티마이저의 실행 계획 수립을 담당하고, 아래쪽의 스토리지 엔진은 실행 계획에 따라
"이 조건의 행을 읽어 달라", "이 행을 써 달라" 같은 요청(Handler API)을 받아 실제 데이터 입출력을
처리합니다. 비유하면 MySQL 엔진은 무엇을 할지 정하는 두뇌이고, 스토리지 엔진은 실제로 일을 하는
손발입니다.

그래서 데이터 저장 구조, 인덱스 구현, 트랜잭션과 락, 장애 복구 방식은 모두 스토리지 엔진이 결정하고,
테이블마다 다른 엔진을 선택할 수도 있습니다. 대표적으로 InnoDB는 트랜잭션, 행 단위 락, MVCC, 외래키,
Redo/Undo 기반 장애 복구, 클러스터드 인덱스를 지원하는 MySQL의 기본 엔진입니다. 예전 기본이었던
MyISAM은 트랜잭션을 지원하지 않고 테이블 단위 락을 사용해 동시 쓰기에 약하며, Memory 엔진은 데이터를
메모리에만 저장합니다.
```

**핵심 키워드** → 격리 레벨 = 동시 트랜잭션 간 가시성 기준(정확성 vs 동시성), READ UNCOMMITTED(Dirty Read) → READ COMMITTED(Non-Repeatable Read, Oracle·PostgreSQL 기본) → REPEATABLE READ(Phantom Read, MySQL 기본, MVCC·넥스트 키 락으로 대부분 방지) → SERIALIZABLE(모두 방지·SELECT도 공유 락), 표준은 하한선(Oracle은 RC·SERIALIZABLE만, PostgreSQL RU = RC), Undo(변경 전 값·롤백·MVCC 과거 버전, 긴 트랜잭션 시 비대) vs Redo(변경 후 값·WAL·장애 복구·순환 파일), 스토리지 엔진(실제 저장·읽기 담당, MySQL 엔진 = 두뇌 / 스토리지 엔진 = 손발, Handler API, InnoDB vs MyISAM)

**내 답변**

```
정규화는 테이블의 데이터 중복을 최소화하고 이상 현상을 없애기 위해, 함수적 종속성을 기준으로 테이블을
더 작은 테이블로 분해하는 과정입니다. 함수적 종속성은 "X 값이 정해지면 Y 값이 하나로 정해진다"(X → Y)는
관계로, 예를 들어 학번이 정해지면 이름이 정해지므로 학번 → 이름입니다.

하나의 테이블에 여러 주제의 데이터가 섞여 있으면 같은 정보가 여러 행에 반복 저장되고, 이 때문에 삽입,
수정, 삭제 시 문제가 생깁니다. 정규화는 "하나의 테이블은 하나의 주제만 다룬다"는 방향으로 테이블을
나누어, 각 정보가 한 곳에만 저장되도록 합니다. 단계별로 제1정규형(1NF)부터 제2정규형, 제3정규형,
BCNF, 제4, 제5정규형이 있으며, 실무에서는 보통 제3정규형이나 BCNF까지 진행합니다.

중요한 점은 정규화는 정보를 잃지 않는 분해(무손실 분해)여야 한다는 것입니다. 나눈 테이블들을 다시
JOIN하면 원래 데이터를 그대로 복원할 수 있어야 합니다. 정규화를 하면 중복이 줄고 데이터 정합성이
좋아지지만, 테이블이 많아져 조회 시 JOIN 비용이 늘어나는 트레이드오프가 있습니다.
```

**꼬리 질문 답변**

- 정규화를 하지 않을 경우, 발생할 수 있는 이상현상에 대해 설명해 주세요.
```
수강(학번, 이름, 학과, 과목코드, 과목명, 성적) 테이블처럼 학생 정보와 과목 정보가 한 테이블에 섞여
있다고 가정하겠습니다.

삽입 이상(Insertion Anomaly)은 원하지 않는 정보까지 함께 넣어야만 데이터를 삽입할 수 있는 문제입니다.
기본키가 (학번, 과목코드)이므로, 아직 아무 과목도 수강하지 않은 신입생은 과목코드가 없어 학생 정보만
따로 등록할 수 없습니다.

갱신 이상(Update Anomaly)은 중복된 데이터 중 일부만 수정되어 불일치가 생기는 문제입니다. 한 학생이
5과목을 들으면 학과 정보가 5행에 중복 저장되는데, 학과를 옮겼을 때 일부 행만 수정하면 같은 학생의
학과가 행마다 달라집니다.

삭제 이상(Deletion Anomaly)은 데이터를 삭제할 때 함께 지켜야 할 정보까지 지워지는 문제입니다. 어떤
과목을 듣는 학생이 한 명뿐인데 그 학생이 수강을 취소해 행을 지우면, 그 과목의 과목명 정보 자체가
데이터베이스에서 사라집니다.
```

- 각 정규화에 대해, 그 정규화가 진행되기 전/후의 테이블의 변화에 대해 설명해 주세요.
```
제1정규형(1NF): 모든 속성 값이 더 이상 나눌 수 없는 원자값이어야 합니다.
  전) 학생(학번, 이름, 수강과목) — 수강과목에 "DB, OS, 네트워크"처럼 여러 값이 한 칸에 들어 있음
  후) 학생수강(학번, 이름, 과목) — 한 칸에 한 값만 오도록 과목마다 행을 나눔

제2정규형(2NF): 1NF를 만족하고, 기본키의 일부에만 종속되는 부분 함수 종속을 제거합니다(복합키일 때
의미가 있음).
  전) 수강(학번, 과목코드, 이름, 과목명, 성적), 기본키 (학번, 과목코드)
      이름은 학번에만, 과목명은 과목코드에만 종속 → 부분 함수 종속
  후) 학생(학번, 이름) / 과목(과목코드, 과목명) / 수강(학번, 과목코드, 성적)
      성적만 기본키 전체에 종속되므로 수강 테이블에 남김

제3정규형(3NF): 2NF를 만족하고, 기본키가 아닌 속성이 다른 일반 속성을 거쳐 기본키에 종속되는 이행적
함수 종속을 제거합니다.
  전) 학생(학번, 이름, 학과코드, 학과명) — 학번 → 학과코드 → 학과명 (이행적 종속)
  후) 학생(학번, 이름, 학과코드) / 학과(학과코드, 학과명)
      학과명이 바뀌어도 학과 테이블 한 곳만 수정하면 됨

BCNF: 3NF를 만족하고, 모든 결정자가 후보키여야 합니다(아래 질문에서 예시로 설명).
```

- BCNF가 무엇인지 설명하고, 제3정규형과 어떤 차이가 있는지 예시를 들어 설명해 주세요.
```
BCNF(Boyce-Codd Normal Form)는 "모든 함수적 종속 X → Y에서 결정자 X가 반드시 후보키여야 한다"는
조건입니다. 3NF와의 차이는 종속되는 쪽(Y)의 종류에 있습니다. 3NF는 "기본키가 아닌 일반 속성"이 다른
일반 속성에 종속되는 경우만 막기 때문에, Y가 후보키의 일부인 속성(주 속성)이라면 결정자가 후보키가
아니어도 허용합니다. BCNF는 이 예외까지 없애서, 후보키가 아닌 속성이 무언가를 결정하는 것 자체를
허용하지 않습니다. 그래서 BCNF가 3NF보다 더 엄격하고, 주로 후보키가 여러 개이고 서로 겹치는 복합키일
때 차이가 드러납니다.

예시) 특강신청(학번, 과목, 교수) 테이블에서 규칙이 다음과 같다고 하겠습니다.
  - 한 학생은 한 과목에 대해 한 명의 교수에게만 신청한다: (학번, 과목) → 교수
  - 한 교수는 한 과목만 가르친다: 교수 → 과목
  - 한 과목은 여러 교수가 가르칠 수 있다

후보키는 (학번, 과목)과 (학번, 교수)입니다. 이 테이블은 모든 속성이 후보키의 일부(주 속성)이므로
부분·이행 종속을 따질 일반 속성이 없어 3NF를 만족합니다. 하지만 교수 → 과목에서 결정자인 교수는
후보키가 아니므로 BCNF를 위반합니다. 그 결과, 어떤 교수가 담당 과목을 바꾸면 그 교수의 모든 신청 행을
고쳐야 하는 갱신 이상이 생기고, 신청한 학생이 아직 없는 교수의 담당 과목 정보는 저장할 수 없습니다.

BCNF로 분해하면 교수과목(교수, 과목)과 신청(학번, 교수)으로 나뉘어, 교수의 담당 과목이 한 곳에만
저장됩니다. 다만 이 분해로 원래의 (학번, 과목) → 교수 종속을 한 테이블 안에서 제약으로 강제할 수
없게 되는데(종속성 보존 실패), 이것이 3NF에서 멈추기도 하는 이유입니다.
```

- 제3정규형을 만족하는데도 BCNF를 만족하지 못하는 테이블이 있을 수 있나요? 있다면 예시를 들어주세요.
```
네, 있습니다. 바로 위의 특강신청(학번, 과목, 교수) 테이블이 그 예입니다. 정리하면, 결정자(교수)가
후보키가 아닌데, 그것이 결정하는 속성(과목)이 후보키 (학번, 과목)의 일부인 주 속성일 때 발생합니다.
3NF는 "결정자가 후보키이거나, 종속되는 속성이 주 속성이면 OK"라는 예외를 두기 때문에 통과하지만,
BCNF는 결정자가 반드시 후보키여야 하므로 위반입니다.

다른 예로, 도시와 거리 주소가 정해지면 우편번호가 정해지고(도시, 거리 → 우편번호), 우편번호가
정해지면 도시가 정해지는(우편번호 → 도시) 주소(도시, 거리, 우편번호) 테이블도 마찬가지입니다.
후보키는 (도시, 거리)와 (거리, 우편번호)이고, 우편번호 → 도시에서 우편번호는 후보키가 아니지만
도시가 주 속성이라 3NF는 만족하고 BCNF는 위반합니다. 이런 상황은 겹치는 복합 후보키가 여러 개 있을
때만 생기므로, 후보키가 하나뿐인 테이블이라면 3NF를 만족하면 BCNF도 만족합니다.
```

- BCNF까지 정규화하면 모든 이상현상이 사라지나요? 제4, 제5정규형은 어떤 문제를 다루나요?
```
아닙니다. BCNF는 함수적 종속성으로 인한 이상 현상만 없애기 때문에, 함수적 종속이 아닌 다른 종류의
종속성으로 인한 중복은 남을 수 있습니다.

제4정규형(4NF)은 다치 종속(Multi-Valued Dependency)을 다룹니다. 다치 종속은 한 속성 값에 대해
서로 독립적인 여러 값의 집합이 대응되는 관계입니다. 예를 들어 학생(학번, 취미, 수강과목)에서 한 학생의
취미와 수강과목은 서로 아무 관계가 없는데, 한 테이블에 두면 취미 2개 × 과목 3개 = 6개 행을 모든
조합으로 저장해야 합니다. 이 테이블은 모든 속성이 기본키라 BCNF는 만족하지만, 취미 하나를 추가하면 과목
수만큼 행을 추가해야 하는 이상 현상이 생깁니다. 4NF는 이를 학생취미(학번, 취미)와 학생과목(학번,
과목)으로 분해해 해결합니다.

제5정규형(5NF)은 조인 종속(Join Dependency)을 다룹니다. 테이블을 두 개로 나눠서는 무손실 분해가
안 되지만 세 개 이상으로 나눴다가 JOIN하면 원래대로 복원되는 경우로, 예를 들어 "공급자가 부품을
취급하고, 부품이 프로젝트에 쓰이고, 공급자가 프로젝트에 참여하면 반드시 공급자가 그 부품을 그
프로젝트에 공급한다"는 규칙이 있을 때, (공급자, 부품, 프로젝트) 테이블을 세 개의 이진 관계로 분해해
중복을 없앱니다. 다만 4·5정규형이 필요한 상황은 드물어 실무에서는 거의 다루지 않습니다.
```

- 정규화가 무조건 좋은가요? 그렇지 않다면, 어떤 상황에서 역정규화를 하는게 좋은지 설명해 주세요.
```
무조건 좋은 것은 아닙니다. 정규화를 할수록 테이블이 잘게 나뉘어 중복과 이상 현상은 줄지만, 데이터를
조회할 때 여러 테이블을 JOIN해야 해서 쿼리가 복잡해지고 성능이 떨어질 수 있습니다. 역정규화
(반정규화)는 성능을 위해 의도적으로 중복을 허용하거나 테이블을 합치는 것입니다.

역정규화를 고려할 만한 상황은 첫째, 조회가 쓰기보다 훨씬 많고, 자주 쓰는 조회에 JOIN이 많아 성능
문제가 실제로 확인된 경우입니다. 예를 들어 게시글 목록마다 작성자 이름을 보여주기 위해 매번 회원
테이블과 JOIN한다면, 게시글 테이블에 작성자 이름을 중복 저장할 수 있습니다. 둘째, 집계 값을 매번
계산하는 비용이 큰 경우입니다. 게시글의 댓글 수를 매번 COUNT하는 대신 게시글 테이블에 댓글 수 칼럼을
두고 댓글이 추가될 때마다 갱신합니다. 셋째, 통계·리포트처럼 대량의 과거 데이터를 분석하는 경우로,
조회 전용 요약 테이블을 따로 만듭니다.

다만 역정규화하면 중복된 데이터를 항상 일치시켜야 하는 책임이 생기므로(트리거나 애플리케이션 로직,
배치로 동기화), 먼저 인덱스 튜닝이나 캐시로 해결할 수 없는지 확인하고, 측정된 성능 문제가 있을 때
필요한 부분에만 적용하는 것이 좋습니다.
```

**핵심 키워드** → 정규화 = 함수적 종속 기준 테이블 분해(중복·이상 현상 제거, 무손실 분해, JOIN 증가 트레이드오프), 이상 현상(삽입·갱신·삭제), 1NF(원자값) → 2NF(부분 함수 종속 제거) → 3NF(이행적 함수 종속 제거) → BCNF(모든 결정자가 후보키), 3NF vs BCNF(종속되는 쪽이 주 속성이면 3NF는 허용, BCNF는 불허, 겹치는 복합 후보키에서 발생), 특강신청(학번, 과목, 교수)·주소(도시, 거리, 우편번호) 예시, BCNF 분해 시 종속성 보존 실패 가능, 4NF(다치 종속·독립 집합 조합 중복), 5NF(조인 종속), 역정규화(조회 위주·JOIN 비용·집계 칼럼·리포트 테이블, 중복 동기화 책임, 인덱스·캐시 먼저 검토)

<summary><b>꼬리 질문 1개 (펼치기)</b></summary>

- 그렇다면, View의 값을 수정해도 실제 테이블에는 반영되지 않나요?

</details>

**내 답변**

```
View는 하나 이상의 테이블에서 원하는 데이터를 조회하는 SELECT 쿼리를 이름을 붙여 저장해 둔 가상
테이블입니다. 실제 데이터를 따로 저장하지 않고 쿼리 정의만 저장하며, View를 조회하면 그 시점에 정의된
쿼리가 실행되어 원본 테이블의 최신 데이터를 보여줍니다.

사용하는 경우는 첫째, 복잡한 쿼리를 단순화할 때입니다. 여러 테이블을 JOIN하고 집계하는 쿼리를 자주
쓴다면 View로 만들어 두고 SELECT * FROM 주문요약처럼 간단히 조회할 수 있습니다. 둘째, 보안을 위해
접근을 제한할 때입니다. 회원 테이블에서 비밀번호나 주민번호 같은 민감한 칼럼을 뺀 View를 만들고,
사용자에게는 원본 테이블이 아닌 View에만 권한을 주면 필요한 데이터만 노출할 수 있습니다. 셋째, 논리적
독립성을 위해서입니다. 원본 테이블의 구조가 바뀌어도 View의 정의만 수정하면, View를 사용하던
애플리케이션 쿼리는 바꿀 필요가 없습니다.

단점으로는 View 자체에는 인덱스를 만들 수 없고, 복잡한 View를 조회하면 매번 원본 쿼리가 실행되어
성능이 기대보다 나쁠 수 있으며, View 위에 View를 겹쳐 쓰면 실행되는 실제 쿼리를 파악하기 어려워집니다.
결과를 실제로 저장해서 빠르게 조회하는 Materialized View(Oracle, PostgreSQL 지원)도 있지만, 이는
원본이 바뀔 때 별도로 갱신해야 합니다.
```

**꼬리 질문 답변**

- 그렇다면, View의 값을 수정해도 실제 테이블에는 반영되지 않나요?
```
반영됩니다. View는 데이터를 따로 저장하지 않는 가상 테이블이라, View에 INSERT, UPDATE, DELETE를
하면 실제로는 원본 테이블의 데이터가 수정됩니다. 단, 모든 View가 수정 가능한 것은 아닙니다. View의
한 행이 원본 테이블의 어느 한 행에 정확히 대응되어야, DBMS가 어떤 행을 수정할지 알 수 있기 때문입니다.

그래서 SUM, COUNT 같은 집계 함수, GROUP BY, DISTINCT, UNION을 사용한 View는 결과 한 행이 원본의
여러 행을 합친 것이라 수정할 수 없습니다. 계산식으로 만든 칼럼도 수정할 수 없고, JOIN한 View는
DBMS에 따라 한쪽 테이블의 칼럼만 수정하는 등 제한적으로 허용됩니다. 또한 View에 포함되지 않은 원본
칼럼이 NOT NULL이면서 기본값이 없다면, View로는 그 값을 넣을 수 없어 INSERT가 실패합니다.

추가로, WHERE 조건이 있는 View에 그 조건을 벗어나는 값으로 수정하면 수정 후 그 행이 View에서
사라져 버리는 문제가 있는데, View를 만들 때 WITH CHECK OPTION을 주면 View의 조건을 만족하지
않는 수정을 막을 수 있습니다.
```

**핵심 키워드** → View = 저장된 SELECT 쿼리(가상 테이블, 데이터 저장 X, 조회 시 원본 최신 데이터), 용도(복잡한 쿼리 단순화·민감 칼럼 숨겨 보안·논리적 독립성), 단점(인덱스 불가·매번 원본 쿼리 실행·중첩 시 파악 어려움), Materialized View(결과 저장·별도 갱신), View 수정 → 원본 테이블 반영, 수정 불가 조건(집계·GROUP BY·DISTINCT·UNION·계산 칼럼, JOIN은 제한적, 누락된 NOT NULL 칼럼), WITH CHECK OPTION

- Schema의 3계층에 대해 설명해 주세요.

</details>

**내 답변**

```
스키마는 데이터베이스의 구조와 제약 조건을 정의한 명세, 즉 데이터베이스의 설계도입니다. 어떤 테이블이
있고, 각 테이블에 어떤 칼럼이 어떤 타입으로 있는지, 기본키·외래키·NOT NULL 같은 제약 조건과 테이블
간의 관계는 무엇인지를 정의합니다. 스키마는 DDL(CREATE, ALTER)로 정의하며, 시스템 카탈로그(데이터
사전)에 저장됩니다.

스키마와 구분되는 개념이 인스턴스입니다. 스키마가 "학생 테이블은 학번, 이름, 학과로 이루어진다"는
틀이라면, 인스턴스는 특정 시점에 실제로 저장되어 있는 데이터의 집합입니다. 스키마는 한 번 정하면
잘 바뀌지 않는 반면, 인스턴스는 데이터가 삽입·수정될 때마다 계속 바뀝니다.

참고로 "스키마"라는 단어는 DBMS마다 가리키는 범위가 조금 다릅니다. MySQL에서는 스키마가 데이터베이스와
같은 의미(CREATE SCHEMA = CREATE DATABASE)이고, PostgreSQL이나 Oracle에서는 하나의 데이터베이스
안에서 테이블 같은 객체들을 묶는 네임스페이스(Oracle은 사용자 계정 단위)를 의미합니다.
```

**꼬리 질문 답변**

- Schema의 3계층에 대해 설명해 주세요.
```
ANSI/SPARC에서 정의한 3단계 스키마 구조로, 데이터베이스를 바라보는 관점에 따라 세 단계로 나눕니다.

외부 스키마(External Schema)는 개별 사용자나 애플리케이션의 관점에서 본 데이터베이스의 구조입니다.
전체 데이터 중 각자 필요한 부분만 보는 것으로, 서브 스키마라고도 하며 여러 개가 존재할 수 있습니다.
View가 대표적인 예입니다.

개념 스키마(Conceptual Schema)는 조직 전체의 관점에서 본 데이터베이스의 논리적 구조로, 데이터베이스에
하나만 존재합니다. 모든 테이블, 칼럼, 관계, 제약 조건, 접근 권한 등을 정의하며, 우리가 흔히 말하는
"스키마"가 이것입니다.

내부 스키마(Internal Schema)는 저장 장치의 관점에서 데이터가 디스크에 실제로 어떻게 저장되는지를
정의합니다. 레코드의 물리적 구조, 저장 순서, 인덱스, 데이터 파일의 구성 등이 해당합니다.

이렇게 나누는 목적은 데이터 독립성입니다. 개념 스키마가 바뀌어도 외부 스키마(애플리케이션)는 영향을
받지 않는 것을 논리적 독립성이라고 하고, 예를 들어 테이블에 칼럼이 추가되어도 View의 정의만 유지하면
기존 프로그램은 그대로 동작합니다. 내부 스키마가 바뀌어도 개념 스키마는 영향을 받지 않는 것을 물리적
독립성이라고 하고, 예를 들어 인덱스를 추가하거나 저장 장치를 바꿔도 테이블 구조와 쿼리는 그대로 쓸
수 있습니다. 각 단계 사이의 사상(Mapping)이 이 변경을 흡수합니다.
```

**핵심 키워드** → 스키마 = DB 구조·제약 조건 명세(테이블·칼럼·타입·키·관계, DDL, 시스템 카탈로그), 스키마(틀, 잘 안 바뀜) vs 인스턴스(특정 시점 실제 데이터), DBMS별 의미 차이(MySQL = DB, PostgreSQL·Oracle = 네임스페이스), 3단계 스키마(외부 = 사용자 관점·여러 개·View / 개념 = 조직 전체 논리 구조·하나 / 내부 = 물리 저장 구조·인덱스), 목적 = 데이터 독립성(논리적 독립성: 개념 변경 ↛ 외부, 물리적 독립성: 내부 변경 ↛ 개념), 사상(Mapping)

```
설계 아이디어이며, 개발자 간에 "여기는 전략 패턴으로 했다"처럼 설계 의도를 짧게 공유하는 공통 언어
역할도 합니다. GoF(Gang of Four)가 정리한 23가지 패턴이 대표적이고, 목적에 따라 세 가지로 나뉩니다.

생성 패턴은 객체를 생성하는 방식을 다룹니다. 싱글톤(Singleton)은 클래스의 인스턴스를 하나만 만들어
전역에서 공유하고, 팩토리 메서드(Factory Method)는 어떤 클래스의 객체를 만들지 결정하는 일을
하위 클래스나 별도 메서드에 맡겨 생성 코드와 사용 코드를 분리하며, 빌더(Builder)는 매개변수가 많은
객체를 단계적으로 읽기 쉽게 생성합니다.

구조 패턴은 클래스와 객체를 조합해 더 큰 구조를 만드는 방식을 다룹니다. 어댑터(Adapter)는 호환되지
않는 인터페이스를 변환해 함께 쓸 수 있게 하고, 프록시(Proxy)는 실제 객체 앞에 대리 객체를 두어 접근
제어, 지연 로딩, 부가 기능을 추가하며(Spring AOP, @Transactional이 이 방식), 데코레이터(Decorator)는
객체를 감싸 기능을 동적으로 덧붙입니다(Java I/O의 BufferedReader).

행위 패턴은 객체 간의 책임 분배와 상호작용 방식을 다룹니다. 전략(Strategy) 패턴은 알고리즘을
인터페이스로 분리해 실행 중에 갈아 끼울 수 있게 하고(Comparator), 옵저버(Observer) 패턴은 한 객체의
상태가 바뀌면 그것을 구독하는 객체들에게 자동으로 알리며(이벤트 리스너), 템플릿 메서드(Template
Method)는 알고리즘의 큰 흐름은 상위 클래스가 정하고 세부 단계만 하위 클래스가 구현합니다.
```

- Singleton의 장단점에 대해 설명해 주세요.
```
장점은 첫째, 인스턴스를 하나만 만들어 재사용하므로, DB 커넥션 풀, 설정 정보, 로거처럼 생성 비용이
크거나 여러 개일 필요가 없는 객체의 메모리와 생성 비용을 아낄 수 있습니다. 둘째, 애플리케이션 어디서든
같은 인스턴스에 접근할 수 있어 데이터를 공유하기 쉽습니다.

단점은 첫째, 전역 상태처럼 동작하기 때문에 싱글톤에 가변 상태를 두면 여러 곳에서 값을 바꿔 동작을
예측하기 어렵고, 멀티스레드 환경에서는 동시성 문제가 생깁니다. 둘째, 사용하는 클래스가
Singleton.getInstance()로 구체 클래스에 직접 의존하게 되어 결합도가 높아지고, 의존성 역전 원칙(DIP)과
개방-폐쇄 원칙(OCP)을 위반하기 쉽습니다. 셋째, 테스트가 어렵습니다. 인스턴스를 가짜 객체로 바꾸기
어렵고, 상태가 테스트 간에 공유되어 테스트 순서에 따라 결과가 달라질 수 있습니다. 넷째, private
생성자 때문에 상속이 어렵습니다.

Spring은 이 단점을 보완해서, 클래스 자체를 싱글톤으로 만들지 않고 스프링 컨테이너가 빈(Bean)을

인터페이스에 의존할 수 있고 테스트도 쉽습니다. 다만 이 경우에도 빈은 여러 스레드가 공유하므로 상태를
갖지 않는(Stateless) 구조로 설계해야 합니다.
```

- Singleton이 하나의 객체를 생성한다는 것을 어떻게 보장할 수 있을까요?
```
기본은 생성자를 private으로 막아 외부에서 new로 만들 수 없게 하고, static 메서드로만 유일한 인스턴스를
얻게 하는 것입니다. 문제는 멀티스레드 환경입니다. "인스턴스가 null이면 생성"하는 지연 초기화를 단순하게
구현하면, 두 스레드가 동시에 null을 확인하고 각각 객체를 만들 수 있습니다. 이를 해결하는 방법은
다음과 같습니다.

첫째, 즉시 초기화(Eager Initialization)입니다. private static final 필드에 클래스 로딩 시점에
바로 생성해 둡니다. 클래스 로딩은 JVM이 스레드 안전하게 한 번만 수행하므로 안전하지만, 사용하지 않아도
생성됩니다. 둘째, getInstance()에 synchronized를 붙이는 방법은 안전하지만 매번 락을 잡아 느립니다.
셋째, DCL(Double-Checked Locking)은 null일 때만 synchronized 블록에 들어가 한 번 더 확인하는
방식으로, 반드시 필드에 volatile을 붙여야 합니다. 그렇지 않으면 명령어 재배치 때문에 다른 스레드가
생성자 실행이 끝나지 않은 객체를 볼 수 있습니다.

넷째, 가장 많이 권장되는 Bill Pugh 방식(LazyHolder)입니다. 인스턴스를 static 내부 클래스의 static
final 필드로 두면, 내부 클래스는 getInstance()가 처음 호출될 때 로딩되므로 지연 초기화가 되고, 클래스
로딩의 스레드 안전성을 그대로 이용하므로 락이 필요 없습니다. 다섯째, enum 싱글톤입니다. JVM이 enum
상수가 하나만 존재함을 보장하므로, 리플렉션으로 private 생성자를 강제로 호출하거나 직렬화·역직렬화로
새 객체가 만들어지는 공격까지 막을 수 있어 가장 안전합니다(Effective Java 권장).
```

```
Java에서 static은 해당 멤버가 객체(인스턴스)가 아니라 클래스 자체에 속한다는 의미입니다. 그래서

static 변수(클래스 변수)는 객체마다 따로 만들어지는 인스턴스 변수와 달리 클래스당 하나만 존재해서,
예를 들어 생성된 객체 수를 세는 카운터처럼 모든 객체가 공유해야 하는 값에 씁니다. static 메서드는
객체 없이 호출되므로 this를 쓸 수 없고, 인스턴스 변수나 인스턴스 메서드에 직접 접근할 수 없습니다.
그래서 객체의 상태와 상관없이 입력만으로 동작하는 유틸리티 메서드나 팩토리 메서드에 적합합니다. 그 외에
클래스가 처음 로딩될 때 한 번 실행되는 static 초기화 블록, 바깥 클래스의 인스턴스 없이 생성할 수 있는
static 중첩 클래스, 클래스 이름 없이 static 멤버를 쓰게 해주는 static import가 있습니다.

주의할 점으로, static 변수는 프로그램이 끝날 때까지 메모리에 남고 모든 곳에서 공유되는 전역 상태라서,
가변 static 변수를 남용하면 메모리 누수나 멀티스레드 동시성 문제, 테스트하기 어려운 코드가 될 수
있습니다. 또한 static 메서드는 오버라이딩되지 않습니다(같은 시그니처로 선언하면 숨김(hiding)이
됩니다).
```

**꼬리 질문 답변**

- 컴파일 할 때, static 키워드가 붙은 변수, 함수는 어떻게 처리되나요?
```
Java 기준으로 설명하면, 컴파일 시점에는 static 멤버도 .class 파일에 ACC_STATIC 플래그가 붙은 필드와
메서드로 기록될 뿐이고, 실제 메모리 할당과 초기화는 런타임에 클래스가 로딩될 때 일어납니다.

static 변수에 대입하는 초기값과 static 블록은 컴파일러가 모아서 <clinit>이라는 클래스 초기화 메서드로
만듭니다. 런타임에 클래스가 처음 사용되는 시점(객체 생성, static 멤버 접근 등)에 클래스 로더가 클래스를
로딩하고, 링킹의 준비(Preparation) 단계에서 static 변수의 메모리를 할당해 기본값(0, null)으로 채운
뒤, 초기화(Initialization) 단계에서 <clinit>을 실행해 실제 값을 넣습니다. 이 초기화는 JVM이 스레드
안전하게 딱 한 번만 수행합니다. static 변수는 Java 8부터 힙 영역의 Class 객체와 함께 저장되고,
클래스의 메타데이터는 메서드 영역(Metaspace)에 저장됩니다.

static 메서드는 호출할 객체가 필요 없으므로 컴파일러가 invokestatic 명령어로 컴파일합니다. 인스턴스
메서드처럼 실행 중에 객체의 실제 타입을 보고 어떤 메서드를 호출할지 정하는 동적 바인딩이 아니라, 컴파일
시점에 호출할 메서드가 정해지는 정적 바인딩이라 오버라이딩이 되지 않습니다. 예외적으로 static final이면서
컴파일 시점에 값이 정해지는 기본형·문자열 상수는 컴파일러가 그 값을 사용하는 코드에 직접 박아 넣습니다
(상수 인라이닝).

(참고로 C/C++에서는 static 전역 변수가 프로그램 시작 시 데이터 영역(초기화 여부에 따라 .data/.bss)에
잡히고, static 함수와 전역 변수는 해당 파일 안에서만 보이도록 내부 링크(internal linkage)로
처리됩니다.)
```

- Java에서 static과 static final은 어떤 차이를 갖나요? final과 static final은요?
```
static은 "클래스에 하나만 존재"한다는 의미이고, final은 "한 번 초기화되면 다시 대입할 수 없다"는
의미로, 서로 독립적인 두 성질입니다.

static과 static final의 차이는 값을 바꿀 수 있는지입니다. static 변수는 클래스에 하나만 있지만 값을
언제든 바꿀 수 있는 공유 변수이고, static final 변수는 클래스에 하나만 있으면서 값도 바꿀 수 없는
상수입니다. 그래서 MAX_SIZE처럼 모든 객체가 공유하는 고정 값은 static final로 선언하고 대문자로
이름 짓습니다. static final은 선언할 때나 static 블록에서 반드시 한 번 초기화해야 합니다.

final과 static final의 차이는 값이 어디에 속하는지입니다. final 인스턴스 변수는 객체마다 따로 존재하며,
생성자에서 객체마다 다른 값으로 초기화할 수 있고 그 뒤로는 바꿀 수 없습니다. 예를 들어 각 회원의 가입
번호처럼 객체마다 다르지만 한 번 정해지면 바뀌지 않는 값에 씁니다. 반면 static final은 모든 객체에
공통인 단 하나의 값입니다. 따라서 모든 객체에 같은 값을 final 인스턴스 변수로 두면 객체마다 같은 값을
중복 저장하는 셈이라, 그런 경우는 static final로 선언하는 것이 좋습니다.

주의할 점은 final은 참조를 바꾸지 못하게 할 뿐, 참조하는 객체의 내부 상태까지 불변으로 만들지는
않는다는 것입니다. static final List<String> LIST = new ArrayList<>()에 LIST.add()는 여전히
가능하므로, 진짜 불변이 필요하면 List.of()나 Collections.unmodifiableList()를 사용해야 합니다.
```

**핵심 키워드** → static = 인스턴스가 아닌 클래스에 속함(객체 없이 접근·모든 객체가 공유), static 변수(클래스당 하나), static 메서드(this·인스턴스 멤버 접근 불가, 유틸·팩토리), static 블록·중첩 클래스·import, 남용 시 전역 상태 문제·오버라이딩 X(hiding), 처리 과정(.class에 ACC_STATIC → 클래스 로딩 시 준비 단계 기본값 → 초기화 단계 <clinit> 한 번 실행, static 변수는 힙의 Class 객체, 메타데이터는 Metaspace), invokestatic·정적 바인딩, 상수 인라이닝, C/C++ static(데이터 영역·내부 링크), static(공유·변경 가능) vs static final(공유 상수), final(객체마다·생성자 초기화) vs static final(클래스 공통 하나), final은 참조만 고정(List.of로 진짜 불변)

```java
class MyHashTable<K, V> {

    private static class Node<K, V> {
        final K key;
        V value;
        Node<K, V> next;

        Node(K key, V value, Node<K, V> next) {
            this.key = key;
            this.value = value;
            this.next = next;
        }
    }

    private static final double LOAD_FACTOR = 0.75;

    private Node<K, V>[] buckets;
    private int size;

    @SuppressWarnings("unchecked")
    MyHashTable() {
        buckets = (Node<K, V>[]) new Node[16];
        size = 0;
    }

    // 음수 hashCode도 있으므로 floorMod로 항상 0 ~ length-1 범위의 인덱스로 변환
    private int indexFor(Object key, int length) {
        return Math.floorMod(key.hashCode(), length);
    }

    void put(K key, V value) {
        if (key == null) throw new IllegalArgumentException("key must not be null");

        int index = indexFor(key, buckets.length);
        for (Node<K, V> node = buckets[index]; node != null; node = node.next) {
            if (node.key.equals(key)) { // 이미 있는 키면 값만 덮어씀
                node.value = value;
                return;
            }
        }

        buckets[index] = new Node<>(key, value, buckets[index]); // 체인의 맨 앞에 추가
        size++;

        if (size > buckets.length * LOAD_FACTOR) resize();
    }

    V get(K key) {
        if (key == null) return null;

        for (Node<K, V> node = buckets[indexFor(key, buckets.length)]; node != null; node = node.next) {
            if (node.key.equals(key)) return node.value;
        }
        return null;
    }

    V remove(K key) {
        if (key == null) return null;

        int index = indexFor(key, buckets.length);
        Node<K, V> prev = null;
        for (Node<K, V> node = buckets[index]; node != null; prev = node, node = node.next) {
            if (node.key.equals(key)) {
                if (prev == null) buckets[index] = node.next; // 체인의 첫 노드를 지우는 경우
                else prev.next = node.next;
                size--;
                return node.value;
            }
        }
        return null;
    }

    int size() {
        return size;
    }

    // 버킷 수를 2배로 늘리고, 모든 노드를 새 인덱스로 다시 분배 (재해싱)
    @SuppressWarnings("unchecked")
    private void resize() {
        Node<K, V>[] old = buckets;
        buckets = (Node<K, V>[]) new Node[old.length * 2];

        for (Node<K, V> head : old) {
            Node<K, V> node = head;
            while (node != null) {
                Node<K, V> next = node.next;
                int index = indexFor(node.key, buckets.length);
                node.next = buckets[index];
                buckets[index] = node;
                node = next;
            }
        }
    }
}
```

**체이닝 방식 설명** — 배열의 각 칸(버킷)에 연결 리스트를 두고, 해시 값이 같은 키(충돌)는 같은 버킷의 리스트에 이어 붙입니다. `put`은 해당 버킷을 훑어 같은 키가 있으면 값을 덮어쓰고 없으면 맨 앞에 추가, `get`은 버킷을 훑어 `equals`로 같은 키를 찾고, `remove`는 이전 노드의 `next`를 다음 노드로 연결해 리스트에서 빼냅니다. 키 비교에 `hashCode`가 아닌 `equals`를 쓰는 이유는 서로 다른 키도 해시 값이 같을 수 있기 때문입니다.

**load factor와 리사이징** — load factor는 `저장된 원소 수 / 버킷 수`로, 버킷 하나에 평균 몇 개의 원소가 들어있는지를 뜻합니다. 이 값이 커질수록 체인이 길어져 탐색이 O(1)에서 점점 느려지므로, 0.75(Java HashMap과 같은 값)를 넘으면 버킷 수를 2배로 늘립니다. 버킷 수가 바뀌면 `hashCode % 버킷 수`로 계산되는 인덱스도 바뀌기 때문에, 단순히 배열을 복사하면 안 되고 모든 원소의 인덱스를 다시 계산해 새 배열에 넣는 재해싱이 필요합니다. 0.75는 메모리 낭비(값이 작을 때)와 충돌 증가(값이 클 때) 사이의 절충값입니다.

**개방 주소법과의 차이** — 개방 주소법(Open Addressing)은 연결 리스트 없이 배열 하나만 사용하고, 충돌이 나면 정해진 규칙으로 배열의 다른 빈칸을 찾아 저장합니다. 다음 칸을 차례로 보는 선형 탐사(Linear Probing), 1², 2², 3²칸씩 건너뛰는 제곱 탐사(Quadratic Probing), 두 번째 해시 함수로 건너뛸 간격을 정하는 이중 해싱(Double Hashing)이 있습니다. 노드 객체와 포인터가 없어 메모리를 적게 쓰고, 데이터가 배열에 연속으로 있어 CPU 캐시 효율이 좋다는 장점이 있습니다. 대신 배열이 차면 탐사 길이가 급격히 길어지므로 load factor를 0.5~0.7 정도로 더 낮게 유지해야 하고, 선형 탐사는 데이터가 한곳에 뭉치는 클러스터링 문제가 있습니다. 또 `remove` 시 칸을 그냥 비우면 그 뒤에 탐사로 저장된 키를 찾을 때 탐색이 중간에 끊기므로, "삭제됨" 표시(Tombstone)를 남겨야 합니다. 체이닝은 삭제가 간단하고 load factor가 1을 넘어도 동작하지만 노드마다 추가 메모리가 듭니다. (Java HashMap은 체이닝을 쓰고, 한 버킷의 노드가 8개를 넘으면 연결 리스트를 레드-블랙 트리로 바꿔 최악의 탐색을 O(log N)으로 줄입니다.)

**시간복잡도** → `put`·`get`·`remove` 평균 O(1), 최악 O(N) (모든 키가 한 버킷에 충돌할 때), 리사이징은 한 번에 O(N)이지만 분할 상환하면 `put`당 O(1)
**공간복잡도** → O(N + M) (N = 원소 수, M = 버킷 수, load factor 제한으로 M은 O(N) 수준)

#### 7. 알파벳으로 이뤄진 단어가 있을 때, 이 단어에서 중복된 값을 제거하고 오름차순으로 정렬하는 코드를 작성해 보세요. (단, 최대한 효율적으로 작성해 주세요.)

```java
class DedupSort {

    // 알파벳은 52가지(대문자 26 + 소문자 26)뿐이므로, 정렬 대신 "등장 여부"만 체크하는 계수 방식
    static String dedupAndSort(String word) {
        boolean[] seen = new boolean[128]; // ASCII 코드를 인덱스로 사용

        for (int i = 0; i < word.length(); i++) {
            char c = word.charAt(i);
            if (!Character.isLetter(c) || c >= 128) {
                throw new IllegalArgumentException("알파벳이 아닌 문자: " + c);
            }
            seen[c] = true;
        }

        // ASCII 순서대로 훑으면 자동으로 오름차순 (대문자 'A'~'Z' → 소문자 'a'~'z')
        StringBuilder result = new StringBuilder();
        for (char c = 'A'; c <= 'z'; c++) {
            if (seen[c]) result.append(c);
        }
        return result.toString();
    }

    public static void main(String[] args) {
        System.out.println(dedupAndSort("banana"));      // abn
        System.out.println(dedupAndSort("programming")); // agimnopr
        System.out.println(dedupAndSort("HelloWorld"));  // HWdelor
    }
}
```

**풀이 설명**

가장 먼저 떠오르는 방법은 `TreeSet`에 문자를 모두 넣는 것(O(N log K))이나, 문자 배열을 `Arrays.sort`로 정렬한 뒤 이웃한 중복을 건너뛰는 것(O(N log N))입니다. 하지만 입력이 **알파벳으로만** 이루어진다는 조건 덕분에, 나올 수 있는 값의 종류가 52개로 고정되어 있다는 점을 이용하면 비교 정렬 없이 더 빠르게 풀 수 있습니다.

계수 정렬(Counting Sort)의 아이디어를 응용해서, ASCII 코드를 인덱스로 하는 크기 128의 `boolean` 배열을 만들고 단어를 한 번 훑으며 등장한 문자를 `true`로 표시합니다. 중복된 문자는 같은 칸을 다시 `true`로 만들 뿐이라 자연스럽게 제거됩니다. 그 뒤 배열을 'A'부터 'z'까지 순서대로 훑으면서 `true`인 문자만 이어 붙이면, ASCII 코드 순서가 곧 알파벳 오름차순이므로 별도의 정렬 없이 결과가 정렬된 상태로 나옵니다. ('Z'와 'a' 사이의 몇몇 기호 칸은 항상 `false`라 건너뛰어집니다.)

정렬 기준은 ASCII 순서라 대문자가 소문자보다 앞에 옵니다. 대소문자를 구분하지 않아야 한다면 `Character.toLowerCase`로 바꾼 뒤 크기 26의 배열(`c - 'a'`)을 쓰면 되고, 값이 26가지뿐이니 `boolean` 배열 대신 `int` 하나의 비트 26개로 등장 여부를 표시하는 비트마스크로도 구현할 수 있습니다.

**시간복잡도** → O(N) (단어를 한 번 훑기 O(N) + 고정 크기 배열 훑기 O(1)), 비교 정렬의 O(N log N)보다 빠름
**공간복잡도** → O(1) (입력 크기와 무관한 고정 크기 128 배열, 결과 문자열도 최대 52자)
