## 1. Key (기본키, 후보키, 슈퍼키 등)에 대해 설명해 주세요.

### 내 답변

키는 테이블에서 행을 식별하거나 다른 테이블과 관계를 맺기 위해 사용하는 속성입니다.

- **슈퍼키(Super Key)**: 행을 유일하게 식별할 수 있는 속성의 집합
- **후보키(Candidate Key)**: 슈퍼키 중 최소성을 만족하는 키
- **기본키(Primary Key)**: 후보키 중 대표로 선택한 키
- **대체키(Alternate Key)**: 후보키 중 기본키로 선택되지 않은 키
- **외래키(Foreign Key)**: 다른 테이블의 기본키 또는 UNIQUE 키를 참조하는 키
- **복합키(Composite Key)**: 둘 이상의 컬럼으로 구성된 키

기본키는 `NULL`을 가질 수 없고 중복될 수 없습니다.

### 핵심 키워드

`유일성`, `최소성`, `Primary Key`, `Candidate Key`, `Super Key`, `Foreign Key`

### 꼬리 질문

#### 기본키는 수정이 가능한가요?

기술적으로는 수정할 수 있습니다.

하지만 기본키가 다른 테이블의 외래키에서 참조되고 있다면 연쇄적으로 영향을 줄 수 있기 때문에 일반적으로 자주 변경되지 않는 값을 기본키로 선택하는 것이 좋습니다.

그래서 주민번호나 이메일처럼 변경 가능성이 있는 값보다는 Auto Increment ID나 UUID 같은 대리키를 사용하는 경우가 많습니다.

#### MySQL은 기본키가 없어도 테이블 생성이 가능한데 왜 그런가요?

기본키는 관계형 모델에서 행을 식별하기 위한 중요한 요소지만, SQL 문법상 모든 테이블에 반드시 명시해야 하는 것은 아닙니다.

특히 InnoDB는 명시적인 Primary Key가 없으면 적절한 `UNIQUE NOT NULL` 인덱스를 찾아 클러스터링 키로 사용할 수 있고, 그것도 없다면 내부적으로 숨겨진 행 ID를 생성해 사용할 수 있습니다.

#### 외래키 값은 NULL이 들어올 수 있나요?

가능합니다.

외래키 컬럼이 `NOT NULL`로 선언되지 않았다면 `NULL`을 가질 수 있습니다.

`NULL`은 특정 부모 행을 참조하지 않는다는 의미로 사용할 수 있습니다.

#### UNIQUE 컬럼을 활용한 쿼리 성능은 어떻게 달라지나요?

DBMS는 일반적으로 UNIQUE 제약조건을 구현하기 위해 인덱스를 생성합니다.

따라서 해당 컬럼을 조건으로 검색하는 쿼리는 인덱스를 이용할 수 있어 Full Scan보다 빠를 가능성이 높습니다.

단, 실제 성능은 데이터 분포와 옵티마이저 판단에 따라 달라집니다.

## 2. RDB와 NoSQL의 차이에 대해 설명해 주세요.

### 내 답변

RDB는 데이터를 테이블 형태로 저장하고, 정해진 스키마와 관계를 기반으로 데이터를 관리합니다.

SQL을 사용하고 JOIN, 트랜잭션, 제약조건 등을 통해 데이터 정합성을 강하게 보장할 수 있습니다.

NoSQL은 관계형 모델 이외의 다양한 데이터 모델을 사용하는 데이터베이스를 통칭합니다.

대표적으로 Key-Value, Document, Column Family, Graph 형태가 있습니다.

NoSQL은 유연한 스키마와 수평 확장에 유리한 경우가 많지만, 제품에 따라 JOIN이나 강한 트랜잭션 기능이 제한적일 수 있습니다.

### 핵심 키워드

`RDB`, `정형 스키마`, `SQL`, `JOIN`, `ACID`, `NoSQL`, `수평 확장`, `Document`, `Key-Value`

### 꼬리 질문

#### NoSQL의 강점과 약점은 무엇인가요?

강점:
- 유연한 스키마
- 대규모 분산 환경에 적합한 제품이 많음
- 수평 확장이 비교적 쉬운 경우가 많음
- 데이터 구조에 맞는 특화된 모델 사용 가능

약점:
- DB 제품마다 쿼리 방식이 다름
- JOIN이나 복잡한 관계 표현이 어려울 수 있음
- 데이터 중복이 증가할 수 있음
- 일관성 모델이 RDB보다 느슨할 수 있음

#### 왜 RDB가 NoSQL보다 부하가 많이 걸릴 수 있나요?

RDB는 JOIN, 제약조건, 트랜잭션, Lock, 인덱스 유지 등 데이터 정합성을 보장하기 위한 추가 작업이 발생할 수 있습니다.

하지만 이것이 곧 NoSQL이 무조건 빠르다는 의미는 아닙니다.

워크로드와 데이터 모델에 따라 RDB가 더 빠른 경우도 많습니다.

#### NoSQL을 활용한 경험이 있나요?

실제 경험이 있다면 프로젝트 기준으로 답변해야 합니다.

예:

> Firebase Firestore를 사용해 본 경험이 있습니다. 모바일 앱에서 사용자별 관리비 데이터와 커뮤니티 데이터를 저장했는데, 빠르게 개발해야 했고 서버를 직접 운영하지 않아도 되며 문서 단위 데이터 구조가 화면 중심 데이터 모델과 잘 맞아 선택했습니다.

## 3. 트랜잭션이 무엇이고, ACID 원칙에 대해 설명해 주세요.

### 내 답변

트랜잭션은 데이터베이스에서 하나의 논리적인 작업 단위입니다.

여러 SQL이 하나의 작업을 구성할 때, 모두 성공하거나 모두 실패하도록 묶을 수 있습니다.

ACID는 트랜잭션이 가져야 할 대표적인 성질입니다.

- **Atomicity**: 모두 수행되거나 모두 수행되지 않아야 함
- **Consistency**: 트랜잭션 전후 데이터 무결성이 유지되어야 함
- **Isolation**: 동시에 수행되는 트랜잭션이 서로 영향을 최소화해야 함
- **Durability**: Commit된 결과는 장애가 발생해도 유지되어야 함

### 핵심 키워드

`Atomicity`, `Consistency`, `Isolation`, `Durability`, `Commit`, `Rollback`

### 꼬리 질문

#### Durability는 어떻게 보장하나요?

DBMS는 일반적으로 Redo Log나 WAL(Write Ahead Logging)을 사용합니다.

데이터 페이지를 디스크에 바로 반영하기 전에 변경 내역을 로그에 기록하고, 장애 발생 시 로그를 이용해 Commit된 내용을 복구할 수 있습니다.

#### 트랜잭션은 언제 사용하나요?

여러 변경 작업이 하나의 논리적 작업으로 처리되어야 할 때 사용합니다.

예:

```text
계좌 A에서 10,000원 차감
→ 계좌 B에 10,000원 증가
```

두 작업 중 하나만 성공하면 데이터가 잘못되므로 하나의 트랜잭션으로 묶어야 합니다.

#### 읽기에는 트랜잭션을 걸지 않아도 될까요?

단순 조회 하나라면 명시적인 트랜잭션이 필요하지 않은 경우가 많습니다.

하지만 여러 번의 조회 결과가 동일한 시점의 데이터여야 하는 경우에는 읽기 전용 트랜잭션도 필요할 수 있습니다.

## 4. 트랜잭션 격리 레벨에 대해 설명해 주세요.

### 내 답변

트랜잭션 격리 수준은 동시에 실행되는 트랜잭션이 서로의 변경 사항을 어느 정도 볼 수 있는지를 결정하는 기준입니다.

대표적으로 네 단계가 있습니다.

| 레벨 | Dirty Read | Non-Repeatable Read | Phantom Read |
|---|---|---|---|
| READ UNCOMMITTED | 발생 가능 | 발생 가능 | 발생 가능 |
| READ COMMITTED | 방지 | 발생 가능 | 발생 가능 |
| REPEATABLE READ | 방지 | 방지 | 발생 가능 |
| SERIALIZABLE | 방지 | 방지 | 방지 |

격리 수준이 높을수록 일관성은 강해지지만 동시성이 떨어질 수 있습니다.

### 핵심 키워드

`Dirty Read`, `Non-Repeatable Read`, `Phantom Read`, `READ COMMITTED`, `REPEATABLE READ`, `SERIALIZABLE`

### 꼬리 질문

#### 모든 DBMS가 4개 레벨을 동일하게 구현하나요?

아닙니다.

SQL 표준에서 정의하고 있지만 DBMS마다 MVCC와 Lock 구현 방식이 다르기 때문에 실제 동작은 다를 수 있습니다.

#### MySQL InnoDB의 Undo와 Redo는 무엇인가요?

- **Undo Log**: 변경 이전 값을 보관하며 Rollback과 MVCC에 사용
- **Redo Log**: 변경 이후 내용을 기록하며 장애 복구와 Durability 보장에 사용

#### 스토리지 엔진이 무엇인가요?

DBMS 내부에서 실제 데이터를 저장하고 읽고 수정하는 부분입니다.

MySQL은 SQL 처리 계층과 스토리지 엔진을 분리하고 있으며 대표적인 스토리지 엔진이 InnoDB입니다.

InnoDB는 트랜잭션, MVCC, Row Lock, 외래키 등을 지원합니다.

## 5. 인덱스가 무엇이고, 언제 사용하는지 설명해 주세요.

### 내 답변

인덱스는 테이블 전체를 탐색하지 않고 원하는 데이터를 빠르게 찾을 수 있도록 별도로 관리하는 자료구조입니다.

일반적으로 B+Tree 기반 인덱스를 많이 사용합니다.

WHERE, JOIN, ORDER BY, GROUP BY에 자주 사용되는 컬럼에 인덱스를 생성하면 조회 성능을 높일 수 있습니다.

대신 INSERT, UPDATE, DELETE 시 인덱스도 함께 수정해야 하므로 쓰기 비용과 저장 공간이 증가합니다.

### 핵심 키워드

`B+Tree`, `검색 성능`, `쓰기 비용`, `선택도`, `복합 인덱스`, `Covering Index`

### 꼬리 질문

#### 수정이 잦은 테이블에 인덱스를 많이 만들면 왜 안 좋나요?

데이터가 변경될 때마다 인덱스도 갱신해야 하기 때문입니다.

인덱스가 많으면 INSERT/UPDATE/DELETE의 비용이 증가하고 저장 공간도 많이 사용합니다.

#### 인덱스에서 선택하지 않은 값도 정책을 그대로 따라가나요?

인덱스는 실제 테이블의 모든 값을 정렬해 두는 것이 아니라 인덱스로 지정한 컬럼의 값과 행 위치 정보를 관리합니다.

따라서 인덱스에 포함되지 않은 컬럼은 해당 인덱스의 정렬/탐색 구조에 직접 참여하지 않습니다.

#### ORDER BY / GROUP BY와 인덱스

적절한 인덱스의 순서와 쿼리의 정렬 조건이 일치하면 추가 정렬 없이 인덱스를 순서대로 읽을 수 있습니다.

반대로 적절한 인덱스가 없으면 DBMS가 별도의 Sort 작업을 수행할 수 있습니다.

#### 기본키는 인덱스인가요?

기본키 자체는 제약조건입니다.

하지만 DBMS는 기본키의 유일성과 검색 성능을 보장하기 위해 일반적으로 인덱스를 생성합니다.

MySQL InnoDB에서는 기본키가 클러스터드 인덱스 역할을 합니다.

#### 외래키는 인덱스인가요?

외래키 자체는 관계 무결성을 위한 제약조건입니다.

DBMS에 따라 외래키 인덱스를 자동으로 생성하거나 사용자가 직접 생성해야 할 수 있습니다.

#### 인덱스가 물리적 저장에 영향을 미치나요?

인덱스 종류에 따라 다릅니다.

MySQL InnoDB의 클러스터드 인덱스는 실제 레코드가 기본키 순서의 B+Tree Leaf에 저장되므로 물리적 조직에 큰 영향을 줍니다.

보조 인덱스는 별도의 구조로 관리됩니다.

#### NoSQL에도 인덱스가 있나요?

있습니다.

MongoDB는 B-Tree 계열 인덱스를 제공하며 다양한 필드에 인덱스를 생성할 수 있습니다.

Redis는 기본적으로 Key 자체에 매우 빠르게 접근하며 Sorted Set 등 자료구조가 별도의 정렬/탐색 구조 역할을 할 수 있습니다.

#### 복합 인덱스 `(A, B)`에서 B만 조건으로 사용하면?

일반적인 B-Tree 복합 인덱스는 왼쪽 컬럼부터 정렬되므로 `A` 조건 없이 `B`만 사용하면 효율적으로 사용하기 어렵습니다.

이를 **Leftmost Prefix** 원칙이라고 합니다.

DBMS와 실행 계획에 따라 일부 최적화가 가능할 수 있지만 기본 원칙은 `(A, B)`에서 A가 중요합니다.

## 6. RDBMS, NoSQL에서의 클러스터링/레플리케이션 방식에 대해 설명해 주세요.

### 내 답변

레플리케이션은 동일한 데이터를 여러 DB 서버에 복제하는 방식입니다.

주로 가용성을 높이거나 읽기 트래픽을 분산하기 위해 사용합니다.

클러스터링은 여러 서버를 하나의 시스템처럼 동작하게 구성하는 더 넓은 개념으로 볼 수 있습니다.

구현 방식에 따라 Active-Active, Active-Standby, Primary-Replica 등의 구조가 있습니다.

### 핵심 키워드

`Replication`, `Primary-Replica`, `Failover`, `Read Replica`, `Sharding`, `Distributed Transaction`

### 꼬리 질문

#### 분산 환경에서 트랜잭션은 어떻게 관리하나요?

전통적으로 2PC(Two Phase Commit) 같은 분산 트랜잭션 프로토콜을 사용할 수 있습니다.

마이크로서비스 환경에서는 강한 분산 트랜잭션 대신 Saga Pattern과 보상 트랜잭션을 사용하기도 합니다.

#### Replica 동기화 전 데이터 정합성은?

비동기 복제에서는 Replication Lag 때문에 최신 데이터가 Replica에 아직 반영되지 않을 수 있습니다.

방법:
- 중요한 읽기는 Primary에서 수행
- 동기식 복제 사용
- Read-after-write 보장 전략
- 일정 시간 Primary를 읽도록 Sticky 처리

#### 다중 트랜잭션의 Deadlock 해결 방법

DBMS는 Wait-for Graph 등을 이용해 Deadlock을 탐지하고, 관련 트랜잭션 중 하나를 Victim으로 선택해 Rollback시킬 수 있습니다.

애플리케이션에서는 트랜잭션을 짧게 유지하고 Lock 획득 순서를 일정하게 만드는 것이 중요합니다.

#### Sharding과 Replication 중 무엇을 사용할 것인가요?

목적이 다릅니다.

- Replication: 가용성, 읽기 확장
- Sharding: 데이터 자체를 여러 서버에 분할해 저장 용량과 쓰기 트래픽 분산

필요하다면 둘을 함께 사용할 수 있습니다.

## 7. 정규화가 무엇인가요?

### 내 답변

정규화는 데이터 중복을 줄이고 데이터의 삽입, 수정, 삭제 과정에서 발생할 수 있는 이상 현상을 줄이기 위해 테이블을 구조화하는 과정입니다.

대표적으로 1NF, 2NF, 3NF, BCNF가 있습니다.

### 핵심 키워드

`중복 제거`, `삽입 이상`, `수정 이상`, `삭제 이상`, `함수 종속`, `BCNF`

### 꼬리 질문

#### 정규화를 하지 않으면 어떤 이상 현상이 발생하나요?

- 삽입 이상: 특정 정보가 없으면 다른 정보를 삽입할 수 없음
- 수정 이상: 중복된 데이터를 모두 수정하지 않아 불일치 발생
- 삭제 이상: 한 데이터를 삭제하면서 다른 필요한 데이터까지 함께 삭제

#### 1NF / 2NF / 3NF

**1NF**
- 모든 컬럼 값이 원자값

**2NF**
- 1NF 만족
- 기본키 일부에만 종속되는 부분 함수 종속 제거

**3NF**
- 2NF 만족
- 기본키가 아닌 속성 간 이행 함수 종속 제거

#### BCNF와 3NF 차이

BCNF는 모든 결정자가 후보키여야 합니다.

3NF보다 더 강한 조건입니다.

3NF는 특정 조건에서 후보키가 아닌 결정자를 허용할 수 있지만 BCNF는 허용하지 않습니다.

#### 3NF를 만족하지만 BCNF를 만족하지 않을 수 있나요?

가능합니다.

후보키가 여러 개 존재하고 후보키의 일부 속성이 다른 속성을 결정하는 특수한 함수 종속 관계에서 발생할 수 있습니다.

#### BCNF면 모든 이상 현상이 사라지나요?

아닙니다.

BCNF는 주로 함수 종속을 다룹니다.

4NF는 다치 종속(Multivalued Dependency), 5NF는 조인 종속(Join Dependency) 문제를 다룹니다.

#### 정규화가 무조건 좋은가요?

아닙니다.

조회 성능이 매우 중요하고 JOIN 비용이 큰 경우 일부 데이터를 중복 저장하는 역정규화를 사용할 수 있습니다.

다만 데이터 일관성을 애플리케이션이나 다른 방법으로 관리해야 합니다.

## 9. DB JOIN이 무엇인지 설명하고, 각각의 종류에 대해 설명해 주세요.

### 내 답변

JOIN은 둘 이상의 테이블을 공통 조건을 기준으로 결합하여 조회하는 연산입니다.

대표적으로 다음과 같습니다.

- INNER JOIN: 양쪽 모두 조건에 일치하는 행
- LEFT OUTER JOIN: 왼쪽 전체 + 오른쪽 일치 행
- RIGHT OUTER JOIN: 오른쪽 전체 + 왼쪽 일치 행
- FULL OUTER JOIN: 양쪽 전체
- CROSS JOIN: 두 테이블의 Cartesian Product
- SELF JOIN: 같은 테이블을 자기 자신과 JOIN

### 핵심 키워드

`INNER JOIN`, `OUTER JOIN`, `Nested Loop Join`, `Hash Join`, `Merge Join`, `EXPLAIN`

### 꼬리 질문

#### JOIN 구현 방식에는 무엇이 있나요?

대표적으로:

**Nested Loop Join**
- 한 테이블의 행마다 다른 테이블을 탐색
- 인덱스가 있으면 효율적일 수 있음

**Hash Join**
- 한쪽 테이블을 Hash Table로 만들고 다른 쪽에서 탐색
- Equality Join에 적합

**Sort Merge Join**
- 두 입력을 Join Key 기준으로 정렬한 뒤 병합
- 이미 정렬된 데이터나 범위 조건에 유리할 수 있음

#### 어떤 JOIN 알고리즘을 사용하는지 어떻게 알 수 있나요?

`EXPLAIN`, `EXPLAIN ANALYZE` 등 실행 계획을 확인합니다.

#### JOIN 성능도 인덱스 영향을 받나요?

매우 큰 영향을 받을 수 있습니다.

JOIN 조건 컬럼에 적절한 인덱스가 있으면 Nested Loop Join에서 반복 탐색 비용을 크게 줄일 수 있습니다.

#### 3중 JOIN은 어떻게 동작하나요?

DBMS 옵티마이저는 세 테이블을 한 번에 합치는 것이 아니라 어떤 테이블부터 JOIN할지 순서를 결정합니다.

예:

```text
(A JOIN B) JOIN C
```

JOIN 순서에 따라 중간 결과 크기가 크게 달라질 수 있어 성능에 중요한 영향을 줍니다.

## 10. B-Tree와 B+Tree에 대해 설명해 주세요.

### 내 답변

B-Tree와 B+Tree는 균형 다진 탐색 트리로, 디스크 I/O를 줄이기 위해 하나의 노드에 여러 Key를 저장합니다.

B-Tree는 내부 노드와 Leaf 노드 모두 실제 데이터를 가질 수 있습니다.

B+Tree는 실제 데이터 또는 데이터 위치 정보가 Leaf 노드에만 존재하고, 내부 노드는 탐색을 위한 Key만 가집니다.

또한 B+Tree의 Leaf 노드는 일반적으로 서로 연결되어 있어 범위 검색에 유리합니다.

### 핵심 키워드

`균형 트리`, `Fan-out`, `디스크 I/O`, `Leaf Linked List`, `Range Scan`

### 꼬리 질문

#### B+Tree가 항상 B-Tree보다 좋은가요?

아닙니다.

B+Tree는 데이터가 Leaf에 집중되므로 특정 Key 검색 시 항상 Leaf까지 내려가야 합니다.

반면 B-Tree는 내부 노드에서 데이터를 찾으면 탐색을 일찍 종료할 수도 있습니다.

하지만 DB 인덱스에서는 범위 검색과 높은 Fan-out 때문에 B+Tree가 일반적으로 유리합니다.

#### 왜 Red-Black Tree 대신 B-Tree/B+Tree를 사용하나요?

RBT는 노드 하나당 Key 수가 적어 트리 높이가 더 커집니다.

DB는 메모리보다 디스크/페이지 I/O 비용이 매우 크기 때문에 한 노드에 많은 Key를 저장해 트리 높이를 낮출 수 있는 B-Tree 계열이 유리합니다.

#### 오름차순 인덱스로 내림차순 정렬하면?

B+Tree Leaf가 순서대로 연결되어 있다면 역방향으로 탐색하여 DESC 결과를 생성할 수 있습니다.

따라서 단일 컬럼 인덱스에서는 반드시 별도 정렬이 필요한 것은 아닙니다.

복합 인덱스의 ASC/DESC 방향 조합은 DBMS의 인덱스 지원 방식에 따라 달라질 수 있습니다.

## 11. DB Locking에 대해 설명해 주세요.

### 내 답변

DB Lock은 여러 트랜잭션이 동시에 동일한 데이터에 접근할 때 데이터 일관성을 유지하기 위해 접근을 제어하는 방법입니다.

대표적으로 Shared Lock과 Exclusive Lock이 있습니다.

- Shared Lock: 읽기 허용, 여러 트랜잭션이 동시에 획득 가능
- Exclusive Lock: 수정 목적, 다른 Shared/Exclusive Lock과 충돌

Lock의 범위는 Row, Page, Table 등으로 나뉠 수 있습니다.

### 핵심 키워드

`Shared Lock`, `Exclusive Lock`, `Row Lock`, `Table Lock`, `Optimistic Lock`, `Pessimistic Lock`

### 꼬리 질문

#### Optimistic Lock과 Pessimistic Lock

**Pessimistic Lock**
- 충돌이 발생할 것이라고 가정
- 먼저 Lock을 획득하고 작업
- `SELECT ... FOR UPDATE` 등

**Optimistic Lock**
- 충돌이 드물다고 가정
- 실제 Lock을 오래 잡지 않고 Version 값 등을 사용
- UPDATE 시 Version이 변경되지 않았는지 확인

#### Lock 보유 요청이 비정상 종료되면 영원히 Lock이 남나요?

DBMS는 일반적으로 트랜잭션과 세션 단위로 Lock을 관리합니다.

연결이 종료되거나 트랜잭션이 Rollback되면 해당 Lock도 해제됩니다.

또한 Lock Wait Timeout이나 Deadlock Detection 등을 통해 장시간 대기를 처리할 수 있습니다.

## 14. DB의 Connection Pool에 대해 설명해 주세요.

### 내 답변

Connection Pool은 DB와 미리 여러 개의 Connection을 만들어두고 애플리케이션 요청이 들어오면 빌려주고, 사용 후 다시 반환받아 재사용하는 방식입니다.

```text
Client
→ TCP Connection 생성
→ DB 인증
```

## 15. Table Full Scan, Index Range Scan에 대해 설명해 주세요.

### 내 답변

Table Full Scan은 테이블의 데이터를 처음부터 끝까지 읽으면서 조건에 맞는 행을 찾는 방식입니다.

Index Range Scan은 B+Tree 인덱스를 이용해 조건에 맞는 시작 위치를 찾은 뒤 필요한 범위만 순서대로 읽는 방식입니다.

일반적으로 선택도가 높은 조건에서는 Index Range Scan이 효율적이고, 테이블의 매우 많은 행을 읽어야 한다면 Full Scan이 더 효율적일 수 있습니다.

### 핵심 키워드

`Full Scan`, `Index Range Scan`, `Selectivity`, `Random I/O`, `Optimizer`

### 꼬리 질문

#### 인덱스가 있는데도 Full Scan을 할 수 있나요?

가능합니다.

예를 들어 전체 행의 대부분을 조회해야 한다면 인덱스를 따라 랜덤 접근하는 것보다 테이블을 순차적으로 읽는 것이 더 빠를 수 있습니다.

옵티마이저는 통계 정보를 이용해 비용이 더 낮다고 판단되는 실행 계획을 선택합니다.

#### COUNT(1), COUNT(*), COUNT(column)의 차이

**COUNT(*)**
- 조건에 해당하는 모든 행의 수

**COUNT(1)**
- 각 행에 대해 상수 `1`을 세므로 일반적으로 COUNT(*)와 같은 결과
- 현대 DBMS에서는 성능 차이가 거의 없거나 최적화됨

**COUNT(column)**
- 해당 컬럼 값이 `NULL`이 아닌 행만 셈

따라서 의미상 차이가 중요합니다.

## 16. SQL Injection에 대해 설명해 주세요.

### 내 답변

SQL Injection은 사용자 입력값이 SQL 문자열에 그대로 포함될 때 공격자가 SQL 구문을 조작해 원하지 않는 쿼리를 실행하게 만드는 공격입니다.

예를 들어 문자열 연결 방식으로 로그인 SQL을 만들 경우 공격자가 조건식을 조작할 수 있습니다.

가장 중요한 방어 방법은 Prepared Statement와 Parameter Binding을 사용하는 것입니다.

`Prepared Statement`, `Parameter Binding`, `ORM`, `Validation`, `Least Privilege`

### 꼬리 질문

```java
String sql = "SELECT * FROM users WHERE id = ?";

ps.setString(1, userId);
```

- 입력값 검증
- 최소 권한 DB 계정 사용
- 동적 SQL 작성 최소화
- 민감한 오류 메시지를 사용자에게 직접 노출하지 않기

# 최종 암기 압축

```text
Primary Key = 유일 + NOT NULL
Candidate Key = 유일성 + 최소성
Foreign Key = 다른 테이블 Key 참조

RDB = 관계 + 정형 스키마 + SQL
NoSQL = 다양한 데이터 모델 + 분산/확장에 유리한 경우가 많음

Transaction = 하나의 논리적 작업 단위
ACID = Atomicity / Consistency / Isolation / Durability

Index = 조회는 빠르게, 쓰기는 추가 비용
B+Tree = 낮은 높이 + Leaf 연결 → 범위 검색 유리

Normalization = 중복/이상 현상 감소
Denormalization = 조회 성능을 위해 일부 중복 허용

JOIN = 여러 테이블 결합
Nested Loop / Hash / Merge Join

Lock = 동시 접근 제어
Optimistic = 충돌 드물다고 가정
Pessimistic = 먼저 Lock

Connection Pool = DB 연결 재사용

Full Scan = 테이블 전체 탐색
Index Range Scan = 인덱스 범위 탐색

SQL Injection 방어 = Prepared Statement + Parameter Binding
```
