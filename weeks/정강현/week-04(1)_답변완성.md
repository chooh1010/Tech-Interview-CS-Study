#### 1. 뮤텍스와 세마포어의 차이점은 무엇인가요?

`★★☆` · `필수` · 원본 [운영체제 #8](../02-OPERATING_SYSTEM.md)

<details>
<summary><b>꼬리 질문 3개 (펼치기)</b></summary>

- 이진 세마포어와 뮤텍스의 차이에 대해 설명해 주세요.
  - **답변:** 둘 다 값이 0 또는 1이라 한 번에 하나의 스레드만 접근하게 만들 수 있지만, 가장 큰 차이는 **소유권**입니다. 뮤텍스는 락을 획득한 스레드만 해제할 수 있지만, 이진 세마포어는 다른 스레드가 `signal`하여 해제할 수도 있어 동기화 신호 전달에도 사용할 수 있습니다.
- Lock을 얻기 위해 대기하는 프로세스들은 Spin Lock 기법을 사용할 수 있습니다. 이 방법의 장단점은 무엇인가요? 단점을 해결할 방법은 없을까요?
  - **답변:** Spin Lock은 락이 풀릴 때까지 반복 확인하기 때문에 **컨텍스트 스위칭 비용이 없고**, 임계 구역이 매우 짧다면 빠릅니다. 반면 락이 오래 유지되면 CPU를 계속 소비하는 Busy Waiting이 발생합니다. 대기 시간이 길 것으로 예상되면 스레드를 잠재우는 Mutex를 사용하거나, 일정 시간만 Spin한 뒤 Sleep하는 Adaptive Spin 방식으로 보완할 수 있습니다.
- 뮤텍스와 세마포어 모두 커널이 관리하기 때문에, Lock을 얻고 방출하는 과정에서 시스템 콜을 호출해야 합니다. 이 방법의 장단점이 있을까요? 단점을 해결할 수 있는 방법은 없을까요?
  - **답변:** 커널이 관리하면 대기 중인 스레드를 Sleep 상태로 두고 스케줄링할 수 있어 CPU 낭비를 줄일 수 있습니다. 하지만 시스템 콜과 컨텍스트 스위칭에는 비용이 발생합니다. 이를 줄이기 위해 실제 구현에서는 경쟁이 없을 때는 사용자 영역의 원자적 연산으로 처리하고, 경쟁이 생겼을 때만 커널에 진입하는 `futex` 같은 방식을 사용할 수 있습니다.

</details>

**내 답변**

```
뮤텍스는 한 번에 하나의 스레드만 임계 구역에 들어가도록 하는 상호 배제 도구이며, 락을 획득한 스레드가 직접 해제해야 합니다. 반면 세마포어는 카운터를 이용해 동시에 접근할 수 있는 자원의 개수를 제어하며, 이진 세마포어와 카운팅 세마포어로 나눌 수 있습니다. 즉, 뮤텍스는 락의 소유권이 있지만 세마포어는 소유권 개념이 없고, 자원 개수 제어나 스레드 간 신호 전달에도 사용할 수 있습니다.
```

#### 2. Deadlock 에 대해 설명해 주세요.

`★★☆` · `필수` · 원본 [운영체제 #9](../02-OPERATING_SYSTEM.md)

<details>
<summary><b>꼬리 질문 5개 (펼치기)</b></summary>

- Deadlock 이 동작하기 위한 4가지 조건에 대해 설명해 주세요.
  - **답변:** 네 가지는 **상호 배제(Mutual Exclusion), 점유 대기(Hold and Wait), 비선점(No Preemption), 순환 대기(Circular Wait)**입니다. 하나의 자원은 한 번에 하나만 사용하고, 자원을 가진 채 다른 자원을 기다리며, 강제로 자원을 빼앗을 수 없고, 프로세스들이 원형으로 서로의 자원을 기다릴 때 Deadlock이 발생할 수 있습니다.
- 그렇다면 3가지만 충족하면 왜 Deadlock 이 발생하지 않을까요?
  - **답변:** 네 조건은 Deadlock이 발생하기 위한 **필요조건**이므로 하나라도 만족하지 않으면 기다림의 고리가 끊어질 수 있습니다. 예를 들어 순환 대기가 없다면 프로세스들이 원형으로 서로의 자원을 기다리는 구조 자체가 만들어지지 않으므로 Deadlock이 발생하지 않습니다.
- 어떤 방식으로 예방할 수 있을까요?
  - **답변:** 네 가지 필요조건 중 하나를 깨면 됩니다. 예를 들어 모든 자원을 한 번에 요청해 점유 대기를 없애거나, 자원 획득 순서를 정해 순환 대기를 막거나, 필요하면 자원을 선점할 수 있도록 설계할 수 있습니다. 다만 자원 활용률이나 동시성이 낮아질 수 있다는 단점이 있습니다.
- 왜 현대 OS는 Deadlock을 처리하지 않을까요?
  - **답변:** 일반적인 Deadlock을 OS가 완벽하게 예방·탐지하려면 모든 프로세스의 자원 요구량과 상태를 계속 추적해야 해 비용이 큽니다. 또한 애플리케이션이 사용하는 락처럼 OS가 의미를 완전히 알 수 없는 자원도 많습니다. 그래서 범용 OS는 모든 Deadlock을 자동 해결하기보다는 애플리케이션이 락 순서, 타임아웃 등으로 관리하도록 두는 경우가 많습니다.
- Wait Free와 Lock Free를 비교해 주세요.
  - **답변:** Lock Free는 여러 스레드가 경쟁해도 **전체 시스템 차원에서는 적어도 하나의 스레드가 계속 진행**하는 것을 보장합니다. Wait Free는 더 강한 조건으로, **모든 스레드가 유한한 단계 안에 자신의 작업을 완료**할 수 있음을 보장합니다. 따라서 Wait Free가 더 강한 진행 보장을 제공하지만 구현 난이도도 높습니다.

</details>

**내 답변**

```
Deadlock은 여러 프로세스나 스레드가 서로가 가진 자원을 기다리면서 영원히 진행하지 못하는 상태입니다. 발생하려면 상호 배제, 점유 대기, 비선점, 순환 대기의 네 가지 조건이 모두 만족되어야 합니다. 따라서 이 조건 중 하나를 깨면 예방할 수 있고, 시스템에 따라 예방, 회피, 탐지 후 회복 방식으로 처리할 수 있습니다.
```

#### 3. IPC가 무엇이고, 어떤 종류가 있는지 설명해 주세요.

`★★☆` · `심화` · 원본 [운영체제 #11](../02-OPERATING_SYSTEM.md)

<details>
<summary><b>꼬리 질문 2개 (펼치기)</b></summary>

- Shared Memory가 무엇이며, 사용할 때 유의해야 할 점에 대해 설명해 주세요.
  - **답변:** Shared Memory는 여러 프로세스가 같은 물리 메모리 영역을 자신의 주소 공간에 매핑해 데이터를 직접 공유하는 IPC 방식입니다. 복사 횟수가 적어 빠르지만 여러 프로세스가 동시에 같은 데이터를 수정하면 Race Condition이 생길 수 있으므로 Semaphore나 Mutex 같은 별도의 동기화가 필요합니다.
- 메시지 큐는 단방향이라고 할 수 있나요?
  - **답변:** 메시지 큐 자체를 반드시 단방향이라고 할 수는 없습니다. 하나의 큐에서는 송신자와 수신자의 역할이 구분되지만, 양방향 통신이 필요하면 각 방향별 큐를 두거나 여러 프로세스가 같은 큐에 메시지를 넣고 꺼내는 구조로 구성할 수 있습니다.

</details>

**내 답변**

```
IPC는 서로 독립된 프로세스들이 데이터를 주고받거나 상태를 전달하기 위한 통신 방법입니다. 대표적으로 Pipe, Named Pipe, Message Queue, Shared Memory, Socket, Signal 등이 있습니다. Shared Memory는 같은 메모리 영역을 공유하기 때문에 빠르지만, 동시에 접근할 경우 Race Condition이 발생할 수 있어 별도의 동기화가 필요합니다.
```

#### 4. Thread Safe 하다는 것은 어떤 의미인가요?

`★★☆` · `필수` · 원본 [운영체제 #12](../02-OPERATING_SYSTEM.md)

<details>
<summary><b>꼬리 질문 4개 (펼치기)</b></summary>

- Thread Safe 를 보장하기 위해 어떤 방법을 사용할 수 있나요?
  - **답변:** 공유 자원에 대한 접근을 Mutex, Semaphore, `synchronized` 같은 락으로 보호할 수 있습니다. 그 밖에도 Atomic 연산, 불변 객체, Thread Local, 동시성 컬렉션을 사용하거나 애초에 공유 상태를 최소화하는 방법이 있습니다.
- Peterson's Algorithm 이 무엇이며, 한계점에 대해 설명해 주세요.
  - **답변:** Peterson's Algorithm은 두 프로세스가 `flag`와 `turn` 변수를 사용하여 임계 구역 진입을 조정하는 소프트웨어 상호 배제 알고리즘입니다. 상호 배제와 진행 조건을 설명하기 좋은 고전적 알고리즘이지만 기본적으로 두 프로세스에 한정되고 Busy Waiting을 사용합니다. 또한 현대 CPU와 컴파일러의 명령 재배치·메모리 모델 때문에 적절한 메모리 순서 보장 없이 그대로 사용하기 어렵습니다.
- Race Condition 이 무엇인가요?
  - **답변:** 여러 스레드나 프로세스가 공유 데이터에 동시에 접근할 때 **실행 순서에 따라 결과가 달라지는 상황**입니다. 특히 읽기-수정-쓰기처럼 여러 단계로 이루어진 연산이 원자적으로 처리되지 않을 때 발생하기 쉽습니다.
- Thread Safe를 구현하기 위해 반드시 락을 사용해야 할까요? 그렇지 않다면, 어떤 다른 방법이 있을까요?
  - **답변:** 반드시 락이 필요한 것은 아닙니다. CAS 기반 Atomic 연산으로 Lock-Free 구조를 만들거나, 불변 객체를 사용하거나, Thread Local로 데이터를 스레드별로 분리하거나, 메시지 전달 방식으로 공유 상태 자체를 줄일 수도 있습니다.

</details>

**내 답변**

```
Thread Safe하다는 것은 여러 스레드가 동시에 같은 코드나 데이터를 사용해도 Race Condition이나 데이터 불일치 없이 올바른 결과가 보장된다는 의미입니다. 이를 위해 Mutex나 Semaphore 같은 락, Atomic 연산, 불변 객체, Thread Local, 동시성 컬렉션 등을 사용할 수 있습니다. 따라서 Thread Safe를 구현할 때 반드시 락만 사용해야 하는 것은 아닙니다.
```

#### 5. Thread Pool, Monitor, Fork-Join에 대해 설명해 주세요.

`★★★` · `심화` · 원본 [운영체제 #13](../02-OPERATING_SYSTEM.md)

<details>
<summary><b>꼬리 질문 2개 (펼치기)</b></summary>

- Thread Pool을 사용한다고 가정하면, 어떤 기준으로 스레드의 수를 결정할 것인가요?
  - **답변:** 작업의 성격을 먼저 봅니다. CPU 연산 중심이면 컨텍스트 스위칭을 줄이기 위해 보통 CPU 코어 수와 비슷하게 설정하고, I/O 대기가 많은 작업이면 대기 시간 동안 다른 작업을 처리할 수 있도록 코어 수보다 더 많은 스레드를 둘 수 있습니다. 실제로는 처리량, 응답 시간, 메모리 사용량을 측정하며 조정하는 것이 좋습니다.
- 어떤 데이터를 정렬 하려고 합니다. 어떤 방식의 전략을 사용하는 것이 가장 안전하면서도 좋은 성능을 낼 수 있을까요?
  - **답변:** 데이터가 충분히 크고 병렬 처리 이점이 있다면 Fork-Join 방식으로 데이터를 나눈 뒤 각 부분을 병렬 정렬하고 마지막에 병합하는 전략을 사용할 수 있습니다. 병합 정렬 계열은 최악의 경우에도 O(n log n)을 보장하고 병합 단계가 명확해 병렬화하기 좋습니다. 다만 데이터가 작으면 병렬화 오버헤드가 더 클 수 있으므로 일정 크기 이하에서는 순차 정렬로 전환하는 것이 좋습니다.

</details>

**내 답변**

```
Thread Pool은 일정 수의 스레드를 미리 만들어 두고 작업을 재사용하여 처리하는 방식으로, 스레드 생성·삭제 비용을 줄이고 동시 실행 수를 제한할 수 있습니다. Monitor는 공유 자원과 그 자원에 접근하는 연산을 묶고 상호 배제와 조건 대기를 제공하는 동기화 구조입니다. Fork-Join은 큰 작업을 작은 작업으로 재귀적으로 나누어 병렬 처리한 뒤 결과를 합치는 방식이며, 보통 Work Stealing을 이용해 작업을 효율적으로 분배합니다.
```

#### 6. 동기화를 구현하기 위한 하드웨어적인 해결 방법에 대해 설명해 주세요.

`★★★` · `심화` · 원본 [운영체제 #20](../02-OPERATING_SYSTEM.md)

<details>
<summary><b>꼬리 질문 2개 (펼치기)</b></summary>

- volatile 키워드는 어떤 의미가 있나요?
  - **답변:** Java의 `volatile`은 한 스레드가 변수에 쓴 값을 다른 스레드가 **최신 값으로 볼 수 있도록 가시성**을 보장하고, 해당 변수 주변의 일부 명령 재배치를 제한합니다. 하지만 `count++`처럼 읽기-수정-쓰기가 결합된 연산 전체의 원자성을 보장하지는 않으므로 이런 경우에는 Atomic 클래스나 락이 필요합니다.
- 싱글코어가 아니라 멀티코어라면, 어떻게 동기화가 이뤄질까요?
  - **답변:** 멀티코어에서는 여러 코어가 동시에 실행되므로 단순히 한 코어의 인터럽트만 막아서는 동기화할 수 없습니다. CPU가 제공하는 CAS 같은 원자적 명령어와 Memory Barrier를 사용하고, 하드웨어의 Cache Coherence 프로토콜이 코어별 캐시의 일관성을 유지하도록 합니다. OS와 언어의 락·Atomic 기능은 이러한 하드웨어 기능을 기반으로 구현됩니다.

</details>

**내 답변**

```
하드웨어에서는 Test-and-Set, Compare-and-Swap(CAS), Swap, Fetch-and-Add 같은 원자적 명령어를 제공하여 동기화를 구현할 수 있습니다. 이러한 연산은 중간에 다른 스레드가 끼어들 수 없기 때문에 Spin Lock이나 Atomic 연산의 기반이 됩니다. 싱글코어에서는 인터럽트 비활성화 방식도 가능하지만 멀티코어에서는 충분하지 않으며, 원자적 명령어와 Memory Barrier, Cache Coherence 등을 함께 이용합니다.
```

#### 7. 동기와 비동기, 블로킹과 논블로킹의 차이에 대해 설명해 주세요.

`★★★` · `필수` · 원본 [운영체제 #23](../02-OPERATING_SYSTEM.md)

<details>
<summary><b>꼬리 질문 3개 (펼치기)</b></summary>

- 그렇다면, 동기이면서 논블로킹이고, 비동기이면서 블로킹인 경우는 의미가 있다고 할 수 있나요?
  - **답변:** 가능합니다. **동기 + 논블로킹**은 호출이 즉시 반환되지만 호출자가 반복적으로 완료 여부를 확인하는 Polling 방식이 대표적입니다. **비동기 + 블로킹**은 작업 자체는 비동기로 시작했지만 이후 `Future.get()`처럼 결과를 기다리는 지점에서 호출 스레드가 블로킹되는 경우로 볼 수 있습니다.
- I/O 멀티플렉싱에 대해 설명해 주세요.
  - **답변:** 하나의 스레드가 여러 I/O 채널이나 소켓의 상태를 동시에 감시하고, 실제로 읽거나 쓸 준비가 된 대상만 처리하는 방식입니다. `select`, `poll`, `epoll` 등이 대표적이며, 연결마다 스레드를 하나씩 만드는 방식보다 많은 연결을 적은 스레드로 처리할 수 있습니다.
- 논블로킹 I/O를 수행한다고 하면, 그 결과를 어떻게 수신할 수 있나요?
  - **답변:** 호출 직후 결과가 준비되지 않았다면 즉시 반환하고, 이후 Polling으로 다시 확인하거나 `select`/`epoll` 같은 I/O 멀티플렉싱으로 준비 이벤트를 감지할 수 있습니다. 비동기 API라면 Callback, Future/Promise, 이벤트 방식으로 완료 결과를 전달받을 수도 있습니다.

</details>

**내 답변**

```
동기와 비동기는 작업의 완료를 누가 확인하고 결과를 전달받는지에 대한 개념이고, 블로킹과 논블로킹은 호출한 스레드가 작업이 끝날 때까지 멈추는지에 대한 개념입니다. 동기는 호출 측이 작업 완료를 직접 확인하는 방식이고, 비동기는 작업이 완료되면 콜백이나 이벤트 등으로 결과를 전달받는 방식입니다. 블로킹은 결과가 준비될 때까지 호출 스레드가 대기하고, 논블로킹은 즉시 제어권을 돌려받아 다른 작업을 수행할 수 있습니다. 두 기준은 서로 독립적이므로 동기·논블로킹이나 비동기·블로킹 조합도 가능합니다.
```

#### 8. 가상화가 무엇이고, 이것이 가상머신과 어떠한 차이가 있는지 설명해 주세요.

`★★☆` · `필수` · 원본 [개발상식·기타 #1](../05-ETC.md)

<details>
<summary><b>꼬리 질문 3개 (펼치기)</b></summary>

- 그렇다면 Docker는 둘 중 어디에 속하나요? 왜 사람들이 Docker를 많이 채택할까요?
  - **답변:** Docker는 **OS 수준 가상화인 컨테이너 기술**에 속합니다. VM처럼 Guest OS를 각각 실행하지 않고 Host OS의 커널을 공유하기 때문에 이미지가 작고 시작 속도가 빠르며 자원 사용량도 적습니다. 또한 애플리케이션과 실행 환경을 이미지로 함께 묶을 수 있어 개발·테스트·배포 환경을 일관되게 유지하기 쉽습니다.
- 하나의 Host OS에서 돌아간다면 충분히 한 컨테이너가 다른 컨테이너에 간섭할 수 있는 위험이 있지 않을까요? 이를 어떻게 방어할 수 있을까요?
  - **답변:** 같은 커널을 공유하기 때문에 VM보다 격리 경계가 약할 수 있습니다. Linux의 Namespace로 프로세스·네트워크·파일 시스템 등을 격리하고, cgroups로 CPU와 메모리 사용량을 제한하며, 최소 권한 실행, capability 제한, seccomp, AppArmor/SELinux 등을 함께 적용해 위험을 줄일 수 있습니다.
- Docker 위에 Docker를 올릴 순 없을까요?
  - **답변:** 가능합니다. 대표적으로 컨테이너 내부에서 별도의 Docker daemon을 실행하는 **Docker-in-Docker(DinD)** 방식이 있습니다. 다만 권한과 보안, 스토리지 관리가 복잡해질 수 있어 CI 환경에서는 Host의 Docker daemon을 소켓으로 공유하는 방식도 사용되지만, 이 역시 강한 권한을 주기 때문에 보안에 주의해야 합니다.

</details>

**내 답변**

```
가상화는 CPU, 메모리, 저장장치 같은 물리 자원을 추상화하여 여러 개의 독립된 실행 환경처럼 사용할 수 있게 하는 기술입니다. 가상머신은 이러한 가상화를 구현한 하나의 형태로, Hypervisor 위에서 가상 하드웨어와 별도의 Guest OS를 실행합니다. 반면 Docker 같은 컨테이너는 Host OS의 커널을 공유하는 OS 수준 가상화이기 때문에 가상머신보다 가볍고 시작 속도가 빠릅니다.
```

#### 9. CI/CD 를 사용해 본 경험이 있나요? 있다면 간단하게 설명해 주세요.

`★★☆` · `필수` · 원본 [개발상식·기타 #2](../05-ETC.md)

<details>
<summary><b>꼬리 질문 7개 (펼치기)</b></summary>

- 소스코드를 작성하고 나서, 실제 사용자에게 배포되기까지의 과정을 순서대로 설명해 주세요.
  - **답변:** 일반적으로 `코드 작성 → Git Push/PR → 자동 빌드 → 테스트 및 정적 분석 → 배포 가능한 결과물 생성 → Staging 검증 → 운영 환경 배포 → 모니터링` 순서로 진행됩니다. 문제가 발견되면 배포를 중단하거나 이전 버전으로 롤백할 수 있도록 구성합니다.
- 빌드와 배포는 어떻게 다른가요?
  - **답변:** 빌드는 소스코드를 컴파일하고 의존성을 처리하여 실행 가능한 JAR, 번들, Docker 이미지 같은 **배포 가능한 결과물**을 만드는 과정입니다. 배포는 그 결과물을 실제 서버나 클라우드 환경에 설치하고 실행하여 사용자가 접근할 수 있게 만드는 과정입니다.
- CI와 CD는 각각 무엇을 자동화하는 것인가요? CD의 Delivery와 Deployment는 어떤 차이가 있나요?
  - **답변:** CI는 코드 변경을 자주 통합하고 그때마다 빌드와 테스트를 자동화하는 과정입니다. **Continuous Delivery**는 검증된 결과물을 언제든 운영에 배포할 수 있는 상태까지 자동으로 준비하지만 최종 운영 배포에는 승인이 들어갈 수 있습니다. **Continuous Deployment**는 그 승인 단계까지 자동화하여 검증을 통과한 변경을 운영 환경에 자동 배포합니다.
- 파이프라인의 어느 단계에 테스트를 넣는 것이 좋을까요? 그 이유는 무엇인가요?
  - **답변:** 빠른 단위 테스트와 정적 분석은 빌드 초기에 실행해 잘못된 변경을 최대한 빨리 걸러내는 것이 좋습니다. 이후 통합 테스트와 E2E 테스트처럼 비용이 큰 테스트를 수행하고, 운영 배포 전에는 Staging 환경 검증을 추가할 수 있습니다. 실패를 빨리 발견할수록 불필요한 빌드·배포 비용이 줄어듭니다.
- 무중단 배포는 어떻게 구현할 수 있을까요? (Rolling, Blue-Green, Canary)
  - **답변:** Rolling은 여러 인스턴스를 순차적으로 새 버전으로 교체하고, Blue-Green은 기존 환경과 새 환경을 동시에 준비한 뒤 트래픽을 한 번에 전환합니다. Canary는 일부 사용자나 일부 인스턴스에만 새 버전을 먼저 배포해 지표를 확인한 후 점차 확대합니다. 세 방식 모두 Health Check와 트래픽 라우팅을 이용해 서비스 중단을 최소화합니다.
- 배포한 버전에 장애가 발생했을 때, 롤백은 어떤 방식으로 준비해 둘 수 있을까요?
  - **답변:** 이전에 정상 동작한 빌드 결과물이나 Docker 이미지에 버전을 붙여 보관하고, 배포 도구에서 이전 버전으로 빠르게 되돌릴 수 있도록 준비합니다. Blue-Green이라면 트래픽을 기존 환경으로 다시 돌릴 수 있고, 데이터베이스 변경은 이전 버전과 호환되도록 단계적으로 적용해 애플리케이션 롤백이 막히지 않도록 해야 합니다.
- 빌드 결과물을 이미지로 만들어 배포하는 방식은, 서버에서 직접 빌드하는 방식과 비교해 어떤 장점이 있을까요?
  - **답변:** 한 번 검증한 동일한 이미지를 개발·Staging·운영 환경에 그대로 배포할 수 있어 **환경 차이로 인한 문제를 줄일 수 있습니다**. 운영 서버에 컴파일러나 빌드 도구를 둘 필요도 없고, 이미지 버전만 바꾸면 재배포나 롤백이 쉬워져 배포의 재현성과 일관성이 높아집니다.

</details>

**내 답변**

```
직접 운영 환경까지 이어지는 완전한 CI/CD 파이프라인 경험은 많지 않지만, 프로젝트에서 Git으로 변경 사항을 관리하고 테스트와 빌드 과정을 반복적으로 검증해 본 경험이 있습니다. CI는 코드가 변경될 때 빌드와 테스트를 자동으로 수행하여 문제를 빠르게 발견하는 과정이고, CD는 검증된 결과물을 배포 가능한 상태로 전달하거나 실제 운영 환경까지 자동 배포하는 과정입니다. 이를 통해 사람의 반복 작업을 줄이고 배포 과정의 일관성과 안정성을 높일 수 있습니다.
```

#### [정렬 2/6] 병합 정렬

**구현 범위** — 재귀 분할 + `merge` 병합. 임시 배열을 매번 할당하지 않는 방법과, 병합 정렬이 안정 정렬인 이유

```java
static void mergeSort(int[] arr) {
    int[] temp = new int[arr.length];
    mergeSort(arr, temp, 0, arr.length - 1);
}

static void mergeSort(int[] arr, int[] temp, int left, int right) {
    if (left >= right) return;

    int mid = (left + right) / 2;
    mergeSort(arr, temp, left, mid);
    mergeSort(arr, temp, mid + 1, right);
    merge(arr, temp, left, mid, right);
}

static void merge(int[] arr, int[] temp, int left, int mid, int right) {
    int i = left;
    int j = mid + 1;
    int k = left;

    while (i <= mid && j <= right) {
        if (arr[i] <= arr[j]) temp[k++] = arr[i++];
        else temp[k++] = arr[j++];
    }

    while (i <= mid) temp[k++] = arr[i++];
    while (j <= right) temp[k++] = arr[j++];

    for (int idx = left; idx <= right; idx++) {
        arr[idx] = temp[idx];
    }
}
```

**시간복잡도** → O(n log n)  **공간복잡도** → O(n)

```java
static Node merge(Node a, Node b) {
    Node dummy = new Node(0);
    Node cur = dummy;

    while (a != null && b != null) {
        if (a.value <= b.value) {
            cur.next = a;
            a = a.next;
        } else {
            cur.next = b;
            b = b.next;
        }
        cur = cur.next;
    }

    cur.next = (a != null) ? a : b;
    return dummy.next;
}
```
