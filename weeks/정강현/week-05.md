#### 1. 캐시 메모리 및 메모리 계층성에 대해 설명해 주세요.

`★★☆` · `필수` · 원본 [운영체제 #14](../02-OPERATING_SYSTEM.md)

<details>
<summary><b>꼬리 질문 8개 (펼치기)</b></summary>

- 캐시 메모리는 어디에 위치해 있나요?
- L1, L2 캐시에 대해 설명해 주세요.
- 캐시에 올라오는 데이터는 어떻게 관리되나요?
- 캐시간의 동기화는 어떻게 이루어지나요?
- 캐시 메모리의 Mapping 방식에 대해 설명해 주세요.
- 캐시의 지역성에 대해 설명해 주세요.
- 캐시의 지역성을 기반으로, 이차원 배열을 가로/세로로 탐색했을 때의 성능 차이에 대해 설명해 주세요.
- 캐시의 공간 지역성은 어떻게 구현될 수 있을까요? (힌트: 캐시는 어떤 단위로 저장되고 관리될까요?)

</details>

**내 답변**

```
캐시 메모리는 CPU와 메인 메모리 사이의 속도 차이를 줄이기 위해 사용하는 빠른 메모리입니다.
CPU에 가까운 순서대로 보통 레지스터 → L1 캐시 → L2 캐시 → L3 캐시 → RAM → 보조 저장장치 형태의 메모리 계층을 구성합니다.
CPU에 가까울수록 속도는 빠르지만 용량이 작고 가격이 비싸며, 멀어질수록 속도는 느리지만 용량이 커지고 가격이 저렴해집니다.
캐시는 프로그램이 최근 사용한 데이터나 주변 데이터를 다시 사용할 가능성이 높다는 시간 지역성과 공간 지역성을 활용해서 메모리 접근 시간을 줄입니다.
```

**꼬리 답변**

```
1. CPU 내부 또는 CPU와 메인 메모리 사이에 위치합니다. 현대 CPU에서는 일반적으로 L1, L2, L3 캐시가 CPU 칩 내부에 존재합니다.

2. L1은 CPU 코어와 가장 가까운 캐시로 가장 빠르지만 용량이 가장 작습니다. 보통 명령어 캐시와 데이터 캐시로 나뉩니다.
L2는 L1보다 크지만 조금 느리고, L1에서 데이터를 찾지 못했을 때 다음으로 확인하는 캐시입니다.
일반적으로 L1 → L2 → L3 → RAM 순으로 탐색합니다.

3. 메모리에서 데이터를 한 바이트씩 가져오는 것이 아니라 Cache Line이라는 일정 크기의 블록 단위로 가져옵니다.
캐시가 가득 찬 경우 LRU와 같은 교체 정책 또는 CPU에서 사용하는 유사한 정책을 이용해 기존 데이터를 제거합니다.

4. 멀티코어 환경에서는 같은 메모리 데이터를 여러 코어의 캐시가 가지고 있을 수 있기 때문에 Cache Coherence Protocol을 사용합니다.
대표적으로 MESI 프로토콜이 있고, 한 코어에서 데이터를 변경하면 다른 코어의 캐시 데이터를 무효화하거나 최신 상태로 유지합니다.

5. 대표적으로 세 가지가 있습니다.
- Direct Mapping: 하나의 메모리 블록이 특정 캐시 위치에만 들어감
- Fully Associative Mapping: 아무 캐시 위치에나 저장 가능
- Set Associative Mapping: 캐시를 여러 Set으로 나누고 해당 Set 안에서 위치를 선택
실제 CPU에서는 Set Associative 방식이 많이 사용됩니다.

6. 최근 사용한 데이터가 다시 사용될 가능성이 높은 것을 시간 지역성, 사용한 데이터 주변의 데이터도 곧 사용될 가능성이 높은 것을 공간 지역성이라고 합니다.
예를 들어 반복문의 변수는 시간 지역성을 가지고, 배열을 순서대로 접근하는 것은 공간 지역성을 활용합니다.

7. Java의 2차원 배열도 각 행의 데이터가 연속적으로 접근되는 형태이므로 일반적으로 행 방향으로 순차 접근하는 것이 캐시 효율이 좋습니다.
for (int i = 0; i < N; i++)
    for (int j = 0; j < M; j++)
        arr[i][j];
이렇게 접근하면 한 번 가져온 Cache Line에 있는 주변 데이터를 연속으로 사용할 수 있습니다.
반대로 열 방향 접근은 서로 떨어진 메모리를 반복적으로 접근하게 되어 Cache Miss가 증가할 수 있습니다.

8. 캐시가 데이터를 한 개씩 저장하지 않고 Cache Line 단위로 가져오기 때문에 가능합니다.
필요한 데이터 주변의 데이터까지 같이 캐시에 저장하기 때문에 이후 인접 데이터 접근이 빨라집니다.

```

#### 2. 메모리의 연속할당 방식 세 가지를 설명해주세요. (first-fit, best-fit, worst-fit)

`★☆☆` · `심화` · 원본 [운영체제 #15](../02-OPERATING_SYSTEM.md)

<details>
<summary><b>꼬리 질문 2개 (펼치기)</b></summary>

- worst-fit 은 언제 사용할 수 있을까요?
- 성능이 가장 좋은 알고리즘은 무엇일까요?

</details>

**내 답변**

```
연속 메모리 할당에서 프로세스를 빈 메모리 공간에 배치하는 대표적인 방식은 First-fit, Best-fit, Worst-fit입니다.
First-fit은 앞에서부터 탐색해서 프로세스가 들어갈 수 있는 첫 번째 공간에 배치합니다.
Best-fit은 프로세스가 들어갈 수 있는 공간 중 가장 작은 공간을 선택합니다.
Worst-fit은 가장 큰 빈 공간을 선택합니다.
First-fit은 탐색 속도가 빠르다는 장점이 있고, Best-fit이나 Worst-fit은 남는 공간을 고려하지만 탐색 비용과 외부 단편화 문제가 발생할 수 있습니다.
파일의 꼬리 질문은 Worst-fit의 사용 상황과 알고리즘 성능 비교야.
```

**꼬리 답변**

```
1. 큰 빈 공간을 일부 사용하고도 비교적 큰 공간을 남기고 싶을 때 사용할 수 있습니다.
작은 조각을 많이 만드는 것을 피하려는 아이디어지만 실제로 항상 좋은 결과를 보장하지는 않습니다.

2. 상황에 따라 다르지만 일반적으로 First-fit이 구현이 간단하고 탐색 시간이 짧아서 실용적입니다.
Best-fit은 가장 적절한 공간을 찾기 위해 많은 공간을 탐색해야 하고 아주 작은 빈 공간들이 많이 생길 수 있습니다.

```

#### 3. Thrashing 이란 무엇인가요?

`★★☆` · `필수` · 원본 [운영체제 #16](../02-OPERATING_SYSTEM.md)

<details>
<summary><b>꼬리 질문 1개 (펼치기)</b></summary>

- Thrashing 발생 시, 어떻게 완화할 수 있을까요?

</details>

**내 답변**

```
Thrashing은 프로세스가 실행되는 시간보다 Page Fault를 처리하고 페이지를 교체하는 데 더 많은 시간을 사용하는 상태입니다.
물리 메모리에 필요한 페이지를 충분히 올려두지 못하면 Page Fault가 계속 발생하고, 디스크와 메모리 사이에서 페이지 교체가 반복됩니다.
그 결과 CPU 이용률과 전체 시스템 성능이 크게 떨어집니다.
```

**꼬리 답변**

```
프로세스에 충분한 프레임을 할당해야 합니다.
대표적으로 Working Set이나 Page Fault Frequency를 이용해 프로세스가 실제로 필요한 페이지 수를 추정할 수 있습니다.
또한 동시에 실행되는 프로세스 수를 줄여 각 프로세스에 더 많은 메모리를 제공하거나 물리 메모리를 증가시키는 방법도 있습니다.
```

#### 4. 가상 메모리란 무엇인가요?

`★★☆` · `필수` · 원본 [운영체제 #17](../02-OPERATING_SYSTEM.md)

<details>
<summary><b>꼬리 질문 5개 (펼치기)</b></summary>

- 가상 메모리가 가능한 이유가 무엇일까요?
- Page Fault가 발생했을 때, 어떻게 처리하는지 설명해 주세요.
- 페이지 크기에 대한 Trade-Off를 설명해 주세요.
- 페이지 크기가 커지면, 페이지 폴트가 더 많이 발생한다고 할 수 있나요?
- 세그멘테이션 방식을 사용하고 있다면, 가상 메모리를 사용할 수 없을까요?

</details>

**내 답변**

```
가상 메모리는 프로세스에게 실제 물리 메모리보다 큰 독립적인 가상 주소 공간이 있는 것처럼 제공하는 메모리 관리 기법입니다.
프로세스가 사용하는 가상 주소를 MMU가 페이지 테이블을 이용해 실제 물리 주소로 변환합니다.
현재 필요한 페이지만 메모리에 올리고 나머지는 디스크에 둘 수 있기 때문에 실제 RAM보다 큰 프로그램도 실행할 수 있습니다.
또한 프로세스마다 독립적인 주소 공간을 제공하기 때문에 메모리 보호에도 도움이 됩니다.
```

**꼬리 답변**

```
1. 프로그램이 실행되는 동안 모든 코드와 데이터를 동시에 사용하는 것이 아니기 때문입니다.
프로그램은 특정 시간에 일부 영역만 집중적으로 사용하는 **지역성(Locality)**을 보이기 때문에 현재 필요한 페이지만 RAM에 올려 실행할 수 있습니다.

2. CPU가 페이지에 접근
페이지 테이블을 확인
해당 페이지가 RAM에 없으면 Page Fault 발생
OS로 제어권 이동
디스크에서 해당 페이지 탐색
빈 Frame이 있으면 적재
없으면 Page Replacement 수행
페이지 테이블 수정
중단됐던 명령어 다시 실행

3. 페이지가 크면 페이지 테이블의 엔트리 수가 줄기 때문에 페이지 테이블 크기가 작아질 수 있습니다.
하지만 실제로 필요하지 않은 데이터까지 가져오면서 내부 단편화가 증가할 수 있습니다.
반대로 페이지가 작으면 메모리를 세밀하게 사용할 수 있지만 페이지 테이블이 커지고 주소 변환 관리 비용도 증가합니다.

4. 반드시 그렇지는 않습니다.
페이지가 커지면 한 번의 Page Fault에서 더 많은 인접 데이터를 가져오기 때문에 공간 지역성이 높은 프로그램에서는 오히려 Page Fault가 감소할 수 있습니다.
하지만 불필요한 데이터까지 가져와 메모리를 낭비할 수도 있기 때문에 단순히 크기만으로 판단할 수 없습니다.

5. 아닙니다.
가상 메모리는 반드시 Paging만 사용하는 개념이 아닙니다.
Segmentation 기반 가상 메모리도 가능하고, 실제 시스템에서는 Segmentation과 Paging을 조합하는 방식도 사용할 수 있습니다.

```

- 페이지에서 실제 주소를 어떻게 가져올 수 있는지 설명해 주세요.
- 어떤 주소공간이 있을 때, 이 공간이 수정 가능한지 확인할 수 있는 방법이 있나요?
- 32비트에서, 페이지의 크기가 1kb 이라면 페이지 테이블의 최대 크기는 몇 개일까요?
- 32비트 운영체제는 램을 최대 4G 까지 사용할 수 있습니다. 이 이유를 페이징과 연관 지어서 설명해 주세요.
- C/C++ 개발을 하게 되면 Segmentation Fault 라는 에러를 접할 수 있을텐데, 이 에러는 세그멘테이션/페이징과 어떤 관계가 있을까요?

</details>

**내 답변**

```
Paging은 메모리를 고정 크기로 나누는 방식이고, Segmentation은 프로그램을 의미 있는 가변 크기 단위로 나누는 방식입니다.
Paging에서는 가상 메모리를 Page, 물리 메모리를 같은 크기의 Frame으로 나눕니다.
고정 크기이므로 외부 단편화는 줄일 수 있지만 마지막 페이지 등에 내부 단편화가 발생할 수 있습니다.
Segmentation은 Code, Data, Stack 등 논리적 단위로 메모리를 나누기 때문에 프로그램 구조를 반영하기 좋지만 크기가 서로 달라 외부 단편화가 발생할 수 있습니다.
```

**꼬리 답변**

```
1. Page는 가상 메모리를 나눈 단위이고 Frame은 물리 메모리를 나눈 단위입니다.
Page와 Frame의 크기는 동일합니다.
페이지 테이블을 통해 Page 번호가 어떤 Frame 번호에 대응하는지 관리합니다.

2. 내부 단편화는 할당된 메모리 공간 내부에 사용하지 않는 공간이 생기는 현상입니다.
Paging에서 마지막 Page가 Page 크기를 모두 사용하지 못하는 경우가 대표적입니다.
외부 단편화는 사용 가능한 전체 공간은 충분하지만 여러 작은 공간으로 흩어져 있어서 연속된 공간을 할당하지 못하는 현상입니다.

3. 가상 주소를
Page Number + Offset
으로 나눕니다.
Page Number를 이용해 Page Table에서 Frame Number를 찾고,
Frame Number + Offset
을 결합하여 실제 물리 주소를 얻습니다.

4. 페이지 테이블 엔트리에 존재하는 Protection Bit / Permission Bit을 확인합니다.
일반적으로 Read, Write, Execute 권한이 저장되어 있고, 쓰기 권한이 없는 페이지에 쓰기를 시도하면 예외가 발생합니다.

5. 32비트 주소 공간은
2^32 Byte
입니다.
페이지 크기 1KB는
2^10 Byte
이므로
2^32 / 2^10 = 2^22
따라서 약 419만 개의 페이지가 존재할 수 있습니다.

6. 32비트 주소는 총
2^32
개의 주소를 표현할 수 있습니다.
각 주소가 1Byte를 가리킨다면
2^32 Byte = 4GB
가 됩니다.
따라서 하나의 32비트 가상 주소 공간은 기본적으로 최대 4GB를 표현할 수 있습니다.

7. 이름은 역사적으로 Segmentation에서 유래했지만 현대 OS에서 Segmentation Fault가 발생한다고 해서 반드시 세그멘테이션 메모리 관리 때문에 발생하는 것은 아닙니다.
프로세스가 접근 권한이 없는 메모리나 존재하지 않는 메모리에 접근했을 때 OS가 보호 예외를 발생시키고 이를 Segmentation Fault라고 부르는 것입니다.

```

#### 6. TLB는 무엇인가요?

`★★☆` · `심화` · 원본 [운영체제 #19](../02-OPERATING_SYSTEM.md)

<details>
<summary><b>꼬리 질문 5개 (펼치기)</b></summary>

- TLB를 쓰면 왜 빨라지나요?
- MMU가 무엇인가요?
- TLB와 MMU는 어디에 위치해 있나요?
- 코어가 여러개라면, TLB는 어떻게 동기화 할 수 있을까요?
- TLB 관점에서, Context Switching 발생 시 어떤 변화가 발생하는지 설명해 주세요.

</details>

**내 답변**

```
TLB는 Translation Lookaside Buffer의 약자로 가상 주소에서 물리 주소로 변환한 결과를 저장하는 작은 고속 캐시입니다.
가상 주소를 물리 주소로 변환할 때 매번 메모리에 있는 Page Table을 조회하면 비용이 크기 때문에 최근 사용한 Page Number와 Frame Number의 매핑을 TLB에 저장합니다.
TLB Hit가 발생하면 Page Table을 메모리에서 조회하지 않고 빠르게 주소 변환을 할 수 있습니다.
```

**꼬리 답변**

```
1. 페이지 테이블은 메모리에 있기 때문에 주소 변환을 위해 추가적인 메모리 접근이 필요합니다.
TLB는 자주 사용되는 주소 변환 결과를 CPU 가까이에 캐싱하므로 TLB Hit가 발생하면 Page Table 접근을 생략할 수 있습니다.

2. MMU는 Memory Management Unit으로 CPU가 생성한 가상 주소를 물리 주소로 변환하는 하드웨어입니다.
TLB와 Page Table 등을 이용해 주소 변환을 수행하고 메모리 접근 권한도 검사합니다.

3. 현대 시스템에서는 일반적으로 CPU 내부에 위치합니다.
TLB는 MMU가 주소를 변환할 때 사용하는 고속 캐시라고 이해하면 됩니다.

4. 각 CPU 코어가 독립적인 TLB를 가지고 있기 때문에 페이지 테이블이 변경되면 다른 코어에 남아 있는 기존 TLB Entry를 무효화해야 합니다.
이를 TLB Shootdown이라고 합니다.
OS가 다른 CPU 코어에 인터럽트를 보내 해당 TLB Entry를 제거하도록 할 수 있습니다.

5. 프로세스마다 가상 주소 공간과 Page Table이 다르기 때문에 이전 프로세스의 TLB Entry를 그대로 사용하면 잘못된 주소 변환이 발생할 수 있습니다.
따라서 TLB를 Flush하거나, 현대 CPU에서는 ASID(Address Space Identifier) 같은 식별자를 사용해 여러 프로세스의 TLB Entry를 구분하기도 합니다.

```

#### 7. 페이지 교체 알고리즘에 대해 설명해 주세요.

<details>
<summary><b>꼬리 질문 3개 (펼치기)</b></summary>

**내 답변**

```
페이지 교체 알고리즘은 Page Fault가 발생했는데 사용할 수 있는 Frame이 없을 때 어떤 Page를 제거할지 결정하는 알고리즘입니다.
대표적으로 FIFO, OPT, LRU 등이 있습니다.
FIFO는 가장 먼저 들어온 페이지를 제거합니다.
OPT는 앞으로 가장 오랫동안 사용되지 않을 페이지를 제거해서 이론적으로 가장 좋은 성능을 가지지만 미래의 접근을 알아야 하므로 실제 구현은 어렵습니다.

2. HashMap과 Doubly Linked List를 함께 사용할 수 있습니다.
HashMap으로 페이지를 O(1)에 찾고, Linked List에서 최근 사용한 페이지를 앞으로 이동시킵니다.
가장 뒤에 있는 페이지가 가장 오랫동안 사용되지 않은 페이지가 됩니다.

3. 모든 페이지 접근 순서를 정확히 관리하면 비용이 큽니다.
따라서 실제 OS에서는 완전한 LRU 대신 Reference Bit를 이용하는 Clock Algorithm / Second Chance Algorithm 같은 근사 알고리즘을 사용할 수 있습니다.
```

#### 9. GC에 대해 설명해 주세요.

`★★☆` · `필수` · 원본 [개발상식·기타 #11](../05-ETC.md)

<details>
<summary><b>꼬리 질문 4개 (펼치기)</b></summary>

- 본인이 사용하는 언어에서는 GC를 어떻게 구현했나요?
- GC의 장단점에 대해 설명해 주세요.
- GC는 어떤 영역에 있는 데이터를 관리하나요?
- Reference Counting 방식에 대해 설명하고, 이 알고리즘에서 발생할 수 있는 순환 참조 및 Retain Cycle에 대해 설명해 주세요.

</details>

**내 답변**

```
GC는 Garbage Collection의 약자로 프로그램에서 더 이상 사용하지 않는 Heap 메모리의 객체를 자동으로 찾아 제거하는 메모리 관리 방식입니다.
개발자가 직접 메모리를 해제하지 않아도 되기 때문에 메모리 관리가 편리하고 잘못된 메모리 해제로 인한 오류를 줄일 수 있습니다.
Java에서는 객체의 도달 가능성을 기준으로 더 이상 참조할 수 없는 객체를 Garbage로 판단합니다.
대표적으로 GC Root에서 객체 참조를 따라가는 Tracing 방식을 사용합니다.
```

**꼬리 답변**

```
1. Java에서는 기본적으로 Reachability를 기준으로 객체가 살아 있는지를 판단합니다.
GC Root에서 참조를 따라가면서 접근할 수 있는 객체는 살아 있는 객체로 판단하고, 접근할 수 없는 객체는 GC 대상으로 판단합니다.
JVM에는 여러 GC가 있지만 기본 원리는 살아 있는 객체와 그렇지 않은 객체를 구분하여 불필요한 객체를 정리하는 것입니다.

2. 장점은 개발자가 직접 메모리를 해제할 필요가 없어 개발이 편리하고 Memory Leak이나 잘못된 메모리 해제 문제를 줄일 수 있다는 것입니다.
단점은 GC가 언제 실행되는지를 개발자가 완전히 통제하기 어렵고, GC 수행 시 추가적인 CPU 비용이나 애플리케이션 정지 시간이 발생할 수 있다는 것입니다.

3. Java에서는 주로 Heap 영역에 생성된 객체를 관리합니다.
지역 변수 자체는 Stack에 있을 수 있지만 지역 변수가 가리키는 객체는 Heap에 존재하며 GC의 관리 대상이 됩니다.

4. 각 객체를 참조하고 있는 참조의 개수를 저장하는 방식입니다.
참조가 생기면 Count를 증가시키고 참조가 사라지면 감소시킵니다.
Count가 0이 되면 더 이상 사용되지 않는 객체라고 판단해서 제거합니다.
문제는 순환 참조입니다.
예를 들어,
A → B
↑   ↓
└───┘

A와 B가 서로를 참조하고 있다면 프로그램에서는 더 이상 둘을 사용하지 않더라도 Reference Count가 0이 되지 않습니다.
이 때문에 객체가 제거되지 않는 Retain Cycle이 발생할 수 있습니다.

```
