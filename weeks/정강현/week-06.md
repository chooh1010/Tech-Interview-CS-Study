<details>
<summary><b>꼬리 질문 4개 (펼치기)</b></summary>

- 세션 방식의 로그인 과정에 대해 설명해 주세요.
- HTTP의 특성인 Stateless에 대해 설명해 주세요.
- Stateless의 의미를 살펴보면, 세션은 적절하지 않은 인증 방법 아닌가요?
- 규모가 커져 서버가 여러 개가 된다면, 세션을 어떻게 관리할 수 있을까요?

</details>

**내 답변**

```
쿠키와 세션은 HTTP의 Stateless 특성을 보완해서 사용자의 상태를 유지하기 위한 방법입니다.

쿠키는 데이터를 클라이언트의 브라우저에 저장합니다. 서버가 응답으로 쿠키를 보내면 브라우저가 저장하고, 이후 요청에 해당 쿠키를 함께 전송할 수 있습니다.

세션은 실제 사용자 정보를 서버에 저장하고, 클라이언트는 일반적으로 세션을 식별하기 위한 Session ID만 쿠키로 가지고 있습니다.

따라서 쿠키는 서버 부담이 적지만 클라이언트에 저장되기 때문에 민감한 정보를 직접 저장하면 안 되고, 세션은 서버에서 관리하기 때문에 상대적으로 안전하지만 사용자가 많아질수록 서버의 저장 공간이 필요합니다.
```


**꼬리 답변**

```
1.
1. 사용자가 ID와 비밀번호로 로그인 요청
2. 서버가 사용자 정보를 확인
3. 서버가 Session 생성
4. Session ID 생성
5. 서버가 Session ID를 쿠키 등에 담아서 클라이언트에게 전달
6. 브라우저가 Session ID 저장
7. 이후 요청마다 Session ID 전송
8. 서버가 Session ID를 이용해서 사용자를 식별


2. 서버가 이전 요청의 상태를 기본적으로 기억하지 않는다는 의미입니다.

예를 들어,
1번째 요청: 나는 정강현입니다.
2번째 요청: 내 이름이 뭐야?

HTTP 자체만 놓고 보면 서버는 두 번째 요청에서 첫 번째 요청을 기억하지 않습니다.

그래서 로그인 상태 같은 정보를 유지하려면 쿠키, 세션, 토큰 등을 사용합니다.

3. HTTP 자체는 Stateless이지만 애플리케이션 요구사항에 따라 로그인 상태를 유지해야 할 수 있습니다.

세션은 HTTP 자체의 특성을 바꾸는 것이 아니라 애플리케이션 계층에서 상태를 별도로 관리하는 방식입니다.

따라서 Stateless와 세션은 모순되는 개념은 아닙니다.

다만 세션을 많이 사용하면 서버가 상태를 저장해야 하므로 확장성이 떨어질 수 있습니다.

4. 대표적으로 세 가지 방법이 있습니다.
- Sticky Session: 같은 사용자의 요청을 항상 같은 서버로 보냄
- Session Replication: 서버끼리 세션 정보를 복제
- 외부 저장소 사용: Redis 같은 공통 저장소에 세션 저장
실제 분산 환경에서는 여러 서버가 공유할 수 있는 Redis 같은 외부 세션 저장소를 사용하는 방법이 많이 사용됩니다.
```

#### 2. HTTP 응답코드에 대해 설명해 주세요.

`★☆☆` · `필수` · 원본 [네트워크 #2](../03-NETWORK.md)

<details>
<summary><b>꼬리 질문 3개 (펼치기)</b></summary>

- 401 (Unauthorized) 와 403 (Forbidden)은 의미적으로 어떤 차이가 있나요?
- 200 (ok) 와 201 (created) 의 차이에 대해 설명해 주세요.
- 필요하다면 저희가 직접 응답코드를 정의해서 사용할 수 있을까요? 예를 들어 285번 처럼요.

</details>

**내 답변**

```
HTTP 상태 코드는 서버가 클라이언트 요청을 처리한 결과를 숫자로 표현한 것입니다.

크게 다섯 종류로 구분할 수 있습니다.
1xx : 정보
2xx : 성공
3xx : 리다이렉션
4xx : 클라이언트 오류
5xx : 서버 오류

대표적으로,
200 OK             요청 성공
201 Created        리소스 생성 성공

301 Moved Permanently
302 Found           리다이렉션

400 Bad Request     잘못된 요청
401 Unauthorized    인증 필요
403 Forbidden       권한 없음
404 Not Found       리소스 없음

500 Internal Server Error
503 Service Unavailable

가 있습니다.
```

**꼬리 답변**

```
1. 쉽게 말하면,
401 → 너 누구야?
403 → 누군지는 아는데 들어오면 안 돼.

입니다.

401 Unauthorized는 일반적으로 인증 정보가 없거나 유효하지 않은 경우입니다.

403 Forbidden은 서버가 사용자를 알고 있지만 해당 리소스에 접근할 권한이 없는 경우입니다.

2. 둘 다 성공 응답입니다.

200 OK는 일반적인 요청 성공이고,

201 Created는 요청 결과로 새로운 리소스가 생성되었을 때 사용합니다.

예를 들어,
GET /users/1 → 200
POST /users → 새로운 회원 생성 → 201

이라고 생각하면 됩니다.

3. 기술적으로 서버가 임의의 숫자를 응답할 수는 있지만 권장하지 않습니다.

HTTP 표준에 정의된 상태코드를 사용하는 것이 클라이언트, 프록시, 브라우저 등과의 호환성과 의미 전달 측면에서 좋습니다.

애플리케이션의 세부 결과가 필요하면 보통 표준 HTTP 상태 코드와 함께 Response Body에 별도의 비즈니스 코드를 제공합니다.
```

#### 3. HTTP Method 에 대해 설명해 주세요.

`★☆☆` · `필수` · 원본 [네트워크 #3](../03-NETWORK.md)

<details>
<summary><b>꼬리 질문 4개 (펼치기)</b></summary>

- HTTP Method의 멱등성에 대해 설명해 주세요.
- GET과 POST의 차이는 무엇인가요?
- POST와 PUT, PATCH의 차이는 무엇인가요?
- HTTP 1.1 이후로, GET에도 Body에 데이터를 실을 수 있게 되었습니다. 그럼에도 불구하고 왜 아직도 이런 방식을 지양하는 것일까요?

</details>

**내 답변**

```
HTTP Method는 클라이언트가 서버의 리소스에 어떤 작업을 원하는지를 나타냅니다.

대표적으로,
GET     조회
POST    생성 또는 처리
PUT     전체 수정/교체
PATCH   일부 수정
DELETE  삭제

가 있습니다.

REST API에서는 URL로 리소스를 나타내고 HTTP Method를 이용해서 해당 리소스에 수행할 행동을 표현합니다.
```

**꼬리 답변**

```
1. 같은 요청을 한 번 보내든 여러 번 보내든 서버의 최종 상태가 같으면 멱등하다고 합니다.

예를 들어,
DELETE /users/1

을 한 번 실행하든 여러 번 실행하든 최종 결과는
user 1이 없음

이므로 멱등합니다.

일반적으로:
GET     멱등
PUT     멱등
DELETE  멱등
POST    비멱등

이라고 봅니다.

PATCH는 구현에 따라 멱등할 수도, 아닐 수도 있습니다.

2. GET은 주로 리소스 조회, POST는 주로 리소스 생성 또는 서버에서의 처리에 사용합니다.

GET은 일반적으로 Query Parameter를 이용하고, 캐싱이 가능하며 멱등성을 가집니다.

POST는 요청 Body에 데이터를 담는 경우가 많고 같은 요청을 반복하면 새로운 데이터가 여러 번 생성될 수 있기 때문에 일반적으로 멱등하지 않습니다.

3. POST  → 생성 또는 처리
PUT   → 리소스 전체 교체
PATCH → 리소스 일부 수정

예를 들어 기존 데이터가
{
  "name": "Kim",
  "age": 20
}

인데 age만 변경하고 싶다면 PATCH가 자연스럽습니다.

PUT은 보통 해당 리소스 전체 상태를 전달해 교체하는 의미로 사용합니다.

4. HTTP 문법상 GET 요청에 Body를 절대 넣을 수 없는 것은 아니지만, GET Body의 의미가 표준에서 일반적인 요청 전달 방식으로 명확하게 정의되어 있지 않습니다.

또한 브라우저, 프록시, 캐시, 서버 프레임워크 등이 GET Body를 지원하지 않거나 무시할 수 있기 때문에 호환성 문제가 생길 수 있습니다.

따라서 GET에서는 일반적으로 Query Parameter를 사용합니다.

```

#### 4. HTTP에 대해 설명해 주세요.

`★★☆` · `필수` · 원본 [네트워크 #4](../03-NETWORK.md)

<details>
<summary><b>꼬리 질문 3개 (펼치기)</b></summary>

- 공개키와 대칭키에 대해 설명해 주세요.
- 왜 HTTPS Handshake 과정에서는 인증서를 사용하는 것 일까요?
- SSL과 TLS의 차이는 무엇인가요?

</details>

**내 답변**

```
HTTP는 HyperText Transfer Protocol의 약자로 클라이언트와 서버가 데이터를 주고받기 위한 애플리케이션 계층 프로토콜입니다.

클라이언트가 Request를 보내면 서버가 Response를 반환하는 요청-응답 구조를 사용합니다.

대표적인 특징은 Stateless이며, HTTP/1.1과 HTTP/2는 일반적으로 TCP 위에서 동작합니다.

HTTP 자체는 데이터를 암호화하지 않기 때문에 보안이 필요한 경우 TLS를 적용한 HTTPS를 사용합니다.
```

**꼬리 답변**

```
1. 대칭키 암호화는 암호화와 복호화에 같은 키를 사용합니다.

장점은 빠르다는 것이고, 단점은 상대방에게 키를 안전하게 전달하는 것이 어렵다는 것입니다.

공개키 암호화는 공개키와 개인키라는 서로 다른 키를 사용합니다.

공개키로 암호화하면 대응되는 개인키로 복호화할 수 있습니다.

속도는 대칭키보다 느리지만 안전하게 키를 교환하거나 신원을 확인하는 데 사용할 수 있습니다.

HTTPS에서는 두 방식을 적절히 결합해서 사용합니다.

2. 암호화만 한다고 해서 현재 통신하는 서버가 진짜 서버인지 알 수 있는 것은 아닙니다.

인증서는
이 공개키는 실제로 이 서버의 것입니다.

라는 사실을 신뢰할 수 있는 **인증기관(CA)**을 통해 확인하는 역할을 합니다.

따라서 중간자 공격을 방지하고 서버의 신원을 확인하는 데 사용합니다.

3. TLS는 SSL을 개선해서 만든 후속 프로토콜입니다.

SSL의 오래된 버전들은 보안상 문제가 있어 현재는 사용하지 않고, 실질적으로는 TLS를 사용합니다.

다만 관습적으로 아직도 SSL 인증서, SSL 연결이라는 표현을 사용하는 경우가 있습니다.
```

- 소켓과 포트의 차이가 무엇인가요?
- 여러 소켓이 있다고 할 때, 그 소켓의 포트 번호는 모두 다른가요?
- 사용자의 요청이 무수히 많아지면, 소켓도 무수히 생성되나요?

</details>

**내 답변**

```
Socket은 네트워크에서 프로세스 간 통신을 위한 통신의 끝점입니다.

TCP Socket이나 UDP Socket 등을 이용해서 데이터를 송수신할 수 있습니다.

반면 WebSocket은 웹 환경에서 클라이언트와 서버가 하나의 연결을 유지하면서 양방향 통신을 할 수 있도록 만든 애플리케이션 계층 프로토콜입니다.

WebSocket은 처음 연결할 때 HTTP를 이용한 Handshake를 수행한 후 WebSocket 연결로 전환합니다.

따라서 채팅이나 실시간 알림처럼 서버가 클라이언트에게 즉시 데이터를 보내야 하는 서비스에 적합합니다.
```

**꼬리 답변**

```
1. Port는 운영체제가 어떤 프로세스에게 데이터를 전달할지를 구분하기 위한 번호입니다.

Socket은 실제 네트워크 통신을 위한 끝점입니다.

쉽게 말하면,
IP   → 건물 주소
Port → 방 번호
Socket → 그 방에서 실제 통신하는 통로

정도로 이해하면 됩니다.

2. 아닙니다.

서버는 하나의 포트 번호를 이용해 여러 클라이언트와 동시에 통신할 수 있습니다.

TCP 연결은 일반적으로 다음 네 가지 정보로 구분됩니다.
출발지 IP
출발지 Port
목적지 IP
목적지 Port

따라서 서버의 포트가 모두 443이어도 클라이언트 IP나 포트가 다르면 서로 다른 연결로 구분할 수 있습니다.

3. 연결마다 소켓이 생성될 수 있지만 실제로 무한히 만들 수 있는 것은 아닙니다.

OS의 File Descriptor 제한, 메모리, 포트, CPU 등의 자원 제한이 존재합니다.

대규모 서버에서는 Thread 하나가 Socket 하나를 담당하는 방식 대신 epoll 같은 I/O Multiplexing 기술을 사용해서 많은 연결을 효율적으로 처리하기도 합니다.
```

#### 6. HTTP/1.1과 HTTP/2의 차이점은 무엇인가요?

`★★☆` · `필수` · 원본 [네트워크 #6](../03-NETWORK.md)

<details>
<summary><b>꼬리 질문 2개 (펼치기)</b></summary>

- HOL Blocking 에 대해 설명해 주세요.
- HTTP/3.0의 주요 특징에 대해 설명해 주세요.

</details>

**내 답변**

```
HTTP/1.1에서는 하나의 TCP 연결에서 여러 요청을 처리할 수 있지만 요청 처리 과정에서 비효율이 존재했습니다.

HTTP/2에서는 데이터를 텍스트 단위가 아닌 Binary Frame으로 처리하고, 하나의 TCP 연결에서 여러 요청과 응답을 동시에 처리하는 Multiplexing을 제공합니다.

또한 Header Compression을 사용해서 반복되는 HTTP Header의 크기를 줄입니다.

따라서 HTTP/2는 HTTP/1.1보다 여러 리소스를 동시에 요청할 때 효율적입니다.
```

**꼬리 답변**

```
1. HOL은 Head Of Line Blocking입니다.

앞에 있는 요청이나 패킷의 처리가 지연되면서 뒤에 있는 요청들도 같이 기다리게 되는 현상입니다.

HTTP/1.1에서는 요청 처리 순서 때문에 애플리케이션 계층에서 이런 문제가 발생할 수 있었습니다.

HTTP/2는 Multiplexing으로 HTTP 계층의 HOL Blocking을 크게 개선했습니다.

하지만 HTTP/2도 TCP를 사용하기 때문에 TCP 패킷 하나가 손실되면 해당 TCP 연결의 다른 Stream도 재전송을 기다리는 문제가 있습니다.

2. HTTP/3는 TCP 대신 QUIC를 사용합니다.

QUIC는 UDP를 기반으로 구현되며 각 Stream을 독립적으로 처리할 수 있어 TCP 수준에서 발생하던 HOL Blocking 문제를 줄일 수 있습니다.

또한 연결 및 암호화 설정 비용을 줄여 빠른 연결 수립을 목표로 합니다.
```

#### 7. Stateless와 Connectionless에 대해 설명해 주세요.

`★★☆` · `필수` · 원본 [네트워크 #16](../03-NETWORK.md)

<details>
<summary><b>꼬리 질문 3개 (펼치기)</b></summary>

- 왜 HTTP는 Stateless 구조를 채택하고 있을까요?
- Connectionless의 논리대로면 성능이 되게 좋지 않을 것으로 보이는데, 해결 방법이 있을까요?
- TCP의 keep-alive와 HTTP의 keep-alive의 차이는 무엇인가요?

</details>

**내 답변**

```
Stateless는 서버가 클라이언트의 이전 요청 상태를 기본적으로 기억하지 않는 특성입니다.

각 요청은 독립적으로 처리됩니다.

Connectionless는 통신에 필요한 연결을 계속 유지하지 않고 필요한 시점에 요청과 응답을 처리하는 특성을 의미합니다.

이런 특성 덕분에 서버가 많은 클라이언트를 효율적으로 처리하고 확장하기 쉬워집니다.

다만 HTTP/1.1부터는 매 요청마다 TCP 연결을 새로 생성하는 비용을 줄이기 위해 Persistent Connection, 즉 HTTP Keep-Alive를 기본적으로 활용합니다.
```

**꼬리 답변**

```
1. 서버가 모든 클라이언트의 상태를 계속 저장해야 한다면 사용자 수가 증가할수록 서버 부담이 커집니다.

Stateless에서는 각각의 요청을 독립적으로 처리할 수 있기 때문에 여러 서버에 요청을 분산하기 쉽고 서버 확장성이 좋아집니다.

2. 맞습니다.

TCP 연결을 요청마다 새로 생성하면 TCP Handshake 비용이 발생합니다.

그래서 HTTP/1.1에서는 Persistent Connection / Keep-Alive를 이용해 하나의 TCP 연결을 여러 HTTP 요청에 재사용합니다.

3. HTTP Keep-Alive는 하나의 TCP 연결을 여러 HTTP 요청과 응답에 재사용하는 것입니다.

반면 TCP Keep-Alive는 오랫동안 데이터가 없는 TCP 연결이 여전히 살아 있는지 확인하기 위해 주기적으로 Probe 패킷을 보내는 TCP 기능입니다.

즉,
HTTP Keep-Alive
→ TCP 연결 재사용

TCP Keep-Alive
→ TCP 상대방이 아직 살아 있는지 확인

입니다.

```

#### 8. 문자열 인코딩에 대해 설명해 주세요.

`★★☆` · `심화` · 원본 [개발상식·기타 #16](../05-ETC.md)

<details>
<summary><b>꼬리 질문 1개 (펼치기)</b></summary>

- Base64 인코딩은 일반적인 문자열 인코딩과는 달리, 사용자가 읽기 어려운 알파벳과 숫자 조합으로 변경합니다. 이를 사용하는 이유는 무엇일까요?

</details>

**내 답변**

```
문자열 인코딩은 사람이 사용하는 문자를 컴퓨터가 저장하고 전송할 수 있는 바이트 형태로 변환하는 규칙입니다.

예를 들어 ASCII, Unicode, UTF-8 등이 있습니다.

ASCII는 영문자와 숫자 등 제한적인 문자만 표현할 수 있었기 때문에 다양한 언어를 표현하기 위해 Unicode가 만들어졌습니다.

UTF-8은 Unicode 문자를 실제 바이트로 표현하는 대표적인 인코딩 방식이며 현재 웹에서 널리 사용됩니다.

인코딩과 디코딩 방식이 서로 다르면 한글이 깨지는 것처럼 문자열이 정상적으로 표시되지 않을 수 있습니다.
```

**꼬리 답변**

```
Base64는 데이터를 암호화하기 위한 것이 아니라 Binary 데이터를 문자 데이터로 안전하게 표현하기 위한 인코딩 방식입니다.

일부 통신 환경에서는 Binary 데이터를 그대로 전송하기 어렵거나 특정 문자가 특별한 의미를 가질 수 있습니다.

그래서 Binary 데이터를
A-Z
a-z
0-9
+
/

같은 제한된 문자 집합으로 변환해서 안전하게 전달할 수 있습니다.

대표적으로 이미지나 인증 관련 데이터를 문자열 형태로 전달해야 할 때 사용할 수 있습니다.

중요한 점은:
Base64는 암호화가 아니다.

누구나 쉽게 다시 디코딩할 수 있기 때문에 비밀번호를 보호하는 용도로 사용하면 안 됩니다.
```

#### 9. MVC 패턴이 무엇인가요?

`★★☆` · `필수` · 원본 [개발상식·기타 #9](../05-ETC.md)

<details>
<summary><b>꼬리 질문 1개 (펼치기)</b></summary>

- 다른 아키텍쳐 패턴은 없나요? MVC랑 비교해서 어떤 차이가 있나요?

</details>

**내 답변**

```
MVC는 애플리케이션을 Model, View, Controller 세 가지 역할로 분리하는 디자인 패턴입니다.

Model은 데이터와 비즈니스 로직을 담당합니다.

View는 사용자에게 보여주는 화면을 담당합니다.

Controller는 사용자의 요청을 받아 Model과 View를 연결하는 역할을 합니다.

이렇게 역할을 분리하면 관심사가 분리되어 코드의 유지보수성과 확장성이 좋아집니다.
```

**꼬리 답변**

```
대표적으로 MVP, MVVM 등이 있습니다.
MVC
Model - View - Controller

MVP
Model - View - Presenter

MVVM
Model - View - ViewModel

MVC에서는 Controller가 사용자 입력을 받고 Model과 View를 연결합니다.

MVP에서는 Presenter가 View의 로직을 더 적극적으로 담당합니다.

MVVM에서는 ViewModel이 View가 사용할 데이터를 제공하고 Data Binding을 통해 View와 연결하는 방식이 많이 사용됩니다.

Android나 프론트엔드 개발에서는 MVVM 구조도 자주 볼 수 있습니다.
```
