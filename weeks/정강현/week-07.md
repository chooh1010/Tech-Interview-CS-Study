#### 1. TCP와 UDP의 차이에 대해 설명해 주세요.

`★★☆` · `필수` · 원본 [네트워크 #7](../03-NETWORK.md)

<details>
<summary><b>꼬리 질문 9개 (펼치기)</b></summary>

- Checksum이 무엇인가요?
- TCP와 UDP 중 어느 프로토콜이 Checksum을 수행할까요?
- 그렇다면, Checksum을 통해 오류를 정정할 수 있나요?
- TCP가 신뢰성을 보장하는 방법에 대해 설명해 주세요.
- TCP의 혼잡 제어 처리 방법에 대해 설명해 주세요.
- 왜 HTTP는 TCP를 사용하나요?
- 그렇다면, 왜 HTTP/3 에서는 UDP를 사용하나요? 위에서 언급한 UDP의 문제가 해결되었나요?
- 그런데, 브라우저는 어떤 서버가 TCP를 쓰는지 UDP를 쓰는지 어떻게 알 수 있나요?
- 본인이 새로운 통신 프로토콜을 TCP나 UDP를 사용해서 구현한다고 하면, 어떤 기준으로 프로토콜을 선택하시겠어요?

</details>

**내 답변**

```
TCP와 UDP는 모두 전송 계층(Transport Layer) 프로토콜입니다.

TCP는 연결 지향형 프로토콜로, 통신 전에 연결을 설정하고 데이터가 제대로 전달되었는지 확인합니다. 순서 보장, 재전송, 흐름 제어, 혼잡 제어 등을 제공하기 때문에 신뢰성이 높지만 상대적으로 오버헤드가 큽니다.

UDP는 비연결형 프로토콜로, 연결 과정 없이 데이터를 바로 전송합니다. 데이터 도착 여부나 순서를 보장하지 않지만 구조가 단순해서 빠르고 지연이 적습니다.

따라서 TCP는 웹, 파일 전송처럼 정확성이 중요한 곳에 사용하고, UDP는 실시간 스트리밍, 게임, DNS처럼 속도와 지연이 중요한 곳에 많이 사용합니다.
```

**꼬리 답변**

```
1. 전송 중 데이터가 손상되었는지 확인하기 위한 오류 검출 값입니다.

송신자가 데이터를 기반으로 Checksum을 계산해 같이 보내고, 수신자가 다시 계산해서 값이 다르면 데이터가 손상됐다고 판단합니다.

2. 둘 다 Checksum을 사용할 수 있습니다.

TCP는 Checksum 필드를 가지고 있고, UDP도 Checksum 필드를 가지고 있습니다.

즉 UDP가 신뢰성 보장을 하지 않는다고 해서 오류 검출 자체를 전혀 안 하는 것은 아닙니다.

3. 아니요.

Checksum의 기본 목적은 오류 검출입니다.
Checksum 불일치
→ "데이터가 잘못됐다"는 건 알 수 있음
→ 어느 부분이 잘못됐는지 직접 고치지는 못함

TCP에서는 오류나 손실을 감지하면 재전송을 통해 신뢰성을 보장합니다.

4. 대표적으로 다음 방법을 사용합니다.
- Sequence Number: 데이터 순서 관리
- ACK: 수신 여부 확인
- Timeout: 일정 시간 ACK가 없으면 재전송
- Checksum: 데이터 오류 검출
- 흐름 제어: 수신자가 처리 가능한 만큼 전송
- 혼잡 제어: 네트워크 상황에 맞게 전송량 조절
핵심은 순서 번호 + ACK + 재전송이라고 기억하면 됩니다.

5. TCP는 네트워크가 처리 가능한 양보다 너무 많은 데이터를 보내지 않도록 전송량을 조절합니다.

대표적으로 **Congestion Window(cwnd)**를 이용합니다.

처음에는 적은 양을 보내다가 정상적으로 ACK가 들어오면 전송량을 증가시키고, 패킷 손실이 감지되면 네트워크가 혼잡하다고 판단해 전송량을 줄입니다.

대표 개념으로 Slow Start, Congestion Avoidance 등이 있습니다.

6. HTTP에서는 HTML, JSON, 이미지 같은 데이터가 손실되거나 순서가 바뀌면 정상적인 통신이 어렵습니다.

그래서 신뢰성 있고 순서를 보장하는 TCP를 사용해 왔습니다.

7. HTTP/3는 단순한 UDP만 사용하는 것이 아니라 UDP 위에 QUIC라는 프로토콜을 구현합니다.

QUIC가 자체적으로
- 신뢰성
- 재전송
- 흐름 제어
- 혼잡 제어
- 암호화
등을 제공합니다.

즉,
UDP의 문제를 그냥 방치
X

UDP 위에서 QUIC가 필요한 기능을 구현
O

입니다.

8. 사용하려는 프로토콜 버전과 서버가 지원하는 기능을 협상해서 결정합니다.

HTTPS 연결 과정에서 서버가 HTTP/2 또는 HTTP/3 등을 지원하는지 확인할 수 있고, HTTP/3 사용이 가능하면 QUIC 기반 통신을 사용할 수 있습니다.

9. 요구사항에 따라 선택합니다.

정확한 데이터 전달과 순서 보장이 중요하다면 TCP를 선택하고, 약간의 데이터 손실을 허용하면서 낮은 지연과 빠른 전송이 중요하다면 UDP를 선택하겠습니다.

예를 들어,
파일 전송 → TCP
실시간 게임 위치 정보 → UDP

처럼 판단할 수 있습니다.

```

#### 2. OSI 7계층에 대해 설명해 주세요.

<details>
<summary><b>꼬리 질문 5개 (펼치기)</b></summary>

- 각 Layer는 패킷을 어떻게 명칭하나요? 예를 들어, Transport Layer의 경우 Segment라 부릅니다.
- 각각의 Header의 Packing Order에 대해 설명해 주세요.
- ARP에 대해 설명해 주세요.

**내 답변**

```
OSI 7계층은 네트워크 통신 과정을 역할별로 7개의 계층으로 나눈 모델입니다.
7 Application     응용
6 Presentation    표현
5 Session         세션
4 Transport       전송
3 Network         네트워크
2 Data Link       데이터 링크
1 Physical        물리

각 계층은 자신의 역할을 담당하고 아래 계층의 기능을 이용합니다.

대표적으로 HTTP는 응용 계층, TCP/UDP는 전송 계층, IP는 네트워크 계층, Ethernet은 데이터 링크 계층에 해당합니다.
```

**꼬리 답변**

```
1. Transport Layer는 프로세스와 프로세스 사이의 통신을 담당합니다.

TCP/UDP와 Port 번호가 여기에 해당합니다.

Network Layer는 호스트와 호스트 사이의 통신 및 경로 선택을 담당합니다.

IP와 Router가 대표적입니다.
Network   → 어느 컴퓨터로?
Transport → 그 컴퓨터의 어느 프로그램으로?

2. 둘 다 IP 주소를 기반으로 패킷을 전달할 수 있습니다.

일반적으로 L3 Switch는 LAN 내부에서 빠른 패킷 전달에 초점을 두고, Router는 서로 다른 네트워크를 연결하고 WAN 라우팅, NAT 등 더 다양한 기능을 수행하는 경우가 많습니다.

다만 현대 장비에서는 기능 경계가 많이 겹칩니다.

3. Application                  Data
Transport                    Segment(TCP) / Datagram(UDP)
Network                      Packet
Data Link                    Frame
Physical                     Bit

4. 상위 계층의 데이터에 하위 계층이 자신의 Header를 붙이는 Encapsulation 과정을 거칩니다.

예를 들어:
HTTP Data
↓
TCP Header + HTTP Data
↓
IP Header + TCP Segment
↓
Ethernet Header + IP Packet

수신 측에서는 반대로 하나씩 제거하는 Decapsulation을 수행합니다.

5. ARP는 IP 주소를 이용해서 해당 장치의 MAC 주소를 알아내는 프로토콜입니다.

같은 LAN에서 데이터를 보내려면 실제 Ethernet Frame에 목적지 MAC 주소가 필요합니다.

따라서 IP 주소는 알고 있지만 MAC 주소를 모르는 경우 ARP를 이용합니다.

```

#### 3. 3-Way Handshake에 대해 설명해 주세요.

`★★☆` · `필수` · 원본 [네트워크 #11](../03-NETWORK.md)

<details>
<summary><b>꼬리 질문 5개 (펼치기)</b></summary>

- ACK, SYN 같은 정보는 어떻게 전달하는 것 일까요?
- 2-Way Handshaking 를 하지않는 이유에 대해 설명해 주세요.
- 두 호스트가 동시에 연결을 시도하면, 연결이 가능한가요? 가능하다면 어떻게 통신 연결을 수행하나요?
- SYN Flooding 에 대해 설명해 주세요.
- 위 질문과 모순될 수 있지만, 3-Way Handshake의 속도 문제 때문에 이동 수를 줄이는 0-RTT 기법을 많이 적용하고 있습니다. 어떤 방식으로 가능한 걸까요?

</details>

**내 답변**

```
3-Way Handshake는 TCP 연결을 설정하기 위한 과정입니다.
Client                         Server

SYN ------------------------->
     <---------------- SYN + ACK
ACK ------------------------->

연결 완료

첫 번째로 클라이언트가 SYN을 보내 연결을 요청합니다.

서버는 SYN을 받고 SYN + ACK로 응답합니다.

마지막으로 클라이언트가 ACK를 보내면서 양쪽이 서로 송수신할 수 있음을 확인하고 연결이 성립됩니다.
```

**꼬리 답변**

```
1. TCP Header에 있는 Flag Bit를 이용합니다.

TCP Header에는 SYN, ACK, FIN, RST 등의 제어 Flag가 있습니다.

예를 들어 SYN Flag를 1로 설정하면 연결 요청임을 나타냅니다.

2. 양쪽 모두가 송신과 수신이 가능한 상태인지 확인해야 하기 때문입니다.

2-Way만 사용하면 서버는 클라이언트의 요청을 받고 응답할 수 있다는 것은 알 수 있지만, 서버의 응답이 실제로 클라이언트에게 전달되었는지 서버 입장에서 확인할 수 없습니다.

세 번째 ACK를 통해 서버도 클라이언트가 자신의 응답을 받았다는 사실을 확인합니다.

3. 가능합니다.

TCP에서는 양쪽이 동시에 SYN을 보내는 Simultaneous Open 상황도 처리할 수 있습니다.

각자 SYN을 보낸 뒤 서로의 SYN에 ACK를 보내면서 연결 상태를 맞춥니다.

4. 공격자가 대량의 SYN 패킷을 보내고 마지막 ACK를 보내지 않는 공격입니다.

서버는 연결이 완료될 것으로 생각하고 Half-Open Connection 상태로 자원을 유지하게 됩니다.

이것이 대량으로 발생하면 정상 사용자가 연결하지 못하는 DoS 공격이 될 수 있습니다.

대응 방법 중 하나로 SYN Cookie가 있습니다.

5. 이전에 서버와 통신했던 정보를 재사용해서 처음부터 일부 데이터를 전송하는 방식입니다.

예를 들어 QUIC/TLS에서는 이전 연결에서 얻은 세션 정보를 이용해 새 연결 시 Handshake 왕복 횟수를 줄일 수 있습니다.

다만 0-RTT 데이터는 Replay Attack 등에 주의해야 합니다.

```

#### 4. 4-Way Handshake에 대해 설명해 주세요.

`★★☆` · `필수` · 원본 [네트워크 #12](../03-NETWORK.md)

<details>
<summary><b>꼬리 질문 4개 (펼치기)</b></summary>

- 패킷이 4-way handshake 목적인지 어떻게 파악할 수 있을까요?
- 빨리 끊어야 할 경우엔, (즉, 4-way Handshake를 할 여유가 없다면) 어떻게 종료할 수 있을까요?
- 4-Way Handshake 과정에서 중간에 한쪽 네트워크가 강제로 종료된다면, 반대쪽은 이를 어떻게 인식할 수 있을까요?
- 왜 종료 후에 바로 끝나지 않고, TIME_WAIT 상태로 대기하는 것 일까요?

</details>

**내 답변**

```
4-Way Handshake는 TCP 연결을 정상적으로 종료하는 과정입니다.
Client                      Server

FIN ----------------------->
     <---------------- ACK

     <---------------- FIN
ACK ----------------------->

한쪽에서 FIN을 보내 더 이상 보낼 데이터가 없다고 알립니다.

상대방은 ACK를 보내고, 자신도 데이터를 모두 보낸 뒤 FIN을 보냅니다.

마지막으로 ACK가 전달되면서 연결 종료가 진행됩니다.

연결 설정보다 단계가 많은 이유는 TCP가 양방향 통신이기 때문에 각 방향을 독립적으로 종료할 수 있기 때문입니다.
```

**꼬리 답변**

```
1. TCP Header의 FIN, ACK Flag를 확인합니다.

FIN은 연결 종료 의사를 나타냅니다.

2. 정상적인 FIN 기반 종료 대신 TCP의 RST(Reset) 패킷으로 연결을 즉시 종료할 수 있습니다.

RST는 정상적인 graceful shutdown이 아니라 연결을 강제로 끊는 방식입니다.

3. 즉시 알아차리지 못할 수도 있습니다.

이후 데이터를 보냈는데 응답이 없고 재전송이 계속 실패하면 Timeout을 통해 연결이 끊어진 것으로 판단할 수 있습니다.

TCP Keep-Alive 등을 이용해 장시간 통신이 없는 연결의 생존 여부를 확인할 수도 있습니다.

4. 대표적으로 두 가지 이유가 있습니다.

첫째, 마지막 ACK가 유실됐을 때 상대방이 FIN을 다시 보내면 ACK를 재전송하기 위해서입니다.

둘째, 이전 연결에서 지연된 패킷이 같은 IP/Port를 사용하는 새로운 연결에 잘못 전달되는 것을 방지하기 위해서입니다.

5. 라우터가 패킷을 받으면 목적지 IP 주소를 확인하고 Forwarding Table을 조회해서 어느 인터페이스로 패킷을 내보낼지 결정합니다.

일반적으로 목적지 IP 주소와 가장 잘 일치하는 네트워크 Prefix를 찾는 Longest Prefix Match를 사용합니다.

이후 결정된 출력 인터페이스를 통해 다음 Router 또는 목적지 네트워크로 패킷을 전달합니다.

```

#### 9. 순수함수가 무엇인지를 함수형 프로그래밍 매커니즘과 연관지어 설명해 주세요.

`★★☆` · `심화` · 원본 [개발상식·기타 #8](../05-ETC.md)

<details>
<summary><b>꼬리 질문 4개 (펼치기)</b></summary>

- Side Effect가 무엇인가요? 이를 모두 없애는 프로그래밍이 이상적이라고 할 수 있을까요?
- 왜 함수형 프로그래밍 매커니즘을 사용한다고 생각하시나요?
- 순수함수는 Thread Safe 한가요? 왜 그럴까요?
- 고차함수에 대해 설명해 주세요.

</details>

**내 답변**

```
순수함수는 같은 입력에 대해서 항상 같은 출력을 반환하고 외부 상태를 변경하지 않는 함수입니다.

예를 들어:
int add(int a, int b) {
    return a + b;
}

는 같은 a, b가 들어오면 항상 같은 결과를 반환하고 외부 상태를 변경하지 않으므로 순수함수라고 할 수 있습니다.

함수형 프로그래밍에서는 이런 순수함수와 불변성을 활용해서 프로그램의 상태 변경을 최소화합니다.

그 결과 코드의 동작을 예측하기 쉽고 테스트와 병렬 처리에도 유리합니다.
```

**꼬리 답변**

```
1. Side Effect는 함수가 자신의 반환값 이외에 외부 상태에 영향을 미치는 것을 의미합니다.

예를 들어:
전역 변수 변경
파일 쓰기
DB 수정
화면 출력
네트워크 요청

등이 있습니다.

모든 Side Effect를 없앨 수는 없습니다. 실제 프로그램은 DB 저장이나 네트워크 통신처럼 외부 세계와 상호작용해야 하기 때문입니다.

따라서 함수형 프로그래밍에서는 Side Effect를 무조건 제거하기보다 가능한 부분은 순수하게 만들고 Side Effect가 발생하는 부분을 명확하게 분리하려고 합니다.

2. 상태 변경과 Side Effect를 줄여 프로그램의 동작을 예측하기 쉽게 만들기 때문입니다.

또한 함수가 독립적이므로 테스트하기 쉽고, 공유 상태가 줄어들기 때문에 병렬 처리나 동시성 처리에서도 장점이 있습니다.

3. 순수함수 자체는 일반적으로 Thread Safe하다고 볼 수 있습니다.

외부의 변경 가능한 상태를 공유하지 않고 같은 입력에 같은 결과를 반환하기 때문입니다.

여러 Thread가 동시에 호출하더라도 서로 변경하는 공유 상태가 없기 때문에 Race Condition이 발생할 가능성이 적습니다.

4. 함수를 매개변수로 받거나 함수를 반환하는 함수입니다.

예를 들어 Java Stream에서:
list.stream()
    .filter(x -> x > 10)
    .map(x -> x * 2);

filter()와 map()은 동작을 나타내는 함수를 전달받습니다.

따라서 함수형 프로그래밍에서는 함수를 하나의 값처럼 다룰 수 있습니다.

```
