#### 1. Key (기본키, 후보키, 슈퍼키 등등...) 에 대해 설명해 주세요.

`★☆☆` · `필수` · 원본 [데이터베이스 #1](../04-DATABASE.md)

<details>
<summary><b>꼬리 질문 4개 (펼치기)</b></summary>

- 기본키는 수정이 가능한가요?
- 사실 MySQL의 경우, 기본키를 설정하지 않아도 테이블이 만들어집니다. 어떻게 이게 가능한 걸까요?
- 외래키 값은 NULL이 들어올 수 있나요?
- 어떤 칼럼의 정의에 UNIQUE 키워드가 붙는다고 가정해 봅시다. 이 칼럼을 활용한 쿼리의 성능은 그렇지 않은 것과 비교해서 어떻게 다를까요?

</details>

**내 답변**

```
Key는 테이블의 행을 식별하거나 테이블 간 관계를 연결하는 데 사용하는 속성입니다.

슈퍼키는 행을 유일하게 구분할 수 있는 속성의 집합이고, 후보키는 그중 불필요한 속성을 제거한 최소 슈퍼키입니다. 후보키 중 하나를 기본키(Primary Key)로 선택하며, 선택되지 않은 후보키는 대체키라고 합니다.

기본키는 중복되거나 NULL일 수 없습니다. 외래키(Foreign Key)는 다른 테이블의 키를 참조해 관계를 표현하고, 참조 무결성을 유지하는 데 사용합니다.

예를 들어 회원 테이블에서 회원 ID와 이메일이 각각 후보키라면 회원 ID를 기본키로 선택하고 이메일에는 UNIQUE 제약을 둘 수 있습니다.
```

**꼬리 답변**

```
1. 기술적으로는 기본키 값을 UPDATE할 수 있습니다. 다만 다른 테이블의 외래키가 참조 중이면 제약 조건 때문에 수정이 거부되거나 ON UPDATE CASCADE 설정에 따라 함께 변경됩니다. 기본키가 자주 바뀌면 참조 관계와 인덱스 유지 비용이 커지므로 보통 변경되지 않는 값을 선택합니다.

2. MySQL은 PRIMARY KEY 선언을 필수로 요구하지 않습니다. InnoDB는 명시적인 기본키가 없으면 적합한 UNIQUE NOT NULL 인덱스를 클러스터형 인덱스로 사용하고, 그것도 없으면 내부적으로 숨겨진 행 ID를 만듭니다. 따라서 테이블은 생성할 수 있지만, 행 식별과 성능을 고려하면 명시적인 기본키를 두는 편이 좋습니다.

3. 외래키 칼럼에 NULL을 허용했다면 NULL이 들어갈 수 있습니다. NULL은 참조할 대상이 정해지지 않았다는 뜻으로, 일반적으로 외래키 참조 검사를 통과합니다. 반드시 관계가 있어야 한다면 외래키와 함께 NOT NULL 제약을 설정합니다.

4. UNIQUE 제약은 중복을 막으며, MySQL에서는 이를 위한 UNIQUE 인덱스가 만들어집니다. 해당 칼럼을 조건으로 조회하면 인덱스를 활용해 검색이 빨라질 수 있고, 값이 유일하므로 결과가 최대 한 행이라는 점도 최적화에 도움이 됩니다. 다만 실제 성능은 쿼리 조건, 데이터 분포, 실행 계획에 따라 달라지고 INSERT나 UPDATE에는 인덱스 유지 비용이 듭니다.
```

#### 2. RDB와 NoSQL의 차이에 대해 설명해 주세요.

`★★☆` · `필수` · 원본 [데이터베이스 #2](../04-DATABASE.md)

<details>
<summary><b>꼬리 질문 3개 (펼치기)</b></summary>

- NoSQL의 강점과, 약점이 무엇인가요?
- RDB의 어떠한 특징 때문에 NoSQL에 비해 부하가 많이 걸릴 "수" 있을까요? (주의: 무조건 NoSQL이 RDB 보다 빠르다라고 생각하면 큰일 납니다!)
- NoSQL을 활용한 경험이 있나요? 있다면, 왜 RDB를 선택하지 않고 해당 DB를 선택했는지 설명해 주세요.

</details>

**내 답변**

```
RDB는 행과 열로 이루어진 테이블에 데이터를 저장하고, SQL과 테이블 간 관계를 이용하는 데이터베이스입니다. 스키마와 제약 조건을 통해 데이터의 구조와 무결성을 관리하며, JOIN과 트랜잭션이 필요한 업무에 적합합니다.

NoSQL은 문서, 키-값, 컬럼 패밀리, 그래프 등 관계형 테이블 이외의 다양한 데이터 모델을 사용하는 데이터베이스를 가리킵니다. 데이터 구조와 조회 패턴에 맞게 모델을 선택할 수 있고, 제품에 따라 수평 확장에 유리합니다.

둘 중 하나가 항상 더 빠른 것은 아닙니다. 데이터 간 관계, 일관성 요구, 조회 방식, 확장 방식에 맞춰 선택해야 합니다.
```

**꼬리 답변**

```
1. NoSQL의 강점은 제품별 데이터 모델을 활용해 유연한 구조나 특정 조회 패턴을 효율적으로 처리할 수 있다는 점입니다. 반면 관계 조회나 복잡한 집계를 직접 구현해야 할 수 있고, 트랜잭션과 일관성 보장 범위도 제품마다 다릅니다. NoSQL 전체가 스키마나 ACID 트랜잭션을 지원하지 않는다는 뜻은 아닙니다.

2. RDB에서 여러 테이블을 JOIN하거나 강한 제약 조건과 트랜잭션을 유지할 때, 데이터 양과 동시 요청이 커지면 처리 비용이 늘 수 있습니다. 특히 여러 서버에 걸쳐 관계와 일관성을 유지하는 작업은 복잡합니다. 하지만 적절한 인덱스와 쿼리 설계가 된 RDB는 많은 조회에서 매우 빠르므로 실제 실행 계획과 부하를 측정해야 합니다.

3. 실제 사용 경험이 없다면 경험을 만들어 말하지 않겠습니다. 예를 들어 세션처럼 키로 자주 조회하고 만료 시간이 필요한 데이터라면 Redis를 검토할 수 있습니다. 관계형 테이블 간 JOIN보다 키 기반 접근과 만료 기능이 요구에 잘 맞기 때문입니다. 반대로 주문과 결제처럼 여러 데이터의 원자적 변경이 중요하면 RDB를 우선 고려하겠습니다.
```

#### 3. 트랜잭션이 무엇이고, ACID 원칙에 대해 설명해 주세요.

`★★☆` · `필수` · 원본 [데이터베이스 #3](../04-DATABASE.md)

<details>
<summary><b>꼬리 질문 3개 (펼치기)</b></summary>

- ACID 원칙 중, Durability를 DBMS는 어떻게 보장하나요?
- 트랜잭션을 사용해 본 경험이 있나요? 어떤 경우에 사용할 수 있나요?
- 읽기에는 트랜잭션을 걸지 않아도 될까요?

</details>

**내 답변**

```
트랜잭션은 여러 데이터베이스 작업을 하나의 논리적 작업 단위로 묶은 것입니다. 모두 성공하면 COMMIT하고, 도중에 실패하면 ROLLBACK해 중간 상태가 남지 않도록 합니다.

ACID는 네 가지 성질입니다. Atomicity(원자성)는 작업이 전부 반영되거나 전혀 반영되지 않는 것, Consistency(일관성)는 트랜잭션 전후에 정의된 제약 조건을 지키는 것, Isolation(격리성)은 동시 실행되는 트랜잭션이 서로 간섭하는 정도를 제어하는 것, Durability(지속성)는 커밋된 결과가 장애 후에도 유지되는 것입니다.

예를 들어 계좌 이체에서는 출금과 입금을 하나의 트랜잭션으로 묶어 둘 중 하나만 반영되지 않게 합니다.
```

**꼬리 답변**

```
1. 대표적으로 변경 내용을 먼저 로그에 기록하는 WAL(Write-Ahead Logging) 방식이 있습니다. MySQL InnoDB는 Redo Log를 이용해 커밋된 변경을 장애 후 복구할 수 있습니다. 다만 실제 지속성 보장은 로그를 디스크에 동기화하는 설정과 스토리지의 정상 동작에도 영향을 받습니다.

2. 실제 경험이 없다면 사용했다고 말하지 않겠습니다. 사용할 수 있는 예로 주문 생성과 재고 차감을 들 수 있습니다. 두 작업을 하나의 트랜잭션으로 묶으면 재고만 줄고 주문은 생성되지 않는 상태를 막을 수 있습니다.

3. 읽기에도 트랜잭션이 필요할 수 있습니다. 여러 SELECT가 서로 같은 시점의 데이터를 봐야 하거나 읽은 값을 바탕으로 쓰기를 할 때 격리 수준과 잠금이 중요합니다. 반면 독립적인 단일 조회는 자동 커밋 환경에서 별도 트랜잭션을 명시하지 않아도 처리할 수 있습니다. 필요한 일관성 범위에 따라 결정합니다.
```

#### 4. 트랜잭션 격리 레벨에 대해 설명해 주세요.

`★★★` · `필수` · 원본 [데이터베이스 #4](../04-DATABASE.md)

<details>
<summary><b>꼬리 질문 3개 (펼치기)</b></summary>

- 모든 DBMS가 4개의 레벨을 모두 구현하고 있나요? 그렇지 않다면 그 이유는 무엇일까요?
- 만약 MySQL을 사용하고 있다면, (InnoDB 기준) Undo 영역과 Redo 영역에 대해 설명해 주세요.
- 그런데, 스토리지 엔진이 정확히 무엇을 하는 건가요?

</details>

**내 답변**

```
트랜잭션 격리 수준은 동시에 실행되는 트랜잭션이 서로의 변경을 어느 정도 볼 수 있는지 정하는 기준입니다.

Read Uncommitted는 커밋되지 않은 값까지 읽을 수 있어 Dirty Read가 발생할 수 있습니다. Read Committed는 커밋된 값만 읽지만 같은 행을 다시 읽으면 값이 달라지는 Non-Repeatable Read가 생길 수 있습니다. Repeatable Read는 같은 행을 반복 조회할 때 일관된 값을 보장하는 수준입니다. Serializable은 트랜잭션을 직렬 실행한 것과 같은 결과를 보장하는 가장 강한 수준입니다.

격리가 강해질수록 동시 처리 비용이 커질 수 있습니다. Phantom Read 같은 현상의 허용 여부와 구현 방식은 DBMS에 따라 차이가 있으므로 사용 중인 DBMS 기준으로 확인해야 합니다.
```

**꼬리 답변**

```
1. 모든 DBMS가 네 수준을 동일하게 구현하지는 않습니다. 표준에서 정의한 현상을 MVCC, 잠금, 스냅샷 등 서로 다른 방식으로 제어하고, 제품에 따라 특정 수준을 제공하지 않거나 이름이 같아도 실제 보장이 다를 수 있기 때문입니다. 예를 들어 PostgreSQL의 Read Uncommitted는 실제로 Read Committed처럼 동작합니다.

2. InnoDB의 Undo 영역에는 변경 전 버전이 기록되어 롤백과 MVCC의 과거 버전 읽기에 쓰입니다. Redo 영역에는 변경 내용을 다시 적용할 수 있는 로그가 기록되어 장애 후 커밋된 데이터를 복구하는 데 쓰입니다. 간단히 Undo는 되돌리기와 이전 버전 조회, Redo는 다시 적용하기에 관련됩니다.

3. 스토리지 엔진은 DBMS에서 데이터를 실제로 저장하고 읽고 수정하는 방식을 담당하는 구성 요소입니다. 인덱스, 잠금, 트랜잭션, 복구 방식도 엔진에 따라 달라질 수 있습니다. MySQL의 InnoDB는 트랜잭션과 외래키 등을 지원하는 대표적인 스토리지 엔진입니다.
```

- BCNF까지 정규화하면 모든 이상현상이 사라지나요? 제4, 제5정규형은 어떤 문제를 다루나요?

**내 답변**

```
정규화는 데이터의 중복을 줄이고 삽입·수정·삭제 이상을 방지하기 위해 테이블을 구조적으로 나누는 과정입니다. 어떤 속성이 다른 속성을 결정하는지, 즉 함수 종속성을 기준으로 분해합니다.

제1정규형은 각 칸의 값이 원자적이어야 합니다. 제2정규형은 복합 후보키의 일부에만 종속되는 일반 속성을 분리하고, 제3정규형은 일반 속성 사이의 이행 종속을 분리합니다. BCNF는 모든 비자명한 함수 종속의 결정자가 슈퍼키가 되도록 더 엄격하게 정규화합니다.

정규화로 중복과 이상 현상을 줄일 수 있지만 테이블이 나뉘면 JOIN이 늘 수 있습니다. 그래서 요구되는 무결성과 조회 성능을 함께 고려합니다.
```

**꼬리 답변**

```
1. 삽입 이상은 다른 정보가 없으면 새 데이터를 넣지 못하는 현상입니다. 수정 이상은 같은 정보가 여러 행에 있어 일부만 고치면 값이 서로 달라지는 현상입니다. 삭제 이상은 한 행을 지우면서 유지해야 할 다른 정보까지 사라지는 현상입니다. 예를 들어 학생·수강과목·교수 정보를 한 테이블에 반복 저장하면 교수 정보 변경 시 여러 행을 수정해야 합니다.

2. 1NF 전에는 한 칸에 'DB, 운영체제'처럼 여러 값이 있을 수 있고, 1NF에서는 과목마다 한 행으로 분리합니다. 2NF 전에는 복합키 (학생ID, 과목ID)인 수강 테이블에 학생이름처럼 학생ID에만 종속된 값이 중복될 수 있으므로 학생 테이블로 분리합니다. 3NF 전에는 학생 테이블에 학과ID와 학과이름이 함께 있어 학생ID → 학과ID → 학과이름이 되므로 학과 테이블을 분리합니다. BCNF에서는 후보키가 아닌 결정자에 종속된 값을 별도 테이블로 분리합니다.

3. BCNF는 모든 비자명한 함수 종속 X → Y에서 X가 슈퍼키여야 한다는 조건입니다. 예를 들어 수강(학생, 과목, 교수)에서 한 학생의 한 과목 담당 교수는 한 명이고, 각 교수는 한 과목만 가르친다고 가정하겠습니다. (학생, 과목)과 (학생, 교수)가 후보키이므로 모든 속성이 후보키에 포함되어 3NF는 만족할 수 있습니다. 하지만 교수 → 과목에서 교수는 슈퍼키가 아니므로 BCNF는 만족하지 않습니다. 교수·과목 관계를 분리할 수 있습니다.

4. 있습니다. 바로 앞 예시에서 (학생, 과목)과 (학생, 교수)가 후보키이고 '과목'은 후보키에 속한 주요 속성입니다. 따라서 교수 → 과목은 3NF 조건에는 허용되지만, 교수 혼자 모든 행을 식별하지 못하므로 BCNF에는 위배됩니다.

5. 아닙니다. BCNF는 함수 종속으로 생기는 중복을 다루지만 모든 종류의 중복을 없애지는 못합니다. 제4정규형은 서로 독립적인 다치 종속으로 생기는 중복을, 제5정규형은 더 복잡한 조인 종속으로 생기는 중복을 다룹니다. 실제 분해에서는 무손실 조인과 필요한 제약 조건을 유지할 수 있는지도 확인해야 합니다.

6. 무조건 정규화 수준을 높이는 것이 최선은 아닙니다. 조회가 매우 빈번하고 여러 테이블 JOIN 비용이 큰 경우, 측정 결과를 근거로 일부 데이터를 중복 저장하는 역정규화를 고려할 수 있습니다. 예를 들어 주문 목록에 조회용 상품명을 함께 저장할 수 있습니다. 대신 원본 변경 시 중복 값을 어떻게 갱신할지 정해야 합니다.
```

#### 9. static 키워드는 어떤 의미를 갖나요? (본인이 사용하는 언어에서 없다면 패스...)

`★☆☆` · `필수` · 원본 [개발상식·기타 #4](../05-ETC.md)

<details>
<summary><b>꼬리 질문 2개 (펼치기)</b></summary>

- 컴파일 할 때, static 키워드가 붙은 변수, 함수는 어떻게 처리되나요?
- Java에서 static과 static final은 어떤 차이를 갖나요? final과 static final은요?

</details>

**내 답변**

```
Java에서 static은 필드, 메서드, 중첩 클래스 등이 특정 객체가 아니라 클래스에 속한다는 뜻입니다.

static 필드는 해당 클래스를 사용하는 객체들이 공유하며, static 메서드는 인스턴스를 만들지 않고 클래스 이름으로 호출할 수 있습니다. 예를 들어 Math.max()가 static 메서드입니다.

static 메서드에는 this가 없어서 인스턴스 필드나 메서드에 직접 접근할 수 없습니다. 접근하려면 객체 참조가 필요합니다. 공통 상수나 객체 상태에 의존하지 않는 기능에 사용하지만, 변경 가능한 static 필드는 여러 곳에서 공유되므로 동시성에 주의해야 합니다.
```

**꼬리 답변**

```
1. 컴파일러는 static 필드와 메서드를 클래스 멤버로 기록하고, 호출 코드도 정적 호출에 맞는 바이트코드로 만듭니다. 실제 초기화는 컴파일 시점이 아니라 JVM이 클래스를 초기화할 때 일어납니다. static 메서드는 오버라이딩에 따른 동적 디스패치 대상이 아니고, 메서드 선택은 참조의 선언 타입을 기준으로 합니다. static final의 컴파일타임 상수는 사용하는 쪽 코드에 값이 인라인될 수 있습니다.

2. static은 클래스에 속한다는 뜻이고, final은 한 번 대입한 뒤 다시 대입할 수 없다는 뜻입니다. static final 필드는 클래스에 속하면서 재대입할 수 없습니다. 반면 인스턴스 final 필드는 객체마다 하나씩 있고 각 객체에서 한 번 대입할 수 있습니다. 참조형 final은 참조 재대입만 막으며 참조 대상의 내부 상태까지 자동으로 불변으로 만들지는 않습니다.
```
