```

Big-Omega: 상한과 하한이 모두 같은 경우, 즉 정확한 증가율

```

#### 2. 링크드 리스트에 대해 설명해 주세요.

`★☆☆` · `필수` · 원본 [자료구조·알고리즘 #2](../01-DATA_STRUCTURE_ALGORITHM.md)

<details>
<summary><b>꼬리 질문 5개 (펼치기)</b></summary>

- 일반 배열과, 링크드 리스트를 비교해 주세요.
- 동적 배열(ex. Java의 ArrayList)은 일반 배열, 링크드 리스트와 각각 어떤 차이를 갖나요?
- 리스트에서 인덱스가 아닌 "값"으로 데이터를 찾는다면, 시간복잡도는 어떻게 되나요?
- 그 리스트가 정렬되어 있다는 조건이 붙는다면, 시간복잡도는 어떻게 달라질까요? 링크드 리스트여도 마찬가지일까요?
- 링크드 리스트를 사용해서 구현할 수 있는 다른 자료구조에 대해 설명해 주세요.

</details>

**내 답변**
```
링크드 리스트(Linked List)는 각 노드가 데이터와 다음 노드의 참조를 가지고 연결되는 선형 자료구조입니다.
배열과 달리 메모리에 연속적으로 저장될 필요가 없고, 노드들이 참조를 통해 연결됩니다.
```

**꼬리 답변**
```
일반 배열은 메모리상 연속된 공간에 데이터를 저장하고, 링크드 리스트는 각각의 노드가 데이터와 다음 노드의 주소를 가지고 연결되는 구조입니다.
가장 큰 차이는 접근 속도와 삽입·삭제 방식입니다. 배열은 주소를 O(1)으로 바로 접근할 수 있습니다. 하지만 중간 삽입/삭제는 O(n)이 필요합니다.
링크드 리스트는 삽입하거나 삭제할 노드의 위치를 이미 알고 있다면 연결 변경 자체는 O(1)이지만, 위치를 찾아야 한다면 탐색에 O(n)이 필요합니다.

ArrayList는 이름에 List가 들어가지만 내부적으로는 배열을 사용하는 동적 배열입니다.
일반 배열과 차이점은 일반 배열은 생성할 때 크기를 정합니다. 처음에 정한 크기를 변경할 수 없습니다. 
반면 ArrayList는 add(n)을 통해 내부 배열을 더 큰 배열로 교체합니다.

배열, ArrayList, LinkedList 모두 기본적으로 O(n)입니다.
예를 들어 배열에서 num이라는 값이 어디 있는지 찾는다고 했을 때, 인덱스를 모르면 하나씩 확인해야 합니다. 따라서 최악의 경우 마지막까지 확인해야 하므로 O(n)입니다.
ArrayList도 마찬가지입니다. list.contains(num);, list.indexOf(num); 기본적으로 앞에서부터 비교하기 때문에 O(n)입니다.
LinkedList 역시 head -> node -> node -> node...를 순차적으로 확인해야 하므로 O(n)입니다.
중요한 점은, ArrayList에서 list.get(index) -> O(1)과 list.indexOf(value) -> O(n)은 완전히 다릅니다.

여기서 배열/ArrayList와 LinkedList의 차이가 크게 발생합니다.
데이터가 정렬되어 있을 때, 배열 또는 ArrayList라면 이진 탐색 (Binary Search)을 사용하면 O(log n)까지 줄일 수 있습니다.
그런데 LinkedList는 정렬되어 있어도 일반적인 이진 탐색의 이점을 얻기 어렵습니다. 왜냐하면 이진탐색에서는 계속 중간 값으로 이동해야 하는데 ArrayList에서는 list.get(mid); 를 O(1)에 할 수 있지만, LinkedList는 중간 노드까지 직접 이동해야 하는데, 중간 노드 하나를 찾는 데 이미 O(n)이 걸릴 수도  있습니다.
따라서 정렬된 LinkedList에서 값을 찾는 것도 일반적으로 O(n)입니다.
정렬된 배열이나 ArrayList는 랜덤 접근이 O(1)이므로 이진 탐색을 사용해 O(log n)에 검색할 수 있습니다. 하지만 LinkedList는 중간 노드에 접근하는 데 O(n)이 필요하기 때문에 정렬되어 있어도 일반적인 탐색 시간은 O(n)입니다.

대표적으로 Stack, Queue, Deque를 구현할 수 있습니다.
Stack은 LIFO(Last In First Out)입니다.
LinkedList의 head를 top으로 사용하여 같은 쪽에서 삽입과 삭제를 하면 LIFO 구조인 Stack을 구현할 수 있고, push와 pop 모두 O(1)입니다.
head와 tail을 관리하면서 tail에 데이터를 추가하고 head에서 데이터를 제거하면 FIFO 구조인 Queue를 구현할 수 있으며, 두 연산 모두 O(1)입니다.
이중 연결 리스트에서 head와 tail을 관리하면 이전 노드와 다음 노드를 모두 알 수 있기 때문에 양쪽 끝에서 삽입과 삭제를 모두 O(1)에 수행하는 Deque를 구현할 수 있습니다.
```

**핵심 키워드** → 이진 탐색이 빠른 이유는 단순히 "정렬되어 있어서"가 아니라, 중간 위치에 빠르게 접근할 수 있기 때문입니다.

#### 3. 스택과 큐에 대해서 설명해 주세요.

`★★☆` · `필수` · 원본 [자료구조·알고리즘 #3](../01-DATA_STRUCTURE_ALGORITHM.md)

<details>
<summary><b>꼬리 질문 5개 (펼치기)</b></summary>

- 스택 2개로 큐를, 큐 2개로 스택을 만드는 방법과, 그 시간복잡도에 대해 설명해 주세요.
- 시간복잡도를 유지하면서, 배열로 스택과 큐를 구현할 수 있을까요?
- Prefix, Infix, Postfix 에 대해 설명하고, 이를 스택을 활용해서 계산/하는 방법에 대해 설명해 주세요.
- Deque는 어떻게 구현할 수 있을까요?
- (C++ 한정) Deque의 Random Access 시간복잡도는 O(1) 입니다. 이게 어떻게 가능한걸까요?

</details>

**내 답변**

```
스택은 LIFO(후입선출) 구조로, 나중에 들어온 데이터가 먼저 나옵니다. 대표 연산은 push, pop, peek이고, 함수 호출 스택이나 괄호 검사 등에 사용됩니다.
큐는 FIFO(선입선출) 구조로, 먼저 들어온 데이터가 먼저 나옵니다. 대표 연산은 offer, poll, peek이고, BFS나 작업 대기열 등에 사용됩니다.
```

**꼬리 답변**

```
스택 두 개로 큐를 만들 때는 입력용 스택과 출력용 스택을 사용합니다. 삽입은 입력 스택에 하고, 삭제 시 출력 스택이 비어 있으면 입력 스택의 값을 모두 옮겨 순서를 뒤집습니다. 단일 삭제 연산은 최악 O(n)이지만 각 원소가 두 스택 사이를 한 번만 이동하기 때문에 분할상환 시간복잡도는 O(1)입니다.
큐 두 개로 스택을 구현할 때는 push 또는 pop 중 하나를 O(n)으로 만들어야 합니다. push 시 기존 원소를 모두 재배치하면 push O(n), pop O(1)이고, 반대로 pop할 때 마지막 원소를 제외한 값을 다른 큐로 옮기면 push O(1), pop O(n)입니다.

가능합니다. 스택은 top 인덱스를 관리하면 push와 pop을 O(1)에 구현할 수 있습니다. 큐는 일반 배열에서 삭제할 때 원소를 이동시키면 O(n)이 되므로, front와 rear를 관리하는 원형 큐로 구현합니다. 이렇게 하면 데이터를 이동하지 않고 인덱스만 변경하므로 삽입과 삭제 모두 O(1)에 수행할 수 있습니다.

Infix는 연산자가 피연산자 사이에 있는 일반적인 표기법이고, Prefix는 연산자가 앞에, Postfix는 뒤에 위치하는 표기법입니다. Postfix는 스택을 이용해 계산할 수 있는데, 피연산자를 스택에 넣고 연산자를 만나면 두 값을 꺼내 계산한 뒤 결과를 다시 스택에 넣습니다. 이를 통해 괄호나 별도의 우선순위 처리 없이 계산할 수 있습니다.

Deque는 양쪽 끝에서 삽입과 삭제가 가능한 자료구조입니다. 이중 연결 리스트를 사용하면 head와 tail에서 연결만 변경하여 네 가지 연산을 모두 O(1)에 수행할 수 있고, 원형 배열을 사용하면 front와 rear 인덱스를 이동시키는 방식으로 역시 O(1)에 구현할 수 있습니다.

C++의 deque는 일반적으로 여러 개의 고정 크기 메모리 블록과 그 블록의 주소를 관리하는 배열 형태로 구현됩니다. 인덱스를 블록 크기로 나누어 블록 번호와 블록 내부 위치를 바로 계산할 수 있기 때문에 메모리가 하나로 연속되어 있지 않아도 Random Access를 O(1)에 수행할 수 있습니다. 다만 간접 참조가 추가되므로 실제 상수 비용은 vector보다 클 수 있습니다.
```


**꼬리 답변**

```
좋은 해시 함수는 같은 입력에 대해 항상 같은 결과를 반환하면서, 서로 다른 키들을 전체 버킷에 최대한 균등하게 분산시켜 충돌을 줄여야 합니다. 또한 키의 일부가 아니라 전체 정보를 충분히 반영하고, 해시 계산 자체도 빠르게 수행할 수 있어야 합니다.

해시 충돌 해결 방법에는 크게 Separate Chaining과 Open Addressing이 있습니다. Chaining은 같은 버킷에 여러 값을 연결해서 저장하고, Open Addressing은 충돌이 발생하면 테이블 내부의 다른 빈 공간을 찾아 저장합니다. Open Addressing에는 Linear Probing, Quadratic Probing, Double Hashing 등이 있습니다.

Java의 HashMap은 기본적으로 Separate Chaining 방식으로 충돌을 처리합니다. 같은 버킷에 여러 엔트리가 들어오면 연결해서 관리하고, 현대 Java에서는 한 버킷에 충돌이 많이 발생하면 성능 저하를 줄이기 위해 트리 구조로 변환할 수 있습니다.

Double Hashing은 충돌 시 두 번째 해시 함수로 다음 탐색 위치의 간격을 결정하는 Open Addressing 방식입니다. Linear Probing보다 데이터가 한곳에 몰리는 Clustering을 줄일 수 있다는 장점이 있습니다. 하지만 두 번째 해시 함수가 잘못 설계되면 테이블 전체를 탐색하지 못할 수 있으므로, 이동 간격과 테이블 크기가 서로소가 되도록 설계하는 것이 중요합니다.

Load Factor는 해시 테이블이 어느 정도 찼을 때 크기를 확장할지를 결정하는 기준입니다. 값이 너무 높으면 메모리를 절약할 수 있지만 충돌이 증가하고, 너무 낮으면 충돌은 줄지만 메모리를 낭비할 수 있습니다. Java HashMap의 기본 Load Factor는 0.75이며, 엔트리 수가 capacity와 Load Factor의 곱을 넘으면 테이블을 확장합니다.

일반 HashMap은 멀티스레드에서 동시에 수정하면 Race Condition이 발생할 수 있습니다. 단순히 전체 Map에 synchronized를 걸 수도 있지만 동시성이 크게 떨어지므로 Java에서는 보통 ConcurrentHashMap을 사용합니다. 또한 get 후 수정하고 다시 put하는 복합 연산은 여전히 경쟁 상태가 생길 수 있으므로 compute, merge, putIfAbsent 같은 원자적 연산을 사용하는 것이 좋습니다. 직접 설계한다면 전체 테이블을 잠그기보다는 버킷이나 일부 영역 단위로 락을 분리하여 동시성을 높일 수 있습니다.
```

**핵심 키워드** → HashMap의 검색이 무조건 O(1)은 아닙니다. 평균적으로 O(1)입니다.

**내 답변**

```
트리는 노드들이 부모-자식 관계로 연결된 계층형 자료구조이고, 이진트리는 각 노드가 최대 두 개의 자식을 가지는 트리입니다. 이진탐색트리는 이진트리에 왼쪽에는 작은 값, 오른쪽에는 큰 값을 저장하는 규칙을 추가한 구조입니다. 균형이 잘 잡힌 BST는 검색·삽입·삭제를 평균 O(log n)에 수행할 수 있지만, 한쪽으로 편향되면 최악의 경우 O(n)까지 느려질 수 있습니다.
```
**꼬리 답변**

```
그래프는 노드와 간선으로 관계를 표현하는 일반적인 자료구조이고, 사이클이나 여러 경로가 존재할 수 있습니다. 트리는 그래프의 특수한 형태로, 사이클이 없고 모든 노드가 연결되어 있으며 두 노드 사이의 경로가 하나만 존재합니다. 또한 노드가 N개라면 간선은 N-1개입니다.

BST에서 중위 순회는 왼쪽 서브트리, 현재 노드, 오른쪽 서브트리 순으로 방문합니다. BST는 왼쪽 값이 작고 오른쪽 값이 크다는 규칙을 가지므로 중위 순회의 결과는 오름차순으로 정렬된 데이터가 됩니다.

BST의 검색, 삽입, 삭제는 모두 트리의 높이만큼 노드를 따라 이동하므로 O(h)입니다. 트리가 균형 잡혀 있으면 높이가 O(log n)이기 때문에 주요 연산도 O(log n)이지만, 한쪽으로 편향되면 높이가 O(n)이 되어 주요 연산 역시 O(n)까지 떨어질 수 있습니다.

일반 BST의 가장 큰 한계는 트리의 균형을 스스로 보장하지 않는다는 점입니다. 정렬된 값처럼 특정 순서로 데이터가 삽입되면 한쪽으로 편향될 수 있고, 이 경우 트리 높이가 n까지 증가해 검색·삽입·삭제가 O(n)으로 떨어집니다. 이를 해결하기 위해 AVL Tree나 Red-Black Tree 같은 균형 이진 탐색 트리를 사용할 수 있습니다.

BST 삽입은 현재 노드보다 값이 작으면 왼쪽, 크면 오른쪽으로 이동하여 빈 위치에 삽입합니다. 삭제는 자식이 없는 경우 바로 제거하고, 자식이 하나면 자식과 부모를 연결하며, 자식이 둘이면 보통 오른쪽 서브트리의 최솟값이나 왼쪽 서브트리의 최댓값으로 대체합니다. 정렬된 값을 순서대로 삽입하면 한쪽으로만 노드가 추가되어 편향 트리가 발생할 수 있습니다.

일반 BST와 완전히 동일한 로직으로는 삼진 탐색 트리를 정의하기 어렵습니다. BST는 하나의 기준값으로 작은 값과 큰 값이라는 두 영역을 나누기 때문에 두 자식이 자연스럽습니다. 자식을 세 개로 나누려면 값을 세 영역으로 구분해야 하므로 최소 두 개의 기준값이 필요합니다. 따라서 노드에 여러 키를 저장하는 2-3 Tree나 B-Tree 같은 방식으로는 구현할 수 있지만, BST의 단일 키 비교 로직을 그대로 사용할 수는 없습니다.
```

**핵심 키워드** →  BST의 시간복잡도를 처음부터 O(log n)이라고 단정하지 않고 O(h), 균형일 때 O(log n), 최악 O(n)이라고 답하기

```
BBST는 일반 이진 탐색 트리가 한쪽으로 편향되어 O(n)까지 성능이 떨어지는 문제를 해결하기 위해 트리의 균형을 유지하는 자료구조입니다. 대표적으로 AVL Tree와 Red-Black Tree가 있으며, AVL은 균형을 더 엄격하게 유지해 검색에 유리하고, Red-Black Tree는 균형 조건이 상대적으로 느슨해 삽입·삭제 비용을 줄이는 데 유리합니다. 균형을 유지하면 검색·삽입·삭제를 O(log n) 수준으로 유지할 수 있습니다.
```

**꼬리 답변**

```

Red-Black Tree의 핵심 성질은 모든 노드가 Red 또는 Black이고, 루트는 Black이며, Red 노드의 자식은 반드시 Black이고, 임의의 노드에서 NIL 리프까지 가는 모든 경로의 Black 노드 개수가 동일해야 한다는 것입니다. 또한 NIL 리프는 Black으로 취급합니다. 이 규칙 때문에 특정 경로만 지나치게 길어질 수 없어 높이가 O(log n)으로 유지됩니다.

AVL Tree는 균형을 더 엄격하게 유지하기 때문에 검색 성능은 좋지만 삽입·삭제 시 회전과 재조정이 더 자주 발생할 수 있습니다. Red-Black Tree는 균형 조건을 조금 느슨하게 유지해 검색 성능은 O(log n)으로 보장하면서 삽입·삭제의 재조정 비용을 줄일 수 있습니다. 따라서 검색뿐 아니라 삽입과 삭제가 함께 발생하는 일반적인 환경에서 전체적인 성능 균형이 좋아 많이 사용됩니다.
```

- 정렬해야 하는 데이터는 50G 인데, 메모리가 4G라면, 어떤 방식으로 정렬을 진행할 수 있을까요?

</details>

**내 답변**

```
정렬 알고리즘은 데이터를 일정한 기준으로 재배치하는 알고리즘입니다. 대표적으로 Bubble, Selection, Insertion, Merge, Quick, Heap Sort가 있습니다. 단순 정렬은 주로 O(n²), Merge·Quick·Heap Sort는 평균적으로 O(n log n) 수준입니다. Merge Sort는 안정적이고 최악에도 O(n log n)이지만 추가 메모리가 필요하고, Quick Sort는 평균적으로 빠르지만 최악의 경우 O(n²)이 될 수 있습니다. 따라서 시간복잡도, 메모리, Stable 여부 등을 고려해 상황에 맞는 정렬을 선택해야 합니다.
```
**꼬리 답변**

```
Quick Sort는 피벗을 기준으로 데이터를 분할하는 방식으로 평균 O(n log n)이지만 피벗 선택이 나쁘면 최악 O(n²)이 될 수 있습니다. Merge Sort는 데이터를 절반씩 나눈 뒤 병합하며 항상 O(n log n)의 성능을 보장하지만 배열에서는 추가 메모리가 필요합니다. 또한 일반적인 Merge Sort는 Stable하지만 Quick Sort는 Stable하지 않습니다.

Quick Sort에서 항상 첫 번째나 마지막 값을 피벗으로 잡는 상황에서 이미 정렬된 데이터가 들어오면 한쪽에는 0개, 다른 쪽에는 n-1개의 원소가 계속 생겨 O(n²)이 될 수 있습니다. 이를 개선하기 위해 Random Pivot이나 Median-of-Three 등을 사용해 분할이 한쪽으로 치우치지 않도록 할 수 있습니다.

Stable Sort는 정렬 기준값이 같은 데이터들의 기존 상대적인 순서를 보존하는 정렬입니다. 대표적으로 Bubble, Insertion, Merge Sort가 Stable하며, 일반적인 Selection, Quick, Heap Sort는 Stable하지 않습니다. 여러 기준으로 연속해서 정렬할 때 Stable 여부가 중요합니다.

가능합니다. Bottom-Up Merge Sort를 사용하면 크기 1짜리 구간부터 시작해 2, 4, 8배씩 구간 크기를 증가시키며 인접한 정렬 구간을 반복적으로 병합할 수 있습니다. 따라서 재귀 없이 반복문만으로도 O(n log n)의 Merge Sort를 구현할 수 있습니다.

Radix Sort는 데이터를 직접 비교하지 않고 각 자릿수를 기준으로 여러 번 정렬하는 방식입니다. LSD 방식에서는 낮은 자릿수부터 높은 자릿수 순으로 정렬하며 각 단계의 상대 순서를 보존해야 하므로 Stable한 정렬을 사용해야 합니다. 시간복잡도는 보통 O(d(n+k))로 표현하며, 정수처럼 자릿수 구조가 명확한 데이터에 효과적입니다.

Bubble Sort는 인접한 값을 반복 교환하고, Selection Sort는 남은 영역의 최솟값을 찾아 교환하며, Insertion Sort는 현재 값을 이미 정렬된 앞부분에 삽입합니다. 일반적으로 모두 O(n²)이지만 Selection Sort는 swap 횟수가 적고, Insertion Sort는 데이터가 거의 정렬되어 있을 때 특히 유리합니다.

달라집니다. 이미 정렬되거나 거의 정렬된 데이터에서는 Insertion Sort가 이동할 원소가 거의 없어서 O(n)에 가까워지고, 조기 종료를 적용한 Bubble Sort도 O(n)까지 개선될 수 있습니다. 반면 Selection Sort는 입력 상태와 관계없이 남은 모든 원소에서 최솟값을 찾아야 하므로 O(n²)이 유지됩니다.

Java에서는 정렬 대상에 따라 알고리즘이 다릅니다. Arrays.sort()에서 int 같은 기본형 배열은 Dual-Pivot Quicksort 계열을 사용하고, 객체 배열은 Stable한 Adaptive Merge Sort 계열로 TimSort의 기법을 사용합니다. 따라서 Java가 항상 하나의 정렬 알고리즘만 사용하는 것은 아닙니다.

50GB 데이터가 4GB 메모리에 들어가지 않기 때문에 External Merge Sort를 사용할 수 있습니다. 데이터를 메모리에 들어갈 크기의 여러 블록으로 나누고, 각 블록을 메모리에서 정렬해 디스크에 저장합니다. 이후 정렬된 파일들을 k-way merge 방식으로 순차적으로 병합하여 최종 정렬 결과를 만듭니다. 이렇게 하면 전체 데이터를 한 번에 메모리에 올리지 않고도 대용량 데이터를 정렬할 수 있습니다.
```

```
객체지향 프로그래밍은 프로그램을 상태와 행동을 가진 객체들의 협력으로 구성하는 프로그래밍 방식입니다. 대표적인 특징으로 추상화, 캡슐화, 상속, 다형성이 있으며, 이를 통해 코드의 재사용성과 유지보수성, 확장성을 높일 수 있습니다. 특히 다형성을 활용하면 구체적인 구현에 대한 의존성을 줄이고 유연한 설계가 가능합니다.
```

**꼬리 답변**

```
SOLID는 유지보수성과 확장성이 좋은 객체지향 설계를 위한 다섯 가지 원칙입니다. SRP는 하나의 책임, OCP는 확장에는 열리고 수정에는 닫힌 설계, LSP는 자식이 부모를 안전하게 대체할 수 있어야 한다는 원칙, ISP는 인터페이스를 필요한 기능 단위로 분리하는 원칙, DIP는 구체적인 구현보다 추상화에 의존하라는 원칙입니다.

다형성은 같은 인터페이스나 타입을 사용하면서 실제 객체에 따라 서로 다른 동작을 수행할 수 있는 성질입니다. 정적 다형성은 컴파일 시 호출할 메서드가 결정되는 오버로딩이 대표적이고, 동적 다형성은 실행 시 실제 객체에 따라 메서드가 결정되는 오버라이딩이 대표적입니다.

오버로딩은 같은 이름의 메서드를 매개변수의 개수나 타입을 다르게 여러 개 정의하는 것으로 컴파일 시점에 결정됩니다. 오버라이딩은 부모의 메서드를 자식이 같은 시그니처로 재정의하는 것으로 실행 시 실제 객체에 따라 호출될 메서드가 결정됩니다.

상속은 부모 클래스의 속성과 기능을 자식 클래스가 물려받아 재사용하거나 확장하는 기능입니다. 코드 재사용과 다형성을 얻을 수 있다는 장점이 있지만, 부모와 자식 사이의 결합도가 높아지고 부모의 변경이 자식에게 전파될 수 있다는 단점이 있습니다. 따라서 단순한 코드 재사용 목적보다는 명확한 IS-A 관계에서 사용하는 것이 좋습니다.

상속은 부모의 구현에 자식이 강하게 결합되어 부모 변경의 영향을 받기 쉽습니다. 반면 합성은 필요한 객체를 필드로 가지고 기능을 위임하기 때문에 구현을 쉽게 교체할 수 있고 결합도를 낮출 수 있습니다. 따라서 명확한 IS-A 관계가 아니라 단순한 기능 재사용 목적이라면 상속보다 합성을 사용하는 것이 변경과 확장에 유리합니다.

캡슐화는 관련된 상태와 행동을 하나의 객체로 묶는 것이고, 정보은닉은 객체 내부의 구현과 상태를 외부에서 직접 접근하지 못하도록 숨기는 것입니다. 접근제어자는 정보은닉을 위한 수단일 뿐이며, 단순히 private을 붙이고 모든 값을 getter/setter로 노출하면 좋은 캡슐화라고 보기 어렵습니다. 객체가 자신의 상태와 규칙을 스스로 관리하도록 설계하는 것이 중요합니다.

Java에서는 부모 클래스나 인터페이스 타입으로 여러 구현 객체를 다루는 방식으로 다형성을 활용합니다. 예를 들어 Payment 인터페이스를 CardPayment와 KakaoPayment가 구현하면 서비스는 Payment 타입에만 의존하고 실제 객체에 따라 서로 다른 pay()가 실행됩니다. 이를 통해 구현체를 쉽게 교체하거나 추가할 수 있어 결합도를 낮추고 확장성을 높일 수 있습니다.

클래스가 존재한다고 해서 반드시 객체지향 언어 또는 객체지향적인 프로그램이라고 할 수는 없습니다. 클래스는 객체지향을 구현하기 위한 하나의 수단이고, 객체의 책임·협력·캡슐화·다형성을 어떻게 설계하는지가 더 중요합니다. 반대로 클래스 문법이 없어도 프로토타입 기반 객체처럼 객체지향의 특성을 구현할 수 있기 때문에 클래스는 객체지향의 필요조건도 충분조건도 아닙니다.
```
