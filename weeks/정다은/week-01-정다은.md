### 알고리즘 성능 (Algorithm Performance)

- **정의**: 알고리즘이 주어진 문제를 해결하는 데 소요되는 **시간(연산량)**과 **메모리(공간)**의 척도. [medium] [stackoverflow](https://stackoverflow.com/questions/36316271/time-complexity-of-binary-search-in-java)
- **핵심 포인트**:
  - 성능은 **절대 시간(ms)**이 아니라 **입력 크기 n에 대한 상대적 증가율**로 평가. [youtube] [baeldung](https://www.baeldung.com/java-algorithm-complexity)
  - **시간복잡도**와 **공간복잡도** 두 축으로 분석.
  - **최악 경우(worst-case)**를 기준으로 평가하는 것이 일반적. [medium] [baeldung](https://www.baeldung.com/java-binary-search)
- **관련 용어**: 시간복잡도, 공간복잡도, Big-O, auxiliary space, worst-case, scalability.

### 시간복잡도 (Time Complexity)

- **정의**: 입력 크기 n이 증가할 때 알고리즘이 수행하는 **기본 연산의 수**가 어떻게 증가하는지 나타낸 함수. [medium] [stackoverflow](https://stackoverflow.com/questions/36316271/time-complexity-of-binary-search-in-java)
- **핵심 포인트**:
  - 실제 실행 시간이 아닌 **연산 횟수의 증가 추세**를 표현. [youtube] [baeldung](https://www.baeldung.com/java-algorithm-complexity)
  - **최악의 경우**를 기준으로 Big-O 표기.
  - 상수 계수와 낮은 차수 항은 무시하고 **최고차항만** 고려. [en.wikipedia] [stackoverflow](https://stackoverflow.com/questions/29463531/simple-merge-sort-in-java)
- **관련 용어**: Big-O, worst-case, 연산 횟수, 최고차항.

### 공간복잡도 (Space Complexity)

- **정의**: 입력 크기 n이 증가할 때 알고리즘이 **추가로 사용하는 메모리량**을 나타낸 함수. [medium] [stackoverflow](https://stackoverflow.com/questions/36316271/time-complexity-of-binary-search-in-java)
- **핵심 포인트**:
  - **입력 데이터 자체는 제외**, 알고리즘이 새로 할당하는 **auxiliary space**만 계산. [abstractalgorithms] [study](https://study.com/academy/lesson/big-o-notation-complexity-analysis-and-examples.html)
  - 변수, 배열, 재귀 호출 스택 등이 포함.
  - 시간복잡도와 동일하게 **Big-O**로 표현. [dev] [medium](https://medium.com/@YodgorbekKomilo/big-o-notation-a-comprehensive-guide-to-runtime-and-space-complexity-in-java-dc36d793e847)
- **관련 용어**: auxiliary space, 재귀 스택, 메모리 할당, in-place.

### Big-O 표기법 (Big-O Notation)

- **정의**: 함수 f(n)이 입력 n이 커질 때 **어떤 함수 g(n)보다 빠르게 증가하지 않음**을 표현하는 수학적 표기. [en.wikipedia] [stackoverflow](https://stackoverflow.com/questions/29463531/simple-merge-sort-in-java)
- **핵심 포인트**:
  - 상한(upper bound)을 의미하며, 주로 **최악의 경우**를 나타냄. [simplilearn] [medium](https://medium.com/@niteshthakur498/binary-search-core-concept-time-complexity-java-implementation-variations-real-use-cases-c21fce4c85c1)
  - 상수 계수와 낮은 차수 항은 제거하고, **최고차항만 남김**. [en.wikipedia] [stackoverflow](https://stackoverflow.com/questions/29463531/simple-merge-sort-in-java)
  - n이 무엇인지 명확히 정의해야 함 (배열 길이? 문자열 길이? 노드 수?). [youtube] [baeldung](https://www.baeldung.com/java-algorithm-complexity)

## 1-5. 노드 (Node)

- **정의**: 링크드리스트를 구성하는 기본 단위입니다. 일반적으로 실제 데이터와 다른 노드를 가리키는 포인터 또는 참조를 포함합니다.
- **구성 요소**:
  - `data`: 저장할 실제 값
  - `next`: 다음 노드에 대한 포인터 또는 참조
  - `prev`: 이전 노드에 대한 포인터 또는 참조
- **단일 링크드리스트**:

```text
[ data | next ]
```

- **이중 링크드리스트**:

```text
[ prev | data | next ]
```

### 포인터와 참조

- **포인터**: 다른 데이터나 노드가 저장된 메모리 주소를 저장하는 변수입니다.
- **참조**: 다른 객체나 노드를 가리키는 개념이며, Java에서는 참조(reference) 타입으로 구현됩니다.
- **면접 핵심**: 링크드리스트의 삽입과 삭제는 데이터를 직접 이동하는 것이 아니라 노드 사이의 연결 관계를 변경하는 작업입니다.

***

## 1-6. 링크드리스트의 종류

### 단일 링크드리스트 (Singly Linked List)

- **정의**: 각 노드가 다음 노드만 가리키는 링크드리스트입니다.
- **구조**:

```text
head → A → B → C → null
```

- **핵심 포인트**:
  - 각 노드에 `next`만 존재합니다.
  - 순방향 탐색만 가능합니다.
  - 마지막 노드의 `next`는 일반적으로 `null`입니다.
  - 노드당 포인터가 하나이므로 상대적으로 메모리를 적게 사용합니다.
  - 특정 노드를 삭제하려면 이전 노드를 찾아야 할 수 있습니다.

### 이중 링크드리스트 (Doubly Linked List)

- **정의**: 각 노드가 이전 노드와 다음 노드를 모두 가리키는 링크드리스트입니다.
- **구조**:

```text
null ← A ⇄ B ⇄ C → null
```

- **핵심 포인트**:
  - `prev`와 `next`를 모두 가집니다.
  - 양방향 탐색이 가능합니다.
  - 주어진 노드를 알고 있다면 삭제가 편리합니다.
  - 단일 링크드리스트보다 포인터 저장 공간이 더 필요합니다.
  - 삽입·삭제 시 여러 연결을 정확하게 수정해야 합니다.

### 원형 링크드리스트 (Circular Linked List)

- **정의**: 마지막 노드가 처음 노드를 가리키도록 연결한 링크드리스트입니다.
- **구조**:

```text
head → A → B → C
        ↑       ↓
        └───────┘
```

- **핵심 포인트**:
  - 마지막 노드의 `next`가 `head`를 가리킵니다.
  - 단일 또는 이중 링크드리스트 형태로 만들 수 있습니다.
  - `null`을 만나는 대신 시작 노드로 돌아옵니다.
  - 라운드 로빈 스케줄링처럼 순환 처리가 필요한 상황에 유용합니다.
  - 종료 조건을 잘못 작성하면 무한 루프가 발생할 수 있습니다.

세 가지 유형의 차이는 [W3Schools 링크드리스트 자료](https://www.w3schools.com/dsa/dsa_data_linkedlists_types.php)에서도 확인할 수 있습니다.

### 유형 비교

| 구분 | 단일 링크드리스트 | 이중 링크드리스트 | 원형 링크드리스트 |
|---|---|---|---|
| 포인터 | `next` | `prev`, `next` | 마지막 노드가 시작 노드를 참조 |
| 탐색 방향 | 순방향 | 양방향 | 순환 방향 |
| 추가 메모리 | 적음 | 더 많음 | 구조에 따라 다름 |
| 삭제 편의성 | 이전 노드 필요 | 주어진 노드 삭제에 유리 | 종료 조건 주의 |
| 주요 활용 | 단순 연결 구조 | LRU Cache, 브라우저 기록 | 라운드 로빈 처리 |

## 1-7. 주요 연산

### 맨 앞 삽입

```java
newNode.next = head;
head = newNode;
```

- **시간복잡도**: O(1)
- 기존 노드를 이동할 필요가 없습니다.
- 빈 리스트라면 `tail`도 새 노드로 설정해야 할 수 있습니다.

### 중간 삽입

`prev` 노드 뒤에 새 노드를 삽입하는 경우입니다.

```java
newNode.next = prev.next;
prev.next = newNode;
```

- 삽입할 위치를 이미 알고 있으면 O(1)
- 위치를 탐색해야 하면 전체 복잡도는 O(n)
- 이중 링크드리스트에서는 `prev`와 `next`를 모두 갱신해야 합니다.

### 맨 뒤 삽입

- `tail` 포인터가 있으면 O(1)
- `tail` 포인터가 없으면 마지막 노드를 찾기 위해 O(n)
- 면접에서는 tail 포인터를 유지하는지 반드시 구분해야 합니다.

### 삭제

#### 단일 링크드리스트

```text
prev.next = target.next;
```

#### 이중 링크드리스트

```text
target.prev.next = target.next;
target.next.prev = target.prev;
```

- 삭제할 노드와 필요한 연결 정보를 알고 있으면 O(1)
- 삭제할 값을 먼저 찾아야 하면 탐색 때문에 O(n)
- 삭제 후 `head`, `tail`, `prev`, `next`가 올바르게 갱신되었는지 확인해야 합니다.

### 탐색

- `head`부터 `next`를 따라가며 데이터를 비교합니다.
- 평균 및 최악의 경우 O(n)입니다.
- 인덱스 기반의 빠른 임의 접근은 어렵습니다.

## 3. 왜 중요한가?

## 3-1. 실제 개발 및 시스템 관점

배열과 링크드리스트의 차이를 이해하면 특정 연산에 적합한 자료구조를 선택할 수 있습니다.

- **대량 조회**: 배열이 유리합니다.
- **인덱스 기반 접근**: 배열이 O(1)로 빠릅니다.
- **빈번한 삽입·삭제**: 위치를 알고 있다면 링크드리스트가 유리합니다.
- **순서 변경**: 이중 링크드리스트가 적합할 수 있습니다.
- **캐시 효율이 중요한 경우**: 연속 메모리를 사용하는 배열이 유리합니다.
- **크기가 자주 변하는 경우**: 링크드리스트는 노드를 개별적으로 추가할 수 있습니다.
- **메모리가 제한된 경우**: 링크드리스트의 포인터 저장 공간까지 고려해야 합니다.

자료구조는 단순히 "어떤 데이터가 저장되는가"보다 "어떤 연산이 얼마나 자주 수행되는가"를 기준으로 선택해야 합니다.

</details>

  - 노드들이 메모리상 연속적으로 배치될 필요가 없습니다.
  - 인덱스 접근이 어려워 특정 위치에 접근하려면 순차 탐색이 필요합니다.

- **관련 용어**: Node, Pointer, Reference, Head, Tail, Sequential Access, Pointer Chasing

### 원형 큐 (Circular Queue)

## 3. 왜 중요한가?

### 실제 개발 및 시스템 관점

스택과 큐는 단순한 자료구조처럼 보이지만 실행 흐름과 작업 순서를 통제하는 핵심 도구입니다.

- **대용량 데이터 처리**: 큐를 이용해 데이터를 한 번에 모두 처리하지 않고 순차적으로 처리할 수 있습니다.
- **성능 최적화**: 스택의 끝 연산이나 원형 큐의 인덱스 이동은 원소 전체를 이동하지 않아 빠릅니다.
- **메모리 사용량**: 스택·큐에 저장되는 원소 수가 증가하면 기본 저장 공간은 \(O(n)\)으로 증가합니다.
- **서버 비용**: 작업을 큐에 넣고 worker가 처리하면 서버 부하를 조절할 수 있지만, 큐가 계속 증가하면 메모리와 지연 시간이 늘어납니다.
- **응답 시간**: FIFO 큐는 요청 순서를 보장하지만, 오래 걸리는 작업 하나가 뒤의 작업을 지연시키는 Head-of-Line Blocking이 발생할 수 있습니다.
- **확장성**: 여러 worker가 큐의 작업을 나누어 처리하면 수평 확장이 가능합니다.
- **제한된 자원 환경**: 원형 큐는 고정된 메모리 안에서 버퍼를 운영할 수 있어 임베디드 시스템에 적합합니다.

함수 호출 스택은 함수가 호출될 때 추가되고 실행이 끝나면 제거되는 구조이며, 이 과정은 LIFO 방식으로 동작합니다. [Oracle Java Docs](https://docs.oracle.com/javase/8/docs/api/java/util/Stack.html)

### 입력 크기 n이 커질 때

여기서 \(n\)은 스택이나 큐에 저장되는 원소 수입니다. 그래프 탐색에서는 \(V\)를 정점 수, \(E\)를 간선 수로 별도로 사용합니다.

- `push`, `pop`, `enqueue`, `dequeue`가 \(O(1)\)이면 원소 수 \(n\)이 커져도 **한 번의 연산 시간은 이론적으로 일정**합니다.
- 그러나 자료구조가 보유하는 전체 메모리는 \(O(n)\)으로 증가합니다.
- 단순 배열 큐에서 `dequeue`마다 원소를 이동시키면 전체 처리 시간이 누적되어 \(O(n^2)\)이 될 수 있습니다.
- 큐의 길이가 증가하면 대기 시간, 메모리 사용량, 장애 시 유실될 수 있는 작업량이 증가합니다.
- BFS·DFS는 인접 리스트 기준 \(O(V+E)\)이며, 정점과 간선이 많아질수록 탐색 시간과 방문 배열·스택·큐 공간이 함께 증가합니다.

</details>

<summary><b>상세 설명</b></summary>

### 이중 해싱 (Double Hashing)

- **정의**: 두 번째 해시 함수를 이용해 충돌 시 이동 폭을 결정하는 방식이다.

```text
index_i = (hash1(key) + i × hash2(key)) % tableSize
```

- **장점**:
  - 선형 탐사와 제곱 탐사보다 군집화가 적다.
  - 키별 탐사 순서가 달라질 수 있다.
- **단점**:
  - 두 개의 해시 함수가 필요하다.
  - 두 번째 해시값이 0이 되지 않도록 해야 한다.
- **복잡도**:
  - 평균: `O(1)`
  - 최악: `O(n)`
  - 공간: `O(m)`

***

### 부하율 (Load Factor)

- **정의**: 해시 테이블이 얼마나 채워져 있는지를 나타내는 비율이다.

```text
load factor α = 저장된 원소 수 n / 버킷 수 m
```

- **핵심 포인트**:
  - `n`은 저장된 키-값 엔트리 수다.
  - `m`은 버킷 또는 배열 슬롯 수다.
  - 부하율이 높아지면 충돌 가능성이 증가한다.
  - 부하율이 낮으면 성능은 좋아질 수 있지만 메모리 낭비가 커진다.
  - Java `HashMap`의 기본 부하율은 일반적으로 `0.75`다. Oracle 문서도 기본값 `0.75`를 시간과 공간의 균형점으로 설명한다. [docs.oracle](https://docs.oracle.com/javase/8/docs/api/java/util/HashMap.html)
- **리해싱 (Rehashing)**:
  - 저장 개수가 `capacity × loadFactor`를 초과하면 테이블을 확장한다.
  - 더 큰 배열을 만들고 기존 엔트리를 새로운 위치에 다시 배치한다.
  - 확장 순간에는 `O(n)`의 비용이 발생할 수 있다.
- **복잡도**:
  - 일반 연산 평균: `O(1)`
  - 리해싱이 발생하는 한 번의 연산: `O(n)`
  - 여러 번의 확장을 전체적으로 보면 삽입 비용은 분할 상환하여 평균 `O(1)`로 볼 수 있다.
- **면접 한 줄 정리**: 부하율은 원소 수를 버킷 수로 나눈 값이며, 높아지면 충돌이 증가하므로 임계값을 넘을 때 리해싱합니다.

## 3. 왜 중요한가?

### 실제 개발 및 시스템 관점

해시 테이블은 사용자 ID 조회, 세션 확인, 캐시 접근, 중복 제거처럼 “키로 데이터를 찾는” 작업에서 매우 중요하다.

- **대용량 데이터 처리**: 선형 검색 대신 평균 `O(1)`에 가까운 조회가 가능하다.
- **응답 시간**: 요청마다 사용자·권한·세션을 빠르게 확인할 수 있다.
- **성능 최적화**: 자주 조회하는 데이터를 해시맵이나 캐시에 보관할 수 있다.
- **메모리 사용량**: 빠른 접근을 위해 버킷 배열과 엔트리 노드 메모리를 추가로 사용한다.
- **확장성**: 데이터가 증가하면 리해싱이 발생하므로 초기 용량을 적절하게 설정해야 한다.
- **장애와 병목**: 나쁜 해시 함수나 공격자가 만든 충돌 입력은 특정 버킷에 부하를 집중시킬 수 있다.
- **동시성**: 일반 `HashMap`은 멀티스레드 환경의 동기화를 보장하지 않으므로 동시 접근에는 별도 설계가 필요하다.

### 입력 크기 n이 커질 때

- `n`이 증가하면 저장할 엔트리와 필요한 메모리가 대체로 `O(n)`으로 증가한다.
- 부하율 임계값을 넘으면 리해싱으로 배열 크기가 증가한다.
- 평균 조회 시간은 여전히 `O(1)`에 가깝지만, 캐시 미스와 메모리 접근 비용은 증가할 수 있다.
- 버킷 분포가 나쁘면 특정 버킷의 `k`가 커져 조회 시간이 증가한다.
- 전체 순회는 단순히 원소 수뿐 아니라 테이블 capacity의 영향도 받는다. Java 문서도 `HashMap`의 컬렉션 뷰 순회 시간이 capacity와 size에 비례한다고 설명한다. [docs.oracle](https://docs.oracle.com/javase/8/docs/api/java/util/HashMap.html)

## 1. 개념 정리

### 루트 (Root)

- **정의**: 트리에서 부모가 없는 최상단 노드로, 트리 전체의 시작점입니다. [habitus92.tistory](https://habitus92.tistory.com/19)
- **핵심 포인트**:
  - 트리는 반드시 하나의 루트만 가집니다.
  - 루트에서 다른 모든 노드로의 경로가 유일하게 존재합니다.
  - 루트의 깊이(Depth) 는 0, 레벨(Level) 은 1로 정의하는 경우가 많습니다. [kyeong-hoon.tistory](https://kyeong-hoon.tistory.com/570)
- **관련 용어**: Root Node, 근 노드
- **간단한 예시**: 트리 `1 → 2, 3`에서 `1`이 루트입니다.
- **복잡도**: 해당 없음
- **면접 한 줄 정리**: "루트는 부모가 없는 트리의 최상단 노드로, 트리 접근의 시작점입니다."

***

### 부모·자식 (Parent / Child)

- **정의**: 어떤 노드의 바로 위 단계 노드를 부모(Parent), 바로 아래 단계 노드를 자식(Child) 이라 합니다. [habitus92.tistory](https://habitus92.tistory.com/19)
- **핵심 포인트**:
  - 부모는 하나 이상의 자식을 가질 수 있습니다.
  - 자식은 정확히 하나의 부모를 가집니다(트리 조건).
  - 부모-자식 관계는 간선(Edge) 으로 연결됩니다.
- **관련 용어**: Parent Node, Child Node, Branch
- **간단한 예시**: `A → B, C`에서 A 는 B, C 의 부모, B 와 C 는 A 의 자식입니다.
- **복잡도**: 해당 없음
- **면접 한 줄 정리**: "부모는 자식을 가진 노드, 자식은 부모로부터 내려온 노드입니다."

***

### 리프 (Leaf)

- **정의**: 자식이 없는 노드로, 단말 노드(Terminal Node) 라고도 합니다. [habitus92.tistory](https://habitus92.tistory.com/19)
- **핵심 포인트**:
  - 리프는 트리의 끝에 위치합니다.
  - 리프의 차수(Degree) 는 0 입니다.
  - 포화이진트리에서는 모든 리프가 같은 레벨에 있습니다. [hsc-tech.tistory](https://hsc-tech.tistory.com/7)
- **관련 용어**: Leaf Node, Terminal Node, 단말 노드
- **간단한 예시**: `A → B, C`에서 B 와 C 가 자식이 없다면 리프입니다.
- **복잡도**: 해당 없음
- **면접 한 줄 정리**: "리프는 자식이 없는 트리의 끝 노드입니다."

***

### 높이·깊이·레벨 (Height / Depth / Level)

- **정의**:
  - **깊이(Depth)**: 루트에서 특정 노드까지 가는 간선의 수입니다. [habitus92.tistory](https://habitus92.tistory.com/19)
  - **레벨(Level)**: 같은 깊이를 가진 노드들의 그룹으로, 보통 깊이 +1 로 정의합니다. [kyeong-hoon.tistory](https://kyeong-hoon.tistory.com/570)
  - **높이(Height)**: 해당 노드에서 가장 깊은 리프까지의 최대 간선 수이며, 트리의 높이는 루트의 높이입니다. [kyeong-hoon.tistory](https://kyeong-hoon.tistory.com/570)
- **핵심 포인트**:
  - 루트의 깊이는 0, 레벨은 1입니다.
  - 리프의 높이는 0 입니다.
  - 트리의 높이는 `h`일 때, 포화이진트리의 노드 수는 `2^h - 1`입니다. [hsc-tech.tistory](https://hsc-tech.tistory.com/7)
- **관련 용어**: Depth, Level, Height, 높이, 깊이, 레벨
- **간단한 예시**: 루트에서 2 단계 내려간 노드는 깊이 2, 레벨 3 입니다.
- **복잡도**: 해당 없음
- **면접 한 줄 정리**: "깊이는 루트부터의 거리, 레벨은 같은 깊이의 노드 그룹, 높이는 가장 깊은 리프까지의 거리입니다."

***

### 트리 순회 (Tree Traversal)

- **정의**: 트리의 모든 노드를 특정 순서로 방문하는 방법입니다. [ko.wikipedia](https://ko.wikipedia.org/wiki/%ED%8A%B8%EB%A6%AC_%EC%88%9C%ED%9A%8C)
- **핵심 포인트**:
  - **Preorder(전위)**: 루트 → 왼쪽 → 오른쪽 (VLR)
  - **Inorder(중위)**: 왼쪽 → 루트 → 오른쪽 (LVR)
  - **Postorder(후위)**: 왼쪽 → 오른쪽 → 루트 (LRV)
  - **Level Order(레벨 순서)**: 위에서 아래, 왼쪽에서 오른쪽 (BFS)
  - BST 에서 Inorder 는 정렬된 순서를 반환합니다. [devinus.tistory](https://devinus.tistory.com/20)
- **관련 용어**: DFS, BFS, Depth-First, Breadth-First
- **간단한 예시**:
  ```
      F
     / \
    B   G
   / \   \
  A   D   I
     / \  /
    C   E H
  ```
  - Preorder: F, B, A, D, C, E, G, I, H [ko.wikipedia](https://ko.wikipedia.org/wiki/%ED%8A%B8%EB%A6%AC_%EC%88%9C%ED%9A%8C)
  - Inorder: A, B, C, D, E, F, G, H, I [ko.wikipedia](https://ko.wikipedia.org/wiki/%ED%8A%B8%EB%A6%AC_%EC%88%9C%ED%9A%8C)
  - Postorder: A, C, E, D, B, H, I, G, F [devinus.tistory](https://devinus.tistory.com/20)
  - Level Order: F, B, G, A, D, I, C, E, H [devinus.tistory](https://devinus.tistory.com/20)
- **복잡도**:
  - 시간복잡도: O(n) (n: 노드 수)
  - 공간복잡도: 재귀 사용 시 O(h) (h: 트리 높이), Level Order 는 O(w) (w: 최대 너비)
- **면접 한 줄 정리**: "트리의 모든 노드를 체계적으로 방문하는 방법으로, Preorder, Inorder, Postorder, Level Order 가 있습니다."

***

### BST 연산 (탐색·삽입·삭제)

- **정의**: BST 에서 데이터를 찾거나 추가·제거하는 기본 연산입니다. [until](https://until.blog/@uzlnee/-cs-%EC%9E%90%EB%A3%8C%EA%B5%AC%EC%A1%B0--%ED%8A%B8%EB%A6%AC-tree-)
- **핵심 포인트**:
  - **탐색**: 루트부터 비교하며 왼쪽/오른쪽으로 이동
  - **삽입**: 탐색 경로 끝에 새 노드 추가
  - **삭제 3 경우**:
    1. Leaf: 그냥 제거
    2. Child 1 개: 자식을 부모에 연결
    3. Child 2 개: 오른쪽 서브트리의 최소(또는 왼쪽 서브트리의 최대) 로 대체
  - 편향 시 성능 저하로 BBST(AVL, Red-Black) 가 등장했습니다. [hsc-tech.tistory](https://hsc-tech.tistory.com/7)
- **관련 용어**: Search, Insert, Delete, Leaf, Child
- **간단한 예시**: 위 BST 에서 6 삭제 시 Child 1 개이므로 6 의 부모(3) 가 6 의 자식(없음) 을 연결합니다.
- **복잡도**:
  - 평균: O(log n)
  - 최악: O(n)
- **면접 한 줄 정리**: "BST 연산은 탐색·삽입·삭제로, 삭제는 Leaf, Child 1 개, Child 2 개 경우로 나뉩니다."

***

## 3. 왜 중요한가?

### 실제 개발 및 시스템 관점

트리는 계층적 데이터(파일 시스템, DOM, 조직도) 를 표현하고, BST 는 정렬된 데이터의 효율적 탐색을 가능하게 합니다.  대용량 데이터에서 O(log n) 탐색은 서버 응답 시간과 비용에 직접적인 영향을 미치며, 편향 시 O(n) 으로 성능이 급격히 저하됩니다.  메모리 사용량은 노드 수에 비례하며, 재귀 호출 시 스택 오버플로우 위험이 있습니다. [habitus92.tistory](https://habitus92.tistory.com/19)

### 입력 크기 n 이 커질 때

- **연산량**: O(log n) 은 n 이 100 만일 때 약 20 회, O(n) 은 100 만 회입니다.
- **실행 시간**: O(log n) 은 거의 일정, O(n) 은 선형 증가합니다.
- **메모리 사용량**: O(n) 으로 노드 수에 비례합니다.
- **응답 시간**: 편향 시 급격히 증가합니다.
- **확장성**: 균형 트리(AVL, Red-Black) 는 대규모 데이터에서도 안정적입니다.
- **병목 발생 가능성**: 편향트리에서 탐색·삽입·삭제가 병목이 됩니다.

### 면접 답변 예시

"트리는 계층적 데이터를 표현하는 비선형 자료구조로, 이진트리는 각 노드가 최대 2개의 자식을 갖습니다. BST 는 왼쪽 < 부모 < 오른쪽 규칙으로 평균 O(log n) 탐색이 가능하지만, 편향 시 O(n) 으로 성능이 저하되어 AVL·Red-Black 트리 같은 균형 트리가 필요합니다."

## 1. 개념 정리

### 힙 (Heap)

- **정의**: 힙은 완전 이진 트리 구조와 힙 속성을 동시에 만족하는 자료구조입니다.
- **핵심 포인트**:
  - 완전 이진 트리이므로 트리의 높이는 `O(log n)`입니다.
  - 부모 노드와 자식 노드 사이의 대소 관계만 보장합니다.
  - 전체 데이터가 정렬되어 있는 것은 아닙니다.
  - 루트(root)에 최댓값 또는 최솟값이 위치합니다.
  - 배열(Array)로 효율적으로 구현할 수 있습니다.
- **관련 용어**:
  - 완전 이진 트리, Complete Binary Tree
  - 힙 속성, Heap Property
  - 루트, Root
  - 부모 노드, Parent
  - 자식 노드, Child
  - 상향식 조정, Up Heap
  - 하향식 조정, Down Heap
- **간단한 예시**:

Max Heap:

```text
        90
       /  \
     70    60
    /  \   /
   20  40 50
```

각 부모가 자식보다 크거나 같으므로 Max Heap입니다.

- **복잡도**:
  - 최댓값 또는 최솟값 조회: `O(1)`
  - 삽입: `O(log n)`
  - 루트 삭제: `O(log n)`
  - 전체 공간: `O(n)`
- **면접 한 줄 정리**:  
  “힙은 완전 이진 트리와 힙 속성을 이용해 최댓값 또는 최솟값을 효율적으로 관리하는 자료구조입니다.”

***

### 완전 이진 트리 (Complete Binary Tree)

- **정의**: 마지막 레벨을 제외한 모든 레벨이 가득 차 있고, 마지막 레벨은 왼쪽부터 빈틈없이 채워지는 이진 트리입니다.
- **핵심 포인트**:
  - 높이가 데이터 개수에 대해 `O(log n)`입니다.
  - 노드를 삽입할 위치가 항상 정해져 있습니다.
  - 배열로 저장할 때 빈 공간이 거의 발생하지 않습니다.
  - 일반 이진 트리와 달리 균형이 비교적 잘 유지됩니다.
- **관련 용어**:
  - 이진 트리, Binary Tree
  - 포화 이진 트리, Perfect Binary Tree
  - 높이, Height
  - 레벨, Level
- **간단한 예시**:

```text
        10
       /  \
      8    9
     / \  /
    3  5 7
```

마지막 레벨이 왼쪽부터 채워져 있으므로 완전 이진 트리입니다.

- **복잡도**:
  - 높이: `O(log n)`
  - 노드 순회 자체: `O(n)`
- **면접 한 줄 정리**:  
  “완전 이진 트리는 마지막 레벨을 제외한 레벨이 모두 차 있고, 마지막 레벨은 왼쪽부터 채워지는 구조라 배열 구현에 적합합니다.”

***

### 힙 속성 (Heap Property)

- **정의**: 부모 노드와 자식 노드 사이에 유지되는 우선순위 관계입니다.
- **핵심 포인트**:
  - Max Heap에서는 부모가 자식보다 크거나 같습니다.
  - Min Heap에서는 부모가 자식보다 작거나 같습니다.
  - 형제 노드 사이의 순서는 보장하지 않습니다.
  - 이진 탐색 트리처럼 왼쪽 자식이 항상 작고 오른쪽 자식이 항상 큰 것은 아닙니다.
- **관련 용어**:
  - Max Heap Property
  - Min Heap Property
  - 우선순위, Priority
  - 불변식, Invariant
- **간단한 예시**:

Min Heap:

```text
        10
       /  \
      20   15
     / \   /
    30 40 25
```

각 부모가 자식보다 작거나 같으므로 Min Heap입니다.

- **복잡도**:
  - 속성 위반 여부를 전체적으로 확인: 최대 `O(n)`
  - 특정 경로를 따라 복구: `O(log n)`
- **면접 한 줄 정리**:  
  “힙 속성은 전체 정렬이 아니라 부모와 자식 사이의 우선순위 관계만 보장한다는 점이 핵심입니다.”

***

### 배열 기반 힙 (Array-Based Heap)

힙은 완전 이진 트리이므로 별도의 `left`, `right`, `parent` 포인터 없이 배열에 저장할 수 있습니다.

#### 1-index 기준

노드의 인덱스를 `i`라고 하면 다음과 같습니다.

| 관계 | 인덱스 |
|---|---:|
| 부모 | `⌊i / 2⌋` |
| 왼쪽 자식 | `2i` |
| 오른쪽 자식 | `2i + 1` |

예를 들어 `i = 3`이면 부모는 `1`, 왼쪽 자식은 `6`, 오른쪽 자식은 `7`입니다.

#### 0-index 기준

Java 배열은 일반적으로 0부터 시작하므로 다음 공식을 사용합니다.

| 관계 | 인덱스 |
|---|---:|
| 부모 | `(i - 1) / 2` |
| 왼쪽 자식 | `2i + 1` |
| 오른쪽 자식 | `2i + 2` |

> 주의: 질문에 제시된 `부모 i`, `왼쪽 2i`, `오른쪽 2i+1`은 노드 자체의 인덱스가 아니라 1-index 기준에서 자식 관계를 표현할 때의 형태로 이해해야 합니다. 1-index에서 부모는 `⌊i/2⌋`입니다.

- **핵심 포인트**:
  - 배열 저장은 포인터가 없어 메모리 효율이 좋습니다.
  - 부모와 자식의 위치를 산술식으로 계산합니다.
  - Java에서는 0-index 방식이 자연스럽습니다.
  - 배열 크기가 부족하면 동적 배열 확장이 발생할 수 있습니다.
- **복잡도**:
  - 부모·자식 인덱스 계산: `O(1)`
  - 배열 저장 공간: `O(n)`
- **면접 한 줄 정리**:  
  “힙은 완전 이진 트리이기 때문에 0-index 배열에서 부모 `(i-1)/2`, 왼쪽 자식 `2i+1`, 오른쪽 자식 `2i+2`로 표현할 수 있습니다.”

***

### 상향식 조정 (Up Heap 또는 Sift Up)

- **정의**: 새 원소를 힙의 마지막 위치에 추가한 뒤, 부모와 비교하며 위쪽으로 이동시키는 과정입니다.
- **동작 원리**:
  1. 새 원소를 배열의 마지막에 추가합니다.
  2. 부모와 비교합니다.
  3. 힙 속성을 위반하면 두 원소를 교환합니다.
  4. 루트에 도달하거나 더 이상 교환이 필요 없을 때 종료합니다.
- **간단한 예시**:

Min Heap에 `5`를 삽입하는 경우:

```text
삽입 전:       10
              /  \
             20   15

5 추가:        10
              /  \
             20   15
            /
           5

상향 조정:
5와 20 교환
5와 10 교환
```

결과:

```text
        5
       / \
      10 15
     /
    20
```

- **복잡도**:
  - 최선: `O(1)` — 추가 직후 부모보다 우선순위가 낮거나 높아 이동하지 않는 경우
  - 평균: 일반적으로 `O(log n)`
  - 최악: `O(log n)` — 루트까지 이동하는 경우
  - 보조 공간: 반복문 구현 시 `O(1)`
- **면접 한 줄 정리**:  
  “삽입은 마지막 위치에 넣은 뒤 부모 방향으로 올라가며 힙 속성을 복구하므로 최악의 경우 트리 높이인 `O(log n)`입니다.”

***

### 하향식 조정 (Down Heap 또는 Sift Down)

- **정의**: 루트 삭제 후 마지막 원소를 루트로 옮기고, 자식과 비교하면서 아래쪽으로 이동시키는 과정입니다.
- **동작 원리**:
  1. 루트 원소를 저장합니다.
  2. 마지막 원소를 루트로 이동합니다.
  3. 두 자식 중 우선순위가 더 높은 자식과 비교합니다.
  4. 힙 속성을 위반하면 교환합니다.
  5. 더 이상 위반이 없을 때 종료합니다.
- **중요한 점**:
  - Min Heap에서는 두 자식 중 더 작은 자식과 비교합니다.
  - Max Heap에서는 두 자식 중 더 큰 자식과 비교합니다.
- **복잡도**:
  - 최선: `O(1)`
  - 평균: 일반적으로 `O(log n)`
  - 최악: `O(log n)`
  - 보조 공간: 반복문 구현 시 `O(1)`
- **면접 한 줄 정리**:  
  “삭제는 마지막 원소를 루트로 옮긴 뒤 더 우선순위가 높은 자식과 교환하며 내려가므로 `O(log n)`입니다.”

***

### 힙 구성 (Build Heap)

- **정의**: 정렬되지 않은 배열 전체를 힙으로 변환하는 과정입니다.
- **방법**:
  - 모든 원소를 하나씩 삽입: `O(n log n)`
  - 마지막 내부 노드부터 Down Heap 수행: `O(n)`
- **왜 `O(n)`인가?**:
  - 잎 노드는 이동할 필요가 없습니다.
  - 많은 노드는 높이가 작아서 적은 횟수만 이동합니다.
  - 일부 루트 근처 노드만 긴 경로를 이동합니다.
  - 각 노드의 높이를 합산하면 전체 비용이 `O(n)`이 됩니다.
- **복잡도**:
  - 반복 삽입 방식: `O(n log n)`
  - Bottom-up Build Heap: 최선·평균·최악 모두 `O(n)`
  - 보조 공간: 배열 내부 수정 시 `O(1)`
- **면접 한 줄 정리**:  
  “배열을 힙으로 만드는 Bottom-up Heapify는 각 노드의 높이 합을 이용해 전체 `O(n)`에 수행할 수 있습니다.”

***

### 우선순위 큐 (Priority Queue)

- **정의**: 먼저 들어온 순서가 아니라 우선순위가 가장 높은 원소부터 처리하는 추상 자료형입니다.
- **핵심 포인트**:
  - 일반적으로 힙을 이용해 구현합니다.
  - 삽입은 `offer` 또는 `add`입니다.
  - 최우선 원소 조회는 `peek`입니다.
  - 최우선 원소 제거는 `poll`입니다.
  - Java `PriorityQueue`는 기본적으로 자연 순서에 따라 가장 작은 원소를 먼저 반환합니다. [Oracle Java PriorityQueue 문서](https://docs.oracle.com/javase/8/docs/api/java/util/PriorityQueue.html)

## 3. 왜 중요한가?

### 실제 개발 및 시스템 관점

힙은 “가장 중요한 작업을 먼저 처리해야 하는 상황”을 효율적으로 해결합니다.

- **대용량 데이터 처리**: 전체를 정렬하지 않고도 현재 최솟값·최댓값만 빠르게 얻을 수 있습니다.
- **성능 최적화**: 매번 전체 배열을 정렬하는 대신 `peek`와 `poll`을 사용해 필요한 원소만 처리할 수 있습니다.
- **메모리 사용량**: 배열 기반 힙은 노드 객체와 포인터를 사용하는 트리보다 메모리 지역성이 좋습니다.
- **응답 시간**: 작업 우선순위, 네트워크 패킷, 이벤트 예약 등에서 다음 처리 대상을 빠르게 선택합니다.
- **확장성**: 원소가 `n`개일 때 삽입과 삭제가 `O(log n)`이므로 선형 검색보다 확장성이 좋습니다.
- **실시간 처리**: 가장 긴급한 작업 또는 가장 가까운 이벤트를 반복적으로 꺼낼 수 있습니다.
- **한계**: 특정 값을 빠르게 검색하거나 모든 데이터를 정렬된 순서로 조회하는 용도에는 적합하지 않습니다.

### 입력 크기 n이 커질 때

- `peek`는 `n`이 증가해도 루트만 확인하므로 연산량이 거의 변하지 않습니다.
- 삽입과 삭제는 `O(log n)`이므로 데이터가 10배 증가해도 트리 높이는 약 `log₂10`만큼 증가합니다.
- 힙 전체를 저장해야 하므로 메모리는 `O(n)`으로 증가합니다.
- 특정 값 검색은 `O(n)`이므로 데이터가 10배 증가하면 최악의 탐색량도 약 10배 증가합니다.
- 반복적으로 우선순위 원소를 처리하는 서버에서는 `O(n)` 검색보다 `O(log n)` 삽입·삭제가 큰 성능 차이를 만듭니다.

### **간단한 예시**:

정렬된 순서로 `1, 2, 3, 4, 5`를 일반 BST에 삽입하면 다음과 같이 됩니다.

```text
1
 \
  2
   \
    3
     \
      4
       \
        5
```

BBST는 회전을 통해 다음과 같이 높이를 줄일 수 있습니다.

```text
    2
   / \
  1   4
     / \
    3   5
```

- **복잡도**:
  - 탐색·삽입·삭제: 일반적으로 최악의 경우 `O(log n)`
  - 회전 하나: `O(1)`
  - 저장 공간: `O(n)`

***

### 1-3. 트리 높이 (Height)

- **정의**: 루트에서 가장 깊은 리프까지의 간선 수 또는 노드 수입니다. 구현에 따라 빈 트리의 높이를 `-1` 또는 `0`으로 정의할 수 있습니다.
- **핵심 포인트**:
  - BST 연산의 시간복잡도를 결정하는 핵심 요소입니다.
  - 노드 수가 `n`일 때 균형 트리의 높이는 대략 `O(log n)`입니다.
  - 편향 트리의 높이는 `n`에 가까워져 `O(n)`이 됩니다.
  - AVL은 Red-Black Tree보다 더 엄격하게 높이를 제한합니다.
- **관련 용어**: 깊이(Depth), 레벨(Level), 균형(Balance), 서브트리 높이
- **복잡도**:
  - BST 탐색·삽입·삭제: `O(h)`
  - 균형 트리: `h = O(log n)`
  - 편향 트리: `h = O(n)`
- **면접 한 줄 정리**: “BST의 성능은 노드 개수보다 높이에 직접적으로 좌우되므로, BBST에서는 높이를 `O(log n)`으로 유지하는 것이 핵심입니다.”

***

### 1-4. 회전 (Rotation)

회전은 BST의 정렬 관계를 유지하면서 트리의 구조를 바꾸는 연산입니다. 노드의 연결 관계 일부만 바꾸므로 한 번의 회전은 `O(1)`입니다.

#### 왼쪽 회전 (Left Rotation)

```text
      x                         y
       \                       / \
        y       →              x   C
       / \                     / \
      B   C                   A   B
```

- `y`가 `x`의 오른쪽 자식일 때 수행합니다.
- `y`의 왼쪽 서브트리 `B`를 `x`의 오른쪽 서브트리로 이동시킵니다.
- BST의 대소 관계는 유지됩니다.

#### 오른쪽 회전 (Right Rotation)

```text
        y                       x
       /                       / \
      x       →                 A   y
     / \                           / \
    A   B                         B   C
```

- `x`가 `y`의 왼쪽 자식일 때 수행합니다.
- `x`의 오른쪽 서브트리 `B`를 `y`의 왼쪽 서브트리로 이동시킵니다.

#### 이중 회전 (Double Rotation)

| 유형 | 발생 형태 | 수행 순서 |
|---|---|---|
| LL | 왼쪽 자식의 왼쪽에 삽입 | 오른쪽 회전 |
| RR | 오른쪽 자식의 오른쪽에 삽입 | 왼쪽 회전 |
| LR | 왼쪽 자식의 오른쪽에 삽입 | 왼쪽 회전 후 오른쪽 회전 |
| RL | 오른쪽 자식의 왼쪽에 삽입 | 오른쪽 회전 후 왼쪽 회전 |

***

### 1-5. AVL Tree

- **정의**: 모든 노드에서 왼쪽과 오른쪽 서브트리 높이 차이가 최대 1이 되도록 유지하는 높이 균형 BST입니다.
- **Balance Factor**:

```text
Balance Factor = height(left subtree) - height(right subtree)
```

허용되는 값은 `-1`, `0`, `1`입니다.

- **핵심 포인트**:
  - 삽입·삭제 후 조상 노드 방향으로 올라가며 높이와 Balance Factor를 갱신합니다.
  - Balance Factor가 `2` 또는 `-2`가 되면 회전이 필요합니다.
  - 높이를 엄격하게 유지하므로 탐색 성능이 좋습니다.
  - 삽입과 삭제 시 균형 조정 비용이 Red-Black Tree보다 커질 수 있습니다.
- **회전 조건**:

| 불균형 유형 | 조건 | 해결 |
|---|---|---|
| LL | 현재 노드의 왼쪽 자식 왼쪽에 삽입 | Right Rotation |
| RR | 현재 노드의 오른쪽 자식 오른쪽에 삽입 | Left Rotation |
| LR | 왼쪽 자식 오른쪽에 삽입 | Left Rotation → Right Rotation |
| RL | 오른쪽 자식 왼쪽에 삽입 | Right Rotation → Left Rotation |

- **관련 용어**: Balance Factor, Height Update, LL Rotation, RR Rotation, LR Rotation, RL Rotation
- **복잡도**:
  - 탐색: 최선 `O(1)`, 평균·최악 `O(log n)`
  - 삽입: 평균·최악 `O(log n)`
  - 삭제: 평균·최악 `O(log n)`
  - 회전: `O(1)`
  - 보조 공간: 반복 구현은 `O(1)`, 재귀 구현은 호출 스택 `O(log n)`
- **면접 한 줄 정리**: “AVL Tree는 모든 노드의 Balance Factor를 `-1`에서 `1` 사이로 유지하기 때문에 탐색에는 유리하지만, 삽입·삭제 시 회전과 높이 갱신이 더 자주 발생합니다.”

AVL Tree는 높이 균형을 위해 인접 서브트리의 높이 차이를 최대 1로 제한하며, 최소 노드 수가 피보나치 형태의 점화식을 따르므로 높이가 로그 수준으로 제한됩니다. [opendatastructures](https://opendatastructures.org/newhtml/ods/latex/redblack.html)

***

### 1-6. Red-Black Tree

- **정의**: 각 노드에 Red 또는 Black 색을 부여하고, 색상 규칙을 통해 트리 높이를 제한하는 자기 균형 BST입니다.
- **색상 규칙**:
  1. 모든 노드는 Red 또는 Black입니다.
  2. 루트는 Black입니다.
  3. 모든 NIL 또는 외부 리프는 Black으로 간주합니다.
  4. Red 노드의 자식은 Red일 수 없습니다.
  5. 각 노드에서 NIL 리프까지 내려가는 모든 경로의 Black 노드 수가 같습니다. 이를 Black Height라고 합니다.
- **핵심 포인트**:
  - AVL보다 균형 조건이 느슨합니다.
  - 삽입·삭제 시 색상 변경(Color Flip)과 회전을 사용합니다.
  - 트리 높이는 `O(log n)`으로 제한됩니다.
  - 회전 횟수가 AVL보다 적은 편이라 업데이트가 많은 환경에 적합합니다.
- **관련 용어**: Red Node, Black Node, NIL Leaf, Black Height, Color Flip, Recoloring
- **복잡도**:
  - 탐색: 최선 `O(1)`, 평균·최악 `O(log n)`
  - 삽입: 평균·최악 `O(log n)`
  - 삭제: 평균·최악 `O(log n)`
  - 공간: `O(n)`
- **면접 한 줄 정리**: “Red-Black Tree는 색상 규칙과 회전을 이용해 높이를 `O(log n)`으로 제한하며, AVL보다 업데이트에 유리한 완화된 균형 트리입니다.”

Red-Black Tree는 높이가 최대 로그 수준으로 제한되며, 탐색·삽입·삭제를 최악의 경우 `O(log n)`에 수행할 수 있습니다. [opendatastructures](https://opendatastructures.org/newhtml/ods/latex/redblack.html)

***

### 1-7. AVL Tree와 Red-Black Tree 비교

| 구분 | AVL Tree | Red-Black Tree |
|---|---|---|
| 균형 기준 | 서브트리 높이 차이 | 색상 및 Black Height |
| 균형 엄격도 | 엄격함 | 상대적으로 느슨함 |
| 높이 | 더 낮은 편 | AVL보다 높은 편 |
| 탐색 | 일반적으로 더 빠름 | AVL보다 약간 불리할 수 있음 |
| 삽입 | 회전·갱신 가능성이 상대적으로 큼 | 색상 변경으로 끝나는 경우가 많음 |
| 삭제 | 복구 과정이 복잡하고 회전 가능 | 삭제 복구가 복잡하지만 업데이트에 적합 |
| 최악 탐색 | `O(log n)` | `O(log n)` |
| 최악 삽입·삭제 | `O(log n)` | `O(log n)` |
| 적합한 상황 | 탐색 비중이 높은 경우 | 삽입·삭제가 빈번한 경우 |
| 대표 Java 사용처 | 표준 컬렉션의 기본 구현은 아님 | `TreeMap`, `TreeSet`, HashMap Tree Bin |

AVL은 Red-Black Tree보다 높이가 더 낮게 유지되는 경향이 있고, Red-Black Tree는 업데이트 과정에서 균형을 조금 느슨하게 유지합니다. [opendatastructures](https://opendatastructures.org/newhtml/ods/latex/redblack.html)

***

## 3. 왜 중요한가?

### 실제 개발 및 시스템 관점

BBST를 사용하면 데이터가 특정 순서로 입력되더라도 트리 높이가 선형으로 증가하지 않습니다.

- **대용량 데이터 처리**: `n`이 커질수록 `O(n)`과 `O(log n)`의 차이가 크게 벌어집니다.
- **응답 시간 안정성**: 최악의 경우에도 `O(log n)`을 보장해 예측 가능한 응답 시간을 만들 수 있습니다.
- **정렬과 검색 동시 지원**: 트리 구조 자체가 정렬되어 있으므로 범위 검색과 순서 기반 연산이 가능합니다.
- **확장성**: 데이터가 증가해도 연산 횟수가 선형으로 증가하지 않습니다.
- **장애 및 병목 방지**: 해시 충돌이나 나쁜 삽입 순서가 특정 연산을 `O(n)`으로 악화시키는 것을 완화합니다.
- **메모리 trade-off**: 균형 정보를 저장하는 필드와 부모·자식 포인터 때문에 배열이나 단순 연결 리스트보다 메모리를 더 사용할 수 있습니다.

데이터베이스의 인덱스는 디스크 I/O와 페이지 단위 접근 때문에 보통 B-Tree 계열을 사용하지만, 애플리케이션 메모리 내부의 정렬 집합이나 맵에는 BBST가 적합할 수 있습니다.

### 입력 크기 n이 커질 때

여기서 `n`은 트리에 저장된 노드 또는 키의 개수입니다.

- 균형 트리의 높이 `h`는 `O(log n)`으로 증가합니다.
- 탐색 경로의 길이도 `O(log n)`으로 증가합니다.
- 트리 전체 저장 공간은 노드 수에 비례해 `O(n)`입니다.
- 회전 자체는 `O(1)이지만`, 삽입·삭제 후 루트까지 균형 정보를 갱신하는 과정은 `O(log n)`입니다.
- 일반 BST가 편향되면 `n`이 10배 증가할 때 탐색 비용도 대략 10배 증가하지만, BBST는 높이가 약 `log₂ 10 ≈ 3.32`만큼 증가합니다.

### Bubble Sort (버블 정렬)

- **정의**: 인접한 두 원소를 비교하고 순서가 잘못되었으면 교환하는 과정을 반복한다.
- **핵심 포인트**:
  - 한 번의 순회가 끝나면 가장 큰 원소가 오른쪽 끝으로 이동한다.
  - 인접 원소만 비교하므로 구현이 매우 쉽다.
  - 한 번도 교환하지 않았다면 조기 종료할 수 있다.
  - 거의 정렬된 입력에서는 최선의 경우 \(O(n)\)이 가능하다.
  - 일반적인 대규모 데이터에는 부적합하다.
- **간단한 예시**: `[3, 1, 2]`에서 `3`과 `1`을 교환한 뒤, `3`과 `2`를 교환하면 `[1, 2, 3]`이 된다.
- **복잡도**: 최선 \(O(n)\), 평균·최악 \(O(n^2)\), 보조 공간 \(O(1)\).
- **안정성·제자리 여부**: Stable, In-place.
- **면접 한 줄 정리**: “Bubble Sort는 인접 원소 교환 기반의 Stable·In-place 정렬이지만 평균과 최악이 \(O(n^2)\)라 교육 목적 외에는 거의 사용하지 않습니다.”

### Selection Sort (선택 정렬)

- **정의**: 정렬되지 않은 영역에서 최솟값을 찾아 현재 위치와 교환한다.
- **핵심 포인트**:
  - 첫 번째 위치에는 전체 최솟값, 두 번째 위치에는 남은 원소 중 최솟값을 배치한다.
  - 교환 횟수는 최대 \(O(n)\)으로 적다.
  - 최선·평균·최악 모두 \(O(n^2)\)이다.
  - 일반적인 swap 구현은 Stable하지 않다.
  - 쓰기 연산이 비싼 플래시 저장장치 등에서는 교환 횟수가 적다는 장점이 있을 수 있다.
- **간단한 예시**: `[4, 2, 5, 1]`에서 최솟값 `1`을 첫 원소 `4`와 교환한다.
- **복잡도**: 최선·평균·최악 \(O(n^2)\), 보조 공간 \(O(1)\).
- **안정성·제자리 여부**: 일반 구현 기준 Unstable, In-place.
- **면접 한 줄 정리**: “Selection Sort는 매 단계 최솟값을 선택해 교환하므로 swap 횟수는 적지만 비교 횟수는 항상 \(O(n^2)\)입니다.”

### Insertion Sort (삽입 정렬)

- **정의**: 정렬된 왼쪽 영역에 현재 원소를 알맞은 위치에 삽입한다.
- **핵심 포인트**:
  - 카드 게임에서 손에 카드를 정렬하는 방식과 유사하다.
  - 이미 정렬된 데이터나 거의 정렬된 데이터에서 매우 효율적이다.
  - 원소를 뒤로 이동시켜 빈 위치를 만들고 현재 값을 삽입한다.
  - 동일한 값에 대해 `>`만 사용하면 기존 순서를 유지할 수 있다.
- **간단한 예시**: `[2, 4, 1]`에서 `1`을 왼쪽으로 이동시키면 `[1, 2, 4]`가 된다.
- **복잡도**: 최선 \(O(n)\), 평균·최악 \(O(n^2)\), 보조 공간 \(O(1)\).
- **안정성·제자리 여부**: Stable, In-place.
- **면접 한 줄 정리**: “Insertion Sort는 거의 정렬된 입력에서 \(O(n)\)에 가까운 성능을 내며, 작은 배열이나 하이브리드 정렬의 작은 구간 처리에 적합합니다.”

### Merge Sort (병합 정렬)

- **정의**: 배열을 절반씩 나눈 뒤 각각 정렬하고, 정렬된 두 배열을 병합한다.
- **핵심 포인트**:
  - Divide & Conquer(분할 정복) 알고리즘이다.
  - 두 정렬 배열을 앞에서부터 비교해 작은 값을 결과 배열에 넣는다.
  - 분할은 재귀적으로 진행하고 병합은 선형 시간에 처리한다.
  - 입력 상태와 무관하게 최악의 경우에도 \(O(n \log n)\)을 보장한다.
  - 일반적인 배열 구현은 임시 배열이 필요하다.
- **점화식**:

```text
T(n) = 2T(n/2) + O(n)
T(n) = O(n log n)
```

  - `2T(n/2)`: 절반 크기의 배열 두 개를 정렬한다.
  - `O(n)`: 두 정렬 결과를 병합한다.
- **복잡도**: 최선·평균·최악 \(O(n \log n)\), 보조 공간 \(O(n)\), 재귀 스택 \(O(\log n)\).
- **안정성·제자리 여부**: Stable, 일반 배열 구현 기준 Not In-place.
- **면접 한 줄 정리**: “Merge Sort는 입력에 관계없이 \(O(n \log n)\)을 보장하고 Stable하지만, 배열 병합을 위한 \(O(n)\) 보조 공간이 필요합니다.”

### Quick Sort (퀵 정렬)

- **정의**: Pivot을 기준으로 원소를 분할하고, 분할된 부분 배열을 재귀적으로 정렬한다.
- **핵심 포인트**:
  - Pivot 선택 방식이 성능을 크게 좌우한다.
  - Partition 이후 Pivot보다 작은 값은 왼쪽, 큰 값은 오른쪽에 배치한다.
  - 평균적으로 \(O(n \log n)\)이며 캐시 효율이 좋아 실제로 빠른 경우가 많다.
  - 최악에는 한쪽 부분 배열만 계속 커져 \(O(n^2)\)이 된다.
  - Randomized Pivot 또는 Median-of-Three로 최악 가능성을 줄일 수 있다.
- **점화식**:
  - 균형 분할: `T(n) = 2T(n/2) + O(n)` → \(O(n \log n)\)
  - 편향 분할: `T(n) = T(n-1) + O(n)` → \(O(n^2)\)
- **복잡도**: 최선 \(O(n \log n)\), 평균 \(O(n \log n)\), 최악 \(O(n^2)\).
- **공간복잡도**: 평균 재귀 스택 \(O(\log n)\), 최악 \(O(n)\). In-place Partition을 사용하면 추가 배열은 거의 없다.
- **안정성·제자리 여부**: 일반 구현 기준 Unstable, In-place.
- **면접 한 줄 정리**: “Quick Sort는 평균 \(O(n \log n)\)과 좋은 캐시 지역성을 가지지만, Pivot이 편향되면 \(O(n^2)\)이 되므로 Pivot 전략과 재귀 깊이를 관리해야 합니다.”

### Heap Sort (힙 정렬)

- **정의**: 배열을 Max Heap 또는 Min Heap으로 만든 뒤 최댓값·최솟값을 반복해서 꺼내 정렬한다.
- **핵심 포인트**:
  - Max Heap에서는 루트가 항상 최댓값이다.
  - Heapify는 한 노드에서 아래 방향으로 힙 속성을 복구한다.
  - 전체 Heap 생성은 \(O(n)\)이다.
  - 원소를 \(n\)번 삭제하며 각 삭제가 \(O(\log n)\)이므로 전체는 \(O(n \log n)\)이다.
  - 최악의 경우에도 \(O(n \log n)\)을 보장한다.
- **복잡도**: 최선·평균·최악 \(O(n \log n)\), 보조 공간 \(O(1)\).
- **안정성·제자리 여부**: Unstable, In-place.
- **면접 한 줄 정리**: “Heap Sort는 추가 배열 없이 최악 \(O(n \log n)\)을 보장하지만, 일반적으로 Quick Sort보다 캐시 효율과 평균 성능이 떨어질 수 있습니다.”

### Counting Sort (계수 정렬)

- **정의**: 각 값의 등장 횟수를 세어 누적 위치를 계산하고 원소를 배치한다.
- **적용 조건**:
  - 정수 또는 정수로 매핑 가능한 값이어야 한다.
  - 최솟값부터 최댓값까지의 범위 \(k\)가 지나치게 크지 않아야 한다.
- **핵심 포인트**:
  - 원소끼리 직접 비교하지 않는다.
  - 빈도 배열 크기는 값의 범위에 비례한다.
  - 안정적인 배치 방식으로 구현하면 Stable하다.
  - 음수는 `value - minValue` 형태로 offset을 적용할 수 있다.
- **복잡도**: \(O(n+k)\), 보조 공간 \(O(n+k)\).
- **면접 한 줄 정리**: “Counting Sort는 값의 범위 \(k\)가 작을 때 \(O(n+k)\)로 빠르지만, 범위가 크면 메모리 낭비가 발생합니다.”

### Radix Sort (기수 정렬)

- **정의**: 숫자의 각 자릿수를 기준으로 여러 번 정렬하는 비비교 기반 정렬이다.
- **핵심 포인트**:
  - 보통 일의 자리부터 시작하는 LSD(Least Significant Digit) 방식을 사용한다.
  - 각 자릿수 정렬은 Stable해야 이전 자릿수의 정렬 결과가 보존된다.
  - 각 자릿수에 Counting Sort를 사용할 수 있다.
  - `d`가 자릿수 개수이고 각 자릿수의 기수 범위가 `b`라면 \(O(d(n+b))\)이다.
- **복잡도**: \(O(d(n+b))\), 보조 공간 \(O(n+b)\).
- **면접 한 줄 정리**: “Radix Sort는 자릿수별 Stable 정렬을 반복하며, 자릿수 \(d\)가 제한된 정수 데이터에서는 비교 기반 정렬보다 빠를 수 있습니다.”

### 안정 정렬 (Stable Sort)

- **정의**: 정렬 기준이 같은 원소들의 기존 상대 순서를 유지하는 정렬이다.
- **예시**:
  - 입력: `(점수 90, 김)`, `(점수 90, 이)`
  - Stable 정렬 후에도 김이 이보다 앞에 있어야 한다.
- **Stable 예시**: Bubble, Insertion, Merge, Counting의 안정 구현, Radix.
- **Unstable 예시**: Selection, 일반 Quick, Heap.
- **중요성**:
  - 여러 기준으로 연속 정렬할 때 중요하다.
  - 먼저 이름순으로 정렬한 후 점수순으로 Stable 정렬하면 점수가 같은 학생은 이름순을 유지한다.
  - Java `Arrays.sort(Object[])`는 안정성이 명세상 요구되지만, 구체적인 구현 알고리즘은 명세가 아닌 구현 세부사항이다. [Oracle Java Arrays API](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/Arrays.html) [docs.oracle](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/Arrays.html)
- **면접 한 줄 정리**: “Stable Sort는 동등한 키를 가진 객체의 기존 순서를 보존하므로 다중 기준 정렬과 레코드 처리에서 중요합니다.”

### In-place Sort (제자리 정렬)

- **정의**: 입력 배열 내부에서 원소를 재배치하며 \(O(1)\) 또는 \(O(\log n)\) 수준의 추가 공간만 사용하는 정렬이다.
- **In-place 예시**: Bubble, Selection, Insertion, Heap, 일반적인 Quick.
- **Not In-place 예시**: 일반적인 Merge, Counting, Radix.
- **주의점**:
  - 재귀 호출 스택은 보조 공간에 포함한다.
  - “In-place”라고 해서 메모리를 전혀 사용하지 않는다는 뜻은 아니다.
  - Stable과 In-place는 서로 다른 속성이다.
- **면접 한 줄 정리**: “In-place는 추가 메모리를 적게 사용하는 특성이며, Stable 여부와는 독립적인 개념입니다.”

***

## 2. 대표 유형·복잡도·동작 비교

여기서 `n`은 원소 개수, `k`는 Counting Sort의 값 범위, `d`는 Radix Sort의 자릿수 개수이다. 최선은 가장 유리한 입력, 평균은 일반적인 입력, 최악은 가장 불리한 입력에서의 복잡도다.

| 알고리즘 | 핵심 아이디어 | 최선 | 평균 | 최악 | 공간복잡도 | Stable | In-place | 특징 및 활용 |
|---|---|---:|---:|---:|---:|---|---|---|
| Bubble | 인접 원소 교환 | \(O(n)\) | \(O(n^2)\) | \(O(n^2)\) | \(O(1)\) | 예 | 예 | 교육, 거의 정렬된 작은 데이터 |
| Selection | 최솟값 선택 후 교환 | \(O(n^2)\) | \(O(n^2)\) | \(O(n^2)\) | \(O(1)\) | 아니오 | 예 | 교환 횟수가 중요한 경우 |
| Insertion | 정렬 영역에 삽입 | \(O(n)\) | \(O(n^2)\) | \(O(n^2)\) | \(O(1)\) | 예 | 예 | 작은 배열, 거의 정렬된 데이터 |
| Merge | 분할 후 병합 | \(O(n\log n)\) | \(O(n\log n)\) | \(O(n\log n)\) | \(O(n)\) | 예 | 보통 아니오 | 안정성, 외부 정렬 |
| Quick | Pivot 기준 Partition | \(O(n\log n)\) | \(O(n\log n)\) | \(O(n^2)\) | 평균 \(O(\log n)\) | 아니오 | 예 | 평균 성능, 캐시 효율 |
| Heap | Heap에서 반복 삭제 | \(O(n\log n)\) | \(O(n\log n)\) | \(O(n\log n)\) | \(O(1)\) | 아니오 | 예 | 최악 보장, 메모리 제한 |
| Counting | 값별 빈도 계산 | \(O(n+k)\) | \(O(n+k)\) | \(O(n+k)\) | \(O(n+k)\) | 구현에 따라 | 아니오 | 작은 정수 범위 |
| Radix | 자릿수별 정렬 | \(O(d(n+b))\) | \(O(d(n+b))\) | \(O(d(n+b))\) | \(O(n+b)\) | 예 | 아니오 | 고정 길이 정수·문자열 |

비교 기반 정렬의 대표적인 하한은 \(Ω(n \log n)\)이다. 따라서 Counting·Radix Sort의 빠른 성능은 모든 데이터에 적용되는 것이 아니라, 값의 범위나 자릿수라는 추가 정보를 활용한 결과다. [MIT 6.006 Sorting Lecture](https://ocw.mit.edu/courses/6-006-introduction-to-algorithms-spring-2008/0c8bb24ef91668bfe85f1eaee80e72a0_lec11.pdf) [ocw.mit](https://ocw.mit.edu/courses/6-006-introduction-to-algorithms-spring-2008/0c8bb24ef91668bfe85f1eaee80e72a0_lec11.pdf)

## 3. 왜 중요한가?

### 실제 개발 및 시스템 관점

정렬은 단순히 데이터를 보기 좋게 배치하는 작업이 아니라 검색, 중복 제거, 순위 계산, 범위 질의, 병합 처리의 기반이 된다.

- 정렬 후 이진 탐색을 사용하면 검색을 \(O(n)\)에서 \(O(\log n)\)으로 줄일 수 있다.
- 데이터베이스의 `ORDER BY`, 인덱스 생성, 외부 정렬, 로그 분석에서 정렬이 사용된다.
- 추천 시스템에서는 점수·거리·우선순위에 따라 상위 결과를 정렬하거나 Top-K를 선택한다.
- 대용량 데이터에서는 \(O(n^2)\) 알고리즘이 서버 비용과 응답 시간을 급격히 증가시킨다.
- 메모리가 제한된 임베디드 환경에서는 Heap·Quick처럼 In-place인 알고리즘이 유리할 수 있다.
- 객체의 여러 필드를 정렬할 때는 Stable 여부가 결과의 정확성에 영향을 준다.

### 입력 크기 n이 커질 때

- \(O(n)\): 입력이 10배가 되면 연산량도 약 10배 증가한다.
- \(O(n \log n)\): 약 10배보다 조금 더 크게 증가한다.
- \(O(n^2)\): 입력이 10배가 되면 연산량이 약 100배 증가한다.
- Merge·Counting·Radix는 추가 메모리도 입력 크기에 따라 증가할 수 있다.
- Quick Sort는 평균적으로 빠르지만 최악의 재귀 깊이가 \(O(n)\)이 되면 스택 오버플로 가능성이 있다.
- 정렬 결과를 반복적으로 사용하는 시스템에서는 한 번의 정렬 비용을 지불하고 이후 검색 비용을 줄일 수 있다.

## 1. 개념 정리

### 객체 (Object) / 인스턴스 (Instance)

- **정의**: 객체는 상태 (필드) 와 행동 (메서드) 을 가진 실체이며, 클래스를 기반으로 메모리에 생성된 구체적인 존재입니다. [jaykim0510.github](https://jaykim0510.github.io/java-oop-series1)
- **핵심 포인트**:
  - 클래스는 설계도, 객체는 그 설계도로 만든 실제 제품
  - 객체는 힙 (Heap) 메모리에 생성되며, 참조 변수를 통해 접근
  - 하나의 클래스로 여러 객체 (인스턴스) 를 생성 가능
  - 객체 ≒ 인스턴스 (일반적으로 같은 의미로 사용)
- **관련 용어**: 인스턴스화 (Instantiation), 참조 변수 (Reference Variable), new 키워드
- **간단한 예시**:
  ```java
  class Car {
      String color;
      void drive() { System.out.println("Driving"); }
  }
  Car myCar = new Car(); // myCar 는 Car 클래스의 객체 (인스턴스)
  ```
- **복잡도**: 객체 생성은 일반적으로 O(1) (메모리 할당 및 초기화)
- **면접 한 줄 정리**: "객체는 클래스를 기반으로 메모리에 생성된 실체로, 상태와 행동을 함께 가집니다."

***

### 클래스 (Class)

- **정의**: 클래스는 객체를 생성하기 위한 설계도 또는 템플릿으로, 필드 (변수) 와 메서드 (함수) 를 정의합니다. [geeksforgeeks](https://www.geeksforgeeks.org/java/understanding-encapsulation-inheritance-polymorphism-abstraction-in-oops/)
- **핵심 포인트**:
  - 클래스 자체는 메모리에 존재하지 않음 (설계도일 뿐)
  - 필드는 객체의 상태, 메서드는 객체의 행동을 정의
  - 생성자 (Constructor) 를 통해 객체 초기화
  - 접근 제어자 (public, private, protected) 로 캡슐화 지원
- **관련 용어**: 필드 (Field), 메서드 (Method), 생성자 (Constructor), 접근 제어자 (Access Modifier)
- **간단한 예시**:
  ```java
  public class Person {
      private String name; // 필드
      public Person(String name) { this.name = name; } // 생성자
      public void greet() { System.out.println("Hello, " + name); } // 메서드
  }
  ```
- **복잡도**: 클래스 정의는 컴파일 타임, 객체 생성은 O(1)
- **면접 한 줄 정리**: "클래스는 객체를 생성하기 위한 설계도로, 필드와 메서드를 정의합니다."

***

### 캡슐화 (Encapsulation)

- **정의**: 캡슐화는 데이터 (필드) 와 이를 조작하는 메서드를 하나의 단위로 묶고, 외부에서 직접 접근을 제한하여 내부 구현을 숨기는 개념입니다. [geeksforgeeks](https://www.geeksforgeeks.org/java/understanding-encapsulation-inheritance-polymorphism-abstraction-in-oops/)
- **핵심 포인트**:
  - private 필드 + public Getter/Setter 메서드로 구현
  - 데이터 무결성 보장 (유효성 검증 가능)
  - 내부 구현 변경 시 외부 코드 영향 최소화
  - 정보 은닉 (Information Hiding) 과 밀접한 관계
- **관련 용어**: Getter, Setter, 접근 제어자 (Access Modifier), 정보 은닉
- **간단한 예시**:
  ```java
  public class Account {
      private int balance; // private 필드
      public int getBalance() { return balance; } // Getter
      public void deposit(int amount) {
          if (amount > 0) balance += amount; // 유효성 검증
      }
  }
  ```
- **복잡도**: Getter/Setter 호출은 O(1)
- **면접 한 줄 정리**: "캡슐화는 데이터를 private 으로 감싸고 Getter/Setter 로만 접근하게 하여 내부 구현을 숨기는 것입니다."

***

### 상속 (Inheritance)

- **정의**: 상속은 한 클래스 (자식) 가 다른 클래스 (부모) 의 필드와 메서드를 그대로 물려받아 재사용하는 메커니즘입니다. [geeksforgeeks](https://www.geeksforgeeks.org/java/understanding-encapsulation-inheritance-polymorphism-abstraction-in-oops/)
- **핵심 포인트**:
  - extends 키워드로 구현 (Java 는 단일 상속만 지원)
  - IS-A 관계 (예: Dog IS-A Animal)
  - 코드 재사용성 향상, 계층적 구조 표현
  - 오버라이딩 (Overriding) 을 통해 부모 메서드 재정의 가능
- **관련 용어**: 부모 클래스 (Superclass), 자식 클래스 (Subclass), extends, IS-A 관계
- **간단한 예시**:
  ```java
  class Animal { void eat() { System.out.println("Eating"); } }
  class Dog extends Animal { void bark() { System.out.println("Barking"); } }
  ```
- **복잡도**: 상속 자체는 컴파일 타임 개념, 런타임 오버헤드 미미
- **면접 한 줄 정리**: "상속은 자식 클래스가 부모 클래스의 필드와 메서드를 물려받아 코드 재사용성을 높이는 메커니즘입니다."

***

### 다형성 (Polymorphism)

- **정의**: 다형성은 하나의 인터페이스로 여러 형태의 객체를 처리할 수 있게 하며, 같은 메서드 호출이 객체 타입에 따라 다르게 동작하는 특성입니다. [geeksforgeeks](https://www.geeksforgeeks.org/java/understanding-encapsulation-inheritance-polymorphism-abstraction-in-oops/)
- **핵심 포인트**:
  - 오버라이딩 (런타임 다형성) 과 오버로딩 (컴파일 타임 다형성)
  - 업캐스팅 (Upcasting): 자식 객체를 부모 타입 참조 변수에 대입
  - 동적 바인딩 (Dynamic Binding): 런타임에 실제 객체 타입에 따라 메서드 결정
  - 인터페이스와 추상 클래스를 통한 다형성 구현
- **관련 용어**: 오버라이딩 (Overriding), 오버로딩 (Overloading), 업캐스팅, 동적 바인딩
- **간단한 예시**:
  ```java
  Animal a = new Dog(); // 업캐스팅
  a.eat(); // Dog 의 eat() 호출 (동적 바인딩)
  ```
- **복잡도**: 동적 바인딩은 O(1) (가상 메서드 테이블 참조)
- **면접 한 줄 정리**: "다형성은 같은 메서드 호출이 객체 타입에 따라 다르게 동작하며, 오버라이딩과 동적 바인딩으로 구현됩니다."

***

### 추상화 (Abstraction)

- **정의**: 추상화는 복잡한 내부 구현을 숨기고 필수적인 기능만 노출하여, 사용자가 '무엇을' 하는지에 집중하게 하는 개념입니다. [geeksforgeeks](https://www.geeksforgeeks.org/java/understanding-encapsulation-inheritance-polymorphism-abstraction-in-oops/)
- **핵심 포인트**:
  - abstract 클래스와 interface 로 구현
  - 구현 세부사항 숨김, 인터페이스만 공개
  - 캡슐화와 유사하지만, 캡슐화는 '데이터 보호', 추상화는 '기능 단순화'에 중점
  - 설계 단계에서 핵심 기능 식별에 유용
- **관련 용어**: abstract 클래스, interface, 구현 은닉
- **간단한 예시**:
  ```java
  abstract class Shape {
      abstract double area(); // 구현 없이 선언만
  }
  class Circle extends Shape {
      double area() { return Math.PI * r * r; }
  }
  ```
- **복잡도**: 추상 메서드 호출은 O(1) (실제 구현에 의존)
- **면접 한 줄 정리**: "추상화는 내부 구현을 숨기고 필수 기능만 노출하여, 사용자가 복잡성 없이 핵심 기능만 사용할 수 있게 합니다."

***

### 오버로딩 vs 오버라이딩

| 구분 | 오버로딩 (Overloading) | 오버라이딩 (Overriding) |
|---|---|---|
| **정의** | 같은 클래스 내에서 같은 이름, 다른 파라미터의 메서드 여러 개 정의 | 자식 클래스가 부모 클래스의 메서드를 재정의 |
| **발생 시점** | 컴파일 타임 (정적 바인딩) | 런타임 (동적 바인딩) |
| **파라미터** | 이름은 같지만, 파라미터 수/타입/순서 다름 | 이름, 파라미터, 반환 타입 동일 |
| **접근 제어자** | 제한 없음 | 부모 메서드보다 좁은 접근 제어자 사용 불가 |
| **사용 목적** | 편의성 (예: System.out.println()) | 다형성 구현, 부모 동작 재정의 |
| **예시** | `void print(int a)`, `void print(String s)` | `Dog.eat()` 가 `Animal.eat()` 재정의 |

- **면접 한 줄 정리**: "오버로딩은 같은 클래스 내에서 파라미터가 다른 같은 이름 메서드를, 오버라이딩은 자식 클래스가 부모 메서드를 재정의하는 것입니다."

***

### 인터페이스 vs 추상 클래스

| 구분 | 인터페이스 (Interface) | 추상 클래스 (Abstract Class) |
|---|---|---|
| **메서드 타입** | public abstract 메서드 (Java 8 부터 default, static 가능) | abstract 메서드 + 구체적 메서드 모두 가능 |
| **필드** | public static final 상수만 가능 | 일반 필드 가능 |
| **상속** | implements (다중 구현 가능) | extends (단일 상속만 가능) |
| **생성자** | 없음 | 있음 (자식 클래스에서 호출) |
| **사용 목적** | 완전한 추상화, 다중 상속 효과 | 부분적 추상화 + 공통 코드 재사용 |
| **예시** | `interface Flyable { void fly(); }` | `abstract class Animal { abstract void eat(); }` |

- **언제 사용하는가**:
  - **인터페이스**: 완전 다른 클래스들이 공통 동작을 공유할 때 (예: `Comparable`, `Runnable`)
  - **추상 클래스**: 공통 필드/메서드를 공유하는 계층적 관계일 때 (예: `Animal` → `Dog`, `Cat`)

***

### SOLID 원칙

| 원칙 | 정의 | 예시 |
|---|---|---|
| **SRP **(Single Responsibility Principle) | 한 클래스는 하나의 책임만 가져야 함 | `UserService` 는 사용자 관리만, `EmailService` 는 이메일 발송만 |
| **OCP **(Open-Closed Principle) | 확장에는 열려 있고, 수정에는 닫혀 있어야 함 | `Shape` 인터페이스에 `Circle`, `Rectangle` 추가 시 기존 코드 수정 없음 |
| **LSP **(Liskov Substitution Principle) | 자식 클래스는 부모 클래스를 대체할 수 있어야 함 | `Dog` 가 `Animal` 을 대체할 때 `eat()` 동작이 일관되어야 함 |
| **ISP **(Interface Segregation Principle) | 클라이언트는 사용하지 않는 인터페이스에 의존하지 않아야 함 | `Flyable`, `Swimmable` 분리하여 `Dog` 는 `Swimmable` 만 구현 |
| **DIP **(Dependency Inversion Principle) | 고수준 모듈은 저수준 모듈에 의존하지 않고, 추상화에 의존해야 함 | `UserService` 가 `MySQLRepository` 대신 `Repository` 인터페이스에 의존 |

- **면접 한 줄 정리**: "SOLID 는 유지보수성 높은 객체지향 설계를 위한 5 가지 원칙으로, SRP, OCP, LSP, ISP, DIP 를 포함합니다."

### 입력 크기 n 이 커질 때

OOP 는 알고리즘이 아니므로 '입력 크기 n'은 일반적으로 객체 수 또는 데이터 양을 의미합니다.

- **연산량**: 객체 수가 n 배 증가하면, 각 객체 연산이 O(1) 일 때 총 연산량은 O(n)
- **실행 시간**: 객체 생성 및 메서드 호출이 n 배 증가하면 선형적으로 증가
- **메모리 사용량**: 객체 수가 n 배 증가하면 힙 메모리 사용량도 O(n)
- **응답 시간**: 객체 간 의존성이 복잡해지면 간접 호출로 인해 지연 증가 가능
- **확장성**: 잘 설계된 OOP 는 n 증가에 따라 모듈 단위로 확장 가능
- **병목 발생 가능성**: 객체 풀 (Object Pool) 이 없으면 빈번한 GC 로 인한 병목 발생 가능

#### [자료구조 1/6] LinkedList

**구현 범위** — 단일 연결 리스트의 `add(index, e)` · `remove(index)` · `get(index)`. 이중 연결 리스트로 확장하면 무엇이 달라지는지도 함께 정리

```
struct NODE {
  int data;
  int* next;
}

struct NODE *head = malloc(sizeof(struct NODE));
struct NODE *tail = malloc(sizeof(struct NODE));

struct NODE *node1 = malloc(sizeof(struct NODE));
head->next = node1;
node1->data = 10;

struct NODE *node2 = malloc(sizeof(struct NODE));
node1->next = node2;
node2->data = 20;

struct NODE *node3 = malloc(sizeof(struct NODE));
node2->next = node3;
node3->data = 30;

# e가 데이터
add(index, e) {
    int *cur = head;
    struct NODE *node = malloc(sizeof(struct NODE));
    if (index==0) {
      node->next = head;
      node->data = e;
      head->next = node;
    } else {
      for (int i=0;i<index-1;i++) {
      cur = cur->next;
      node->next = cur->next;
      node->data = e;
      cur->next = node;
      }
    }
}

remove(index) {
  int *cur = head;
  if (index==0) {
    head = head->next;
  } else {
    for (int i=0;i<index-1;i++) {
      cur = cur->next;
    }
    cur->next = cur->next->next;
  }
}


get(index) {
  int *cur = head;
  for (int i=0;i<index;i++) {
    cur = cur->next;
  }
  return cur->data;
}
```
