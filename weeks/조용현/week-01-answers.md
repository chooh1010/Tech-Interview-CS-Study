## 1. 시간복잡도와 공간복잡도

> 예상 소요: 70초

입력 크기 `n`이 커질 때 **자원 사용량이 얼마나 빠르게 증가하는지**를 나타내는 지표입니다.

초 단위 실행 시간이 아니라 **증가율**을 봅니다. 그래서 CPU나 언어, 컴파일러와 무관하게 알고리즘 자체를 비교할 수 있습니다.

시간복잡도는 기본 연산 횟수의 증가율이고, 공간복잡도는 필요 메모리의 증가율입니다. 공간복잡도는 보통 **입력 자체를 제외한 추가 메모리**를 말합니다. 병합 정렬을 "공간 O(n)"이라고 부르는 게 그 의미입니다.

한 가지 덧붙이면, **Big-O는 "최악의 경우"라는 뜻이 아닙니다.** 케이스와 표기법은 서로 다른 축입니다.

- **케이스** — 최선/평균/최악. 어떤 **입력**을 볼 것인가
- **표기법** — O/Ω/Θ. 그 비용 함수를 어떤 **경계**로 묶을 것인가

그래서 최악의 경우를 정확히 표현하려면, 최악 입력에 대한 비용 함수를 먼저 정의하고 거기에 **Θ**를 붙입니다. `O`는 상한일 뿐이라 최선의 경우에도 붙일 수 있습니다.

마지막으로, **Big-O가 같아도 실제 성능은 다릅니다.** 상수 계수와 캐시 지역성 때문인데, 제 프로젝트에서 게스트 비밀번호 BCrypt cost를 10에서 8로 낮춘 게 그 사례입니다. 복잡도는 그대로고 상수만 4분의 1이 됐습니다.

> **유도되는 꼬리질문** — "amortized는 뭔가요?" / "그럼 O(1)이 O(n²)보다 항상 빠른가요?"

## 2. 링크드 리스트

> 예상 소요: 90초

각 노드가 **데이터와 다음 노드의 참조**를 갖고, 노드들이 사슬처럼 연결된 선형 자료구조입니다.

배열과의 결정적 차이는 **메모리 배치**입니다. 배열은 연속된 공간에 놓이니까 `arr[i]`를 주소 계산으로 바로 찾습니다. 그게 O(1) 무작위 접근이죠. 연결 리스트는 흩어져 있고 다음 주소만 아니까, **반드시 head부터 걸어가야** 합니다.

여기서 모든 성질이 나옵니다.

| | 배열 | 링크드 리스트 |
|---|---|---|
| 인덱스 접근 | **O(1)** | O(n) |
| 중간 삽입/삭제 | O(n) *(밀어내기)* | **O(1)** *(단, 노드를 알 때)* |
| 메모리 | 연속, 캐시 친화적 | 흩어짐, 노드당 참조 오버헤드 |

**"O(1) 삽입"에는 반드시 조건을 붙여야 합니다.** 삽입할 위치의 노드 참조를 **이미 알고 있을 때만** O(1)입니다. 인덱스로 지정하면 거기까지 걸어가는 O(n)이 먼저 들기 때문에 실제로는 O(n)입니다.

Java의 `ArrayList`는 동적 배열이라 둘의 중간에 있습니다. 꼬리 삽입이 **amortized O(1)**인데, 이건 "가끔만 복사해서"가 아니라 증명이 있습니다. 성장이 등비적이라 총 복사 비용이 최종 크기의 상수 배로 묶이거든요.

실무에서는 인덱스 접근이 필요하면 `ArrayList`, 양끝 연산만 하면 `ArrayDeque`를 씁니다. `LinkedList`는 캐시 지역성이 나빠서 실제로 쓸 일이 드뭅니다.

> **유도되는 꼬리질문** — "amortized 증명해보세요" / "정렬돼 있으면 이진 탐색이 되나요?"

**정렬돼 있어도 이진 탐색은 안 됩니다.** 비교 횟수는 O(log n)이지만 중간으로 이동하는 비용이 `n/2 + n/4 + …= Θ(n)`이라 선형 탐색과 같아집니다. 무작위 접근이 O(1)이 아니면 이진 탐색의 전제가 무너지는 겁니다.

## 3. 스택과 큐

> 예상 소요: 80초

둘 다 **원소를 넣고 빼는 순서를 제약한** 자료구조입니다.

- **스택** — LIFO. 나중에 넣은 게 먼저 나옵니다. `push` / `pop` / `peek`
- **큐** — FIFO. 먼저 넣은 게 먼저 나옵니다. `offer` / `poll` / `peek`

핵심 연산이 전부 **O(1)**이고, 그 대신 중간 접근을 포기한 구조입니다.

Java에서는 셋 다 **`ArrayDeque`** 하나로 해결합니다. `Stack`은 `Vector`를 상속해서 모든 메서드가 `synchronized`인 레거시라 안 쓰고, `LinkedList`도 `Queue`로 동작하지만 노드 할당 때문에 `ArrayDeque`가 빠릅니다. 다만 `ArrayDeque`는 **`null`을 저장할 수 없다**는 제약이 있습니다.

실무에서 스택은 **재귀 호출**이 대표적입니다. 제 프로젝트에서 대댓글 트리를 재귀로 조립하는데, 그게 쓰는 게 JVM 콜스택입니다. 그래서 댓글 깊이가 극단적으로 깊어지면 `StackOverflowError`가 날 수 있고, 대응은 명시적 스택을 쓴 반복 변환이나 깊이 제한입니다.

큐는 작업 대기열이나 BFS에 쓰이고, 우선순위가 붙으면 힙 기반 `PriorityQueue`가 됩니다.

> **유도되는 꼬리질문** — "스택 2개로 큐를 만들어보세요"

**입력용과 출력용 스택 두 개**를 둡니다. 넣을 땐 `in`에 쌓고, 뺄 때 `out`이 **비어 있으면** `in`을 전부 옮깁니다. 두 번 뒤집히니까 순서가 FIFO가 됩니다.

**"비어 있을 때만"이 핵심입니다.** 안 비었는데 옮기면 늦게 들어온 원소가 위에 얹혀서 **FIFO 순서 자체가 깨집니다.** 정확성 문제지 성능 문제가 아닙니다. 그리고 원소가 `out`에서 `in`으로 되돌아가지 않으니 원소당 연산이 4회로 고정돼서 **amortized O(1)**이 됩니다.

반대로 큐 2개로 스택은 매번 전체를 회전시켜야 하고, 그 작업이 다음 연산에 아무것도 남기지 않습니다. **amortized로도 O(n)**입니다.

## 4. 해시 자료구조

> 예상 소요: 100초

**키를 해시 함수로 정수에 대응시키고, 그 값으로 배열 인덱스를 계산해 상수 시간에 접근하는 구조**입니다.

본질은 **배열의 무작위 접근이 O(1)이라는 성질을 빌려 쓰는 것**입니다. 배열은 인덱스로만 O(1)인데, 해시 함수가 임의의 키를 인덱스로 바꿔주니 키로도 O(1)이 되는 거죠.

**다만 O(1)에는 조건이 붙습니다.**

- 조회와 삭제는 **기대(expected) O(1)**입니다. 보장이 아니고, 해시가 균등 분포하고 load factor가 상수로 억제된다는 전제가 필요합니다
- **최악은 O(n)** — 모든 키가 한 버킷에 몰리면 리스트 순회가 됩니다. 이걸 악의적으로 유도하는 게 Hash DoS 공격입니다
- 삽입은 리사이즈 때 재해싱이 O(n)이라 **분할상환**까지 함께 붙습니다

충돌 처리는 크게 두 계열입니다. **분리 연결법**은 버킷에 여러 개를 매다는 방식이고, **개방 주소법**은 다른 빈 버킷을 찾아가는 방식입니다. 개방 주소법이 메모리가 촘촘해 캐시에 유리한 대신 클러스터링 문제가 있습니다.

Java의 `HashMap`은 **분리 연결법에 트리화를 더한** 형태입니다. 한 버킷의 노드가 8개인 상태에서 하나 더 들어와 9개가 되면 **레드-블랙 트리로 변환**해서 최악을 O(n)에서 O(log n)으로 낮춥니다. 단 테이블 길이가 64 미만이면 트리화 대신 리사이즈를 합니다. 테이블이 작아서 몰린 것일 수도 있으니까요.

멀티스레드에서는 `Hashtable`이나 `synchronizedMap`이 map 단위로 직렬화돼서 병목입니다. `ConcurrentHashMap`은 **락 단위를 버킷 하나로 쪼갭니다.** 빈 버킷에 첫 노드를 넣을 땐 CAS로 락 없이 처리하고, 이미 노드가 있으면 그 **첫 노드를 monitor로** 잡습니다. 조회는 lock-free고요.

제 경험으로는, 엔티티의 `hashCode()`를 ID 기반으로 두면 persist 전후로 값이 바뀌어서 **`HashSet`에 넣어둔 객체를 다시 못 찾는** 문제가 생깁니다. 좋은 해시 함수의 조건 중 "안정성" 위반이죠. 그래서 JPA 엔티티는 해시 키로 쓸 때 주의해야 합니다.

> **유도되는 꼬리질문** — "충돌 적은 해시 함수는 어떻게 설계하나요?" / "Load Factor 정책은요?"

## 5. 트리와 이진트리, 이진탐색트리

> 예상 소요: 100초

**트리**는 연결되어 있고 **사이클이 없는 그래프**입니다. 노드가 n개면 간선은 정확히 n-1개고, 두 노드 사이의 경로가 정확히 하나입니다. 그래프의 특수한 경우라고 보면 됩니다.

**이진 트리**는 자식이 **최대 2개**인 트리입니다. "정확히 2개"가 아니라 최대입니다. 하위 분류로 Full, Complete, Perfect가 있는데, 특히 **Complete**는 마지막 레벨을 제외하고 꽉 차 있고 마지막은 왼쪽부터 채워진 형태입니다. 힙의 전제가 되는 개념입니다.

**이진 탐색 트리**는 여기에 순서 불변식이 붙습니다.

> 모든 노드에 대해 **왼쪽 서브트리 전체 < 노드 < 오른쪽 서브트리 전체**

"왼쪽 자식"이 아니라 **서브트리 전체**라는 게 중요합니다. 이 불변식 덕분에 **중위 순회를 하면 정렬된 순서로 나옵니다.**

검색·삽입·삭제가 모두 **O(h)**, 높이에 비례합니다. 비교할 때마다 후보가 절반씩 날아가니까 균형 잡혀 있으면 O(log n)입니다.

**검색만 빠른 게 아니라 삽입·삭제도 O(h)라는 점이 BST의 존재 이유입니다.** 정렬된 배열도 검색은 O(log n)인데 삽입·삭제가 O(n)이거든요. 밀어내야 하니까요. BST는 정렬 상태를 유지하면서 삽입·삭제까지 O(log n)으로 만든 구조입니다.

한계는 **편향**입니다. 정렬된 데이터를 순서대로 넣으면 한쪽으로 늘어져서 사실상 링크드 리스트가 되고, 그러면 O(n)이 됩니다. 단, 이건 **회전이나 재균형이 없는 일반 BST에 한정**된 이야기고, AVL이나 레드-블랙 트리는 그렇지 않습니다.

제 프로젝트의 대댓글 구조가 트리인데, BST가 아니라 일반 n-ary 트리입니다. MySQL Recursive CTE로 평평하게 뽑은 뒤 애플리케이션에서 조립하고, 정렬 순서는 ID를 zero-padding한 path 문자열로 표현했습니다.

> **유도되는 꼬리질문** — "그래프와 트리의 차이는?" / "삽입 시 편향은 어떻게 발생하나요?"

## 6. 힙

> 예상 소요: 90초

**힙 성질을 만족하는 Complete 이진 트리**입니다. 최대 힙이면 모든 노드에서 **부모가 두 자식보다 크거나 같습니다.**

**먼저 분명히 할 것은, 힙은 정렬된 구조가 아니라는 점입니다.** 이진 탐색 트리와 자주 혼동되는데 목적이 다릅니다.

| | BST | 힙 |
|---|---|---|
| 불변식 | 왼쪽 < 노드 < 오른쪽 | 부모 ≥ 자식 |
| 형제 간 순서 | 정해짐 | **관계 없음** |
| 임의 값 검색 | O(log n) | **O(n)** |

힙은 **부분 순서만 보장**합니다. 부모-자식 사이에만 대소 관계가 있고 **형제끼리는 아무 관계가 없습니다.** 그래서 특정 값을 찾으면 어느 쪽으로 갈지 결정할 근거가 없어서 O(n)입니다.

**힙이 존재하는 이유는 하나입니다 — 최댓값이나 최솟값만 빠르게 꺼내는 것.** 우선순위 큐를 구현하려고 만든 구조입니다.

두 조건이 각각 다른 일을 합니다. **힙 성질**은 루트가 항상 최댓값임을 보장하고, **Complete**는 배열로 표현 가능하게 만듭니다. 빈 칸이 없으니 포인터 없이 배열에 담기고, 0-based로 부모가 `(i-1)/2`, 자식이 `2i+1`과 `2i+2`입니다.

연산은 peek이 O(1), 삽입과 추출이 O(log n)입니다. 삽입은 배열 끝에 붙이고 위로 올리고, 추출은 루트와 마지막 원소를 바꾼 뒤 아래로 내립니다.

**BST와 달리 편향이 생기지 않는 이유는, 값이 삽입 위치를 결정하지 않기 때문입니다.** 무조건 배열의 다음 빈 칸에 넣으니까 값과 무관하게 Complete가 유지되고, 높이가 항상 `log n`입니다. 재균형 로직 자체가 필요 없죠. 대신 임의 검색 능력을 포기한 대가입니다.

한 가지 덧붙이면, 무작위 배열을 힙으로 만들 때 **바닥부터 sift-down 하는 방식은 O(n log n)이 아니라 O(n)**입니다. 노드의 절반은 잎이라 비용이 0이고, 비싼 노드가 극소수라서요.

> **유도되는 꼬리질문** — "힙 정렬은 stable한가요?" (아닙니다. 루트와 마지막을 스왑하면서 같은 값의 순서가 뒤집힙니다)

## 7. BBST (Balanced Binary Search Tree)

> 예상 소요: 100초

**삽입·삭제할 때마다 스스로 모양을 고쳐 높이를 O(log n)으로 강제하는 이진 탐색 트리**입니다.

일반 BST는 정렬된 입력이 오면 링크드 리스트로 무너져서 O(n)이 됩니다. BBST는 그 최악을 막아서 **검색·삽입·삭제가 평균이 아니라 최악에도 O(log n)**임을 보장합니다. 이 "최악 보장"이 존재 이유 전부입니다.

균형을 맞추는 도구는 **회전**입니다. 포인터 몇 개만 바꾸는 O(1) 연산인데, 중요한 건 **중위 순회 순서가 보존된다**는 점입니다. 그래서 BST 불변식을 깨지 않으면서 높이만 줄일 수 있습니다.

대표적으로 둘이 있습니다.

**AVL**은 모든 노드에서 좌우 서브트리 높이 차이를 `-1, 0, +1`로 유지합니다.

**레드-블랙 트리**는 다섯 가지 속성으로 균형을 유지합니다. 노드가 빨강 또는 검정이고, 루트와 잎(NIL)은 검정이며, **빨강 노드의 자식은 둘 다 검정**이라 빨강이 연속될 수 없고, **어떤 노드에서든 아래 NIL까지 검정 노드 개수가 같습니다.**

뒤의 두 속성이 함께 높이를 묶습니다. 검정 개수가 같으니 경로 길이가 비슷하고, 빨강이 연속 못 하니 최대 2배까지만 벌어집니다. 그래서 **높이가 `2·log₂(n+1)` 이하**입니다.

AVL이 더 엄격해서 조회가 조금 빠릅니다. 그런데 실무에서 레드-블랙이 더 많이 쓰이는데, **차이는 삭제에 있습니다.**

| | 삽입 | 삭제 |
|---|---|---|
| AVL | 최대 2회 회전 | **최악 O(log n) 회전** |
| 레드-블랙 | 최대 2회 회전 | **최대 3회** |

**삽입은 둘 다 상수 회전으로 같습니다.** AVL은 삭제 시 재균형이 루트까지 연쇄 전파될 수 있는데, 레드-블랙은 3회로 끝납니다. 쓰기가 섞인 범용 워크로드에서 최악 비용이 예측 가능하다는 게 결정적입니다. 조회 성능의 소폭 손해와 맞바꾼 거죠.

Java `TreeMap`과 `TreeSet`, C++ `std::map`, 그리고 `HashMap`의 트리화된 버킷이 전부 레드-블랙입니다.

참고로 **레드-블랙 트리는 2-3-4 트리의 이진 인코딩**이라 둘은 동형입니다. 그리고 DB 인덱스가 B+트리를 쓰는 건 점근적으로 더 좋아서가 아니라, **fanout이 높아서 트리 높이가 3~4로 낮아지고 디스크 I/O 횟수가 줄기** 때문입니다.

> **유도되는 꼬리질문** — "레드-블랙 속성 다시 말해보세요" / "왜 AVL 대신 RB인가요?"

## 8. 정렬 알고리즘

> 예상 소요: 120초

정렬은 **다섯 가지 축**으로 나눠 보면 정리가 됩니다. **비교 기반인가, 안정적인가, 제자리인가, 최악이 보장되는가, 적응적인가.**

먼저 **비교 기반은 최악에 Ω(n log n)보다 잘할 수 없습니다.** 입력 순열이 `n!`개라 결정 트리에 잎이 `n!`개 필요하고, 이진 트리의 높이가 최소 `log₂(n!)`인데 그게 `Θ(n log n)`이기 때문입니다.

주요 알고리즘은 이렇습니다.

| | 평균 | 최악 | 공간 | Stable |
|---|:--:|:--:|:--:|:--:|
| 삽입 | O(n²) | O(n²) | O(1) | ✓ |
| **병합** | O(n log n) | **O(n log n)** | O(n) | **✓** |
| **퀵** | O(n log n) | **O(n²)** | O(log n) | ✗ |
| **힙** | O(n log n) | **O(n log n)** | **O(1)** | ✗ |

**퀵과 병합을 같이 묶으면 안 됩니다.** 병합은 항상 O(n log n)이지만 퀵은 평균만 그렇고 **최악이 O(n²)**입니다. 이게 둘을 가르는 가장 중요한 차이입니다.

그럼에도 실무에서 퀵이 기본인 이유는 **파티셔닝이 배열을 순차적으로 훑어서 캐시 지역성이 좋고, 추가 메모리를 안 쓰기** 때문입니다. Big-O가 같아도 성능이 다른 전형적 사례죠.

퀵이 O(n²)이 되는 건 **피벗이 계속 극단값일 때**입니다. 첫 원소를 피벗으로 쓰는데 이미 정렬된 입력이 오면 매번 한쪽이 비니까요. 대책은 랜덤 피벗이나 median-of-three인데, **실무의 정답은 introsort**입니다. 재귀 깊이가 `2·log n`을 넘으면 힙 정렬로 전환해서, 퀵의 속도와 힙의 최악 보장을 둘 다 가져갑니다.

**안정성**은 같은 값의 원래 순서가 보존되는 건데, **다중 기준 정렬** 때문에 중요합니다. "부서별로 묶고 그 안에서 입사일순"을 하려면 입사일로 먼저 정렬한 뒤 부서로 정렬하면 되는데, 두 번째 정렬이 stable해야 첫 결과가 살아남습니다.

**적응성**도 짚을 만합니다. O(n²) 삼총사 중 삽입 정렬만 적응적이라 **거의 정렬된 입력에서 O(n)에 근접**합니다. 그래서 실무 라이브러리들이 작은 구간에서 삽입 정렬로 전환합니다. 반면 **선택 정렬은 입력이 어떻든 항상 `n(n-1)/2`번 비교**합니다.

Java는 **원시 타입과 객체를 다르게 처리합니다.** `int[]`는 Dual-Pivot Quicksort에 heapsort 폴백을 붙인 형태고, `Object[]`는 TimSort입니다. 이유는 **원시 타입은 identity가 없어서 안정성이 관측 불가능**하기 때문입니다. `int` 5와 다른 `int` 5는 구별할 수 없으니 stable할 필요가 없죠.

> **유도되는 꼬리질문** — "50GB를 4GB 메모리로 정렬한다면?"

**외부 병합 정렬**입니다. 메모리에 들어가는 크기로 잘라서 각각 정렬해 디스크에 정렬된 run으로 쓰고, 그다음 **최소 힙으로 k-way 병합**합니다. 병목이 CPU가 아니라 디스크 I/O라서 순차 읽기를 살리는 게 실제 튜닝 포인트입니다.

## 9. 객체지향 프로그래밍

> 예상 소요: 100초

**상태와 그 상태를 다루는 행위를 하나의 객체로 묶고, 객체들이 메시지를 주고받으며 협력하도록 프로그램을 구성하는 방식**입니다.

절차지향과 비교하면 명확해집니다. 절차지향은 **데이터와 그걸 처리하는 함수가 분리**돼 있습니다. 그래서 데이터 구조가 바뀌면 그걸 만지는 모든 함수를 찾아 고쳐야 하죠. OOP는 둘을 한 곳에 묶어서 **변경의 파급을 객체 경계 안에 가둡니다.** 이게 유지보수성이 좋다고 하는 이유의 실제 메커니즘입니다.

흔히 네 가지 축으로 정리합니다 — 캡슐화, 상속, 다형성, 추상화. 다만 이건 **교육적 관습이지 형식적으로 합의된 정의는 아닙니다.** Alan Kay가 OOP라는 말을 만들 때 강조한 건 **메시지 패싱과 캡슐화, 늦은 바인딩**이었고, 상속은 다형성을 구현하는 수단 중 하나일 뿐이라는 시각도 있습니다.

실무에서 가장 중요하게 보는 건 **캡슐화**인데, 여기에 흔한 오해가 있습니다. **필드를 `private`으로 막고 getter/setter를 1:1로 뚫으면 캡슐화가 아닙니다.** 내부 표현이 그대로 노출되니 `public` 필드와 실질적으로 같고, 이걸 빈약한 도메인 모델이라고 합니다.

진짜 캡슐화는 **데이터를 꺼내서 밖에서 처리하는 게 아니라, 객체에게 일을 시키는 형태**입니다. `post.setLikeCount(post.getLikeCount() + 1)`이 아니라 `post.increaseLikeCount()`처럼요.

그리고 **상속보다 합성을 권하는 이유**도 캡슐화와 연결됩니다. 상속하면 하위 클래스가 상위 클래스의 **구현 세부사항**에 의존하게 되는데, 상위가 내부적으로 자기 메서드를 호출하는지 여부까지 알아야 안전합니다. 그건 문서화되지 않은 부분이고 언제든 바뀔 수 있어서, 상위가 바뀌면 하위가 조용히 망가집니다. 합성은 인터페이스만 쓰니까 그 문제가 없고, 런타임에 교체도 가능합니다.

제 프로젝트에서는 서비스가 리포지토리 **인터페이스**에만 의존하고 구현체는 생성자 주입으로 받습니다. 의존성 역전이면서, 테스트에서 mock으로 바꿔 끼울 수 있다는 실질적 이득이 있습니다.

> **유도되는 꼬리질문** — "SOLID 설명해주세요" / "다형성이 실제 코드에서 어떻게 쓰이나요?" / "클래스가 있으면 객체지향 언어인가요?"

**마지막 질문의 답은 "아니다"입니다.** Java로도 `static` 메서드만 잔뜩 만들면 절차지향이고, JavaScript는 클래스 없이도 객체지향입니다. **클래스는 OOP의 필요조건도 충분조건도 아닙니다.**

## 자주 걸리는 함정 요약

말하다가 실수하기 쉬운 것들. 답변 전에 한 번 훑을 것.

| 함정 | 올바른 표현 |
|---|---|
| "Big-O는 최악의 경우" | 케이스와 표기법은 **직교**. 최악을 못 박으려면 Θ |
| "amortized는 평균" | **최악의 연산 순서에서도 성립하는 보장.** average는 입력 분포 기댓값 |
| "해시는 O(1)" | **기대** O(1). 균등 분포 + bounded load factor 전제. 최악 O(n) |
| "해시는 링크드 리스트에 저장" | 체이닝은 **구현 하나**. 개방 주소법도 있음 |
| "BST는 삽입·삭제가 느리다" | **삽입·삭제도 O(h).** 정렬 배열의 O(n) 삽입을 극복한 구조 |
| "힙은 정렬된 구조" | **부분 순서만 보장.** 형제 간 관계 없음, 임의 검색 O(n) |
| "AVL은 회전이 더 많다" | **삽입은 동일(최대 2회).** 차이는 삭제뿐 |
| "퀵과 병합 둘 다 O(n log n)" | 병합은 **항상**, 퀵은 **평균**. 퀵 최악은 O(n²) |
| "선택 정렬도 정렬된 입력엔 빠르다" | **적응적이지 않음.** 항상 `n(n-1)/2`회 비교 |
| "private + getter/setter = 캡슐화" | 1:1로 뚫으면 **내부 표현 노출**. 빈약한 도메인 모델 |
