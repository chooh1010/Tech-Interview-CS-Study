## 1. 시간복잡도와 공간복잡도 `★☆☆`

### 핵심 정의

입력 크기 `n`이 커질 때 **자원 사용량이 얼마나 빠르게 증가하는가**. 초 단위 실행시간이 아니라 **증가율**이다. 그래서 CPU·언어·컴파일러와 무관하게 알고리즘을 비교할 수 있다.

- **시간복잡도** — 기본 연산 횟수의 증가율
- **공간복잡도** — 필요 메모리의 증가율. 보통 입력 자체를 뺀 **추가 메모리(auxiliary space)**를 말한다. 병합 정렬을 "공간 O(n)"이라 할 때가 그 의미.

### 꼬리질문 ① Big-O / Big-Θ / Big-Ω

| 표기 | 의미 | 정의 |
|---|---|---|
| `O(g)` | **상한** | ∃c, n₀ : f(n) ≤ c·g(n) (n ≥ n₀) |
| `Ω(g)` | **하한** | ∃c, n₀ : f(n) ≥ c·g(n) |
| `Θ(g)` | **상한이자 하한** (tight) | O(g) ∧ Ω(g) |

**여기서 90%가 틀린다.** "Big-O는 최악의 경우"라고 답하면 그 자리에서 걸린다.

> **최선/평균/최악**은 *어떤 입력이냐*의 구분이고, **O/Ω/Θ**는 *함수를 어떻게 감싸느냐*의 구분이다. 둘은 직교한다.

그래서 이런 문장이 전부 성립한다.

- "퀵소트의 **평균** 시간복잡도는 **Θ(n log n)**"
- "퀵소트의 **최악** 시간복잡도는 **Θ(n²)**"
- "삽입 정렬의 **최선**은 **Ω(n)**"

그리고 `n²`짜리 알고리즘을 `O(n³)`이라 해도 **참**이다. 상한이니까. 느슨할 뿐 틀리지 않는다. Θ만이 유일하게 딱 맞는 표기.

### 꼬리질문 ② 왜 Big-O만 쓰나?

1. **실무 관심사가 보장(guarantee)이다.** "최악에도 이 이상은 안 걸린다"가 SLA를 설계할 때 필요한 정보. 하한은 별로 쓸모가 없다.
2. **Θ를 증명하려면 하한까지 증명해야 하는데** 알고리즘에 따라 어렵거나 아직 안 밝혀진 경우가 많다. 상한만 보이는 게 훨씬 쉽다.
3. **관례.** 실무에서 O라고 말할 때 대부분 tight bound(Θ)를 의도한다. 면접에서는 *"엄밀히는 Θ지만 관례상 O로 말합니다"* 한 마디를 덧붙이면 구분을 안다는 신호가 된다.

### 꼬리질문 ③ O(1)이 O(N²)보다 무조건 빠른가?

**아니오.** 이유는 셋.

**(a) 점근 표기는 n→∞ 기준이다.** 정의의 `n ≥ n₀` 조건이 핵심. n₀ 이전 구간은 아무것도 보장하지 않는다. n=10이면 `100n`보다 `n²`가 빠르다.

**(b) 숨은 상수가 다르다.** O(1)인데 상수가 1억일 수 있다.

**(c) 메모리 계층.** 연산 횟수가 같아도 캐시 미스가 나면 수십 배 느리다. Big-O 모델은 모든 메모리 접근을 1로 치는데, 실제 하드웨어는 L1과 RAM이 100배 차이난다.

#### 내 경험으로 답하기

**BCrypt 사례 (C08)**

> BCrypt 해싱은 입력 길이와 무관하게 **O(1)**이다. cost 8이든 10이든 복잡도 클래스는 똑같이 O(1). 그런데 jshell로 실측하니 strength 8은 61ms, 10은 103ms였고, 그 결과 게스트 댓글 작성이 1,248ms, 회원이 88ms로 **14배** 벌어졌다. 같은 O(1) 안에서 상수만 조정(cost 10→8)해서 전체 평균 322ms→156ms, P95 1,961ms→724ms로 줄였다.

> 📌 **단서**: "BCrypt는 O(1)"은 **cost를 상수로 고정했을 때** 성립한다. cost를 변수 `k`로 보면 내부 반복이 2^k회이므로 **Θ(2^k)**다. cost 10→8이 실측 103ms→61ms(약 1.7배)인 것도 2² = 4배가 아니라 다른 고정 비용이 섞여 있기 때문. 면접에서 "그럼 cost를 늘리면 O(1)이 아니지 않나요?"가 들어오면 이 구분으로 답한다.

→ *"복잡도가 같아도 상수가 응답시간을 지배할 수 있다"*의 실측 증거. 게다가 BCrypt의 그 상수는 **의도적으로 크게 만든 것**(brute-force 방어)이라, 보안-성능 트레이드오프 이야기까지 자연스럽게 이어진다.

**댓글 트리 사례 (C25)**

> 트리 조립을 3-pass에서 2-pass로 바꿨다. `buildTree` → `mergeLikeCounts` → `mergeReaction` 세 번 순회하던 걸 `enrichComments()` 한 번에 통합. **Big-O는 O(n)에서 O(n)으로 하나도 안 변했다.** 그런데 평균응답 169ms→122ms(-27.8%), **p99는 8~9초에서 300ms**로 떨어졌다. 순회 횟수 3→2와 임시 객체 300개 제거, 즉 상수 계수만 줄인 결과.

→ *"Big-O가 같으면 성능이 같은가?"*에 대한 정면 반례. p99가 27배 좋아진 건 GC 부담 감소분이 꼬리 지연에 집중됐기 때문.

**공간복잡도 쪽 (C19)**

> Caffeine 캐시에 `maximumSize`를 건 것 — 공간을 O(1)로 묶는 대신 히트율을 포기한 명시적 트레이드오프. 무제한 캐시는 공간 O(n)이고 `-Xmx240m` 컨테이너에서는 OOM으로 간다.

## 2. 링크드 리스트 `★☆☆`

### 핵심 정의

노드(데이터 + 다음 노드 **참조**)가 포인터로 이어진 구조. **메모리상 비연속**이 배열과의 근본 차이. 단일 / 이중 / 원형 연결 리스트가 있다.

### 꼬리질문 ① 배열 vs 링크드 리스트

| | 배열 | 링크드 리스트 |
|---|---|---|
| 인덱스 접근 | **O(1)** (주소 = base + i×size) | O(n) |
| 위치를 **아는** 삽입/삭제 | O(n) (뒤 원소 당기기) | **O(1)** |
| **인덱스로** 삽입/삭제 | O(n) | **O(n)** ← 함정 |
| 메모리 오버헤드 | 없음 | 노드마다 포인터 + 객체 헤더 |
| 캐시 지역성 | **좋음** | 나쁨 |
| 크기 | 고정 | 동적 |

**반드시 짚어야 할 함정**: *"링크드 리스트는 삽입/삭제가 O(1)"*은 **노드 참조를 이미 손에 쥐고 있을 때만** 참이다. `list.add(index, e)`는 탐색 O(n) + 연결 O(1) = **O(n)**. 이걸 그냥 O(1)이라고 답하면 바로 파고든다.

**메모리 숫자로 말하면 강해진다.** 64bit HotSpot + 압축 OOP 기준으로 `LinkedList.Node` 하나는

- 객체 헤더 **12B** (mark word 8B + 압축 klass 포인터 4B)
- 참조 3개(`item`, `next`, `prev`) × **4B** = 12B
- 합 24B, 8B 정렬에 이미 맞으므로 → **24B**

`ArrayList`는 원소당 참조 **4B**뿐이다. 100만 개면 **24MB vs 4MB**로 6배 차이. `-Xmx240m` 컨테이너에서는 무시할 수 없다.

> 압축 OOP가 꺼진 상태(힙 32GB 초과)라면 헤더 16B + 참조 8B×3 = **40B**가 된다. 숫자를 말할 땐 어느 전제인지 밝힐 것.

### 꼬리질문 ② 동적 배열(ArrayList)은?

내부는 그냥 **배열**. 꽉 차면 더 큰 배열을 새로 할당하고 복사한다.

- **Java 21 기준**: `grow()`가 `ArraysSupport.newLength(old, minGrowth, old >> 1)`을 호출하고, 이건 `old + max(minGrowth, old >> 1)`을 돌려준다. 즉 **"대략 1.5배"**지 정확히 1.5배가 아니다. 정수 내림 때문에 실제 용량 열은 **10 → 15 → 22 → 33 → 49 …** 로 간다.
- 기본 생성자는 lazy라서 첫 `add()` 때 `DEFAULT_CAPACITY = 10`으로 잡힌다.
- 개별 `add()`는 확장이 걸리면 O(n)이지만, **분할상환(amortized) O(1)**.

**amortized 증명 (집계 분석)**

증가 비율을 `r`(> 1)이라 하고 **마지막 확장부터 거꾸로** 더하는 게 요령이다.

> 최종 크기가 n일 때, 마지막 복사는 약 n번, 그 직전은 n/r, 그 전은 n/r² … 이다. 총 복사 비용은
>
> `n + n/r + n/r² + … = n · r/(r−1)`
>
> 이건 **비율이 1보다 작은 감소 등비급수**라 수렴한다. r=1.5면 3n, r=2면 2n. 어느 쪽이든 **O(n)**이고, 이걸 삽입 횟수 n으로 나누면 연산당 **O(1)**이다.

> ⚠️ "1, 1.5, 2.25 … 가 등비급수라 수렴한다"고 말하면 안 된다. **증가하는** 등비급수는 발산한다. 반드시 **최종 크기 n에서 역방향으로** 합쳐야 한다.

참고로 분할상환 분석에는 **집계(aggregate) · 회계(accounting) · 포텐셜(potential)** 세 기법이 있다. 위는 집계 분석이고, 뒤에 나올 "스택 2개 큐"는 회계 분석이다. *"amortized와 average의 차이는?"*도 자주 나오는데, **average는 입력 분포에 대한 기댓값**이고 **amortized는 최악 입력에서도 성립하는 연산당 평균 보장**이다. 후자가 더 강하다.

세 자료구조의 관계를 한 줄로: **ArrayList = 배열의 인덱스 접근 + 링크드 리스트의 동적 크기**, 대신 **꼬리 삽입만 amortized O(1)**이고 중간 삽입/삭제는 여전히 O(n).

다만 그 O(n)은 `System.arraycopy` — 메모리 블록 복사라 상수가 극단적으로 작다. 그래서 실무에서 n이 수천~수만이어도 `ArrayList`가 `LinkedList`보다 빠른 경우가 흔하다. **대부분의 경우 `ArrayList`가 기본값이고, 양끝 연산만 필요하면 `ArrayDeque`**다.

다만 *"LinkedList는 절대 쓰지 마라"*까지 단정하면 그것도 걸린다. 아직 유효한 자리가 있다.

- `ListIterator`로 **위치를 이미 확보한 뒤 반복 삽입/삭제**하는 경우 — 이땐 진짜 O(1)이다
- `List` 인터페이스가 필요하면서 `Deque`도 겸해야 할 때
- **`null` 원소를 담아야 할 때** — `ArrayDeque`는 `null`을 금지한다(`NullPointerException`)

#### 내 코드 연결 (C25)

> 댓글 트리에서 자식 목록을 `ArrayList`로 담고 있다. 근거: 자식은 **append만 하고 순회만** 한다. 중간 삽입이 없다. 반면 트리 조립은 전체 노드를 반복 순회하는 작업이라 **캐시 지역성이 지배적**이다. 실제로 3-pass 시절 임시 객체 300개 생성이 GC 부담으로 잡혔는데, 노드당 40B 오버헤드가 있는 `LinkedList`였다면 더 나빴을 것.

### 꼬리질문 ③④ 값으로 찾기 / 정렬되어 있다면?

- **정렬 안 됨**: 둘 다 순차 탐색 **O(n)**. 차이 없다.
- **정렬됨**:
  - 배열 → **이진 탐색 O(log n)**. 가능한 이유는 딱 하나, **랜덤 접근이 O(1)**이라서.
  - 링크드 리스트 → **여전히 O(n)**. 중간 지점으로 점프할 수 없다. 이진 탐색을 흉내내도 중간 노드를 찾는 데 O(n)이 들어서 전체가 O(n).

**심화 한 방**: *"그럼 링크드 리스트로는 O(log n) 탐색이 영영 불가능한가?"* → **Skip List**. 정렬된 연결 리스트에 확률적으로 상위 레벨 링크를 얹어 "건너뛰기 고속도로"를 만드는 구조다.

- **평균 O(log n)**, 다만 **최악은 O(n)**이다. 레벨을 동전 던지기로 정하는 **확률적** 자료구조라 보장이 아니라 기댓값이다. Red-Black Tree의 O(log n) *보장*과의 결정적 차이 — 이걸 빼먹으면 파고든다.
- Java의 `ConcurrentSkipListMap`이 이걸 쓴다. 균형 트리보다 락 없는 동시성 구현이 쉬워서 선호된다.
- Redis `ZSET`도 skip list를 쓰지만 **항상은 아니다.** 원소가 적으면 `listpack`(구버전 ziplist)으로 인코딩하고, `zset-max-listpack-entries` 등을 넘어서면 그때 **dict + skiplist** 조합으로 전환한다. "ZSET = skip list"라고만 답하면 반쪽이다.

### 꼬리질문 ⑤ 링크드 리스트로 구현 가능한 것

- Stack, Queue, **Deque**(이중 연결)
- **해시 테이블의 체이닝 버킷** — 단, Java 8부터 `HashMap`은 한 버킷의 노드가 **8개(`TREEIFY_THRESHOLD`)를 넘고 테이블 크기가 64(`MIN_TREEIFY_CAPACITY`) 이상**이면 그 버킷을 **red-black tree로 treeify**한다. "`HashMap` = 연결 리스트 체이닝"은 Java 7까지의 이야기다 (세션 1-B에서 상세히)
- **LRU 캐시 = HashMap + 이중 연결 리스트** — `LinkedHashMap(accessOrder=true)`이 순서 유지는 해주지만, **`removeEldestEntry()`를 재정의해야** 비로소 퇴출이 일어나는 LRU가 된다. 그리고 thread-safe가 아니다
- 그래프 **인접 리스트**
- 다항식, 임의 정밀도 큰 수

#### 내 코드 연결 (C19, C21)

> Caffeine에 `maximumSize`를 걸었을 때 뒤에서 도는 게 이 계열이다. 고전 LRU가 HashMap + 이중 연결 리스트고(해시로 O(1) 찾고, 리스트로 O(1) 재배치), Caffeine은 여기서 더 나아간 **W-TinyLFU**를 쓴다. "왜 캐시 자료구조가 해시맵 *하나*로는 안 되는가?" → 퇴출 순서를 O(1)에 갱신하려면 순서를 담는 연결 리스트가 별도로 필요하기 때문.

## 3. 스택과 큐 `★★☆`

### 핵심 정의

- **스택** — LIFO. `push`/`pop`/`peek` 모두 O(1)
- **큐** — FIFO. `offer`/`poll` 모두 O(1)

### 꼬리질문 ① 스택 2개로 큐, 큐 2개로 스택

**스택 2개 → 큐** (`in`, `out` 두 개)

```
enqueue(x): in.push(x)

dequeue():  if (out.isEmpty()) {
                while (!in.isEmpty()) out.push(in.pop());
            }
            return out.pop()
```

`in`을 통째로 `out`으로 옮기면 순서가 뒤집혀 FIFO가 된다.

**복잡도가 핵심.** 단일 `dequeue`는 **최악 O(n)**이다. 하지만 **amortized O(1)**.

> 증명: 모든 원소는 평생 `in.push → in.pop → out.push → out.pop` **정확히 4번**만 관여한다. n개 연산의 총 비용이 4n이므로 연산당 O(1).

> ⚠️ 그냥 "O(1)입니다"라고 답하면 *"단일 dequeue가 최악에 몇 번 걸리죠?"*로 바로 무너진다. **"최악 O(n), amortized O(1)"**로 답할 것.

**큐 2개 → 스택**

두 방식이 있고 **어느 쪽도 amortized O(1)이 안 된다.**

- **push를 비싸게**: 새 원소를 빈 큐에 넣고 기존 전부를 뒤에 붙임 → push **O(n)**, pop O(1)
- **pop을 비싸게**: push O(1), pop 때 n-1개를 옮기고 마지막 하나 반환 → pop **O(n)**

**이 비대칭성이 좋은 심화 답변이다.** 왜 한쪽만 amortized O(1)일까?

회계 분석으로 보면 명확하다.

> **스택 2개 큐**: 한 번 `out`으로 옮긴 원소는 **다시는 옮겨지지 않는다.** 원소당 이동 횟수가 **상수 4로 상한**이 잡히므로 n개 연산의 총 비용이 O(n)이고, 나누면 O(1)이다.
>
> **큐 2개 스택**: 큐에 남아 있는 원소는 **연산이 일어날 때마다 매번 다시 옮겨진다.** 원소당 이동 횟수에 상한이 없고, 크기 k인 상태에서 연산 하나가 항상 Θ(k)를 쓴다. n번 연산의 총 비용이 Θ(n²)라서 나눠도 Θ(n)이다. 상수로 상한이 잡히지 않으니 amortized O(1)이 원리적으로 불가능하다.

핵심 차이는 **"한 번 지불한 재배치 비용이 이후 연산에 재사용되는가"**다. 스택 2개는 재사용되고, 큐 2개는 매번 버려진다.

### 꼬리질문 ② 배열로 O(1) 유지하며 구현 가능?

- **스택**: 자명. `top` 인덱스 하나. 꽉 차면 2배 확장 → amortized O(1).
- **큐**: 단순 배열에 `front`를 0에 고정하면 `dequeue`마다 전체를 당겨야 해서 **O(n)**. 그래서 **원형 큐(circular buffer)**를 쓴다. `front`/`rear` 인덱스를 모듈러로 감아서 O(1).
  - *가득 참*과 *비어 있음*이 둘 다 `front == rear`가 되는 문제 → **한 칸 비워두기** 또는 **size 카운터 유지**로 해결.
  - Java `ArrayDeque`가 정확히 이것. **다만 내부 구현이 버전에 따라 다르다** — 아래 참고.

> ⚠️ **버전 함정 (Java 8 vs Java 21)**
>
> - **Java 8까지**: 용량을 항상 **2의 거듭제곱**으로 유지하고 `%` 대신 `& (elements.length - 1)`로 감았다. 흔히 인용되는 설명이 이것.
> - **Java 9~ (재작성 이후, Java 21 포함)**: 더 이상 2의 거듭제곱을 강제하지 않는다. 기본 생성자의 배열 길이는 **17**(= 16 + 1)이고, 인덱스는 비트마스크가 아니라 **분기**로 감는다.
>   ```java
>   static final int inc(int i, int modulus) { if (++i >= modulus) i = 0; return i; }
>   static final int dec(int i, int modulus) { if (--i < 0) i = modulus - 1; return i; }
>   ```
>
> 원형 버퍼의 **원리**를 묻는 거라면 모듈러/비트마스크로 설명해도 되지만, *"Java의 `ArrayDeque`는 어떻게 구현돼 있나요?"*라고 **버전을 특정해서** 물으면 위 구분을 해야 한다. 이 프로젝트는 Java 21이다.

### 꼬리질문 ③ Prefix / Infix / Postfix

| 표기 | 예 | 특징 |
|---|---|---|
| Infix | `A + B` | 사람이 읽는 식. 괄호·우선순위 필요 |
| Prefix | `+ A B` | 폴란드 표기법 |
| Postfix | `A B +` | 역폴란드(RPN). **괄호 불필요** |

**Postfix 계산** — 스택 하나면 된다. 피연산자는 push, 연산자를 만나면 2개 pop해서 계산 후 결과를 push. *먼저 pop한 값이 오른쪽 피연산자*라는 순서만 주의(`-`, `/`에서 갈림).

**Infix → Postfix (Shunting-yard)** — 피연산자는 바로 출력, 연산자는 스택에 넣되 조건에 맞으면 먼저 pop해서 출력. `(`는 push, `)`를 만나면 `(`가 나올 때까지 pop.

**여기서 결합법칙(associativity)을 빼먹으면 틀린 알고리즘이 된다.**

| 현재 연산자 | pop 조건 |
|---|---|
| **좌결합** (`+ - * /`) | 스택 top의 우선순위가 **현재 이상(≥)**이면 pop |
| **우결합** (`^`, 단항 `-`, 대입 `=`) | 스택 top의 우선순위가 **현재 초과(>)**일 때만 pop |

우결합인데 동순위에서 pop해버리면 `2^3^2`가 `(2^3)^2 = 64`로 잘못 계산된다. 정답은 `2^(3^2) = 512`다. 그냥 *"우선순위가 이상이면 pop"*이라고만 답하면 이 반례로 걸린다.

**왜 하필 스택인가**가 진짜 질문이다.

> 수식 평가는 *"가장 최근에 미뤄둔 연산을 가장 먼저 처리해야 한다"*는 성질을 갖는다. 괄호도 가장 안쪽(=가장 최근에 열린) 것부터 닫힌다. 이게 LIFO와 정확히 일치한다.

### 꼬리질문 ④ Deque 구현

- **이중 연결 리스트**: 양끝 O(1). 자명하지만 노드 오버헤드 + 캐시 지역성 나쁨
- **원형 배열**: 양끝 인덱스를 각각 이동. `ArrayDeque`

→ 거의 항상 `ArrayDeque`가 우세하다. **Java에서 스택이 필요하면 `Stack`(레거시, `Vector` 상속이라 전부 `synchronized`)도 `LinkedList`도 아닌 `ArrayDeque`**가 정답. 이것도 단골 꼬리질문.

> 단, `ArrayDeque`는 **`null` 원소를 허용하지 않는다.** `null`을 "비었음" 신호로 쓰기 때문. `null`을 담아야 하면 `LinkedList`를 써야 한다.

### 꼬리질문 ⑤ C++ deque의 O(1) random access

`std::deque`는 하나의 연속 배열이 **아니다**.

> **고정 크기 청크(블록) 여러 개 + 그 청크들의 포인터를 담은 중앙 map 배열** 구조다. 청크 크기가 상수 K로 고정이니, i번째 원소는 `map[(i + offset) / K][(i + offset) % K]`로 찾을 수 있다. 나눗셈·나머지 각 1회 = 상수 시간이므로 **O(1)**.

> 📌 정확히 하면, 표준이 강제하는 건 **"random access가 O(1), 양끝 삽입이 amortized O(1)"이라는 요구사항**이지 이 청크 구조 자체가 아니다. 다만 모든 주류 구현(libstdc++, libc++, MSVC)이 이 방식을 쓴다. *"표준이 이렇게 정한 건가요?"*라는 꼬리질문에 대비할 것.

이 구조 덕에 `push_front`도 새 청크만 할당하면 되고 기존 원소를 옮기지 않는다. 여기서 **꼭 구분해야 할 게 있다.**

> 양끝 삽입 시 **원소에 대한 포인터·참조는 유효하게 유지되지만, 이터레이터는 무효화된다.** (`vector`는 재할당 시 참조·이터레이터가 **둘 다** 전부 무효화.) map 배열이 재할당되면서 이터레이터가 들고 있는 내부 상태가 깨지기 때문이다.

대가는 접근할 때마다 **간접 참조가 2번**이라 `vector`보다 상수가 크다는 점.

### 내 프로젝트 연결

**커넥션 풀의 대기 큐 (C18, C24)**

> HikariCP 튜닝 때 로그에서 본 `waiting=21`, Read Pool의 `pending 최대 119`가 바로 **큐 길이**다. 커넥션을 못 받은 스레드가 FIFO로 대기하는 구조. 풀을 10→30으로 늘려 에러율 30.7%→0%, 평균응답 13,791ms→302ms가 된 건 **큐 대기 길이를 줄인 것**이다. 여기서 *"큐가 무한정 길어지면?"* → 타임아웃과 백프레셔 이야기로 넘어갈 수 있다.

**조회수 카운터의 자료구조 선택 (C23)**

> 30초 주기 flush는 전형적인 **생산자-소비자 버퍼링**이다. 그런데 큐가 아니라 `ConcurrentHashMap<Long, LongAdder>`를 썼다. **이 선택의 근거를 말할 수 있으면 좋은 답변**: 큐를 썼다면 조회 이벤트 100건이 원소 100개로 쌓이지만, Map은 키 1개에 카운트만 올라간다. 조회수는 **순서가 무의미하고 키별 합산만 필요**하니까. 실제로 30초간 100건 요청 시 UPDATE 100건→1건.

**재귀 트리 순회와 콜스택 (C25)**

> 댓글 트리 조립의 재귀가 쓰는 게 JVM 콜스택이다. *"댓글 깊이가 1만이면?"*이라는 꼬리질문에는 `StackOverflowError`와, 명시적 스택을 쓴 반복 변환 또는 깊이 제한으로 답할 수 있다.

## 모의면접 채점 (2026-08-11)

| 문항 | 평가 | 사유 |
|:--:|:--:|---|
| ① | △ | 순환 정의. 예시가 케이스 구분을 못 보여줌 |
| ② | ✗ | amortized를 average로 혼동 |
| ③ | ○ | 정확 |
| ④ | ○△ | 핵심 불변식은 짚었으나 회계 논증 부족 |
| ⑤ | ○ | 결론 맞음. 트레이드오프 언급 누락 |

**약점 패턴** — ①②가 같은 뿌리다. **케이스(어떤 입력) · 표기법(어떤 경계) · 상환(연산 순서 전체)이 서로 다른 축**이라는 게 아직 안 잡혔다.

### ① 최악의 경우는 뭘로 표현하나

2단계다.

1. **케이스를 고정해 비용 함수를 정의** — `W(n) = max{ T(x) : |x| = n }`
2. **그 함수에 O/Ω/Θ를 붙인다** — `W(n) = Θ(n)`

케이스와 표기법은 **직교**한다. 최악을 못 박으려면 **Θ**, "적어도 이만큼"은 **Ω**. `O`는 상한일 뿐이라 최선의 경우에도 붙일 수 있다("최선이 O(n²)"도 문법적으로 참, 느슨할 뿐).

**내가 든 예시의 문제** — "링크드 리스트의 마지막 값 반환"은 tail 포인터가 없으면 어떤 입력에도 항상 Θ(n)이다. best와 worst가 **Θ(n)으로 퇴화**해 같아져서 케이스 구분을 못 보여준다. (worst case가 *없는* 게 아니라 best와 *같은* 것이다.)

**좋은 예시** — 선형 탐색. 최선 Θ(1)(head에 있음) / 최악 Θ(n)(없거나 tail).

### ② ArrayList.add() amortized 증명

**amortized ≠ average**
- **average**: 입력 분포에 대한 기댓값. 운이 나쁘면 깨진다
- **amortized**: **최악의 연산 순서에서도** 성립하는 연산당 평균 비용의 **보장**. 운과 무관하다

"가끔만 복사하니 평균 O(1)"은 증명이 아니라 관찰이다.

**증명 (역방향 합)** — n번 append가 끝난 시점에서 복사 비용을 뒤에서부터 더한다. 성장 배수 g에 대해 마지막 복사 ≈ n, 그 전 n/g, 그 전 n/g²…

```
총 복사 비용 ≤ n + n/g + n/g² + … < n · 1/(1 - 1/g)
```

g = 1.5이면 `1/(1-2/3) = 3` → **총 복사 비용 < 3n**. n번에 총 O(n)이므로 **연산당 O(1)**.

주의 3가지:
- **3n은 상한이지 정확한 값이 아니다.** "정확히 3n 복사"라고 하면 틀림
- 역방향 합을 쓰는 이유는 "정방향이 발산해서"가 **아니다**. 유한합 `1+g+…+g^k`도 `Θ(g^k)=Θ(n)`으로 똑같이 나온다. 최종 크기 n을 기준점으로 잡아 계산이 깔끔한 것뿐
- **1.5배는 OpenJDK 구현 세부사항**(`oldCapacity + (oldCapacity >> 1)`). Java 명세가 보장하는 건 "amortized constant time"뿐, 특정 성장 배수가 아니다
- 꼬리 삽입 한정. `add(index, e)`는 여전히 O(n)

### ③ 정렬된 링크드 리스트 이진 탐색

**비교 횟수는 여전히 O(log n)**이다. 깨지는 건 **중간으로 이동하는 비용** — `n/2 + n/4 + n/8 + … = Θ(n)`. 결국 선형 탐색과 점근적으로 같아진다.

한 줄 요약: **무작위 접근이 O(1)이 아니면 이진 탐색의 전제가 무너진다.**

### ④ 큐 2개 스택이 amortized로도 안 되는 이유

스택 2개 큐가 되는 결정적 이유는 **원소가 out → in으로 절대 되돌아가지 않는다**는 불변식이다. 원소 하나의 일생 동안 스택 연산이 최대 4회로 **고정**된다. 그래서 비싼 연산(out으로 통째 이동)이 **미래를 위한 저축**이 된다.

큐 2개 스택은 매 연산마다 기존 k개를 회전시키는데 **그 작업이 다음 연산에 아무것도 남기지 않는다.** 저축이 없으니 상환할 것도 없다.

**정밀한 표현** (면접에서 차이가 큼):
- ✗ "n번 연산하면 항상 Θ(n²)"
- ○ "**총비용이 Θ(n²)이 되는 연산 순서가 존재한다.** 따라서 amortized Θ(n)"

또한 "큐 2개로는 O(1)이 **불가능함이 증명됐다**"고 단정하면 안 된다. 표준 두 변형(costly-push / costly-pop)에서 안 알려져 있다는 것이지, 모든 구현에 대한 불가능성 증명이 아니다.

### ⑤ BCrypt cost 10 → 8

시간복잡도가 아니라 **상수 계수**를 낮춘 것. 정확히 `2¹⁰/2⁸ = 4배`.

- **"O(1)"에 조건이 붙는다.** cost를 **고정 상수로 볼 때만** 입력 크기 기준 O(1)이다. cost를 파라미터 c로 보면 **Θ(2^c) — c에 대해 지수적**
- cost c는 **2^c번의 outer round** 수를 정하고, 각 round마다 password/salt에 대해 ExpandKey를 2회씩 호출한다. "2^c번의 key expansion"은 부정확한 표현
- **반드시 트레이드오프를 먼저 말할 것** — 무차별 대입 저항력도 똑같이 **4배 하락**했다. BCrypt의 cost는 "느린 게 기능"인 파라미터라, 낮추는 건 최적화가 아니라 **보안 예산과 성능의 교환**이다. 이 말을 빼면 "벤치마크만 보고 보안을 모른다"로 읽힌다
- 실제 설계 근거를 붙일 것: **회원 인증은 cost 10 유지, 게스트만 8**. 보호 자산의 가치가 다르기 때문

## 이번 세션 필수 암기 포인트

| # | 포인트 |
|---|---|
| 1 | Big-O ≠ 최악의 경우. 최선/평균/최악 × O/Ω/Θ는 **직교** |
| 2 | `ArrayList.add()` = 꼬리 삽입만 **amortized** O(1). 중간은 O(n). 증명은 **최종 크기 n에서 역방향 합** |
| 3 | amortized ≠ average. average는 입력 분포 기댓값, **amortized는 최악 입력에서도 성립하는 연산당 보장** |
| 4 | 링크드 리스트의 O(1) 삽입 = **노드 참조를 이미 알 때만**. 인덱스 삽입은 O(n) |
| 5 | `LinkedList.Node` = **24B**(압축 OOP: 헤더 12B + 참조 4B×3) vs `ArrayList` 원소당 4B |
| 6 | 정렬된 링크드 리스트에 이진 탐색 불가 → **Skip List** (평균 O(log n), **최악 O(n)**) |
| 7 | 스택 2개 큐 = 최악 O(n), **amortized O(1)** / 큐 2개 스택 = 매번 Θ(k), amortized로도 불가 |
| 8 | Java에서 스택·큐·덱이 필요하면 **`ArrayDeque`** — 단 `null` 금지 |
| 9 | **`ArrayDeque`는 Java 9부터 2의 거듭제곱이 아니다.** 기본 길이 17, 분기로 감음 (2의 거듭제곱 + 비트마스크는 Java 8 이야기) |
| 10 | `HashMap` 체이닝은 Java 8+에서 **treeify**된다 (버킷 8개 초과 & 테이블 64 이상) |
| 11 | Shunting-yard에서 **우결합 연산자는 동순위에 pop하면 안 된다** (`2^3^2` 반례) |
| 12 | Big-O가 같아도 성능은 다르다 — 상수 계수, 캐시 지역성 (내 사례: BCrypt, 3-pass→2-pass) |
| 13 | 최악의 경우 표현법 = **케이스 고정**(`W(n) = max T(x)`) **후 O/Ω/Θ**. 못 박으려면 Θ |
| 14 | 두 스택 큐의 핵심 불변식 = **out → in으로 되돌아가지 않음**. 비싼 연산이 **저축**이 되어야 amortize가 성립 |
| 15 | "항상 Θ(n²)"이 아니라 "**총비용 Θ(n²)인 연산 순서가 존재**". amortized는 최악 순서 기준 |

## 정정 이력 (Codex 검증)

### 2026-08-11 추가 정정

| 초안 | 정정 |
|---|---|
| "증가 등비급수는 **발산**하므로 역방향 합이 필요하다" | **틀림.** 유한합 `1+g+…+g^k`는 발산할 수 없다(무한급수와 유한 부분합 혼동). 역방향 합은 정확성 때문이 아니라 **최종 크기 n을 기준점으로 잡아 계산이 깔끔해서** 쓴다 |
| ArrayList 총 복사 비용 = 3n | **상한이다.** `< n/(1-1/g) = 3n` (g=1.5). 정확한 값이 아님 |
| BCrypt cost c = "2^c번의 key expansion" | **2^c번의 outer round**이며 각 round마다 password/salt에 ExpandKey를 2회씩 호출 |
| 링크드 리스트 마지막 값 반환 = 최악의 경우 예시 | best = worst = Θ(n)으로 **퇴화**한 사례. 케이스 구분을 못 보여줌 |

### 2026-08-09

초안 작성 후 Codex(gpt-5.6-sol)로 15개 기술 주장을 팩트체크한 결과.

**틀렸던 것 (2건)**

| 초안 | 정정 |
|---|---|
| `LinkedList.Node` ≈ **40B** (압축 OOP) | **24B**. 헤더 12B + 참조 4B×3. 40B는 압축 OOP가 *꺼진* 경우 |
| `ArrayDeque`는 2의 거듭제곱 용량 + `& (capacity-1)` | **Java 8까지의 이야기.** Java 9 재작성 이후(21 포함) 기본 길이 17, 분기 기반 `inc()/dec()` |

**부정확해서 보강한 것 (7건)** — ArrayList 성장식(정확히 1.5배 아님) · amortized 증명(역방향 합, 상한 3n) · "LinkedList 절대 쓰지 마라"(과장) · Skip List 최악 O(n) 및 Redis ZSET listpack 인코딩 · Shunting-yard 결합법칙 · `std::deque` 이터레이터/참조 무효화 구분 · `LinkedHashMap` LRU는 `removeEldestEntry()` 필요

**추가한 것 (3건)** — `HashMap` treeify · amortized vs average 구분 · BCrypt O(1)은 cost 고정 시에만

**검증 통과 (5건)** — O/Ω/Θ 직교성 · n²을 O(n³)이라 해도 참 · 두 스택 큐의 4회 회계 분석 · postfix에서 먼저 pop한 값이 우피연산자 · Caffeine W-TinyLFU / 고전 LRU 구조
