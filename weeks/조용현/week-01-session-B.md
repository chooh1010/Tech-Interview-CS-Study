## 4. 해시 자료구조 `★★☆`

### 핵심 정의

**키를 해시 함수로 정수(해시값)에 대응시키고, 그 값으로 배열 인덱스를 계산해 O(1)에 접근하는 구조.**

```
key ──[해시 함수]──> 해시값 ──[인덱스 계산]──> 버킷 배열[i]
"user42"            0x8A3F...            (n-1) & hash → 7
```

본질은 **"배열의 무작위 접근이 O(1)"이라는 성질을 빌려 쓰는 것**이다. 배열은 인덱스로만 O(1)인데, 해시 함수가 임의의 키를 인덱스로 변환해주니 키로도 O(1)이 된다.

> **웜업에서 틀린 점** — "링크드 리스트에 저장"은 충돌 처리 방식 중 하나(체이닝)일 뿐이다. 오픈 어드레싱으로 구현하면 링크드 리스트가 아예 등장하지 않는다. **구현을 정의로 말하면 안 된다.**

### 시간복잡도 — 조건을 반드시 붙일 것

| 연산 | 평균(기대) | 최악 |
|---|:--:|:--:|
| 조회 | **기대 O(1)** | O(n) |
| 삭제 | **기대 O(1)** | O(n) |
| 삽입 | **기대 + 분할상환 O(1)** | O(n) |

세 가지를 정확히 구분한다.

- **"기대(expected) O(1)"**이지 보장이 아니다. **해시가 균등 분포하고 load factor가 상수로 억제된다**는 전제 위에서만 성립
- **최악은 O(n)** — 모든 키가 한 버킷에 몰리면 리스트 순회. 악의적 입력으로 이를 유도하는 것이 **Hash DoS**
- **삽입만 "분할상환"이 추가로 붙는다** — 리사이즈(재해싱) 순간이 O(n)이기 때문. 세션 1-A의 `ArrayList` amortized 논리가 그대로 재사용된다

### 좋은 해시 함수의 조건

| 조건 | 설명 |
|---|---|
| **균등 분포** | 버킷에 고르게 흩어져야 함. 가장 중요 |
| **속도** | 조회마다 호출된다. 느리면 O(1)의 상수가 커짐 |
| **`equals`와의 일관성** | `a.equals(b)` → `a.hashCode() == b.hashCode()` **필수** |
| **안정성** | 키가 저장돼 있는 동안 해시값이 변하면 안 됨 |

**Avalanche 효과**(1비트 변화 → 출력 절반 반전)는 있으면 좋지만 **해시 테이블의 필수 조건은 아니다.** 암호학적 강도는 오히려 느려서 해롭다.

#### 내 코드 연결

`User.hashCode()`를 `Objects.hashCode(id)`로 두면 persist 전후 id가 `null` → `1`로 바뀌면서 **HashSet에 넣어둔 객체를 다시 못 찾는다.** 이것이 정확히 위 표의 **"안정성" 조건 위반**이다. (수정안: `User.class.hashCode()` 상수 — `getClass()`는 프록시 클래스라 사용 불가)

→ 가변 객체를 해시 키로 쓰지 말 것. JPA 엔티티는 특히 위험하다.

### 충돌 처리

대표적인 두 계열 (이것이 전부는 아니다 — Cuckoo, Hopscotch 등도 있음).

**(1) 분리 연결법 (Separate Chaining)** — 한 버킷에 여러 개를 리스트/트리로 매단다. 구현이 단순하고 load factor가 1을 넘어도 동작. 단 포인터 추적이라 캐시 지역성이 나쁘다.

**(2) 개방 주소법 (Open Addressing)** — 충돌 시 다른 빈 버킷을 찾아간다. 배열 하나로 끝나 메모리가 촘촘하고 캐시에 유리.

| 방식 | 탐사식 | 특성 |
|---|---|---|
| Linear probing | `h+1, h+2, …` | **Primary clustering**. 대신 **캐시 지역성은 보통 가장 좋음** |
| Quadratic probing | `h+1², h+2², …` | **Secondary clustering** — 시작 버킷이 같으면 탐사 경로도 동일 |
| Double hashing | `h₁ + i·h₂(key)` | 클러스터링을 **크게 줄임**(제거는 아님). 2차 해시 비용 + 캐시 불리 |

Double hashing은 **스텝이 테이블 크기와 서로소**여야 모든 칸을 방문한다. 테이블 크기를 소수로 잡거나, 2의 거듭제곱이면 스텝을 홀수로 강제한다.

> **주의** — "개방 주소법 삭제에는 항상 tombstone이 필요하다"는 **틀렸다.** tombstone이 흔하긴 하지만 backward-shift deletion처럼 실제로 원소를 당겨오는 방식도 있다. 다만 **그냥 지우면 탐사 사슬이 끊어져 뒤의 값을 못 찾는다**는 문제 자체는 맞다.

### Java의 HashMap (Java 21)

**분리 연결법 + 트리화.**

```java
static final int hash(Object key) {
    int h;
    return (key == null) ? 0 : (h = key.hashCode()) ^ (h >>> 16);
}
```

**왜 `^ (h >>> 16)`인가?** 버킷 인덱스가 `(n - 1) & hash`인데 `n`이 2의 거듭제곱이라 **하위 비트만 쓰인다.** 상위 16비트의 엔트로피가 통째로 버려지므로, XOR로 상위 비트를 하위에 섞어 내린다.

**트리화(treeify)** — 버킷이 길어지면 **레드-블랙 트리로 변환**해 최악을 O(n) → **O(log n)**으로.

- `TREEIFY_THRESHOLD = 8` — 정확히는 **노드 8개인 bin에 새 키가 추가돼 9개가 되는 순간** `treeifyBin()` 호출
- **단, 테이블 길이가 `MIN_TREEIFY_CAPACITY = 64` 미만이면 트리화 대신 리사이즈.** 테이블이 작아서 몰린 것일 수 있으므로
- `UNTREEIFY_THRESHOLD = 6` — 주로 **리사이즈 중 split된 bin**에 적용

**Load factor** — 기본 용량 16, load factor 0.75, `++size > threshold`면 약 2배 리사이즈.

- **배열은 첫 삽입 전까지 지연 할당된다.** `new HashMap<>()`만으로는 배열이 생기지 않음
- 0.75의 **Poisson 분포 정당화는 class Javadoc이 아니라 내부 구현 주석**에 있다 (면접에서 출처를 잘못 대지 말 것)

### 멀티스레드

| 방식 | 동작 | 문제 |
|---|---|---|
| `Hashtable` / `synchronizedMap` | 개별 연산이 **map 단위 monitor로 직렬화** | 스레드 수만큼 병목 |
| `ConcurrentHashMap` (Java 8+) | 아래 참조 | — |

`ConcurrentHashMap`의 실제 동작:

- **빈 bin에 첫 노드 삽입** = 락 없이 **CAS**
- **비어있지 않은 bin에 쓰기** = 그 bin의 **첫 노드를 monitor로 잡음.** 경합 시에만이 아니라 **항상**
- **조회는 lock-free** — `volatile` 읽기만
- Java 7의 **Segment(lock striping) 구조는 제거됨.** 단 `concurrencyLevel` 생성자 인자는 초기 sizing 힌트로 아직 살아있어 "완전히 죽은 유물"은 아님

핵심은 **락 단위를 map 전체 → 버킷 하나로 쪼갠 것.**

## 5. 트리와 이진트리, 이진탐색트리 `★★☆`

### 핵심 정의 — 트리

**연결되어 있고 사이클이 없는 그래프.** 노드가 n개면 **간선은 정확히 n-1개**.

**트리는 그래프의 특수한 경우**다. 이것이 "그래프와 트리의 차이" 질문의 답 뼈대.

| | 그래프 | 트리 |
|---|---|---|
| 사이클 | 있을 수 있음 | **없음** |
| 두 노드 간 경로 | 0개 ~ 여러 개 | **정확히 1개** |
| 루트 | 개념 없음 | 있음 (루트 트리) |
| 간선 수 | 자유 | **n-1** |

용어: **깊이(depth)** = 루트부터 그 노드까지 / **높이(height)** = 그 노드부터 가장 깊은 잎까지.

### 이진 트리

**자식이 최대 2개**인 트리. ("2개로 제한"이 아니라 **최대** 2개 — 0개, 1개도 이진 트리다.)

| 종류 | 조건 |
|---|---|
| Full | 모든 노드가 자식 0개 또는 2개 |
| **Complete** | 마지막 레벨 빼고 꽉 참 + 마지막 레벨은 **왼쪽부터** 채워짐 |
| Perfect | 모든 잎의 깊이가 같고 완전히 꽉 참 |

**Complete는 반드시 기억.** 6번 힙의 전제다.

### 이진 탐색 트리 (BST)

**불변식: 모든 노드에 대해 `왼쪽 서브트리 전체 < 노드 < 오른쪽 서브트리 전체`**

"왼쪽 **자식** < 부모"가 아니라 **서브트리 전체**라는 것이 포인트. 여기를 틀리면 트리가 깨진다.

**중위 순회(in-order)를 하면 정렬된 순서로 나온다.** 이것이 BST 불변식의 직접적 귀결이고, "정렬된 구조"라는 말의 정확한 의미다.

> 정확히는 — **중복을 허용하지 않는 엄격한 불변식**에서만 strictly increasing. 중복 허용 시 nondecreasing, comparator 사용 시 그 comparator의 순서.

### 시간복잡도 — 웜업에서 틀린 지점

**BST의 삽입·삭제도 검색과 똑같이 O(h)다.** 균형 잡혀 있으면 셋 다 O(log n).

"삽입·삭제가 느리다"는 **정렬된 배열**과 혼동한 것이다. 정렬된 배열은 검색 O(log n)인데 삽입·삭제가 O(n)(밀어내야 하므로)이다. **BST는 바로 그 문제를 풀려고 만든 구조** — "정렬 상태를 유지하면서 삽입·삭제도 O(log n)으로."

| 구조 | 검색 | 삽입/삭제 |
|---|:--:|:--:|
| 정렬된 배열 | O(log n) | **O(n)** |
| 링크드 리스트 | O(n) | O(1) *(노드를 알 때)* |
| **BST (균형)** | **O(log n)** | **O(log n)** |

한 번 비교할 때마다 후보가 절반씩 날아가므로 O(h)가 나온다.

### 한계 — 편향(skew)

**정렬된 데이터를 순서대로 삽입하면 한쪽으로 늘어져 링크드 리스트가 된다.** 그러면 O(h) = **O(n)**.

```
1, 2, 3, 4, 5 순서로 삽입 →   1
                              \
                               2
                                \
                                 3 ...
```

> **전제를 반드시 붙일 것** — 이는 **회전(rotation)이나 재균형이 없는 일반 BST에 한정**된다. AVL이나 레드-블랙 트리는 정렬된 입력에도 편향되지 않는다. 이 전제를 빼면 7번(BBST)에서 자기모순이 된다.

### 삭제 3가지 경우

| 경우 | 처리 |
|---|---|
| 잎 | 그냥 제거 |
| 자식 1개 | 자식을 그 자리로 끌어올림 |
| 자식 2개 | **중위 후속자**(오른쪽 서브트리의 최좌단) 또는 중위 선행자로 값을 대체하고, 그 노드를 재귀적으로 삭제 |

자식 2개가 핵심. 중위 후속자는 **"오른쪽 서브트리에서 가장 작은 값"**이라 불변식이 유지되고, 그 노드는 왼쪽 자식이 없으므로 반드시 앞의 두 경우로 환원된다.

#### 내 코드 연결

`Comment`의 대댓글 구조가 트리다. 단 BST가 아니라 **일반 트리(n-ary)**. MySQL Recursive CTE로 flat하게 뽑은 뒤 `CommentService.buildCommentTree`에서 조립하고, `LPAD(id, 10, '0')` path로 정렬한다.

→ "트리 순서를 DB에서 표현하는 실무적 방법"으로 설명할 수 있다. 페이징 때문에 부모가 누락되면 루트에 배치하는 fallback이 있다는 점도 함께.

## 6. 힙 `★★☆`

### 힙은 정렬된 구조가 아니다

웜업에서 "이진탐색트리와 같이 정렬된 것"이라 답했는데 **틀렸다.** 목적도 불변식도 다르다.

| | BST | 힙 |
|---|---|---|
| 불변식 | 왼쪽 < 노드 < 오른쪽 | **부모 ≥ 두 자식** (최대 힙) |
| 형제 간 순서 | 정해짐 | **아무 관계 없음** |
| 순회하면 | 중위 순회 → **정렬됨** | 어떻게 순회해도 **정렬 안 됨** |
| 잘하는 것 | 임의 키 검색 O(log n) | **최댓값/최솟값 O(1)** |
| 임의 값 검색 | O(log n) | **O(n)** |
| 모양 | 자유 (편향 가능) | **Complete 강제** |

**힙은 "부분 순서(partial order)"만 보장한다.** 부모-자식 사이에만 대소 관계가 있고 **형제끼리는 아무 관계가 없다.** 왼쪽 자식이 오른쪽 자식보다 클 수도 작을 수도 있다.

그래서 힙에서 특정 값을 찾으면 **O(n)**이다. 어느 쪽으로 갈지 결정할 근거가 없어 전부 뒤져야 한다. **이것이 BST와의 결정적 차이.**

**힙이 존재하는 이유는 딱 하나 — "최댓값/최솟값만 빠르게".** 우선순위 큐를 구현하려고 만든 구조다.

### 핵심 정의

**힙 성질을 만족하는 Complete 이진 트리.** 두 조건이 각각 다른 일을 한다.

- **힙 성질** (부모 ≥ 자식) → 루트가 항상 최댓값임을 보장
- **Complete** → **배열로 표현 가능**하게 만듦

### 배열 표현

Complete라 빈 칸이 없으니 **포인터 없이 배열에 그대로 담긴다.**

```
        9              배열: [9, 7, 6, 3, 5, 2]
      /   \                   0  1  2  3  4  5
     7     6
    / \   /
   3   5 2
```

| | 0-based | 1-based |
|---|---|---|
| 부모 | `(i-1)/2` | `i/2` |
| 왼쪽 자식 | `2i+1` | `2i` |
| 오른쪽 자식 | `2i+2` | `2i+1` |

포인터가 없어 메모리를 아끼고, 배열이라 캐시 지역성도 좋다.

### 연산

| 연산 | 방법 | 복잡도 |
|---|---|:--:|
| peek | `arr[0]` | **O(1)** |
| insert | 배열 **끝에 추가** → **sift-up** | O(log n) |
| extract-max | 루트와 **마지막 원소 스왑** → 크기 축소 → **sift-down** | O(log n) |

extract-max에서 마지막 원소를 루트로 올리는 이유는 **Complete를 깨지 않으려면 지울 수 있는 칸이 마지막뿐**이기 때문이다.

### 왜 BST와 달리 편향이 없는가

**삽입 위치를 값이 결정하지 않기 때문.**

BST는 값이 작으면 왼쪽, 크면 오른쪽 — **값이 모양을 결정**한다. 그래서 정렬 입력에 쏠린다.

힙은 **무조건 배열의 다음 빈 칸**에 넣는다. 값과 무관하게 구조적으로 Complete가 유지되고, 값은 sift-up으로 **위아래로만** 움직일 뿐 모양을 바꾸지 않는다.

**따라서 힙의 높이는 삽입 순서와 무관하게 항상 `⌊log₂ n⌋`이다.** 재균형 로직이 아예 필요 없다 — BBST가 회전으로 힘들게 얻는 것을 힙은 공짜로 얻는다. 대신 **임의 검색 능력을 포기**한 대가다.

### Heapify는 O(n)

무작위 배열을 힙으로 만들 때 하나씩 insert하면 O(n log n)이지만, **바닥부터 sift-down하는 방식(Floyd)은 O(n)**이다.

**직관** — 노드의 절반은 잎이라 sift-down 비용이 0이고, 비용이 log n인 노드는 루트 하나뿐이다. **비싼 노드가 압도적으로 적다.**

```
∑ (n / 2^(h+1)) · h  →  수렴해서 O(n)
```

"heapify는 O(n)"은 자주 나오는 함정 질문.

### Heap sort

**O(n log n) 최악 보장 + in-place + 불안정(unstable)**

- 힙 구성 O(n) + n번 extract O(log n) = **O(n log n)**
- 추가 메모리 O(1)
- **Stable하지 않다** — 루트와 마지막 원소를 스왑하는 과정에서 같은 값의 상대 순서가 뒤집힌다
- 최악이 O(n log n)으로 **보장**되는 것이 퀵소트(최악 O(n²)) 대비 강점

> 실측에서는 퀵소트보다 느린 경우가 많다 — 배열 전체를 넓게 점프해 캐시 지역성이 나쁘고, 부분 정렬된 입력에 적응하지 못한다. **다만 이는 경향이지 정리(theorem)가 아니다.** 구현·피벗 전략·자료형·캐시에 따라 달라진다.

### Java의 PriorityQueue

- **배열 기반 이진 최소 힙**
- 같은 우선순위끼리 **순서 보장 없음(unstable)** — 필요하면 삽입 순번을 tiebreaker로
- 크기 제한 없이 자동 확장
- **`iterator()`가 우선순위 순으로 주지 않는다.** 배열 순서 그대로이므로 정렬해서 꺼내려면 `poll()`을 반복해야 한다. 실무 버그 단골

## 이번 세션 필수 암기 포인트

| # | 포인트 |
|:--:|---|
| 1 | 해시의 O(1)은 **기대값**이지 보장이 아니다. **최악 O(n)**, 삽입은 재해싱 때문에 **분할상환**도 함께 붙는다 |
| 2 | 체이닝은 충돌 처리 **한 가지**일 뿐. 정의에 넣지 말 것 |
| 3 | 좋은 해시 함수 = 균등 분포 · 속도 · **`equals` 일관성** · **안정성**. avalanche는 필수 아님 |
| 4 | `HashMap` 트리화 = bin이 **9개가 되는 순간** + 테이블 길이 **64 이상**. 미만이면 리사이즈 |
| 5 | `hash()`의 `^ (h >>> 16)` = 인덱스가 `(n-1) & hash`라 **하위 비트만 쓰이므로** 상위 엔트로피를 섞어 내림 |
| 6 | `ConcurrentHashMap` = 빈 bin은 **CAS**, 아니면 **첫 노드 monitor(항상)**. 조회 lock-free. Segment 제거됨 |
| 7 | 개방 주소법 삭제에 **tombstone이 항상 필요한 건 아니다** (backward-shift deletion) |
| 8 | 트리 = **연결된 비순환 그래프**, 간선 **n-1**개, 두 노드 간 경로 **정확히 1개** |
| 9 | **BST의 삽입·삭제도 O(h)**. 정렬 배열의 O(n) 삽입을 극복하려고 만든 구조 |
| 10 | BST 불변식은 "왼쪽 자식"이 아니라 **왼쪽 서브트리 전체** |
| 11 | 정렬 입력 → 편향은 **회전 없는 일반 BST 한정**. AVL/RB에는 해당 없음 |
| 12 | BST 삭제 자식 2개 → **중위 후속자**(오른쪽 서브트리 최좌단)로 대체 |
| 13 | **힙 ≠ 정렬된 구조.** 부분 순서만 보장, 형제 간 관계 없음, **임의 검색 O(n)** |
| 14 | 힙이 편향 없는 이유 = **값이 삽입 위치를 결정하지 않음**. 높이 항상 `⌊log₂ n⌋` |
| 15 | **Heapify는 O(n)**, heap sort는 O(n log n) · in-place · **unstable** |
| 16 | `PriorityQueue.iterator()`는 **우선순위 순이 아니다** |

## 정정 이력 (Codex 검증, 2026-08-11)

강의 **전에** Codex(gpt-5.6-sol)로 20개 주장을 사전 팩트체크했다. 세션 1-A의 교훈("강의 후 검증하면 이미 틀린 채로 전달됨")을 반영한 것.

**틀렸던 것 (1건)**

| 초안 | 정정 |
|---|---|
| 개방 주소법 삭제에는 **항상 tombstone이 필요**하다 | **틀림.** backward-shift deletion 등 대안 존재. 다만 그냥 지우면 탐사 사슬이 끊긴다는 문제 자체는 맞음 |

**부정확해서 보강한 것 (11건)**

| 항목 | 정정 |
|---|---|
| 해시 O(1) | 조회·삭제는 **기대** O(1), 삽입은 **기대 + 분할상환**. "기대"와 "분할상환"은 배타적이지 않음 |
| 좋은 해시 함수 | **avalanche는 필수 아님.** 필수는 균등 분포·속도·`equals` 일관성·안정성. 결정성도 보통 "한 실행 내"에서만 필요 |
| 충돌 처리 분류 | 체이닝/오픈어드레싱은 **대표 두 계열**일 뿐 완전한 분류가 아님. "double hashing이 항상 최악의 locality"는 과한 단정 |
| treeify 트리거 | 조건은 맞으나, 정확히는 **8개 bin에 새 키가 붙어 9개가 되는 순간**. `UNTREEIFY=6`은 주로 **resize 중 split된 bin**에 적용 |
| load factor | 배열은 **첫 삽입까지 지연 할당**. Poisson 정당화는 **class Javadoc이 아니라 내부 구현 주석** |
| `ConcurrentHashMap` | 비어있지 않은 bin은 **경합 여부와 무관하게 항상** 첫 노드 monitor 사용 ("contended writes에서만"은 오해 소지 큼). `concurrencyLevel`은 여전히 sizing hint로 살아있음 |
| `Hashtable`/`synchronizedMap` | "map 전체를 락"보다 **"개별 연산이 map-level monitor로 직렬화"**가 정확 |
| BST 중위 순회 | **중복 없는 엄격 invariant에서만** strictly increasing. 중복 허용 시 nondecreasing |
| BST 편향 | **회전/재균형 없는 일반 BST 한정**이라는 전제 필요 |
| 삼진 탐색 트리 | 실재하는 자료구조. 2-key/3-child 노드는 2-3 트리의 **3-node 형태**일 뿐이고, 불균형 multiway tree도 정확성은 유지됨(self-balancing은 O(log n) 보장에만 필요) |
| heap sort vs quicksort | "quicksort보다 느리다"는 **실측 경향이지 정리가 아님** |

**검증 통과 (8건)** — `hash()`의 `^ (h>>>16)` 설명 · 트리 정의와 n-1 간선 · BST 삭제 3케이스 · 힙 Complete/배열 표현 · 부모/자식 인덱스 식 · sift-up/sift-down · 힙 무편향 근거 · Floyd heapify O(n) · `PriorityQueue` 특성
