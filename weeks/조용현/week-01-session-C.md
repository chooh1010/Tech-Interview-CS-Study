## 7. BBST — 균형 이진 탐색 트리 `★★★`

### 왜 필요한가

5번에서 배운 문제. **일반 BST는 정렬된 입력이 들어오면 링크드 리스트로 무너져 O(n)이 된다.** BBST는 **삽입·삭제할 때마다 스스로 모양을 고쳐 높이를 O(log n)으로 강제**하는 BST다.

결과: 검색·삽입·삭제가 **평균이 아니라 최악에도 O(log n)**. 이 "최악 보장"이 BBST의 존재 이유 전부다.

### 회전(rotation) — 모든 BBST의 공통 도구

```
    y            회전            x
   / \        ─────────▶        / \
  x   C       (우회전)          A   y
 / \                               / \
A   B                             B   C
```

두 성질이 핵심이다.

- **O(1)** — 포인터 몇 개만 바꾸는 국소 연산
- **중위 순회 순서가 보존됨** — 회전 전후 모두 `A, x, B, y, C`

두 번째가 결정적이다. **BST 불변식을 깨지 않으면서 높이만 줄일 수 있다**는 뜻이므로 모든 BBST가 회전을 쓴다.

### AVL 트리

**균형 인수(balance factor) = 왼쪽 높이 − 오른쪽 높이를 모든 노드에서 `{-1, 0, +1}`로 유지.**

벗어나면 즉시 회전으로 교정. 네 경우(LL, RR, LR, RL)가 있고 LL/RR은 단일 회전, LR/RL은 이중 회전.

### 레드-블랙 트리 — 5가지 속성

면접 단골. 그대로 외울 것.

1. 모든 노드는 **빨강 또는 검정**
2. **루트는 검정**
3. 모든 **잎(NIL 센티넬)은 검정**
4. **빨강 노드의 자식은 둘 다 검정** (빨강 연속 불가)
5. 임의의 노드에서 그 아래 모든 NIL까지의 경로에 **검정 노드 개수가 같다** (black-height 동일)

**4와 5가 함께 높이를 묶는다.** 5번이 "검정만 세면 모든 경로가 같은 길이"를 보장하고, 4번이 "빨강을 끼워도 연속은 못 하니 최대 2배까지만"을 보장한다.

따라서 **가장 긴 경로 ≤ 가장 짧은 경로의 2배**, 높이 **≤ 2·log₂(n+1)**.

### AVL vs 레드-블랙

AVL이 **더 엄격**하게 균형을 잡는다. AVL 높이 상한 ≈ 1.44·log₂n, RB ≈ 2·log₂n. 그래서 **AVL이 조회가 조금 더 빠르다.**

회전 횟수는 다음과 같다.

| | 삽입 | 삭제 |
|---|:--:|:--:|
| **AVL** | 최대 2회 = **O(1)** | 최악 **Θ(log n)** |
| **레드-블랙** | 최대 2회 = **O(1)** | 최대 3회 = **O(1)** |

**삽입에서는 차이가 없다.** "AVL은 삽입도 회전이 많다"는 흔한 오해.

**차이는 삭제에서만.** AVL은 삭제 후 재균형이 루트까지 **연쇄 전파**될 수 있어 조상마다 회전이 걸린다. RB는 **최대 3회로 끝난다.**

> "이중 회전을 1회로 세는" 교재는 AVL 삽입을 "최대 1회"로 쓰기도 한다. 회전 카운팅 관례 차이.

### 왜 레드-블랙이 더 많이 쓰이나

**삭제 시 회전 상한이 상수(3회)라는 점**이 실무의 핵심 근거다. 쓰기가 섞인 범용 워크로드에서 최악 비용의 예측 가능성이 좋다. 조회 성능의 소폭 손해를 쓰기 안정성과 맞바꾼 것.

> **정확히 말하기** — "RB는 구조 변경이 amortized O(1)이라 낫다"는 **회전과 재색칠을 혼동한 것**이다. 회전은 이미 **최악 O(1)**(삽입 2회 / 삭제 3회)이라 amortized 분석이 필요 없다. amortized가 의미 있는 대상은 **재색칠(recoloring)** — 삽입 한 번에 재색칠이 루트까지 O(log n)번 전파될 수 있으나, 삽입 시퀀스 전체로는 **amortized O(1)**이다 (이진 카운터 증가와 유사한 potential function 분석, CLRS 연습문제).

**실제 사용처**: Java `TreeMap`/`TreeSet`, C++ `std::map`/`std::set`, `HashMap`의 트리화된 bin, Linux CFS 스케줄러(과거).

### 2-3-4 트리와 B-트리

**레드-블랙 트리는 2-3-4 트리의 이진 인코딩이다.** 둘은 동형(isomorphic). 검정 노드에 빨강 자식이 붙은 형태가 2-3-4 트리의 3-노드·4-노드에 대응한다. "빨강 = 부모와 같은 층에 눌러 붙은 것"으로 보면 된다.

**B-트리 / B+트리**가 DB 인덱스에 쓰이는 이유는 점근적 우월성이 **아니다.** 노드 하나에 키를 수백 개 담는 **높은 fanout** 덕분에 **트리 높이가 3~4로 낮아져 디스크 I/O 횟수가 줄기** 때문이다.

#### 내 코드 연결

MySQL InnoDB의 모든 인덱스가 **B+트리**다. `post`, `comment`, `likes`의 PK와 인덱스 전부.

→ "인덱스 타면 왜 빨라지나요?"의 답: 풀스캔 O(n)이 트리 탐색 O(log n)이 되고, 그 log의 밑이 **수백**이라 실질적으로 3~4번의 디스크 접근으로 끝난다.

## 8. 정렬 알고리즘 `★★☆`

### 답변 프레임 — 축부터 세우기

"정렬 설명해주세요"에는 **먼저 축을 선언**하고 들어간다.

> "정렬은 다섯 축으로 나눠 볼 수 있습니다. **비교 기반인가 / 안정적인가 / 제자리인가 / 최악이 보장되는가 / 적응적인가.** 이 축으로 보면…"

이 한 문장이 나열형 답변과 구조적 답변을 가른다.

| 축 | 질문 | 왜 중요한가 |
|---|---|---|
| **비교 기반인가** | Ω(n log n) 하한을 받는가 | counting/radix가 왜 O(n)인지 설명하는 유일한 근거 |
| **안정성(stable)** | 같은 값의 원래 순서가 보존되는가 | 다중 기준 정렬에 직결 |
| **제자리(in-place)** | 추가 메모리 O(1)인가 | 병합 vs 퀵의 실제 선택 기준 |
| **최악 보장** | 평균만 좋은가, 최악도 보장되는가 | 퀵과 힙/병합을 가르는 지점 |
| **적응성(adaptive)** | 부분 정렬된 입력에 빨라지는가 | TimSort와 삽입 정렬의 존재 이유 |

### 축 0 — 비교 기반의 하한

**비교로만 정렬하면 최악에 Ω(n log n)보다 잘할 수 없다.**

**결정 트리 논증**: 입력 순열이 `n!`개이므로 결정 트리에 잎이 `n!`개 필요하다. 이진 결정 트리의 높이는 최소 `log₂(n!)`이고, 스털링 근사로 `log₂(n!) = Θ(n log n)`. 높이 = 최악의 비교 횟수.

**counting sort와 radix sort가 O(n)인 이유는 비교를 안 하기 때문이다.** 하한을 깬 것이 아니라 **적용 대상이 아닌 것.** 이 구분을 정확히 말하면 점수가 크다.

### 전체 비교표

| 알고리즘 | 평균 | 최악 | 공간 | Stable | Adaptive |
|---|:--:|:--:|:--:|:--:|:--:|
| 버블 | O(n²) | O(n²) | O(1) | ✓ | ✓ *(플래그 시)* |
| 선택 | O(n²) | O(n²) | O(1) | **✗** | **✗** |
| 삽입 | O(n²) | O(n²) | O(1) | ✓ | **✓** |
| **병합** | O(n log n) | **O(n log n)** | **O(n)** | **✓** | ✗ |
| **퀵** | O(n log n) | **O(n²)** | O(log n) | ✗ | ✗ |
| **힙** | O(n log n) | **O(n log n)** | **O(1)** | ✗ | ✗ |
| TimSort | O(n log n) | O(n log n) | O(n) | ✓ | **✓** |
| Counting | O(n+k) | O(n+k) | O(k) | ✓ | — |
| Radix | O(d(n+k)) | O(d(n+k)) | O(n+k) | ✓ | — |

### 퀵 vs 병합

| | 퀵 | 병합 |
|---|---|---|
| 최악 | **O(n²)** | **O(n log n) 보장** |
| 공간 | O(log n) 스택 | **O(n) 추가 배열** |
| Stable | ✗ | **✓** |
| 실측 속도 | **보통 더 빠름** | 상수 큼 |
| 강점 | 캐시 지역성, 제자리 | 최악 보장, 안정성, **외부 정렬·병렬화 용이** |

퀵이 실측에서 빠른 이유는 **파티셔닝이 배열을 순차적으로 훑어 캐시에 친화적**이고 추가 메모리 할당이 없기 때문이다. Big-O가 같아도 성능이 다른 전형적 사례 — 세션 1-A 암기 포인트 12번.

> **"퀵은 in-place O(log n) 스택"에는 조건이 붙는다.** **두 파티션 중 작은 쪽을 먼저 재귀하고 큰 쪽은 반복문으로 처리**해야 O(log n)이 보장된다. 순진하게 항상 왼쪽부터 재귀하면 최악에 스택 깊이가 **O(n)**까지 간다.

### 퀵이 O(n²)이 되는 경우와 대책

**피벗이 계속 극단값**일 때. 첫/마지막 원소를 피벗으로 쓰는데 **이미 정렬된 입력**이 오면 매번 한쪽이 0개, 다른 쪽이 n-1개로 갈려 재귀 깊이가 n이 된다.

| 대책 | 효과 |
|---|---|
| 랜덤 피벗 | 기대 O(n log n). 적대적 입력 방어 |
| Median-of-three | 실무적으로 매우 효과적, 보장은 아님 |
| Median-of-medians | **O(n log n) 보장.** 상수가 커서 실전엔 잘 안 씀 |
| **Introsort** | 재귀 깊이가 `2·log n`을 넘으면 **힙 정렬로 전환**. 보장 + 실전 속도 |

Introsort가 실무의 정답 — 퀵의 속도와 힙의 최악 보장을 둘 다 가져간다.

### Stable — 왜 중요한가

**같은 값의 원래 순서가 보존되는 것.**

실무에서 결정적인 이유는 **다중 기준 정렬**이다. "부서별로 묶고 그 안에서 입사일순"을 하려면 **입사일로 먼저 정렬 → 부서로 정렬**하면 되는데, 두 번째 정렬이 stable해야 첫 번째 결과가 살아남는다.

**선택 정렬이 unstable한 이유**: 최솟값을 찾아 현재 위치와 **통째로 스왑**하는데, 그 스왑이 사이에 있던 같은 값의 순서를 넘어뜨린다.

```
[3a, 3b, 1]  →  1과 3a를 스왑  →  [1, 3b, 3a]
                                      3b가 3a보다 앞으로 갔다 ✗
```

### Adaptive — 부분 정렬된 입력

**삽입 정렬이 O(n²) 삼총사 중 실전에서 압도적으로 나은 이유.**

- **삽입 정렬**: `O(n + 역전쌍 수)`. 거의 정렬돼 있으면 **O(n)에 근접.** 실무 라이브러리들이 작은 구간에서 삽입 정렬로 전환하는 이유
- **버블 정렬**: 조기 종료 플래그를 넣으면 이미 정렬된 입력에 **O(n)**
- **선택 정렬**: **적응적이지 않다.** 입력이 어떻든 **항상 정확히 `n(n-1)/2`번 비교**한다. 대신 **스왑은 O(n)회로 가장 적어서**, 원소 이동 비용이 극단적으로 비쌀 때만 의미가 있다

### Java의 실제 구현 (JDK 21)

"본인 언어는 뭘 쓰나요"가 반드시 나온다. 분기가 생각보다 세분화돼 있다.

| 대상 | 알고리즘 |
|---|---|
| `int[]`, `long[]`, `double[]` | **Dual-Pivot Quicksort** + 작은 구간 insertion sort + 거의 정렬된 입력엔 run-merging + **재귀가 깊어지면 heapsort 폴백** |
| `byte[]` | **DPQ를 안 씀.** 작으면 insertion, 크면 **counting sort** (값이 256종뿐) |
| `short[]`, `char[]` | 길이 > 1750이면 **counting sort**, 아니면 DPQ 계열 |
| `Object[]` (자연 순서) | **`ComparableTimSort`** |
| `Object[]` (comparator) | **`TimSort`** |

**왜 원시 타입과 객체를 다르게 처리하나?** — **원시 타입은 identity가 없어 안정성이 관측 불가능**하기 때문. `int` 5와 다른 `int` 5는 구별할 방법이 없으니 stable할 필요가 없다. 객체는 같은 키라도 서로 다른 인스턴스라 순서가 관측된다. JDK 소스 주석에도 명시된 근거다.

정확히 알아둘 것:

- 원시/객체 분리는 **JDK 7(2011)**에 도입. **JDK 14**는 `DualPivotQuicksort`를 대폭 개편(heapsort 가드, run-merging 추가 — JDK-8226297)했으나 분류 자체는 안 바꿈
- **`Arrays.parallelSort`는 Java 8(2014)**. Fork/Join 기반, `ForkJoinPool.commonPool()` 사용
- `Collections.sort`는 `List.sort()`에 위임하고 기본 구현이 배열 복사 후 `Arrays.sort`를 부르지만, **`List` 구현체가 오버라이드할 수 있어 "항상 TimSort"는 과장**
- `-Djava.util.Arrays.useLegacyMergeSort=true`로 구식 merge sort 사용 가능

**TimSort**는 병합 + 삽입 하이브리드로, 이미 정렬된 구간(run)을 찾아 병합한다. **stable하고 adaptive** — 실제 데이터가 부분적으로 정렬돼 있다는 관찰에 기반한 설계.

### 50GB를 4GB 메모리로 — 외부 정렬

**External Merge Sort.**

1. **분할** — 메모리에 들어가는 크기(예: 2GB)로 잘라 읽는다
2. **정렬 후 기록** — 각 청크를 메모리에서 정렬해 **정렬된 run**으로 디스크에 쓴다 (약 25개)
3. **k-way 병합** — 각 run의 맨 앞 원소를 **최소 힙**에 넣고 최솟값을 꺼내 출력 → 그 run의 다음 원소를 push. 반복

**여기가 힙이 실전에서 쓰이는 대표 사례다.** k개 중 최솟값을 반복해 뽑는 것이 정확히 우선순위 큐의 일.

한 번에 병합할 run 수(fan-in)는 메모리와 버퍼 크기가 정한다. run이 너무 많으면 **여러 패스**로 나눈다. 병목이 CPU가 아니라 **디스크 I/O**라서, 순차 읽기를 살리도록 큰 버퍼를 쓰는 것이 실제 튜닝 포인트.

## 9. 객체지향 프로그래밍 `★★☆`

### 핵심 정의

**상태(데이터)와 그 상태를 다루는 행위(메서드)를 하나의 객체로 묶고, 객체들이 서로 메시지를 주고받으며 협력하도록 프로그램을 구성하는 방식.**

핵심 대비를 넣으면 강해진다 — **절차지향은 "데이터"와 "그 데이터를 처리하는 함수"가 분리**돼 있다. 그래서 데이터 구조가 바뀌면 그걸 만지는 모든 함수를 찾아 고쳐야 한다. OOP는 **둘을 한 곳에 묶어 변경의 파급을 객체 경계 안에 가둔다.**

**이것이 "유지보수성이 좋다"의 메커니즘이다.** 결론만 말하고 이 부분을 빼면 답이 되지 않는다.

### 4대 축 — 단, 조건을 붙여서

캡슐화 · 상속 · 다형성 · 추상화.

> **정확히 말하기** — 이는 **널리 쓰이는 교육적 관습**이지 형식적으로 합의된 CS 정의가 아니다. Alan Kay가 OOP라는 말을 만들 때 강조한 것은 **메시지 패싱 · 캡슐화 · 늦은 바인딩(late binding)**이었고, **상속은 다형성을 구현하는 한 수단일 뿐 필수 축이 아니라는 반론**도 있다 (프로토타입 기반 언어는 클래스 상속 없이 다형성을 구현). 면접에서 4개를 답하되 "흔히 이렇게 정리합니다"라고 단서를 달면 오히려 깊이 있어 보인다.

### SOLID

| | 원칙 | 한 줄 |
|---|---|---|
| **S** | 단일 책임 | 클래스가 바뀌어야 할 이유는 **하나**여야 한다 |
| **O** | 개방-폐쇄 | **확장에는 열리고 수정에는 닫힌다** — 새 기능은 코드 추가로 |
| **L** | 리스코프 치환 | **하위 타입은 상위 타입을 대체해도 정확성이 깨지지 않아야** |
| **I** | 인터페이스 분리 | 안 쓰는 메서드에 의존하지 않게, 작은 인터페이스 여러 개 |
| **D** | 의존성 역전 | **구체가 아니라 추상에 의존** |

L이 가장 자주 틀린다. "정사각형은 직사각형인가?" — `Rectangle`을 상속한 `Square`는 `setWidth`가 높이까지 바꿔서 "너비만 바꾸면 넓이는 너비×기존높이"라는 상위 타입의 계약을 깬다. **is-a 관계가 아니라 "계약을 지키는가"가 기준.**

#### 내 코드 연결 (D)

`@RequiredArgsConstructor` + `final` 필드 주입으로 서비스가 `CommentRepository` **인터페이스**에만 의존하고 구현체는 Spring이 주입한다. `@Autowired`를 안 쓰고 생성자 주입만 쓰는 것도 "의존이 생성 시점에 확정되고 불변"이라는 이점 때문.

### 다형성 — 정적 vs 동적

| | 정적(컴파일 타임) | 동적(런타임) |
|---|---|---|
| 수단 | **오버로딩** | **오버라이딩** |
| 결정 시점 | 컴파일러가 **인자의 정적 타입**으로 | JVM이 **객체의 실제 타입**으로 |
| 메커니즘 | 시그니처 매칭 | **동적 디스패치** (`invokevirtual`, vtable) |

**Java 제네릭도 정적 다형성(매개변수 다형성)**이다. 타입 소거(type erasure) 때문에 런타임에는 타입 정보가 사라지고 컴파일 시점에만 존재한다.

### 오버로딩 vs 오버라이딩

| | 오버로딩 | 오버라이딩 |
|---|---|---|
| 위치 | 같은 클래스(또는 상속받은) | **하위 클래스** |
| 시그니처 | **파라미터 목록이 달라야** | **완전히 같아야** |
| 반환 타입 | **반환 타입만 다르면 안 됨** | **공변(covariant) 허용** |
| 접근 제어자 | 무관 | **좁힐 수 없음** |
| 체크 예외 | 무관 | **넓힐 수 없음** |

"반환 타입만 다른 오버로딩 불가"는 단골. `int f()`와 `String f()`는 호출부 `f();`만 봐서 결정할 수 없다.

### 상속보다 합성 — 이유 4가지

1. **상속은 캡슐화를 깬다** — 하위 클래스가 상위의 **구현 세부사항**에 의존하게 된다. 상위가 내부를 바꾸면 하위가 조용히 망가진다 (**fragile base class**)
2. **컴파일 타임에 고정** — 런타임에 바꿀 수 없다. 합성은 주입만 바꾸면 된다
3. **Java는 상태의 다중 상속이 불가** — 클래스는 하나만 상속. 합성은 여러 개를 담을 수 있다
4. **관계가 잘못 맺어지기 쉽다** — is-a가 아닌데 코드 재사용 목적으로 상속하면 LSP가 깨진다

**Effective Java Item 18** (3판 기준, 2판은 Item 16)의 예시가 이를 보여준다.

`HashSet`을 상속해 원소 추가 횟수를 세는 `InstrumentedHashSet`을 만들고 `add`와 `addAll` 양쪽에서 카운트를 올리면 **`addAll(3개짜리 컬렉션)` 호출 시 카운트가 6이 된다.**

> **정확한 호출 체인** ("HashSet의 addAll"이라는 표현은 부정확):
>
> `InstrumentedHashSet.addAll()` → `super.addAll()` — 그런데 **`HashSet`은 `addAll`을 오버라이드하지 않으므로** 실제로는 상속받은 **`AbstractCollection.addAll()`**이 실행 → 그 안에서 `this.add(e)`를 반복 호출 → 동적 디스패치로 **`InstrumentedHashSet.add()`가 불려** 카운트가 또 올라감.
>
> 즉 **self-use 취약점의 실제 소유자는 `HashSet`이 아니라 `AbstractCollection`이다.**

핵심 교훈: **하위 클래스가 상위의 "내부에서 자기 메서드를 호출하는지(self-use)"까지 알아야 안전하다** — 그건 문서화되지 않은 구현 세부사항이고 언제든 바뀔 수 있다. 이것이 "상속이 캡슐화를 깬다"의 구체적 의미.

### 캡슐화 vs 정보 은닉

| | 캡슐화 | 정보 은닉 |
|---|---|---|
| 뜻 | **데이터와 행위를 하나로 묶는 것** | **구현 결정을 안정적인 인터페이스 뒤에 의도적으로 감추는 것** |
| 초점 | 응집 | 은닉 |

**`private` 붙이고 getter/setter를 필드마다 1:1로 뚫으면 캡슐화가 아니다.** 내부 표현이 그대로 노출되니 `public` 필드와 실질적으로 같다 — **빈약한 도메인 모델(anemic model)**.

진짜 캡슐화는 **"데이터를 꺼내가서 밖에서 처리"가 아니라 "객체에게 일을 시키는" 형태**다.

```java
// ✗ 캡슐화 아님 — 상태를 꺼내 밖에서 판단
if (post.getLikeCount() < 0) { ... }
post.setLikeCount(post.getLikeCount() + 1);

// ○ 객체에게 일을 시킴 — 규칙이 객체 안에 있음
post.increaseLikeCount();
```

#### 내 코드 연결

`Post`, `Comment`의 `likeCount`가 이 문제의 현장이다. 실제로는 동시성 때문에 `UPDATE ... SET count = count + :delta` 네이티브 쿼리로 DB에서 처리한다.

→ "왜 엔티티 메서드가 아니라 DB에 맡겼나"를 설명할 수 있으면 좋은 답변이 된다: **캡슐화(도메인 규칙을 객체 안에)와 동시성 정확성(lost update 방지)이 충돌할 때 후자를 택한 것.**

### 클래스가 있으면 객체지향 언어인가

**아니다. 양방향 모두 성립하지 않는다.**

- **클래스가 있어도 OOP가 아닐 수 있다** — Java로 `static` 메서드만 잔뜩 만들어 절차지향으로 짤 수 있다. 실제로 많은 "서비스 클래스"가 그렇게 생겼다
- **클래스가 없어도 OOP일 수 있다** — JavaScript(프로토타입 기반), Self는 클래스 없이 객체지향

**클래스는 OOP의 필요조건도 충분조건도 아니다.** 객체를 만드는 **한 가지 메커니즘**일 뿐.
