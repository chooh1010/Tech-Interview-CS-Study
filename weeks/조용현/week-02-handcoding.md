## 워밍업 — 버블 · 선택 · 삽입 정렬

### 한 장 요약

| | 최선 | 평균 | 최악 | 공간 | 안정성 | 비교 횟수 |
|---|:--:|:--:|:--:|:--:|:--:|---|
| **버블** | Θ(n) *(조건부)* | Θ(n²) | Θ(n²) | O(1) | **stable** | 조기 종료 시 입력 의존 |
| **선택** | **Θ(n²)** | Θ(n²) | Θ(n²) | O(1) | **unstable** | **항상 n(n-1)/2 고정** |
| **삽입** | Θ(n) | Θ(n²) | Θ(n²) | O(1) | **stable** | 역전 쌍(inversion) 수에 비례 |

**이 표에서 면접관이 파고드는 지점 3개**

1. **버블의 최선 Θ(n)은 공짜가 아니다.** `swapped` 플래그로 조기 종료를 넣었을 때만 Θ(n)이다. 플래그 없는 교과서 이중 루프는 **이미 정렬된 입력에도 Θ(n²)**이다. "버블은 최선 O(n)"이라고 조건 없이 말하면 바로 걸린다.
2. **선택 정렬만 입력과 무관하게 Θ(n²)이다.** 최선/평균/최악이 전부 같다. 비교 횟수가 `n(n-1)/2`로 고정이기 때문이다. 이미 정렬된 배열을 줘도 똑같이 다 본다. (스왑 횟수는 O(n)으로 적다 — 이건 선택 정렬의 유일한 장점이고, 쓰기 비용이 비싼 매체에서 의미가 있다)
3. **선택 정렬은 unstable이다.** 이유가 "선택 방식" 때문이 아니라 **장거리 스왑** 때문이라는 걸 말해야 한다.

### 선택 정렬 unstable 반례 (이걸 외워두면 끝)

```
입력: [2a, 2b, 1]        (2a와 2b는 값이 같고, 2a가 원래 앞)

i=0: 최솟값은 1 (인덱스 2). arr[0]과 arr[2]를 스왑
     → [1, 2b, 2a]        ← 2a가 2b 뒤로 밀려남. 상대 순서 깨짐
```

한 번의 스왑이 **멀리 떨어진 원소를 건너뛰면서** 같은 값의 상대 순서를 뒤집는다. 버블과 삽입은 **인접 교환만** 하기 때문에 같은 값을 절대 건너뛰지 않고, 그래서 stable하다.

> **stable을 왜 신경 쓰나** — 다중 키 정렬 때문이다. "부서로 정렬한 뒤 이름으로 정렬"을 하려면 두 번째 정렬이 stable해야 첫 번째 정렬 결과가 보존된다.
>
> Java도 이 구분을 따른다. **`Arrays.sort(Object[])`는 TimSort 계열로 stable을 문서상 보장**하고(자연 순서면 `ComparableTimSort`, comparator를 주면 `TimSort`), **원시 타입 오버로드는 안정성을 보장하지 않는다.**
>
> 다만 **"원시 타입은 값이 같으면 구분이 불가능하니 안정성이 무의미하다"는 설명은 조심해서 써야 한다.** int 계열에는 통하는 실용적 직관이지만, `float`/`double`은 **raw bit가 다른 NaN이 존재**해서 `Float.floatToRawIntBits`로 구별이 가능하다. 게다가 이건 **JDK가 문서화한 근거가 아니다** — 공식 문서는 객체 정렬에 안정성을 명시적으로 보장하고 원시 타입에는 보장 없이 알고리즘만 기술할 뿐, "구별 불가능해서 허용한다"고 쓰지 않는다. 면접에서는 "**원시 타입 오버로드는 안정성을 보장하지 않습니다**"까지만 말하는 게 안전하다.

### 구현

#### 1. 버블 정렬

```java
static void bubbleSort(int[] arr) {
    int n = arr.length;
    for (int i = 0; i < n - 1; i++) {
        boolean swapped = false;              // 조기 종료용 - 이게 없으면 최선도 O(n^2)
        for (int j = 0; j < n - 1 - i; j++) { // -i: 뒤쪽 i개는 이미 확정됨
            if (arr[j] > arr[j + 1]) {        // > 이지 >= 가 아니다. >= 면 unstable
                swap(arr, j, j + 1);
                swapped = true;
            }
        }
        if (!swapped) return;                 // 한 바퀴 돌며 교환이 없었다 = 정렬 완료
    }
}
```

**불변식** — `i`번째 외부 루프가 끝나면 **배열 뒤쪽 `i+1`개가 최종 위치에 확정**된다. 매 패스마다 가장 큰 값이 거품처럼 뒤로 떠오른다.

**손코딩 함정 2개**
- `j < n - 1 - i` 의 `-1`을 빠뜨리면 `arr[j+1]`에서 `ArrayIndexOutOfBoundsException`
- 비교를 `>=`로 쓰면 **값이 같아도 교환**해서 stable이 깨진다

#### 2. 선택 정렬

```java
static void selectionSort(int[] arr) {
    int n = arr.length;
    for (int i = 0; i < n - 1; i++) {   // n-1까지. 마지막 1개는 자동으로 제자리
        int minIdx = i;
        for (int j = i + 1; j < n; j++) {
            if (arr[j] < arr[minIdx]) { // < 이지 <= 가 아니다. <= 면 뒤쪽 같은 값을 골라 더 불안정해짐
                minIdx = j;
            }
        }
        swap(arr, i, minIdx);           // 장거리 스왑 - 여기서 stable이 깨진다
    }
}
```

**불변식** — `i`번째 루프가 끝나면 **배열 앞쪽 `i+1`개가 정렬된 상태로 확정**된다. 버블과 반대 방향이다.

**핵심** — 안쪽 루프는 `i`와 무관하게 **항상 끝까지 돈다**. `break`할 조건이 없다. 이게 최선도 Θ(n²)인 이유다.

#### 3. 삽입 정렬

```java
static void insertionSort(int[] arr) {
    for (int i = 1; i < arr.length; i++) { // i=0이 아니라 i=1부터. 원소 1개는 이미 정렬됨
        int key = arr[i];                  // 자리를 비우고 값을 손에 든다
        int j = i - 1;
        while (j >= 0 && arr[j] > key) {   // > 이지 >= 가 아니다. >= 면 stable 깨짐
            arr[j + 1] = arr[j];           // 스왑이 아니라 "밀어내기" - 대입 1번
            j--;
        }
        arr[j + 1] = key;                  // 멈춘 자리 바로 뒤에 꽂는다
    }
}
```

**불변식** — `i`번째 루프 시작 시점에 **`arr[0..i-1]`이 정렬되어 있다.** `arr[i]`를 그 안의 올바른 위치에 끼워 넣는다.

**손코딩 함정 3개**
- `i = 0`부터 시작하면 `j = -1`로 시작해 while이 그냥 스킵 — 틀리진 않지만 의미 없는 반복
- `while (j >= 0 && ...)` 에서 **`j >= 0`을 먼저 검사**해야 한다. 순서를 바꾸면 `arr[-1]`로 예외. 자바의 `&&` 단축 평가에 의존하는 코드다
- 루프 종료 후 `arr[j + 1] = key` — `arr[j]`가 아니다. while이 `j--` 하고 나왔으므로 한 칸 앞이 빈자리

**왜 삽입 정렬이 실무에서 살아남았나** — 이 셋 중 유일하게 실제로 쓰인다. 이유가 2개다.
- **거의 정렬된 입력에 Θ(n)**이다. 비용이 역전 쌍 개수에 비례하기 때문
- **작은 배열에서 상수가 가장 작다.** 그래서 Java의 실제 정렬 구현들이 작은 구간에서는 삽입 정렬로 전환한다. JDK 17~21 기준 실제 상수는 **TimSort의 `MIN_MERGE = 32`**(전체 길이가 32 미만이면 binary insertion sort로 마무리), **`DualPivotQuicksort.MAX_INSERTION_SORT_SIZE = 44`**(`size < 44` 조건이라 실질 최대 43)이다

> **여기서 과하게 단순화하지 말 것.** "원시 타입은 전부 듀얼피벗 퀵정렬"은 틀리다. JDK 17~21의 `DualPivotQuicksort`는 **타입과 입력에 따라 디스패치하는 하이브리드**다.
> - `int`/`long`/`float`/`double` — 듀얼피벗 퀵정렬이 기본이되, 정렬된 run이 많으면 `tryMergeRuns`로 머지 경로를 타고, 재귀가 나빠지면 힙 정렬로 폴백
> - `byte[]` — 길이 > 64면 **계수 정렬**, 이하는 삽입 정렬 (퀵정렬을 아예 안 쓴다)
> - `short[]`/`char[]` — 길이 > 1750이면 계수 정렬
>
> 면접에서 상수를 정확히 욀 필요는 없다. 말해야 할 것은 **"작은 구간은 삽입 정렬로 전환한다"**와 **"원시 타입 경로는 타입별 하이브리드다"** 두 가지다. 상수를 자신 있게 틀리게 말하는 것보다 "정확한 값은 기억 안 납니다"가 낫다.

> **유도되는 꼬리질문** — "그럼 O(n²) 정렬이 O(n log n)보다 빠를 수 있나요?" → 있다. 위의 컷오프가 그 증거다. 점근 복잡도는 n이 충분히 클 때의 이야기고, n이 작으면 상수 계수와 캐시 지역성이 지배한다.

```java
static void swap(int[] arr, int a, int b) {
    int tmp = arr[a];
    arr[a] = arr[b];
    arr[b] = tmp;
}

// 아래 Quickselect에서 쓴다. Fisher-Yates - 뒤에서부터 [0..i] 중 하나와 교환
static void shuffle(int[] arr) {
    Random rnd = new Random();
    for (int i = arr.length - 1; i > 0; i--) {
        swap(arr, i, rnd.nextInt(i + 1));   // nextInt(i+1) - 자기 자신도 후보여야 균등하다
    }
}
```

**시간복잡도** → 위 표 참조 · **공간복잡도** → 셋 다 O(1) (in-place)

## 응용 문항

### 9. 길이 N인 배열에서 K번째로 큰 수 구하기 (O(N log N)보다 빠르게)

#### 먼저 함정을 짚고 시작한다

이 문제의 조건은 **"O(N log N)보다 작아야 한다"**이다. 그래서 두 가지를 먼저 말해야 한다.

1. **정렬 후 인덱싱은 오답이다.** `Arrays.sort` 후 `arr[n-k]`는 Θ(N log N)이라 조건 위반.
2. **크기 K 힙 풀이는 조건부로만 정답이다.** O(N log K)인데, 이게 O(N log N)보다 **진짜로** 좋으려면 `log K = o(log N)`이어야 한다. `K = N/2`면 `log K = log N - 1`이라 여전히 Θ(N log N)이고, **`K = √N`처럼 K가 N의 거듭제곱꼴이어도 `log K = c·log N`이라 여전히 Θ(N log N)**이다. K가 상수이거나 그에 준하게 작을 때만 의미가 있다.

**따라서 K가 제한되지 않은 일반해는 Quickselect다.**

#### 풀이 1 — Quickselect (일반해, 기대 O(N))

```java
static int findKthLargest(int[] arr, int k) {
    // k번째 "큰" 수 = 오름차순 정렬 시 인덱스 n-k
    int target = arr.length - k;
    int lo = 0, hi = arr.length - 1;

    shuffle(arr);                       // 중요: 랜덤화. 이게 없으면 기대 O(N) 보장이 깨진다

    while (lo < hi) {
        int p = partition(arr, lo, hi); // p는 피벗의 최종 확정 위치
        if (p == target) return arr[p];
        if (p < target) lo = p + 1;     // 정렬과 달리 "한쪽만" 재귀 - 이게 O(N log N)이 아닌 이유
        else hi = p - 1;
    }
    return arr[lo];
}

// Lomuto partition
static int partition(int[] arr, int lo, int hi) {
    int pivot = arr[hi];
    int i = lo;                         // i = "pivot보다 작은 구간"의 다음 자리
    for (int j = lo; j < hi; j++) {
        if (arr[j] < pivot) {
            swap(arr, i++, j);
        }
    }
    swap(arr, i, hi);                   // 피벗을 제자리로
    return i;
}
```

**퀵정렬과의 결정적 차이 한 줄** — 퀵정렬은 분할 후 **양쪽 모두** 재귀하지만, Quickselect는 **찾는 값이 있는 한쪽만** 내려간다. 그래서 `N + N/2 + N/4 + … = 2N`이 된다.

**단, 이 급수는 "증명"이 아니라 "직관"이다.** 면접에서 이걸 증명이라고 말하면 안 된다. 균형 분할이 매번 일어난다는 보장이 없기 때문이다. 기대 O(N)이 성립하려면 **매 단계 피벗의 rank가 조건부 균등 분포**여야 하고, 그러려면 **랜덤 피벗 선택이나 입력 사전 셔플이 필요**하다. 위 코드에 `shuffle`이 있는 이유가 이것이다.

| | 시간 | 비고 |
|---|---|---|
| 평균/기대 | **O(N)** | 랜덤화 전제 |
| 최악 | **O(N²)** | 매번 최악 피벗 (정렬된 입력 + 고정 피벗) |
| 공간 | **O(1)** | 위처럼 while 루프로 쓰면 재귀 스택도 없음 |

**최악을 없애려면** — median-of-medians(BFPRT)로 피벗을 고르면 **최악에도 O(N)**이다. 다만 상수가 커서 실제로는 느린 경우가 많고, 현실적으로는 Quickselect를 쓰다가 재귀가 깊어지면 median-of-medians로 전환하는 방식을 쓴다. (이게 유일한 표준 해법은 아니고, 여러 선택지 중 하나다)

#### 풀이 2 — 크기 K 최소 힙 (K가 작을 때, O(N log K))

```java
static int findKthLargestHeap(int[] arr, int k) {
    PriorityQueue<Integer> minHeap = new PriorityQueue<>();  // 기본이 최소 힙
    for (int x : arr) {
        minHeap.offer(x);
        if (minHeap.size() > k) {
            minHeap.poll();          // 가장 작은 걸 버린다 -> 항상 "상위 K개"만 남음
        }
    }
    return minHeap.peek();           // 그 K개 중 최솟값 = K번째로 큰 수
}
```

**왜 최대 힙이 아니라 최소 힙인가** — 여기서 대부분 틀린다. "K번째로 큰 수"니까 최대 힙을 떠올리지만, **상위 K개를 유지하려면 그 중 가장 작은 것을 버려야** 하므로 최소 힙이 맞다. 최대 힙으로 풀면 전체 N개를 넣고 K번 `poll`해야 해서 O(N + K log N)이 된다.

**이 풀이가 진짜로 쓰이는 지점** — 배열 전체가 메모리에 없어도 된다는 것이다. **스트리밍 데이터에서 상위 K개**를 유지할 때는 Quickselect를 못 쓰고 이 방법만 가능하다. 힙 풀이의 진짜 장점은 복잡도가 아니라 여기에 있다.

> **유도되는 꼬리질문** — "K=1이면요?" → 그냥 최댓값 순회 O(N). "배열이 100억 개라 메모리에 안 들어가면요?" → 힙 풀이 또는 외부 정렬 / 분산 처리

**시간복잡도** → Quickselect 기대 O(N) / 최악 O(N²) · 힙 O(N log K)
**공간복잡도** → Quickselect O(1) *(단, 입력 배열을 파괴적으로 수정한다)* · 힙 O(K)
