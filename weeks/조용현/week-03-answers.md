## 1. 시스템 콜이 무엇인지 설명해 주세요

> 예상 소요: 80초

시스템 콜은 **사용자 프로그램이 운영체제 커널의 기능을 요청하는 공식 인터페이스**입니다. 애플리케이션은 사용자 모드에서 실행되기 때문에 디스크 I/O, 프로세스 생성, 가상 메모리 설정처럼 보호된 자원에 직접 접근할 수 없습니다. 대신 `read`, `write`, `open`, `fork` 같은 시스템 콜을 호출합니다.

일반적인 흐름은 이렇습니다. 프로그램이 보통 C 라이브러리의 래퍼 함수를 호출하면 시스템 콜 번호와 인자를 정해진 레지스터나 메모리에 넣고, `syscall` 같은 명령을 실행합니다. CPU는 사용자 모드에서 커널 모드로 전환하고 미리 등록된 진입점으로 이동합니다. 커널은 번호에 맞는 처리 루틴을 실행하고 권한과 인자를 검증한 뒤 결과를 반환합니다. 이후 다시 사용자 모드로 돌아옵니다.

시스템 콜은 프로세스 제어, 파일 관리, 장치 관리, 정보 조회, 통신, 권한 관리 등으로 분류할 수 있습니다. 핵심은 단순한 함수 호출이 아니라 **보호 경계를 넘는 제어된 진입**이라는 점입니다.

### 꼬리질문 대비

- **Dual Mode가 필요한 이유** — 모든 프로그램이 특권 명령을 실행할 수 있으면 한 프로그램의 오류가 시스템 전체와 다른 프로세스를 망가뜨릴 수 있습니다. CPU의 권한 수준과 메모리 보호로 이를 차단합니다.
- **서로 다른 시스템 콜의 구분** — ABI가 정한 시스템 콜 번호로 구분합니다. 번호와 인자 전달 규약은 운영체제와 CPU 아키텍처에 따라 다릅니다.
- **일반 함수 호출과 차이** — 일반 호출은 같은 권한 수준에서 분기하지만 시스템 콜은 CPU 모드 전환, 커널 스택 사용, 검증 과정이 있어 더 비쌉니다.
- **라이브러리 함수와 관계** — `printf` 같은 라이브러리 함수가 항상 즉시 시스템 콜인 것은 아닙니다. 사용자 공간에서 버퍼링한 뒤 필요할 때 `write`를 호출할 수 있습니다.

## 2. 인터럽트가 무엇인지 설명해 주세요

> 예상 소요: 80초

인터럽트는 **CPU가 현재 실행 흐름을 잠시 멈추고 우선 처리해야 할 사건을 처리하도록 알리는 메커니즘**입니다. 키보드 입력이나 디스크 완료 같은 하드웨어 사건뿐 아니라 예외와 시스템 콜처럼 명령 실행 중 발생하는 동기적 사건도 넓은 의미의 인터럽트 처리 체계를 사용합니다.

인터럽트가 발생하면 CPU는 현재 실행을 재개할 수 있도록 프로그램 카운터와 상태 레지스터 등 필요한 문맥을 저장하고, 커널 모드로 전환해 인터럽트 벡터가 가리키는 핸들러를 실행합니다. 핸들러는 원인을 확인하고 필요한 최소 작업을 수행한 뒤, 지연 가능한 작업은 별도 처리로 넘길 수 있습니다. 처리가 끝나면 저장한 문맥을 복원해 중단된 흐름으로 돌아가거나 스케줄러가 다른 태스크를 선택합니다.

폴링은 CPU가 장치 상태를 반복 확인하는 방식입니다. 구현은 단순하고 매우 짧은 지연이 중요한 상황에는 유리할 수 있지만, 사건이 드물면 CPU 시간을 낭비합니다. 인터럽트는 사건이 생겼을 때 장치가 알리므로 일반적으로 효율적이지만, 지나치게 자주 발생하면 처리 오버헤드가 커집니다.

### 꼬리질문 대비

- **하드웨어/소프트웨어** — 하드웨어 인터럽트는 장치 등 CPU 외부에서 비동기적으로 옵니다. 예외는 현재 명령 때문에 동기적으로 생기며 page fault, divide-by-zero 등이 있습니다. 시스템 콜은 프로그램이 의도적으로 커널 진입 명령을 실행합니다.
- **동시에 여러 개가 발생하면** — 인터럽트 컨트롤러와 CPU가 우선순위, 마스킹, 중첩 허용 여부에 따라 처리합니다. 처리 중 새 인터럽트를 무조건 모두 막는다고 일반화하면 안 됩니다.
- **인터럽트와 컨텍스트 스위치** — 인터럽트가 발생했다고 반드시 프로세스 전환이 일어나는 것은 아닙니다. 처리 후 같은 프로세스로 복귀할 수도 있습니다.

## 3. 프로세스가 무엇인가요?

> 예상 소요: 90초

프로세스는 **실행 중인 프로그램과 그 실행 상태를 운영체제가 관리하는 단위**입니다. 디스크의 프로그램은 명령과 데이터가 담긴 정적인 파일이고, 프로세스는 주소 공간, 레지스터 문맥, 열린 파일, 권한, 스케줄링 상태 같은 실행 자원을 가진 동적인 객체입니다.

운영체제는 이 정보를 PCB에 관리합니다. PCB에는 PID, 프로세스 상태, 프로그램 카운터와 레지스터, 스케줄링 정보, 메모리 관리 정보, 열린 자원 정보 등이 들어갑니다. 스레드는 프로세스의 주소 공간과 파일 같은 자원을 공유하지만 각자 프로그램 카운터, 레지스터, 스택, 스케줄링 상태를 가집니다. 리눅스는 프로세스와 스레드를 완전히 다른 객체로 나누기보다 `task_struct`로 태스크를 표현하고, `clone` 시 어떤 자원을 공유하느냐로 구분합니다.

### 꼬리질문 대비

- **PCB와 스레드** — 개념적으로 스레드도 자신의 실행 문맥을 저장하는 TCB가 필요합니다. 실제 커널 자료구조의 명칭과 분리 방식은 OS마다 다릅니다.
- **`fork`와 `exec`** — `fork`는 부모의 실행 문맥을 복제한 자식을 만들며 현대 OS는 보통 copy-on-write를 사용합니다. `exec`는 현재 프로세스의 주소 공간을 새 프로그램으로 교체하며 PID는 유지됩니다.
- **좀비 프로세스** — 자식은 종료했지만 부모가 `wait`로 종료 상태를 회수하지 않은 상태입니다. 실행 자원은 대부분 반납했지만 PID와 종료 정보가 남습니다.
- **고아 프로세스** — 부모가 먼저 종료한 살아 있는 자식입니다. 리눅스에서는 init 역할의 프로세스나 subreaper가 입양해 종료 상태를 회수합니다.
- **데몬** — 터미널과 독립되어 백그라운드에서 서비스를 제공하는 장기 실행 프로세스입니다. 현대 리눅스에서는 systemd 같은 서비스 관리자가 생명주기를 관리하는 경우가 많습니다.
- **프로세스 트리의 루트** — 일반적으로 PID 1인 init 프로세스이며 현대 배포판에서는 흔히 systemd입니다. 다만 PID namespace 안에서는 그 namespace의 PID 1이 따로 존재할 수 있습니다.

## 4. 프로세스 주소 공간에 대해 설명해 주세요

> 예상 소요: 100초

프로세스 주소 공간은 **프로세스가 사용할 수 있다고 보는 가상 주소의 범위와 그 배치**입니다. 전형적으로 실행 명령이 있는 text, 초기화된 전역·정적 변수가 있는 data, 0으로 초기화되는 전역·정적 변수가 있는 BSS, 동적 할당에 쓰이는 heap, 함수 호출과 지역 변수에 쓰이는 stack, 공유 라이브러리와 메모리 매핑 영역으로 구성됩니다.

각 프로세스가 독립된 가상 주소 공간을 가지므로 같은 가상 주소도 서로 다른 물리 메모리를 가리킬 수 있습니다. 페이지 테이블이 가상 주소를 물리 주소로 변환하며, 이를 통해 격리, 공유, demand paging, copy-on-write를 구현합니다. 주소 배치는 OS, 실행 파일 형식, 아키텍처, ASLR에 따라 달라지므로 그림의 위치나 성장 방향을 절대 규칙처럼 말하면 안 됩니다.

스레드는 같은 프로세스의 text, data, heap과 매핑을 공유하고 각자 스택과 레지스터 문맥을 가집니다.

### 꼬리질문 대비

- **초기화하지 않은 변수** — 전역·정적 변수는 BSS에 놓여 0으로 초기화됩니다. 초기화하지 않은 지역 자동 변수는 스택 프레임 등에 생기지만 값은 미정이므로 읽으면 안 됩니다.
- **스택과 힙의 크기** — 가상 주소 범위와 제한이 먼저 정해질 수 있지만 물리 메모리가 한 번에 모두 배정되는 것은 아닙니다. 페이지는 접근 시점에 할당될 수 있습니다. 스택 제한은 리눅스의 `ulimit` 등으로 조정할 수 있습니다.
- **접근 속도** — 둘 다 결국 메모리이므로 영역 이름만으로 접근 속도가 정해지지 않습니다. 스택 할당은 포인터 조정이라 빠르고 지역성이 좋은 경향이 있지만 실제 접근 비용은 캐시와 패턴에 좌우됩니다.
- **자료구조와의 관계** — 호출 스택은 LIFO로 프레임을 쌓고 빼므로 스택 자료구조와 직접 관련됩니다. 메모리 heap은 자유롭게 할당·해제하는 영역이라는 뜻이며 우선순위 큐의 heap 자료구조와는 별개입니다.
- **공유 메모리 위치** — 공유 메모리 객체를 각 프로세스의 가상 주소 공간에 매핑합니다. 서로 다른 가상 주소일 수 있지만 같은 물리 페이지를 가리킵니다.

## 5. 단기, 중기, 장기 스케줄러를 설명해 주세요

> 예상 소요: 80초

세 스케줄러는 **결정을 내리는 시간 범위와 대상**이 다릅니다. 장기 스케줄러는 제출된 작업 중 어떤 것을 메모리에 들여 실행 경쟁에 참여시킬지 결정해 다중 프로그래밍 정도를 조절합니다. 단기 스케줄러인 CPU 스케줄러는 준비 큐에서 다음 실행 대상을 고르며 매우 자주 동작하므로 빨라야 합니다. 중기 스케줄러는 메모리 압박이나 시스템 균형을 위해 프로세스를 일시 중단하고 스왑 아웃했다가 다시 들여옵니다.

프로세스의 기본 상태는 new, ready, running, waiting 또는 blocked, terminated로 설명할 수 있고, 중기 스케줄링을 표현하면 suspended ready와 suspended blocked 상태를 추가할 수 있습니다.

현대 범용 OS가 이 세 가지를 교과서 이름 그대로 모두 독립 모듈로 둔다고 말하기는 어렵습니다. 대화형 시스템에서는 장기 스케줄러의 역할이 약하고, 가상 메모리의 페이지 회수나 메모리 압축·스왑이 중기 스케줄링과 비슷한 역할을 합니다. 단기 CPU 스케줄링은 항상 핵심입니다.

### 꼬리질문 대비

- **선점/비선점과 상태** — 상태 자체가 사라진다기보다 전이 경로가 다릅니다. 선점형은 타이머 만료 등으로 running에서 ready로 강제 이동할 수 있고, 비선점형은 보통 종료하거나 블록될 때 CPU를 내놓습니다.
- **메모리가 부족하면** — 일부 페이지가 회수·스왑되거나 프로세스가 중단될 수 있습니다. 극심한 경우 리눅스의 OOM killer처럼 프로세스를 종료할 수도 있어 단일 상태 전이로 고정할 수 없습니다.

## 6. 컨텍스트 스위칭 시 어떤 일이 일어나나요?

> 예상 소요: 90초

컨텍스트 스위칭은 **CPU에서 실행 중인 태스크의 문맥을 저장하고 다른 태스크의 문맥을 복원하는 과정**입니다. 스케줄러가 전환을 결정하면 현재 태스크의 프로그램 카운터, 스택 포인터, 범용 레지스터와 필요한 CPU 상태를 커널이 관리하는 구조체와 커널 스택에 보존합니다. 다음 태스크의 상태를 복원하고 주소 공간이 달라진다면 페이지 테이블 기준도 바꾼 뒤 그 태스크가 멈췄던 지점부터 실행합니다.

프로세스 간 전환은 주소 공간까지 달라질 수 있지만 같은 프로세스 내 스레드 전환은 주소 공간을 공유하므로 보통 더 가볍습니다. 그래도 스레드 전환 역시 레지스터와 스택을 바꾸고 캐시 상태에 영향을 주므로 비용이 0은 아닙니다. 또한 ASID나 PCID, TLB 동작에 따라 페이지 테이블 전환 비용은 하드웨어별로 다릅니다.

직접 비용은 커널의 저장·복원과 스케줄링 작업이고, 간접 비용은 새 태스크의 코드와 데이터 때문에 CPU 캐시, TLB, 분기 예측기의 유효성이 떨어지는 것입니다.

### 꼬리질문 대비

- **언제 발생하나** — time slice 만료, 더 높은 우선순위 태스크의 준비, 현재 태스크의 I/O 대기·sleep·락 대기, 명시적 yield 등이 대표적입니다.
- **인터럽트와 차이** — 사용자 모드에서 커널로 들어가는 모드 스위치와 실행 태스크가 바뀌는 컨텍스트 스위치는 다른 개념입니다. 시스템 콜 후 같은 태스크로 돌아오면 프로세스 컨텍스트 스위치는 없습니다.
- **커널 스택에 저장되는 형식** — 인터럽트 진입 시 일부 레지스터는 하드웨어가, 나머지는 진입 코드가 트랩 프레임 형태로 저장할 수 있습니다. 정확한 형식은 CPU와 OS 구현에 따라 다릅니다.

## 7. 프로세스 스케줄링 알고리즘에는 어떤 것들이 있나요?

> 예상 소요: 110초

CPU 스케줄링 알고리즘은 **응답 시간, 처리량, 공정성, 예측 가능성 중 무엇을 우선하느냐**에 따라 선택합니다.

FCFS는 도착 순서대로 실행해 단순하지만 긴 작업 뒤에 짧은 작업이 기다리는 convoy effect가 생깁니다. SJF는 실행 시간이 가장 짧은 작업을 골라 평균 대기 시간을 최소화하지만 실제 burst 시간을 정확히 알기 어렵고 긴 작업이 기아 상태에 빠질 수 있습니다. SRTF는 SJF의 선점형입니다. Priority scheduling은 우선순위가 높은 작업을 먼저 처리하며 aging으로 기아를 완화합니다. Round Robin은 일정 time quantum씩 순환해 대화형 시스템의 응답성을 높입니다. Multilevel Queue는 작업 종류별 큐를 나누고, MLFQ는 실행 행동에 따라 프로세스를 큐 사이에서 이동시켜 짧고 대화형인 작업을 우대하면서 주기적 boost 등으로 기아를 줄입니다.

현대 OS는 이 알고리즘 하나를 그대로 쓰기보다 다중 코어, CPU affinity, 부하 균형, 우선순위와 공정성을 함께 고려하는 복합 스케줄러를 사용합니다. 그리고 커널이 실제로 스케줄하는 단위는 흔히 프로세스보다 **커널 스레드 또는 태스크**입니다.

### 꼬리질문 대비

- **RR quantum의 trade-off** — 너무 크면 FCFS에 가까워져 응답성이 나빠지고, 너무 작으면 컨텍스트 스위치가 지나치게 잦아집니다.
- **상시 돌아가야 하는 작업** — 의미가 마감시간 보장이라면 일반 시분할 알고리즘보다 실시간 스케줄링 정책을 검토해야 합니다. 단순히 높은 우선순위를 주면 다른 작업의 기아와 priority inversion을 함께 고려해야 합니다.
- **동시성과 병렬성** — 동시성은 여러 작업의 진행 구간이 겹치는 성질이고, 병렬성은 같은 시점에 여러 코어에서 실제로 실행되는 것입니다. 단일 코어도 시분할로 동시성을 만들 수 있습니다.
- **FCFS의 용도** — 실행 시간이 비슷한 배치 작업이나 도착 순서가 중요한 단순 큐에서는 예측 가능하고 오버헤드가 낮다는 장점이 있습니다.
- **사용자 스레드** — N:1 모델에서는 사용자 런타임이 사용자 스레드를 스케줄하고 커널은 그 아래 커널 스레드만 봅니다. 1:1 모델에서는 각 스레드가 커널 스케줄링 대상입니다.

## 8. 프로그램이 컴파일되어 실행되는 과정을 설명해 주세요

> 예상 소요: 100초

C 계열의 전통적인 흐름을 기준으로 설명하면 **전처리, 컴파일, 어셈블, 링크, 로드, 실행** 순서입니다. 전처리기는 헤더 포함과 매크로를 처리하고, 컴파일러는 소스 코드를 어셈블리나 중간 표현을 거쳐 목적 코드로 변환합니다. 어셈블러는 기계어가 든 오브젝트 파일을 만들고, 링커는 여러 오브젝트와 라이브러리의 심볼 참조를 해결해 실행 파일을 만듭니다.

실행 요청이 오면 운영체제의 실행 로딩 경로가 실행 파일 형식을 읽고 코드·데이터 등을 가상 주소 공간에 매핑하며 스택, 인자, 환경 변수를 준비합니다. 동적 링크 프로그램이라면 동적 링커가 공유 라이브러리를 매핑하고 재배치를 처리합니다. CPU 레지스터와 프로그램 카운터를 진입점에 맞춘 뒤 사용자 코드가 시작됩니다. 실제 물리 페이지는 demand paging으로 처음 접근할 때 들어올 수 있습니다.

링커는 **파일 안의 참조를 연결해 실행 가능한 이미지를 만드는 역할**, 로더는 **그 이미지를 프로세스 주소 공간에 배치하고 실행을 시작시키는 역할**이라는 차이가 있습니다.

### 꼬리질문 대비

- **컴파일과 인터프리트** — 구현 전략의 차이입니다. 컴파일은 실행 전 다른 형태로 변환하고, 인터프리트는 실행 시 명령을 해석합니다. 현대 런타임은 바이트코드와 JIT를 섞으므로 언어 자체를 둘 중 하나로 단정하기보다 구현체를 말해야 합니다.
- **JIT** — 실행 중 자주 수행되는 코드를 네이티브 코드로 컴파일하고 실제 실행 정보를 이용해 최적화합니다. 초기 워밍업 비용과 추가 메모리가 들지만 장기 실행 성능을 높일 수 있습니다.
- **Java** — `javac`가 바이트코드가 든 class 파일을 만들고 JVM이 로딩·검증·링킹·초기화를 거쳐 실행합니다. 인터프리터로 시작한 뒤 hot code를 JIT 컴파일할 수 있습니다.
- **Python 구현체** — CPython은 보통 Python 바이트코드를 자체 VM에서 실행하고, PyPy는 tracing JIT를 사용합니다. Jython은 JVM 위에서 동작합니다. 같은 Python 언어여도 구현체에 따라 실행 과정과 호환성이 달라집니다.
- **`fork`/`exec`와 로더** — 유닉스에서 `fork`가 새 프로세스 실행 문맥을 만들고 `exec`가 그 프로세스의 주소 공간을 새 프로그램으로 교체합니다. `exec`의 커널 경로와 동적 링커가 넓은 의미의 로딩을 담당합니다. 프로세스 생성 API는 OS마다 다릅니다.

## 9. 32비트와 64비트의 차이는 무엇인가요?

> 예상 소요: 70초

32비트와 64비트는 문맥에 따라 CPU의 일반 레지스터와 연산 폭, 포인터 크기, 명령어 집합과 ABI의 차이를 가리킵니다. 애플리케이션 관점에서 가장 체감되는 차이는 **가상 주소 공간의 크기와 포인터 크기**입니다.

32비트 포인터는 서로 다른 주소를 이론상 `2^32`개 표현하므로 바이트 주소 방식이면 주소 공간이 4GiB입니다. 다만 이 전체를 한 사용자 프로세스가 모두 쓰는 것은 아닙니다. 커널 영역 배치, 장치 메모리, OS 정책 때문에 실제 사용자 공간은 더 작을 수 있고, PAE 같은 기술은 시스템 전체가 4GiB보다 많은 물리 메모리를 쓰게 해도 개별 32비트 프로세스의 기본 가상 주소 폭을 64비트로 만들지는 않습니다.

64비트 환경은 훨씬 큰 주소 공간과 더 넓은 정수 연산 등의 장점이 있지만 포인터와 관련 자료구조가 커져 메모리 사용량과 캐시 부담이 늘 수 있습니다. 또한 실제 CPU가 `2^64`바이트의 가상·물리 주소를 모두 구현하는 것은 아니며 지원 비트 수는 아키텍처와 세대에 따라 제한됩니다.

### 꼬리질문 대비

- **왜 4GB인가** — 주소 하나가 1바이트를 가리킨다고 할 때 `2^32 byte = 4 GiB`이기 때문입니다. 엄밀히는 4GB보다 4GiB가 정확합니다.
- **64비트 정수와 64비트 시스템** — 32비트 CPU도 여러 명령으로 64비트 정수를 처리할 수 있습니다. 시스템의 비트 수와 특정 자료형의 비트 수는 같은 개념이 아닙니다.
- **호환성** — 64비트 OS가 32비트 프로그램을 실행할 수 있는지는 CPU의 호환 모드와 OS의 32비트 ABI·라이브러리 지원 여부에 달려 있습니다.
