## 워밍업 — 병합 정렬 (Merge Sort)

### 한 장 요약

| 항목 | 값 |
|---|---|
| 시간복잡도 | 최선·평균·최악 **모두 Θ(n log n)** |
| 공간복잡도 | 배열 구현 **O(n)** (보조 배열), 연결 리스트 구현 **O(log n)** (재귀 스택) |
| 안정성 | **안정 정렬** (동률일 때 왼쪽 우선을 지키는 구현에 한함) |
| 제자리 정렬 | 아님 (보조 배열 필요) |

**퀵소트와의 대비가 이 문항의 핵심입니다.** 퀵소트는 평균 Θ(n log n)이지만 최악 Θ(n²)이고, 병합 정렬은 **입력 분포와 무관하게 항상 Θ(n log n)** 입니다. 대신 추가 메모리를 씁니다. 즉 **"최악을 보장받는 대가로 메모리를 낸다"** 는 트레이드오프입니다.

### 구현

```java
final class MergeSort {

    /** 진입점 — 보조 배열을 여기서 한 번만 할당한다. */
    static void sort(int[] a) {
        if (a == null || a.length < 2) {
            return;
        }
        int[] buffer = new int[a.length];
        sort(a, buffer, 0, a.length - 1);
    }

    private static void sort(int[] a, int[] buffer, int low, int high) {
        if (low >= high) {          // 원소가 0개 또는 1개면 이미 정렬 상태
            return;
        }

        int mid = low + (high - low) / 2;   // (low + high) / 2 는 오버플로 위험

        sort(a, buffer, low, mid);
        sort(a, buffer, mid + 1, high);

        if (a[mid] <= a[mid + 1]) {  // 이미 이어 붙여도 정렬이면 merge 생략
            return;
        }
        merge(a, buffer, low, mid, high);
    }

    private static void merge(int[] a, int[] buffer, int low, int mid, int high) {
        System.arraycopy(a, low, buffer, low, high - low + 1);

        int i = low;        // 왼쪽 구간 커서
        int j = mid + 1;    // 오른쪽 구간 커서

        for (int k = low; k <= high; k++) {
            if (i > mid) {                      // 왼쪽 소진 → 오른쪽만 남음
                a[k] = buffer[j++];
            } else if (j > high) {              // 오른쪽 소진 → 왼쪽만 남음
                a[k] = buffer[i++];
            } else if (buffer[j] < buffer[i]) { // 오른쪽이 "더 작을 때만" 선택
                a[k] = buffer[j++];
            } else {                            // 같으면 왼쪽 → 안정성 확보
                a[k] = buffer[i++];
            }
        }
    }
}
```

### 반드시 설명할 포인트 4개

**① 임시 배열을 매번 할당하지 않는 방법** — 이게 이 주차 구현 범위에 명시된 항목입니다.

순진한 구현은 `merge`마다 `new int[...]`를 합니다. `merge`는 총 **n-1회 가까이 호출**되므로 할당과 GC 부담이 그만큼 발생합니다. 해결은 **진입점에서 원본 크기만 한 보조 배열을 한 번만 만들고 재귀 전체가 공유**하는 것입니다. 각 `merge`는 `[low, high]` 구간만 건드리므로 **서로 다른 재귀 호출이 같은 구간을 동시에 쓰는 일이 없어** 하나를 돌려써도 안전합니다.

> 더 나아간 기법으로 **원본과 보조 배열의 역할을 단계마다 맞바꾸는(role swap)** 방식이 있습니다. 매 merge에서 하는 `arraycopy`조차 없앨 수 있지만, 마지막에 결과가 어느 배열에 있는지를 추적해야 해서 손코딩에서는 실수하기 쉽습니다. **"이런 방법도 있다"까지만 말하고 위 구현을 제출하는 게 안전합니다.**

**② 왜 안정 정렬인가** — 분할 자체는 순서를 바꾸지 않으므로, 안정성은 **오직 `merge`의 타이브레이크 규칙**에서 결정됩니다. 위 코드에서 조건이 `buffer[j] < buffer[i]`인 것이 핵심입니다. **값이 같으면 이 조건이 거짓이 되어 왼쪽(`i`)을 먼저 가져갑니다.** 왼쪽 구간은 원본에서 더 앞에 있던 원소들이므로 동률 원소의 원래 순서가 보존됩니다.

> **여기가 함정입니다.** 조건을 `buffer[j] <= buffer[i]`로 바꾸면 동률일 때 오른쪽을 먼저 집어 **안정성이 깨집니다.** 부등호 하나로 성질이 바뀌므로 면접에서 "왜 `<`인가요?"를 물으면 이걸 답해야 합니다.

**③ `if (a[mid] <= a[mid + 1]) return;` 의 의미** — 왼쪽 구간의 최댓값이 오른쪽 구간의 최솟값보다 작거나 같으면 두 구간은 이미 이어 붙인 것만으로 정렬 상태입니다. **이미 정렬된 입력에서 `merge`를 전부 건너뛰어 O(n) 가까이 동작**하게 만드는 최적화입니다. 다만 최악 복잡도는 그대로 Θ(n log n)입니다.

**④ `mid` 계산에서 오버플로** — `(low + high) / 2`는 두 값이 클 때 `int` 범위를 넘겨 **음수가 됩니다.** 그러면 `low >= high` 판정과 인덱싱이 무너집니다. `low + (high - low) / 2`로 써야 합니다. 실제로 자바 `Arrays.binarySearch`에 오래 남아 있던 유명한 버그입니다.

### 꼬리질문 대비

- **왜 항상 Θ(n log n)인가** — 분할이 **입력 값과 무관하게 항상 절반**이기 때문입니다. 재귀 깊이가 `log n`으로 고정되고 각 깊이에서 전체 n개를 한 번씩 훑으므로 `n × log n`입니다. 퀵소트는 분할 지점이 **피벗 값에 의존**해서 한쪽으로 치우치면 깊이가 n까지 늘어납니다.
- **점화식으로 증명** — `T(n) = 2T(n/2) + Θ(n)`. 마스터 정리에서 `a=2, b=2, f(n)=Θ(n)`이고 `n^(log_b a) = n^1 = n`이므로 **case 2**에 해당해 `T(n) = Θ(n log n)`입니다.
  > **주의 (Week 02에서 틀렸던 부분)** — case 2는 `f(n) = Θ(n^(log_b a))`를 요구합니다. `f(n) = O(n)`만 주고 `Θ(n log n)`을 결론내면 안 됩니다. **Θ를 쓰려면 Θ를 가정해야 합니다.**
- **연결 리스트에 병합 정렬이 어울리는 이유** — 배열과 달리 **보조 배열 없이 포인터만 바꿔 병합**할 수 있어 추가 공간이 O(1)(재귀 스택 제외)입니다. 또 연결 리스트는 임의 접근이 O(n)이라 퀵소트의 피벗 분할이나 힙 정렬이 불리합니다. 실제로 자바 `Collections.sort`와 `Arrays.sort(Object[])`는 병합 정렬 계열인 **TimSort**를 씁니다.
- **왜 자바는 원시 타입에 병합 정렬을 안 쓰는가** — `Arrays.sort(int[])`는 듀얼 피벗 퀵소트 계열입니다. 원시 타입은 **비교 비용이 매우 싸고 안정성이 의미가 없습니다**(값이 같으면 구별 불가). 그래서 추가 메모리를 쓰지 않고 캐시 지역성이 좋은 퀵소트가 유리합니다. 반대로 객체 배열은 **안정성이 관측 가능**하고 비교가 비싸므로 비교 횟수가 적은 TimSort가 유리합니다. **"안정성이 필요한가"와 "비교가 비싼가"가 갈림길입니다.**
- **외부 정렬** — 데이터가 메모리에 다 안 들어가면 병합 정렬이 사실상 표준입니다. 조각으로 나눠 각각 정렬해 디스크에 쓰고, **순차 읽기만으로 다방향 병합**할 수 있기 때문입니다. 퀵소트는 임의 접근이 필요해 디스크에서 불리합니다.

## 응용 문항 12 — 정렬된 두 LinkedList를 하나의 정렬된 LinkedList로 병합

### 문제의 핵심

**병합 정렬의 `merge` 단계를 연결 리스트로 옮긴 것**입니다. 이미 각각 정렬돼 있으므로 **양쪽 머리를 비교해 작은 쪽을 떼어 붙이는 것을 반복**하면 됩니다.

여기서 **새 노드를 만들지 말고 기존 노드를 재배치**하는 게 요점입니다. 그래야 추가 공간이 O(1)이 됩니다.

### 구현 (반복 — 권장)

```java
final class Node {
    int value;
    Node next;

    Node(int value) {
        this.value = value;
    }
}

final class SortedListMerger {

    static Node merge(Node a, Node b) {
        Node dummy = new Node(0);   // 더미 헤드: 첫 노드 결정 분기를 없앤다
        Node tail = dummy;

        while (a != null && b != null) {
            if (a.value <= b.value) {   // 같으면 a 먼저 → 안정성
                tail.next = a;
                a = a.next;
            } else {
                tail.next = b;
                b = b.next;
            }
            tail = tail.next;
        }

        tail.next = (a != null) ? a : b;   // 남은 쪽은 통째로 이어 붙인다

        return dummy.next;
    }
}
```

**시간복잡도** → **O(n + m)** — 각 노드를 정확히 한 번씩만 보고 지나갑니다.
**공간복잡도** → **O(1)** — 더미 노드 1개와 포인터 2개뿐입니다. 새 노드를 만들지 않습니다.

### 반드시 설명할 포인트 3개

**① 더미 헤드(dummy head)를 쓰는 이유** — 더미가 없으면 **첫 노드를 정하는 분기**를 따로 써야 합니다.

```java
// 더미 없이 쓰면 이렇게 지저분해집니다
Node head;
if (a.value <= b.value) { head = a; a = a.next; }
else                    { head = b; b = b.next; }
Node tail = head;
// ... 게다가 a 또는 b가 처음부터 null인 경우를 위에서 또 처리해야 함
```

더미 헤드는 **"tail은 항상 유효한 노드를 가리킨다"는 불변식**을 시작부터 성립시켜 이 분기를 통째로 없앱니다. 연결 리스트 문제에서 가장 자주 쓰는 기법이므로 **왜 쓰는지를 말로 설명할 수 있어야** 합니다.

**② 마지막 `tail.next = (a != null) ? a : b;`** — 반복문을 빠져나온 시점에 **둘 중 최소 하나는 `null`** 입니다. 남은 쪽은 이미 정렬돼 있고 전부 현재 `tail`보다 크거나 같으므로 **하나씩 옮길 필요 없이 통째로 이어 붙이면** 됩니다. 여기서 루프를 한 번 더 도는 구현은 틀린 건 아니지만 불필요합니다.

> **빠뜨리기 쉬운 점** — 이 줄을 아예 안 쓰면 남은 노드들이 버려집니다. 그리고 `a`와 `b`가 **둘 다 null**이어도 `tail.next = null`이 되어 정상 종료되므로 별도 분기가 필요 없습니다.

**③ 동률 처리와 안정성** — `a.value <= b.value`에서 **같을 때 `a`를 먼저** 집습니다. 값만 있는 리스트에서는 티가 안 나지만, 노드가 객체를 담고 있고 "a 리스트가 원래 앞"이라는 의미가 있다면 이 선택이 안정성을 결정합니다. 병합 정렬의 `merge`와 **정확히 같은 논리**입니다.

> 위 배열 구현에서는 조건이 `buffer[j] < buffer[i]`(오른쪽이 작을 때만)이고 여기서는 `a.value <= b.value`(왼쪽이 작거나 같을 때)입니다. **부등호 방향은 다르지만 결과는 같습니다** — 둘 다 동률이면 왼쪽을 집습니다. 헷갈리면 "동률일 때 왼쪽"만 기억하고 그에 맞게 부등호를 맞추면 됩니다.

### 재귀 구현 (비교용)

```java
static Node mergeRecursive(Node a, Node b) {
    if (a == null) {
        return b;
    }
    if (b == null) {
        return a;
    }

    if (a.value <= b.value) {
        a.next = mergeRecursive(a.next, b);
        return a;
    }
    b.next = mergeRecursive(a, b.next);
    return b;
}
```

훨씬 짧지만 **공간복잡도가 O(n + m)** 입니다. 재귀 깊이가 전체 노드 수만큼 쌓이기 때문입니다. **자바는 꼬리 호출 최적화를 하지 않으므로** 리스트가 길면 `StackOverflowError`가 납니다. 면접에서는 **반복 버전을 제출하고 "재귀로도 되지만 스택 깊이 때문에 반복을 택했다"** 고 말하는 게 낫습니다.

### 꼬리질문 대비

- **왜 O(n+m)보다 빠를 수 없나** — 결과 리스트에 모든 노드가 들어가야 하므로 **최소한 전부 한 번은 봐야** 합니다. 출력 크기가 n+m이라 하한이 Ω(n+m)입니다.
- **k개의 정렬된 리스트를 병합하려면?** — 두 가지입니다. ① **최소 힙**에 각 리스트의 현재 머리를 넣고 꺼내면서 그 리스트의 다음 노드를 넣습니다. 전체 원소 N개에 대해 **O(N log k)** ② **쌍끼리 반복 병합**(divide and conquer)해도 같은 **O(N log k)** 입니다. 앞에서부터 하나씩 누적 병합하면 **O(N k)** 로 나빠지므로 이 방식은 피해야 합니다.
- **정렬돼 있지 않다면?** — 각각 정렬한 뒤 병합하거나, 이어 붙여 전체를 정렬합니다. 연결 리스트 정렬은 **위의 병합 정렬**이 적합합니다. 중간 노드를 찾는 데는 **느린/빠른 포인터**를 씁니다.
- **원본을 보존해야 한다면?** — 위 구현은 기존 노드의 `next`를 바꾸므로 **원본 두 리스트가 파괴됩니다.** 보존이 필요하면 노드를 새로 만들어야 하고 공간이 O(n+m)이 됩니다. **면접에서 "원본이 파괴돼도 되나요?"를 먼저 확인하면 좋은 인상을 줍니다.**
- **중복을 제거해야 한다면?** — 붙이기 직전에 `tail.value`와 비교해 같으면 건너뜁니다. 입력이 정렬돼 있으므로 **직전 값 하나만 비교하면 충분**합니다.

## 손코딩 체크리스트 (제출 전 자문)

- [ ] `mid` 계산에 `low + (high - low) / 2`를 썼는가
- [ ] 보조 배열을 **진입점에서 한 번만** 할당했는가
- [ ] `merge`의 동률 처리가 **왼쪽 우선**인가 (안정성)
- [ ] 연결 리스트에서 **더미 헤드**를 쓰고, 왜 쓰는지 말할 수 있는가
- [ ] 반복문 종료 후 **남은 쪽을 통째로 이어 붙였는가**
- [ ] `null` 입력과 원소 1개 입력에서 동작하는가
- [ ] 재귀 구현의 **스택 깊이 문제**를 언급할 수 있는가
