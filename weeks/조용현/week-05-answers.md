## 1. 캐시 메모리 및 메모리 계층성에 대해 설명해 주세요.

**캐시 메모리는 CPU가 자주 사용할 데이터와 명령어를 가까운 곳에 보관해, 느린 하위 메모리에 접근하는 횟수를 줄이는 메모리입니다.**

메모리 계층은 보통 레지스터, L1·L2·L3 캐시, DRAM, SSD·HDD 순서로 설명합니다. CPU에 가까울수록 빠르지만 용량이 작고 비트당 비용이 높습니다. 모든 데이터를 가장 빠른 메모리에 둘 수 없으므로, 자주 쓰는 일부만 상위 계층에 두는 것입니다.

이 구조가 효과적인 이유는 **지역성**입니다. 최근에 사용한 데이터를 다시 사용하는 시간 지역성과, 방금 접근한 주소 주변에 접근하는 공간 지역성이 있습니다. 캐시는 데이터를 한 바이트씩 가져오지 않고 **캐시 라인 단위**로 가져와 이를 활용합니다.

따라서 성능을 볼 때는 연산 횟수뿐 아니라 데이터 배치와 접근 순서도 중요합니다. 같은 O(N) 순회라도 연속된 배열을 읽는 것과 흩어진 노드를 따라가는 것은 캐시 미스와 메모리 접근 비용이 다릅니다.

### 꼬리질문 대비

1. **캐시 메모리는 어디에 위치해 있나요?** — 현대 범용 CPU의 L1·L2·L3 캐시는 대체로 CPU 칩 내부에 있습니다. L1은 코어 가까이에 있고, 마지막 단계 캐시는 여러 코어가 공유하기도 합니다. 정확한 배치와 공유 범위는 CPU마다 다릅니다. OS의 페이지 캐시는 DRAM에 있는 파일 데이터 캐시로, CPU 캐시와 구분합니다.
2. **L1, L2 캐시에 대해 설명해 주세요.** — L1은 작고 빠르며 명령어 캐시와 데이터 캐시로 나뉘는 경우가 많습니다. L2는 보통 L1보다 크지만 접근 지연이 더 큽니다. L1·L2는 코어별 전용인 경우가 많으나 모든 하드웨어에 적용되는 규칙은 아닙니다.
3. **캐시에 올라오는 데이터는 어떻게 관리되나요?** — 주소의 태그로 원하는 라인인지 확인하고 유효 비트로 사용 가능 여부를 판단합니다. 미스가 나면 하위 계층에서 라인을 가져오고, 자리가 없으면 교체 정책으로 희생 라인을 고릅니다. 쓰기는 하위 계층에도 반영하는 write-through와, dirty로 표시했다가 나중에 반영하는 write-back 등이 있습니다. 쓰기 미스 시 라인을 가져올지도 write-allocate 정책으로 결정합니다. 실제 CPU의 교체 정책을 정확한 LRU라고 단정하지 않습니다.
4. **캐시간의 동기화는 어떻게 이루어지나요?** — 여러 코어가 같은 메모리의 복사본을 가질 때 MESI 계열의 캐시 일관성 프로토콜이 라인의 상태와 쓰기 소유권을 관리합니다. 한 코어가 쓰기 권한을 얻으면 다른 복사본을 무효화하는 방식 등이 쓰입니다. **캐시 일관성만으로 여러 주소에 대한 메모리 연산 순서나 복합 연산의 원자성이 보장되지는 않습니다.** 언어의 락·원자 연산·메모리 순서 규칙이 별도로 필요합니다. 서로 다른 변수가 같은 라인에 있어 경합하는 false sharing도 생길 수 있습니다.
5. **캐시 메모리의 Mapping 방식에 대해 설명해 주세요.** — Direct mapped는 메모리 블록마다 들어갈 위치가 하나라 단순하지만 충돌 미스가 많을 수 있습니다. Fully associative는 어느 위치든 가능하지만 태그 검색 비용이 큽니다. Set associative는 정해진 세트 안의 여러 위치 중 하나를 사용해 둘을 절충합니다. 예를 들어 8-way는 각 세트에 라인 8개를 둘 수 있다는 뜻입니다.
6. **캐시의 지역성에 대해 설명해 주세요.** — 시간 지역성은 최근 접근한 데이터를 가까운 미래에 다시 사용하는 성질이고, 공간 지역성은 인접 주소를 함께 사용하는 성질입니다. 반복문에서 같은 변수를 읽는 것은 전자, 배열을 순차 탐색하는 것은 후자의 예입니다.
7. **이차원 배열을 가로/세로로 탐색했을 때 성능 차이는?** — C의 행 우선 연속 배열에서는 행을 바깥 루프, 열을 안쪽 루프로 두면 인접 원소를 읽어 유리합니다. 열 우선 순회는 큰 간격으로 주소를 건너뛰어 캐시·TLB 미스가 늘 수 있습니다. 다만 열 우선 저장 언어에서는 반대이고, **Java의 `int[][]`는 행 배열에 대한 참조 배열**이라 전체가 하나로 연속 배치되지는 않습니다. 그래도 한 행의 `int[]`를 순서대로 읽는 편이 지역성을 활용하기 좋습니다.
8. **캐시의 공간 지역성은 어떻게 구현될 수 있을까요?** — 연속된 여러 바이트를 하나의 캐시 라인으로 가져옵니다. 예를 들어 64바이트 라인이라면 4바이트 정수 16개 분량이 함께 들어오므로 다음 원소 접근이 히트할 수 있습니다. 라인 크기와 정렬 경계에 따라 실제 포함 범위는 달라집니다. 하드웨어 프리페처도 순차 패턴을 감지해 다음 라인을 미리 가져올 수 있습니다.

**핵심 키워드** → 메모리 계층, 캐시 라인, 지역성, set associative, write-back, 캐시 일관성

## 2. 메모리의 연속할당 방식 세 가지를 설명해주세요. (first-fit, best-fit, worst-fit)

**세 방식은 요청한 크기를 수용할 수 있는 연속된 빈 공간 중 어디에 메모리를 배치할지 결정하는 정책입니다.**

First-fit은 정해진 탐색 순서에서 처음으로 충분한 공간을 찾으면 배치합니다. Best-fit은 들어갈 수 있는 공간 중 가장 작은 곳을 골라 이번 할당의 잔여 공간을 최소화합니다. Worst-fit은 가장 큰 공간을 골라 남는 공간도 크게 유지하려고 합니다.

예를 들어 빈 공간이 순서대로 100, 500, 200, 300KB이고 180KB를 요청하면, first-fit과 worst-fit은 500KB, best-fit은 200KB를 선택합니다.

세 방식 모두 할당과 해제를 반복하면 **총 빈 공간은 충분하지만 연속된 큰 공간이 없는 외부 단편화**가 발생할 수 있습니다. 인접 빈 공간을 병합하면 완화되지만, 모든 단편화가 해결되지는 않습니다.

### 꼬리질문 대비

1. **worst-fit은 언제 사용할 수 있을까요?** — 작은 조각 대신 재사용 가능한 큰 잔여 공간을 남기려는 의도로 사용할 수 있습니다. 예를 들어 190KB와 1,000KB 빈 공간에 180KB를 배치하면, 큰 쪽을 골라 820KB를 남길 수 있습니다. 하지만 이후 900KB 요청이 오면 실패하므로 미래 요청에 따라 불리해집니다. 가장 큰 공간을 소모한다는 단점도 있어 일반적인 최선의 선택이라고 하지는 않습니다.
2. **성능이 가장 좋은 알고리즘은 무엇일까요?** — 탐색 비용과 단편화 중 무엇을 평가하는지, 빈 공간을 어떤 자료구조로 관리하는지, 요청 크기 분포가 어떤지에 따라 다릅니다. 단순 리스트에서 first-fit은 일찍 멈출 수 있어 실용적입니다. Best-fit은 작은 잔여 조각을 많이 만들 수 있고, best/worst-fit의 탐색 비용은 크기별 트리·리스트를 쓰면 달라집니다. **이번 할당의 낭비가 최소라고 전체 성능이 최선인 것은 아닙니다.**

참고: [OSTEP — Free-Space Management](https://pages.cs.wisc.edu/~remzi/OSTEP/vm-freespace.pdf)

**핵심 키워드** → 빈 공간 선택, 탐색 비용, 외부 단편화, 병합

## 3. Thrashing이란 무엇인가요?

**스래싱은 필요한 페이지를 메모리에 유지하지 못해, 실제 작업보다 페이지를 내보내고 다시 가져오는 데 지나치게 많은 시간을 쓰는 상태입니다.**

주된 원인은 동시에 실행하는 작업들의 워킹 셋이 가용 물리 메모리를 초과하는 것입니다. 방금 내보낸 페이지를 곧 다시 요청하고, 이를 가져오느라 다른 필요한 페이지를 내보내는 악순환이 생깁니다.

전형적인 상황에서는 페이지 폴트와 저장장치 I/O가 늘고 처리량이 떨어집니다. CPU 사용률이 낮다는 이유만으로 작업 수를 늘리면 메모리 경쟁이 더 심해질 수 있습니다. 다만 **페이지 폴트가 많다는 사실만으로 스래싱이라고 판단하지는 않습니다.** 최초 접근에 따른 minor fault인지, 지속적인 재적재와 지연을 동반하는지 함께 봐야 합니다.

### 꼬리질문 대비

1. **Thrashing 발생 시, 어떻게 완화할 수 있을까요?** — 동시에 실행하는 작업 수를 줄여 워킹 셋을 수용하게 하고, 충분한 프레임을 할당하거나 물리 메모리를 늘립니다. 애플리케이션에서는 과도한 캐시·배치 크기를 줄이고 접근 지역성을 개선할 수 있습니다. OS 정책으로는 워킹 셋 모델이나 페이지 폴트 빈도(PFF)를 활용해 할당량과 실행 작업 수를 조절합니다. 지역 교체는 다른 프로세스로의 피해 확산을 제한할 뿐, 전체 메모리 부족을 해결하지는 못합니다. 스왑 용량만 늘려도 RAM 접근 속도가 빨라지는 것은 아닙니다.

**핵심 키워드** → 워킹 셋, 메모리 압박, 반복 재적재, 동시 실행 수 제어

## 4. 가상 메모리란 무엇인가요?

**가상 메모리는 프로세스가 사용하는 주소 공간을 실제 물리 메모리와 분리하는 추상화입니다.** 프로세스는 자신의 주소 공간을 사용하고, MMU와 OS가 그 주소를 물리 주소로 변환하고 접근 권한을 검사합니다.

이 덕분에 프로세스 사이를 격리하고, 같은 가상 주소를 서로 다른 물리 메모리에 연결하거나 일부 메모리를 공유할 수 있습니다. 또 지금 필요한 부분만 RAM에 올리는 요구 페이징으로 물리 메모리보다 큰 주소 공간을 다룰 수 있습니다.

따라서 가상 메모리를 단순히 '디스크를 RAM처럼 쓰는 기술'이라고 설명하면 부족합니다. **주소 변환·보호·공유가 기본이며, 스왑은 메모리 압박에 대응하는 한 수단**입니다. 스왑 없이도 가상 메모리는 사용할 수 있습니다.

### 꼬리질문 대비

1. **가상 메모리가 가능한 이유가 무엇일까요?** — 하드웨어의 주소 변환·보호 기능과 OS의 매핑 관리가 있기 때문입니다. 필요한 페이지만 적재하는 방식이 실용적인 이유는 프로그램이 한동안 주소 공간의 일부에 집중하는 지역성 때문입니다. 지역성이 부족하거나 워킹 셋이 너무 크면 성능 이점이 무너질 수 있습니다.
2. **Page Fault가 발생했을 때 어떻게 처리하나요?** — CPU가 예외를 발생시키면 커널이 주소와 접근 권한을 검사합니다. 유효한 접근이라면 원인에 따라 새 페이지를 0으로 채우거나, COW 복사본을 만들거나, 파일·스왑에서 내용을 읽습니다. 필요한 경우 다른 페이지를 회수해 프레임을 확보하고, 매핑과 관련 TLB 상태를 정리한 뒤 명령을 재시도합니다. 유효하지 않은 접근이면 Linux에서는 보통 `SIGSEGV`를 전달합니다. **모든 페이지 폴트가 디스크 I/O를 일으키지는 않습니다.**
3. **페이지 크기에 대한 Trade-Off를 설명해 주세요.** — 큰 페이지는 같은 메모리를 더 적은 엔트리로 매핑하므로 페이지 테이블 부담을 줄이고 TLB 도달 범위(TLB reach)를 늘립니다. 반면 일부만 사용해도 큰 단위를 확보해야 하므로 내부 단편화가 늘 수 있고, 연속 물리 공간 확보도 어려워질 수 있습니다. 작은 페이지는 세밀하게 관리할 수 있지만 매핑과 TLB 부담이 커집니다.
4. **페이지 크기가 커지면 페이지 폴트가 더 많이 발생한다고 할 수 있나요?** — 단정할 수 없습니다. 순차 접근에서는 한 번에 더 넓은 범위를 확보해 폴트 횟수가 줄 수 있습니다. 반면 드문드문 접근하면 쓰지 않는 부분이 RAM을 차지해 실제 필요한 페이지가 밀려날 수 있습니다. 접근 패턴·가용 메모리·적재 및 회수 정책에 따라 달라지며, **폴트 횟수와 폴트 한 번의 비용도 구분**해야 합니다.
5. **세그멘테이션 방식이면 가상 메모리를 사용할 수 없을까요?** — 사용할 수 있습니다. 가상 메모리는 주소 공간 추상화이고, 세그멘테이션과 페이징은 이를 구현하는 방식입니다. 세그먼트 테이블로 논리 주소를 변환하고 필요한 세그먼트만 적재할 수 있으며, 세그먼트를 다시 페이지로 나누는 혼합 방식도 가능합니다.

주소 변환과 폴트 처리 근거: [Linux — Page Tables](https://docs.kernel.org/mm/page_tables.html)

**핵심 키워드** → 주소 공간, 격리, 요구 페이징, COW, minor/major fault, TLB reach

## 5. 세그멘테이션과 페이징의 차이점은 무엇인가요?

**세그멘테이션은 코드·데이터·스택 같은 논리적 단위를 가변 크기로 나누고, 페이징은 주소 공간을 고정 크기의 페이지로 나눕니다.**

순수 세그멘테이션에서는 세그먼트 번호와 오프셋으로 주소를 표현하고, 테이블의 base와 limit으로 위치와 범위를 확인합니다. 논리 단위별 보호와 공유에 자연스럽지만, 크기가 서로 달라 외부 단편화가 생깁니다.

페이징에서는 가상 페이지를 같은 크기의 물리 프레임에 연결합니다. 한 프로세스의 페이지들이 물리 메모리에서 연속될 필요가 없어 기본 페이지 할당의 외부 단편화를 피할 수 있지만, 마지막 페이지 등의 미사용 공간에서 내부 단편화가 생깁니다. 주소 변환을 위한 페이지 테이블도 필요합니다.

현대 범용 OS를 설명할 때는 페이징을 중심으로 답하되, 하드웨어나 실행 모드에 따라 세그멘테이션의 사용 범위가 달라진다는 점을 구분하겠습니다.

### 꼬리질문 대비

1. **페이지와 프레임의 차이는?** — 페이지는 가상 주소 공간을 나눈 단위이고 프레임은 물리 메모리를 나눈 단위입니다. 해당 매핑에서 둘의 크기가 같고, 페이지 테이블이 가상 페이지 번호를 물리 프레임 번호에 연결합니다.
2. **내부 단편화와 외부 단편화는?** — 내부 단편화는 할당받은 공간 내부의 낭비, 외부 단편화는 할당 영역 사이에 흩어진 빈 공간입니다. 4KiB 페이지에 1KiB만 사용하면 나머지 3KiB는 내부 단편화입니다. 3KiB 빈 공간 두 개가 떨어져 있어 5KiB 연속 요청을 못 받는 것은 외부 단편화입니다. 페이징도 큰 연속 물리 영역을 요구하는 huge page 등에서는 물리 메모리 단편화의 영향을 받습니다.
3. **페이지에서 실제 주소를 어떻게 가져오나요?** — 가상 주소를 페이지 번호와 오프셋으로 나눕니다. TLB 또는 페이지 테이블에서 프레임 번호와 권한을 확인한 뒤, `물리 주소 = 프레임 번호 × 페이지 크기 + 오프셋`으로 계산합니다. 예를 들어 4KiB 페이지에서 가상 주소 `0x1234`는 페이지 번호 1, 오프셋 `0x234`입니다. 1번 페이지가 9번 프레임에 대응하면 물리 주소는 `0x9234`입니다.
4. **어떤 주소공간이 수정 가능한지 확인할 수 있나요?** — OS의 가상 메모리 영역 정보와 페이지 테이블의 쓰기 권한을 봅니다. CPU는 사용자/커널 모드와 페이지 보호 비트 등을 검사합니다. 단, **PTE가 읽기 전용이라고 항상 최종 쓰기 불가인 것은 아닙니다.** COW 영역은 쓰기 폴트를 처리해 전용 복사본을 만든 뒤 쓰기를 허용할 수 있습니다. 언어의 `const`나 `final`도 OS 페이지 권한과 같은 개념이 아닙니다.
5. **32비트에서 페이지 크기가 1KB라면 페이지 테이블의 최대 크기는 몇 개인가요?** — 바이트 주소 방식, 전체 32비트 가상 주소 공간, **1KiB = 2¹⁰바이트**를 가정하면 페이지 수는 `2³² / 2¹⁰ = 2²² = 4,194,304개`입니다. 이는 전체 공간을 덮는 단일 단계 페이지 테이블의 **엔트리 수**입니다. 엔트리가 4바이트라면 테이블은 16MiB입니다. 엔트리 크기와 다단계 구조가 주어지지 않으면 테이블의 실제 바이트 크기까지 확정할 수 없습니다.
6. **32비트 운영체제는 RAM을 최대 4GB까지만 사용할 수 있는 이유는?** — 질문의 전제를 먼저 구분해야 합니다. 32비트 가상 주소는 바이트 주소 기준 `2³² = 4GiB`의 주소 공간을 표현합니다. 4KiB 페이지라면 페이지 번호 20비트와 오프셋 12비트입니다. 하지만 **가상 주소 폭과 물리 주소 폭은 같아야 하는 것이 아닙니다.** x86 PAE처럼 더 넓은 물리 주소를 페이지 테이블로 표현하면 32비트 OS도 4GiB를 넘는 RAM을 관리할 수 있습니다. 개별 프로세스의 가상 주소 공간 한계는 그대로이고, 사용자 공간은 커널 예약 때문에 그보다 작을 수도 있습니다. [Linux — High Memory / i386 PAE](https://docs.kernel.org/mm/highmem.html)
7. **Segmentation Fault는 세그멘테이션/페이징과 어떤 관계가 있나요?** — 이름 때문에 세그멘테이션 방식에서만 생긴다고 생각하면 안 됩니다. 페이징 시스템에서도 매핑되지 않은 주소에 접근하거나 쓰기 금지 페이지에 쓰면 발생할 수 있습니다. 하드웨어 예외를 OS가 복구할 수 없을 때 `SIGSEGV`를 전달하는 것이 전형적인 경로입니다. 반대로 정상적인 요구 페이징 폴트는 복구 후 실행이 계속됩니다. C/C++의 잘못된 접근은 미정의 동작이므로 항상 이 신호로 나타나는 것도 아닙니다.

## 6. TLB는 무엇인가요?

**TLB는 최근에 사용한 가상 주소에서 물리 주소로의 변환 정보와 접근 권한을 보관하는 하드웨어 캐시입니다.** 일반 데이터 캐시가 데이터 자체를 보관한다면, TLB는 주소 변환 결과를 보관합니다.

매번 다단계 페이지 테이블을 따라가면 실제 데이터 접근에 앞서 여러 메모리 접근이 필요합니다. TLB가 적중하면 이 탐색을 생략할 수 있어 빨라집니다.

TLB 미스는 변환 정보가 캐시에 없다는 뜻이므로 페이지 폴트와 다릅니다. 페이지 테이블에 유효한 매핑이 있으면 변환을 찾아 TLB에 채우고 계속 실행할 수 있습니다.

### 꼬리질문 대비

1. **TLB를 쓰면 왜 빨라지나요?** — 반복 접근 시 페이지 테이블 탐색을 줄입니다. 단일 단계 테이블, 캐시 없음, 폴트 없음이라는 교육용 모델에서 메모리 접근 시간을 `m`, TLB 조회 시간을 `t`, 적중률을 `h`라 하면 평균은 `h(t+m) + (1-h)(t+2m)`입니다. 실제 CPU는 다단계 테이블·페이지 워크 캐시·병렬 조회 등이 있어 이 식 그대로 동작하지는 않습니다.
2. **MMU가 무엇인가요?** — 가상 주소를 물리 주소로 변환하고 접근 권한을 검사하는 하드웨어입니다. TLB는 이 변환을 빠르게 하는 구성 요소입니다. OS가 페이지 테이블을 관리하고 MMU가 참조합니다. TLB 미스 시 테이블 탐색을 하드웨어가 하는지 소프트웨어가 처리하는지는 아키텍처에 따라 다릅니다.
3. **TLB와 MMU는 어디에 위치해 있나요?** — 현대 CPU 내부의 주소 변환 경로에 있습니다. 명령어용·데이터용 TLB가 나뉘고 추가 단계의 TLB가 있을 수 있습니다. 보통 코어에 가까이 배치되며, 세부 공유 구조는 CPU마다 다릅니다.
4. **코어가 여러 개라면 TLB를 어떻게 동기화하나요?** — 페이지 매핑이나 권한을 바꿨을 때 오래된 변환을 가진 코어의 TLB 엔트리를 무효화해야 합니다. 이를 TLB shootdown이라고 하며, OS가 관련 코어에 IPI를 보내거나 아키텍처가 제공하는 무효화 기능을 사용합니다. 필요한 무효화가 끝나기 전에 프레임을 재사용하면 다른 코어가 잘못된 메모리에 접근할 수 있습니다. 일반 데이터 캐시의 일관성 프로토콜만으로 TLB까지 자동 갱신된다고 가정하지 않습니다.
5. **Context Switching 시 TLB에는 어떤 변화가 있나요?** — 다른 주소 공간으로 전환하면 같은 가상 주소가 다른 물리 주소를 가리킬 수 있습니다. 주소 공간 태그가 없으면 기존 사용자 매핑을 비우거나 무효화해야 합니다. ASID·PCID가 있으면 주소 공간을 구분해 여러 프로세스의 변환을 유지할 수 있지만, 매핑 변경이나 태그 재사용 시에는 무효화가 필요합니다. 같은 프로세스의 스레드끼리 전환할 때는 주소 공간이 같으므로 전환 자체만으로 전체 TLB를 비울 필요가 없습니다.

동기화 근거: [Linux — Cache and TLB Flushing](https://docs.kernel.org/core-api/cachetlb.html)

**핵심 키워드** → 주소 변환 캐시, MMU, page walk, shootdown, ASID/PCID

## 7. 페이지 교체 알고리즘에 대해 설명해 주세요.

**페이지 교체 알고리즘은 빈 프레임이 부족할 때 어떤 페이지를 메모리에서 내보낼지 고르는 정책입니다.** 이후 다시 필요한 페이지를 내보내면 폴트와 I/O가 늘므로, 가까운 미래에 덜 사용할 페이지를 고르는 것이 목표입니다.

FIFO는 가장 먼저 들어온 페이지를 내보내므로 단순하지만 자주 쓰는 페이지도 제거할 수 있고, 프레임을 늘렸는데 폴트가 증가하는 Belady의 모순도 가능합니다. OPT는 미래에 가장 늦게 사용할 페이지를 고르는 최적 기준이지만 미래를 알 수 없어 비교 기준으로 씁니다.

LRU는 가장 오래 사용하지 않은 페이지를 내보냅니다. 최근 사용 기록으로 미래를 예측하는 방식입니다. 정확한 LRU는 매 접근을 추적하는 비용이 커서, OS에서는 참조 비트를 이용하는 Clock 같은 근사 방식이나 세대 기반 관리 등을 사용합니다.

또 같은 조건이라면 수정되지 않은 파일 페이지는 버리고 다시 읽을 수 있지만, dirty 페이지는 내용 보존을 위한 쓰기가 필요할 수 있어 회수 비용도 고려해야 합니다.

### 꼬리질문 대비

1. **LRU는 어떤 특성을 이용하나요?** — 최근에 접근한 데이터가 다시 사용될 가능성이 높다는 **시간 지역성**을 이용합니다. 과거를 기반으로 한 예측이므로 모든 접근 패턴에서 최적인 것은 아닙니다.
2. **LRU를 구현한다면 어떻게 하나요?** — 애플리케이션 캐시라면 `해시맵 + 이중 연결 리스트`로 구현합니다. 맵은 키에서 노드를 찾고, 접근한 노드를 리스트의 최근 사용 쪽으로 옮깁니다. 용량을 넘으면 가장 오래된 쪽 노드를 제거합니다. 조회·갱신·퇴출은 평균 O(1), 공간은 O(C)입니다. OS 페이지 교체에서는 모든 메모리 참조마다 소프트웨어 리스트를 갱신하기 어려워 같은 구현을 그대로 적용하지 않습니다.
3. **LRU의 단점과 대안은?** — 접근마다 순서를 갱신하는 비용과 동시 접근 시 경합이 생깁니다. 캐시보다 큰 데이터를 한 번 훑으면 재사용할 항목까지 밀어내는 스캔 오염도 발생합니다. Clock은 참조 비트를 검사해 최근 사용 페이지에 한 번 더 기회를 주어 관리 비용을 줄입니다. 스캔 오염에는 재사용 이력을 추가로 구분하는 2Q·ARC 같은 정책이 대안이 될 수 있습니다. Linux의 Multi-Gen LRU도 세대별 최근성을 관리하는 구현이며, 사용 여부는 커널 설정에 따라 다릅니다. [Linux — Multi-Gen LRU](https://docs.kernel.org/admin-guide/mm/multigen_lru.html)

교체 정책 비교: [OSTEP — Beyond Physical Memory: Policies](https://pages.cs.wisc.edu/~remzi/OSTEP/vm-beyondphys-policy.pdf)

**핵심 키워드** → FIFO, OPT, LRU, Clock, 시간 지역성, dirty page

## 8. File Descriptor와 File System에 대해 설명해 주세요.

**파일 디스크립터는 프로세스가 열린 파일이나 소켓 같은 I/O 자원을 참조하기 위해 사용하는 작은 정수입니다. 파일 시스템은 파일의 이름·메타데이터·내용을 조직하고 저장·조회하는 체계입니다.**

Unix 계열에서는 `open()`이 성공하면 FD를 반환하고, 프로세스는 `read`, `write`, `close` 등에 이를 전달합니다. 커널은 프로세스의 FD 테이블을 통해 열린 파일 상태에 접근합니다. FD는 프로세스별 번호이므로 서로 다른 프로세스에서 같은 번호를 써도 같은 파일이라는 뜻은 아닙니다.

열린 파일 상태에는 현재 오프셋과 상태 플래그 등이 있습니다. `dup`이나 `fork`로 같은 open file description을 공유하면 파일 오프셋도 공유할 수 있습니다. 반대로 같은 경로를 별도로 `open`하면 보통 서로 다른 열린 파일 상태를 갖습니다. [Linux — open(2)](https://man7.org/linux/man-pages/man2/open.2.html)

파일 시스템은 디렉터리에서 이름을 찾고, 메타데이터와 저장된 내용을 연결합니다. 파일 시스템은 디스크 기반뿐 아니라 메모리·네트워크·가상 파일 시스템도 있습니다.

### 꼬리질문 대비

1. **I-Node가 무엇인가요?** — Unix 계열 파일 시스템에서 파일의 종류·권한·소유자·크기·시간·링크 수 등 메타데이터를 나타내는 구조입니다. 데이터 위치를 나타내는 방식은 파일 시스템마다 다릅니다. **파일 이름은 일반적으로 inode 자체가 아니라 디렉터리 엔트리의 이름→inode 연결에 있습니다.** 그래서 여러 이름이 같은 inode를 가리키는 하드 링크가 가능합니다. 경로를 삭제해도 열린 참조가 남아 있으면 파일 내용을 계속 사용할 수 있고, 일반적으로 링크와 열린 참조가 모두 없어져야 저장 공간을 회수할 수 있습니다. inode 번호는 파일 시스템 안에서 해석해야 합니다. [Linux — inode(7)](https://man7.org/linux/man-pages/man7/inode.7.html)
2. **Python `open()`, Java `BufferedReader/Writer` 등은 어떻게 읽고 쓰나요?** — 일반적인 로컬 파일의 버퍼 I/O에서는 `언어의 버퍼 → 파일 스트림/런타임 → OS 시스템 콜 → 커널 페이지 캐시 → 저장장치`가 연결됩니다. 매번 디스크를 읽는 것은 아니며 페이지 캐시가 적중하면 RAM에서 처리할 수 있습니다. Java의 `BufferedReader`는 다른 `Reader`를 감싸 문자 데이터를 버퍼링하므로 그 자체가 파일을 여는 클래스는 아닙니다. 파일을 읽을 때 `InputStreamReader` 등이 바이트를 문자로 디코딩합니다. Python도 기본 텍스트 모드에서는 버퍼링과 디코딩 계층을 사용합니다. 사용자 버퍼의 `flush()`는 데이터를 다음 계층으로 넘기는 것이므로 저장장치에 영구 반영됐다는 보장과 다릅니다. 내구성이 필요하면 `fsync` 등 별도 동기화 의미를 확인해야 합니다. [Java — BufferedReader](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/io/BufferedReader.html), [Python — open](https://docs.python.org/3/library/functions.html#open)

**핵심 키워드** → FD 테이블, open file description, inode, 디렉터리 엔트리, 버퍼, 페이지 캐시

## 9. GC에 대해 설명해 주세요.

**GC는 프로그램에서 더 이상 사용할 수 없는 객체의 메모리를 런타임이 자동으로 찾아 회수하는 기능입니다.** Java의 추적 방식 GC는 단순히 '최근 사용하지 않은 객체'를 지우는 것이 아니라, GC Roots에서 참조를 따라 도달할 수 있는지를 기준으로 판단합니다.

대표적인 방식은 살아 있는 객체를 표시한 뒤 나머지를 회수하는 mark-sweep, 살아 있는 객체를 옮겨 모으는 copying·compaction 등입니다. 실제 수집기는 이런 기법을 조합하고, 작업 일부를 애플리케이션과 동시에 수행하기도 합니다.

개발자가 직접 메모리를 해제하는 부담과 오류를 줄이는 대신, CPU·메모리 비용과 실행 중단 시간이 발생할 수 있습니다. 또한 필요 없는 객체를 컬렉션이나 static 필드가 계속 참조하면 살아 있는 객체로 판단하므로 **GC가 있어도 메모리 누수는 생길 수 있습니다.**

### 꼬리질문 대비

1. **본인이 사용하는 언어에서는 GC를 어떻게 구현했나요?** — Java에서는 JVM의 수집기에 따라 다릅니다. 면접에서는 익숙한 구현으로 **HotSpot G1을 예로 들어** 설명하겠습니다. G1은 힙을 리전으로 나누고 세대별로 관리합니다. 살아 있는 객체를 다른 리전으로 옮겨 공간을 확보하고, 동시 마킹으로 생존 정보를 얻은 뒤 일부 Old 리전을 Young 리전과 함께 회수하는 mixed collection을 수행합니다. 모든 단계가 동시 실행되는 것은 아니며 evacuation 등의 STW 구간이 있습니다. 일시 정지 목표는 보장 시간이 아닙니다. 실제 사용하는 수집기는 실행 옵션과 GC 로그로 확인해야 하며 'Java는 항상 G1'이라고 답하지 않습니다. [Oracle — G1 GC, Java 21](https://docs.oracle.com/en/java/javase/21/gctuning/garbage-first-g1-garbage-collector1.html)
2. **GC의 장단점은?** — 수동 해제의 누락·중복 해제·해제 후 사용 위험을 줄이고 메모리 관리를 단순화합니다. 반면 수집 작업이 CPU를 쓰고 여유 메모리가 필요하며, 정지 시간과 회수 시점을 예측하기 어려울 수 있습니다. 수집기마다 처리량·지연·메모리 사용량 사이의 선택이 다릅니다. 파일·소켓 같은 외부 자원은 GC에 맡기지 않고 Java의 try-with-resources 등으로 명시적으로 닫습니다.
3. **GC는 어떤 영역의 데이터를 관리하나요?** — Java에서는 주로 **힙에 있는 객체와 배열**을 회수합니다. 스택 프레임은 메서드 호출과 반환에 따라 관리되며, 그 안의 살아 있는 참조는 객체 생존 판단의 출발점이 될 수 있습니다. static 참조·JNI 참조 등도 도달성에 영향을 줍니다. 클래스 메타데이터는 힙 밖의 Metaspace에 있지만 클래스 언로딩과 연계해 회수될 수 있습니다. GC가 JVM 프로세스의 네이티브 메모리와 모든 외부 자원을 일괄 관리한다고 설명하지 않습니다.
4. **Reference Counting과 순환 참조·Retain Cycle은?** — 강한 참조가 생기거나 사라질 때 참조 수를 증감하고, 0이 되면 회수하는 방식입니다. 순수 참조 계수에서는 A와 B가 서로 강하게 참조하면 외부 참조를 끊어도 각자의 계수가 0이 되지 않아 회수하지 못합니다. 이것이 retain cycle입니다. 약한 참조로 소유 관계의 순환을 끊거나 별도의 순환 탐지기를 사용할 수 있습니다. Java의 추적 GC는 루트에서 도달할 수 없는 A↔B 전체를 회수할 수 있으므로 **순환 자체가 Java에서 항상 누수인 것은 아닙니다.** 참조 계수도 매 참조 변경의 비용과 연쇄 해제 비용이 있어 언제나 지연이 작은 것은 아닙니다.
