## 1. 쿠키와 세션의 차이에 대해 설명해 주세요.

**쿠키는 서버가 내려준 작은 데이터를 브라우저가 저장했다가 요청마다 보내는 방식이고, 세션은 상태 데이터를 서버 쪽에 두고 클라이언트에는 그것을 찾을 식별자만 주는 방식입니다.**

쿠키는 `Set-Cookie` 응답 헤더로 생성되고, 이후 도메인·경로 조건이 맞는 요청에 `Cookie` 헤더로 자동 전송됩니다. 값이 클라이언트에 있으므로 사용자가 보거나 바꿀 수 있고, 크기도 보통 쿠키 하나당 4KB 안팎으로 제한됩니다.

세션은 서버가 세션 저장소에 사용자 정보를 두고, 그 키인 세션 ID를 보통 쿠키로 전달합니다. **세션도 대개 쿠키를 운반 수단으로 쓰므로 '쿠키 대 세션'은 저장 위치의 차이**로 설명하는 것이 정확합니다. 민감한 정보는 서버에 두기 때문에 상대적으로 안전하지만, 사용자 수만큼 서버 메모리나 저장소를 사용합니다.

세션 ID 쿠키에는 `HttpOnly`(스크립트 접근 차단), `Secure`(HTTPS에서만 전송), `SameSite`(교차 사이트 요청 시 전송 제한)를 설정해 탈취와 CSRF 위험을 줄입니다.

### 꼬리질문 대비

1. **세션 방식의 로그인 과정에 대해 설명해 주세요.** — ① 클라이언트가 아이디·비밀번호를 HTTPS로 보냅니다. ② 서버가 해시된 비밀번호와 비교해 인증합니다. ③ 성공하면 추측하기 어려운 무작위 세션 ID를 만들고, 저장소에 `세션 ID → 사용자 정보`를 저장합니다. 이때 로그인 전 세션 ID를 그대로 쓰지 않고 **새로 발급해 세션 고정 공격을 막습니다.** ④ `Set-Cookie: SESSIONID=...; HttpOnly; Secure; SameSite=Lax`로 내려줍니다. ⑤ 이후 요청마다 브라우저가 쿠키를 보내고 서버는 저장소에서 사용자를 찾습니다. ⑥ 로그아웃하거나 만료 시간이 지나면 서버에서 세션을 삭제합니다.
2. **HTTP의 특성인 Stateless에 대해 설명해 주세요.** — 서버가 이전 요청의 상태를 프로토콜 차원에서 기억하지 않는다는 뜻입니다. 각 요청은 처리에 필요한 정보를 스스로 담고 있어야 하며, 서버는 그 요청만 보고 응답할 수 있어야 합니다. 그래서 어느 서버가 요청을 받아도 처리할 수 있어 수평 확장에 유리합니다.
3. **Stateless의 의미를 살펴보면, 세션은 적절하지 않은 인증 방법 아닌가요?** — Stateless는 **HTTP 프로토콜**이 상태를 유지하지 않는다는 뜻이지, 그 위의 애플리케이션이 상태를 가지면 안 된다는 뜻은 아닙니다. 세션은 상태가 필요한 애플리케이션이 HTTP 위에 상태를 얹는 방법입니다. 매 요청이 세션 ID를 들고 오므로 메시지 단위로는 여전히 자기 완결적입니다. 다만 서버가 상태를 갖게 되면 확장과 장애 대응이 복잡해지는 것은 사실이라, 그 트레이드오프로 JWT 같은 토큰 방식을 고르기도 합니다. 토큰은 서버 저장소 조회가 줄지만 발급한 토큰을 즉시 무효화하기 어렵고 페이로드가 커지는 단점이 있습니다. 어느 쪽이 항상 낫다고 하지 않습니다.
4. **규모가 커져 서버가 여러 개가 된다면, 세션을 어떻게 관리할 수 있을까요?** — 서버마다 메모리에 세션을 두면 다른 서버로 간 요청은 로그인 정보를 찾지 못합니다. 해결책은 세 가지입니다. ① **Sticky Session**: 로드 밸런서가 같은 사용자를 같은 서버로 보냅니다. 단순하지만 부하가 쏠리고 그 서버가 죽으면 세션이 사라집니다. ② **세션 복제(clustering)**: 서버끼리 세션을 복사합니다. 서버가 늘수록 복제 트래픽과 메모리가 커집니다. ③ **외부 세션 저장소**: Redis 같은 공용 저장소에 세션을 둡니다. 서버는 상태가 없어져 확장이 쉽지만 저장소가 단일 장애점이 되지 않도록 복제·클러스터 구성이 필요합니다. 실무에서는 보통 ③을 많이 씁니다. Spring에서는 Spring Session으로 저장소를 바꿀 수 있습니다.

**핵심 키워드** → 저장 위치, `Set-Cookie`, 세션 ID, HttpOnly/Secure/SameSite, 세션 고정, Sticky Session, Redis

## 2. HTTP 응답코드에 대해 설명해 주세요.

**응답코드는 서버가 요청을 어떻게 처리했는지 세 자리 숫자로 알려주는 값이고, 첫 자리로 분류합니다.**

| 범위 | 의미 | 예시 |
|---|---|---|
| 1xx | 정보, 처리 계속 | 100 Continue, 101 Switching Protocols |
| 2xx | 성공 | 200 OK, 201 Created, 204 No Content |
| 3xx | 리다이렉션 | 301 Moved Permanently, 302 Found, 304 Not Modified |
| 4xx | 클라이언트 오류 | 400 Bad Request, 401, 403, 404, 409 Conflict, 429 Too Many Requests |
| 5xx | 서버 오류 | 500 Internal Server Error, 502 Bad Gateway, 503 Service Unavailable |

API를 설계할 때는 모든 응답을 200으로 보내고 본문에 실패를 적기보다, 상황에 맞는 코드를 써야 클라이언트·프록시·모니터링 도구가 결과를 올바르게 해석합니다. 4xx는 요청을 고쳐야 하는 문제, 5xx는 같은 요청을 재시도할 여지가 있는 서버 쪽 문제라는 구분이 특히 중요합니다.

### 꼬리질문 대비

1. **401 (Unauthorized) 와 403 (Forbidden)은 의미적으로 어떤 차이가 있나요?** — 401은 **인증(Authentication)이 없거나 유효하지 않음**, 즉 "누구인지 모른다"입니다. 로그인하거나 유효한 토큰을 보내면 해결될 수 있고, 표준상 `WWW-Authenticate` 헤더로 인증 방법을 알려줍니다. 이름은 Unauthorized지만 실제 의미는 Unauthenticated에 가깝습니다. 403은 **누구인지는 알지만 권한(Authorization)이 없음**입니다. 다시 인증해도 결과가 같습니다. 일반 사용자가 관리자 API를 호출하는 경우가 예입니다. 리소스 존재 자체를 숨기고 싶으면 403 대신 404를 주기도 합니다.
2. **200 (ok) 와 201 (created) 의 차이에 대해 설명해 주세요.** — 200은 요청이 성공했다는 일반적인 응답입니다. 201은 그 결과 **새 리소스가 생성됐다**는 뜻이며, 보통 POST(또는 새로 만든 PUT)에 대한 응답으로 쓰고 `Location` 헤더에 생성된 리소스의 URI를 담습니다. 클라이언트는 201을 보고 생성 사실과 위치를 알 수 있습니다.
3. **필요하다면 저희가 직접 응답코드를 정의해서 사용할 수 있을까요? 예를 들어 285번 처럼요.** — 기술적으로는 보낼 수 있고, HTTP 명세상 클라이언트는 모르는 코드를 **같은 계열의 x00으로 취급**해야 하므로 285는 200처럼 처리됩니다. 하지만 공식 코드는 IANA 레지스트리에 등록된 것만 표준이고, 브라우저·프록시·라이브러리·모니터링 도구가 의미를 모르기 때문에 권장하지 않습니다. 세부 상황을 표현하고 싶으면 표준 코드를 쓰고 **응답 본문에 애플리케이션 에러 코드**를 담는 편이 낫습니다. RFC 9457의 Problem Details(`application/problem+json`) 형식이 그런 용도입니다.

**핵심 키워드** → 1xx~5xx, 인증 vs 인가, `Location`, 미지 코드는 x00 처리, Problem Details

## 3. HTTP Method 에 대해 설명해 주세요.

**HTTP 메서드는 대상 리소스에 어떤 동작을 원하는지 나타내는 요청의 동사입니다.**

- **GET**: 리소스 조회. 서버 상태를 바꾸지 않아야 합니다.
- **POST**: 리소스 생성이나 처리 요청. 의미가 가장 넓습니다.
- **PUT**: 대상 리소스를 요청 본문으로 통째로 대체합니다. 없으면 생성할 수도 있습니다.
- **PATCH**: 리소스의 일부를 수정합니다.
- **DELETE**: 리소스 삭제.
- **HEAD**: GET과 같지만 본문 없이 헤더만 받습니다.
- **OPTIONS**: 대상이 지원하는 통신 옵션을 확인합니다. CORS의 preflight 요청에 쓰입니다.

메서드는 **안전성**(서버 상태를 바꾸지 않음: GET, HEAD, OPTIONS)과 **멱등성**으로 분류하며, 이 성질에 따라 캐시와 재시도 가능 여부가 정해집니다.

### 꼬리질문 대비

1. **HTTP Method의 멱등성에 대해 설명해 주세요.** — 같은 요청을 한 번 보내든 여러 번 보내든 **서버에 의도한 효과가 같은** 성질입니다. GET, HEAD, OPTIONS, PUT, DELETE는 멱등이고 POST는 아닙니다. PATCH는 보장되지 않으며 설계에 따라 다릅니다(`count += 1` 형태는 멱등이 아님). DELETE를 두 번 보내면 두 번째는 404가 올 수 있지만, 서버 상태는 '삭제됨'으로 같으므로 멱등입니다. **멱등성은 응답이 아니라 서버 상태 기준**입니다. 이 성질이 중요한 이유는 타임아웃 때 응답을 못 받아도 멱등 요청은 안전하게 재시도할 수 있기 때문입니다. 결제처럼 POST를 재시도해야 하는 경우는 `Idempotency-Key` 같은 키로 중복 처리를 막습니다.
2. **GET과 POST의 차이는 무엇인가요?** — GET은 조회용으로 안전하고 멱등이며, 데이터를 주로 URL 쿼리 스트링에 담습니다. 응답은 캐시될 수 있고 URL이 북마크·기록에 남습니다. POST는 생성·처리용으로 멱등이 아니고 데이터를 본문에 담으며 기본적으로 캐시하지 않습니다. 흔히 "POST가 더 안전하다"고 하지만 **본문도 HTTP에서는 평문**이므로 보안은 HTTPS가 담당합니다. 다만 URL은 서버 로그·브라우저 기록·Referer에 남을 수 있어 민감한 값을 쿼리에 넣지 않는 것이 맞습니다. URL 길이는 명세상 제한이 없지만 브라우저와 서버 구현이 제한합니다.
3. **POST와 PUT, PATCH의 차이는 무엇인가요?** — POST는 보통 컬렉션(`/users`)에 보내고 **서버가 새 리소스의 URI를 정합니다.** 두 번 보내면 두 개가 생길 수 있어 멱등이 아닙니다. PUT은 클라이언트가 대상 URI(`/users/1`)를 지정하고 **리소스 전체를 대체**합니다. 보내지 않은 필드는 비워지거나 기본값이 될 수 있고, 같은 요청을 반복해도 결과가 같아 멱등입니다. PATCH는 **변경할 부분만** 보냅니다. JSON Merge Patch나 JSON Patch 같은 형식을 쓰며 멱등성은 보장되지 않습니다.
4. **HTTP 1.1 이후로, GET에도 Body에 데이터를 실을 수 있게 되었습니다. 그럼에도 불구하고 왜 아직도 이런 방식을 지양하는 것일까요?** — 명세(RFC 9110)가 GET 본문에 **정의된 의미가 없다**고 하고, 일부 구현이 이를 거부할 수 있다고 명시하기 때문입니다. 실제로 프록시·로드 밸런서·CDN이 본문을 버리거나 요청을 거절할 수 있고, 브라우저 `fetch`는 GET에 본문을 허용하지 않습니다. 캐시는 URL을 키로 쓰므로 본문이 다른 요청을 같은 응답으로 돌려줄 위험도 있습니다. 검색 조건이 너무 복잡하면 POST로 검색 API를 만들거나, 안전하고 멱등하면서 본문을 갖도록 제안된 **QUERY 메서드**를 검토할 수 있습니다(아직 표준화 진행 중).

**핵심 키워드** → 안전성, 멱등성, 재시도, Idempotency-Key, 전체 대체 vs 부분 수정, GET 본문은 의미 없음

## 4. HTTP에 대해 설명해 주세요.

**HTTP는 클라이언트와 서버가 요청과 응답으로 리소스를 주고받는 애플리케이션 계층 프로토콜입니다.** 클라이언트가 메서드·URI·헤더·본문으로 요청하면, 서버가 상태 코드·헤더·본문으로 응답합니다.

특징은 클라이언트-서버 구조, 무상태(Stateless), 그리고 HTTP/1.x 기준으로 TCP 위에서 동작한다는 점입니다. 헤더로 캐시·인증·콘텐츠 협상 같은 기능을 확장할 수 있습니다.

HTTP 자체는 평문이라 중간에서 내용을 엿보거나 바꿀 수 있습니다. 그래서 **HTTPS는 HTTP를 TLS 위에서 실행해 암호화·무결성·서버 인증을 더한 것**입니다. 꼬리질문이 TLS 쪽이라 HTTPS의 동작까지 이어서 설명하겠습니다.

TLS 1.3 기준 핸드셰이크는 ① 클라이언트가 지원하는 암호 스위트와 키 교환용 공개값을 보내고, ② 서버가 자기 공개값과 **인증서**, 그리고 인증서의 개인키로 핸드셰이크에 서명한 값을 보냅니다. ③ 클라이언트는 인증서 체인을 검증하고, 양쪽은 (EC)DHE 키 교환으로 같은 대칭키를 계산합니다. 이후 데이터는 그 대칭키로 암호화합니다.

### 꼬리질문 대비

1. **공개키와 대칭키에 대해 설명해 주세요.** — 대칭키 암호는 암호화와 복호화에 **같은 키**를 씁니다(AES 등). 빠르지만 키를 상대에게 안전하게 전달하는 문제가 있습니다. 공개키(비대칭키) 암호는 **공개키와 개인키 쌍**을 씁니다(RSA, ECC). 공개키로 암호화한 것은 개인키로만 풀 수 있고, 개인키로 서명한 것은 공개키로 검증할 수 있습니다. 키 배포 문제는 해결되지만 연산이 훨씬 느립니다. 그래서 HTTPS는 **비대칭 방식으로 인증과 키 합의를 하고, 실제 데이터는 대칭키로 암호화**하는 하이브리드 구조입니다. 참고로 TLS 1.3에서는 공개키로 대칭키를 직접 암호화해 보내는 RSA 키 교환이 제거되고, 전방 비밀성(forward secrecy)을 주는 (EC)DHE만 남았습니다.
2. **왜 HTTPS Handshake 과정에서는 인증서를 사용하는 것 일까요?** — 암호화만으로는 **지금 대화하는 상대가 진짜 서버인지** 알 수 없기 때문입니다. 공격자가 중간에서 자기 공개키를 주면 클라이언트는 공격자와 안전하게 암호화된 통신을 하게 됩니다(중간자 공격). 인증서는 "이 도메인의 공개키는 이것"이라는 내용에 신뢰할 수 있는 인증기관(CA)이 서명한 문서입니다. 브라우저는 OS·브라우저에 내장된 루트 CA부터 체인을 따라 서명을 검증하고, 도메인 일치·유효 기간·폐기 여부를 확인합니다. 그리고 서버가 그 인증서의 개인키를 실제로 가지고 있는지 핸드셰이크 서명으로 확인합니다.
3. **SSL과 TLS의 차이는 무엇인가요?** — TLS는 SSL의 후속 프로토콜입니다. SSL 3.0을 IETF가 표준화하면서 이름을 TLS 1.0으로 바꿨고, 이후 TLS 1.1, 1.2, 1.3으로 발전했습니다. SSL 2.0·3.0은 POODLE 같은 취약점 때문에 폐기됐고, TLS 1.0·1.1도 RFC 8996으로 폐기됐습니다. 현재는 TLS 1.2와 1.3을 씁니다. TLS 1.3은 핸드셰이크를 1-RTT로 줄이고, 오래된 암호 알고리즘과 RSA 키 교환을 제거했습니다. 관습적으로 'SSL 인증서'라고 부르지만 실제로는 TLS에 쓰입니다.

**핵심 키워드** → 요청/응답, 무상태, HTTPS = HTTP + TLS, 하이브리드 암호화, 인증서 체인, 중간자 공격, (EC)DHE, TLS 1.3

## 5. 웹소켓과 소켓 통신의 차이에 대해 설명해 주세요.

**소켓은 OS가 제공하는 네트워크 통신의 끝점이자 프로그래밍 인터페이스이고, 웹소켓은 그 위에서 동작하는 하나의 애플리케이션 계층 프로토콜입니다.** 둘은 같은 층위의 비교 대상이 아닙니다.

소켓(TCP·UDP 소켓)은 프로토콜·IP·포트로 식별되며, 그 위에서 어떤 형식으로 데이터를 주고받을지는 애플리케이션이 정합니다. TCP 소켓은 경계가 없는 바이트 스트림이므로 메시지 경계도 직접 설계해야 합니다.

웹소켓(RFC 6455)은 브라우저에서도 서버와 **양방향 실시간 통신**을 하기 위한 프로토콜입니다. HTTP 요청에 `Upgrade: websocket` 헤더를 붙여 시작하고, 서버가 `101 Switching Protocols`로 응답하면 같은 TCP 연결을 웹소켓으로 전환합니다. 이후에는 메시지를 프레임 단위로 주고받고, 서버도 요청 없이 먼저 데이터를 보낼 수 있습니다. 80·443 포트와 HTTP 핸드셰이크를 쓰므로 기존 웹 인프라를 통과하기 쉽고, `wss://`로 TLS를 적용합니다.

HTTP 폴링은 변경이 없어도 요청을 반복하고 매번 헤더를 보내지만, 웹소켓은 연결 하나를 유지하므로 채팅·알림·실시간 협업처럼 잦은 양방향 통신에 적합합니다. 대신 연결을 계속 유지하는 상태 있는 구조라, 서버 확장 시 연결 분산과 서버 간 메시지 전달(Redis Pub/Sub 등)을 고민해야 합니다.

### 꼬리질문 대비

1. **소켓과 포트의 차이가 무엇인가요?** — 포트는 한 호스트 안에서 **어떤 프로세스(서비스)로 보낼지 구분하는 16비트 번호**이고, 소켓은 통신을 위해 OS가 만든 **끝점 객체**입니다. 소켓은 프로토콜·IP·포트 등에 바인딩되며, 프로세스는 파일 디스크립터로 소켓을 다룹니다. 포트는 주소의 일부, 소켓은 그 주소로 통신하는 실체라고 구분할 수 있습니다.
2. **여러 소켓이 있다고 할 때, 그 소켓의 포트 번호는 모두 다른가요?** — 아닙니다. TCP 연결은 **(프로토콜, 출발지 IP, 출발지 포트, 목적지 IP, 목적지 포트)의 5-튜플**로 식별됩니다. 서버가 443 포트로 listen하다가 `accept()`하면 연결마다 새 소켓이 생기는데, 이 소켓들의 서버 쪽 포트는 모두 443입니다. 클라이언트 IP·포트가 달라서 구분됩니다. 또한 TCP와 UDP는 같은 포트 번호를 따로 쓸 수 있고, `SO_REUSEPORT` 옵션으로 여러 소켓이 같은 포트에서 listen할 수도 있습니다.
3. **사용자의 요청이 무수히 많아지면, 소켓도 무수히 생성되나요?** — TCP 연결 하나마다 서버에 소켓 하나가 생기므로 동시 연결 수만큼 늘어나지만, 무한하지는 않습니다. 프로세스당 파일 디스크립터 한도(`ulimit -n`), 커널 메모리, 소켓 버퍼, 연결 대기 큐(backlog) 크기에 제한됩니다. 서버 포트는 하나여도 되지만, 프록시처럼 한 IP로 같은 목적지에 많은 연결을 내보내는 쪽은 **임시 포트(ephemeral port)가 고갈**될 수 있고, 닫힌 연결이 TIME_WAIT로 남아 있는 것도 원인이 됩니다. 그래서 연결 수를 줄이는 Keep-Alive·커넥션 풀을 쓰고, 연결마다 스레드를 만들지 않도록 epoll 같은 I/O 멀티플렉싱으로 적은 스레드가 많은 소켓을 처리하게 합니다. 한계를 넘으면 서버를 늘리고 로드 밸런서로 분산합니다.

**핵심 키워드** → OS 인터페이스 vs 프로토콜, `Upgrade`/101, 전이중, 프레임, 5-튜플, 파일 디스크립터 한도, ephemeral port, epoll

## 6. HTTP/1.1과 HTTP/2의 차이점은 무엇인가요?

**가장 큰 차이는 HTTP/2가 하나의 TCP 연결 위에서 여러 요청과 응답을 동시에 섞어 보내는 멀티플렉싱을 지원한다는 점입니다.** 메서드·상태 코드·헤더의 의미는 같고, 메시지를 전송하는 방식이 바뀌었습니다.

| 구분 | HTTP/1.1 | HTTP/2 |
|---|---|---|
| 메시지 형식 | 텍스트 | 바이너리 프레임 |
| 동시 요청 | 연결당 한 번에 하나의 응답, 브라우저는 도메인당 연결 여러 개(보통 6개) 사용 | 연결 하나에 여러 스트림을 멀티플렉싱 |
| 헤더 | 매 요청마다 텍스트로 반복 전송 | HPACK으로 압축하고 이전 헤더를 재사용 |
| 우선순위 | 없음 | 스트림 우선순위 지원 (실제로는 구현 편차가 큼) |
| 서버 푸시 | 없음 | 명세에는 있으나 주요 브라우저가 지원을 제거해 사실상 사용하지 않음 |

HTTP/1.1에서는 연결 수 제한을 피하려고 도메인 샤딩, 이미지 스프라이트, 파일 번들링 같은 우회 기법을 썼습니다. HTTP/2에서는 연결 하나로 충분해 이런 기법의 필요성이 줄었고, 오히려 도메인 샤딩은 연결 재사용을 막아 손해일 수 있습니다. 실제 브라우저는 HTTP/2를 TLS 위에서만 사용합니다.

### 꼬리질문 대비

1. **HOL Blocking 에 대해 설명해 주세요.** — Head-of-Line Blocking은 **앞의 작업이 지연되면 뒤의 작업이 모두 기다리는 현상**입니다. HTTP/1.1에서는 한 연결에서 응답이 요청 순서대로 와야 하므로 앞의 응답이 느리면 뒤가 막힙니다. 파이프라이닝도 이 문제 때문에 사실상 쓰이지 않았습니다. HTTP/2는 스트림을 섞어 보내 **HTTP 계층의 HOL은 해결**했지만, 모든 스트림이 하나의 TCP 연결을 공유하므로 **TCP 계층의 HOL**이 남습니다. TCP는 바이트 순서를 보장해야 해서, 패킷 하나가 손실되면 그 뒤에 도착한 다른 스트림의 데이터도 재전송이 끝날 때까지 애플리케이션에 전달되지 않습니다. 손실이 많은 네트워크에서는 HTTP/2가 여러 연결을 쓰는 HTTP/1.1보다 느릴 수도 있습니다.
2. **HTTP/3.0의 주요 특징에 대해 설명해 주세요.** — HTTP/3는 TCP 대신 **UDP 기반의 QUIC** 위에서 동작합니다. ① QUIC이 스트림별로 순서를 보장하므로 한 스트림의 손실이 다른 스트림을 막지 않아 **TCP HOL이 사라집니다.** ② TLS 1.3이 QUIC에 내장되어 전송·암호화 핸드셰이크를 합쳐 첫 연결이 1-RTT, 재연결은 0-RTT도 가능합니다. 0-RTT 데이터는 재전송 공격에 취약해 멱등 요청에만 쓰는 것이 원칙입니다. ③ 연결을 IP·포트가 아닌 **Connection ID**로 식별해, 와이파이에서 LTE로 바뀌어도 연결을 유지할 수 있습니다(연결 마이그레이션). ④ 헤더 압축은 순서 의존을 줄인 QPACK을 씁니다. 단점은 UDP가 일부 네트워크에서 차단될 수 있어 HTTP/2로 폴백이 필요하고, 사용자 공간에서 처리하는 만큼 CPU 비용이 클 수 있다는 점입니다. 서버는 `Alt-Svc` 헤더로 HTTP/3 지원을 알립니다.

**핵심 키워드** → 바이너리 프레이밍, 멀티플렉싱, 스트림, HPACK, HTTP 계층 HOL vs TCP 계층 HOL, QUIC, 0-RTT, Connection ID

## 7. Stateless와 Connectionless에 대해 설명해 주세요.

**Stateless는 서버가 이전 요청의 상태를 기억하지 않는다는 것이고, Connectionless는 요청과 응답이 끝나면 연결을 끊는다는 것입니다.** 하나는 상태, 하나는 연결에 대한 이야기라 서로 다른 개념입니다.

Stateless 덕분에 각 요청은 독립적으로 처리되고, 어떤 서버가 받아도 처리할 수 있어 서버를 쉽게 늘릴 수 있습니다. 대신 요청마다 인증 정보 같은 필요한 데이터를 함께 보내야 합니다.

Connectionless는 초기 HTTP(1.0)의 기본 동작이었습니다. 수많은 클라이언트와 연결을 계속 유지하지 않으므로 서버 자원을 아낄 수 있습니다. 하지만 **HTTP/1.1부터는 기본이 지속 연결(persistent connection)**이라, 현재의 HTTP를 완전히 Connectionless라고 하기는 어렵습니다. 응답 후에도 연결을 재사용하되, 일정 시간 요청이 없으면 닫는 방식입니다.

### 꼬리질문 대비

1. **왜 HTTP는 Stateless 구조를 채택하고 있을까요?** — **확장성과 단순함** 때문입니다. 서버가 클라이언트 상태를 들고 있지 않으면 요청을 아무 서버에나 보내도 되므로 로드 밸런싱과 서버 추가가 쉽고, 서버 하나가 죽어도 다른 서버가 이어받을 수 있습니다. 서버는 수많은 클라이언트의 상태를 저장할 필요가 없고, 각 요청이 자기 완결적이라 캐시나 프록시 같은 중간 장치가 요청을 이해하고 처리하기도 쉽습니다. 로그인처럼 상태가 꼭 필요한 부분은 쿠키·세션·토큰으로 최소한만 다룹니다.
2. **Connectionless의 논리대로면 성능이 되게 좋지 않을 것으로 보이는데, 해결 방법이 있을까요?** — 맞습니다. 요청마다 TCP 3-way handshake(1 RTT)와 HTTPS라면 TLS 핸드셰이크까지 반복하고, 새 연결은 TCP 혼잡 제어의 slow start부터 시작해 느립니다. 한 페이지에 리소스가 수십 개면 이 비용이 크게 쌓입니다. 해결 방법은 **HTTP Persistent Connection(Keep-Alive)**으로 한 연결을 여러 요청에 재사용하는 것이고, HTTP/1.1부터 기본입니다. 나아가 HTTP/2는 연결 하나에 요청을 멀티플렉싱하고, HTTP/3는 연결 설정 왕복 자체를 줄입니다. 서버 간 통신에서는 커넥션 풀로 연결을 미리 만들어 재사용합니다.
3. **TCP의 keep-alive와 HTTP의 keep-alive의 차이는 무엇인가요?** — 이름은 같지만 목적이 다릅니다. **HTTP keep-alive는 연결 재사용**입니다. 응답 후 연결을 닫지 않고 다음 요청에 쓰는 것으로, HTTP/1.0에서는 `Connection: keep-alive` 헤더가 필요했고 1.1부터는 기본입니다. 서버는 유휴 시간이 지나면 연결을 닫습니다. **TCP keepalive는 연결 생존 확인**입니다. 일정 시간 데이터가 없으면 OS가 데이터 없는 탐침 패킷을 보내 상대가 살아 있는지 확인하고, 응답이 없으면 연결을 정리합니다. 상대가 갑자기 사라진 죽은 연결을 찾아내고, 중간 NAT·방화벽이 유휴 연결을 끊지 않게 하는 데 쓰입니다. 기본 대기 시간이 Linux 기준 2시간으로 길어 보통 소켓 옵션으로 조정합니다. 즉 HTTP는 애플리케이션 계층에서 연결을 **열어두는 정책**, TCP는 전송 계층에서 연결이 **살아 있는지 확인하는 기능**입니다.

**핵심 키워드** → 상태 vs 연결, 수평 확장, 지속 연결, 핸드셰이크·slow start 비용, 커넥션 풀, 연결 재사용 vs 생존 확인

## 8. 문자열 인코딩에 대해 설명해 주세요.

**문자열 인코딩은 문자를 컴퓨터가 저장하고 전송할 수 있는 바이트로 바꾸는 규칙입니다.** 문자 집합(어떤 문자에 어떤 번호를 줄지)과 인코딩 방식(그 번호를 어떤 바이트로 표현할지)을 구분해서 설명할 수 있습니다.

ASCII는 영문·숫자·기호 128개를 7비트로 표현합니다. 이후 나라마다 EUC-KR 같은 별도 인코딩을 만들면서 서로 호환되지 않는 문제가 생겼고, 이를 통합한 것이 **유니코드**입니다. 유니코드는 모든 문자에 `U+AC00`('가') 같은 코드 포인트를 부여하는 문자 집합이고, 이를 바이트로 바꾸는 방식이 UTF-8·UTF-16·UTF-32입니다.

**UTF-8**은 가변 길이로 1~4바이트를 씁니다. ASCII 문자는 1바이트로 기존 ASCII와 호환되고, 한글은 3바이트입니다. 바이트 순서 문제가 없어 웹과 파일 저장의 사실상 표준입니다. UTF-16은 2바이트 또는 4바이트(서로게이트 쌍)를 씁니다. Java의 `String`과 `char`는 UTF-16 기반이라 이모지 같은 문자는 `char` 두 개가 되어 `length()`가 문자 수와 다를 수 있습니다.

글자가 깨지는 이유는 **인코딩한 방식과 디코딩한 방식이 다르기 때문**입니다. 그래서 바이트와 문자를 변환할 때는 `new String(bytes, StandardCharsets.UTF_8)`처럼 인코딩을 명시하고, HTTP에서는 `Content-Type: text/html; charset=UTF-8`로 알려줍니다.

### 꼬리질문 대비

1. **Base64 인코딩은 일반적인 문자열 인코딩과는 달리, 사용자가 읽기 어려운 알파벳과 숫자 조합으로 변경합니다. 이를 사용하는 이유는 무엇일까요?** — **텍스트만 안전하게 다룰 수 있는 곳에 바이너리 데이터를 실어 보내기 위해서**입니다. 이메일(SMTP), JSON, XML, URL, HTTP 헤더 같은 텍스트 기반 형식은 임의의 바이트를 넣으면 제어 문자나 구분자로 오해되거나 전송 중 변형될 수 있습니다. Base64는 3바이트(24비트)를 6비트씩 4개로 나눠 `A-Z`, `a-z`, `0-9`, `+`, `/` 64개 문자로 표현하므로 어떤 시스템을 거쳐도 안전합니다. 이미지를 data URI로 넣거나, HTTP Basic 인증, JWT(URL-safe 변형인 Base64URL)에서 쓰입니다. 대가로 크기가 약 **33% 커집니다.** 또한 **Base64는 암호화가 아니라** 누구나 디코딩할 수 있으므로 보안 목적으로 쓰면 안 됩니다. 사람이 읽기 어려운 것은 목적이 아니라 결과일 뿐입니다.

**핵심 키워드** → 문자 집합 vs 인코딩, 유니코드 코드 포인트, UTF-8 가변 길이, UTF-16 서로게이트, 인코딩 불일치, Base64는 바이너리→텍스트, 33% 증가, 암호화 아님

## 9. MVC 패턴이 무엇인가요?

**MVC는 애플리케이션을 Model, View, Controller로 나눠 데이터·화면·흐름 제어의 책임을 분리하는 패턴입니다.**

- **Model**: 데이터와 비즈니스 로직을 담당합니다.
- **View**: 사용자에게 보여주는 화면을 담당합니다.
- **Controller**: 사용자 입력을 받아 Model을 호출하고, 결과를 어떤 View로 보여줄지 결정합니다.

책임이 나뉘어 있으므로 화면을 바꿔도 비즈니스 로직에 영향이 적고, 각 부분을 따로 테스트하고 유지보수하기 쉽습니다.

Spring MVC를 예로 들면, `DispatcherServlet`이 모든 요청을 받는 프론트 컨트롤러가 되어 핸들러 매핑으로 알맞은 `@Controller`를 찾습니다. 컨트롤러가 서비스를 호출하고 모델 데이터와 뷰 이름을 반환하면, `ViewResolver`가 실제 뷰(Thymeleaf 등)를 찾아 렌더링합니다. REST API에서는 `@RestController`가 뷰 대신 객체를 반환하고 메시지 컨버터가 JSON으로 변환합니다. 이 경우 JSON 응답이 View 역할을 한다고 볼 수 있습니다.

주의할 점은 컨트롤러에 비즈니스 로직이 몰리기 쉽다는 것입니다. 그래서 실무에서는 Controller–Service–Repository 계층으로 나눠 컨트롤러는 요청·응답 변환만 맡깁니다.

### 꼬리질문 대비

1. **다른 아키텍쳐 패턴은 없나요? MVC랑 비교해서 어떤 차이가 있나요?** — 주로 UI 쪽에서 MVC의 단점을 보완한 패턴들이 있습니다. **MVP**(Model-View-Presenter)는 View가 Model을 직접 알지 못하고, Presenter가 인터페이스를 통해 View를 갱신합니다. View와 Model의 의존이 끊겨 Presenter를 단위 테스트하기 쉽지만, View와 Presenter가 1:1에 가깝게 붙고 Presenter 코드가 커지기 쉽습니다. **MVVM**(Model-View-ViewModel)은 ViewModel이 화면 상태를 들고 있고, View는 **데이터 바인딩**으로 그 상태를 관찰합니다. ViewModel은 View를 직접 참조하지 않아 결합도가 더 낮습니다. Android Jetpack, Vue, WPF에서 많이 씁니다. 바인딩이 많아지면 데이터 흐름을 추적하기 어려울 수 있습니다. 이 외에 단방향 데이터 흐름을 강제하는 **Flux/Redux**가 있고, 서버 아키텍처 관점에서는 도메인을 중심에 두고 외부 의존을 바깥으로 미는 **레이어드·헥사고날(포트와 어댑터) 아키텍처**도 비교 대상이 됩니다. MVC는 단순하고 익숙하지만, 화면이 복잡해질수록 View와 Controller가 엉키기 쉽다는 점이 대안 패턴들이 나온 이유입니다.

**핵심 키워드** → 관심사 분리, DispatcherServlet, ViewResolver, @RestController, Fat Controller, MVP의 Presenter, MVVM 데이터 바인딩

## 면접 직전 확인할 구분

| 헷갈리기 쉬운 개념 | 구분해서 말할 내용 |
|---|---|
| 쿠키 / 세션 | 클라이언트에 값 저장 / 서버에 값 저장, ID만 쿠키로 전달 |
| 401 / 403 | 인증 안 됨(누군지 모름) / 인가 안 됨(권한 없음) |
| 안전성 / 멱등성 | 서버 상태를 안 바꿈 / 여러 번 해도 결과 상태가 같음 |
| PUT / PATCH | 전체 대체, 멱등 / 부분 수정, 멱등 보장 없음 |
| HTTP / HTTPS | 평문 / TLS로 암호화·무결성·서버 인증 |
| 소켓 / 웹소켓 | OS 통신 끝점·API / HTTP로 시작하는 양방향 프로토콜 |
| HTTP/2 HOL / TCP HOL | HTTP/2 멀티플렉싱으로 해결 / HTTP/3(QUIC)에서 해결 |
| Stateless / Connectionless | 상태를 기억 안 함 / 응답 후 연결 끊음 (1.1부터 지속 연결이 기본) |
| HTTP keep-alive / TCP keepalive | 연결 재사용 / 연결 생존 확인 |
| 인코딩 / 암호화 | 형식 변환, 누구나 복원 / 키 없이는 복원 불가 |

참고: [RFC 9110 — HTTP Semantics](https://www.rfc-editor.org/rfc/rfc9110) · [RFC 9113 — HTTP/2](https://www.rfc-editor.org/rfc/rfc9113) · [RFC 9114 — HTTP/3](https://www.rfc-editor.org/rfc/rfc9114) · [RFC 8446 — TLS 1.3](https://www.rfc-editor.org/rfc/rfc8446) · [RFC 6455 — WebSocket](https://www.rfc-editor.org/rfc/rfc6455)
