## 1. TCP와 UDP의 차이에 대해 설명해 주세요.

**TCP는 연결을 맺고 순서·신뢰성·흐름·혼잡 제어를 보장하는 바이트 스트림 프로토콜이고, UDP는 연결 없이 데이터그램을 그대로 보내는 가벼운 프로토콜입니다.**

| 구분 | TCP | UDP |
|---|---|---|
| 연결 | 연결 지향 (3-way handshake) | 비연결 |
| 단위 | 바이트 스트림 (메시지 경계 없음) | 데이터그램 (메시지 경계 유지) |
| 신뢰성 | 순서 보장, 재전송, 중복 제거 | 보장 없음 (손실·순서 뒤바뀜 가능) |
| 제어 | 흐름 제어, 혼잡 제어 | 없음 |
| 헤더 | 기본 20바이트 | 8바이트 |
| 통신 형태 | 1:1 | 1:1, 1:N (브로드캐스트·멀티캐스트) |
| 예 | HTTP/1.1·2, SSH, SMTP | DNS, 실시간 스트리밍·게임, QUIC(HTTP/3) |

TCP는 신뢰성 대신 연결 수립 지연과 재전송 대기 같은 비용을 치르고, UDP는 빠르고 단순하지만 필요한 신뢰성은 애플리케이션이 직접 만들어야 합니다. **"UDP는 신뢰성이 없다"가 아니라 "전송 계층이 신뢰성을 대신 해주지 않는다"** 로 말하는 것이 정확합니다.

### 꼬리질문 대비

1. **Checksum이 무엇인가요?** — 전송 중 데이터가 깨졌는지 확인하기 위한 검증 값입니다. TCP·UDP는 헤더와 데이터(그리고 출발지·목적지 IP 등 의사 헤더)를 16비트 단위로 더해 1의 보수를 취한 값을 헤더에 넣고, 수신 측이 같은 계산을 해서 결과가 맞지 않으면 손상된 것으로 보고 버립니다.
2. **TCP와 UDP 중 어느 프로토콜이 Checksum을 수행할까요?** — 둘 다 합니다. TCP는 필수입니다. UDP는 IPv4에서는 선택(0이면 미사용)이지만, IPv6에서는 IP 헤더에 체크섬이 없어져서 UDP 체크섬이 필수가 됐습니다.
3. **그렇다면, Checksum을 통해 오류를 정정할 수 있나요?** — 없습니다. 체크섬은 **오류 검출**만 하고, 어느 비트가 틀렸는지는 알 수 없습니다. TCP는 손상된 세그먼트를 버리고 ACK를 보내지 않아 송신자가 **재전송**하게 만드는 방식으로 복구합니다. 또 단순 합산이라 비트 두 개가 서로 상쇄되게 바뀌면 검출하지 못하는 한계도 있어, 링크 계층의 CRC나 TLS의 MAC이 보완합니다. 정정까지 하려면 해밍 코드나 FEC 같은 별도 기법이 필요합니다.
4. **TCP가 신뢰성을 보장하는 방법에 대해 설명해 주세요.** — ① **시퀀스 번호**로 바이트 순서를 매겨 순서를 맞추고 중복을 제거합니다. ② **ACK**로 받은 위치를 알려줍니다(누적 ACK, SACK 옵션). ③ **재전송**: 타임아웃(RTO)이 지나거나 중복 ACK가 3번 오면 다시 보냅니다. ④ **체크섬**으로 손상을 검출합니다. ⑤ **흐름 제어**: 수신자가 윈도우 크기(rwnd)를 알려 버퍼가 넘치지 않게 합니다. ⑥ **혼잡 제어**: 네트워크가 막히지 않게 송신량을 조절합니다.
5. **TCP의 혼잡 제어 처리 방법에 대해 설명해 주세요.** — 송신자는 혼잡 윈도우(cwnd)를 두고, 실제 전송량은 `min(cwnd, rwnd)`로 정합니다. ① **Slow Start**: cwnd를 1 MSS(요즘은 보통 10)에서 시작해 ACK마다 늘려 RTT마다 두 배가 됩니다. ② **혼잡 회피**: 임계값(ssthresh)에 닿으면 RTT마다 1 MSS씩 선형 증가합니다(AIMD). ③ **Fast Retransmit/Fast Recovery**: 중복 ACK 3개면 타임아웃을 기다리지 않고 재전송하고, cwnd를 절반으로 줄여 혼잡 회피로 갑니다(Reno). ④ **타임아웃**이 나면 심각한 혼잡으로 보고 cwnd를 1로 줄여 Slow Start부터 다시 합니다. 리눅스 기본은 CUBIC이고, 손실 대신 대역폭과 RTT를 측정하는 BBR도 쓰입니다.
6. **왜 HTTP는 TCP를 사용하나요?** — HTTP 메시지는 한 바이트라도 빠지거나 순서가 바뀌면 의미가 깨집니다. 웹 페이지·API 응답은 실시간성보다 정확성이 중요하므로, 신뢰성과 순서를 전송 계층이 보장해 주는 TCP가 맞습니다. HTTP가 직접 재전송을 구현할 필요도 없습니다.
7. **그렇다면, 왜 HTTP/3 에서는 UDP를 사용하나요? 위에서 언급한 UDP의 문제가 해결되었나요?** — HTTP/3는 UDP를 그대로 쓰는 게 아니라 **UDP 위에 QUIC**을 올립니다. QUIC이 재전송·순서 보장·혼잡 제어를 직접 구현하므로 UDP의 신뢰성 문제는 QUIC 계층에서 해결됩니다. UDP를 고른 이유는 ① TCP는 커널과 중간 장비(미들박스)에 굳어 있어 바꾸기 어렵지만 UDP 위면 사용자 공간에서 빠르게 개선할 수 있고, ② TCP는 하나의 바이트 스트림이라 패킷 하나만 잃어도 뒤의 모든 스트림이 막히는 **TCP HOL blocking**이 있는데 QUIC은 스트림별로 독립 처리하며, ③ 전송과 TLS 1.3 핸드셰이크를 합쳐 1-RTT, 재연결 시 0-RTT로 연결하고, ④ IP 대신 Connection ID로 연결을 식별해 Wi-Fi→LTE 전환에도 연결이 유지되기 때문입니다. 단점으로는 UDP를 막거나 제한하는 네트워크가 있고, 암호화·처리를 사용자 공간에서 해 CPU 비용이 큽니다.
8. **그런데, 브라우저는 어떤 서버가 TCP를 쓰는지 UDP를 쓰는지 어떻게 알 수 있나요?** — 처음에는 TCP(HTTP/1.1·2 over TLS)로 접속합니다. 서버가 응답 헤더 `Alt-Svc: h3=":443"`로 HTTP/3 지원을 알리면 다음 연결부터 QUIC을 시도합니다. 또는 DNS의 **HTTPS(SVCB) 레코드**에 `alpn=h3`가 있으면 처음부터 QUIC을 시도할 수 있습니다. QUIC이 막혀 있으면 TCP로 되돌아갑니다(여러 브라우저가 둘을 경쟁시키는 방식도 씀).
9. **본인이 새로운 통신 프로토콜을 TCP나 UDP를 사용해서 구현한다고 하면, 어떤 기준으로 프로토콜을 선택하시겠어요?** — ① 데이터가 **전부, 순서대로** 도착해야 하는가: 파일·결제·채팅 메시지면 TCP. ② **늦게 온 데이터가 쓸모없는가**: 실시간 음성·게임 위치처럼 재전송을 기다리느니 버리는 게 나으면 UDP. ③ 메시지가 작고 요청·응답이 한 번으로 끝나는가: DNS처럼 핸드셰이크 비용이 더 크면 UDP. ④ 브로드캐스트·멀티캐스트가 필요하면 UDP. ⑤ 방화벽·NAT 통과가 중요하면 TCP가 유리합니다. 신뢰성과 낮은 지연이 둘 다 필요하면 직접 만들기보다 QUIC 같은 검증된 UDP 기반 프로토콜을 먼저 검토하겠습니다.

**핵심 키워드** → 연결 지향 vs 비연결, 바이트 스트림 vs 데이터그램, 체크섬은 검출만, 재전송·ACK·시퀀스 번호, cwnd/rwnd, Slow Start·AIMD, QUIC, `Alt-Svc`, HOL blocking

## 2. OSI 7계층에 대해 설명해 주세요.

**OSI 7계층은 네트워크 통신 과정을 기능별로 일곱 단계로 나눈 참조 모델이고, 각 계층은 아래 계층의 서비스를 이용해 위 계층에 서비스를 제공합니다.**

| 계층 | 역할 | 예 |
|---|---|---|
| 7 응용 | 사용자·애플리케이션에 서비스 제공 | HTTP, DNS, SMTP |
| 6 표현 | 데이터 형식 변환, 암호화, 압축 | TLS(일부), JPEG, 인코딩 |
| 5 세션 | 통신 세션의 수립·유지·종료 | RPC 세션 |
| 4 전송 | 프로세스 간 전달, 신뢰성, 포트 | TCP, UDP |
| 3 네트워크 | 다른 네트워크까지 경로 선택, 논리 주소 | IP, ICMP, 라우터 |
| 2 데이터 링크 | 같은 링크 안의 노드 간 전달, MAC 주소, 오류 검출 | Ethernet, Wi-Fi, 스위치 |
| 1 물리 | 비트를 전기·빛·전파 신호로 전송 | 케이블, 허브, 리피터 |

계층을 나누면 한 계층을 바꿔도 다른 계층에 영향이 적고(예: 유선이 Wi-Fi로 바뀌어도 HTTP는 그대로), 문제가 어느 계층에서 생겼는지 좁혀 찾기 쉽습니다. 실제 인터넷은 5~7계층을 응용 계층 하나로 묶은 **TCP/IP 4계층 모델**로 동작합니다.

### 꼬리질문 대비

1. **Transport Layer와, Network Layer의 차이에 대해 설명해 주세요.** — 네트워크 계층은 **호스트 대 호스트**, 전송 계층은 **프로세스 대 프로세스** 통신을 맡습니다. 네트워크 계층(IP)은 IP 주소로 출발지 컴퓨터에서 목적지 컴퓨터까지 경로를 찾아 패킷을 옮기되, 최선형(best-effort) 전달이라 손실·순서를 보장하지 않습니다. 전송 계층은 포트 번호로 그 컴퓨터 안의 어느 프로세스인지 구분하고, TCP라면 신뢰성·흐름·혼잡 제어를 더합니다. 또 IP는 경로의 모든 라우터가 처리하지만, 전송 계층 헤더는 원칙적으로 양 끝 호스트만 봅니다(end-to-end).
2. **L3 Switch와 Router의 차이에 대해 설명해 주세요.** — 둘 다 IP 주소를 보고 3계층 포워딩을 합니다. L3 스위치는 ASIC 하드웨어로 빠르게 포워딩하고 포트가 많아, 주로 **LAN 내부의 VLAN 간 라우팅**에 씁니다. 라우터는 **서로 다른 네트워크·WAN을 연결**하는 장비로, NAT·VPN·방화벽·QoS·다양한 WAN 인터페이스·대규모 라우팅 테이블(BGP) 같은 기능이 풍부합니다. 요즘은 경계가 흐려져서 "LAN 안에서 빠른 포워딩이 목적이면 L3 스위치, 외부 망과의 경계와 부가 기능이 목적이면 라우터"로 구분합니다.
3. **각 Layer는 패킷을 어떻게 명칭하나요? 예를 들어, Transport Layer의 경우 Segment라 부릅니다.** — 이 단위를 PDU라고 합니다. 응용 계층은 **메시지(데이터)**, 전송 계층은 **세그먼트**(UDP는 **데이터그램**), 네트워크 계층은 **패킷**, 데이터 링크 계층은 **프레임**, 물리 계층은 **비트**입니다.
4. **각각의 Header의 Packing Order에 대해 설명해 주세요.** — 보낼 때는 위에서 아래로 내려가며 각 계층이 자기 헤더를 앞에 붙이는 **캡슐화**를 합니다. 그래서 선 위의 순서는 `[Ethernet 헤더][IP 헤더][TCP 헤더][HTTP 데이터][Ethernet 트레일러(FCS)]`이고, 가장 바깥이 2계층 헤더입니다. 2계층만 FCS(CRC)를 트레일러로 뒤에 붙입니다. 받는 쪽은 반대로 바깥 헤더부터 벗기며 올라가는 **역캡슐화**를 하고, 각 헤더의 타입 필드(EtherType, IP의 Protocol, 포트 번호)로 다음에 넘길 상위 프로토콜을 정합니다.
5. **ARP에 대해 설명해 주세요.** — 같은 네트워크 안에서 **IP 주소로 MAC 주소를 알아내는** 프로토콜입니다. 실제 프레임 전달에는 MAC 주소가 필요하기 때문입니다. ① 먼저 ARP 캐시를 확인하고, ② 없으면 "이 IP를 가진 장비는 MAC을 알려 달라"는 ARP 요청을 **브로드캐스트**합니다. ③ 해당 IP의 장비가 자기 MAC을 **유니캐스트**로 응답하고, ④ 결과를 캐시에 일정 시간 저장합니다. 목적지가 다른 네트워크면 목적지가 아니라 **게이트웨이의 MAC**을 ARP로 찾습니다. 인증이 없어 가짜 응답으로 트래픽을 가로채는 ARP 스푸핑에 취약합니다. IPv6는 ARP 대신 NDP를 씁니다.

**핵심 키워드** → 계층 분리, 호스트 간 vs 프로세스 간, PDU(메시지·세그먼트·패킷·프레임·비트), 캡슐화, ARP 브로드캐스트, TCP/IP 4계층

## 3. 3-Way Handshake에 대해 설명해 주세요.

**TCP가 데이터를 보내기 전에 양쪽이 서로 송수신이 가능한지 확인하고, 각자의 초기 시퀀스 번호(ISN)를 교환해 연결을 맺는 과정입니다.**

1. **SYN**: 클라이언트가 `SYN`과 자신의 ISN(x)을 보냅니다. 상태 `CLOSED → SYN_SENT`.
2. **SYN+ACK**: 서버가 `ACK = x+1`로 받았음을 알리고, 자신의 ISN(y)을 담은 `SYN`을 함께 보냅니다. 상태 `LISTEN → SYN_RCVD`.
3. **ACK**: 클라이언트가 `ACK = y+1`을 보냅니다. 양쪽이 `ESTABLISHED`가 됩니다.

ISN은 0이 아니라 무작위에 가깝게 정합니다. 이전 연결에서 늦게 도착한 패킷과 섞이지 않게 하고, 공격자가 시퀀스 번호를 추측해 끼어들지 못하게 하기 위해서입니다. 세 번째 ACK에는 데이터를 실어 보낼 수도 있습니다.

### 꼬리질문 대비

1. **ACK, SYN 같은 정보는 어떻게 전달하는 것 일까요?** — TCP 헤더의 **제어 플래그 비트**로 전달합니다. 헤더에 URG·ACK·PSH·RST·SYN·FIN(그리고 ECE·CWR) 비트가 있고, 해당 비트를 1로 켭니다. SYN+ACK는 두 비트를 동시에 켠 세그먼트 하나입니다. 번호는 헤더의 32비트 시퀀스 번호·확인 응답 번호 필드에 담고, MSS·윈도우 스케일·SACK 허용 같은 협상 값은 SYN 세그먼트의 옵션 필드에 담습니다.
2. **2-Way Handshaking 를 하지않는 이유에 대해 설명해 주세요.** — 연결은 양방향이라 **양쪽 ISN을 모두 상대가 확인**해야 합니다. 2-way면 서버의 ISN을 클라이언트가 받았는지 서버가 알 수 없습니다. 더 중요한 이유는 **지연된 옛 SYN** 문제입니다. 네트워크에 오래 떠돌던 이전 연결의 SYN이 늦게 도착하면, 2-way에서는 서버가 바로 연결을 열고 자원을 잡은 채 오지 않을 데이터를 기다립니다. 3-way에서는 클라이언트가 자기가 보낸 적 없는 SYN+ACK에 RST를 보내 잘못된 연결을 끊을 수 있습니다.
3. **두 호스트가 동시에 연결을 시도하면, 연결이 가능한가요? 가능하다면 어떻게 통신 연결을 수행하나요?** — 가능하며 **Simultaneous Open**이라고 합니다. 양쪽이 동시에 SYN을 보내 둘 다 `SYN_SENT`가 되고, 상대의 SYN을 받으면 `SYN_RCVD`로 가며 SYN+ACK를 보냅니다. 상대의 SYN+ACK(ACK)를 받으면 `ESTABLISHED`가 됩니다. 세그먼트가 4개 오가고, 클라이언트·서버 구분 없이 **연결 하나**가 만들어집니다. 각자 상대의 포트를 정확히 알고 있어야 해서 실제로는 드물고, NAT 홀펀칭에서 활용되기도 합니다.
4. **SYN Flooding 에 대해 설명해 주세요.** — 공격자가 출발지 IP를 위조한 SYN을 대량으로 보내고 마지막 ACK를 보내지 않는 DoS 공격입니다. 서버는 SYN_RCVD 상태의 반쯤 열린 연결을 **SYN 백로그 큐**에 쌓아 두는데, 큐가 가득 차면 정상 사용자의 연결을 받지 못합니다. 대응은 ① **SYN Cookie**: 큐에 상태를 저장하지 않고 연결 정보를 해시해 서버 ISN에 담아 보낸 뒤, 돌아온 ACK 번호로 검증합니다. ② 백로그 크기를 키우고 SYN+ACK 재전송 횟수·타임아웃을 줄입니다. ③ 방화벽·로드 밸런서·DDoS 방어 서비스가 SYN 프록시로 대신 핸드셰이크를 받아 줍니다.
5. **위 질문과 모순될 수 있지만, 3-Way Handshake의 속도 문제 때문에 이동 수를 줄이는 0-RTT 기법을 많이 적용하고 있습니다. 어떤 방식으로 가능한 걸까요?** — **이전 연결에서 받은 정보를 재사용**해 첫 패킷에 데이터를 함께 실어 보냅니다. ① **TCP Fast Open**: 첫 연결 때 서버가 쿠키를 주고, 다음 연결의 SYN에 쿠키와 데이터를 함께 보내면 서버가 쿠키를 검증하고 핸드셰이크 완료 전에 데이터를 처리합니다. ② **TLS 1.3 0-RTT**: 이전 세션의 PSK(세션 티켓)로 첫 메시지(early data)부터 암호화된 요청을 보냅니다. ③ **QUIC 0-RTT**: 전송과 TLS 핸드셰이크가 합쳐져 있어 재연결 시 첫 패킷에 HTTP 요청을 담습니다. 대가는 **리플레이 공격**입니다. 공격자가 0-RTT 데이터를 복사해 다시 보낼 수 있으므로, 0-RTT에는 GET 같은 멱등 요청만 허용하는 식으로 제한합니다. 그래서 질문과 모순되지 않습니다. 0-RTT도 최초 연결은 정상 핸드셰이크로 신뢰를 쌓고, 그 결과를 재사용하는 것입니다.

**핵심 키워드** → SYN / SYN+ACK / ACK, ISN, 상태 전이(SYN_SENT·SYN_RCVD·ESTABLISHED), 플래그 비트, 지연된 SYN, Simultaneous Open, SYN Cookie, TFO·TLS 1.3·QUIC 0-RTT, 리플레이

## 4. 4-Way Handshake에 대해 설명해 주세요.

**TCP 연결을 끊을 때, 양방향 스트림을 각각 따로 닫기 위해 FIN과 ACK를 두 번씩 주고받는 과정입니다.**

1. 먼저 끊는 쪽(Active Close, 보통 클라이언트)이 `FIN`을 보냅니다. `ESTABLISHED → FIN_WAIT_1`.
2. 상대(Passive Close)가 `ACK`를 보냅니다. 상대는 `CLOSE_WAIT`, 먼저 끊은 쪽은 `FIN_WAIT_2`가 됩니다. 이 시점은 **Half-Close** 상태라 상대는 남은 데이터를 계속 보낼 수 있습니다.
3. 상대가 남은 데이터를 다 보내고 애플리케이션이 `close()`를 호출하면 `FIN`을 보냅니다. `LAST_ACK`.
4. 먼저 끊은 쪽이 `ACK`를 보내고 `TIME_WAIT`에서 일정 시간 기다린 뒤 `CLOSED`가 됩니다. 상대는 ACK를 받는 즉시 `CLOSED`.

3-way와 달리 2번과 3번을 합칠 수 없는 경우가 많은 이유는, 상대가 FIN을 받은 순간 아직 보낼 데이터가 남아 있을 수 있기 때문입니다. 보낼 데이터가 없으면 FIN+ACK를 합쳐 3번에 끝나기도 합니다.

### 꼬리질문 대비

1. **패킷이 4-way handshake 목적인지 어떻게 파악할 수 있을까요?** — TCP 헤더의 **FIN 플래그**로 압니다. FIN 비트가 켜져 있으면 "더 보낼 데이터가 없다"는 종료 요청입니다. 그 FIN에 대한 응답은 ACK 플래그와, FIN이 시퀀스 번호를 1 소비하므로 `ACK = FIN의 seq + 1`인 확인 응답 번호로 구분합니다. 수신 측은 현재 연결 상태(ESTABLISHED, FIN_WAIT_1 등)와 플래그를 함께 보고 상태 전이를 결정합니다.
2. **빨리 끊어야 할 경우엔, (즉, 4-way Handshake를 할 여유가 없다면) 어떻게 종료할 수 있을까요?** — **RST 플래그**를 보내 즉시 끊습니다(Abortive Close). 응답을 기다리지 않고 양쪽이 바로 연결을 버리며, 버퍼에 남은 데이터는 전송되지 않고 폐기됩니다. TIME_WAIT도 거치지 않습니다. 소켓에 `SO_LINGER`를 켜고 타임아웃을 0으로 두고 `close()`하면 RST로 종료됩니다. 데이터 유실 위험이 있어 오류 상황에서만 쓰는 것이 원칙입니다.
3. **4-Way Handshake 과정에서 중간에 한쪽 네트워크가 강제로 종료된다면, 반대쪽은 이를 어떻게 인식할 수 있을까요?** — TCP는 상대가 사라져도 알려주는 신호가 없어서 **보내 보거나 타이머로** 압니다. ① 데이터나 FIN을 보냈는데 ACK가 오지 않으면 재전송을 반복하다 한도를 넘으면 연결을 끊습니다. ② 상대 호스트가 재부팅됐다면 그 연결을 모르므로 RST로 응답해서 즉시 압니다. ③ 보낼 데이터가 없으면 영원히 모를 수 있어 **TCP keepalive**(기본 2시간 후 탐침)나 애플리케이션 heartbeat를 씁니다. ④ `FIN_WAIT_2`에서 상대 FIN이 오지 않으면 리눅스는 `tcp_fin_timeout`(기본 60초) 후 정리합니다. 반대로 상대가 FIN을 보냈는데 우리 앱이 `close()`를 안 하면 `CLOSE_WAIT`가 계속 쌓이는데, 이는 대개 애플리케이션의 소켓 누수 버그입니다.
4. **왜 종료 후에 바로 끝나지 않고, TIME_WAIT 상태로 대기하는 것 일까요?** — 두 가지 이유입니다. ① **마지막 ACK 유실 대비**: 마지막 ACK가 사라지면 상대는 FIN을 재전송합니다. 바로 CLOSED가 되면 재전송된 FIN에 RST로 응답하게 되어 상대가 비정상 종료로 처리합니다. ② **지연된 옛 세그먼트 제거**: 같은 포트 조합으로 새 연결을 바로 열면, 네트워크에 남아 있던 이전 연결의 세그먼트가 새 연결의 데이터로 잘못 받아들여질 수 있습니다. 그래서 세그먼트 최대 수명(MSL)의 두 배인 **2MSL** 동안 기다립니다(리눅스는 60초 고정). 짧은 연결이 많은 서버에서는 TIME_WAIT가 쌓여 포트가 고갈될 수 있어, keep-alive·커넥션 풀로 연결을 재사용하거나 `tcp_tw_reuse`를 검토합니다.

**핵심 키워드** → FIN / ACK / FIN / ACK, Half-Close, FIN_WAIT_1·2, CLOSE_WAIT, LAST_ACK, TIME_WAIT 2MSL, RST, keepalive, CLOSE_WAIT 누적은 앱 버그

## 5. 라우터 내의 포워딩 과정에 대해 설명해 주세요.

**포워딩은 라우터가 입력 포트로 들어온 패킷의 목적지 IP를 포워딩 테이블과 대조해 알맞은 출력 포트로 내보내는 과정입니다.**

1. **수신**: 입력 포트가 프레임을 받아 2계층 헤더를 확인하고 벗겨 IP 패킷을 꺼냅니다.
2. **검사와 조회**: IP 헤더 체크섬을 확인하고, 목적지 IP를 포워딩 테이블에서 **최장 접두사 일치(Longest Prefix Match)** 로 찾습니다. 여러 항목이 맞으면 가장 구체적인(접두사가 긴) 경로를 고르고, 아무것도 없으면 기본 경로(0.0.0.0/0)를 씁니다.
3. **헤더 갱신**: **TTL을 1 줄이고**, 0이 되면 버린 뒤 ICMP Time Exceeded를 출발지로 보냅니다. TTL이 바뀌었으니 IPv4 헤더 체크섬을 다시 계산합니다.
4. **스위칭 패브릭**: 패킷을 입력 포트에서 출력 포트로 옮깁니다.
5. **출력**: 다음 홉(next hop)의 MAC 주소를 ARP로 알아내 **새 2계층 헤더로 다시 감싸** 내보냅니다. 출력 큐가 차 있으면 대기하고, 넘치면 버려집니다.

**IP 주소는 끝까지 그대로, MAC 주소는 홉마다 바뀐다**는 점이 핵심입니다(NAT 제외). 고속 라우터는 각 입력 포트에 포워딩 테이블 사본을 두고 TCAM 같은 하드웨어로 나노초 단위에 조회합니다.

### 꼬리질문 대비

1. **라우팅과 포워딩의 차이는 무엇인가요?** — **라우팅은 경로를 정하는 것, 포워딩은 정해진 대로 옮기는 것**입니다. 라우팅은 컨트롤 플레인의 일로, 라우팅 프로토콜로 네트워크 전체 경로를 계산해 포워딩 테이블을 만들며 초 단위로 동작하고 주로 소프트웨어가 처리합니다. 포워딩은 데이터 플레인의 일로, 패킷 하나하나를 테이블대로 출력 포트로 보내며 나노초 단위로 하드웨어가 처리합니다. 여행으로 치면 라우팅은 지도로 경로를 계획하는 것, 포워딩은 교차로마다 방향을 고르는 것입니다. SDN은 라우팅을 중앙 컨트롤러로 분리한 구조입니다.
2. **라우팅 알고리즘에 대해 설명해 주세요.** — 크게 두 가지입니다. ① **링크 상태(Link State)**: 모든 라우터가 링크 정보를 전체에 퍼뜨려 **전체 지도**를 갖고, 각자 **다익스트라**로 최단 경로를 계산합니다(OSPF). 수렴이 빠르지만 메시지·계산량이 큽니다. ② **거리 벡터(Distance Vector)**: 이웃과만 "목적지까지의 거리표"를 주고받고 **벨만-포드** 방식으로 갱신합니다(RIP). 단순하지만 수렴이 느리고, 링크가 끊겼을 때 서로 잘못된 경로를 믿는 **count-to-infinity** 문제가 있어 split horizon 같은 보완을 씁니다. 범위로 나누면 한 조직(AS) 안의 **내부 라우팅(OSPF, RIP)** 과 AS 사이의 **외부 라우팅(BGP)** 이 있고, BGP는 최단 경로보다 정책을 우선하는 경로 벡터 방식입니다.
3. **포워딩 테이블의 구조에 대해 설명해 주세요.** — 기본적으로 `목적지 네트워크 접두사(예: 192.168.1.0/24) → 출력 인터페이스, 다음 홉 IP` 형태의 항목들로 구성되고, 기본 경로 항목이 하나 있습니다. 주소마다 항목을 두면 너무 크기 때문에 **접두사 단위로 묶어** 저장합니다. 조회는 최장 접두사 일치를 해야 해서, 소프트웨어로는 비트 단위 **트라이(radix/Patricia trie)** 를, 하드웨어로는 모든 항목을 한 번에 비교하는 **TCAM**을 씁니다. 라우팅 프로토콜이 만든 RIB(라우팅 정보 베이스)에서 실제로 쓸 최적 경로만 뽑아 FIB(포워딩 정보 베이스)로 내려보내는 구조입니다.

**핵심 키워드** → 최장 접두사 일치, TTL 감소·체크섬 재계산, 홉마다 MAC 교체, 컨트롤 플레인 vs 데이터 플레인, 다익스트라(OSPF)·벨만-포드(RIP)·BGP, RIB/FIB, TCAM

## 6. 서브넷 마스크와, 게이트웨이에 대해 설명해 주세요.

**서브넷 마스크는 IP 주소에서 어디까지가 네트워크 부분이고 어디부터가 호스트 부분인지 구분하는 값이고, 게이트웨이는 다른 네트워크로 나가는 출구 역할을 하는 장비(보통 라우터)의 주소입니다.**

서브넷 마스크는 네트워크 부분을 1, 호스트 부분을 0으로 채운 32비트 값입니다. IP와 마스크를 **AND 연산**하면 네트워크 주소가 나옵니다. 예를 들어 `192.168.1.10/24`는 네트워크 주소 `192.168.1.0`, 브로드캐스트 `192.168.1.255`이고, 사용 가능한 호스트는 2^8 − 2 = 254개입니다. 하나의 큰 네트워크를 작게 나누면(서브네팅) 브로드캐스트 범위가 줄고 주소 낭비를 막을 수 있습니다.

호스트가 패킷을 보낼 때, 자기 IP와 목적지 IP를 각각 마스크와 AND해서 **같으면 같은 네트워크**라 ARP로 목적지 MAC을 찾아 직접 보내고, **다르면 기본 게이트웨이**의 MAC으로 프레임을 보내 라우터가 대신 전달하게 합니다. 그래서 게이트웨이 설정이 틀리면 같은 네트워크끼리는 통신되는데 인터넷은 안 되는 증상이 납니다.

### 꼬리질문 대비

1. **NAT에 대해 설명해 주세요.** — 사설 IP와 공인 IP를 서로 바꿔 주는 기술입니다. 공유기 안의 장비들은 `192.168.x.x` 같은 사설 IP를 쓰고, 밖으로 나갈 때 공유기가 출발지 주소를 자신의 공인 IP로 바꿉니다. 여러 장비가 공인 IP 하나를 함께 쓰도록 **포트 번호까지 바꾸는 방식을 PAT(NAPT)** 라 하며, `(사설 IP, 사설 포트) ↔ (공인 IP, 공인 포트)` 변환 테이블로 응답을 원래 장비에 돌려줍니다. IPv4 주소 부족 문제를 완화하고 내부 구조를 숨기는 효과가 있습니다. 반면 외부에서 먼저 내부로 연결을 걸기 어려워 P2P·게임 서버에는 포트 포워딩이나 홀펀칭(STUN/TURN)이 필요하고, 계층 원칙(end-to-end)을 깨며 테이블 관리 부담이 생깁니다.
2. **서브넷 마스크의 표현 방식에 대해 설명해 주세요.** — ① **점-십진 표기**: `255.255.255.0`. ② **CIDR(접두사) 표기**: 앞에서부터 1인 비트 수를 써서 `/24`로 표현합니다(`192.168.1.0/24`). ③ 2진수 표기: `11111111.11111111.11111111.00000000`. CIDR은 예전의 A·B·C 클래스 고정 구분 대신 원하는 길이로 네트워크를 나눌 수 있게 한 방식이고, 지금은 이 표기가 표준처럼 쓰입니다. 예: `/26`이면 마스크 `255.255.255.192`, 호스트 62개.
3. **그렇다면, 255.0.255.0 같은 꼴의 서브넷 마스크도 가능한가요?** — 현재 표준에서는 **불가능합니다.** 서브넷 마스크는 1이 앞에서부터 **연속**되어야 합니다. 초기 RFC 950은 비연속 마스크를 금지하지 않았지만, CIDR(RFC 4632) 이후 라우팅이 **최장 접두사 일치**로 동작하면서 "접두사 길이"로 표현할 수 없는 마스크는 의미가 없어졌습니다. 비연속이면 주소 범위가 이어지지 않아 경로 요약이 불가능하고, 대부분의 OS·장비가 설정 자체를 거부합니다. 참고로 ACL의 와일드카드 마스크는 비연속을 허용하지만 이는 서브넷 마스크와 다른 용도입니다.

**핵심 키워드** → 네트워크/호스트 부분, AND 연산, CIDR `/24`, 2^n − 2, 같은 네트워크면 직접·다르면 게이트웨이, NAT/PAT, 연속된 1만 허용

## 7. 멀티플렉싱과 디멀티플렉싱에 대해 설명해 주세요.

**멀티플렉싱은 한 호스트의 여러 프로세스(소켓)가 보내는 데이터를 하나의 네트워크 계층으로 모아 보내는 것이고, 디멀티플렉싱은 받은 세그먼트를 헤더 정보로 알맞은 소켓에 나눠 주는 것입니다.**

IP는 패킷을 호스트까지만 데려다 주므로, 그 호스트의 어느 프로세스로 갈지는 전송 계층이 정합니다. 송신 측 전송 계층은 각 소켓의 데이터에 **출발지·목적지 포트 번호**를 담은 헤더를 붙여 IP로 내려보내고(멀티플렉싱), 수신 측은 그 포트 번호를 보고 소켓을 찾아 올려 줍니다(디멀티플렉싱). 덕분에 브라우저 탭 여러 개, 메신저, 게임이 IP 주소 하나로 동시에 통신할 수 있습니다.

같은 개념이 계층마다 있습니다. 2계층은 EtherType으로 IPv4·IPv6·ARP를, 3계층은 Protocol 필드로 TCP·UDP·ICMP를 구분합니다. 넓은 의미로는 HTTP/2처럼 연결 하나에 여러 스트림을 섞어 보내는 것도 멀티플렉싱이라 부릅니다.

### 꼬리질문 대비

1. **디멀티플렉싱의 과정에 대해 설명해 주세요.** — UDP와 TCP가 다릅니다. ① **UDP(비연결형)**: **(목적지 IP, 목적지 포트)** 2-튜플로 소켓을 찾습니다. 그래서 출발지가 달라도 목적지 포트가 같으면 모두 같은 소켓으로 들어가고, 앱은 `recvfrom()`으로 출발지를 확인합니다. ② **TCP(연결형)**: **(출발지 IP, 출발지 포트, 목적지 IP, 목적지 포트)** 4-튜플로 찾습니다. 웹 서버는 80/443 포트로 리스닝 소켓 하나를 두고, `accept()`할 때마다 연결별 새 소켓을 만듭니다. 그래서 모두 443으로 들어와도 클라이언트마다 다른 소켓으로 전달됩니다. 처음 들어온 SYN처럼 맞는 연결 소켓이 없으면 리스닝 소켓으로 보내고, 그것도 없으면 TCP는 RST, UDP는 ICMP Port Unreachable로 응답합니다. 순서로 보면 프레임의 EtherType → IP의 Protocol 필드 → 전송 계층의 포트·튜플 → 소켓 버퍼 → 애플리케이션입니다.

**핵심 키워드** → 프로세스 간 전달, 포트 번호, UDP는 2-튜플·TCP는 4-튜플, 리스닝 소켓 vs 연결 소켓, EtherType·Protocol 필드

## 8. 프레임워크와 라이브러리의 차이에 대해 설명해 주세요.

**가장 큰 차이는 제어 흐름을 누가 쥐는가입니다. 라이브러리는 내 코드가 필요할 때 호출하는 도구이고, 프레임워크는 전체 흐름을 쥐고 정해진 지점에서 내 코드를 호출합니다.**

이를 **제어의 역전(IoC)**, 흔히 "Don't call us, we'll call you"로 설명합니다. 예를 들어 Jackson으로 JSON을 파싱할 때는 내가 원하는 시점에 `objectMapper.readValue()`를 부릅니다. 반면 Spring에서는 내가 `@Controller` 메서드를 만들어 두기만 하면, 요청이 왔을 때 언제 객체를 만들고 어떤 메서드를 부를지를 프레임워크가 결정합니다.

| 구분 | 라이브러리 | 프레임워크 |
|---|---|---|
| 제어 흐름 | 내 코드가 호출 | 프레임워크가 내 코드를 호출 |
| 역할 | 특정 기능 도구 | 애플리케이션의 뼈대·규칙 |
| 교체 | 비교적 쉬움 | 구조 전체에 영향, 어려움 |
| 예 | Jackson, Lombok, Apache Commons, React(공식적으로 UI 라이브러리) | Spring, Django, Angular |

프레임워크는 구조와 규칙이 정해져 있어 팀의 코드가 일관되고 반복 작업이 줄지만, 그 방식에 묶이고 학습 비용이 큽니다. 라이브러리는 자유롭지만 구조는 직접 설계해야 합니다.

### 심화 주제 (직접 추가) — 제어의 역전(IoC)과 의존성 주입(DI)은 같은 것인가요?

같지 않습니다. **IoC는 제어 흐름을 프레임워크에 넘긴다는 넓은 원칙**이고, **DI는 그 원칙을 객체 생성·연결에 적용한 구체적인 방법**입니다. DI에서는 객체가 필요한 의존 객체를 `new`로 직접 만들지 않고, 생성자나 setter로 외부(Spring 컨테이너)에서 받습니다. 그러면 구현체를 바꾸거나 테스트에서 가짜 객체를 넣기 쉬워집니다. Spring에서는 **생성자 주입**을 권장합니다. 필드를 `final`로 둘 수 있어 불변이 보장되고, 필요한 의존성이 빠지면 객체 생성 시점에 바로 실패하며, 프레임워크 없이도 `new`로 테스트할 수 있기 때문입니다. IoC의 다른 예로는 템플릿 메서드 패턴, 이벤트 리스너 콜백, 서블릿 컨테이너가 `service()`를 호출하는 구조가 있습니다.

**핵심 키워드** → 제어 흐름의 주도권, IoC, "Don't call us, we'll call you", 뼈대 vs 도구, DI, 생성자 주입

## 9. 순수함수가 무엇인지를 함수형 프로그래밍 매커니즘과 연관지어 설명해 주세요.

**순수함수는 같은 입력에 항상 같은 출력을 돌려주고, 함수 바깥의 상태를 바꾸지도 읽지도 않는(부수 효과가 없는) 함수입니다.**

예를 들어 `add(a, b) { return a + b; }`는 순수하지만, 전역 변수를 더하거나, 인자로 받은 리스트를 수정하거나, 현재 시간·난수·DB를 읽는 함수는 순수하지 않습니다. 순수함수는 호출을 결과값으로 바꿔도 프로그램 의미가 같은 **참조 투명성**을 가집니다.

함수형 프로그래밍은 프로그램을 **상태 변경 명령의 나열이 아니라 순수함수의 조합**으로 만드는 패러다임입니다. 그래서 다음 특징이 함께 갑니다. ① **불변성**: 데이터를 바꾸지 않고 새 값을 만들어 반환합니다. ② **일급 함수·고차함수**: 함수를 값처럼 넘기고 반환합니다. ③ **함수 합성**: 작은 순수함수를 이어 붙여 큰 동작을 만듭니다. ④ **선언형 스타일**: 루프와 변수 대신 `map`, `filter`, `reduce`로 "무엇을" 할지 적습니다. 결과가 입력에만 의존하므로 테스트·추론·캐싱(메모이제이션)·병렬화가 쉬워집니다. Java에서는 람다와 Stream API가 이 방식을 지원합니다.

### 꼬리질문 대비

1. **Side Effect가 무엇인가요? 이를 모두 없애는 프로그래밍이 이상적이라고 할 수 있을까요?** — 함수가 값을 반환하는 것 외에 **외부에 관찰 가능한 변화**를 일으키는 것입니다. 전역 변수·인자 객체 수정, 파일·DB 쓰기, 네트워크 요청, 콘솔 출력, 예외 던지기 등이 해당합니다. 하지만 모두 없애는 것은 이상적이지 않고 불가능합니다. 화면 출력, DB 저장, 요청 응답 자체가 부수 효과이고, 프로그램이 쓸모 있으려면 결국 외부 세계를 바꿔야 하기 때문입니다. 현실적인 목표는 **부수 효과를 없애는 것이 아니라 격리하고 통제하는 것**입니다. 비즈니스 로직은 순수함수로 만들고, I/O는 바깥 경계에 모으는 구조(Functional Core, Imperative Shell)가 그 예입니다. Haskell도 IO 타입으로 부수 효과를 표시해 분리할 뿐 없애지는 않습니다.
2. **왜 함수형 프로그래밍 매커니즘을 사용한다고 생각하시나요?** — ① **예측 가능성**: 출력이 입력에만 달려 있어 코드만 보고 동작을 추론할 수 있습니다. ② **테스트 용이성**: mock이나 상태 준비 없이 입력과 기대값만 비교하면 됩니다. ③ **동시성 안전**: 공유 가변 상태가 없어 락 없이 병렬 처리가 쉽습니다. 멀티코어 시대에 다시 주목받은 큰 이유입니다. ④ **재사용과 합성**: 작은 함수를 조립해 쓸 수 있습니다. ⑤ **선언형 코드로 의도가 잘 드러납니다.** 다만 불변 객체를 계속 새로 만드는 비용이 있고, 상태가 본질인 문제(게임 루프, 대량 갱신)에는 명령형이 더 자연스러울 수 있어 실무에서는 섞어서 씁니다.
3. **순수함수는 Thread Safe 한가요? 왜 그럴까요?** — 네, **함수 자체는** 스레드 안전합니다. 경쟁 조건은 여러 스레드가 **공유 가변 상태**를 동시에 읽고 쓸 때 생기는데, 순수함수는 외부 상태를 읽거나 쓰지 않고 지역 변수(각 스레드의 스택)만 쓰므로 공유되는 것이 없습니다. 몇 개의 스레드가 동시에 불러도 결과가 같고 서로 간섭하지 않아 락이 필요 없습니다. 단, 전제가 있습니다. 인자로 받은 객체를 **다른 스레드가 동시에 수정**하고 있다면 순수함수라도 그 순간의 일관되지 않은 값을 읽을 수 있습니다. 그래서 불변 데이터와 함께 써야 완전히 안전합니다.
4. **고차함수에 대해 설명해 주세요.** — **함수를 인자로 받거나 함수를 반환하는 함수**입니다. 언어가 함수를 값으로 다룰 수 있는 일급 함수를 지원해야 가능합니다. 예로 `map`, `filter`, `reduce`, `sort(comparator)`가 함수를 인자로 받고, `x -> y -> x + y` 같은 커링이나 `Function.andThen()`처럼 함수를 반환하거나 합성하는 것이 있습니다. Java에서는 `Function<T, R>`, `Predicate<T>` 같은 함수형 인터페이스와 람다로 구현합니다. 공통 흐름(순회, 재시도, 트랜잭션 처리)은 고차함수에 두고 바뀌는 부분만 함수로 넘겨 중복을 줄일 수 있습니다.

**핵심 키워드** → 같은 입력 같은 출력, 부수 효과 없음, 참조 투명성, 불변성, 일급·고차함수, 합성, 부수 효과 격리, 공유 가변 상태 없음

## 면접 직전 확인할 구분

| 헷갈리기 쉬운 개념 | 구분해서 말할 내용 |
|---|---|
| TCP / UDP | 연결·신뢰성·순서·혼잡 제어 / 비연결, 보장 없음, 빠르고 단순 |
| 체크섬 검출 / 정정 | 손상 여부만 확인 / 정정은 재전송(TCP)이나 FEC가 담당 |
| 흐름 제어 / 혼잡 제어 | 수신자 버퍼 보호(rwnd) / 네트워크 보호(cwnd) |
| 네트워크 계층 / 전송 계층 | 호스트 간(IP 주소) / 프로세스 간(포트) |
| 세그먼트 / 패킷 / 프레임 | 4계층 / 3계층 / 2계층 PDU |
| FIN / RST | 정상 종료, 남은 데이터 전송 / 즉시 강제 종료, 데이터 폐기 |
| TIME_WAIT / CLOSE_WAIT | 먼저 끊은 쪽 2MSL 대기 / 상대가 끊었는데 내 앱이 `close()` 안 함 |
