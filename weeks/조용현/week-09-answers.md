## 1. Key (기본키, 후보키, 슈퍼키 등등...) 에 대해 설명해 주세요.

**키는 테이블에서 튜플(행)을 유일하게 식별하거나, 테이블 사이의 관계를 맺기 위해 쓰는 속성(또는 속성의 집합)입니다.**

- **슈퍼키(Super Key)**: 행을 유일하게 식별할 수 있는 속성 집합입니다. **유일성**만 만족하면 되므로 `{학번, 이름}`처럼 불필요한 속성이 섞여 있어도 됩니다.
- **후보키(Candidate Key)**: 슈퍼키 중에서 속성을 하나라도 빼면 유일성이 깨지는, 즉 **유일성과 최소성**을 모두 만족하는 키입니다. `{학번}`, `{주민번호}`가 후보키가 될 수 있습니다.
- **기본키(Primary Key)**: 후보키 중 설계자가 대표로 고른 하나입니다. **NULL을 허용하지 않고 중복될 수 없습니다.**
- **대체키(Alternate Key)**: 기본키로 뽑히지 않은 나머지 후보키입니다. 보통 `UNIQUE` 제약으로 남깁니다.
- **외래키(Foreign Key)**: 다른 테이블(또는 자기 자신)의 기본키나 UNIQUE 키를 참조하는 속성으로, **참조 무결성**을 보장합니다.
- 그 외에 여러 속성을 묶은 **복합키**, 업무 의미가 있는 **자연키**와 의미 없이 만든 일련번호 같은 **대리키(Surrogate Key)** 라는 구분도 씁니다.

포함 관계로 보면 **슈퍼키 ⊇ 후보키 ⊇ 기본키**입니다.

### 꼬리질문 대비

1. **기본키는 수정이 가능한가요?** — 문법적으로는 `UPDATE`로 **수정할 수 있습니다**. 다만 바꾼 값도 NULL이 아니고 중복되지 않아야 하며, 그 키를 참조하는 외래키가 있으면 `ON UPDATE CASCADE`가 없는 한 참조 무결성 위반으로 막힙니다. 실무에서는 **수정하지 않는 것이 원칙**입니다. ① 참조하는 모든 테이블을 같이 바꿔야 하고, ② InnoDB처럼 기본키로 데이터를 정렬해 저장하는 엔진(클러스터드 인덱스)은 행의 물리적 위치가 바뀌며, 모든 보조 인덱스도 기본키 값을 들고 있어 함께 갱신해야 합니다. ③ JPA 같은 ORM도 엔티티 식별자를 바꾸는 것을 허용하지 않습니다. 그래서 바뀔 수 있는 자연키(이메일, 전화번호) 대신 **변하지 않는 대리키**를 기본키로 쓰고, 자연키는 UNIQUE로 두는 경우가 많습니다.
2. **사실 MySQL의 경우, 기본키를 설정하지 않아도 테이블이 만들어집니다. 어떻게 이게 가능한 걸까요?** — InnoDB는 데이터를 반드시 **클러스터드 인덱스** 순서로 저장해야 하므로, 기본키가 없으면 스스로 대신할 키를 정합니다. ① **NOT NULL인 첫 번째 UNIQUE 인덱스**가 있으면 그것을 클러스터드 인덱스로 씁니다. ② 그것도 없으면 사용자에게 보이지 않는 **6바이트 `DB_ROW_ID`** 컬럼을 만들고 이 값으로 `GEN_CLUST_INDEX`라는 숨은 클러스터드 인덱스를 만듭니다. 이 ROW ID는 테이블별이 아니라 **인스턴스 전체에서 공유하는 카운터**라 경합이 생길 수 있고, 쿼리에서 쓸 수 없으며, 복제할 때 행을 식별하기도 어렵습니다. 그래서 기본키는 명시하는 것이 좋습니다. 참고로 MySQL 8.0.30부터는 `sql_generate_invisible_primary_key` 옵션을 켜면 보이지 않는 `my_row_id` 기본키를 자동으로 만들어 줍니다(기본값은 꺼짐).
3. **외래키 값은 NULL이 들어올 수 있나요?** — **들어올 수 있습니다.** 외래키 컬럼에 `NOT NULL`을 따로 걸지 않으면 NULL을 허용하고, NULL은 "아직 참조하는 대상이 없다(관계가 없다)"는 뜻이라 참조 무결성 검사를 하지 않습니다. 예를 들어 `직원.부서ID`가 NULL이면 아직 부서 배정이 안 된 직원입니다. 관계가 필수라면 `NOT NULL`을 함께 겁니다. 복합 외래키는 일부 컬럼만 NULL이어도 기본(MATCH SIMPLE) 동작에서는 검사를 건너뛰므로 주의해야 합니다. 또 `ON DELETE SET NULL`은 부모 행이 지워지면 자식의 외래키를 NULL로 바꾸는 옵션인데, 이것도 외래키가 NULL을 허용해야 쓸 수 있습니다.
4. **어떤 칼럼의 정의에 UNIQUE 키워드가 붙는다고 가정해 봅시다. 이 칼럼을 활용한 쿼리의 성능은 그렇지 않은 것과 비교해서 어떻게 다를까요?** — UNIQUE 제약을 걸면 중복 검사를 위해 **유니크 인덱스가 자동으로 만들어집니다.** ① **조회는 빨라집니다.** 인덱스가 없던 컬럼이라면 풀 스캔이 B+Tree 탐색(O(log N))으로 바뀝니다. 일반 인덱스와 비교해도, 등호 조건이면 값이 하나뿐이라는 것을 옵티마이저가 알기 때문에 **한 건을 찾으면 바로 멈추고**(MySQL 실행 계획의 `const`/`eq_ref`), 조인 순서나 실행 계획을 세울 때도 유리합니다. ② **쓰기는 조금 느려집니다.** INSERT·UPDATE마다 인덱스를 갱신하고 중복 여부를 확인해야 합니다. InnoDB에서 일반 보조 인덱스는 **체인지 버퍼**로 변경을 모아뒀다가 나중에 반영할 수 있지만, 유니크 인덱스는 중복 검사를 위해 해당 페이지를 바로 읽어야 해서 체인지 버퍼를 쓸 수 없습니다. 또 중복 검사 중 공유 잠금이 걸려 동시 삽입이 많으면 경합이나 데드락이 생길 수 있습니다. 정리하면 읽기는 이득, 쓰기는 약간 손해이므로, **진짜로 유일해야 하는 값에만** UNIQUE를 겁니다.

**핵심 키워드** → 유일성·최소성, 슈퍼키 ⊇ 후보키 ⊇ 기본키, 대체키·대리키, 참조 무결성, 클러스터드 인덱스, 숨은 `DB_ROW_ID`(GEN_CLUST_INDEX), FK NULL 허용, 유니크 인덱스 자동 생성·`const` 접근·체인지 버퍼 불가

## 2. RDB와 NoSQL의 차이에 대해 설명해 주세요.

**RDB는 미리 정한 스키마의 테이블에 데이터를 저장하고 SQL과 트랜잭션으로 정합성을 보장하는 DB이고, NoSQL은 관계형 모델을 쓰지 않는 DB를 통칭하는 말로, 유연한 데이터 모델과 수평 확장을 위해 일부 정합성 보장을 덜어낸 경우가 많습니다.**

| 기준 | RDB | NoSQL |
|---|---|---|
| 데이터 모델 | 행·열로 된 테이블, 테이블 간 관계(JOIN) | Key-Value(Redis), Document(MongoDB), Wide-Column(Cassandra), Graph(Neo4j) |
| 스키마 | 고정 스키마, 쓰기 전에 정의(schema-on-write) | 유연한 스키마, 읽을 때 해석(schema-on-read) |
| 정합성 | ACID 트랜잭션 | 제품마다 다름. 많은 경우 BASE·최종 일관성(일부는 ACID 지원) |
| 확장 | 주로 수직 확장(Scale-up), 수평 확장은 샤딩을 직접 설계 | 수평 확장(Scale-out)·샤딩을 기본으로 설계한 경우가 많음 |
| 쿼리 | 표준 SQL, 복잡한 JOIN·집계 | 제품별 API, JOIN이 없거나 제한적 |

데이터 구조가 명확하고 관계와 정합성이 중요하면(주문, 결제, 회원) RDB, 구조가 자주 바뀌거나 대용량 쓰기·단순 조회를 빠르게 처리해야 하면(캐시, 세션, 로그, 피드) NoSQL이 맞습니다.

### 꼬리질문 대비

1. **NoSQL의 강점과, 약점이 무엇인가요?** — **강점**: ① 스키마가 유연해 필드를 추가하거나 문서마다 구조를 다르게 둘 수 있습니다. ② 처음부터 분산을 전제로 만든 제품이 많아 노드를 늘려 **수평 확장**하기 쉽습니다. ③ 함께 읽는 데이터를 한 문서나 한 키에 모아두면 JOIN 없이 한 번에 읽어 특정 접근 패턴에서 매우 빠릅니다. ④ Redis처럼 메모리 기반이면 지연 시간이 매우 짧습니다. **약점**: ① JOIN이 없거나 약해서 관계가 복잡한 데이터는 애플리케이션에서 직접 합쳐야 합니다. ② 데이터를 중복 저장하는 경우가 많아, 원본이 바뀌면 여러 곳을 갱신해야 하고 불일치가 생길 수 있습니다. ③ 여러 문서·노드에 걸친 트랜잭션 지원이 약하거나 비용이 큽니다(MongoDB는 4.0부터 다중 문서 트랜잭션을 지원하지만 성능 비용이 있음). ④ **쿼리 패턴을 먼저 정하고 모델링**해야 해서, 나중에 새로운 조회 요구가 생기면 대응하기 어렵습니다. ⑤ 최종 일관성 모델이면 방금 쓴 값이 바로 안 보일 수 있습니다.
2. **RDB의 어떠한 특징 때문에 NoSQL에 비해 부하가 많이 걸릴 "수" 있을까요?** — "수"가 핵심입니다. 단일 노드의 단순 조회는 인덱스를 탄 RDB도 충분히 빠르고, 접근 패턴에 맞지 않게 쓰면 NoSQL도 느립니다. RDB가 부하를 받기 쉬운 이유는 정합성을 보장하는 장치들 때문입니다. ① **ACID 보장 비용**: 커밋마다 Redo 로그를 디스크에 fsync하고, Undo 로그로 이전 버전을 남기고, 잠금·MVCC로 동시성을 제어합니다. ② **정규화와 JOIN**: 데이터를 여러 테이블로 나눠 저장하므로 읽을 때 JOIN이 필요하고, 데이터가 커지면 JOIN 비용이 커집니다. ③ **제약 조건 검사**: 외래키·UNIQUE·인덱스를 쓰기마다 검사·갱신합니다. ④ **수평 확장의 어려움**: 트랜잭션과 JOIN이 여러 노드에 걸치면 분산 트랜잭션(2PC)이 필요해 비싸므로, 보통 한 대의 쓰기 노드(primary)에 쓰기가 몰립니다. 읽기는 복제본으로 나눌 수 있지만 쓰기 확장이 어렵습니다. 반대로 NoSQL은 이런 보장을 일부 포기하고 키 기준으로 데이터를 나눠 노드끼리 협의할 일을 줄였기 때문에 대량 쓰기에서 유리할 수 있습니다.
3. **NoSQL을 활용한 경험이 있나요? 있다면, 왜 RDB를 선택하지 않고 해당 DB를 선택했는지 설명해 주세요.** — 커뮤니티 서비스 **popping-community**에서 **Redis**를 두 가지 용도로 썼습니다. 게시글·댓글·좋아요 같은 원본 데이터는 그대로 MySQL에 두고, Redis에는 **여러 앱 서버가 함께 봐야 하는 휘발성 데이터**만 올렸습니다.
   - **① HTTP 세션 저장소** — **[문제]** HAProxy 뒤에 App을 2대로 늘렸더니, 세션이 각 Tomcat 메모리에 있어서 한 대가 죽으면 거기 붙어 있던 사용자가 모두 로그아웃됐습니다. 세션을 가진 인스턴스를 내리고 같은 쿠키로 다시 요청하면 `/login`으로 302가 났습니다. HAProxy sticky 쿠키는 문제를 가리고 있었을 뿐이라 함께 제거했습니다. **[왜 Redis인가]** 세션은 세션 ID 하나로 조회하고, 요청마다 읽히며, 30분 뒤에는 사라져야 하는 데이터입니다. RDB에 두면 요청마다 디스크 DB를 거치고 만료 세션을 지우는 작업도 따로 필요한데, Redis는 메모리 기반 Key-Value라 빠르고 **TTL로 만료를 자동 처리**합니다. Spring Session(`@EnableRedisHttpSession`)으로 옮긴 뒤에는 같은 시나리오에서 200이 났습니다. **[트레이드오프와 보완]** ① Redis가 새로운 장애 지점이 됩니다. 기본 명령 타임아웃 60초로는 Redis가 죽었을 때 세션을 쓰는 요청이 1분 넘게 멈춰서, `timeout: 2s`, `connect-timeout: 1s`로 줄여 몇 초 안에 실패하게 했습니다. ② 메모리가 차도 세션이 소리 없이 지워지면 안 되므로 `allkeys-lru` 대신 **`noeviction`** 정책을 쓰고, `maxmemory`를 컨테이너 메모리 한도보다 낮게 잡아 OOM으로 죽기 전에 쓰기를 거부하게 했습니다. ③ Spring Boot 3는 클래스패스에 spring-session-data-redis만 있어도 모든 환경을 Redis 세션으로 바꾸고 `spring.session.store-type`이 없어져 끌 수도 없었습니다. 그래서 자동 설정을 제외하고 `app.session.store=redis`일 때만 켜지게 해서, Redis가 없는 로컬 환경에서는 Tomcat 세션을 쓰게 했습니다.
   - **② 좋아요 실시간 반영(Pub/Sub)** — 각 App이 자기 메모리 안의 STOMP 브로커를 쓰기 때문에, 좋아요 변경이 같은 App에 붙은 사용자에게만 전달됐습니다. App 2대로 측정해 보니 같은 App 시청자에게는 400건 중 400건, 다른 App 시청자에게는 0건이 도착했습니다. 그래서 커밋된 좋아요 변경을 **Redis Pub/Sub 채널**로 발행하고 다른 App이 받아 자기 브로커로 다시 보내게 했습니다. 자기가 보낸 메시지는 origin id로 걸러 무한 루프를 막았습니다. 메시지 큐(Kafka 등)를 따로 두지 않고, 이미 세션용으로 운영 중인 Redis를 재사용한 것이 선택 이유입니다. Pub/Sub은 메시지를 보장하지 않지만, 놓쳐도 사용자가 다시 조회하면 DB의 정확한 값을 받으므로 허용했습니다. 또 Redis가 멈춰도 좋아요 응답이 기다리지 않도록 발행은 크기가 정해진 큐와 백그라운드 스레드 하나로 처리하고, 큐가 차면 버리고 지표로 셌습니다.
   - 정리하면 **"정합성이 중요한 원본은 RDB, 서버끼리 공유해야 하고 잃어도 복구 가능한 휘발성 데이터는 Redis"** 라는 기준으로 나눴습니다. 실제로 Redis는 디스크 저장(RDB 스냅샷·AOF)을 꺼 두었기 때문에, 재시작하면 세션이 사라져 재로그인이 필요하다는 것도 감수한 비용입니다.

**핵심 키워드** → 고정 스키마 vs 유연한 스키마, Key-Value·Document·Wide-Column·Graph, ACID vs BASE·최종 일관성, Scale-up vs Scale-out, 쿼리 패턴 중심 모델링, 데이터 중복, ACID 보장 비용·JOIN·쓰기 노드 집중, Redis TTL·캐시

## 3. 트랜잭션이 무엇이고, ACID 원칙에 대해 설명해 주세요.

**트랜잭션은 DB의 상태를 바꾸는 하나의 논리적 작업 단위로, 그 안의 연산이 모두 성공하면 반영(Commit)하고 하나라도 실패하면 전부 되돌리는(Rollback) 단위입니다.**

계좌 이체는 "A 출금"과 "B 입금"이 함께 성공하거나 함께 실패해야 합니다. 출금만 되고 입금이 안 되면 돈이 사라지므로, 두 연산을 하나의 트랜잭션으로 묶습니다. 트랜잭션은 다음 네 가지 성질을 보장해야 합니다.

- **Atomicity(원자성)**: 전부 반영되거나 전혀 반영되지 않습니다(All or Nothing). **Undo 로그**로 실패 시 되돌립니다.
- **Consistency(일관성)**: 트랜잭션 전후로 DB가 정의된 규칙(제약 조건, "잔액은 음수가 될 수 없다" 같은 무결성)을 만족하는 상태를 유지합니다. DB의 제약 조건과 애플리케이션 로직이 함께 책임집니다.
- **Isolation(격리성)**: 동시에 실행되는 트랜잭션이 서로의 중간 상태를 보지 않고, 따로 실행한 것처럼 동작해야 합니다. 잠금과 **MVCC**로 구현하고, 성능과의 타협으로 **격리 수준**을 고릅니다.
- **Durability(지속성)**: 커밋이 완료된 결과는 시스템이 죽어도 사라지지 않습니다. **Redo 로그(WAL)** 로 보장합니다.

### 꼬리질문 대비

1. **ACID 원칙 중, Durability를 DBMS는 어떻게 보장하나요?** — 핵심은 **WAL(Write-Ahead Logging)** 입니다. 데이터 페이지를 매번 디스크에 쓰면 무작위 쓰기라 느리므로, DBMS는 변경을 메모리(버퍼 풀)에서 하고, 대신 **변경 내용을 로그로 먼저 순차 기록**합니다. ① 커밋 시점에 Redo 로그를 디스크에 **fsync**한 뒤에야 커밋 성공을 응답합니다(MySQL `innodb_flush_log_at_trx_commit=1`이 기본값, PostgreSQL은 WAL). ② 실제 데이터 페이지(dirty page)는 나중에 백그라운드로 디스크에 씁니다. ③ 장애 후 재시작하면 마지막 **체크포인트** 이후의 Redo 로그를 다시 적용(Redo)해 커밋된 변경을 복구하고, 커밋되지 않은 변경은 Undo 로그로 되돌립니다. ④ InnoDB는 페이지를 쓰다 중간에 죽어 페이지가 반쯤 깨지는 문제를 막기 위해 **Doublewrite Buffer**에 먼저 쓰고 실제 위치에 씁니다. ⑤ 디스크 자체가 망가지는 경우까지 대비하려면 **복제(Replication)와 백업**이 필요합니다. 참고로 fsync 설정을 완화하면(값 0이나 2) 성능은 좋아지지만 장애 시 최근 약 1초의 커밋이 유실될 수 있습니다.
2. **트랜잭션을 사용해 본 경험이 있나요? 어떤 경우에 사용할 수 있나요?** — **여러 쓰기 작업이 함께 성공하거나 함께 실패해야 할 때** 씁니다. 예: ① 주문 생성 + 재고 차감 + 결제 내역 저장, ② 계좌 이체의 출금 + 입금, ③ 회원 탈퇴 시 회원 정보와 연관 데이터 삭제, ④ 재고나 좌석처럼 "조회 후 수정"을 동시에 할 때 `SELECT ... FOR UPDATE`로 잠그고 수정하는 경우. Spring에서는 서비스 메서드에 `@Transactional`을 붙이면 프록시가 메서드 시작 시 트랜잭션을 열고, 정상 종료하면 커밋, **RuntimeException**(언체크 예외)이 나면 롤백합니다. 주의할 점은 ① 체크 예외는 기본적으로 롤백하지 않는다(`rollbackFor`로 지정), ② 같은 클래스 안에서 자기 메서드를 호출하면 프록시를 거치지 않아 적용되지 않는다, ③ 트랜잭션 안에서 외부 API 호출처럼 오래 걸리는 작업을 하면 DB 커넥션과 잠금을 오래 잡는다는 것입니다.

   **popping-community에서 쓴 사례**는 세 가지입니다.
   - **좋아요: 행 삽입 + 카운트 증가를 하나로 묶기** — 좋아요는 `likes` 테이블에 행을 넣고, 게시글·댓글의 `like_count`를 1 올리는 두 작업입니다. 둘 중 하나만 반영되면 개수가 틀어지므로 `LikeService` 전체를 `@Transactional`로 묶었습니다. 처음에는 "이미 눌렀는지 조회 → 없으면 INSERT"(check-then-act)라서, 같은 사용자가 동시에 누르면 둘 다 "없음"을 보고 INSERT해 UNIQUE 제약 예외가 터졌습니다. 이를 `INSERT ... ON DUPLICATE KEY UPDATE id = id`로 바꾸고, **실제로 삽입된 행 수가 1일 때만** 카운트를 올리게 했습니다. 동일 사용자 동시 요청 20건에서 예외가 17건에서 0건이 되었고, 행과 카운트가 각각 한 번만 반영되는 것을 확인했습니다. 함정도 있었는데, MySQL Connector/J는 기본으로 "바뀐 행"이 아니라 "찾은 행" 수를 돌려줘서 중복이어도 1이 나옵니다. JDBC URL에 `useAffectedRows=true`를 넣어야 중복일 때 0이 나옵니다.
   - **댓글 작성: 데드락 해결** — 같은 게시글에 댓글을 동시에 쓰면 InnoDB가 트랜잭션 하나를 데드락으로 죽였습니다. 댓글 INSERT의 **외래키 검사가 부모 게시글 행에 공유 잠금(S)** 을 걸고, 두 트랜잭션이 그 뒤 `comment_count`를 바꾸려고 **배타 잠금(X)으로 올리려다** 서로를 기다린 것입니다. 그래서 INSERT 전에 `SELECT ... FOR UPDATE`(`@Lock(PESSIMISTIC_WRITE)`)로 **부모 게시글의 X 잠금을 먼저** 잡게 해, 작성자들이 S→X 업그레이드 경쟁 대신 줄을 서게 했습니다. 이 잠금 메서드는 `Propagation.MANDATORY`로 만들어 **이미 열린 트랜잭션 안에서만** 호출되게 했습니다. 트랜잭션 밖에서 호출되면 잠금이 바로 풀려 수정이 아무 효과 없이 지나가기 때문입니다. 게스트 댓글의 BCrypt 해시도 잠금을 잡기 전에 계산하게 옮겨 잠금 시간을 줄였습니다. 대가는 같은 게시글의 쓰기가 직렬화된다는 것이라 따로 측정했는데, 게시글 하나에 동시 작성자 10·50·100명을 몰았을 때 수정 후에는 초당 약 145건이 성공했고, 수정 전 순서는 시도의 21%(10명)~3~4%만 성공했으며 댓글 수 증가분도 절반가량 사라졌습니다.
   - **커밋 이후에만 하는 작업 분리** — 캐시 무효화는 `@TransactionalEventListener(phase = AFTER_COMMIT)`으로, 쓰기 직후 Primary DB를 읽게 하는 sticky 쿠키는 `TransactionSynchronization.afterCommit()`으로 처리했습니다. 트랜잭션 안에서 캐시를 지우면, 커밋 전에 다른 요청이 옛 데이터를 다시 캐시에 넣을 수 있고, 롤백되면 지울 필요가 없던 캐시를 지우게 되기 때문입니다.
3. **읽기에는 트랜잭션을 걸지 않아도 될까요?** — 단건 조회 하나라면 DB가 어차피 문장마다 자동 커밋 트랜잭션으로 실행하므로 큰 차이가 없습니다. 하지만 **여러 번 읽은 결과가 서로 맞아야 하면** 트랜잭션이 필요합니다. 예를 들어 "주문 목록"과 "주문 총액"을 따로 조회하는데 그 사이에 다른 트랜잭션이 커밋하면 두 결과가 맞지 않을 수 있습니다. 하나의 트랜잭션(REPEATABLE READ 이상)으로 묶으면 같은 스냅샷을 읽어 일관된 결과를 얻습니다. Spring에서는 `@Transactional(readOnly = true)`를 쓰면 추가 이점도 있습니다. ① Hibernate가 플러시를 하지 않고 변경 감지(dirty checking)용 스냅샷을 줄여 메모리·CPU를 아낍니다. ② JDBC 드라이버에 읽기 전용 힌트를 줘 MySQL은 읽기 전용 트랜잭션 최적화를 할 수 있습니다. ③ 라우팅 데이터소스를 쓰면 읽기 전용 트랜잭션을 **복제본(Replica)** 으로 보낼 수 있습니다. popping-community의 Read Replica 실험에서는 `LazyConnectionDataSourceProxy`에 읽기 전용 데이터소스를 지정해, `readOnly = true` 트랜잭션은 Replica로, 쓰기 트랜잭션은 Primary로 가게 했습니다. 다만 재측정에서 처리량 이득이 재현되지 않았고 부하 시 복제 지연이 수백 초까지 커져, 지금은 Replica 읽기를 끄고 라우팅 코드만 남겨 두었습니다. ④ 지연 로딩도 트랜잭션(영속성 컨텍스트) 범위 안에서 동작합니다. 반대로 너무 넓게 잡으면 커넥션을 오래 잡고, 오래 열린 트랜잭션 때문에 Undo 로그를 정리하지 못하는 문제가 생깁니다.

**핵심 키워드** → 논리적 작업 단위, Commit·Rollback, 원자성(Undo)·일관성(제약)·격리성(잠금·MVCC)·지속성(Redo), WAL·fsync·체크포인트·Doublewrite, `@Transactional`·RuntimeException 롤백·자기 호출, 읽기 일관성·`readOnly = true`·복제본 라우팅

## 4. 트랜잭션 격리 레벨에 대해 설명해 주세요.

**격리 수준은 동시에 실행되는 트랜잭션이 서로의 변경을 어디까지 볼 수 있는지 정하는 단계로, 격리가 강할수록 이상 현상은 줄지만 동시성(성능)은 떨어집니다.**

먼저 막아야 할 이상 현상이 세 가지 있습니다.

- **Dirty Read**: 다른 트랜잭션이 **아직 커밋하지 않은** 값을 읽는 것. 그 트랜잭션이 롤백하면 존재하지 않는 값을 읽은 셈이 됩니다.
- **Non-Repeatable Read**: 같은 행을 두 번 읽었는데, 그 사이 다른 트랜잭션이 **수정·커밋**해서 값이 달라지는 것.
- **Phantom Read**: 같은 조건으로 두 번 조회했는데, 그 사이 다른 트랜잭션이 **삽입·삭제**해서 없던 행이 생기거나 있던 행이 사라지는 것.

| 격리 수준 | Dirty Read | Non-Repeatable Read | Phantom Read |
|---|:--:|:--:|:--:|
| READ UNCOMMITTED | 발생 | 발생 | 발생 |
| READ COMMITTED | 방지 | 발생 | 발생 |
| REPEATABLE READ | 방지 | 방지 | 발생 (표준 기준, InnoDB는 대부분 방지) |
| SERIALIZABLE | 방지 | 방지 | 방지 |

예시로, 잔액이 1,000원인 계좌를 T1이 2,000원으로 바꾸고 아직 커밋하지 않았습니다. READ UNCOMMITTED에서 T2는 2,000원을 읽고(Dirty Read), READ COMMITTED부터는 커밋된 1,000원을 읽습니다. T1이 커밋한 뒤 T2가 다시 읽으면 READ COMMITTED에서는 2,000원이 보이고(Non-Repeatable Read), REPEATABLE READ에서는 처음 읽은 스냅샷 그대로 1,000원이 보입니다. 기본값은 **MySQL(InnoDB)이 REPEATABLE READ**, **Oracle·PostgreSQL·SQL Server가 READ COMMITTED**입니다.

### 꼬리질문 대비

1. **모든 DBMS가 4개의 레벨을 모두 구현하고 있나요? 그렇지 않다면 그 이유는 무엇일까요?** — **아닙니다.** ① **Oracle**은 READ COMMITTED와 SERIALIZABLE만 제공합니다(별도로 READ ONLY 모드). ② **PostgreSQL**은 네 가지 이름을 모두 받지만 READ UNCOMMITTED를 지정해도 **READ COMMITTED처럼 동작**하고, REPEATABLE READ는 스냅샷 격리라 표준보다 강해서 팬텀도 생기지 않습니다. 이유는 ① SQL 표준이 각 수준에서 **"허용되는" 이상 현상**만 정했을 뿐, 그보다 강하게 막는 것은 허용하기 때문입니다. ② **MVCC** 기반 DB는 이전 버전을 읽으면 되므로, 커밋되지 않은 값을 읽게 하는 READ UNCOMMITTED를 만들 이유가 없습니다. 읽기가 쓰기를 기다리지 않는다는 이점이 이미 있으니 Dirty Read를 허용해 얻는 성능 이득이 거의 없습니다. ③ 표준의 정의는 잠금 기반 구현을 전제로 해서, Lost Update나 Write Skew 같은 다른 이상 현상을 다 담지 못합니다. 그래서 DB마다 구현 방식에 맞게 수준을 고르고, 같은 이름이라도 동작이 다를 수 있습니다. 실제로 MySQL InnoDB의 REPEATABLE READ는 일반 SELECT는 스냅샷으로, `SELECT ... FOR UPDATE` 같은 잠금 읽기는 **넥스트 키 락(레코드 락 + 갭 락)** 으로 팬텀을 대부분 막지만, 한 트랜잭션 안에서 일반 SELECT와 잠금 읽기를 섞으면 팬텀이 보일 수 있습니다.
2. **만약 MySQL을 사용하고 있다면, (InnoDB 기준) Undo 영역과 Redo 영역에 대해 설명해 주세요.** — **Undo 로그**는 데이터를 바꾸기 **전 값**을 기록합니다. ① 트랜잭션이 롤백하면 이 값으로 되돌리고(원자성), ② 다른 트랜잭션이 아직 커밋되지 않았거나 자기 스냅샷 이후에 바뀐 행을 읽을 때 Undo 로그를 따라가 **이전 버전**을 만들어 보여줍니다(MVCC, 격리성). 각 행에는 마지막으로 바꾼 트랜잭션 ID(`DB_TRX_ID`)와 Undo 로그를 가리키는 포인터(`DB_ROLL_PTR`)가 있어서 버전 체인을 따라갈 수 있습니다. 더 이상 읽을 트랜잭션이 없으면 **Purge 스레드**가 정리하는데, 오래 열린 트랜잭션이 있으면 정리하지 못해 Undo가 계속 커집니다. Undo 로그는 Undo 테이블스페이스에 저장됩니다. **Redo 로그**는 바꾼 **후 값**을 기록합니다. 커밋 시 데이터 페이지 대신 Redo 로그를 디스크에 순차 기록하므로 빠르고, 장애가 나면 이 로그를 다시 적용해 커밋된 변경을 복구합니다(지속성). 고정 크기 파일을 **원형으로 재사용**하며, 체크포인트로 디스크에 반영된 부분은 덮어씁니다(8.0.30부터 `innodb_redo_log_capacity`로 크기 설정). 정리하면 **Undo는 되돌리기와 과거 버전 읽기, Redo는 장애 후 다시 적용하기**를 위한 것입니다. 참고로 복제와 시점 복구에 쓰는 **Binlog**는 InnoDB가 아니라 MySQL 서버 계층의 논리 로그라 Redo와 별개입니다.
3. **그런데, 스토리지 엔진이 정확히 무엇을 하는 건가요?** — 스토리지 엔진은 **데이터를 실제로 디스크·메모리에 저장하고, 읽고, 쓰는 일을 맡는 DBMS의 하위 계층**입니다. MySQL은 구조가 두 층으로 나뉩니다. **MySQL 서버 엔진**(위층)은 접속 관리, SQL 파싱, 옵티마이저, 실행 계획 수립을 하고, **스토리지 엔진**(아래층)은 핸들러 API를 통해 "이 키로 행을 찾아라", "이 행을 써라" 같은 요청을 받아 처리합니다. 그래서 테이블마다 엔진을 다르게 고를 수 있습니다(`ENGINE=InnoDB`). 스토리지 엔진이 정하는 것은 ① 데이터·인덱스의 **저장 구조**(InnoDB는 클러스터드 인덱스), ② **트랜잭션 지원** 여부, ③ **잠금 단위**(InnoDB는 행 단위, MyISAM은 테이블 단위), ④ 장애 복구(Redo·Undo), ⑤ 버퍼 풀 같은 캐시, ⑥ 외래키 지원입니다. InnoDB는 트랜잭션·행 잠금·MVCC·장애 복구를 지원해 MySQL 5.5부터 기본 엔진이고, MyISAM은 트랜잭션이 없고 테이블 잠금이라 지금은 거의 쓰지 않으며, MEMORY 엔진은 메모리에만 저장해 재시작하면 데이터가 사라집니다.

**핵심 키워드** → Dirty Read·Non-Repeatable Read·Phantom Read, RU·RC·RR·SERIALIZABLE, MySQL 기본 RR / Oracle·PostgreSQL 기본 RC, 표준은 허용 하한만 정의, MVCC·스냅샷, 넥스트 키 락, Undo(이전 값·롤백·MVCC·Purge) vs Redo(이후 값·장애 복구·원형 로그), 서버 엔진 vs 스토리지 엔진·핸들러 API

## 5. 정규화가 무엇인가요?

**정규화는 테이블을 함수 종속성에 따라 분해해서 데이터 중복을 줄이고, 삽입·수정·삭제 시 생기는 이상 현상을 없애는 설계 과정입니다.**

함수 종속성 `X → Y`는 "X 값이 정해지면 Y 값이 하나로 정해진다"는 뜻입니다(학번 → 이름). 정규화는 단계별로 나뉩니다.

- **제1정규형(1NF)**: 모든 컬럼 값이 **원자값**입니다. 한 칸에 `"수학, 영어"`처럼 여러 값을 넣지 않습니다.
- **제2정규형(2NF)**: 1NF + **부분 함수 종속 제거**. 기본키가 복합키일 때, 키의 일부에만 종속되는 컬럼을 떼어냅니다.
- **제3정규형(3NF)**: 2NF + **이행 함수 종속 제거**. `A → B → C`처럼 키가 아닌 컬럼을 거쳐 종속되는 컬럼을 떼어냅니다.
- **BCNF**: 3NF보다 강한 조건으로, **모든 결정자가 후보키**여야 합니다.
- 그 위에 다치 종속을 다루는 **4NF**, 조인 종속을 다루는 **5NF**가 있습니다. 실무에서는 보통 3NF나 BCNF까지 합니다.

정규화를 하면 중복이 줄고 무결성을 지키기 쉬워지지만, 테이블이 나뉘어 조회할 때 JOIN이 늘어납니다.

### 꼬리질문 대비

1. **정규화를 하지 않을 경우, 발생할 수 있는 이상현상에 대해 설명해 주세요.** — `수강(학번, 이름, 학과, 과목코드, 과목명, 성적)` 테이블 하나에 모두 넣었다고 하겠습니다. ① **삽입 이상**: 아직 수강 신청을 안 한 신입생은 과목코드가 없어(키의 일부가 NULL) 학생 정보를 넣을 수 없습니다. 원하지 않는 값을 억지로 넣어야만 삽입할 수 있는 문제입니다. ② **갱신 이상**: 한 학생이 과목을 5개 들으면 이름·학과가 5번 중복 저장됩니다. 학과가 바뀌었을 때 일부 행만 고치면 같은 학생의 학과가 행마다 달라지는 **불일치**가 생깁니다. ③ **삭제 이상**: 어떤 과목을 듣는 학생이 한 명뿐인데 그 학생이 수강을 취소해 행을 지우면, 그 **과목 정보까지 함께 사라집니다.** 원인은 모두 서로 다른 주제(학생, 과목, 수강)를 한 테이블에 섞어 중복 저장했기 때문입니다.
2. **각 정규화에 대해, 그 정규화가 진행되기 전/후의 테이블의 변화에 대해 설명해 주세요.** — 위의 수강 예시로 단계별로 보겠습니다.
   - **1NF**: 전: `학생(학번, 이름, 수강과목="수학, 영어")` → 후: 한 칸에 하나의 값만 두도록 `(학번, 과목코드)`마다 한 행으로 나눕니다. 결과는 `수강(학번, 과목코드, 이름, 학과, 학과사무실, 과목명, 성적)`, 기본키 `{학번, 과목코드}`.
   - **2NF**: 이름·학과는 `학번`에만, 과목명은 `과목코드`에만 종속됩니다(키 일부에 종속 = 부분 종속). 전: 위 테이블 하나 → 후: `학생(학번, 이름, 학과, 학과사무실)`, `과목(과목코드, 과목명)`, `수강(학번, 과목코드, 성적)`. 이제 성적만 `{학번, 과목코드}` 전체에 종속됩니다.
   - **3NF**: `학생` 테이블에 `학번 → 학과 → 학과사무실`이라는 이행 종속이 남아 있습니다. 학과가 같은 학생마다 사무실이 중복됩니다. 전: `학생(학번, 이름, 학과, 학과사무실)` → 후: `학생(학번, 이름, 학과)`, `학과(학과, 학과사무실)`.
   - **BCNF**: 3NF를 만족해도 후보키가 아닌 결정자가 있으면 분해합니다. 예시는 다음 꼬리질문에서 설명합니다.
3. **BCNF가 무엇인지 설명하고, 제3정규형과 어떤 차이가 있는지 예시를 들어 설명해 주세요.** — BCNF는 **모든 함수 종속 `X → Y`에서 X가 슈퍼키**여야 한다는 조건입니다. 3NF는 `X → Y`에서 X가 슈퍼키가 아니어도 **Y가 후보키의 일부(주 속성)이면 허용**하는데, BCNF는 이 예외까지 없앱니다. 즉 3NF는 "키가 아닌 컬럼"이 잘못 종속되는 것만 막고, BCNF는 **키를 이루는 컬럼이 다른 컬럼에 종속되는 것**까지 막습니다. 예시로 `특강신청(학생, 과목, 교수)`에서 "학생은 과목마다 교수 한 명에게 듣고, 교수는 한 과목만 가르친다"고 하면 함수 종속은 `{학생, 과목} → 교수`, `교수 → 과목`입니다. 후보키는 `{학생, 과목}`과 `{학생, 교수}`이므로 세 컬럼 모두 주 속성입니다. `교수 → 과목`에서 교수는 슈퍼키가 아니지만, 과목이 주 속성이라 **3NF는 만족**합니다. 하지만 결정자인 교수가 후보키가 아니므로 **BCNF는 위반**입니다. 실제로 "김교수는 DB를 가르친다"는 사실이 수강생 수만큼 중복되고, 수강생이 없으면 이 사실을 저장할 수 없습니다. 분해하면 `교수과목(교수, 과목)`, `수강(학생, 교수)`가 됩니다. 단, BCNF로 분해하면 원래 있던 `{학생, 과목} → 교수` 종속을 한 테이블에서 검사할 수 없게 되는 **종속성 보존 손실**이 생길 수 있어, 3NF에서 멈추는 선택도 합니다.
4. **제3정규형을 만족하는데도 BCNF를 만족하지 못하는 테이블이 있을 수 있나요? 있다면 예시를 들어주세요.** — **있습니다.** 바로 위 `특강신청(학생, 과목, 교수)` 예시가 그렇습니다. 이런 경우는 **후보키가 여러 개이고, 그 후보키들이 서로 겹치는(컬럼을 공유하는) 복합키**일 때 생깁니다. 위 예시에서 두 후보키 `{학생, 과목}`, `{학생, 교수}`가 `학생`을 공유하고, 한 후보키의 일부(교수)가 다른 후보키의 일부(과목)를 결정합니다. 3NF는 결정되는 쪽(과목)이 주 속성이면 허용하므로 통과하지만, BCNF는 결정자(교수)가 슈퍼키가 아니라서 위반입니다. 반대로 후보키가 하나뿐이거나 후보키가 단일 컬럼이면 3NF를 만족할 때 BCNF도 만족합니다.
5. **BCNF까지 정규화하면 모든 이상현상이 사라지나요? 제4, 제5정규형은 어떤 문제를 다루나요?** — **아닙니다.** BCNF는 **함수 종속**에서 오는 이상만 없앱니다. 함수 종속이 아닌 다른 종류의 종속이 남아 있으면 여전히 중복과 이상 현상이 생깁니다. ① **4NF는 다치 종속(MVD)** 을 다룹니다. `X →→ Y`는 X 하나에 Y 값 여러 개가 **다른 컬럼과 무관하게** 대응하는 것입니다. 예: `강좌(강좌, 교수, 교재)`에서 강좌마다 교수 여러 명, 교재 여러 권이 있고 교수와 교재가 서로 상관없다면, 모든 조합을 행으로 저장해야 합니다(교수 2명 × 교재 3권 = 6행). 키가 세 컬럼 전체라 BCNF는 만족하지만, 교재 하나를 추가하면 교수 수만큼 행을 추가해야 합니다. `강좌교수(강좌, 교수)`, `강좌교재(강좌, 교재)`로 나누면 해결됩니다. ② **5NF는 조인 종속(JD)** 을 다룹니다. 두 테이블로는 손실 없이 나눌 수 없지만 **세 개 이상으로 나눴다가 조인하면 원래대로 복원되는** 경우입니다. 예: `공급(공급자, 부품, 프로젝트)`에서 "공급자가 그 부품을 공급하고, 그 프로젝트가 그 부품을 쓰고, 그 공급자가 그 프로젝트에 납품한다면 반드시 그 조합이 존재한다"는 업무 규칙이 있으면, 세 쌍(공급자-부품, 부품-프로젝트, 공급자-프로젝트)으로 나누는 것이 5NF입니다. 실무에서는 4NF·5NF까지 의식적으로 맞추는 경우가 드물고, 보통 설계 단계에서 독립된 다대다 관계를 별도 테이블로 빼면 자연스럽게 해결됩니다.
6. **정규화가 무조건 좋은가요? 그렇지 않다면, 어떤 상황에서 역정규화를 하는게 좋은지 설명해 주세요.** — **무조건 좋지는 않습니다.** 정규화는 쓰기 정합성에 유리하지만 테이블이 잘게 나뉘어 **조회할 때 JOIN이 많아지고**, 데이터가 크면 성능이 떨어집니다. 역정규화(반정규화)는 **읽기 성능을 위해 의도적으로 중복을 허용**하는 것입니다. 적합한 상황은 ① **읽기가 쓰기보다 압도적으로 많고**, 같은 JOIN을 매번 반복할 때(게시글 목록에 작성자 닉네임을 함께 저장), ② **집계 값을 자주 조회**할 때(게시글의 `댓글 수`, `좋아요 수`를 매번 `COUNT` 대신 컬럼으로 저장), ③ 통계·리포트처럼 **과거 시점 값이 필요하거나 실시간 정합성이 덜 중요**할 때(주문 당시의 상품 가격을 주문 테이블에 복사 — 이건 사실 중복이 아니라 별개의 사실), ④ 샤딩해서 테이블이 서로 다른 DB에 있어 **JOIN 자체를 할 수 없을 때**입니다. 대신 중복된 값을 동기화할 책임이 생기므로, 트리거나 애플리케이션 로직, 배치로 맞추고, 동시 갱신 시 카운터 경합 같은 문제도 고려해야 합니다. 순서는 **먼저 정규화하고, 인덱스·쿼리 튜닝·캐시로도 안 될 때 측정한 근거를 가지고 역정규화**하는 것이 원칙입니다. popping-community에서는 댓글 목록을 보여줄 때 좋아요 수 집계와 "내가 눌렀는지" 조회를 `likes` 테이블 쿼리 하나로 처리했는데, 450만 건에서 풀스캔이 일어났습니다. 집계는 `comment` 테이블에 비정규화해 둔 `like_count` 컬럼을 읽고, 개인화 조회는 기존 UNIQUE 인덱스를 타는 별도 쿼리로 나눠 평균 응답시간을 10,460ms에서 167ms로, 에러율을 15.53%에서 0%로 줄였습니다. 그 대신 카운트가 실제 행 수와 어긋날 수 있어서, 좋아요 삽입·삭제와 카운트 변경을 한 트랜잭션으로 묶고 매일 새벽 4시에 실제 행 수와 맞춰 보는 보정 스케줄러(`LikeCountReconcileScheduler`)를 두었습니다.

**핵심 키워드** → 함수 종속, 이상 현상(삽입·갱신·삭제), 1NF 원자값·2NF 부분 종속·3NF 이행 종속·BCNF 모든 결정자가 후보키, 겹치는 복합 후보키, 종속성 보존, 4NF 다치 종속·5NF 조인 종속, 역정규화(읽기 성능, 집계 컬럼, JOIN 불가) + 동기화 책임

## 6. View가 무엇이고, 언제 사용할 수 있나요?

**View는 하나 이상의 테이블에서 원하는 데이터를 SELECT 쿼리로 정의해 둔 가상 테이블입니다. 보통 데이터를 따로 저장하지 않고, View를 조회할 때마다 정의된 쿼리가 실행됩니다.**

```sql
CREATE VIEW active_member AS
SELECT id, name, email FROM member WHERE status = 'ACTIVE';
```

사용하는 경우는 다음과 같습니다.

- **복잡한 쿼리 단순화**: 자주 쓰는 JOIN·집계 쿼리를 View로 만들어 두면 테이블처럼 간단히 조회할 수 있습니다.
- **보안(접근 제어)**: 테이블 전체 대신 필요한 컬럼·행만 보여주는 View에 권한을 줘서, 주민번호·급여 같은 민감한 컬럼을 숨길 수 있습니다.
- **논리적 독립성**: 테이블 구조가 바뀌어도 View 정의만 고치면, View를 쓰는 애플리케이션 쿼리는 그대로 둘 수 있습니다.

단점은 ① View 자체에 인덱스를 만들 수 없고, ② 정의를 바꾸려면 `CREATE OR REPLACE`로 다시 만들어야 하며, ③ View 위에 View를 쌓으면 실제 실행 쿼리가 복잡해져 성능 문제를 찾기 어렵다는 것입니다. 결과를 실제로 저장해 두는 **Materialized View**(Oracle, PostgreSQL 지원, MySQL은 미지원)도 있는데, 조회는 빠르지만 원본이 바뀌면 갱신(REFRESH)해야 합니다.

### 꼬리질문 대비

1. **그렇다면, View의 값을 수정해도 실제 테이블에는 반영되지 않나요?** — **반영됩니다.** View는 데이터를 따로 저장하지 않으므로, View에 `INSERT`·`UPDATE`·`DELETE`를 하면 DBMS가 이를 **원본(base) 테이블에 대한 연산으로 바꿔 실행**합니다. 단, View의 각 행이 원본 테이블의 어느 행인지 **하나로 정확히 대응**할 때만 가능합니다. 다음이 포함되면 수정할 수 없습니다: 집계 함수(`SUM`, `COUNT`), `GROUP BY`·`HAVING`, `DISTINCT`, `UNION`, 계산식으로 만든 컬럼(그 컬럼만 수정 불가), 일부 서브쿼리. JOIN View는 MySQL에서 한 번에 한 테이블의 컬럼만 수정할 수 있는 등 제한이 많습니다. 또 View에 없는 컬럼이 원본에서 NOT NULL이고 기본값이 없으면 View로 INSERT할 수 없습니다. 주의할 점은 View의 `WHERE` 조건을 벗어나는 값으로 바꿀 수도 있다는 것입니다. 위 예시에서 `status`를 `'INACTIVE'`로 바꾸면 그 행은 View에서 사라집니다. 이를 막으려면 `WITH CHECK OPTION`을 붙여 View 조건을 만족하는 변경만 허용합니다. 수정할 수 없는 복잡한 View도 Oracle·SQL Server·PostgreSQL에서는 **INSTEAD OF 트리거**로 원본 테이블에 어떻게 반영할지 직접 정의할 수 있습니다. Materialized View는 저장된 복사본이라 수정해도 원본에 반영되지 않습니다.

**핵심 키워드** → 가상 테이블, 저장된 SELECT, 쿼리 단순화·보안·논리적 독립성, 인덱스 불가, Materialized View·REFRESH, 갱신 가능 View(1:1 대응), 집계·GROUP BY·DISTINCT·UNION 불가, `WITH CHECK OPTION`, INSTEAD OF 트리거

## 7. Schema가 무엇인가요?

**스키마는 데이터베이스의 구조와 제약 조건을 정의한 것, 즉 어떤 데이터를 어떤 형태로 저장하고 어떤 관계와 규칙을 갖는지에 대한 명세입니다.**

테이블 이름, 컬럼 이름과 타입, 기본키·외래키, 제약 조건(NOT NULL, UNIQUE, CHECK), 인덱스, View 등이 스키마에 들어갑니다. 스키마는 **DB의 설계도**라 잘 바뀌지 않고, 특정 시점에 실제로 저장된 데이터는 **인스턴스(상태)** 라고 해서 계속 바뀝니다. 스키마 정보 자체는 DBMS의 **데이터 사전(시스템 카탈로그)** 에 저장됩니다(MySQL의 `information_schema`).

DBMS마다 용어가 조금 다릅니다. **MySQL에서는 스키마와 데이터베이스가 같은 말**이라 `CREATE SCHEMA`와 `CREATE DATABASE`가 동일합니다. PostgreSQL·SQL Server에서는 하나의 데이터베이스 안에 여러 스키마를 두는 **네임스페이스**이고(`public.member`), Oracle에서는 사용자 계정이 소유한 객체 묶음을 스키마라고 합니다.

### 꼬리질문 대비

1. **Schema의 3계층에 대해 설명해 주세요.** — ANSI/SPARC가 제안한 구조로, DB를 보는 관점에 따라 세 단계로 나눕니다. ① **외부 스키마(External, 서브 스키마)**: 사용자나 애플리케이션 **각각이 보는 DB의 모습**입니다. 하나의 DB에 여러 개가 있을 수 있고, 예를 들어 인사팀은 직원 급여까지, 일반 직원은 이름·부서만 봅니다. View가 대표적인 구현입니다. ② **개념 스키마(Conceptual)**: 조직 **전체 관점에서 본 논리적 구조**로, DB에 어떤 테이블·속성·관계·제약 조건·접근 권한이 있는지 정의합니다. DB당 하나이고, 보통 "스키마"라고 하면 이것을 말합니다. ③ **내부 스키마(Internal)**: **물리적 저장 장치 관점**에서 데이터가 실제로 어떻게 저장되는지를 정의합니다. 레코드 구조, 인덱스, 파일 구성, 저장 순서 같은 것입니다. 이렇게 나누는 목적은 **데이터 독립성**입니다. ① **논리적 독립성**: 개념 스키마가 바뀌어도(테이블에 컬럼 추가, 테이블 분리) 외부 스키마와 애플리케이션은 영향을 받지 않습니다(외부/개념 사상). ② **물리적 독립성**: 내부 스키마가 바뀌어도(인덱스 추가, 저장 장치 교체) 개념 스키마는 그대로입니다(개념/내부 사상). 실무에서 물리적 독립성은 잘 지켜지지만, 논리적 독립성은 컬럼 삭제처럼 애플리케이션이 영향을 받는 경우가 많아 상대적으로 지키기 어렵습니다.

**핵심 키워드** → 구조·제약 조건 명세, 스키마 vs 인스턴스, 데이터 사전·`information_schema`, MySQL은 스키마 = 데이터베이스, 외부·개념·내부 스키마, 논리적·물리적 데이터 독립성

## 8. 디자인 패턴이 무엇인지 설명해주고, 대표적인 디자인 패턴에 대해 설명해 주세요.

**디자인 패턴은 소프트웨어 설계에서 반복해서 나타나는 문제에 대해, 검증된 해결 방법을 이름 붙여 정리한 설계 템플릿입니다.** 코드 그 자체가 아니라 클래스와 객체를 어떻게 구성하고 협력시킬지에 대한 구조이고, "여기는 전략 패턴으로 했다"처럼 개발자끼리 설계 의도를 짧게 전달하는 공통 언어 역할도 합니다.

GoF(Gang of Four)는 23개 패턴을 목적에 따라 세 가지로 나눴습니다.

- **생성 패턴**: 객체를 만드는 방법을 감춥니다.
  - **Singleton**: 클래스의 인스턴스를 하나만 만들고 어디서나 그 인스턴스에 접근하게 합니다.
  - **Factory Method**: 객체 생성을 하위 클래스나 별도 메서드에 맡겨, 사용하는 쪽이 구체 클래스를 몰라도 되게 합니다.
  - **Builder**: 매개변수가 많은 객체를 단계별로 만듭니다(Lombok `@Builder`).
- **구조 패턴**: 클래스와 객체를 조합해 더 큰 구조를 만듭니다.
  - **Adapter**: 호환되지 않는 인터페이스를 감싸서 원하는 인터페이스로 바꿉니다(Spring MVC의 `HandlerAdapter`).
  - **Proxy**: 실제 객체 대신 대리 객체를 둬서 접근 제어, 지연 로딩, 부가 기능을 넣습니다(Spring AOP, `@Transactional`, JPA 지연 로딩 프록시).
  - **Decorator**: 객체를 감싸서 기능을 동적으로 덧붙입니다(`BufferedInputStream`).
- **행위 패턴**: 객체 사이의 책임 분배와 통신 방법을 다룹니다.
  - **Strategy**: 알고리즘을 인터페이스로 분리해 실행 중에 바꿔 끼웁니다(할인 정책, `Comparator`).
  - **Template Method**: 전체 흐름은 상위 클래스가 정하고, 일부 단계만 하위 클래스가 구현합니다(`JdbcTemplate`이 비슷한 목적을 콜백으로 해결).
  - **Observer**: 한 객체의 상태 변화를 구독자들에게 알립니다(이벤트 리스너, Spring `ApplicationEvent`).

패턴은 목적이 아니라 수단이므로, 문제가 없는데 패턴을 먼저 적용하면 오히려 코드가 복잡해집니다.

### 꼬리질문 대비

1. **Singleton의 장단점에 대해 설명해 주세요.** — **장점**: ① 인스턴스를 한 번만 만들어 **메모리와 생성 비용을 아낍니다.** DB 커넥션 풀, 설정 정보, 로거, 캐시처럼 여러 개일 필요가 없고 만들기 비싼 객체에 적합합니다. ② 어디서나 같은 인스턴스에 접근해 **데이터를 공유**하기 쉽습니다. **단점**: ① **전역 상태**가 되어, 어디서 바뀌었는지 추적하기 어렵고 클래스 간 결합도가 높아집니다. ② 사용하는 쪽이 `Singleton.getInstance()`로 **구체 클래스에 직접 의존**하므로 DIP·OCP를 위반하기 쉽습니다. ③ 생성자가 private이라 상속하기 어렵고, 테스트할 때 **목(mock) 객체로 바꾸기 어렵고**, 테스트 사이에 상태가 남아 서로 영향을 줍니다. ④ 여러 스레드가 공유하므로 **상태(가변 필드)를 두면 동시성 문제**가 생깁니다. 그래서 싱글톤은 상태 없이(stateless) 만드는 것이 원칙입니다. ⑤ 멀티스레드 환경에서 하나만 생성되도록 보장하는 구현 자체가 까다롭습니다. Spring은 이 단점을 **싱글톤 컨테이너**로 해결합니다. 개발자가 private 생성자나 `getInstance()`를 쓰지 않고 평범한 클래스를 만들면, 컨테이너가 빈을 하나만 만들어 **DI로 주입**하므로 인터페이스에 의존할 수 있고 테스트에서 쉽게 바꿀 수 있습니다. 다만 상태를 두면 안 된다는 점은 똑같습니다.
2. **Singleton이 하나의 객체를 생성한다는 것을 어떻게 보장할 수 있을까요?** — 기본은 **생성자를 `private`으로 막고, 클래스 안의 `static` 필드에 하나만 만들어 두는 것**입니다. 문제는 **멀티스레드**입니다. `if (instance == null) instance = new Singleton();`처럼 늦게 만들면, 두 스레드가 동시에 null을 보고 둘 다 생성할 수 있습니다. 해결 방법은 다음과 같습니다.
   - **Eager Initialization**: `private static final Singleton INSTANCE = new Singleton();` 클래스가 초기화될 때 JVM이 한 번만, 스레드 안전하게 실행합니다. 간단하지만 쓰지 않아도 만들어집니다.
   - **`synchronized` 메서드**: 안전하지만 생성 후에도 매번 잠금을 잡아 느립니다.
   - **Double-Checked Locking**: null 검사 → `synchronized` 블록 → 다시 null 검사. 이때 필드에 **`volatile`** 이 반드시 필요합니다. 없으면 객체 생성(메모리 할당 → 생성자 실행 → 참조 대입)이 재정렬되어, 다른 스레드가 생성자가 끝나지 않은 객체를 볼 수 있습니다.
   - **Lazy Holder(Bill Pugh)**: 내부 `static class Holder { static final Singleton INSTANCE = new Singleton(); }`를 두고 `getInstance()`에서 `Holder.INSTANCE`를 반환합니다. Holder 클래스는 처음 참조될 때 초기화되고, **JVM의 클래스 초기화는 스레드 안전**하므로 잠금 없이 지연 생성과 안전성을 모두 얻습니다. 가장 많이 권장되는 방법입니다.
   - **Enum Singleton**: `enum Singleton { INSTANCE; }` JVM이 enum 상수를 하나만 만들도록 보장하고, **리플렉션으로 생성자를 호출하는 공격과 직렬화·역직렬화로 새 객체가 생기는 문제까지 막아줍니다.** 『Effective Java』가 권하는 방법이지만 다른 클래스를 상속할 수 없습니다.
   다른 방법에서는 리플렉션으로 private 생성자를 호출할 수 있으므로 생성자에서 이미 인스턴스가 있으면 예외를 던지고, 직렬화를 쓴다면 `readResolve()`에서 기존 인스턴스를 반환해야 합니다. 그리고 이 보장은 **하나의 클래스 로더 안에서**만 성립합니다. 클래스 로더가 다르면 같은 클래스라도 따로 로딩되어 인스턴스가 여러 개 생길 수 있습니다.

**핵심 키워드** → 반복되는 문제의 검증된 해결책, 공통 언어, GoF 생성·구조·행위, Singleton·Factory·Builder·Adapter·Proxy·Decorator·Strategy·Template Method·Observer, 전역 상태·DIP 위반·테스트 어려움·stateless, Spring 싱글톤 컨테이너, private 생성자, DCL + `volatile`, Lazy Holder, Enum(리플렉션·직렬화 방어), 클래스 로더 단위

## 9. static 키워드는 어떤 의미를 갖나요? (본인이 사용하는 언어에서 없다면 패스...)

**Java에서 `static`은 그 멤버가 객체(인스턴스)가 아니라 클래스에 속한다는 뜻입니다.** 그래서 객체를 만들지 않고 `클래스명.멤버`로 쓸 수 있고, 모든 인스턴스가 하나를 공유합니다.

- **static 변수(클래스 변수)**: 클래스가 로딩될 때 한 번 만들어지고 모든 인스턴스가 공유합니다. 인스턴스 수를 세는 카운터나 상수에 씁니다.
- **static 메서드**: 객체 없이 호출하며, `this`가 없으므로 **인스턴스 변수·메서드에 직접 접근할 수 없습니다.** 상태가 필요 없는 유틸리티(`Math.max()`, `Collections.sort()`)나 정적 팩토리 메서드(`List.of()`)에 씁니다. 또 오버라이딩되지 않고, 같은 시그니처를 하위 클래스에 만들면 숨김(hiding)이 됩니다.
- **static 블록**: 클래스가 초기화될 때 한 번 실행되어 static 변수를 복잡하게 초기화할 때 씁니다.
- **static 중첩 클래스**: 바깥 클래스의 인스턴스 없이 만들 수 있고, 바깥 인스턴스 참조를 들고 있지 않아 메모리 누수 위험이 적습니다(Builder, Lazy Holder).
- **static import**: `import static java.lang.Math.*;`로 클래스 이름 없이 쓸 수 있습니다.

주의할 점은 static 변수가 **클래스가 언로딩될 때까지 살아 있어** 큰 컬렉션을 담으면 메모리 누수가 되기 쉽고, 여러 스레드가 공유하므로 **가변 static 변수는 동시성 문제**를 일으키며, 전역 상태라 테스트하기 어렵다는 것입니다.

### 꼬리질문 대비

1. **컴파일 할 때, static 키워드가 붙은 변수, 함수는 어떻게 처리되나요?** — Java 기준으로 단계별로 보면, ① **컴파일 시점**: `javac`는 static 필드와 메서드에 `ACC_STATIC` 플래그를 붙여 `.class` 파일에 기록하고, static 변수 초기화 코드와 static 블록을 소스 순서대로 모아 **`<clinit>`(클래스 초기화 메서드)** 라는 특별한 메서드로 만듭니다. static 메서드 호출은 **`invokestatic`** 명령어로 컴파일되는데, 객체 타입을 볼 필요가 없으므로 어떤 메서드를 호출할지 **컴파일 시점에 정해집니다(정적 바인딩).** 인스턴스 메서드는 `invokevirtual`로 실행 시점에 실제 객체 타입을 보고 정합니다. 또 `static final`이면서 **컴파일 시점에 값이 정해지는 상수**(기본형이나 String 리터럴, 예: `static final int MAX = 10`)는 컴파일러가 사용하는 곳에 **값을 직접 복사(인라이닝)** 합니다. 그래서 상수 값을 바꾸고 상수를 정의한 클래스만 다시 컴파일하면, 그 상수를 쓰는 다른 클래스는 옛 값을 그대로 가지고 있을 수 있습니다. ② **실행 시점**: 클래스는 처음 사용될 때 로딩되고, 준비(Preparation) 단계에서 static 변수에 메모리를 할당하고 기본값(0, null)을 넣은 뒤, 초기화(Initialization) 단계에서 `<clinit>`을 **한 번, 스레드 안전하게** 실행합니다. 클래스 메타데이터와 메서드 코드는 **Metaspace**에 있고, static 변수 값은 Java 8부터 그 클래스의 `Class` 객체와 함께 **힙**에 있습니다(Java 7 이전에는 PermGen). 참고로 C/C++에서 `static`은 의미가 달라서, 전역 변수·함수에 붙이면 **그 파일 안에서만 보이게(내부 링크)** 하고, 지역 변수에 붙이면 함수가 끝나도 값이 유지되며 **데이터 영역**(초기값이 있으면 `.data`, 없으면 `.bss`)에 할당됩니다.
2. **Java에서 static과 static final은 어떤 차이를 갖나요? final과 static final은요?** — 두 키워드는 축이 다릅니다. `static`은 **어디에 속하는가**(클래스냐 인스턴스냐), `final`은 **다시 대입할 수 있는가**입니다. ① **`static` vs `static final`**: `static`은 클래스에 하나뿐이지만 값을 언제든 바꿀 수 있는 공유 변수입니다(가변이라 동시성 주의). `static final`은 클래스에 하나뿐이고 **한 번 초기화하면 다시 대입할 수 없어**, 보통 상수(`static final int MAX_SIZE = 100;`, 대문자 스네이크 표기)로 씁니다. 선언할 때나 static 블록에서 반드시 초기화해야 합니다. ② **`final` vs `static final`**: `final` 인스턴스 변수는 다시 대입할 수 없지만 **인스턴스마다 따로 존재**하므로, 생성자에서 객체마다 다른 값을 넣을 수 있습니다(예: 객체마다 다른 `id`, 생성자 주입으로 받은 의존성). `static final`은 **모든 인스턴스가 하나의 값을 공유**하므로, 모든 객체에서 같은 값이라면 `static final`로 만들어 메모리 중복을 막습니다. 공통 주의점은 `final`이 **참조 재할당만 막을 뿐 객체 내부는 바꿀 수 있다**는 것입니다. `static final List<String> LIST = new ArrayList<>();`는 `LIST.add()`가 가능하므로, 진짜 불변으로 만들려면 `List.of()`처럼 불변 컬렉션을 씁니다. 또 앞 질문처럼 컴파일 시점 상수인 `static final`만 인라이닝됩니다.

**핵심 키워드** → 클래스 소속·공유, 객체 없이 호출, `this` 없음·인스턴스 멤버 접근 불가, 오버라이딩 불가(hiding), static 블록·중첩 클래스·import, `<clinit>`·`invokestatic`·정적 바인딩, 컴파일 시점 상수 인라이닝, 클래스 초기화 한 번·스레드 안전, Metaspace·힙, C의 내부 링크·데이터 영역, static(소속) vs final(재대입 금지), 참조 불변 ≠ 객체 불변
